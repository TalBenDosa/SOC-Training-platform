Section 1 of 8

What a firewall is and how it decides

Match each connection against an ordered rulebase, then allow or deny.

HACKTHESOCLesson 74Firewall fundamentals6 / 40

Every rule matches on the five-tuple

The checkpoint between trusted internal network and untrusted internet.

  • Source IPWhere the traffic is coming from.
  • Destination IPWhere it is going.
  • Source and destination portWhich service is involved, e.g. 443 is HTTPS, 22 is SSH.
  • ProtocolTCP, UDP, and so on.

"Allow TCP to port 443 from the internal network" lets users browse. "Deny all inbound to 3389" blocks external RDP.

A rule says: traffic matching these properties is allowed or denied. Everything else in the lesson builds on this model.
HACKTHESOCLesson 74Firewall fundamentals7 / 40

Two principles every analyst must know

Rules are evaluated in order

Usually the first matching rule wins, so changing rule order changes behaviour.

Default deny

A well-configured firewall ends with an implicit rule that blocks anything not explicitly allowed. You decide what is permitted; everything else is refused.

A blocked connection in the log may simply be traffic that matched no allow rule.

Default deny is the opposite of allowing everything and blocking known-bad. It is key to reading logs correctly.

Section 2 of 8

Stateless, stateful, and next-generation firewalls

How deeply a firewall understands traffic decides what it can catch.

HACKTHESOCLesson 74Firewall fundamentals9 / 40

Three generations, three depths of inspection

Packet filter (stateless)

Checks each packet in isolation against the five-tuple. Fast, but cannot easily tell a real reply from an unsolicited packet crafted to look like one.

  • Guard checks badges, remembers nothing

Stateful inspection

Tracks connection state. Permits the matching reply to an allowed outbound request, still blocks unsolicited inbound. The norm for decades.

  • Guard remembers who they let in

Next-generation (NGFW)

Adds application-awareness and deeper inspection: identifies the app, inspects content, uses threat intel, often decrypts traffic.

  • Can tell malware on 443 from browsing
Because stateful firewalls track replies, you write rules for the initiating direction only. Attackers hide inside allowed ports; that is why NGFW depth matters.
HACKTHESOCLesson 74Firewall fundamentals10 / 40

Network firewalls and host firewalls see different things

Network firewall

Guards the boundary between whole networks, protecting the organisation at its edge. Shows traffic crossing the perimeter.

Host-based firewall

Runs on one machine: Windows Defender Firewall, or iptables/nftables on Linux. Can contain a compromised machine or reveal local connection attempts.

Know which kind produced a log: a stateless device sees less than a stateful one, and an NGFW may give application-level detail.

This tells you how much to trust a log line and what it could possibly have seen.

Section 3 of 8

NGFW deep inspection: IPS and TLS decryption

The two engines that let an NGFW see attacks hiding inside allowed traffic.

HACKTHESOCLesson 74Firewall fundamentals12 / 40

Permitted and safe are two separate questions

App-ID

Answers what application is this traffic? This is SMB, this is web-browsing.

IPS

Answers does this traffic contain a known exploit attempt, regardless of application? Exploit signatures, malformed protocol fields, known-bad byte sequences tied to CVEs.

A rule can correctly allow SMB between two servers while IPS blocks an EternalBlue (MS17-010) exploit riding inside it.

IPS works inline in real time: it can drop the packet, reset the connection, or block the source.
HACKTHESOCLesson 74Firewall fundamentals13 / 40

How TLS inspection works

Without decryption, an NGFW on HTTPS sees little more than destination IP, port 443 and the SNI hostname.

  1. 1Terminate client TLSThe firewall acts as a trusted man-in-the-middle by design.
  2. 2Decrypt and inspectPlaintext goes through the full stack: app-ID, IPS, antivirus, DLP.
  3. 3Re-encrypt and forwardA second TLS connection to the real destination.
  4. 4Trusted root CA on endpointsThe firewall's CA certificate is installed on every managed endpoint, so re-signed traffic raises no browser warnings.
Also called SSL decryption or SSL forward proxy. Most modern traffic is TLS, which blinds every engine until it is decrypted.
HACKTHESOCLesson 74Firewall fundamentals14 / 40

TLS inspection has real trade-offs

  • Performance costDecrypting and re-encrypting every connection is computationally expensive at scale.
  • Privacy and complianceDecrypting healthcare or banking portals can violate policy or regulation, so sensitive categories are usually excluded.
  • Broken pinningApps that pin one specific certificate fail, since they will not trust the firewall's re-signed certificate.
When you see no decryption on some traffic, it may be a deliberate exclusion, not a misconfiguration.
HACKTHESOCLesson 74Firewall fundamentals15 / 40

The payoff: an IPS block inside decrypted traffic

  • app=web-browsing on 443: allowed traffic by policy
  • decrypted=yes: IPS could only see Log4j because TLS was opened
  • action=reset-both: the IPS killed the connection inline
One log line wrapped for readability. Without decryption this would have been an unremarkable allowed HTTPS connection.

Section 4 of 8

Firewall rules in practice across platforms

Same five-tuple-plus-action idea, different syntax.

HACKTHESOCLesson 74Firewall fundamentals17 / 40

Linux: iptables and nftables

  • Append (-A) to INPUT, TCP, from any source, to port 3389 (RDP), DROP
  • Second rule allows outbound HTTPS to the internal 10.0.0.0/8 range
  • nftables is the modern replacement: same idea, newer syntax
iptables is classic and still widely deployed. nftables is the direction of the trend across the industry.
HACKTHESOCLesson 74Firewall fundamentals18 / 40

Windows Firewall with netsh

  • dir=in: direction
  • action=block, protocol=TCP, localport=3389: action, protocol, port
The host-based firewall from section 2, with the Windows command shape. Wrapped with the cmd caret to fit.
HACKTHESOCLesson 74Firewall fundamentals19 / 40

An enterprise NGFW rulebase, read top to bottom

#SourceDestinationService / Action
1Internal_NetAnyHTTPS / Allow
2AnyDMZ_WebHTTP/S / Allow
3AnyAnyRDP / Deny
4AnyAnyAny / Deny (default)

Always read four things: direction, matched traffic, action, and the rule's position in the order.

Conceptually Palo Alto or Check Point style. Rule 4 is the default-deny catch-all silently blocking anything above did not address.

Security zones, the DMZ, and NAT/PAT

Zone-to-zone policy, an isolated public segment, and address rewriting.

HACKTHESOCLesson 74Firewall fundamentals21 / 40

Zones keep large rulebases readable

Rules become zone-to-zone policies: from this zone, to that zone, this service, this action.

Trust

The internal network.

Untrust

The internet.

DMZ

Isolated segment for public-facing servers: web server, mail relay, public DNS. Reachable from the internet, never directly into internal systems.

DMZ servers are the most exposed and most likely to be compromised, so isolation stops an attacker pivoting straight inward.
HACKTHESOCLesson 74Firewall fundamentals22 / 40

One rule enforces the DMZ's isolation

#Src zoneDst zoneService / Action
1UntrustDMZHTTPS (443) / Allow
2DMZTrustAny / Deny
3TrustUntrustHTTPS (443) / Allow
4AnyAnyAny / Deny (default)
Rule 2 is defense in depth in a single rule: a compromised DMZ web server cannot simply walk into the internal network.
HACKTHESOCLesson 74Firewall fundamentals23 / 40

Three kinds of address translation

NAT

Rewrites source or destination IP as packets cross. Usually private RFC 1918 addresses (e.g. 10.0.0.0/8) to a public, routable one.

PAT (NAT overload)

Also rewrites the source port, so a whole organisation shares one public IP and replies route back to the right host.

DNAT (port forwarding)

Maps a public IP and port to an internal server, letting outsiders reach a service that only has a private address.

PAT is the near-universal form for outbound internet access. It is why a single public IP can serve an entire office.
HACKTHESOCLesson 74Firewall fundamentals24 / 40

NAT in iptables, and the log-search trap

  • Rules and logs may reference pre-NAT or post-NAT addresses, by platform
  • Many logs record both: xlatesrc and xlatedst
  • Search for the internal IP when only the public IP was logged: you find nothing
Correlate pre- and post-NAT addresses when pivoting between firewall logs and internal endpoint telemetry.

Section 6 of 8

Ingress, egress, and why outbound matters

The less obvious direction is often the more valuable one.

HACKTHESOCLesson 74Firewall fundamentals26 / 40

Inbound tells you who is knocking

Ingress (inbound)

Keeps attackers out by blocking unsolicited connections to management ports, databases and file shares. Exposing RDP (3389) to the internet is the classic dangerous misconfiguration.

Egress (outbound)

Controls what leaves. Frequently neglected, since many organisations allow almost all outbound, yet once an attacker is inside, their activity shows up as outbound traffic.

Common beginner mistake: focusing only on inbound.
HACKTHESOCLesson 74Firewall fundamentals27 / 40

Everything an intruder does crosses the firewall outbound

  1. 1Command and control (C2)Malware reaches out to the attacker's server for instructions.
  2. 2Data exfiltrationStolen data flows out to somewhere the attacker controls.
  3. 3Downloading toolsMore payloads are pulled in, initiated by an outbound request.

If hosts may only reach approved destinations and ports, C2 to an unknown server is blocked or at least logged as an anomaly.

This is why egress filtering is such a powerful control.
HACKTHESOCLesson 74Firewall fundamentals28 / 40
Outbound denials and anomalies often tell you who is already inside and trying to phone home.

The firewall is a detector of insiders reaching out, not just a wall against outsiders reaching in.

This reframing is what turns firewall logs into a live investigation tool rather than a passive barrier.

Reading firewall logs as an analyst

Turn the silent barrier into a rich source of evidence.

HACKTHESOCLesson 74Firewall fundamentals30 / 40
At this time, traffic from this source to this destination on this port was allowed or denied by this rule.

Every entry carries the action, the five-tuple, a timestamp, and often the matched rule, the direction and bytes transferred.

Teach students to assemble every log line into this sentence before interpreting it.
HACKTHESOCLesson 74Firewall fundamentals31 / 40

What analysts hunt for in firewall logs

PatternWhat it suggests
Denied inbound bursts across many ports from one sourcePort scanning: mapping what is exposed
Outbound to known-bad IP, new domain, odd country or portC2 or exfiltration
Unusually large outbound volume from one hostData exfiltration
Workstation to internet on odd port, or scanning peersShould never happen; possible lateral movement
Allowed traffic reaching management portsRisky services that should be restricted
The outbound rows are where egress visibility pays off.
HACKTHESOCLesson 74Firewall fundamentals32 / 40

One source among several: the classic C2 pivot

  1. 1Firewall logA workstation beacons to an external IP every few minutes.
  2. 2Endpoint telemetryThe process tree shows which process makes the connection.
  3. 3Threat intelligenceConfirms whether the destination is known-bad.

The firewall is both a control (it blocks) and a sensor (it records allowed traffic too).

On its own a firewall log shows that a connection happened. Combined with EDR and intel it becomes conclusive.

Worked example: catching C2 beaconing

The most important line was one the firewall was happy to allow.

HACKTHESOCLesson 74Firewall fundamentals34 / 40

A top-talkers flag on 10.14.22.108

  • Every line is action=allow: no deny-based alert ever fired
  • Same destination, same port, almost exactly every five minutes
  • Near-identical byte counts: 1204, 1198, 1211
Ask the class what is wrong here before revealing: the shape, not the content.
HACKTHESOCLesson 74Firewall fundamentals35 / 40

From allowed traffic to verdict

  1. 1Notice the shapeFlat, mechanically regular beaconing, not the bursty, irregular pattern of a person browsing.
  2. 2Check reputation91.203.5.14: no business association, hosting registered weeks ago, reported as C2 for a known malware family.
  3. 3Pivot to the endpointEDR shows windowless PowerShell making the connections, parent a Word document from an email attachment.
  4. 4VerdictTextbook C2 beacon: fixed interval, destination and size, from PowerShell hanging off a phishing document.
A defender only watching for denials would never see this. Read the log as evidence, not as a pass/fail control.

Key takeaways

  1. 01A firewall matches each connection's five-tuple against an ordered rulebase; first match wins and default deny blocks the rest.
  2. 02Stateless filters check packets alone, stateful firewalls track connections, NGFWs add app-ID, IPS and TLS decryption.
  3. 03iptables, nftables, netsh and NGFW tables all express direction, matched traffic, action and rule order.
  4. 04Zones and the DMZ isolate exposed servers; NAT means logs may hold pre- or post-NAT addresses.
  5. 05Egress is the under-used, high-value control: C2, exfiltration and tool downloads all cross outbound.
  6. 06The firewall is a sensor too: fully allowed traffic can reveal C2 beaconing by interval, destination and size.

Check your understanding, question 1 of 3

Many organisations focus their firewall effort on inbound rules. Why is egress (outbound) filtering such a valuable detection control?

After a foothold, C2, stolen data and tool downloads all flow outbound, so watching what leaves catches what inbound rules never see. Exploits arrive inbound, stateful tracking is not created by egress rules, and inbound denials still show who is knocking.

Check your understanding, question 2 of 3

Rulebase, top to bottom: (1) Any to Any, any service, Allow; (2) Internal_Net to Any, HTTPS, Allow; (3) Any to Any, RDP, Deny; (4) default Deny. An external host tries RDP to an internal server. What happens?

Rules are evaluated in order and the first match usually wins. Rule 1 matches the RDP attempt, so rule 3 is never reached. Position decides, not specificity, and the default deny only catches traffic no rule above matched.
