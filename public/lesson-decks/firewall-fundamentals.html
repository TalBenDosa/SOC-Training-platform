What a firewall is and how it decides

Match each connection against an ordered rulebase, then allow or deny.

HACKTHESOCLesson 74Firewall fundamentals6 / 63

HACKTHESOCLesson 74Firewall fundamentals7 / 63

Every rule matches on the five-tuple

The checkpoint between trusted internal network and untrusted internet.

  • Source IPWhere the traffic is coming from.
  • Destination IPWhere it is going.
  • Source and destination portWhich service is involved, e.g. 443 is HTTPS, 22 is SSH.
  • ProtocolTCP, UDP, and so on.
Source port plus destination port make the five: source IP, destination IP, source port, destination port, protocol.
HACKTHESOCLesson 74Firewall fundamentals8 / 63

Turning a plain-English rule into the five-tuple

Rule partAllow internal web browsingBlock external RDP
SourceThe internal networkAnywhere outside
DestinationAnyInternal hosts
Protocol / portTCP 443 (HTTPS)TCP 3389 (Remote Desktop)
ActionAllowDeny
"Allow TCP to port 443 from the internal network" lets users browse. "Deny all inbound to 3389" blocks external RDP. Same structure, opposite actions.
HACKTHESOCLesson 74Firewall fundamentals9 / 63

What happens to one connection, step by step

  1. 1Read the propertiesThe firewall takes the connection's source, destination, ports and protocol.
  2. 2Compare with rule 1If every field of rule 1 matches, its action is applied and checking stops.
  3. 3Otherwise, go down the listRule 2, rule 3, and so on, in order. Usually the first match wins.
  4. 4No rule matchedThe implicit default-deny rule at the bottom blocks the connection.
  5. 5Record the decisionThe log keeps the action, the five-tuple, the time and often the rule.
Because the first match wins, moving a broad allow above a specific deny silently disables the deny. Rule order is behaviour.
HACKTHESOCLesson 74Firewall fundamentals10 / 63

Two principles every analyst must know

Rules are evaluated in order

Usually the first matching rule wins, so changing rule order changes behaviour.

Default deny

A well-configured firewall ends with an implicit rule that blocks anything not explicitly allowed. You decide what is permitted; everything else is refused.

A blocked connection in the log may simply be traffic that matched no allow rule.

Default deny is the opposite of allowing everything and blocking known-bad. It is key to reading logs correctly.

Section 2 of 8

Stateless, stateful, and next-generation firewalls

How deeply a firewall understands traffic decides what it can catch.

HACKTHESOCLesson 74Firewall fundamentals12 / 63

Three generations, three depths of inspection

Packet filter (stateless)

Checks each packet in isolation against the five-tuple. Fast, but cannot easily tell a real reply from an unsolicited packet crafted to look like one.

  • Guard checks badges, remembers nothing

Stateful inspection

Tracks connection state. Permits the matching reply to an allowed outbound request, still blocks unsolicited inbound. The norm for decades.

  • Guard remembers who they let in

Next-generation (NGFW)

Adds application-awareness and deeper inspection: identifies the app, inspects content, uses threat intel, often decrypts traffic.

  • Can tell malware on 443 from browsing
Each generation adds to the one before. An NGFW is still stateful underneath.
HACKTHESOCLesson 74Firewall fundamentals13 / 63

How a stateful firewall remembers a connection

  1. 1Outbound request allowedAn internal host opens a connection that a rule permits, for example HTTPS out.
  2. 2Connection rememberedThe firewall records that connection as open.
  3. 3Reply recognisedReturn traffic that belongs to the remembered connection is let back in automatically.
  4. 4Unsolicited inbound stoppedA packet that belongs to no remembered connection still has to match an inbound rule, so it is blocked.
This is why you write rules for the initiating direction only and trust the firewall with the replies.
HACKTHESOCLesson 74Firewall fundamentals14 / 63

What each generation can and cannot catch

SituationStatelessStatefulNGFW
Allowed outbound browsingAllowedAllowedAllowed, app identified
Packet crafted to look like a replyMay slip throughBlocked: no open connectionBlocked
Malware talking out over 443Looks like web trafficLooks like web trafficOften told apart by behaviour and content
Exploit inside an allowed serviceNot seenNot seenSeen by IPS, if it can read the bytes
Attackers hide inside allowed ports. That single fact is why NGFW depth matters to a SOC.
HACKTHESOCLesson 74Firewall fundamentals15 / 63

Network firewalls and host firewalls see different things

At the boundary

Network firewall

Guards the boundary between whole networks, protecting the organisation at its edge. Shows traffic crossing the perimeter, and nothing that stays inside one segment.

On one machine

Host-based firewall

Windows Defender Firewall, or iptables/nftables on Linux. Can contain a compromised machine by blocking its own outbound and lateral traffic, and reveals local connection attempts a perimeter device never sees.

Containment works because the host firewall filters the machine's own traffic before it reaches any network device.
HACKTHESOCLesson 74Firewall fundamentals16 / 63
Know which firewall wrote the log before you trust what it says.

A stateless device sees less than a stateful one, an NGFW may add application detail, and a perimeter device never sees traffic between two internal hosts.

When a log seems to be missing something, first ask whether that device could ever have seen it.

Section 3 of 8

NGFW deep inspection: IPS and TLS decryption

The two engines that let an NGFW see attacks hiding inside allowed traffic.

HACKTHESOCLesson 74Firewall fundamentals18 / 63

Permitted and safe are two separate questions

What is it?

App-ID

Answers what application is this traffic? This is SMB, this is web-browsing.

Is it an attack?

IPS

An Intrusion Prevention System answers does this traffic contain a known exploit attempt, regardless of application?

A rule can correctly allow SMB between two servers while IPS blocks an EternalBlue (MS17-010) exploit riding inside it.

IPS turns 'this connection is permitted' and 'this connection is safe' into two separate, both-necessary questions.
HACKTHESOCLesson 74Firewall fundamentals19 / 63

What IPS looks for, and what it can do

  • Exploit signaturesPatterns of a known attack technique inside the traffic content.
  • Malformed protocol fieldsValues a well-behaved client would never send.
  • Known-bad byte sequencesContent tied to specific CVEs, the public IDs for known vulnerabilities.
  • Inline actionsDrop the packet, reset the connection, or block the source, in real time.
IPS sits inline, so unlike a passive detector it can stop the attack, not only report it.
HACKTHESOCLesson 74Firewall fundamentals20 / 63

What an NGFW sees on HTTPS, with and without decryption

ItemWithout TLS decryptionWith TLS decryption
Destination IP and port 443VisibleVisible
SNI (Server Name Indication) hostnameVisible in the TLS handshakeVisible
The actual request and URL pathHiddenVisible to app-ID and IPS
Payload: files, exploit bytesHidden from antivirus, IPS and DLPInspected by the full engine stack
Most modern traffic is TLS. Without decryption, every content engine is blind and only the handshake metadata is left.
HACKTHESOCLesson 74Firewall fundamentals21 / 63

How TLS inspection works

Also called SSL decryption or SSL forward proxy.

  1. 1Terminate client TLSThe firewall acts as a trusted man-in-the-middle by design.
  2. 2Decrypt and inspectPlaintext goes through the full stack: app-ID, IPS, antivirus, DLP.
  3. 3Re-encrypt and forwardA second TLS connection to the real destination.
  4. 4Trusted root CA on endpointsThe firewall's CA certificate is installed on every managed endpoint, so re-signed traffic raises no browser warnings.
Two TLS sessions exist: client to firewall, and firewall to server. The endpoint trusts the first only because the organisation installed the firewall's CA.
HACKTHESOCLesson 74Firewall fundamentals22 / 63

TLS inspection has real trade-offs

  • Performance costDecrypting and re-encrypting every connection is computationally expensive at scale.
  • Privacy and complianceDecrypting healthcare or banking portals can violate policy or regulation, so sensitive categories are usually excluded.
  • Broken pinningApps that pin one specific certificate fail, since they will not trust the firewall's re-signed certificate.
When you see no decryption on some traffic, it may be a deliberate exclusion, not a misconfiguration.
HACKTHESOCLesson 74Firewall fundamentals23 / 63

The payoff: an IPS block inside decrypted traffic

  • app=web-browsing on 443: allowed traffic by policy
  • decrypted=yes: IPS could only see Log4j because TLS was opened
  • action=reset-both: the IPS killed the connection inline
One log line wrapped for readability. Without decryption this would have been an unremarkable allowed HTTPS connection.
HACKTHESOCLesson 74Firewall fundamentals24 / 63

Firewall rules in practice across platforms

Same five-tuple-plus-action idea, different syntax.

HACKTHESOCLesson 74Firewall fundamentals26 / 63
Every rule, on every platform, answers the same four questions.

Which direction? What traffic does it match? What action? Where does it sit in the order? Map unfamiliar keywords onto those four and the syntax stops being intimidating.

Have students fill in the four answers for each of the next rules before reading the callouts.
HACKTHESOCLesson 74Firewall fundamentals27 / 63

Linux: iptables and nftables

  • Two iptables rules, one blocking inbound RDP, one allowing outbound HTTPS
  • nftables is the modern replacement: same idea, newer syntax
iptables is classic and still widely deployed. nftables is the direction of the trend across the industry.

Windows Firewall with netsh

  • dir=in: direction
  • action=block, protocol=TCP, localport=3389: action, protocol, port
The host-based firewall from section 2, with the Windows command shape. Wrapped with the cmd caret to fit.
HACKTHESOCLesson 74Firewall fundamentals30 / 63

One idea, three syntaxes: block inbound RDP

iptables

-A INPUT for direction, --dport 3389 for the port, -j DROP for the action.

nftables

input chain for direction, tcp dport 3389 for the match, drop for the action.

netsh

dir=in for direction, protocol=TCP localport=3389 for the match, action=block.

Same four answers each time. Only the keywords change.
HACKTHESOCLesson 74Firewall fundamentals31 / 63

An enterprise NGFW rulebase, read top to bottom

#SourceDestinationService / Action
1Internal_NetAnyHTTPS / Allow
2AnyDMZ_WebHTTP/S / Allow
3AnyAnyRDP / Deny
4AnyAnyAny / Deny (default)

Always read four things: direction, matched traffic, action, and the rule's position in the order.

Conceptually Palo Alto or Check Point style. Rule 4 is the default-deny catch-all silently blocking anything above did not address.
HACKTHESOCLesson 74Firewall fundamentals32 / 63

Walk four connections down that rulebase

  1. 1Employee browses HTTPSFrom Internal_Net, service HTTPS: rule 1 matches, allowed.
  2. 2Internet visits the websiteTo DMZ_Web over HTTP/S: rule 2 matches, allowed.
  3. 3Internet tries RDPRules 1 and 2 do not match; rule 3 does: denied.
  4. 4Internal host tries SSH outNo rule above matches SSH: rule 4, default deny.
The SSH case is the one students miss: it was never explicitly blocked, it simply was never allowed.

Section 5 of 8

Security zones, the DMZ, and NAT/PAT

Zone-to-zone policy, an isolated public segment, and address rewriting.

HACKTHESOCLesson 74Firewall fundamentals34 / 63

Zones keep large rulebases readable

Rules become zone-to-zone policies: from this zone, to that zone, this service, this action.

Trust

The internal network.

Untrust

The internet.

DMZ

Isolated segment for public-facing servers: web server, mail relay, public DNS. Reachable from the internet, never directly into internal systems.

Palo Alto, Fortinet, Check Point and similar NGFWs group interfaces into named zones. It is the five-tuple idea with zones in place of raw addresses.
HACKTHESOCLesson 74Firewall fundamentals35 / 63

Why a DMZ exists

  • DMZDemilitarized zone: a separate segment isolated by the firewall from both the internet and the internal network.
  • What lives thereServers that must be reachable from the internet: web server, mail relay, public DNS.
  • Why isolate themThey are the most exposed and most likely to be compromised.
  • The payoffIf one is breached, the isolation stops the attacker pivoting straight into the internal network.
The DMZ accepts that public servers will be attacked and limits how far a successful attack can go.
HACKTHESOCLesson 74Firewall fundamentals36 / 63

One rule enforces the DMZ's isolation

#Src zoneDst zoneService / Action
1UntrustDMZHTTPS (443) / Allow
2DMZTrustAny / Deny
3TrustUntrustHTTPS (443) / Allow
4AnyAnyAny / Deny (default)
Rule 2 is defense in depth in a single rule: a compromised DMZ web server cannot simply walk into the internal network.
HACKTHESOCLesson 74Firewall fundamentals37 / 63

What rule 2 does when the web server is breached

  1. 1Web server compromisedAn attacker gains control of the public server in the DMZ.
  2. 2Attempts to reach insideIt tries to connect from the DMZ zone to a host in the Trust zone.
  3. 3Rule 2 deniesAny service from DMZ to Trust is blocked, whatever the port.
  4. 4The deny is loggedA DMZ-to-Trust denial is evidence the public server may be doing something it should not.
A legitimate DMZ server has no reason to start connections into Trust, which is what makes those denials worth a look.
HACKTHESOCLesson 74Firewall fundamentals38 / 63

Three kinds of address translation

NAT

Network Address Translation rewrites source or destination IP as packets cross. Usually private RFC 1918 addresses (e.g. 10.0.0.0/8) to a public, routable one.

PAT (NAT overload)

Port Address Translation also rewrites the source port, so one public IP is shared by the whole organisation.

DNAT (port forwarding)

Destination NAT maps a public IP and port to an internal server, letting outsiders reach a service that only has a private address.

Private addresses cannot be routed on the internet, which is why outbound traffic is translated before it leaves.
HACKTHESOCLesson 74Firewall fundamentals39 / 63

How PAT tells thousands of sessions apart

Internal host and portLeaves asReply comes back to
10.0.0.5 : 51422Public IP : port APort A, so it goes to 10.0.0.5
10.0.0.9 : 51422Public IP : port BPort B, so it goes to 10.0.0.9
10.0.0.5 : 51500Public IP : port CPort C, so it goes to 10.0.0.5
The firewall keeps this translation table. Even two hosts using the same internal source port get different public ports, so every reply finds its owner.
HACKTHESOCLesson 74Firewall fundamentals40 / 63

NAT in iptables

  • MASQUERADE on the way out: source rewritten to the public IP
  • DNAT on the way in: public 443 forwarded to 10.1.1.5:443
POSTROUTING changes the source after routing; PREROUTING changes the destination before routing.
HACKTHESOCLesson 74Firewall fundamentals41 / 63

The log-search trap: which address did the log record?

  • Pre-NATThe original internal address, such as the workstation's 10.x IP.
  • Post-NATThe translated public address that actually left the network.
  • xlatesrc / xlatedstFields many firewall logs use to record translated source and destination alongside the originals.
  • The trapSearch for the internal IP when only the post-NAT public IP was logged and you find nothing.
Which address a rule matches and a log records differs by platform. Correlate pre- and post-NAT addresses when pivoting to endpoint telemetry.

Section 6 of 8

Ingress, egress, and why outbound matters

The less obvious direction is often the more valuable one.

HACKTHESOCLesson 74Firewall fundamentals43 / 63

Inbound tells you who is knocking

Ingress (inbound)

Keeps attackers out by blocking unsolicited connections to management ports, databases and file shares. Exposing RDP (3389) to the internet is the classic dangerous misconfiguration.

Egress (outbound)

Controls what leaves. Frequently neglected, since many organisations allow almost all outbound, yet once an attacker is inside, their activity shows up as outbound traffic.

Common beginner mistake: focusing only on inbound.
HACKTHESOCLesson 74Firewall fundamentals44 / 63

Everything an intruder does crosses the firewall outbound

  1. 1Command and control (C2)Malware reaches out to the attacker's server for instructions.
  2. 2Data exfiltrationStolen data flows out to somewhere the attacker controls.
  3. 3Downloading toolsMore payloads are pulled in, initiated by an outbound request.
Even a download into the network starts with an outbound request, so it still crosses egress policy.
HACKTHESOCLesson 74Firewall fundamentals45 / 63

The same C2 attempt under two egress policies

Allow almost all outbound

The connection to an unknown server is allowed. It is only logged, and only noticed if someone reads allowed traffic for patterns.

Approved destinations only

The connection to an unknown server is blocked, or at minimum logged as an anomaly. A blocked outbound attempt is often the first sign of compromise.

Section 8 shows the first case: the beacon was allowed, and only pattern-reading found it.
HACKTHESOCLesson 74Firewall fundamentals46 / 63
Outbound denials and anomalies often tell you who is already inside and trying to phone home.

The firewall is a detector of insiders reaching out, not just a wall against outsiders reaching in.

This reframing is what turns firewall logs into a live investigation tool rather than a passive barrier.

Turn the silent barrier into a rich source of evidence.

Three attack shapes in firewall data

Inbound, denied

Port scan

One external source, many destination ports, in a burst. An attacker mapping what is exposed.

Outbound, allowed

C2 beacon

One internal host, one destination, regular interval, similar size every time.

Outbound, large

Exfiltration

One internal host sending an unusually large volume of data out.

Shape is the clue: count, spread and timing of connections, not any single line.
HACKTHESOCLesson 74Firewall fundamentals51 / 63

PatternWhat it suggests
Denied inbound bursts across many ports from one sourcePort scanning: mapping what is exposed
Outbound to known-bad IP, new domain, odd country or portC2 or exfiltration
Unusually large outbound volume from one hostData exfiltration
Workstation to internet on odd port, or scanning peersShould never happen; possible lateral movement
Allowed traffic reaching management portsRisky services that should be restricted
The outbound rows are where egress visibility pays off.
HACKTHESOCLesson 74Firewall fundamentals52 / 63

One source among several: the classic C2 pivot

  1. 1Firewall logA workstation beacons to an external IP every few minutes.
  2. 2Endpoint telemetryThe process tree shows which process makes the connection.
  3. 3Threat intelligenceConfirms whether the destination is known-bad.

The firewall is both a control (it blocks) and a sensor (it records allowed traffic too).

On its own a firewall log shows that a connection happened. Combined with EDR and intel it becomes conclusive.

Worked example: catching C2 beaconing

The most important line was one the firewall was happy to allow.

HACKTHESOCLesson 74Firewall fundamentals54 / 63

A top-talkers flag on 10.14.22.108

  • Every line is action=allow: no deny-based alert ever fired
  • Same destination, same port, almost exactly every five minutes
  • Near-identical byte counts: 1204, 1198, 1211
Ask the class what is wrong here before revealing: the shape, not the content.

HACKTHESOCLesson 74Firewall fundamentals56 / 63

Beacon or human browsing?

Human browsing

Bursty and irregular: many destinations, varied sizes, clustered when the user is active, quiet at night.

C2 beacon

Flat and mechanical: one destination, fixed interval, near-identical size, running while nobody is at the keyboard.

Some malware adds random jitter to the interval. The destination and size consistency still give it away.
HACKTHESOCLesson 74Firewall fundamentals57 / 63

From allowed traffic to verdict

  1. 1Notice the shapeFlat, mechanically regular beaconing, not the bursty, irregular pattern of a person browsing.
  2. 2Check reputation91.203.5.14: no business association, hosting registered weeks ago, reported as C2 for a known malware family.
  3. 3Pivot to the endpointEDR shows windowless PowerShell making the connections, parent a Word document from an email attachment.
  4. 4VerdictTextbook C2 beacon: fixed interval, destination and size, from PowerShell hanging off a phishing document.
A defender only watching for denials would never see this. Read the log as evidence, not as a pass/fail control.
HACKTHESOCLesson 74Firewall fundamentals58 / 63
The firewall is a sensor, not just a wall.

Fully allowed traffic, read for interval, destination and size, revealed a compromise that no deny rule would ever have flagged.

Close the lesson by contrasting the two mindsets: pass/fail control versus evidence source.

Key takeaways

  1. 01A firewall matches each connection's five-tuple against an ordered rulebase; first match wins and default deny blocks the rest.
  2. 02Stateless filters check packets alone, stateful firewalls track connections, NGFWs add app-ID, IPS and TLS decryption.
  3. 03iptables, nftables, netsh and NGFW tables all express direction, matched traffic, action and rule order.
  4. 04Zones and the DMZ isolate exposed servers; NAT means logs may hold pre- or post-NAT addresses.
  5. 05Egress is the under-used, high-value control: C2, exfiltration and tool downloads all cross outbound.
  6. 06The firewall is a sensor too: fully allowed traffic can reveal C2 beaconing by interval, destination and size.
HACKTHESOCLesson 74Firewall fundamentals60 / 63

Check your understanding, question 1 of 3

Many organisations focus their firewall effort on inbound rules. Why is egress (outbound) filtering such a valuable detection control?

After a foothold, C2, stolen data and tool downloads all flow outbound, so watching what leaves catches what inbound rules never see. Exploits arrive inbound, stateful tracking is not created by egress rules, and inbound denials still show who is knocking.

Check your understanding, question 2 of 3

Rulebase, top to bottom: (1) Any to Any, any service, Allow; (2) Internal_Net to Any, HTTPS, Allow; (3) Any to Any, RDP, Deny; (4) default Deny. An external host tries RDP to an internal server. What happens?

Rules are evaluated in order and the first match usually wins. Rule 1 matches the RDP attempt, so rule 3 is never reached. Position decides, not specificity, and the default deny only catches traffic no rule above matched.
