One dangerous account setting: 'do not require Kerberos pre-authentication.'

When it is set, any attacker can request a response containing material encrypted with the user's password, then crack it offline with no lockout.

This lesson starts from zero: what happens at login, what preauth protects against, and why skipping it is catastrophic.

Section 1 of 9

Kerberos login and why preauth exists

What happens the first moment you log in to a domain.

HACKTHESOCLesson 40AS-REP Roasting6 / 36

The front-gate exchange and the whisper check

  1. 1AS-REQYour computer asks the KDC: 'I am this user, give me a TGT', the wristband proving you logged in.
  2. 2Pre-authenticationBy default you must first prove you know the password by encrypting a timestamp with a password-derived key.
  3. 3KDC verifiesIt decrypts the timestamp with your hash. If it works and is recent, you have proven knowledge of the password.
  4. 4AS-REPOnly then does the KDC reply with the TGT. Preauth is a bouncer's whisper-check, done cryptographically.
Your computer never sends the password itself. The KDC (Key Distribution Center) is the office that hands out tickets.
HACKTHESOCLesson 40AS-REP Roasting7 / 36
Set DONT_REQ_PREAUTH and the KDC skips the whisper check, handing the AS-REP to anyone who asks.

The flag is bit 0x400000 in userAccountControl. Crucially, the session-key portion of the AS-REP is still encrypted with the account's password-derived key.

The KDC stopped checking the key before responding, but never stopped using it to encrypt part of the reply. That is the opening.
HACKTHESOCLesson 40AS-REP Roasting8 / 36
The attacker takes that ciphertext to their own hardware and guesses passwords one by one.

Offline cracking: no server to notice wrong guesses, no lockout counter, no rate limit. The attacker's GPU is the only limit.

Unlike typing a wrong password at a login screen, nothing on the domain sees any of it. This is the exact mechanism AS-REP Roasting weaponises.

Section 2 of 9

What AS-REP Roasting is

T1558.004: find preauth-disabled accounts, request the AS-REP, crack it offline.

HACKTHESOCLesson 40AS-REP Roasting10 / 36

Why would any account have preauth disabled?

  • Legacy compatibilityOlder Kerberos clients, some Unix/Linux stacks, could not do preauth, so admins disabled it to make login work.
  • Copy-paste provisioningAn admin clones an old service account template that had the flag set, not realising what it does.
  • Forgotten testingA flag toggled for troubleshooting once, never reverted.

The flag is silent and low-visibility: nothing looks obviously broken, which is why attackers hunt for it.

Nobody sets this maliciously; it becomes a vulnerability through misconfiguration or legacy interoperability.
HACKTHESOCLesson 40AS-REP Roasting11 / 36
Account lockout never engages, because the attacker never sends a wrong password to the domain.

They request the AS-REP, which the KDC hands over unconditionally, then guess against a copy of the ciphertext. Event 4625 (failed logon) counters see nothing.

The account's fate rests entirely on password strength, or on removing the preauth exemption. A weak password on a privileged preauth-disabled account is one of the cheapest full compromises available.

Section 3 of 9

How the attack works step by step

Often no valid domain credentials needed to find and roast targets.

HACKTHESOCLesson 40AS-REP Roasting13 / 36

Discovery and request, and what the DC records

  • Enumerate targetsThe attacker queries LDAP for the DONT_REQ_PREAUTH bit (...:1.4.803:=4194304), a normal directory read that rarely stands out alone.
  • Request the AS-REPFor each preauth-disabled account an AS-REP is requested. Tools such as Rubeus or Impacket GetNPUsers automate this, often unauthenticated.
  • The DC recordEach request lands as Event 4768 with Pre-Authentication Type: 0. A burst for many accounts from one source IP is the tell.

No valid domain credentials are needed to find and roast targets, so the recon rarely trips an auth alarm.

Describe the enumerate-then-request flow in words; the defender's signal is the 4768 pattern, covered in detail in the detection section.
HACKTHESOCLesson 40AS-REP Roasting14 / 36

Cracking is offline, so the DC sees nothing

  • The ciphertextThe AS-REP session-key portion is encrypted with the account's password key. Redacted it reads $krb5asrep$23$user@DOMAIN:<hash>.
  • RC4 is the fast path23 marks RC4-HMAC (etype 0x17), the quickest to crack. Offline tools (Hashcat mode 18200) grind a wordlist on the attacker's own GPU.
  • Nothing to seeNo server sees the guesses: no lockout, no rate limit, no failed logon. The cracked password is then reused like any stolen credential.

The highest-impact version finds a privileged account carelessly exempted from preauth.

A weak password on a privileged preauth-disabled account is one of the cheapest full compromises available, and none of the cracking touches the domain.

Section 4 of 9

Targeted roasting: setting the flag yourself

If you can write to a user object, turn the flag on, roast, then flip it back.

HACKTHESOCLesson 40AS-REP Roasting16 / 36
A dangerous ACL edge removes the dependency on the flag already being set.

GenericAll, GenericWrite, or WriteProperty over a user object, often via sloppy helpdesk delegation, lets you modify their userAccountControl.

BloodHound draws exactly these edges as attack paths, which is why recon tooling and AS-REP Roasting chain so naturally.
HACKTHESOCLesson 40AS-REP Roasting17 / 36

Targeted roasting: a three-step flag toggle

  1. 1Set the flagWith write access to the user object, the attacker turns DONT_REQ_PREAUTH (4194304) on via an XOR of userAccountControl.
  2. 2Roast the accountThe now preauth-disabled account is roasted: the AS-REP is requested and carried off to crack offline.
  3. 3Revert the bitToggle the flag back off so the account looks untouched. XOR-ing the same bit twice restores the original setting.

After the revert, only the paired Event 4738s around the 4768 betray the change.

Even a strong password does not save an account whose flag can be set by a compromised helpdesk account. The telemetry of this toggle is covered on the next slide.
HACKTHESOCLesson 40AS-REP Roasting18 / 36

The telemetry that exposes the toggle

  • Event 4738A user account was changed. A 4738 adding DONT_REQ_PREAUTH, then a 4768 PreAuthType=0, then a 4738 reverting, is near-unambiguous.
  • Event 5136Directory Service Changes records the attribute modification when object-change auditing is enabled.

Auditing who holds write access over user objects belongs in the same conversation as password strength.

The paired 4738 events around the 4768 are the tell of targeted roasting.

AS-REP Roasting vs Kerberoasting

Both crack Kerberos ciphertext offline, but differ in target, ticket, and prerequisites.

HACKTHESOCLesson 40AS-REP Roasting20 / 36

Know the distinction cold

AspectAS-REP Roasting (T1558.004)Kerberoasting (T1558.003)
Targeted accountsUsers with preauth disabledAccounts with a Service Principal Name
Kerberos messageAS-REP, the initial auth exchangeTGS-REP, a service ticket
Needs valid domain creds?No, can be fully unauthenticatedYes, must be able to request a TGS
Key event ID4768, AS ticket requested4769, service ticket requested

Both share RC4 plus weak passwords as the weakness, and both are defeated by strong passwords and gMSA. Only AS-REP Roasting is fixed by re-enabling preauth; you cannot remove SPNs services legitimately need.

Section 6 of 9

Detection: spotting it in Event 4768

The DC-side record of every AS-REQ/AS-REP exchange.

HACKTHESOCLesson 40AS-REP Roasting22 / 36

The fingerprint inside a single 4768

  • Pre-Authentication Type: 0 means no preauth was performed: the direct signal
  • 0x17 RC4 where AES is standard is itself worth flagging
A normal interactive logon shows a non-zero preauth type, commonly 2. Type 0 for an account that should be a normal user is the single strongest indicator.
HACKTHESOCLesson 40AS-REP Roasting23 / 36

Build the rule, then baseline and bait

  • Watch the patternA burst of 4768s for many usernames from one source IP in a short window is bulk roasting, not a person.
  • Correlation ruleEventID=4768 AND PreAuthType=0, enriched with encryption type, grouped by source IP.
  • Baseline exemptionsList accounts that legitimately have preauth disabled, so requests outside that list stand out.
  • HoneytokenA preauth-disabled account with a tempting name and a long random password. Any 4768 PreAuthType=0 against it is a real detection.
Nobody logs in as fifty accounts from one workstation in ten seconds. The honeytoken has no legitimate reason to be queried, so it is near-zero false positive.

Section 7 of 9

Defence: closing the gap

Attack the root cause, not just the cracking activity.

HACKTHESOCLesson 40AS-REP Roasting25 / 36

Four defensive moves

Require preauth

Audit userAccountControl for the 0x400000 flag and remove it wherever legacy needs do not truly require it. This alone neutralises the attack.

Strong passwords / gMSA

Any account that must stay exempt needs 25+ random characters. Prefer gMSA so passwords are machine-generated and auto-rotated.

Disable RC4, use AES

Forces Kerberos onto AES, removing the fast-to-crack type roasting relies on and making any RC4 an anomaly.

Continuously audit

A migration or template copy can silently re-add the flag. Schedule a recurring query that alerts on any new exemption.

Pair the recurring audit with the honeytoken so a missed window still has a tripwire.

Re-enabling preauth returns the KDC to demanding the whisper-check before issuing any AS-REP.

AES hashes and zero-credential targeting

What changes when the target uses AES, and how an attacker builds a list with no creds.

HACKTHESOCLesson 40AS-REP Roasting30 / 36

The hash prefix tells you which cracker

Hash prefixEncryption typeTool / mode
$krb5asrep$23$RC4-HMAC (etype 23)Hashcat mode 18200
$krb5asrep$17$AES128-CTS-HMAC-SHA1-96 (etype 17)John the Ripper, --format=krb5asrep
$krb5asrep$18$AES256-CTS-HMAC-SHA1-96 (etype 18)John the Ripper, --format=krb5asrep
Disabling RC4 does not make roasting impossible; it only removes the fast path, pushing every roast onto slower AES cracking and buying time for a strong password.
HACKTHESOCLesson 40AS-REP Roasting31 / 36

Building a target list with no credentials

  • Username oracleA bad username gives KDC_ERR_C_PRINCIPAL_UNKNOWN; a real one gives KDC_ERR_PREAUTH_REQUIRED. kerbrute automates validating a wordlist.
  • Null-session enumerationLegacy anonymous LDAP or SAMR binds allow RID cycling to list all usernames. Modern defaults block this.

Once a username list exists, GetNPUsers or Rubeus roasts only the preauth-disabled ones.

Validating usernames is a separate step from requesting AS-REPs. Blocking anonymous enumeration and alerting on repeated KDC error codes from one source catches the recon phase, before the 4768 roast.
HACKTHESOCLesson 40AS-REP Roasting32 / 36

Key takeaways

  1. 01Kerberos normally requires preauth: proving you know the password before the KDC issues a TGT, like a bouncer's whisper-check.
  2. 02DONT_REQ_PREAUTH (bit 0x400000) tells the KDC to skip that check, handing out an AS-REP whose key is still password-encrypted.
  3. 03Cracking is fully offline (Rubeus, GetNPUsers, Hashcat 18200), so there is no lockout, rate limit, or failed-logon event.
  4. 04AS-REP Roasting (unauthenticated, 4768) is easy to confuse with Kerberoasting (authenticated, 4769, SPN accounts).
  5. 05Detect on 4768 with PreAuthType=0 and RC4 (0x17); defend by re-enabling preauth, strong passwords or gMSA, and disabling RC4.
