Section 1 of 13

EDR vs antivirus: what changed

From matching files against a blocklist to recording behavior all the time.

HACKTHESOCLesson 10EDR explained6 / 58

Three ways attackers outgrew signatures

Polymorphism and packing

Malware re-encrypts or repacks itself on every build, so each sample has a new hash. A hash blocklist is always one step behind.

Fileless and LOLBins

Malicious PowerShell in memory, or abuse of signed binaries like rundll32.exe, regsvr32.exe, mshta.exe. No bad file to scan.

Legitimate-tool abuse

PsExec, WMI and remote management frameworks are real admin tools. A signature cannot block them without breaking the business.

Signature AV is a bouncer checking IDs against a photo list. Fast and cheap against known file-based malware, but reactive: it only catches what someone already analyzed.
HACKTHESOCLesson 10EDR explained7 / 58

Antivirus asks about files, EDR asks about behavior

Point at the retroactive-investigation row. That is the capability that did not exist before.
HACKTHESOCLesson 10EDR explained8 / 58

Two paradigms side by side

  • The sensor, the agent, streams telemetry to a central platform
  • Office spawning encoded PowerShell is the tell, though both are signed
  • Recording everything all the time is what enables retrospective search
Most platforms bundle a next-gen AV engine for prevention with the EDR recording layer. The visibility is the part that changed the job.

The telemetry EDR collects

Four event types, all hanging off one process tree.

HACKTHESOCLesson 10EDR explained10 / 58

Four telemetry types, four kinds of evidence

TypeWhat it recordsWhat it reveals
Process eventsName/path, command line, PID, user, hash, signature status, parentIntent (the command line) and lineage (the parent)
File eventsCreation, modification, deletion, renaming on diskDropped payloads, ransomware encryption, staging, log-clearing
Network eventsSource and destination IP, port, direction, owning processThe exact process behind a connection (C2 attribution)
Registry eventsKey and value creation and modificationPersistence (Run keys, services) and defense impairment
Never triage a process event without reading its full command line: -enc, Invoke-WebRequest, certutil -urlcache all live there. Tampering with security-tool registry values is Defense Impairment, the ATT&CK v19 tactic that took over tool tampering.
HACKTHESOCLesson 10EDR explained11 / 58
A firewall says 10.4.2.9 talked to an external IP on 443. The EDR says it was rundll32.exe.

That process-to-connection link is what turns a bland network log into a C2 finding.

This is the EDR superpower for network events. Seen from the host, every socket has an owner.
HACKTHESOCLesson 10EDR explained12 / 58

A phishing-to-C2 chain as a process tree

  • PROCESS: Office spawning encoded PowerShell is the tell
  • FILE: the dropped payload. REGISTRY: Run-key persistence
  • NETWORK: the C2 connection attributed to svc32.exe, not just an IP
Read top-down for the story, bottom-up from the flagged process to learn how the attacker got there. An unexpected parent, like services.exe spawning cmd.exe, starts the investigation.

Section 3 of 13

Detections vs preventions

Why blocked or quarantined is the start of an investigation, not the end.

HACKTHESOCLesson 10EDR explained14 / 58

First question: did it stop this, or only watch?

Detect-only

The sensor observes, records and alerts, but takes no action. The activity proceeds. Used during tuning, to avoid breaking software, or for ambiguous behavior.

Prevent / block

The sensor intervenes: kills the process, quarantines the file, or blocks the connection before or during execution.

The answer is in the action or status field, and it changes everything about your urgency.

Organizations deliberately run some logic in detect-only mode. Never assume a detection means something was stopped.
HACKTHESOCLesson 10EDR explained15 / 58
Quarantine addresses the artifact, not the incident.

Behavioral detection must observe before it can judge. By the time it acts, the code has already run. Prevention reduces blast radius; it rarely rewinds time.

In the chain from the last section, svc32.exe was quarantined only after the Run key, the C2 connection and possibly credential theft. Fileless attacks may leave no file to quarantine at all.
HACKTHESOCLesson 10EDR explained16 / 58

After a quarantine, check what already happened

Handled only when persistence is gone, connections are dead, scope is bounded and nothing residual remains. 'The file was blocked' answers what the EDR did, not what the attacker accomplished.

Reading an EDR detection across vendors

One intrusion, three schemas. The concepts stay, the field names change.

HACKTHESOCLesson 10EDR explained18 / 58

Parent (process creation)ParentBaseFileNameInitiatingProcessFileNamesrc.process.name
Child's command lineCommandLineProcessCommandLinetgt.process.cmdline
Child's SHA256SHA256HashDataSHA256tgt.process.image.sha256
Correlation keyaid (agent ID)DeviceId, DeviceNameStoryline ID
Detect vs preventPatternDispositionDescriptionActionTypemitigationStatus
Build a translation cheat sheet in your first week with a new EDR. Once you hold the concepts, the field name is just a lookup.
HACKTHESOCLesson 10EDR explained19 / 58

SentinelOne: src is the actor, tgt is the object

The same process changes prefix depending on which event you are reading.

Process creation event

src.process. is the parent doing the creating (src.process.name, src.process.cmdline). tgt.process. is the new child (tgt.process.name, tgt.process.cmdline, tgt.process.image.sha256).

The trap

The child's later events

In its file writes, DNS lookups and connections the child is now src.process., and its parent appears as src.process.parent..

Files and network

Files use tgt.file.path and tgt.file.sha256. Network events use dst.ip.address and dst.port.number.

Read the event type before you read the src/tgt fields.

On a network event, src.process.name is the process that acted, not its parent. Students who learned 'src means parent' from the creation event misread every later event.
HACKTHESOCLesson 10EDR explained20 / 58

The same detection, queried in Defender KQL

  • In Falcon this is event_simpleName=ProcessRollup2
  • Network lives in DeviceNetworkEvents; Falcon uses NetworkConnectIP4
  • File and registry: DeviceFileEvents, DeviceRegistryEvents
SentinelOne threats also carry threatInfo fields: threatName, classification and mitigationStatus.
HACKTHESOCLesson 10EDR explained21 / 58

The schemas package the story differently

Atomic events

CrowdStrike

ProcessRollup2, NetworkConnectIP4. You correlate them yourself, joining on aid and process IDs over a time window.

Purpose-built tables

Defender

Process, network, file and registry tables you join in KQL on DeviceId and process fields.

Pre-correlated

SentinelOne

Activity arrives as a Storyline, so much of the tree is already assembled for you.

Identify the vendor and its correlation model first, so you reach for the right join key.

None of these is objectively better. When you inherit an investigation mid-flight, this check saves you from asking questions the schema answers differently.

Section 5 of 13

Walking the tree in raw data

Process IDs, PID reuse, and what the sensor actually keeps.

HACKTHESOCLesson 10EDR explained23 / 58

Never join on the PID alone: use the vendor's unique ID

Windows reuses PIDs quickly, so one PID can belong to several unrelated processes in a day.

VendorThis processIts parentOS PID
CrowdStrike FalconTargetProcessId (unique per sensor, scope it with aid)ParentProcessId = the parent's TargetProcessIdRawProcessId
Defender for EndpointDeviceId + ProcessId + ProcessCreationTimeInitiatingProcessId + InitiatingProcessCreationTimeProcessId
SentinelOnetgt.process.uid at creation, src.process.uid latersrc.process.parent.uidtgt.process.pid / src.process.pid
Join on PID alone and you can stitch a malicious child onto an innocent parent. Newer Defender data adds ProcessUniqueId and InitiatingProcessUniqueId; Falcon file and network events point back via ContextProcessId; SentinelOne's storyline.id returns the whole tree in one filter.
HACKTHESOCLesson 10EDR explained24 / 58

Climbing from child to parent and grandparent in KQL

  • Each step is a self-join on ID plus creation time, never ProcessId alone
  • Empty ParentName usually means the parent predates the 30-day window
  • Falcon: search ProcessRollup2 for the parent's TargetProcessId with its aid
In Falcon Advanced Event Search the same climb is a search such as #event_simpleName=ProcessRollup2 aid=4a1f88b2c9 TargetProcessId=289734651298.
HACKTHESOCLesson 10EDR explained25 / 58

Raw telemetry is incomplete, and it ages out

  • Sensors throttleImage loads, file reads and repeated connections get deduplicated or skipped, so a missing DeviceNetworkEvents or NetworkConnectIP4 row is weak.
  • Defender retention30 days of data in Advanced Hunting, while alerts and the device timeline go back further.
  • Falcon and SentinelOneRaw-telemetry retention depends on the licence tier and is often far shorter than the detection history.
  • The practical ruleThe alert can outlive the process tree that explains it, so export or snapshot evidence for any case that may run long.
A present event is strong evidence; an absent one is much weaker. Teach students to say 'no telemetry retained' rather than 'it did not happen'.

Worked example: a Falcon detection end to end

One detection, read start to finish in Falcon's field vocabulary.

HACKTHESOCLesson 10EDR explained27 / 58

The raw detection

  • Detected, not Prevented: the PowerShell very likely ran
  • ParentBaseFileName WINWORD.EXE launched powershell.exe
  • aid is the host you pivot on for file, registry, network
Even without a graphical console, the JSON alone gives you the lineage. Ask the class which field they would read first.
HACKTHESOCLesson 10EDR explained28 / 58

Four steps from alert to decision

  1. 1Read the disposition firstPatternDispositionDescription says Detected. Nothing was blocked, which sets your urgency.
  2. 2Reconstruct the treeWINWORD.EXE spawned powershell.exe with -nop -w hidden -enc: the phishing-to-execution shape.
  3. 3Chase what already happenedOn this aid: files written after launch, Run keys or scheduled tasks, connections, live children.
  4. 4Decide the responseKill the running process, confirm no persistence. Isolate only if live C2 is confirmed.
High severity plus encoded command line plus detect-only clears the bar for action, not passive review. Make reading the disposition field first a habit.

Section 7 of 13

Response actions and questions before isolating

The R in EDR: a tourniquet and a set of scalpels.

HACKTHESOCLesson 10EDR explained30 / 58

Tourniquet or scalpel

The emergency brake

Host isolation

Cuts the host off from everything but the EDR console. Severs C2, halts lateral movement and exfiltration. Can cause outages and tips off the attacker.

Surgical

Kill a process

Terminate the malicious process without cutting the host off, keeping its function and your visibility into what else is happening.

Isolation is powerful and often correct, but it is not free. A tipped-off attacker with remaining access may turn destructive.
HACKTHESOCLesson 10EDR explained31 / 58

Three more scalpels for the toolkit

Collect a forensic package

Defender's "Collect investigation package": autoruns, programs, connections, prefetch, processes, tasks, services, SMB sessions, Security log, temp folders. Preserves volatile state first.

Retrieve a file

getfile in Defender live response, get in Falcon RTR, Fetch Files in SentinelOne (delivered in a password-protected archive so nobody detonates it).

Open a remote shell

Defender live response, Falcon RTR, SentinelOne Remote Shell: list processes and connections, query a registry key, remove a scheduled task.

Access is tiered by role: in Falcon, ps, netstat, reg query sit with lower RTR roles; put and runscript need higher ones.

Collect the package before you kill or isolate anything, otherwise the volatile state you need may be gone.
HACKTHESOCLesson 10EDR explained32 / 58
Every response action is recorded, and that trail is evidence in its own right.

Defender's Action center history, Falcon's RTR audit log, SentinelOne's Activity log: who, when, which host. Write in the ticket what you did and why.

Expect someone to read the audit log against your notes. A missing ticket entry for an RTR session looks worse than the action itself.
HACKTHESOCLesson 10EDR explained33 / 58

Six questions before you isolate

  1. 1What is this host?A laptop vs a domain controller. Isolating a DC can take down authentication company-wide.
  2. 2Confidence and severity?Active C2 or ransomware: isolate now. One ambiguous alert: kill and keep digging.
  3. 3What will I lose?Business disruption, volatile evidence, or the chance to watch a contained host.
  4. 4Is it spreading?Same activity on several hosts: one isolation is not enough. Escalate.
  5. 5Who needs to approve?Critical production: notify the owner or incident commander.
  6. 6Can I be more surgical?Kill process, remove persistence, block the C2 IP: same containment, less damage.
The junior instinct is to isolate everything that alerts. The mature instinct is to isolate decisively when evidence warrants it and know who to bring in when stakes are high.

Section 8 of 13

EDR evasion: blinding the sensor

The sensor is software on a machine the attacker may control.

HACKTHESOCLesson 10EDR explained35 / 58

Four ways attackers blind the sensor

  • Tamper or kill the agentStop or uninstall the service. Tamper protection counters it, so the attempt itself is a high-signal alert.
  • UnhookingRestore the original code under the sensor's userland hooks, so actions run unseen while the sensor stays on.
  • BYOVDLoad a signed but vulnerable driver, exploit it for kernel control, and blind the EDR from below.
  • Run before the sensorExecute early in boot, before the agent initialises, during its blind window.
Roughly in order of sophistication. The BYOVD tell is a known-vulnerable driver loading, especially on a machine with no reason to.
HACKTHESOCLesson 10EDR explained36 / 58

What EDR sees, how it is blinded, where it never was

Use this to bridge into the next section. The middle panel is evasion; the right panel is where EDR simply is not.
HACKTHESOCLesson 10EDR explained37 / 58
Absence of EDR detections is not proof of safety on a compromised host.

A sensor that stopped reporting, a tamper block, or a vulnerable-driver load is often louder than the activity it was meant to hide.

Same lesson as cleared logs: the attack on your visibility is evidence, if you are watching for it.

Section 10 of 13

From EDR to XDR and MDR

How do we see more, and who does the watching?

HACKTHESOCLesson 10EDR explained42 / 58

XDR is breadth, MDR is people

What can we see?

XDR

Correlates endpoint, network, email, cloud and identity telemetry into one view. Links phishing email, laptop process, cloud login and SaaS data loss into one incident.

Who looks at 3 a.m.?

MDR

A service, not a technology. A third-party team watches your EDR/XDR around the clock, doing triage and initial response.

XDR changes your workflow: alerts arrive pre-correlated. MDR shapes the role, not the analysis.

If your organisation uses an MDR, know the division of labour: what they handle and what escalates to you.

EDR across platforms: ETW, ESF, eBPF

Each OS gives the agent a different kernel interface, and that shapes what it sees.

HACKTHESOCLesson 10EDR explained44 / 58

Three operating systems, three collection mechanisms

PlatformMechanismKey characteristic
WindowsETW plus kernel-mode minifilters and callbacksDeepest, most mature telemetry; what vendor docs describe by default
macOSEndpoint Security Framework (ESF), since macOS 10.15User-space, entitlement-gated API; replaced unsupported KEXTs
Linuxauditd (legacy) or eBPF (modern)eBPF: verified in-kernel programs, lower overhead, the new default
Defender for Endpoint on Linux has moved to an eBPF-based sensor and dropped auditd as a supplementary event provider in recent versions.
HACKTHESOCLesson 10EDR explained45 / 58

Same story, three mechanisms

  • A parent spawned a child that made a network call, on every OS
  • Do not assume the field set or blind spots transfer across a mixed fleet
ESF is bounded by the event types Apple chooses to expose. A macOS agent cannot hook anything it wants the way a Windows kernel driver historically could.

Reading macOS telemetry: osascript and signing

What a malicious Mac execution looks like, and why "signed" is not a verdict.

HACKTHESOCLesson 10EDR explained47 / 58

osascript is the Mac sibling of PowerShell

  • What it isThe Apple-signed command-line interpreter for AppleScript, present on every Mac and used constantly by IT automation.
  • ATT&CKT1059.002 (AppleScript), the sibling of PowerShell's T1059.001.
  • How it arrivesAn ESF exec event (ES_EVENT_TYPE_NOTIFY_EXEC), shown with the Windows-style fields: path, command line, parent, user, code-signature status.
The previous section covered the plumbing (ESF). This one shows what one common malicious execution looks like through it.
HACKTHESOCLesson 10EDR explained48 / 58

The credential-phishing one-liner

  • with hidden answer masks input like a real password prompt
  • -d @- makes curl POST whatever arrived on stdin: the typed password
  • No custom binary: osascript and curl are both Apple-signed
The lesson's dialog reads "Invoice Viewer requires your password". The whole payload lives in the arguments; no custom binary is involved.
HACKTHESOCLesson 10EDR explained49 / 58

Read the parent and the arguments, not the signature

Misleading

Code signature

process.code_signature.trusted: true. osascript genuinely is Apple's binary, so this reads trusted on every Mac all day. It proves nothing.

Evidence

Parent

process.parent.name: Invoice Viewer, an unsigned app running from a just-mounted disk image: /Volumes/Invoice_8842/Invoice Viewer.app/...

Evidence

Arguments

The command line builds a hidden-answer password dialog and posts its contents out with curl. Technique: T1059.002.

Signature status answers who built the binary, never what it was told to do.

In Falcon's own schema the same values sit in ImageFileName, CommandLine and ParentBaseFileName; the ECS view uses process.* fields.

Proactive threat hunting with EDR

Searching raw telemetry for what no rule ever flagged.

HACKTHESOCLesson 10EDR explained51 / 58

Triage starts with an alert, hunting with a hypothesis

AspectReactive triageProactive hunting
Starting pointAn alert that already firedA hypothesis, no alert required
Data queriedThe flagged event and its immediate contextRaw, unfiltered telemetry across the fleet or window
GoalDisposition this alertFind what detection missed; a new rule or a confirmed gap
Typical techniqueFilter-aggregate-shape on a known entityFrequency analysis / stack counting for rare outliers
Hunters work where coverage is weakest, like the red cells on the ATT&CK Navigator layer from earlier in the course.
HACKTHESOCLesson 10EDR explained52 / 58

The hunting loop

  1. 1Form a hypothesisFrom intel, an incident or a coverage gap: are LOLBins on servers making outbound connections?
  2. 2Query raw telemetryNot the alert queue: Falcon Event Search, Defender Advanced Hunting, S1 Deep Visibility / PowerQuery.
  3. 3Analyze for outliersRare parent-child pairs, unusual command lines, infrequent destinations.
  4. 4Document findingsBenign explanation, escalation, or best of all a gap that becomes a new detection rule.
Hunting queries often read the same tables as scheduled rules. The difference is they are exploratory and frequency-based.
HACKTHESOCLesson 10EDR explained53 / 58

Stack counting: the rarest Office child processes

A pair seen once across ten thousand endpoints beats one seen ten thousand times: attackers rarely replicate their tooling fleet-wide like deployment tools do. A confirmed hit becomes a rule, not a one-off close.
HACKTHESOCLesson 10EDR explained54 / 58

Key takeaways

  1. 01EDR asks whether behavior is bad and records it continuously, catching fileless and LOLBin attacks and enabling retrospective search.
  2. 02Read the process tree first; in raw data build it on unique IDs plus creation time, never the PID alone.
  3. 03Quarantined contains one artifact, not the incident: check persistence, C2, credentials, children and spread.
  4. 04Vendor field names are a lookup; in SentinelOne src is the actor and tgt the object, so read the event type first.
  5. 05Isolation is a tourniquet; kills, packages, file pulls and remote shells are scalpels, and every action is audit-logged.
  6. 06EDR silence is not safety: sensors get blinded, raw telemetry is throttled and ages out, and blind spots need other sensors.

Check your understanding, question 1 of 3

Your EDR reports that a dropped file, svc32.exe, was quarantined. A colleague suggests closing the alert since the file is gone. What is the correct reasoning?

Quarantine addresses one artifact, not the incident. Behavioral detection usually acts after the code already ran, so verify no persistence, live connections, credential theft, surviving children or spread remain. A fleet-wide reimage overreacts.

Check your understanding, question 3 of 3

You self-join DeviceProcessEvents on InitiatingProcessId = ProcessId to find a suspicious child's parent. The result is a signed backup agent that started three days before the child. What is the most likely problem?

PIDs are recycled, so a PID-only join can match any process that once held that number. Match InitiatingProcessId and InitiatingProcessCreationTime to the parent row. InitiatingProcessId is the direct parent; there is no DeviceParentEvents table.
