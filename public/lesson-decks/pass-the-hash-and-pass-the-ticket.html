The attacker never needs to know the actual password.

They steal the cryptographic proof of identity, an NTLM hash or a Kerberos ticket, and replay it directly. No cracking, no guessing.

Open by dissolving the intuition that stealing a password means cracking it. These are MITRE T1550 techniques: use alternate authentication material.

Section 1 of 12

Kerberos, NTLM, hashes and tickets in plain English

The terms both attacks are built on.

HACKTHESOCLesson 37PtH and PtT6 / 48

Two ways Windows proves who you are

NTLM

The older protocol. Proves identity by demonstrating knowledge of the NTLM hash: a one-way fingerprint Windows stores instead of the plaintext.

Kerberos

The newer, ticket-based protocol AD prefers. The KDC issues a TGT at logon; trade it for a service ticket (TGS) per service.

Think of the TGT as a theme-park wristband and each TGS as a one-ride paper ticket.

Both protocols run side by side in a domain. The hash is easy to compute from a password but effectively impossible to reverse.
HACKTHESOCLesson 37PtH and PtT7 / 48
Both the NTLM hash and your Kerberos tickets live in the memory of one process: LSASS.

LSASS is the vault holding 'proof you are you' for as long as your session is active. Read its memory with local admin (credential dumping) and you take the proof itself.

This is the idea the whole lesson is built on: Windows needs the hash or a valid ticket, and both are just data in LSASS. No cracking, just taking and reusing.

Section 2 of 12

The hash or ticket is the credential

Windows requires proof you know the password, and that proof can be stolen.

HACKTHESOCLesson 37PtH and PtT9 / 48

Two consequences that make this so dangerous

Cracking is skipped

No guessing: the secret is used as-is, instantly. A strong, uncrackable password does not help once its hash or ticket is stolen and replayed.

Admin on ONE machine

Dumping LSASS needs local admin on a single host. From there, harvest every credential used on it and replay to reach everywhere those accounts go.

This is the engine of lateral movement across a domain. MITRE T1550: Use Alternate Authentication Material.

The hash and ticket are password-equivalents: the protocols accept them directly. An attacker simply replays the stolen material.

Section 3 of 12

Pass-the-Hash (T1550.002)

Targeting NTLM: possessing the hash is as good as the password.

HACKTHESOCLesson 37PtH and PtT11 / 48
If NTLM only ever uses the hash, then holding the hash is holding the password.

With nothing but the stolen NTLM hash, the attacker authenticates to a remote system and is logged in as the victim, never knowing the password.

That design choice is the whole vulnerability. The remote system runs NTLM, the hash validates, and the attacker never knew or cracked the password.
HACKTHESOCLesson 37PtH and PtT12 / 48

Why it is a lateral-movement powerhouse

Shared local admin

If every machine shares the same local-admin password and hash, one dumped hash unlocks the whole fleet. Exactly what Microsoft LAPS solves.

Privileged domain accounts

A domain admin's hash, harvested from any machine they logged into, lets the attacker pass straight to domain-wide control. This is why tiering matters.

The tell: PtH produces NTLM authentication where you would expect Kerberos.

In a Kerberos-first domain, a burst of NTLM logons between workstations with privileged accounts is anomalous. The DC records NTLM validation as Event 4776; replay also shows 4624 type 3 then 4672.

Section 4 of 12

Anatomy of an NTLM hash

'The hash' hides four different things that behave very differently.

HACKTHESOCLesson 37PtH and PtT14 / 48
Only the stored NT hash is passable. A captured network hash is not.

A stored hash (LM/NT) is a fingerprint on file you can replay anywhere. A network hash (NTLMv1/v2) is a one-time signature mixing that fingerprint with a random challenge.

Confusing them is a common analyst error: a captured NTLMv2 leads to cracking or relay, not passing.
HACKTHESOCLesson 37PtH and PtT15 / 48

The finite family of NTLM-related secrets

NameWhat it isAttack it enables
LM hashLegacy stored hash, pre-Vista, upper-cased and DES-basedTrivially crackable; disabled by default since Vista/2008
NT hashModern stored hash, MD4(UTF-16LE(password)), fast and unsaltedPass-the-Hash and Overpass-the-Hash (it is the RC4 Kerberos key)
NTLMv1 responseA network challenge-response, DES over the server challengeWeak; crackable and relayable, not directly passable
NTLMv2 responseModern network challenge-response, HMAC-MD5 over challengesOffline crackable (Responder) or NTLM-relayed; not passable
The NT hash is unsalted and never changes until the password does, so the same account shows the same NT hash on every machine. One dump unlocks the fleet; LAPS and hash-rotation are the structural fixes.

Section 5 of 12

Worked example: dump and replay

The telemetry an analyst sees as the hash is dumped and then replayed.

HACKTHESOCLesson 37PtH and PtT17 / 48

The LSASS dump as the defender sees it: Sysmon Event ID 10

  • 0x1410 includes VM_READ: the right needed to read LSASS memory
  • An unbacked CallTrace region is common with credential-dumping tools
The attacker already holds local admin and reads LSASS to list cached credentials. The defender's signal is the handle-open itself: a non-security process opening lsass.exe with memory-read rights.
HACKTHESOCLesson 37PtH and PtT18 / 48

Reading the LSASS-access event field by field

The same four fields separate an EDR scanning LSASS from a dumper reading it.

FieldBenign baselineWhy this instance is suspicious
TargetImageAV and EDR open lsass.exe legitimatelyA binary from Users\Public or Temp has no such reason
GrantedAccess0x1000, query limited info only, is harmless0x1410 adds VM_READ, the right to read LSASS memory
CallTraceBacked by known, on-disk module pathsAn UNKNOWN unbacked region points to injected code
SourceUserA service account whose job is diagnosticsAn account that never runs memory-reading tools
This slide turns the raw dump event into a decision: read these four fields together before escalating, because any one alone has benign explanations.
HACKTHESOCLesson 37PtH and PtT19 / 48

The replay lands on the target: Event 4624

  • Type 3 is a network logon; NTLM where Kerberos is expected is the tell
  • A following Event 4672 confirms a privileged account just logged in
A hash-replay tool injects the stolen NT hash into a new process that authenticates as svc-backup over NTLM. For a privileged service account, NTLM here is exactly the anomaly analysts hunt.
HACKTHESOCLesson 37PtH and PtT20 / 48

Pass-the-Ticket leaves almost no trace on the target

  • Extract then injectA valid TGT or service ticket is pulled from LSASS memory and loaded into the attacker's own logon session.
  • No new logon eventInjecting a ticket into the existing session creates NO new 4624: unlike Pass-the-Hash, there is nothing fresh to catch on the target.
  • Where to look insteadAn injected TGT requests fresh service tickets, so hunt 4769 anomalies and LSASS access (Sysmon 10) on the source host.
Type 9 (NewCredentials) is NOT the Pass-the-Ticket tell. It appears instead for Pass-the-Hash and Overpass-the-Hash, written on the source host where the tool runs, and worth correlating with LSASS access there.

Section 6 of 12

Pass-the-Ticket (T1550.003)

The Kerberos equivalent: steal and replay a ticket, not a hash.

HACKTHESOCLesson 37PtH and PtT22 / 48

What a stolen ticket leaves behind, stage by stage

  1. 1Ticket taken from memoryAccess to lsass.exe on the source host: Sysmon Event 10 is the precursor to look for.
  2. 2Reused in another sessionNo new 4768 on the DC: the ticket was already issued, so nothing fresh is logged for the TGT.
  3. 3Presented to services4769 requests or service access for the account from a host it normally never uses.
  4. 4Reach equals the victim'sA stolen TGT reaches anything the victim can; a stolen service ticket only that one service. Scope accordingly.
As organisations reduce NTLM to blunt Pass-the-Hash, Pass-the-Ticket becomes the natural successor: it abuses the protocol that replaced NTLM.
HACKTHESOCLesson 37PtH and PtT23 / 48
Ticket lifetime is the defensive lever specific to Pass-the-Ticket.

A TGT typically expires after about 10 hours, so a stolen legitimate ticket is only useful within its validity window. A forged ticket with an absurd lifetime is itself a detection signal.

PtT is also the foundation for Golden and Silver Ticket attacks, which are PtT with a forged rather than a stolen ticket.

Section 7 of 12

Overpass-the-Hash (Pass-the-Key)

The bridge: turn a stolen hash into a legitimate Kerberos ticket.

HACKTHESOCLesson 37PtH and PtT25 / 48
For RC4-HMAC, the Kerberos key is literally the NTLM hash.

So an attacker holding the hash already holds a valid Kerberos key. Walk the foreign banknote into the bank (the KDC), exchange it for local currency (a TGT), and spend indistinguishably.

This solves the attacker's problem: classic PtH produces NTLM, which modern defences hunt and disable. Overpass-the-Hash makes every hop look like ordinary Kerberos.
HACKTHESOCLesson 37PtH and PtT26 / 48

Overpass-the-Hash on the DC: a lone Event 4768

  • 0x17 (RC4) where AES is normal is the downgrade tell
  • A TGT request from a host the account never logs on from is anomalous
An attacker holding the NT hash already holds the RC4 Kerberos key, so a hash-replay tool can request a genuine TGT with no plaintext. AES256 is stealthier because requesting RC4 is itself a downgrade signal.
HACKTHESOCLesson 37PtH and PtT27 / 48
'We disabled NTLM' is not the end of the credential-replay story.

Hunting only for Event 4776 misses this. The tells shift to Kerberos: a TGT request (4768) from an odd host, or RC4 (0x17) where AES is expected.

The hash is still a Kerberos key, so disabling NTLM only forces the attacker onto the Kerberos path, where ticket lifetime and source host also fall out of baseline.

Local vs remote execution in the logs

The same technique writes different events on each machine. Know which box holds which evidence.

HACKTHESOCLesson 37PtH and PtT29 / 48

Where the evidence lands: foothold, target, domain controller

Read across a row: each stage of replay leaves a different trace on each machine involved.

StageSource host (the foothold)Target host or DC
Credential accessSysmon 10 on lsass.exe, plus the process that opened itNothing yet
Pass-the-Hash4624 Type 9 (NewCredentials), logon process seclogo4624 Type 3 with NTLM from the foothold's IP; 4776 on the DC
Overpass-the-Hash4624 Type 9 on the source4768 on the DC with RC4 (0x17) for an AES-capable account
Pass-the-TicketTicket reuse creates no new logon4769 or service access from an unusual host; no fresh 4768

Correlate the foothold's Type 9 or lsass access with the target's Type 3 NTLM logon from that same IP.

Tools change every year; these events do not. Hunt the evidence, never a tool name: renamed or custom tooling produces the same rows.
HACKTHESOCLesson 37PtH and PtT30 / 48

Run on the box, or reached from another box?

Executed locally

The host's own process tree tells the story: a parent, a command line and a user. Sysmon 1, 4688 and EDR process events all sit on the same machine.

Arrived over the network

The target shows a logon (4624 Type 3) and a process or service started by it, but the cause lives elsewhere. Pivot to the source IP's own telemetry.

No local parent story on the target means the answer is on the source host: follow the IpAddress field.

This one habit, asking where the cause lives, turns a confusing single-host alert into a two-host chain you can scope.

Section 10 of 12

Detection and defence

Both replay legitimate credentials, so hunt anomalies and remove the stealable secret.

HACKTHESOCLesson 37PtH and PtT34 / 48

The hash or ticket is the credential, replayed directly

Walk the two halves of the figure, then the three defence adjectives: unstealable, unique, low-value.
HACKTHESOCLesson 37PtH and PtT35 / 48

Detection signals, loudest first

  • LSASS access (the precursor)A process opening LSASS (Sysmon Event ID 10) is often the earliest, clearest warning, before any replay.
  • NTLM where Kerberos fitsA rise in NTLM (Event 4776 on the DC) between workstations or with privileged accounts is a Pass-the-Hash smell.
  • Anomalous network logons4624 type 3 from unusual sources then 4672, or one privileged account hitting many hosts.
  • Ticket anomaliesAbnormal lifetimes or encryption, or a ticket used from a host different from the one that obtained it.
Both attacks require stealing the secret first, which is why the LSASS access event precedes every replay and is the signal to catch earliest.
HACKTHESOCLesson 37PtH and PtT36 / 48

Defences: remove the secret and limit its reach

Credential Guard

Isolates secrets in a virtualised container so they cannot be dumped by ordinary means. Attacks the root: the hash/ticket is unstealable.

LAPS

A unique local-admin password per machine, so one stolen hash unlocks exactly one host, not the fleet.

Tiering

Keeps privileged credentials off the machines most likely to be compromised, so a workstation breach yields no domain-admin hash.

Plus: reduce NTLM and shorten ticket lifetimes to limit how long a stolen ticket is useful.

You cannot stop Windows from using hashes and tickets; that is how authentication works. You make the secret unstealable, unique, and low-value.

Detection engineering: fields and hunt queries

Correlate three telemetry layers into one defensible chain.

HACKTHESOCLesson 37PtH and PtT38 / 48

Three layers, three questions

LayerSource and eventWhat it reveals
Source hostSysmon Event ID 10, process opening lsass.exeThe credential dump that precedes every replay
Domain ControllerEvent ID 4776, NTLM credential validationNTLM used where Kerberos is expected
Target hostEvent ID 4624, LogonType 3 or 9, NTLM packageThe replay actually landing
Event 4624's WorkstationName often fails to match the account's normal host: a service account on two known servers suddenly shows a logon whose workstation and source IP belong to a user laptop.
HACKTHESOCLesson 37PtH and PtT39 / 48

Correlate source and target into one chain

  1. 1Pivot on the target IPUse the 4624 IpAddress to identify the source host.
  2. 2Look back on the sourceFind Sysmon 10 access to LSASS a few minutes earlier: the dump.
  3. 3Check the DCConfirm 4776 NTLM validation for the same account, workstation-to-workstation.
  4. 4Read the sequenceDump on host A, then NTLM validation at the DC, then 4624 NTLM logon on host B.
No single event proves theft; the sequence does. A Sysmon 10 pointing at lsass.exe with GrantedAccess like 0x1410 and an unbacked CallTrace is common with dumpers.
HACKTHESOCLesson 37PtH and PtT40 / 48

KQL: one identity, NTLM logons fanning out

  • Hosts >= 3 surfaces the lateral-movement fan-out
  • Join back to Sysmon Event ID 10 on the source to confirm the dump
This surfaces the middle-to-end of the chain: one identity producing NTLM network logons across several hosts in a short window.

Section 12 of 12

Hardening identities

Protected Users, Restricted Admin, and Authentication Policy Silos.

HACKTHESOCLesson 37PtH and PtT42 / 48

The Protected Users group starves both attacks

Restriction on membersEffect on the attack
Cannot authenticate with NTLM (nor Digest, CredSSP)Blocks Pass-the-Hash for these accounts outright
Cannot use DES or RC4 in Kerberos pre-auth (AES required)Removes weak-cipher fallbacks
Cannot be delegated (constrained or unconstrained)Cuts a common escalation path
TGT lifetime capped at 4 hours, non-renewableShrinks the Pass-the-Ticket reuse window
Put Tier 0 admins here; keep service accounts and anything that needs NTLM out, or they break. A side effect: any Event 4776 naming a member is by definition an anomaly worth chasing.
HACKTHESOCLesson 37PtH and PtT43 / 48

Two more controls that change what your logs contain

Restricted Admin / RCG

Restricted Admin RDP leaves no reusable creds on the target; Remote Credential Guard keeps them on the client. Note: Restricted Admin uses a network logon, itself a PtH target, so it complements tiering.

Auth Policy Silos

A Tier 0 account may only authenticate from designated Tier 0 hosts. The KDC refuses tickets elsewhere, so a domain-admin hash replayed from a user workstation is rejected at the protocol level.

Detection tells you a replay is happening; hardening removes the secret or rejects the replay outright.

Silos make a stolen secret useless outside its home. Verify Protected Users membership regularly, and treat any 4776 for a member as an investigation.

Key takeaways

  1. 01Windows accepts the NTLM hash (PtH) or a Kerberos ticket (PtT) as proof directly; both are password-equivalents in LSASS.
  2. 02A strong password does not help once the hash or ticket is stolen, and dumping LSASS needs admin on just one host.
  3. 03Only the stored NT hash is passable; a captured NTLMv1/v2 network hash leads to cracking or relay, not passing.
  4. 04Overpass-the-Hash turns the NT hash into a real TGT, so disabling NTLM alone does not end credential replay.
  5. 05The earliest signal is LSASS access (Sysmon 10); defend with Credential Guard, LAPS, tiering and Protected Users.

A workstation that never runs admin tooling logs Event 4624 Logon Type 9 (NewCredentials), Logon Process seclogo, with a privileged service account as Network Account Name. Why is this a strong replay signal here?

Type 9 is written where a process launches with alternate credentials for outbound use: the runas /netonly mechanism PtH and Overpass-the-Hash tools use. Type 3 is a network logon, and injecting a ticket makes no new logon, so Pass-the-Ticket makes no Type 9.
