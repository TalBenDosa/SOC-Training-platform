Section 1 of 9

What Advanced Hunting is

A query-based tool over raw Defender telemetry, typically the last 30 days.

HACKTHESOCLesson 66Advanced Hunting with KQL6 / 69

Reactive triage versus proactive hunting

Reactive

Respond to alerts and incidents the platform generated. Essential, but by definition limited to what the built-in detections catch.

Proactive (hunting)

Start from a hypothesis, e.g. an attacker would run whoami right after landing, and query the telemetry directly to test it. Hunting finds what detections missed.

Advanced Hunting searches endpoints, email, identities and cloud apps, typically the last 30 days of events.

Use the lesson's second hypothesis too: they might use a renamed copy of a system tool.
HACKTHESOCLesson 66Advanced Hunting with KQL7 / 69

A hunt, from hypothesis to outcome

  1. 1State a hypothesisAn attacker who lands on a host will run whoami to see who they are.
  2. 2Name the evidenceProcess launches, so DeviceProcessEvents.
  3. 3QueryFind whoami.exe launches and group them by parent process.
  4. 4ReviewSeparate admin and script use from parents that make no sense.
  5. 5OutcomeAn incident, a new detection, or a documented "nothing found".
A null result is still a result: write down what was searched and over what window. It tells the next hunter what has already been ruled out.
HACKTHESOCLesson 66Advanced Hunting with KQL8 / 69

Where a hypothesis meets evidence

  • Faint patternsA single unusual process, a rare parent-child relationship, one user's odd sign-in pattern that never crossed an alert threshold.
  • Scoping incidentsOnce you know the technique from one machine, hunt the same pattern everywhere to find every affected host.
  • Built on KQLKusto Query Language, a read-only language designed for fast searching and filtering of huge event tables.
Hunting queries the same underlying data that feeds alerts, which is why it can see what the alerts did not.
HACKTHESOCLesson 66Advanced Hunting with KQL9 / 69

Testing the whoami hypothesis

  • Every whoami launch in the last week, case-insensitive
  • Grouped by the parent process that launched it
  • Rarest parents first: that is where the odd ones sit
Grouping by parent is the trick: whoami itself is common, but who runs it is very telling.

Section 2 of 9

Enough KQL to be dangerous

The operator toolkit that carries you through most real hunts.

HACKTHESOCLesson 66Advanced Hunting with KQL12 / 69

Nine core operators

  • whereFilter to the rows you care about.
  • projectChoose which columns to show, optionally rename them.
  • extendAdd a computed column without removing the existing ones.
  • summarizeAggregate: count, group, min/max, e.g. summarize count() by DeviceName.
  • sort by / top / distinctOrder rows, take the N most extreme, or list unique values.
  • let / joinName a value for reuse; combine two tables on a shared column.
sort by and order by are interchangeable. Each operator takes rows in from the left of the pipe and produces new rows out.
HACKTHESOCLesson 66Advanced Hunting with KQL13 / 69

How rows flow through a KQL pipeline

  1. 1Name a tableEvery row of DeviceProcessEvents in the retention window.
  2. 2where shrinks rowsOnly rows that match each filter continue down the pipe.
  3. 3project shrinks columnsOnly the columns you named continue.
  4. 4summarize collapsesMany rows become one row per group, with counts.
  5. 5sort / top ordersThe final, small table is ordered for reading.
Each pipe hands a table to the next operator. Picture the table getting smaller at every step; if it is not, the query is in the wrong order.
HACKTHESOCLesson 66Advanced Hunting with KQL14 / 69

Read a real query as a sentence

  • ago(24h) means 24 hours ago; time filters belong near the top of nearly every query
  • -enc marks encoded commands, a common attacker tell
  • Output: time, device, account and full command line, newest first
Then show the second example: summarize PowerShellCount = count() by DeviceName with top 10 answers which devices ran the most PowerShell.

HACKTHESOCLesson 66Advanced Hunting with KQL17 / 69

Reach for has first

KQL indexes strings as terms. Plain operators are case-insensitive; _cs makes them case-sensitive.

OperatorMatch styleNotes
=~Whole value equals, case-insensitiveUse when case may vary
has / has_csWhole indexed term presentFast; preferred for word matches
has_any / has_allAny / all of several terms presentOne pass for a watchlist
containsSubstring anywhereSlow character scan; avoid at scale
in / !inValue is / is not in a setUse in~ for insensitive
matches regexValue matches a regular expressionMost flexible, slowest
Fall back to contains only for a mid-term substring like exec in myexecutable.dll. On 30 days of endpoint data it is the difference between two seconds and a timeout.
HACKTHESOCLesson 66Advanced Hunting with KQL18 / 69

has vs contains on one real value

Value: C:\Tools\myexecutable.dll. KQL indexes it as terms: C, Tools, myexecutable, dll.

contains "exe"

Matches. It scans characters and finds exe inside myexecutable: a false hit, and a slow scan.

has "exe"

No match. exe is not a whole term in this value, so the index answers instantly.

has "myexecutable"

Matches. A whole indexed term: fast and exact.

Terms break at non-alphanumeric characters such as backslashes and dots. Once students see the term list, the has rule becomes obvious.

Scalar and aggregation functions

Operators shape rows; functions compute values inside those rows.

HACKTHESOCLesson 66Advanced Hunting with KQL26 / 69

Time is the spine of every hunt

FunctionReturnsExample use
ago(30d)A timestamp N units in the pastwhere Timestamp > ago(30d)
now()The current timeextend Age = now() - Timestamp
bin(Timestamp, 1h)Rounds a time down to a bucketsummarize count() by bin(Timestamp,1h)
startofdayStart of that calendar dayextend Day = startofday(Timestamp)
datetime_diff("hour", a, b)Whole units between two timesDwell-time calculations
Suffixes: d, h, m, s, so ago(90m) is ninety minutes ago. bin() turns a flood of rows into a time series for render timechart.
HACKTHESOCLesson 66Advanced Hunting with KQL27 / 69

bin() turns rows into a time series

  • Every failed logon in the last week
  • bin(Timestamp, 1h) puts each row in its hour: 168 buckets
  • The chart shows the daily rhythm, and the hour that breaks it
Without bin, summarize by Timestamp would give one row per exact timestamp, which is no aggregation at all.
HACKTHESOCLesson 66Advanced Hunting with KQL28 / 69

Two aggregations beginners miss

Aggregation functions only ever appear inside a summarize.

How many distinct things

dcount(X)

Password spray is one source IP failing against many distinct accounts: summarize dcount(AccountName) by RemoteIP | where dcount_AccountName > 20.

Latest full record

arg_max(T, *)

summarize arg_max(Timestamp, *) by DeviceName gives the most recent state of each device when a table has many rows per entity.

Also: count(), countif(), sum()/avg(), min()/max(), make_set()/make_list().

Counting is triage, dcount is fan-out detection (spray, scanning, mass access), arg_max is state.
HACKTHESOCLesson 66Advanced Hunting with KQL29 / 69

dcount in action: spotting a password spray

  • Failed logons per source IP over one day
  • dcount(AccountUpn): how many different accounts each IP failed against
  • Many accounts, few attempts each: the shape of a spray
The threshold of 20 is a starting point. Tune it to your environment before turning it into a detection.
HACKTHESOCLesson 66Advanced Hunting with KQL30 / 69

String and logic helpers carve signal from noise

  • tolower() / toupper()Case-normalise before comparing.
  • split() / substring()Last path segment or a fixed slice, e.g. split(FolderPath, "\\")[-1].
  • extract("re", n, X)Pull the n-th regex capture group out of text.
  • iff() / case()Inline if/else labelling, or bucket into categories.
  • strcat() / replace_string()Build a display key or normalise a value.
  • isnotempty() / isempty()Guard against blank strings.
Knowing the group by name means the function is ready when a hypothesis forms mid-incident, with no fumbling while the attacker moves.
HACKTHESOCLesson 66Advanced Hunting with KQL32 / 69

Helpers inside a real query: label where processes run from

  • tolower() normalises case once, so comparisons are simple
  • case() labels each row: system folder, temp folder, or other
  • Processes started from temp folders, grouped by parent
Executables running from temp folders are a classic dropper pattern, as in the update.exe example from the XDR lesson.

Worked multi-step hunts

Real investigations rarely stop at one table.

HACKTHESOCLesson 66Advanced Hunting with KQL34 / 69

Hunt 1: from a phishing click to on-device execution

let names the intermediate result. The between time window is what turns two unrelated tables into a causal-looking sequence worth investigating: processes within 15 minutes after an allowed click. Join UPN to UPN: matching AccountUpn to the bare AccountName silently returns zero rows.
HACKTHESOCLesson 66Advanced Hunting with KQL35 / 69

Hunt 1, line by line

Part of the queryWhat it does
let SuspiciousClicks = ...;Names the clicks result so it can be reused below
ActionType == "ClickAllowed"Only clicks Safe Links let through: the risky ones
project ClickTime = Timestamp, ...Renames columns so the two timestamps do not collide
join kind=inner (...) on ... AccountUpn == ... ProcUpnPairs each click with processes run by the same user
where ProcTime between (ClickTime .. ClickTime + 15m)Keeps only processes in the 15 minutes after the click
project ... / sort by ClickTime descShows the click and the processes side by side, newest first
The time window is the analytic idea; everything else is plumbing. Without it, every process the user ever ran would match.
HACKTHESOCLesson 66Advanced Hunting with KQL36 / 69

Hunt 2: one bad IP across every sensor

union stacks raw connections and existing alerts in one timeline, telling you at once whether this is a new finding or something Defender already flagged.
HACKTHESOCLesson 66Advanced Hunting with KQL37 / 69

Reading Hunt 2: new finding or already known?

Only network rows

Devices talked to the IP but no alert mentions it. Defender has not flagged this: you found something new.

Alert evidence rows too

Defender already flagged the IP. Open those alerts and incidents before duplicating work.

No rows at all

Nothing reached it in 7 days. Record the null result, and check retention covers your window.

The union is not just convenience: putting both sources in one result answers the "is this known?" question at a glance.
HACKTHESOCLesson 66Advanced Hunting with KQL38 / 69

The shape every good hunt follows

  1. 1Pick a starting factA click, an indicator.
  2. 2Find the next tableThe table that captures the next thing an attacker would need to do.
  3. 3Connect the tablesJoin or union on a shared entity or time window.
  4. 4Widen only as far as evidence goesStart narrow; this separates a focused hunt from a fishing expedition through terabytes.
Same shape as the phishing walkthrough in the MDO lesson.

Section 6 of 9

Advanced patterns: joins, prevalence, time series

Four techniques in almost every serious hunt, each with a trap that gives a confident wrong answer.

HACKTHESOCLesson 66Advanced Hunting with KQL40 / 69

A bare join is innerunique and silently drops rows

The default kind deduplicates the left side on the key first, keeping one arbitrary row per key. State the kind every time.

KindReturnsTypical hunting use
innerEvery matching left/right pairCorrelating each event with every related event
innerunique (default)Left side deduplicated on the key firstRarely what a hunter wants; avoid by accident
leftouterAll left rows, right columns empty where no matchEnrichment that must not lose rows
leftantiLeft rows with no match on the rightSeen here but never there: devices with a process but no AV heartbeat
leftsemiLeft rows that have a match, left columns onlyFiltering one table by the keys in another

For a small reference table (watchlist, device-owner list), lookup is cheaper and keeps unmatched left rows by default.

Every logon joined to every process by the same account gives processes matched to one logon, not all of them, and nothing warns you. That is why a SQL habit of a bare join is dangerous here.
HACKTHESOCLesson 66Advanced Hunting with KQL41 / 69

See the innerunique trap on two tiny tables

  • datatable builds a test table inline: ideal for checking join behaviour
  • The left side has two rows for r.katz; innerunique keeps only one
  • Writing kind=inner returns both, which is what a hunter expects
Have students run this themselves. Seeing a row vanish with no warning is what makes "always state the kind" stick.
HACKTHESOCLesson 66Advanced Hunting with KQL42 / 69

How prevalence analysis works

  1. 1Group by the thingA command line, a file hash, or a parent-child pair.
  2. 2Count distinct devicesdcount(DeviceId): how widespread is it across the fleet?
  3. 3Common is baselineSeen on thousands of devices: almost always legitimate.
  4. 4Rare and new is the leadOne or two devices, first seen recently.
  5. 5Exclude noisy hostsBuild servers and admin workstations are rare by nature.
Prevalence uses the fleet as its own baseline, so you do not need to know in advance what malicious looks like.
HACKTHESOCLesson 66Advanced Hunting with KQL43 / 69

Prevalence: let the fleet tell you what is normal

  • dcount(DeviceId) per command line: thousands of devices is baseline, one or two is rare
  • Prevalence over the full 30 days, but report only items first seen in the last 7
  • Exclude known-unusual hosts (build servers, IT admin workstations) or they dominate
This turns a 30-day table of millions of rows into a short review list. The same idea works for a hash or a parent-child pair.

Time series: flag breaks from each account's own pattern

  • make-series builds evenly spaced hourly buckets per account
  • series_decompose_anomalies() flags buckets that break the seasonal pattern
  • No fixed threshold: 20 files an hour normally, 3,000 at 02:00 stands out
The same structure finds beaconing: bucket one device's connections to one destination per minute and look for an unnaturally regular count across many hours.
HACKTHESOCLesson 66Advanced Hunting with KQL46 / 69

Fixed threshold vs each account's own baseline

Alert above 500 files an hour

Fixed threshold

Floods you with busy service accounts that always exceed it, and misses a quiet user jumping from 5 to 400.

series_decompose_anomalies

Own baseline

Each account is compared with its own hourly and daily rhythm, so a break stands out whatever the account's normal level.

The extra Ops > 10 * Baseline filter in Hunt B keeps only large breaks, which removes small statistical blips.
HACKTHESOCLesson 66Advanced Hunting with KQL47 / 69

Decode encoded PowerShell inside the query

PowerShell encodes as UTF-16LE, so strip the null bytes after base64_decode_tostring(), then search with has.

externaldata can also read a CSV or JSON watchlist from a URL at query time and join it to DeviceFileEvents or DeviceNetworkEvents. Note that externaldata, joins and unions all rule a query out of Continuous (NRT) detections.

Section 7 of 9

Common pitfalls and query performance

A slow or wrong query costs minutes during a live incident.

HACKTHESOCLesson 66Advanced Hunting with KQL49 / 69

Pitfalls that produce wrong results

No time filter

Without where Timestamp > ago(...) the query scans a very large window. The single most common mistake.

Case surprises

FileName == "PowerShell.exe" will not match powershell.exe. Use =~ or tolower().

contains vs has

contains "exe" matches myexecutable.dll; has "exe" matches only a distinct term.

Silent empty joins

DOMAIN\user versus user@domain.com returns zero rows. Run count() on each side before trusting it.

The dangerous one is the empty join: a silently-empty hunt looks identical to nothing bad happened.
HACKTHESOCLesson 66Advanced Hunting with KQL50 / 69

Check both sides before trusting a join

  • Both sides return rows on their own: data exists
  • The values do not look alike: the join can never match
  • Zero join rows plus non-empty sides means a key problem, not a clean bill
This check takes a minute and prevents the most dangerous false conclusion in hunting: "nothing happened".
HACKTHESOCLesson 66Advanced Hunting with KQL51 / 69

Habits that keep queries fast

  1. 1Filter early, filter narrowMost selective where first; constrain time before anything else.
  2. 2Project before join or summarizeDrop unneeded columns so KQL shuffles less data.
  3. 3Prefer has over containsOn large text fields like command lines, when a whole-word match is enough.
  4. 4Test on a short windowValidate against ago(1h) before widening to ago(30d).
Ten wrong rows are easy to catch; ten thousand are not. A slow query in an incident means delayed containment.
HACKTHESOCLesson 66Advanced Hunting with KQL52 / 69

Slow query, fast query: four rewrites

SlowFastWhy
where ProcessCommandLine contains "mimikatz"where ProcessCommandLine has "mimikatz"Indexed term lookup instead of a character scan
Time filter at the end of the querywhere Timestamp > ago(1d) firstLess data enters every later step
Join two full tables, then filterFilter and project each side, then joinSmaller sides, less data shuffled
No project before summarizeProject only the needed columnsWide rows cost memory and time
Each rewrite gives the same answer faster. During an incident, faster means containment starts sooner.

Section 8 of 9

From hunt to custom detection

A saved query Defender runs on a schedule, raising alerts on every match.

HACKTHESOCLesson 66Advanced Hunting with KQL54 / 69

The hunt-to-detection workflow

  1. 1HuntWrite and refine the KQL until it reliably surfaces the pattern with few false positives.
  2. 2TuneExclude known-good behaviour, such as an approved admin script's exact command line.
  3. 3Create the custom detectionSet frequency, severity and title, and map the entities (device, user, file) so alerts correlate.
  4. 4Add response actionsOptionally isolate a device, run an AV scan, or mark a user as compromised.
A detection that fires constantly on benign activity is worse than none, because it trains analysts to ignore it.
HACKTHESOCLesson 66Advanced Hunting with KQL55 / 69

Detection frequency sets the lookback

Rules on Defender data run on one of five frequencies.

FrequencyLookback or constraint
Every 24 hours30 days
Every 12 hours48 hours
Every 3 hours12 hours
Every hour4 hours
Continuous (NRT)Single-table only: no joins, unions, externaldata or comment lines

Do not add a Timestamp filter narrower than the lookback: the service already prefilters by it.

This is why the advanced patterns earlier matter: a join or externaldata choice decides which frequencies a rule can use.
HACKTHESOCLesson 66Advanced Hunting with KQL56 / 69

A good hunt can still make a broken detection

  • Return the right columnsTimestamp and ReportId, plus DeviceId for endpoint tables, so the alert scopes and the process tree builds.
  • Recover them after aggregatingsummarize (Timestamp, ReportId) = arg_max(Timestamp, ReportId), count() by DeviceId
  • Expect a capEach rule run generates at most 150 alerts, another reason to tune before you save.
  • Hunting page limits30 days of data, 100,000 rows and 64 MB per query, a 10-minute timeout, and a per-tenant CPU quota.

A heavy saved query can throttle the whole team; the Query resources report shows which queries use the most.

The CPU quota is measured in 15-minute cycles and blocks further queries when exhausted, so one careless shared query hurts everyone mid-incident.
HACKTHESOCLesson 66Advanced Hunting with KQL57 / 69

A hunt shaped to become a detection

  • Behaviour, not a filename: an Office app launching a shell or script host
  • Timestamp, ReportId, DeviceId returned: the alert can scope and build a tree
  • No time filter: the rule's lookback already limits the window
Map DeviceId to the device entity and AccountName to the user entity when creating the rule, so its alerts correlate into incidents.
HACKTHESOCLesson 66Advanced Hunting with KQL58 / 69

Tuning the rule before you save it

Noise sourceHow to exclude it narrowly
An approved add-in that starts cmd.exeExclude its exact command line, not all cmd.exe
A finance macro used by one teamExclude that file hash or signed publisher

Broad exclusions are how attackers slip through tuned rules. Exclude the specific known-good thing and record who approved it.
HACKTHESOCLesson 66Advanced Hunting with KQL59 / 69

Principles that keep the loop healthy

  • Ground hunts in ATT&CKEach technique suggests a query: how would I see T1059 PowerShell execution in DeviceProcessEvents?
  • Behaviour over stringsA system tool spawning from an unusual parent generalises better than one malware's exact filename.
  • Document intentSay what a detection is meant to catch so the next analyst understands why it fired.

This is detection engineering in miniature, and Advanced Hunting is the workbench.

The best hunts graduate into detections, freeing analysts to hunt for the next gap.

Parsing text and reusable queries

Pull fields out of messy strings, and never write the same hunt twice.

HACKTHESOCLesson 66Advanced Hunting with KQL61 / 69

parse turns a command line into columns

  • * skips text you do not need; quoted literals anchor the pattern
  • More efficient than chains of substring() or multiple extract() calls
  • parse kind=regex is more flexible but slower; use it only when literals fail
Input looks like powershell.exe -ExecutionPolicy Bypass -EncodedCommand SQBFAFgA..., and the payload lands in its own column for decoding or matching.
HACKTHESOCLesson 66Advanced Hunting with KQL62 / 69

Choosing a text tool

ToolBest forTrade-off
parseText with fixed literal anchors, like a flag nameFast; fails if the anchor text varies
extract()One value matched by a regular expressionFlexible; one capture group per call
split()Values separated by a known characterSimple; returns an array to index
parse kind=regexSeveral fields with variable surrounding textMost flexible, slowest
Start with parse, fall back to regex only when the literals do not hold. The cheapest tool that works is the right one.

Key takeaways

  1. 01Advanced Hunting queries 30 days of raw Defender telemetry for hypothesis-driven hunting and incident scoping.
  2. 02KQL is a table and a pipeline: name a table, then pipe rows through where, project, summarize, let and join.
  3. 03Map each question to its table, and join or union tables to rebuild cross-domain attack chains.
  4. 04A bare join is innerunique and silently drops rows: always state the kind, and use lookup for small tables.
  5. 05Fleet prevalence with dcount(DeviceId) and make-series anomalies find outliers without hand-picked thresholds.
  6. 06Detections return Timestamp, ReportId and DeviceId, respect their lookback, and cap at 150 alerts per run.

== compares the whole string case-sensitively, so "PowerShell.exe" does not equal "powershell.exe"; =~ or tolower() fixes it. FileName is the bare image name, a missing time filter scans more not less, and term matching describes has, not ==.
