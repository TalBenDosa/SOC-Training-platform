Why networks outgrew the keyboard

Scale, human error and config drift break manual CLI work.

HACKTHESOCLesson 107Network automation and APIs6 / 47

Three ways manual CLI work breaks down

A network is a large body of configuration state repeated across hundreds of devices.

20 hours of typing

Scale

Changing a syslog server on 400 switches at about three minutes each leaves the network half-changed the whole time. A script does it in minutes, in parallel.

    Typos on live gear

    Human error

    The right command on the wrong device, a mistyped mask, a shutdown on the uplink instead of the access port. The CLI has no built-in review step.

      Invisible until it hurts

      Config drift

      A temporary rule never removed, two same-role switches with different SNMP settings. Drift shows up only in an audit, an outage or an incident.

        Ask the class which of the three they have seen in real life. Drift is the sneaky one: nobody decided it, it just accumulated.

        AspectCLI by handAutomation / intent
        Source of truthThe running config on each boxVersion control, an inventory, or a controller database
        Change recordMaybe a ticket and a screenshotA commit, a reviewer, a run log

        Imperative: enter these commands in order. Declarative: this switch must have these settings. Intent: this group may reach that service.

        The deeper shift is imperative to declarative. A tool works out what has to change, and intent-based networking goes one level higher still.
        HACKTHESOCLesson 107Network automation and APIs8 / 47

        Automation multiplies mistakes as well as good changes

        Ask: what is the source of truth, who may change it, how would we know a device stopped matching it?

        • Wide blast radiusA wrong variable pushed to 400 devices is a 400-device outage in one minute.
        • Roll out in wavesTest in a lab, use dry-run modes, then one device, one site, then everything.
        • Screen scraping is fragileParsing CLI text breaks when an upgrade changes spacing or wording. This is why structured APIs exist.
        • One door onlyIf engineers keep making manual CLI changes, the repository and devices diverge: drift with extra steps.
        A source of truth only works if it is the only door. Mature teams treat the manual back door as a policy violation.

        Data formats: JSON, YAML and XML

        Programs cannot reliably read text designed for people, so APIs exchange structured data.

        HACKTHESOCLesson 107Network automation and APIs10 / 47

        Reading JSON means following a path

        Objects in braces, arrays in brackets, keys always double-quoted strings.

        • Second interface status: interfaces array, index 1, key oper_status
        • After json.loads: data['interfaces'][1]['oper_status']
        • null is a value; a missing key is a different situation
        Arrays count from zero in most languages, so the second interface is index 1. Have students say the path aloud before running any code.
        HACKTHESOCLesson 107Network automation and APIs11 / 47

        Where hand-edited JSON breaks

        • Trailing commaA comma after the last item is the top reason a hand-edited file fails to parse.
        • No comments, no single quotesJSON has no comment syntax, and only double quotes work.
        • Types matter1500 is a number, "1500" is a string. YANG-based APIs encode 64-bit integers as strings (RFC 7951).
        • Missing key versus nullThey are different situations, and robust code handles both.
        This is the exact cause behind the quiz-style parse error: someone edited by hand. Indentation in JSON is only cosmetic, unlike YAML.

        Three formats, three jobs

        Is this file for a person to edit or for a program to consume? Which parser will read it?

        FormatUsed forWatch out
        JSON (RFC 8259)Most APIs: objects, arrays, strings, numbers, true/false, nullNo comments, no trailing commas, double quotes only
        YAMLHuman-edited automation files: Ansible playbooks and inventoriesIndentation is syntax, spaces only; yes/no/on/off may become booleans

        YAML is friendlier and easier to get subtly wrong: one misaligned line can silently change the nesting. Quote a value such as no.

        REST APIs: the common language of network automation

        Resources identified by URIs, acted on with HTTP methods, one stateless request at a time.

        HACKTHESOCLesson 107Network automation and APIs14 / 47

        Five HTTP verbs and whether repeating them is safe

        VerbMeaningTypical useIdempotent?
        GETRead a resourceFetch the interface listYes, and safe (changes nothing)
        POSTCreate a resource or trigger an actionAdd a VLAN, request a tokenNo, repeating may create duplicates
        PUTReplace a resource completelyOverwrite one interface configYes
        PATCHModify part of a resourceChange only a descriptionDepends on the API
        DELETERemove a resourceDelete a VLANYes, the end state is the same

        Idempotent: repeating leaves the same state as sending once. Retrying a timed-out PUT is normally safe; a POST may not be.

        Tie this to the quiz: a timed-out POST that is blindly resent can create a duplicate. The safe habit is PUT, or a GET first.
        HACKTHESOCLesson 107Network automation and APIs15 / 47

        Anatomy of a RESTCONF call and its response

        Requests are stateless: each one carries everything the server needs, including credentials.

        • The URI path says which resource
        • Accept = format wanted back; Authorization = who you are
        • Content-Type states the format you are sending
        For POST, PUT and PATCH a body carries the new data. Forgetting Accept is a classic way to get XML when the parser expects JSON.
        HACKTHESOCLesson 107Network automation and APIs16 / 47

        Read the status code before you read the body

        CodeMeaning
        200 OKSuccess, with a body
        201 CreatedA new resource was created
        204 No ContentSuccess with an empty body, common after a PUT
        400Malformed request or body
        401Not authenticated: missing or expired token
        403Authenticated but not permitted
        404Resource not found

        First digit: 2xx success, 3xx redirect, 4xx client got it wrong, 5xx server failed. Also: 409 conflict, 429 too many requests, 500 server error.

        A 401 or 404 is a valid HTTP response, not a Python exception. Scripts must check the status code or call raise_for_status.
        HACKTHESOCLesson 107Network automation and APIs17 / 47

        The same call with curl

        Authenticate once, then present the bearer token in a header on later calls.

        Basic auth sends the password on every request, base64 encoded, which is encoding and not encryption. A token is a bearer credential: whoever holds it is you. Never disable certificate checks to silence a lab error, and never put a token in the URL query string.

        Section 4 of 8

        NETCONF, RESTCONF and YANG data models

        A shared model of configuration and state, carried by two different protocols.

        HACKTHESOCLesson 107Network automation and APIs19 / 47

        YANG is the model; NETCONF and RESTCONF carry the data

        RFC 7950, the model

        YANG

        A modeling language, not a protocol. It defines containers, lists and leaves, their types, and which are config (writable) or state (read-only).

        • ietf-interfaces (RFC 8343) works across vendors
        • Vendors also publish native modules

        RFC 6241, XML over SSH

        NETCONF

        A session protocol on TCP 830. XML RPCs such as get, get-config, edit-config, lock and commit, against running, candidate and startup datastores.

        • Lock, edit candidate, validate
        • Commit atomically or discard

        RFC 8040, HTTP on URIs

        RESTCONF

        The same YANG-modeled data over HTTPS with JSON or XML bodies. Any HTTP client works, but each request is applied on its own.

        • First URI segment names the module
        • No multi-step lock-and-commit
        YANG itself never travels on the wire as the data. Think of it as the schema both sides agree on; the two protocols carry data that conforms to it.
        HACKTHESOCLesson 107Network automation and APIs20 / 47

        A NETCONF get-config RPC for the interfaces

        • source running: read the active config
        • The subtree filter narrows the reply to the ietf-interfaces data
        • Namespaces say which YANG model each element belongs to
        The client first opens an SSH connection to the NETCONF subsystem on TCP 830 and exchanges capabilities, then sends RPCs like this one.
        HACKTHESOCLesson 107Network automation and APIs21 / 47

        NETCONF versus RESTCONF

        Do I need an atomic multi-step change, or a quick read from a script?

        AspectNETCONFRESTCONF
        Defined inRFC 6241RFC 8040
        TransportSSH, TCP 830HTTPS, TCP 443
        EncodingXMLJSON or XML
        OperationsRPCs: get, get-config, edit-config, commit, lockHTTP verbs: GET, POST, PUT, PATCH, DELETE
        TransactionsCandidate datastore, lock, commit, rollbackEach request applied individually
        SessionStatefulStateless
        Transactions are the deciding row. NETCONF can stage, validate and commit all or nothing; RESTCONF is lighter for scripts but earlier requests are not undone if a later one fails.
        HACKTHESOCLesson 107Network automation and APIs22 / 47

        Four traps when you script against YANG interfaces

        • Slashes in list keysPercent encode them: GigabitEthernet1%2F0%2F1, or the server looks for a different path and returns 404.
        • Module prefix in JSONThe top-level key carries it, as in ietf-interfaces:interface. Omitting it gives a 400.
        • Models differ by versionA path may be deprecated on the next release, e.g. operational data moving from interfaces-state to interfaces.
        • Not on by default everywhereNETCONF and RESTCONF must be enabled and access-controlled on the device.
        Ask which YANG module and revision the device implements before trusting a path copied from another box.

        Config management tooling: Ansible and Python

        Ansible is declarative and agentless; Python gives full control when you need logic.

        HACKTHESOCLesson 107Network automation and APIs24 / 47

        Ansible in four pieces

        It connects over SSH CLI, NETCONF or HTTPS APIs, runs modules, and reports whether each task changed anything.

        • InventoryThe devices grouped by role, plus variables such as the connection type.
        • PlaybookA YAML file describing desired state as a list of tasks.
        • ModuleThe unit of work, e.g. one that manages config lines or gathers facts.
        • VaultEncryption for secrets, so passwords are not plain text in the repository.
        Inventory groups such as access_switches carry variables like ansible_network_os and ansible_connection, so the playbook stays short.
        HACKTHESOCLesson 107Network automation and APIs25 / 47

        A tiny playbook: ensure the NTP server

        • hosts picks a group from the inventory
        • ios_config compares desired with current state
        • Preview first: ansible-playbook with --check --diff
        This is the declarative idea in nine lines: say what must be true, and the module works out whether anything needs to change.
        HACKTHESOCLesson 107Network automation and APIs26 / 47

        Idempotency: why a clean second run proves something

        1. 1PreviewRun with --check --diff to see what would change before touching production.
        2. 2First runReports changed on each switch that is missing the line.
        3. 3Second runReports ok with zero changes: the same result as running once.
        4. 4Beware raw commandsShell-style tasks resend every run and report changed every time, so a clean second run proves nothing.
        Always ask: is this task idempotent, and how do I know? Ansible variable precedence can also surprise you, so keep group variables simple and read the diff.

        Controllers, SDN and intent-based networking

        A central brain holds the desired state of the whole network and pushes it to devices.

        HACKTHESOCLesson 107Network automation and APIs29 / 47

        Three planes, one controller

        SDN separates and centralizes decision-making; devices focus on forwarding.

        • Data planeForwards packets.
        • Control planeDecides where packets should go.
        • Management planeConfigures and monitors the device.
        • Intent-based networkingDescribe the outcome; the controller deploys it and keeps verifying the network matches.

        In practice most enterprise products keep distributed control planes and centralize management and policy.

        Example intent: contractors may reach the guest portal but not the finance servers. Cisco DNA Center is a controller of this kind for campus networks, with inventory, templates, assurance and a REST intent API.
        HACKTHESOCLesson 107Network automation and APIs30 / 47

        Northbound faces up, southbound faces down

        The names are relative to the controller.

        Faces applications

        Northbound API

        Talks to applications, scripts, portals and other systems. Typically REST over HTTPS with JSON.

        • A script asks for all unhealthy devices

        Faces the devices

        Southbound API

        Talks to the network devices with NETCONF, RESTCONF, SSH CLI, SNMP or OpenFlow.

        • The controller pushes a VLAN to 50 switches

        A script calls one northbound API; the controller translates it into whatever each device speaks.

        Tie to the quiz idea: a portal request arriving from above is northbound, the configuration pushed down to the switches is southbound.
        HACKTHESOCLesson 107Network automation and APIs31 / 47

        Controller pattern: authenticate once, then call with the

        • Paths and header names differ by product and version
        • Always read the vendor's API reference
        This is the northbound pattern: one token, one call, and a JSON list of every managed device. Scripts written against one controller version can break after an upgrade.
        HACKTHESOCLesson 107Network automation and APIs32 / 47

        Four ways a controller goes wrong

        Out-of-band drift

        A direct CLI change makes the controller's view and the device disagree. Good controllers flag it; many teams forbid direct changes.

          Concentrated risk

          A controller can configure every device. Whoever owns its credentials or token owns the network, so harden it.

            Controller outage

            Devices should keep forwarding, but changes and assurance stop. Know what degrades.

              Version coupling

              Controller upgrades can change API behavior and break scripts written against the old version.

                Ask: is this setting owned by the controller or the device? What happens if the controller disappears?

                The second card is the one a SOC cares about most. The controller's credentials are the keys to the entire network.

                Why this matters to a SOC analyst and defender

                Every API call is a loggable event, and every management API is an administrative login.

                HACKTHESOCLesson 107Network automation and APIs34 / 47

                A management API access log line

                Source, identity, time, method, URI, status and user agent, wrapped here for display.

                Read it field by field: automation account, a write method, success with an empty body, at 03:12, with a script user agent. Whether it is normal depends on the source host and a matching change record.
                HACKTHESOCLesson 107Network automation and APIs35 / 47

                Detections you can build on API logs

                • Writes from unknown sourcesPUT, POST, PATCH or DELETE from a host not on the list of automation hosts.
                • Valid tokens, odd contextTokens used at unusual hours, or from a new IP or geography.
                • 401 bursts then a 200Credential guessing that succeeded.
                • Rapid GET sweepAcross many /restconf/data paths: config recon, since a full config reveals topology, ACLs and sometimes secrets.
                • New NETCONF sessionsOn TCP 830 from hosts that never used it before.
                • Commit with no ticketConfig saved or commit events with no matching change ticket.
                Review API access logs the same way you review VPN and admin logins. Version control also helps: an unexplained change stands out because it has no matching commit or ticket.
                HACKTHESOCLesson 107Network automation and APIs36 / 47

                Exposed APIs and tokens: the classic failures

                FailureWhat goes wrong
                Reachable from the wrong placeAPI exposed to the internet or user VLANs instead of an ACL-protected management network
                Leaked tokensIn Git, chat, CI logs or proxy-logged URLs. A bearer token needs no password
                Over-privileged automationOne full-admin account on every device: one stolen secret, whole-network compromise
                Weak or default credentialsPlus disabled certificate checks, letting an on-path attacker harvest tokens
                Long-lived tokensNo rotation and no owner

                Mitigations: management-plane ACLs, short-lived tokens, vaulted secrets, least-privilege roles, alerting on non-automation sources.

                A management API is an administrative login that happens to speak HTTP. A leaked token works until it expires or is revoked.
                HACKTHESOCLesson 107Network automation and APIs37 / 47

                Four questions for an unexplained API call

                Verifiable change leaves a commit and a ticket; an unexplained one has neither.

                1. 1Known automation host?Was the call made from a host on the automation list?
                2. 2Matching change record?Does it match a commit or a change ticket?
                3. 3Whose identity?Whose token or account was it, and what else has that identity done recently?
                4. 4Revoke and rotate firstIf the credential is unexplained, revoke and rotate, then investigate.
                A valid token proves only that someone held the credential. Source, hour and absence of a ticket are what separate abuse from routine automation.

                Worked example: polling interface status

                Find every interface that is not up across a fleet, without logging in to any switch.

                HACKTHESOCLesson 107Network automation and APIs39 / 47

                Five steps from inventory to report

                1. 1InventoryManagement IPs from the source of truth: Ansible inventory, CMDB export or controller list.
                2. 2RequestSend a RESTCONF GET for the operational interface data on each device.
                3. 3ParseConvert the JSON body to data structures; pull out name and oper-status.
                4. 4FilterKeep interfaces whose oper-status is not up.
                5. 5AggregateCollect results per device and record devices that could not be reached.
                The parsing path is the top-level key, then the interface array, then each entry's oper-status. Note that speed arrives as a string, since YANG-based JSON encodes 64-bit numbers that way.
                HACKTHESOCLesson 107Network automation and APIs40 / 47

                The polling loop, run in parallel

                • 200 sequential calls at one second each would take over three minutes
                • Timeouts, 401s and missing keys become their own category
                • A read-only role is enough: a leaked secret cannot change a device
                Error handling is half the job. A device that times out or returns an unexpected body must appear in the report, not be skipped silently.
                HACKTHESOCLesson 107Network automation and APIs41 / 47

                Pitfalls that make a fleet look healthier than it is

                • Error handling is half the jobA timeout, a 401 or a missing key must appear in the report, not be skipped silently.
                • Not up is not brokenUnused ports are down by design: compare with intended state before alerting.
                • Model differencesOlder and newer software may place operational status under different YANG paths.
                • Load and rate limitsTen workers is polite; hundreds can trigger 429 responses or burden device CPUs. Add backoff.
                • Numbers as stringsspeed arrives as the string 1000000000, so compare types carefully.
                Ask: what does the script do when a device does not answer, and which role does its account hold?

                    Key takeaways

                    1. 01Automation beats the CLI on scale, human error and drift, but it multiplies mistakes too: dry-run, then roll out in waves.
                    2. 02JSON has objects and arrays with double-quoted keys; YAML allows comments but indentation is syntax; NETCONF speaks XML.
                    3. 03REST maps verbs to resources: GET, PUT and DELETE are idempotent, POST is not, so a blind POST retry can duplicate.
                    4. 04NETCONF gives lock, candidate and commit over SSH; RESTCONF applies each HTTPS request alone. Both carry YANG-modeled data.
                    5. 05Controllers expose a northbound REST API and push southbound over NETCONF, RESTCONF, SSH or SNMP, so they hold the network's keys.
                    6. 06Treat management APIs as admin logins: baseline automation hosts, then chase unexplained writes, off-hours tokens and 401 bursts.
