What HTTP is and how a request works

HyperText Transfer Protocol: request and response over TCP port 80.

HACKTHESOCLesson 84HTTP and HTTPS6 / 36

Anatomy of an HTTP request

Like ordering at a counter: a specific request, a specific response.

  • MethodWhat action you want.
  • URL / pathWhich resource, e.g. /login or /products?id=42.
  • HeadersMetadata such as User-Agent (browser, app or script), Host, cookies.
  • BodySometimes: data being sent, e.g. a submitted form.
When you read a web log you are reading exactly these fields.
HACKTHESOCLesson 84HTTP and HTTPS7 / 36

The methods you will see most

GET

Retrieve a resource, like loading a page. Parameters ride in the URL.

POST

Send data to the server, like submitting a login or form. Data rides in the body.

PUT / DELETE

Update or remove a resource. Common in APIs.

GET /admin/../../etc/passwd or hundreds of POST /login tell a story the moment you can parse them.

HTTP's simplicity and universality are why it is everywhere in your logs, and why attackers hide inside it.

Section 2 of 8

Status codes and the response

A three-digit number that says what happened: your fastest triage filter.

HACKTHESOCLesson 84HTTP and HTTPS9 / 36

Five classes by first digit

2xx Success

200 OK. On a sensitive resource it means the request worked.

3xx Redirect

301/302 send the client elsewhere.

4xx Client error

404, 403, 401. Bursts can be probing for pages or access controls.

5xx Server error

500: the server failed, often when malicious input breaks the backend.

The 4xx and 5xx rows are where most of the security signal lives.
HACKTHESOCLesson 84HTTP and HTTPS10 / 36

The codes that carry security signal

CodeWhat it meansWhy a SOC analyst cares
201 CreatedA new resource was createdCan mark the moment an attacker created an account, key or upload
206 Partial ContentPart of a resource, for a Range requestBulk downloads and some exfil tools pull ranged chunks

HACKTHESOCLesson 84HTTP and HTTPS11 / 36

401 versus 403: the most valuable distinction

401 Unauthorized

The caller is not yet identified: authentication was required or failed. A wall of 401s points at credential guessing.

403 Forbidden

The caller is authenticated but not allowed this resource. A wall of 403s from a valid session is someone probing what they can reach.

Many POST /login returning 401 and then one 200 means a brute force likely succeeded.

A 500 right after a strange quote character in a parameter hints at injection reaching the backend.

HTTPS: adding encryption with TLS

HTTP inside a TLS tunnel on TCP port 443.

HACKTHESOCLesson 84HTTP and HTTPS13 / 36

What TLS adds to plain HTTP

Plain HTTP sends passwords, session cookies and personal data as readable text.

  • EncryptionRequest and response are scrambled; eavesdroppers see only ciphertext.
  • AuthenticationA certificate proves the server is who it claims: the browser padlock.
  • IntegrityData cannot be secretly altered in transit.
Before any HTTP flows, a TLS handshake agrees on encryption and the client validates the server's certificate.
HACKTHESOCLesson 84HTTP and HTTPS14 / 36

What a network monitor loses and keeps

Hidden by HTTPS

The content an analyst could read in plain HTTP.

  • URL path
  • Headers
  • Request and response body

Still visible

The metadata.

  • Which client talked to which server
  • When, how long, how much data
  • Destination IP and often the domain via certificate/SNI

So analysts lean on endpoint logs (full URL before encryption) and TLS fingerprinting.

HTTPS protects users and also lets attackers hide C2 inside encryption. That is the tension the SOC works within.

Section 4 of 8

Inside the TLS handshake: certificates, SNI, HSTS

Two handshake details analysts see and rely on constantly.

HACKTHESOCLesson 84HTTP and HTTPS16 / 36

The TLS 1.3 handshake in four steps

  1. 1ClientHelloSupported versions and cipher suites, random data, an ephemeral key share.
  2. 2ServerHelloServer picks suite and version, sends its key share; both derive the session key.
  3. 3Certificate exchangeX.509 chain to a trusted root; client checks expiry and hostname (Subject/SAN).
  4. 4FinishedBoth confirm handshake integrity; encrypted HTTP begins.
TLS 1.3 does this in a single round trip; TLS 1.2 needed two. The session key is never sent over the wire.
HACKTHESOCLesson 84HTTP and HTTPS17 / 36

SNI and HSTS

In the ClientHello

SNI

The client states the hostname, e.g. login.example.com, in plaintext so the server picks the right certificate. Sensors can read it without decrypting.

A response header

HSTS

Strict-Transport-Security: max-age=31536000; includeSubDomains. The browser refuses plain HTTP to that domain, defeating SSL-stripping.

SNI is how proxies and firewalls block domains on HTTPS without decryption. Encrypted Client Hello (ECH) aims to hide even this: an emerging visibility challenge.
HACKTHESOCLesson 84HTTP and HTTPS18 / 36

Inspecting a certificate directly

  • Mismatched subject: the certificate is not for this site
  • Untrusted issuer: not chained to a trusted authority
  • notAfter in the past: expired certificate
These are exactly the problems that make browsers warn, and what an analyst checks first for a suspected fake or intercepted site.

Section 5 of 8

HTTP/1.1, HTTP/2 and HTTP/3 (QUIC)

Each version changes what a connection looks like on the wire.

HACKTHESOCLesson 84HTTP and HTTPS20 / 36

Three versions, three transports

VersionTransportKey mechanismHead-of-line blocking
HTTP/1.1TCPText-based, sequential; parallel connections as workaroundYes, per connection
HTTP/2TCPBinary framing, multiplexed streams, HPACKReduced at HTTP layer, still at TCP
HTTP/3QUIC (UDP)Per-stream loss recovery, TLS 1.3 built inEffectively eliminated
Head-of-line blocking: one slow or lost item holds up everything behind it. HTTP/2 moved the problem from HTTP down to TCP; QUIC removes it by recovering loss per stream.
HACKTHESOCLesson 84HTTP and HTTPS21 / 36
HTTP/3 runs over UDP port 443, not TCP 443.

Monitoring that assumes encrypted web = TCP 443 can miss QUIC flows. The version is negotiated via ALPN, visible before decryption.

A proxy log showing proto=h3 or alpn=h3 on UDP/443 is just a modern browser. Normal, but confirm your stack actually parses it rather than passing it through unexamined.

Section 6 of 8

Cookies, sessions and web authentication

HTTP is stateless. Cookies give it memory, and give attackers a target.

HACKTHESOCLesson 84HTTP and HTTPS23 / 36

How a session cookie works

After login the server issues a session cookie, often a long random token, so you are recognised without re-entering your password.
HACKTHESOCLesson 84HTTP and HTTPS24 / 36

Session hijacking

  1. 1Steal the tokenMalware on the endpoint, a cross-site scripting flaw, or sniffing unencrypted HTTP.
  2. 2Present itThe attacker sends the same token to the server from their own device.
  3. 3Be treated as youFully logged in, without ever knowing the password.

HTTPS stops the sniffing route, not endpoint malware or a scripting flaw in the site.

Signal for analysts: a session token reused from an unexpected IP or device right after a legitimate login elsewhere. This is also why long-lived sessions are flagged and why logout matters: it invalidates the token server-side.

Section 7 of 8

Why HTTP and HTTPS matter to a SOC analyst

Two angles: attacks coming in, and malware calling out.

HACKTHESOCLesson 84HTTP and HTTPS26 / 36

Reading inbound versus outbound web traffic

Inbound: attacks on servers

Web server and WAF logs: method, path, parameters.

  • Injection, XSS, ../../etc/passwd, then 500 or odd 200
  • 404 bursts, scanner User-Agents like sqlmap, nikto
  • Many POST /login with 401s

Outbound: malware C2 and exfil

Port 443 is everywhere and usually allowed out.

  • Beaconing: small regular requests to one destination
  • New domains, known-bad hosts, fake User-Agents
  • Large outbound POSTs; TLS/JA3 anomalies
The outbound angle is often the more important one, because malware blends into ubiquitous web traffic.
HACKTHESOCLesson 84HTTP and HTTPS27 / 36
Read HTTP as a language.

Inbound: parse method, path, status and User-Agent. Outbound: watch destination, regularity and volume.

Knowing what a benign request looks like versus a probe or a beacon is the core skill.

Key takeaways

  1. 01HTTP on TCP 80 is request/response: method, path, headers like User-Agent, sometimes a body.
  2. 02Status codes are the fastest triage filter; 401 means not authenticated, 403 means authenticated but denied.
  3. 03HTTPS on TCP 443 hides content, not metadata; SNI still names the host in plaintext.
  4. 04HTTP/3 runs over QUIC on UDP 443, which monitoring built for TCP 443 can miss.
  5. 05Stolen session cookies let an attacker be you; watch token reuse from unexpected sources.
  6. 06Inbound logs show recon and brute force; outbound shows beaconing, odd destinations and exfil.

One external IP sends hundreds of GET requests in a minute to /admin, /backup, /wp-login.php and /phpmyadmin, almost all returning 404. What does this indicate?

A rapid spray of GETs to well-known admin/CMS paths, mostly 404, is forced-browsing recon. Stuffing and brute force are POSTs to a login answered with 401, not 404. Real crawlers follow the site's own links and robots rules.

Your organisation uses HTTPS everywhere, so a network sensor cannot read URLs or content. Why can analysts still detect malware command-and-control?

TLS encrypts content but leaves metadata: who, how regularly, how much, plus host telemetry and JA3. ECH is designed to hide the SNI. TLS inspection is real but not the only signal. Payload bytes are encrypted on the wire.

Check your understanding, question 3 of 3

An attacker steals a logged-in user's session cookie through a cross-site scripting flaw, then submits it to the same site from a different device. What happens?

HTTP is stateless, so a valid session cookie alone proves identity. Ordinary cookies are not pinned to an IP, token binding is rarely deployed, and after login the password is not re-sent on each request.
