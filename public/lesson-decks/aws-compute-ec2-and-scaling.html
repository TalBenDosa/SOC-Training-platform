EC2 fundamentals: instances, AMIs and types

Virtual machines billed by the second, built from an image, sized by a type name.

HACKTHESOCLesson 108AWS compute and scaling6 / 53

An instance is a VM, an AMI is its template

The machine

EC2 instance

A virtual machine on AWS hardware. You choose OS, CPU, memory, disk and network, and it runs in about a minute.

    The template

    AMI

    Amazon Machine Image: a root volume snapshot, launch permissions, and a block device mapping of disks to attach.

    • From AWS (Amazon Linux, Windows Server)
    • From the AWS Marketplace or the community
    • From your own account: a golden image

    Watch out

    Regional

    An AMI is regional. An image in one Region must be copied before it can be used in another Region.

      A golden image is what you bake after configuring a server. It comes back later: pre-baked AMIs make scale-out fast.

      The name encodes the purpose.

      Right-size: the questions to ask before picking a type

      • Limited by what?Is the workload bound by CPU, memory, disk or network?
      • Steady or bursty?Burstable t types earn CPU credits idle and spend them under load. A steady, busy workload runs out and slows down.
      • Does it run on Arm?Graviton is often cheaper for the same performance, if the software supports Arm.
      • Measure, then sizeMatch the type to measured usage with CloudWatch metrics and AWS Compute Optimizer. Start small.

      Over-provisioning just in case is the most common source of wasted spend.

      The classic beginner mistake is putting a steady busy workload on a burstable type. In unlimited mode it does not slow down, it costs extra.

      Instance lifecycle, user data and key pairs

      States decide the bill. User data configures the first boot.

      HACKTHESOCLesson 108AWS compute and scaling11 / 53

      Stopped means no compute bill, but the disk still costs

      StateMeaningCompute billingRoot EBS volume
      pendingStarting upNot yet billedBeing attached
      runningUsableBilled per secondBilled
      stopping / stoppedShut down but keptNot billedStill billed
      shutting-down / terminatedDeleted foreverNot billedDeleted by default
      Each state has a different billing consequence. Knowing them prevents both surprise bills and accidental data loss.
      HACKTHESOCLesson 108AWS compute and scaling12 / 53

      Stop, reboot, hibernate, terminate: four different outcomes

      Reversible

      Stop

      Like powering off a PC. Keeps EBS volumes and private IP, loses the auto-assigned public IPv4. EBS-backed only.

        Same host

        Reboot

        Restart on the same host. Same IP, same disks, and even instance store data survives.

          Resume where you were

          Hibernate

          Saves RAM to the encrypted root volume so the instance resumes exactly where it left off.

            Irreversible

            Terminate

            Permanent. Root volume is deleted unless DeleteOnTermination was turned off. Production often enables termination protection.

              A stopped instance may also start later on different physical hardware. Stop does not mean 'saves everything for free'.
              HACKTHESOCLesson 108AWS compute and scaling13 / 53

              User data turns a generic image into a configured server

              A script of up to 16 KB supplied at launch.

              • On Linux AMIs it runs via cloud-init as root, by default only on the first boot
              • For fast scale-out, bake software into your own AMI and keep user data short
              User data is convenient but slow when it installs many packages on every new instance. This is why golden AMIs exist.
              HACKTHESOCLesson 108AWS compute and scaling14 / 53

              Key pairs, and the fixed-address pitfall

              • Key pairPublic/private keys for SSH to Linux instances, and for decrypting the initial Administrator password on Windows.
              • Download onceAWS keeps the public key. The private .pem file is downloaded once at creation, and AWS cannot recover it.
              • A modern alternativeAWS Systems Manager Session Manager often replaces SSH keys entirely.
              • Need a fixed address?Auto-assigned public IPs change on stop/start. Allocate an Elastic IP, or better, use a load balancer with a DNS name.

              Stopping an instance still bills its EBS volumes and any idle Elastic IP address.

              Treat the private key as a credential. Permissions and shared responsibility belong to the cloud security lessons.

              Reserved Instances versus Savings Plans

              Both trade commitment for discount. Savings Plans follow your spend, not a fixed instance configuration.

              Most flexible

              Compute Savings Plan

              Also covers Fargate and Lambda, and lets you move between Regions and instance families.

                Deeper discount

                EC2 Instance Savings Plan

                A bigger discount in exchange for fixing the instance family and the Region.

                  Lower discount

                  Convertible RIs

                  Allow exchanging configurations, but with lower discounts than standard RIs.

                    Savings Plans are the modern default.

                    The main Savings Plan risk is overcommitting beyond your real baseline. Use Cost Explorer recommendations, not guesses.
                    HACKTHESOCLesson 108AWS compute and scaling18 / 53
                    Spot is the biggest saving and the biggest trap.

                    AWS can reclaim the instance with a two-minute notice, delivered via instance metadata and EventBridge. Perfect for queue workers, terrible for a single database.

                    Design for interruption: checkpoint work, keep workers stateless, and diversify across several instance types and AZs to reduce the chance of simultaneous reclaim.
                    HACKTHESOCLesson 108AWS compute and scaling19 / 53

                    The layered strategy for paying less

                    A mature design combines models instead of choosing one.

                    1. 1Always-on baselineCover it with Savings Plans.
                    2. 2Normal variationHandle it with On-Demand through Auto Scaling.
                    3. 3Interruptible background workPush it to Spot: restartable jobs, stateless workers.

                    Cost Explorer and Savings Plans recommendations use your actual usage, which beats guessing.

                    Questions to ask: how predictable is the baseline over the next year, can the work be restarted, is there a licensing or isolation requirement?

                    Storage: EBS, snapshots, instance store and EFS

                    Choosing the wrong place for data is a leading cause of data loss for newcomers.

                    HACKTHESOCLesson 108AWS compute and scaling21 / 53

                    Three answers to where an instance keeps data

                    Persistent block disk

                    EBS

                    A network-attached volume in one AZ. It persists when you stop the instance and is replicated within its AZ.

                    • Attaches only to instances in the same AZ
                    • Most volumes attach to one instance at a time

                    Fast but ephemeral

                    Instance store

                    Disks on the host, included in the price. Data is lost on stop, terminate or hardware failure. A reboot keeps it.

                    • Use for caches, buffers, scratch data

                    Shared NFS for Linux

                    EFS

                    Managed file system spanning multiple AZs, mounted by hundreds of instances at once. You pay for what you store.

                    • Suits web assets or home directories
                    Types that include instance store: i4i, d3, c6id. io1 and io2 support Multi-Attach for special clustered cases.
                    HACKTHESOCLesson 108AWS compute and scaling22 / 53

                    EBS volume types: start with gp3

                    Volume typeMediumPerformanceUse case
                    gp3 (General Purpose SSD)SSD3,000 IOPS, 125 MiB/s baseline; up to 16,000 IOPS, 1,000 MiB/sDefault for boot volumes, web and app servers, small databases
                    gp2 (older General Purpose)SSDIOPS tied to volume size, with burst creditsLegacy; gp3 is usually cheaper and more predictable
                    io2 / io2 Block ExpressSSDProvisioned, up to 64,000 IOPS (256,000 on Block Express)Latency-sensitive databases such as large Oracle or SQL Server
                    st1 (Throughput Optimized)HDDHigh sequential throughputBig data, logs, streaming reads
                    sc1 (Cold HDD)HDDLowest cost per GBInfrequently accessed data

                    Move to io2 only when you can prove sustained high IOPS. Only SSD types can be boot volumes.

                    gp3 performance is independent of volume size, which is why it replaces gp2 in most designs.
                    HACKTHESOCLesson 108AWS compute and scaling23 / 53

                    Snapshots move data between AZs and Regions

                    A snapshot is an incremental point-in-time backup stored in S3: after the first full copy, only changed blocks are saved.

                    1. 1Snapshot the volumeA regional backup, managed by AWS in S3.
                    2. 2Create a new volume from itCreate it in the target AZ. This is how data moves between AZs.
                    3. 3Copy it to reach another RegionCopy the snapshot to the other Region, then create a volume there.
                    4. 4Automate itUse Amazon Data Lifecycle Manager or AWS Backup rather than memory.
                    The snapshot is stored in S3 but does not appear as a bucket in your account. Volumes themselves cannot follow an instance to another AZ.
                    HACKTHESOCLesson 108AWS compute and scaling24 / 53
                    Can I afford to lose this data if the instance disappears?

                    If not, it belongs on EBS with snapshots, in EFS, or in a managed database or S3. Never on instance store.

                    This is the one question to ask of every piece of data before choosing where it lives.

                    Elastic Load Balancing: ALB, NLB and GWLB

                    One front door that spreads requests and skips unhealthy servers.

                    HACKTHESOCLesson 108AWS compute and scaling26 / 53

                    Three load balancer types, three layers

                    ELB is managed by AWS across multiple AZs, and you reach it through a DNS name rather than a fixed IP.

                    TypeLayer and protocolsKey strengthsTypical use
                    ALB (Application)7: HTTP, HTTPS, gRPC, WebSocketRoutes by host, path, header or query stringWebsites, microservices, APIs
                    NLB (Network)4: TCP, UDP, TLSMillions of req/s, low latency, static IP per AZGaming, IoT, non-HTTP, fixed IPs
                    GWLB (Gateway)3: IP packets over GENEVE (port 6081)Inserts third-party appliances such as firewallsInspection fleets

                    Default: ALB for web traffic, NLB for raw TCP/UDP speed or static addresses, GWLB only for network appliances.

                    The older Classic Load Balancer still exists for legacy applications, but new designs choose one of these three. ALB targets can be instances, IPs or Lambda functions.
                    HACKTHESOCLesson 108AWS compute and scaling27 / 53

                    Listener, rule, target group: how a request is routed

                    • Listener: checks for connection requests on a protocol and port, e.g. HTTPS on 443
                    • Rule (ALB): decides what to do with a request, e.g. forward /api/* to one group
                    • Target group: the pool of instances, IPs or Lambda that receives forwarded traffic
                    An HTTP listener on port 80 commonly just redirects to HTTPS.
                    HACKTHESOCLesson 108AWS compute and scaling28 / 53

                    How a health check removes a bad server

                    Each target group runs its own health checks.

                    1. 1ProbeThe load balancer requests a path such as /health on a port at an interval, e.g. every 30 seconds.
                    2. 2CountConsecutive successes or failures are counted against the healthy and unhealthy thresholds.
                    3. 3RemoveA failing target leaves rotation until it recovers.
                    4. 4DrainOn deregister or scale-in, deregistration delay (default 300 seconds) lets in-flight requests finish.

                    The health endpoint should prove the application really works, not merely that the port is open.

                    A health check that only tests an open port keeps sending traffic to a hung application.
                    HACKTHESOCLesson 108AWS compute and scaling29 / 53

                    Cross-zone load balancing: on for ALB, off for NLB

                    Load balancer nodes live in each enabled AZ.

                    ALB: on by default

                    Every node spreads requests across targets in all AZs.

                      NLB: off by default

                      If targets are uneven across AZs and you leave it off, one AZ can get overloaded.

                        With uneven target counts per AZ, check this setting first when one zone is hot and another idle.

                        EC2 Auto Scaling: elasticity and self-healing

                        Capacity follows demand and failed instances are replaced. The service itself costs nothing.

                        HACKTHESOCLesson 108AWS compute and scaling31 / 53

                        A launch template is the recipe for every new instance

                        • What it storesAMI ID, instance type, key pair, security groups, storage, IAM instance profile and user data.
                        • VersionedPublish version 2 with a new AMI and roll it out with an instance refresh.
                        • Mixed instances policyBlends On-Demand and Spot across several instance types.
                        • Launch configurationsThe older form is legacy and no longer recommended.

                        An Auto Scaling group (ASG) manages the instances; you pay only for what it launches.

                        Elasticity means capacity follows demand automatically: more servers during a sale, fewer at 3 a.m.
                        HACKTHESOCLesson 108AWS compute and scaling32 / 53

                        Minimum, desired, maximum: the group's three numbers

                        Example: 2

                        Minimum

                        Never fewer than this. Your floor for availability.

                          Example: 4

                          Desired

                          What the group tries to run right now. Scaling policies change this value.

                            Example: 10

                            Maximum

                            Never more than this. Your cost ceiling and a safety valve against runaway loops or attacks.

                              Policies move desired within the min and max bounds.

                              Without a sensible cap, a runaway loop or an attack could scale you into a very large bill.
                              HACKTHESOCLesson 108AWS compute and scaling33 / 53

                              Five scaling policies, and target tracking comes first

                              PolicyHow it decidesGood for
                              Target trackingPick a metric and a target; capacity is added or removed to hold it, like a thermostatMost workloads, e.g. average CPU at 50 percent or ALBRequestCountPerTarget at 1000
                              Step scalingA CloudWatch alarm triggers adjustments sized by how far the metric breachedFine control: add 1 instance at 60% CPU, add 4 at 85%
                              Simple scalingOne alarm, one adjustment, then a cooldown waitLegacy; step is usually better
                              Scheduled scalingChanges capacity at set timesKnown patterns: scale up at 08:45 before office hours
                              Predictive scalingMachine learning on past load scales ahead of recurring peaksCyclical traffic

                              Pair target tracking with an instance warmup so booting instances are not counted in metrics, or the group overreacts.

                              Scaling on the wrong metric, such as CPU for an I/O-bound app, produces a group that never scales when it should.
                              HACKTHESOCLesson 108AWS compute and scaling34 / 53

                              Self-healing needs ELB health checks switched on

                              Default: EC2 status checks

                              The group checks the virtual machine, not the application, so a crashed app on a running instance goes unnoticed.

                                Recommended with a load

                                ELB health checks on

                                An instance that fails the application-level check is terminated and replaced.

                                • Set a health check grace period for boot and user data
                                • Too short and starting instances are killed in a loop

                                Min equal to max disables elasticity. One instance in one AZ heals itself but has downtime on every replacement.

                                This is the exact fix for the quiz scenario at the end: an app hangs but passes EC2 status checks.

                                Regions, Availability Zones and spreading across AZs

                                Where you place compute determines how it fails.

                                HACKTHESOCLesson 108AWS compute and scaling36 / 53

                                Region and AZ: two layers of AWS infrastructure

                                e.g. us-east-1, eu-west-1

                                Region

                                A geographic area. Fully independent: separate pricing and services, and no automatic data replication between Regions.

                                • Choose by latency, legal rules, services, price

                                e.g. us-east-1a

                                Availability Zone

                                One or more data centers with independent power, cooling and networking, linked by low-latency connections.

                                • Most Regions have three or more AZs
                                • Letters map differently per account; use the AZ ID, e.g. use1-az1
                                The AZ ID is the same for everyone, so use it for cross-account coordination.
                                HACKTHESOCLesson 108AWS compute and scaling37 / 53
                                High availability is something you build, not something a Region gives you.

                                A single AZ is a single failure domain. EBS volumes, subnets and instances each live in exactly one AZ, so you must use more than one.

                                A power event, network fault or capacity shortage in one AZ takes down everything placed only there.
                                HACKTHESOCLesson 108AWS compute and scaling38 / 53

                                What a multi-AZ Auto Scaling group does for you

                                Give the group subnets in different AZs and it will:

                                1. 1BalanceLaunch instances as evenly as possible across the chosen AZs.
                                2. 2ReplaceIf an AZ is unhealthy or out of capacity, launch replacements in the remaining AZs.
                                3. 3RebalanceWhen the AZ recovers, sometimes launch a new instance before terminating an old one, so capacity never dips.

                                Example: min 2, desired 4, max 8, subnets in 3 AZs gives 2 + 1 + 1 instances.

                                Subnet design itself is covered in the separate VPC lesson.
                                HACKTHESOCLesson 108AWS compute and scaling39 / 53

                                More AZs means less idle capacity for the same tolerance

                                Say you need 4 instances of capacity to carry peak load even after losing one AZ.

                                AZs in useInstances per AZTotal fleetVerdict
                                Two AZs48Half the fleet is idle most of the day
                                Three AZs26Same tolerance with less over-provisioning

                                Ask: if one AZ vanished right now, would the remaining instances carry the load while the group scales up?

                                Pitfalls: a multi-AZ ASG with a single-AZ database just moves the single point of failure, and cross-AZ data transfer carries a small per-GB charge.

                                What it bundles

                                    1. 1One application crashesHealth check fails 3 times, traffic stops, and the ASG terminates and replaces it. Users see only in-flight errors.

                                    Key takeaways

                                    1. 01EC2 instances launch from regional AMIs; a type name encodes family, generation, processor and size. Right-size from measured usage.
                                    2. 02Stop keeps EBS volumes (still billed) and drops the auto-assigned public IP; terminate is permanent.
