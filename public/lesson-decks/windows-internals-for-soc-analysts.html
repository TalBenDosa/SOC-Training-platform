Section 1 of 12

Processes and the parent-child tree

Everything a computer does is done by processes. Most investigations are about them.

HACKTHESOCLesson 06Windows internals6 / 77

Every process has an ID and a parent

  • ProcessA program while it is running. chrome.exe on disk is a file; launched, it becomes a process.
  • PIDA unique Process ID, because several copies of one program can run at once.
  • Parent PID (PPID)The ID of the process that launched this one. Double-click an app: the shell is the parent.
  • Process treeFollow parents and children to rebuild a family tree of what launched what.
Individually, many programs are normal. What betrays an attack is a child that has no business being spawned by that parent.
HACKTHESOCLesson 06Windows internals7 / 77

Who launched whom reveals the attack

Word launching PowerShell is one of the most common maldoc signatures: a booby-trapped document starts PowerShell, which downloads the real malware.
HACKTHESOCLesson 06Windows internals8 / 77

Sysmon Event ID 1: Word launched PowerShell

  • Parent: does WINWORD.EXE have any reason to start a scripting engine?
  • Children: what did this process launch in turn?
  • Command line: hidden window plus encoded command reveals intent
Sysmon is a free Microsoft tool that records detailed process activity. Walk the tree up to the root and down to the leaves and narrate it as a story. If the story does not make sense, you have found something.
HACKTHESOCLesson 06Windows internals9 / 77

Students should be able to point at ParentImage and say why it matters before anything else on the record.
HACKTHESOCLesson 06Windows internals10 / 77

Reading a process tree as a story

  1. 1Start at the alert processE.g. the powershell.exe with an encoded command.
  2. 2Walk up to the rootIts parent, and the parent's parent: how did we get here?
  3. 3Walk down to the leavesWhat did it launch in turn? Suspicious processes often have suspicious children.
  4. 4Read every command lineDownload instructions, encoded blobs, external addresses: intent the name hides.
  5. 5Narrate it'This launched that, which launched that.' If the story makes no sense, you found something.
This is the single most transferable Windows skill in the SOC. Tools change; 'what launched this, and does that make sense?' does not.
HACKTHESOCLesson 06Windows internals11 / 77

Parent-child pairs: expected versus no business existing

Expected

The parent has an obvious reason to start the child.

  • explorer.exe -> chrome.exe (user double-click)
  • chrome.exe -> chrome.exe renderer
  • A known IT tool -> powershell.exe

Should not happen

A document or browser has no reason to start a scripting engine or shell.

  • WINWORD.EXE -> powershell.exe
  • A web browser -> cmd.exe
  • powershell.exe -> rundll32.exe from Temp
None of the child programs is malicious on its own. The relationship is the evidence.

Section 2 of 12

Services, scheduled tasks, and autostart

Anything that starts automatically keeps coming back after a reboot: persistence.

HACKTHESOCLesson 06Windows internals13 / 77

Why persistence is the attacker's insurance policy

  1. 1Malware runs onceA process in memory, launched by the initial compromise.
  2. 2The machine rebootsOr an analyst kills the process. A plain process is gone.
  3. 3An autostart relaunches itA service, scheduled task or Run key starts it again, automatically.
  4. 4Remove the mechanism tooKilling the process without removing its autostart means it comes back.
Persistence is one of an attacker's top goals. Every containment needs the question: what would start this again?
HACKTHESOCLesson 06Windows internals14 / 77

Three ways Windows starts programs by itself

Services

Background programs that start at boot, no user needed, often high privilege. PsExec creates a service on a remote machine to run a command.

Scheduled tasks

Run on a trigger: a time, every logon, idle, an interval. Kill the malware and the task starts it again. Created by schtasks.exe or Task Scheduler.

Other ASEPs

AutoStart Extensibility Points: startup folders, registry Run keys, logon scripts. Collectively called 'autoruns'.

Antivirus, Windows Update and print spooling are all legitimate services. That is exactly why attackers like hiding among them.
HACKTHESOCLesson 06Windows internals15 / 77

Persistence that tries to look boring

  • Binary runs from a user Temp/AppData folder, not a real program location
  • WinDefendUpd and SystemUpdateCheck: boring fake names that mimic Windows
  • A hidden PowerShell script set to run at every logon with highest rights
Ask three questions: who created it and when (moments after a suspicious process is a strong sign), what does it launch and from where (temp folders, random names, encoded commands), and does a task with this name and path belong on this machine?
HACKTHESOCLesson 06Windows internals16 / 77

The three questions applied to both entries

QuestionWinDefendUpd serviceSystemUpdateCheck task
Who created it, and when?Check: created moments after a suspicious process?Check: same, via schtasks.exe
What does it launch, from where?svc32.exe in a user Temp folderHidden PowerShell script from Downloads
Does it belong on this machine?Name mimics Defender; path does notBoring name, runs at every logon, highest rights
Legitimate services point to well-known program files in expected locations. Both of these are lying about what they are.
HACKTHESOCLesson 06Windows internals17 / 77

A legitimate autostart entry versus a disguised one

Legitimate

Antivirus, Windows Update, a nightly backup.

  • Known program in Program Files or System32
  • Signed by its vendor
  • Name matches what it launches
  • Present on similar machines

Disguised

A boring name hiding an odd path.

  • User Temp, AppData or Downloads path
  • Random or look-alike filename
  • Encoded or hidden command
  • New on this host only
The name is the attacker's choice; the path and the creation context are much harder to fake.

The registry and autoruns

Windows' master control panel, and where attackers flip switches in their favor.

HACKTHESOCLesson 06Windows internals19 / 77

Hives, keys and values

HKEY_LOCAL_MACHINE

HKLM

Settings for the whole computer.

HKEY_CURRENT_USER

HKCU

Settings for the currently logged-in user.

Keys and values

Keys are like folders; values are the settings, each a name and its data. Paths read like folder paths.

You do not need to memorize the tree. You need to recognize the paths attackers abuse.

Almost every setting lives here: desktop, file associations, network, security policy, and crucially which programs start automatically.
HACKTHESOCLesson 06Windows internals20 / 77

The two classic Run keys

KeyRuns whenWho can write it
HKCU\...\CurrentVersion\RunThis user logs inThe user themselves: no admin needed
HKLM\...\CurrentVersion\RunAny user logs inAdministrators: a write here implies admin rights
Cousins: RunOnce, Winlogon, image-hijack keysVarious triggersSame idea: an entry that auto-starts something
An attacker adds one value pointing to their malware, and Windows itself relaunches it at every logon until someone removes the entry.
HACKTHESOCLesson 06Windows internals21 / 77

A Run key that imitates OneDrive

  • HKCU Run launches at this user's logon; HKLM Run for any user
  • Real OneDrive does not live in AppData\Roaming\odsync.exe
  • Unsigned file in a user-writable folder: highly suspicious
Cousins include RunOnce, Winlogon keys and image-hijack keys. Sysinternals Autoruns lists every Run key, service, task and logon hook in one view. A Run-key write right after malicious PowerShell is persistence installed before your eyes.
HACKTHESOCLesson 06Windows internals22 / 77

Hunting persistence across every autostart point

  1. 1Enumerate everythingSysinternals Autoruns, or EDR telemetry: Run keys, services, tasks, logon hooks.
  2. 2Filter for odd pathsTemp, AppData, Downloads, and anything unsigned.
  3. 3Compare to known goodIs this entry on similar machines, or new to this host?
  4. 4Find the writerWhen was the value written, and which process wrote it?
Checking each location by hand is impractical: there are too many. That is why Autoruns exists.
HACKTHESOCLesson 06Windows internals23 / 77
A Run-key write right after a malicious PowerShell command is persistence being installed before your eyes.

Correlate registry writes with the process that made them. Timing turns a plausible entry into proof.

This is the habit with the highest value in Windows defence: check what starts automatically, and be suspicious of anything new.

Accounts, privileges, and integrity levels

Was this action within the account's rightful power, or did someone reach beyond it?

HACKTHESOCLesson 06Windows internals25 / 77

Scope and power of an account

AccountScope or powerWhat compromise means
Local accountExists only on one computerContained to one host
Domain accountManaged by Active Directory, logs in to many machinesCan spread across the whole environment
Standard userOwn programs and settings onlyLimiting, so attackers try to escalate
AdministratorInstall software, change security, create servicesAlmost anything on the machine
SYSTEMNT AUTHORITY\SYSTEM, runs core Windows componentsOwns the machine completely
Many services run as SYSTEM, which is one reason attackers target services: hijack one and your malware inherits SYSTEM power.
HACKTHESOCLesson 06Windows internals26 / 77

Integrity levels: a trust ranking on every process

  1. 1LowRestricted processes with the least trust.
  2. 2MediumA normal user's programs: the everyday level.
  3. 3HighA program run 'as administrator'.
  4. 4SystemWindows' own core components, running as SYSTEM.

A process that starts at Medium and obtains High through an exploit or trick is privilege escalation in action.

The level is recorded in process telemetry, so the jump is visible if you know to look for it.
HACKTHESOCLesson 06Windows internals27 / 77

Integrity levels expose escalation

  • Levels: Low, Medium (normal user), High (run as admin), System
  • A jump from Medium to High is privilege escalation in action
  • SYSTEM code should never live in a user's Temp directory
For any noteworthy action ask: which account, local or domain, what integrity level, and does the action fit it?
HACKTHESOCLesson 06Windows internals28 / 77

Three questions for any noteworthy action

  • Which account, local or domain?Local compromise is contained to one host; a domain account can spread everywhere.
  • What level, and does it fit?A standard user suddenly doing admin work: a legitimate elevation, or an escalation to explain.
  • Did anything reach SYSTEM?A user-launched program ending up as SYSTEM is a screaming indicator of escalation.
These turn a confusing event into one clear question: was this within the account's rightful power, or did someone reach beyond it?

Event ID 4688: a new process has been created

Same Word-launches-PowerShell chain from section 1, now seen through a different log source.
HACKTHESOCLesson 06Windows internals31 / 77

Translate the 4688 vocabulary into concepts

4688 fieldWhat it means
Creator Process NameThe parent, what Sysmon calls ParentImage
Mandatory LabelThe integrity level in words; High or System right after a document ran is a red flag
Token Elevation TypeWhether it received admin rights; a limited token means no elevation prompt

Don't memorise field names; understand the concept behind them, then read whichever vocabulary the log in front of you uses.
HACKTHESOCLesson 06Windows internals32 / 77

What this 4688 says about elevation

Mandatory Label: Medium

The ordinary level for a standard user's program. If it read High or System right after a document ran, that jump would be a red flag.

Token Elevation Type: %%1938

A limited token: launched as a standard user, no elevation prompt. Fits a hidden PowerShell that has no reason to ask permission.

Target Subject: NULL SID

No account switching: jsmith's own session launched it directly. Filled only when a process runs as a different account.

Medium here does not make it benign: the parent is still Word. Elevation is one question, ancestry is another.

What normal looks like, and the LOLBins

Evil done with legitimate, Microsoft-signed tools already on the machine.

HACKTHESOCLesson 06Windows internals35 / 77

Living-off-the-land binaries you will meet most

LOLBinLegitimate purposeHow attackers abuse it
certutil.exeManaging certificatesDownload files from the internet and decode encoded data
rundll32.exeRun code inside library (.dll) filesExecute malicious DLLs and hide the real payload
mshta.exeRun HTML application files (rarely needed today)Execute malicious scripts pulled from a web address
powershell.exePowerful automation toolMost-abused LOLBin: download, decode, run malware in memory

Also worth knowing: wmic.exe, regsvr32.exe, bitsadmin.exe, cmd.exe.

You cannot blocklist these: the same name appears in benign and malicious activity. The pattern is constant: trusted tool, untrusted use.
HACKTHESOCLesson 06Windows internals36 / 77

Judge the command line and context, not the name

  • A certificate tool fetching an .exe from a raw IP is not certificate work
  • A finance workstation pulling a remote HTA has no reason to
  • Ask: who launched it, did it connect out or drop a file, normal here?
Normal: certutil rarely runs; rundll32 runs constantly but launched by Windows loading system DLLs; PowerShell runs from known IT parents. Abnormal shares tells: odd parent, odd path, external connection, obfuscation.
HACKTHESOCLesson 06Windows internals37 / 77

What normal use of each LOLBin looks like

certutil.exe

Normal: rarely runs; when it does, a scripted admin action. Abnormal: downloading from a random address.

rundll32.exe

Normal: runs constantly, launched by Windows, loading known system DLLs. Abnormal: a DLL from a temp folder.

powershell.exe

Normal: IT automation from known parents. Abnormal: launched by Word, hidden window, encoded command.

Abnormal cases share tells: odd parent, odd file path, external connection, obfuscated command line.

You cannot recognise abnormal until you know normal. Build the baseline per host type: a server's normal is not a workstation's.
HACKTHESOCLesson 06Windows internals38 / 77

Four questions for any LOLBin execution

  1. 1Who launched it?certutil from winword.exe is not certutil from an admin script.
  2. 2What is the full command line?A URL, an encoded blob, a download instruction, a hidden-window flag?
  3. 3Did it connect out or write a file?A certificate tool that just downloaded an executable is not doing certificate work.
  4. 4Is this normal here?For this host and this user? Mshta on a finance workstation is nobody's job.
The shift from 'is the tool bad?' to 'is this USE normal?' is what catches living-off-the-land attacks.
HACKTHESOCLesson 06Windows internals39 / 77

Imposters the baseline catches with no judgement call

  • lsass.exe with the wrong parentAnything other than wininit.exe as parent.
  • services.exe from explorer.exeThe Service Control Manager is started by wininit.exe, never by the user shell.
  • csrss.exe in AppDataCore processes run from System32. A trusted name on the wrong path is an imposter.
Each of these is worth escalating on its own. The baseline turns them into yes/no checks.

LSASS and credential theft in memory

The hinge that turns one compromised laptop into a compromised network.

HACKTHESOCLesson 06Windows internals42 / 77

Why LSASS ends up holding live keys

LSASS = Local Security Authority Subsystem Service, lsass.exe.

  1. 1A user logs inAnd will open file shares and services all day.
  2. 2Windows caches the credentialsIn LSASS memory, so nobody retypes a password for every share.
  3. 3The cache holds secretsNTLM hash, Kerberos tickets; on older or misconfigured systems even plaintext.
  4. 4An admin can read the memoryAn attacker with admin rights can copy LSASS memory and carve out the secrets.
Credential theft is the hinge that turns one compromised laptop into a compromised network.
HACKTHESOCLesson 06Windows internals43 / 77

Why LSASS is the crown jewel

Windows caches credentials in lsass.exe so you do not retype your password for every file share: NTLM hash, Kerberos tickets, and on older or misconfigured systems even plaintext.
HACKTHESOCLesson 06Windows internals44 / 77

Dump, reuse, detect

T1003.001

Dump (needs admin)

Copy LSASS memory and carve the secrets out.

  • Mimikatz reading credentials from LSASS
  • A comsvcs.dll MiniDump of LSASS
  • procdump or a Task Manager dump file

T1550

Reuse

Pass-the-Hash with the NTLM hash, Pass-the-Ticket with a Kerberos ticket. Log into the next machine without knowing the password.

Sysmon 10, 4688

Detect

A non-system process opening lsass.exe (GrantedAccess like 0x1010) is almost never legitimate. Back it with process creation.

comsvcs.dll MiniDump is living off the land: a signed built-in DLL, no foreign tool on disk. Because dumping needs admin, every extra local admin is one more person whose mistake hands over the keys. That is why least privilege matters.
HACKTHESOCLesson 06Windows internals45 / 77

The access signal as Sysmon records it

  • SourceImage: who opened the handle; a Temp-folder binary, not an OS component
  • TargetImage: lsass.exe, the credential cache
  • GrantedAccess 0x1010: read access to LSASS memory
Security and backup agents do open LSASS, but they are known and allowlisted. Anything else is a high-fidelity alert.
HACKTHESOCLesson 06Windows internals46 / 77

Three detection points along the theft

PointWhere you see itWhat to look for
Opening LSASSSysmon Event ID 10A non-system process with read access to lsass.exe

Catching it at the first point stops the spread; at the third point you are already scoping lateral movement.
HACKTHESOCLesson 06Windows internals47 / 77
Every extra local administrator is one more person whose single mistake hands an attacker the keys.

Dumping LSASS requires admin. That is the real reason least privilege is not a bureaucratic nicety.

Tie this back to the accounts section: limiting admin rights shrinks the number of machines where LSASS can be read.

PowerShell and WMI, and the logs that catch them

Trusted, used by every admin, and the attacker's favourite way to operate filelessly.

HACKTHESOCLesson 06Windows internals49 / 77

PowerShell abuse patterns to recognize on sight

  • Encoded commandspowershell -enc <base64> or -EncodedCommand hides the real command from keyword rules.
  • Download and run in memoryIEX (New-Object Net.WebClient).DownloadString(...) executes without writing to disk.
  • Version downgradepowershell -version 2 forces the old engine because it predates modern logging.
  • WMI executionwmic process call create launches a process, sometimes on a remote machine.
  • WMI persistenceAn event subscription: 'at boot, run my payload', stored in the WMI repository. T1546.003.
AMSI, the Antimalware Scan Interface, lets Defender inspect scripts at runtime, which is why attackers try to bypass it.
HACKTHESOCLesson 06Windows internals50 / 77

Why Script Block Logging defeats encoding

  1. 1The command arrives encodedpowershell -enc <base64> hides the text from keyword rules.
  2. 2PowerShell must decode to run itThe engine cannot execute Base64; it turns it back into code.
  3. 3Event 4104 logs at executionThe code is recorded after decoding, including code downloaded into memory.
  4. 4The analyst reads plain codeThe obfuscation never reaches the log.
This is why attackers try 'powershell -version 2': the v2 engine predates this logging. A v2 engine load is itself a signal.
HACKTHESOCLesson 06Windows internals51 / 77

Each abuse has a log that catches it

AbuseToolingThe log that catches it
Obfuscated PowerShell executionpowershell -enc, in-memory IEXScript Block Logging 4104, logs decoded code
PowerShell logging evasion-version 2, AMSI bypassv2 engine load; AMSI failure or tamper events
Execution / lateral movementwmic process call createProcess creation 4688 + suspicious parent
Stealthy persistenceWMI event subscriptionSysmon 19 / 20 / 21 (filter, consumer, binding)
4104 logs code after decoding, at the moment of execution, which defeats most obfuscation. 4103 adds module and pipeline logging. You cannot blocklist PowerShell or WMI, so detection is about behaviour and context.
HACKTHESOCLesson 06Windows internals52 / 77

WMI is abused two ways, caught in two places

WMI = Windows Management Instrumentation, the built-in system for querying and controlling Windows.

Execution and lateral movement

wmic process call create launches a process, sometimes on a remote machine. Caught by process creation (4688) with a suspicious parent.

T1546.003

Persistence

An event subscription: 'at boot, run my payload', stored in the WMI repository, not a visible file. Caught by Sysmon 19, 20 and 21.

You cannot blocklist PowerShell or WMI: the business runs on them. Detection is about behaviour and context.

Section 9 of 12

DLL sideloading: signed program, attacker code

MITRE ATT&CK T1574: a trusted executable tricked into loading a malicious DLL.

HACKTHESOCLesson 06Windows internals54 / 77

How search-order hijacking works

  1. 1Program asks for a DLLA signed executable loads helper.dll without giving a full path.
  2. 2Windows searches in orderIt often checks the program's own folder before protected system folders.
  3. 3Attacker plants a copyA malicious helper.dll dropped right beside the signed executable.
  4. 4Trusted host runs itThe signed program loads the attacker's DLL first, lending it its reputation.
It defeats naming-based trust, hides the payload inside normal activity, and abuses tools that trust signed vendor binaries.
HACKTHESOCLesson 06Windows internals55 / 77

Why attackers reach for sideloading so often

Defeats name trust

You see a signed, familiar process. The malice is in a DLL that never appears as its own process.

Hides in normal activity

The payload runs only when the legitimate program does, so it blends into routine behaviour.

Borrows reputation

Tools that trust signed vendor binaries can be led to trust the whole process, malicious DLL included.

The same lesson as the comsvcs.dll dump and the LOLBins, stated from the defender's side.
HACKTHESOCLesson 06Windows internals56 / 77
A code signature vouches for the file it is on, and nothing else.

Hunt for module loads that don't belong: Sysmon Event ID 7 showing a signed process loading an unsigned DLL from a temp or download folder instead of System32.

'It's GoogleUpdate.exe, it's signed, so it's safe' is the instinct attackers exploit. Ask whether the program is loading what it should, from where it should.
HACKTHESOCLesson 06Windows internals57 / 77

Reading Sysmon Event ID 7: module loads that belong and don't

Look atExpectedSuspicious
DLL pathC:\Windows\System32 or the vendor's install folderA user's Temp or Downloads folder
DLL signatureSigned, like its hostUnsigned DLL loaded by a signed process
Host locationProgram runs from its install directoryA well-known program running from the wrong directory
The question is never 'is this program known?' but 'is this program loading what it should, from where it should?'

Section 10 of 12

svchost.exe: real services vs imposters

Dozens of copies of one trusted name: excellent camouflage.

HACKTHESOCLesson 06Windows internals59 / 77

Why so many svchost.exe processes is normal

  • Shared service hostMany Windows features are DLLs that need a host process. svchost.exe loads them.
  • The -k groupEach instance names its service group, e.g. -k netsvcs or -k DcomLaunch.
  • Registry lookupGroups are listed under HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Svchost.
  • More RAM, more copiesModern machines often run each service in its own svchost, so 60+ entries can be normal.
netsvcs historically included things like the Task Scheduler and BITS, the Background Intelligent Transfer Service.
HACKTHESOCLesson 06Windows internals60 / 77

The three-question svchost.exe check, in order

  1. 1PathExactly C:\Windows\System32\svchost.exe? Anything else is suspicious immediately.
  2. 2ParentIs it services.exe, the Service Control Manager that starts every service?
  3. 3Command lineDoes it carry a -k group that matches a real service group?

A genuine svchost.exe passes all three, every time.

One of the highest-value, lowest-effort triage habits in Windows defence.
HACKTHESOCLesson 06Windows internals61 / 77

The three-question check exposes the imposter

  • Path must be exactly C:\Windows\System32\svchost.exe
  • Parent must be services.exe, the Service Control Manager
  • Command line must carry a real -k group: B has none
Any one mismatch is a stronger signal than the name could ever be. The disguise relies entirely on analysts never looking past the label.
HACKTHESOCLesson 06Windows internals62 / 77

Imposter tricks, and the check that catches each

The trickWhich check catches it

UAC, elevation, and its bypasses

Elevation is meant to require a human clicking Yes. Bypasses remove the human.

HACKTHESOCLesson 06Windows internals64 / 77

How UAC elevation is meant to work

UAC = User Account Control: the dimmed-screen 'allow this app to make changes?' prompt.

  1. 1An admin logs inWindows gives a split token: day-to-day work runs with a filtered Medium token.
  2. 2A program requests elevationIt asks explicitly for administrator rights.
  3. 3The consent prompt appearsShown by consent.exe. A human must click Yes.
  4. 4Only then: High integrityThe full administrator token is granted to that one program.
Before UAC, ordinary users simply were administrators, so malware ran with full power with no friction.
HACKTHESOCLesson 06Windows internals65 / 77

Split tokens and the auto-elevate exception

Split token

Admins work with a filtered Medium token. Only an explicit elevation request, approved at the prompt, grants the full High token.

Auto-elevate

Trusted Microsoft binaries like eventvwr.exe, sdclt.exe and fodhelper.exe carry autoElevate=true and get High with no prompt.

T1548.002

UAC bypass

Some auto-elevate binaries read what to launch from HKCU, which a standard user can write. Plant a command, launch the binary.

Before UAC, ordinary users simply were administrators, so every program including malware had full power. The public UACME project lists dozens of bypass methods.

The classic fodhelper.exe bypass

  • Step 1: a write under HKCU ...\shell\open\command
  • Step 2: an auto-elevate binary launches an unexpected child
  • High integrity with no visible consent.exe prompt
Any High-integrity process that cannot be tied to a visible consent event deserves the same scrutiny as a process unexpectedly running as SYSTEM.

NTFS artifacts: ADS, Mark of the Web, shadows

Hide data inside an ordinary file, and erase the safety net before the ransom note.

HACKTHESOCLesson 06Windows internals69 / 77

How NTFS stores a file, and where a stream hides

  1. 1Every file has an MFT entryIn the Master File Table of the NTFS volume.
  2. 2The entry is made of attributesBasic information, security permissions, and Data.
  3. 3The unnamed Data attributeThe normal, visible content: what you see when you open the file.
  4. 4Extra named Data attributesAlternate Data Streams: invisible in Explorer and a plain dir, yet inside the same file.
Not every stream is malicious: Mark of the Web is itself a stream, and a defensive one.
HACKTHESOCLesson 06Windows internals70 / 77

Three NTFS features attackers lean on

T1564.004

Alternate Data Streams

An MFT entry can hold more than one Data attribute. Named extras are invisible in Explorer and dir, e.g. notes.txt:hidden.exe.

Zone.Identifier

Mark of the Web

A defensive stream: ZoneId=3 means Internet and triggers Protected View and SmartScreen. Attackers wrap payloads in ISO/IMG or run Unblock-File.

T1490

Shadow copy deletion

VSS snapshots let victims roll back encrypted files, so ransomware deletes them first with native signed tools.

ADS has been used by real malware from the Regin platform to ransomware, because static scanning historically focused on the primary content.
HACKTHESOCLesson 06Windows internals71 / 77

Find hidden streams, and the pre-encryption tell

  • Any named stream holding an executable is close to a guaranteed finding
  • Did the payload arrive in an ISO or IMG that skips MOTW?
  • Shadow deletion across many hosts in minutes: ransomware is imminent
A burst of these commands often arrives minutes before encryption starts, one of the last points where fast detection can still prevent the damage.

Key takeaways

  1. 01Judge processes by their family: the parent-child relationship, not the name, reveals the attack.
  2. 02Services, tasks and Run keys give persistence: ask who created it, what it launches, does it belong.
  3. 03Medium to High, a user binary as SYSTEM, or High with no consent prompt all signal escalation.
  4. 04LOLBins and PowerShell can't be blocklisted: ask whether this use is normal; 4104 logs decoded code.
  5. 05Any non-system process opening lsass.exe (Sysmon 10) is almost never legitimate.
  6. 06A signature vouches only for its own file; check path, parent and -k before trusting svchost.exe.
