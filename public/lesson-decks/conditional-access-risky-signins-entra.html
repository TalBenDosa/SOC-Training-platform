The one idea: access decisions are adaptive

Conditional Access reads each sign-in's context and applies only the scrutiny that situation warrants.

HACKTHESOCLesson 53Conditional Access6 / 43

A policy engine decides per situation

Too loose

Lets attackers straight through.

Policy engine

Looks at who, from where, on what device, to which app, and decides the response for that situation alone.

Too strict

Every legitimate employee jumps through hoops for zero benefit.

One fixed rule, always or never MFA, is the alternative the engine replaces.
HACKTHESOCLesson 53Conditional Access7 / 43

Claims make sign-in decisions dynamic

  • Token with claimsSmall facts about user and session: group membership, device compliance, calculated risk.
  • Read at sign-inThe same user sails through from the office laptop but is challenged from a new phone abroad.
  • Adds context backA password check is static. Conditional Access does not replace it; it decides how much extra scrutiny to add.
Every later concept is a different way of describing what extra scrutiny this particular sign-in deserves, and why.

How Conditional Access works

Signals lead to conditions lead to access controls.

HACKTHESOCLesson 53Conditional Access9 / 43

Signals, conditions, controls

  1. 1SignalsUser, group, app, device and compliance, location or IP, client app type, risk level.
  2. 2ConditionsTests on those signals: Finance group AND Exchange Online AND outside the corporate network.
  3. 3Grant controlsBlock, or allow but require MFA, a compliant or hybrid-joined device, an approved app.
  4. 4Session controlsShape what happens after access: session lifetime, download restrictions.
Entra ID is Microsoft's cloud identity provider, formerly Azure Active Directory. Every authentication is evaluated against policies before access.
HACKTHESOCLesson 53Conditional Access10 / 43

A real policy: MFA for risky sign-ins

  • If any user, any app, and risk is medium or high, then require MFA
  • excludeUsers: the break-glass account, so no rule locks out every admin
Policies are additive: all applicable ones must be satisfied. Report-only mode lets you observe a policy before enforcing it.

Two evaluation rules for reading logs

Additive, not first-match

All applicable policies must be satisfied, so one policy can challenge and another can block the same sign-in.

Fixed control order

MFA, then device state, then Terms of use. One sign-in can produce more than one log entry as each control is checked.

If you see two entries for one sign-in, this ordering is usually why.
HACKTHESOCLesson 53Conditional Access15 / 43

Legacy authentication: every door, not just IMAP

Basic-auth protocols cannot perform MFA, so they bypass it unless a policy blocks them.

  • Mail protocolsIMAP4, POP3, SMTP AUTH (logged as Authenticated SMTP).
  • Exchange servicesExchange Web Services (EWS), Exchange Online PowerShell, Reporting Web Services.
  • Outlook pathsAutodiscover, MAPI over HTTP, Offline Address Book, Outlook Anywhere, Outlook Service.
  • Exchange ActiveSyncIts own legacy category. Values appear in clientAppUsed.
Extend the hunt's ClientAppUsed filter to this full set so a success over any legacy protocol surfaces as a coverage gap.

Session controls in depth

Four controls that decide how long a stolen token stays useful.

HACKTHESOCLesson 53Conditional Access17 / 43

Four session controls, four different gaps

Session controlWhat it limitsDefault behaviour
Sign-in frequencyTime before re-authentication (OAuth 2.0 / OIDC apps)Rolling 90 days if unset
Persistent browser sessionWhether closing the browser ends the sessionAll-or-nothing per browser
App-enforced restrictionsPasses device state to the app itselfExchange Online, SharePoint Online only
Continuous Access EvaluationHow fast a revoked session stops workingOn by default
Without CAE, a stolen token generally lives until it expires. With CAE, revoking the session can kill it within minutes.
HACKTHESOCLesson 53Conditional Access18 / 43

Tightening an admin portal

  • 4-hour re-auth gives a stolen token a hard expiry, not a 90-day runway
  • never persistent: closing the browser ends the session
  • App-enforced: e.g. web-only mail, no attachment downloads
'The policy required MFA' is not a complete answer to 'how long could a stolen token have been used'. Session controls decide that.

Section 5 of 9

Testing safely: report-only mode

Evaluate against real traffic before enforcing anything.

HACKTHESOCLesson 53Conditional Access20 / 43

Same policy, two states

enabled

Enforced

Enforced from the first sign-in. A badly scoped rule can lock out every admin or leave a gap.

Report-only state

Report-only

enabledForReportingButNotEnforced evaluates every real sign-in and records what it would have done, without enforcing it.

Enforced policies keep running normally alongside a report-only one.
HACKTHESOCLesson 53Conditional Access21 / 43

The practical workflow

  1. 1Draft in report-onlySet state to enabledForReportingButNotEnforced.
  2. 2Run long enoughCover a full weekly and ideally monthly cycle to catch occasional users.
  3. 3Read the workbookInsights and reporting workbook: would-be grants, blocks, challenges by app, user, location.
  4. 4AdjustFix conditions or exclusions for legitimate users caught by controls they should not need.
  5. 5EnforceSwitch state to enabled.
Workbook prerequisites: a Log Analytics workspace receiving sign-in logs, Entra ID P1, and Security Reader plus Log Analytics Reader. Missing them is why results often look empty.

Section 6 of 9

Identity Protection: risky users and sign-ins

Machine-learning risk scores that Conditional Access consumes.

HACKTHESOCLesson 53Conditional Access23 / 43

Two risk scores, two responses

Risky sign-in

One authentication likely not the real user, low to high. Anonymous IP, atypical travel, unfamiliar properties, password spray, token anomalies.

Risky user

The account itself likely compromised, accumulating sign-in risk plus signals like leaked credentials.

Real-time detections drive an immediate decision; offline ones, like impossible travel, raise risk for the next evaluation.

You might challenge one risky sign-in, but a persistently risky user warrants full remediation.
HACKTHESOCLesson 53Conditional Access24 / 43

The loop that risk-based policies close

  1. 1DetectIdentity Protection scores the sign-in medium or high.
  2. 2ReactSign-in risk policy demands MFA in the moment.
  3. 3RemediateMFA succeeds: risk can be auto-remediated and access allowed. MFA fails: denied.
  4. 4EscalateUser risk policy: high user risk requires a secure password change, which revokes sessions.
For analysts: the band sets review order, the risky-user view shows who needs resets, and the remediation state tells you whether the platform already handled it.

How attackers try to evade it

Probe for gaps rather than attack MFA head-on.

HACKTHESOCLesson 53Conditional Access26 / 43

A successful legacy-auth bypass in the sign-in log

  • IMAP4 plus notApplied: no enabled policy was in scope for this client app
  • Single factor only, succeeded, at 03:41
CA can still target legacy via the Client apps condition, but these protocols cannot do MFA so the only effective control is Block. Exchange Online permanently disabled Basic auth for IMAP/POP/EAS/EWS in 2022; read this as the pattern. The live surface is SMTP AUTH, on-prem/hybrid Exchange, and third-party apps.
HACKTHESOCLesson 53Conditional Access27 / 43

The other evasions

T1550

Token theft and replay

AiTM phishing proxies the real login and captures the post-MFA token. Replay skips MFA. Countered by token anomaly detection, CAE, device-bound tokens.

Consent phishing

Obtain OAuth tokens instead of passwords. Covered in its own lesson.

Location and exclusion gaps

Route through a trusted IP range, or find an over-broad excludeUsers entry.

T1550 is Use Alternate Authentication Material. A break-glass exclusion is safe; an over-broad exclusion is a liability once an attacker finds it.

What the analyst sees and how to respond

Read the sign-in log as a narrative of the policy engine's decisions.

HACKTHESOCLesson 53Conditional Access29 / 43
High risk, policy applied, MFA required, MFA not satisfied, sign-in failed: that is the system working.

The entries that demand attention are the mismatches.

Each entry records user, app, time, IP and location, device compliance, client app, Conditional Access result, authentication requirement, risk level and state, and status.
HACKTHESOCLesson 53Conditional Access30 / 43

Mismatches to hunt

  • Legacy successSuccessful sign-in with a legacy client app for a user or app that should need MFA.
  • High risk, single factorA high-risk sign-in still succeeding: a policy gap or an excluded account.
  • Not appliedConditional Access notApplied on a sensitive app: the scope missed it.
  • Token anomaliesA session reused from a new IP or device shortly after AiTM-style phishing.
  • Risky user actingThen registers a new MFA method or creates inbox forwarding rules.
When a step is missing from the story, you have found either an attack or the gap an attacker will use next.
HACKTHESOCLesson 53Conditional Access31 / 43

Expand the per-policy result, not just the summary

  • conditionalAccessStatus is only the summary; the array names each policy's result
  • A sensitive-app sign-in whose MFA policy shows notApplied is the coverage gap
Per-policy result values: success, failure, notApplied (conditions did not match), notEnabled (policy off), and the four reportOnly outcomes. This answers which policy blocked or challenged, and which simply did not apply.
HACKTHESOCLesson 53Conditional Access32 / 43

The CA error codes you meet daily, and What If

  • 53003Access blocked by a Conditional Access policy: the most common CA block.
  • 50074 / 50076MFA required but not completed, or required from this location: a strong-auth challenge was issued.
  • 53000 / 530032Device is not compliant, or blocked by a compliance/security requirement in a CA policy.
  • The What If toolSpecify user, app, IP, device, client app and risk; it reports exactly which policies apply and what they enforce, without replaying traffic.
status.errorCode (KQL ResultType) tells you why a CA outcome happened. A burst of 53003 or 50074 for one account can be a struggling user or an attacker with a valid password repeatedly stopped: correlate with risk and location. errorCode 0 is success, read with authenticationRequirement.

Respond to a confirmed risky account

  1. 1Confirm compromisedIn Identity Protection; this sharpens the model.
  2. 2Reset and revokeForce a secure password reset, revoke sessions and refresh tokens.
  3. 3Re-register MFAAttackers often add their own authenticator.
  4. 4Hunt persistence and fix gapsOAuth grants, mailbox rules; tighten scope, remove exclusions, block legacy.
If a policy gap allowed the attack, feed it back to engineering.

Hunting for Conditional Access gaps

Prove, in writing, whether coverage is complete.

HACKTHESOCLesson 53Conditional Access35 / 43

A KQL hunt for successful legacy authentication

Only legacy protocols, only successes, and the fields to confirm the gap: who, which protocol, from where, and whether Conditional Access evaluated it. Run weekly or as a scheduled analytics rule.
HACKTHESOCLesson 53Conditional Access36 / 43

The other two gaps an attacker hunts for

  • Over-broad exclusionsEnumerate excludeUsers/excludeGroups/excludeRoles via Graph; flag any that is not a documented break-glass account.
  • Watch the excluded principalsIn SigninLogs, excluded accounts hitting sensitive apps with conditionalAccessStatus == notApplied is someone benefiting from the gap.
  • Trusted-location abuseA stolen credential routed through an allowed IP range skips MFA. Flag trusted-location sign-ins contradicted by a new device or foreign ASN.
Also review the named-location CIDR ranges themselves for stale or over-broad blocks. Exclusions and trusted locations are the two gaps attackers probe after legacy auth.
HACKTHESOCLesson 53Conditional Access37 / 43

Two modern controls that close these gaps

Token protection

A session control that binds the token to the device it was issued to, so an AiTM- or infostealer-stolen token fails binding when replayed from the attacker's machine.

CA for workload identities

Extends CA to service principals: block or location-restrict app sign-ins and apply risk detections. Hunt AADServicePrincipalSignInLogs for unexpected IPs.

Non-human identities authenticating outside user-focused policy is a common hole; workload-identity CA closes it.

Token binding is the structural answer to the token-replay evasion in section 7.
HACKTHESOCLesson 53Conditional Access38 / 43
Conditional Access only protects what it actually evaluates.

When a hunt returns results, close the gap: add users or apps to block-legacy-auth, remove the exclusion, tighten the location, or enable token protection, then re-run until zero.

The fix is rarely a detection tweak. It is closing the policy gap itself.

Key takeaways

  1. 01Conditional Access reads sign-in claims and applies controls matched to the situation, like an adaptive checkpoint.
  2. 02A policy has assignments, conditions and grant controls; Block always wins and all applicable policies apply.
  3. 03Session controls and CAE decide how long a stolen token stays useful, not just whether MFA was required.
  4. 04Report-only mode tests a policy against real sign-ins before enforcement.
  5. 05Legacy auth shows as a legacy clientAppUsed with notApplied; AiTM token replay maps to T1550.
  6. 06Hunt SigninLogs for gaps and fix the policy, then re-run the query to prove it closed.

Check your understanding, question 2 of 3

A user is in scope of two enabled policies: one grants access if MFA is satisfied, the other specifies Block access. What is the outcome?

Policies are additive and all applicable ones must be satisfied, and Block always wins. A grant never overrides a block, policies do not cancel out, and creation order plays no part.

Check your understanding, question 3 of 3

An admin wants a stolen admin-portal token to stop working within minutes of a forced password reset, before it technically expires. Which session control is designed for this?

CAE lets supporting services act on a password reset or revocation before the token expires. Sign-in frequency reauthenticates on a schedule, persistent-browser concerns reopening, and app-enforced restrictions pass compliance state, not fast revocation.
