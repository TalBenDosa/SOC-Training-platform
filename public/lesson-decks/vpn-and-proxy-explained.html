Section 1 of 8

What it means to sit in the middle

Both a VPN and a proxy relay traffic, so the far end sees the intermediary, not the real sender.

HACKTHESOCLesson 47VPN and proxy6 / 47

VPN and proxy solve different problems

VPN

Encrypts an entire tunnel of traffic between two points. Typical scope is all traffic from a device. Built for secure remote access.

Proxy

Relays and often filters specific application requests, usually one protocol such as web. Built to enforce policy and log it.

Mixing them up leads to bad investigations: different jobs, different scope, different logs.

VPN expands to Virtual Private Network. Name the distinct job of each up front; the rest of the lesson keeps them apart.
HACKTHESOCLesson 47VPN and proxy7 / 47

The one effect they share

  • A changed apparent sourceBoth can make traffic appear to come from a different IP than the real originating device.
  • Reduced sensor visibilityBoth limit what a security sensor watching the middle of the path can read.
  • So an IP is not an actorBehind either, the address in your log is the intermediary. The real user is one pivot away.
This shared effect is the spine of the lesson: never stop an investigation at an intermediary IP.
HACKTHESOCLesson 47VPN and proxy8 / 47
Encryption scrambles data with a key so anyone without it sees only noise.

A VPN's defining feature is an encrypted tunnel: a sealed, opaque pipe across the open internet that only the two ends can read.

A basic proxy does not necessarily encrypt anything new, though it often runs over HTTPS. The tunnel is what makes a VPN opaque on the wire.

Section 2 of 8

What a VPN is and how it changes the picture

An encrypted tunnel between a client and a VPN server across an untrusted network.

HACKTHESOCLesson 47VPN and proxy10 / 47

How a remote-access tunnel changes the source

  1. 1Before the VPNThe employee's traffic originates from their home ISP address.
  2. 2Traffic enters the tunnelIt is encrypted and encapsulated at the client.
  3. 3It emerges at the concentratorDecrypted at the gateway, it now carries a VPN-pool internal IP such as 10.10.50.14.
  4. 4Inside hosts see the pool IPAny server the user reaches logs the pool address, not the real person.

Site-to-site VPNs link two offices permanently; remote-access VPNs tunnel one laptop in.

The core effect for the analyst: a changed apparent source plus a loss of payload visibility. The real user is on the internet behind the pool IP.
HACKTHESOCLesson 47VPN and proxy11 / 47

A VPN authentication log line, decoded

  • external_ip 95.155.20.44 is the real internet origin
  • assigned_ip 10.10.50.14 is the pool address the user now carries
  • Any later traffic from 10.10.50.14 belongs to d.rosen for this window
This log is the pivot: it ties a pool address to a named user and a real external origin, for one session window only.
HACKTHESOCLesson 47VPN and proxy12 / 47
Encryption shifts your visibility from the network to the endpoints and the gateway logs.

A sensor between client and server sees encrypted blobs, not the requests inside. The gateway records who, from where, when, how long and how much.

Gateway metadata (external IP, user, duration, byte counts) is often your richest source when the payload itself is opaque.
HACKTHESOCLesson 47VPN and proxy13 / 47

Pool addresses are reused, so correlate on time

The trap

Two different employees can hold 10.10.50.14 on different days. The pool address alone names no one.

The discipline

Resolve every pool IP to a named user and real external origin using the gateway log for the exact timestamp, just as with NAT.

Timestamp-accurate correlation is the habit that keeps VPN attribution honest.

Same lesson as NAT: the intermediary is reused over time, so the mapping is only valid for the session window you are investigating.

VPN protocols and tunnel modes

Recognising the protocol in a log tells you how visible the tunnel is on the network.

HACKTHESOCLesson 47VPN and proxy15 / 47

Three protocols, recognisable in logs

ProtocolPort(s)Recognisable as
IPsec (IKE + ESP)UDP 500, IP proto 50, UDP 4500 (NAT-T)Distinct ports and protocol numbers
SSL / TLS-VPNTCP 443Blends in with ordinary HTTPS
WireGuardUDP 51820 (default)A single consistent UDP port

IKE negotiates keys; ESP carries the encrypted data; NAT-T wraps both in UDP 4500 when a NAT device is in the path.

IPsec is Internet Protocol Security, IKE is Internet Key Exchange, ESP is Encapsulating Security Payload. The port pattern is how you spot each on the wire.
HACKTHESOCLesson 47VPN and proxy16 / 47

IPsec establishing, in a firewall log

  • UDP 500 first: the IKE key negotiation
  • UDP 4500 next: NAT-Traversal wrapping ESP because a NAT is in the path
  • The distinct ports make IPsec easy to fingerprint
Contrast with SSL-VPN, which hides on TCP 443. Recognising the ports lets you tell a VPN handshake from ordinary traffic.
HACKTHESOCLesson 47VPN and proxy17 / 47
SSL-VPN on port 443 is the detection challenge: it looks like web browsing.

It passes through any firewall that allows outbound HTTPS, which is convenient for users and hard to distinguish on a network sensor.

IPsec's distinct ports and WireGuard's single UDP port are easier to fingerprint. SSL-VPN deliberately blends in.
HACKTHESOCLesson 47VPN and proxy18 / 47

Split tunnel vs full tunnel: a visibility choice

Full tunnel

All the device's traffic routes through the corporate gateway, so the SOC and web proxy see and can police everything. Costs bandwidth and latency.

Split tunnel

Only corporate-bound traffic uses the tunnel; general browsing goes out directly, bypassing corporate monitoring. Cheaper, faster, and a visibility gap.

A split-tunnel device is trusted inside and exposed to the open internet at once: a bridge an attacker can use.

This is a routing choice independent of protocol. It directly decides how much of the endpoint's activity you can see.
HACKTHESOCLesson 47VPN and proxy19 / 47

IPsec transport mode vs tunnel mode

ModeESP encryptsOriginal IP header
TransportOnly the payloadKept visible; host-to-host use
TunnelThe entire original packetWrapped in a new outer header; VPN use

Tunnel mode is what makes a VPN a VPN: the real inner source and destination are hidden, only the gateway-to-gateway header shows.

When you see a remote-access or site-to-site VPN, assume tunnel mode. Transport mode appears only when the two machines are themselves the endpoints.

Section 4 of 8

Forward and reverse proxies

Keep the direction straight: one sits in front of users, the other in front of servers.

HACKTHESOCLesson 47VPN and proxy21 / 47

Two proxies, opposite positions

PropertyForward proxyReverse proxy
PositionIn front of clientsIn front of servers
Protects / servesInternal usersBackend servers
HidesClient identity from the webServer details from clients
Key SOC log valueOutbound URL historyInbound request inspection (WAF)

Corporate web proxies (secure web gateways) are forward; NGINX, HAProxy and CDN/WAF services are reverse.

Confusing the two leads to bad analysis. Forward centralises outbound web history; reverse can hide the real client IP.
HACKTHESOCLesson 47VPN and proxy22 / 47
A forward proxy is one of your best log sources for C2 and exfiltration.

From the web's view all users share the proxy's public IP, like NAT, but the proxy holds a complete, central record of every outbound URL.

That centralised outbound URL history is where command-and-control beacons and large uploads surface. Treat it as a primary hunting source.
HACKTHESOCLesson 47VPN and proxy23 / 47

X-Forwarded-For carries the real client

  • The first address, 88.212.14.9, is the original internet client
  • 10.0.0.5 is an internal relay hop added after it
  • Log only the proxy's IP and you are looking at the relay, not the actor
A reverse proxy may show its own IP as the source on the backend unless it inserts X-Forwarded-For (or X-Real-IP). Always check for it.
HACKTHESOCLesson 47VPN and proxy24 / 47
TLS inspection decides whether you see content or only metadata.

A proxy configured as a controlled man-in-the-middle decrypts TLS so its engine reads URLs and payloads. Without it, you get the destination and metadata only.

Knowing whether TLS inspection is enabled in your environment tells you how much of a proxied session you can actually read.

Section 5 of 8

Proxy protocols and types

Not every proxy understands the application it relays, and that changes what it can log.

HACKTHESOCLesson 47VPN and proxy26 / 47

SOCKS: a protocol-agnostic relay

What it is

SOCKS (Socket Secure, v5 in RFC 1928) forwards raw TCP, and UDP in v5, without understanding the application inside. It can tunnel web, mail, database or a remote shell.

Why it matters

Because it relays anything, it is a favourite pivot. A compromised host can tunnel deeper while a sensor sees only one encrypted session.

An application-aware proxy reads URLs and enforces policy; SOCKS does not, so it logs far less about the content.

A common admin pattern turns an SSH connection into a local SOCKS proxy, which is also how an attacker pivots. The defender sees the outer session, covered next.
HACKTHESOCLesson 47VPN and proxy27 / 47

What the defender sees of a SOCKS pivot

  • A network sensor sees a single SSH session to the jump box
  • The real destinations tunnelled inside are invisible at the network layer
  • Endpoint telemetry, not the network sensor, is where this surfaces
The teaching point is a blind spot: one benign-looking SSH session can carry many hidden destinations, so you pivot to the endpoint.
HACKTHESOCLesson 47VPN and proxy28 / 47

The proxy types you will meet

TypeClient config?Understands the app?
Forward (explicit)YesOften HTTP-aware
TransparentNo, the network redirects itOften HTTP-aware
SOCKSYes, per applicationNo, a generic relay
CASBVaries: forward / reverse / APICloud-app aware

A transparent proxy intercepts traffic the client never addressed to it, which is why client traffic appears in proxy logs at all.

CASB is Cloud Access Security Broker: it brings the same broker-in-the-middle idea to SaaS, covering shadow IT and DLP a network proxy cannot interpret.

How attackers abuse VPNs and proxies

The same middle position hides their true origin and blends their traffic in.

HACKTHESOCLesson 47VPN and proxy30 / 47

Four abuse patterns

  • Hiding originRoute through commercial VPNs, Tor or residential proxies so a login looks like a datacenter or a home user, not the attacker.
  • C2 through proxiesReach the command-and-control server via chains of relays, so the visible endpoint is a hop, not the operator.
  • Rogue VPNsInstall unsanctioned VPN software on a host to tunnel an encrypted channel past network sensors.
  • Bypassing controlsInsiders run a personal VPN to evade the corporate proxy's policy and logging.

Residential proxies are the nastiest: they route attacker traffic through real consumers' compromised devices.

A newly installed, unsanctioned VPN client on an endpoint is a serious finding. Pivot on behaviour, not on any single IP being bad.
HACKTHESOCLesson 47VPN and proxy31 / 47

Why residential proxies are the hardest to spot

Datacenter VPN

A login from a hosting or VPN provider's range stands out against a residential-ISP baseline, so IP category enrichment flags it.

Residential proxy

Traffic is routed through real consumers' compromised home devices, so the source looks like an ordinary home user and category enrichment does not help.

The lesson: pivot on behaviour (beaconing, odd destinations), not on any single IP looking bad.

This is why IP reputation alone is not enough. Residential proxies defeat the category check that catches cruder hiding.
HACKTHESOCLesson 47VPN and proxy32 / 47

The four Proxy sub-techniques (T1090)

Sub-techniqueIDAnalyst impact
Internal ProxyT1090.001Internal host-to-host relaying; the loud host is not the entry point
External ProxyT1090.002The IP you see is a relay; blocking it does not reach the attacker
Multi-hop ProxyT1090.003Chains like Tor; tracing the true source may need each hop's cooperation
Domain FrontingT1090.004Looks like a trusted CDN domain; only SNI/Host mismatch reveals it
A related technique, Protocol Tunneling (T1572), smuggles one protocol inside another (a shell inside DNS or HTTPS) to slip past controls expecting the outer protocol.
HACKTHESOCLesson 47VPN and proxy33 / 47

How Tor multi-hop routing works

Tor (The Onion Router) is the best-known multi-hop proxy, T1090.003.

  1. 1Three layers of encryptionThe client wraps traffic in three layers and picks three volunteer relays.
  2. 2Entry (guard) nodeKnows the user but not the destination.
  3. 3Middle relayKnows only the hop before and after it.
  4. 4Exit nodeKnows the destination but not the user; the site sees only the exit IP.

A login from a known Tor exit node, when your workforce uses residential ISPs, is a high-value signal. Public exit lists let SIEMs tag it.

No single relay sees both ends, which is why tracing the true origin through Tor is so hard. The exit IP is all the destination learns.
HACKTHESOCLesson 47VPN and proxy34 / 47

Domain fronting, concretely

What the filter sees

The TLS handshake advertises an innocent, allow-listed domain (cdn.trusted-provider.com) in the visible SNI field, so the connection is permitted.

What is really happening

Inside the encrypted session the HTTP Host header names a different domain the same CDN serves: the attacker's real C2.

The SNI-to-Host mismatch is the tell, visible only where TLS is decrypted.

SNI is Server Name Indication. Domain fronting abuses shared CDN infrastructure so the connection looks like trusted-CDN traffic.

Detection considerations

You cannot ban all VPNs and proxies, so detect anomalous use and preserve correlation.

HACKTHESOCLesson 47VPN and proxy36 / 47

Five detection habits

  • Enrich source IPsTag events with datacenter, VPN, Tor-exit or residential category. A login from a VPN block when users are on residential ISPs is a signal.
  • Watch impossible travelA login from one country then another thousands of km away minutes later means a shared credential or a relocating proxy.
  • Hunt rogue tunnelling on endpointsNewly installed VPN/proxy software, or a host that stops routing web traffic through the corporate proxy.
  • Lean on metadataWhen TLS is opaque, use destination, timing, duration and byte counts. Beaconing survives encryption.
  • Resolve the intermediaryAlways pivot from the pool IP, proxy IP or X-Forwarded-For to the real user and origin.
Detection is about anomalous use, not banning the tools. The recurring theme: an intermediary IP is not the actor.
HACKTHESOCLesson 47VPN and proxy37 / 47

Enriching a source IP with category data

CategoryWhat it suggestsWeight against a residential baseline
Residential ISPAn ordinary home or mobile userBaseline: usually expected
Hosting / datacenterA server range, not a personElevated: users rarely log in from here
Known VPN / proxyAn anonymising intermediaryElevated: pivot to find the real origin
Tor exit nodeMulti-hop anonymisationHigh: public exit lists let SIEMs tag it
Many SIEMs apply this tag automatically. The weight is relative to your workforce's normal login pattern, which is why you baseline first.
HACKTHESOCLesson 47VPN and proxy38 / 47
Beaconing is detectable in metadata alone, even when the content is encrypted.

Regular, machine-like connection intervals to the same destination are a classic C2 pattern that a tunnel cannot hide.

This is why timing analysis matters: encryption hides the payload, not the rhythm of the connections.
HACKTHESOCLesson 47VPN and proxy39 / 47

Why resolving the intermediary is non-negotiable

Investigation stops at the IP

You block the pool or proxy address, cut off every legitimate user behind it, and still have not found the actor.

Investigation pivots

You use the gateway, proxy and identity logs to reach the named user and true origin, and scope correctly.

An investigation that stops at the intermediary IP is only half done.

Make this the closing reflex of the section: the IP is a doorway to the actor, not the actor.

Worked scenario: VPN, proxy and firewall logs

An alert fires: large upload to an external file-sharing site from an internal proxy IP.

HACKTHESOCLesson 47VPN and proxy41 / 47

Three logs, three vantage points

  • Proxy shows 10.10.50.14 uploading 850MB, but no named user
  • VPN log maps 10.10.50.14 to d.rosen from 09:01:55, before the upload
  • Firewall confirms the same byte count leaving via the proxy's public IP
Three vantage points, one event. None alone names the actor and the action together.
HACKTHESOCLesson 47VPN and proxy42 / 47

Chaining the logs into one story

  1. 1Start at the alertThe proxy shows 10.10.50.14 uploading 850MB to a file host, but no authenticated user.
  2. 2Pivot to the VPN gatewayThat pool address was assigned to d.rosen at 09:01:55, before the upload: attributable for this window.
  3. 3Corroborate at the firewallThe same 850MB leaves through the proxy's public IP, confirming the transfer size.
  4. 4Now ask the real questionIs d.rosen's 850MB upload a policy violation or a business need? You can only ask it having chained the logs.

Shared identifiers (pool IP, timestamp, byte count) stitch three thin log lines into one coherent, attributable story.

The pattern every investigation here follows: never trust a single log alone; chain the intermediary back to the real actor.
HACKTHESOCLesson 47VPN and proxy43 / 47

Key takeaways

  1. 01A VPN encrypts a whole tunnel; a proxy relays specific application traffic. Both change what a sensor sees.
  2. 02A VPN or proxy IP is an intermediary, not the actor: pivot via gateway, proxy and identity logs to the real user.
  3. 03Forward proxies centralise outbound URL history; reverse proxies can hide the client IP unless X-Forwarded-For is set.
  4. 04Tunnels encrypt payloads, so shift detection to metadata and endpoints: reputation, impossible travel, rogue VPNs, beaconing.
  5. 05Recognise protocols in logs: IPsec on UDP 500/4500 and proto 50, SSL-VPN on 443, WireGuard on UDP 51820.
  6. 06Real investigations chain VPN, proxy and firewall logs through shared identifiers into one attributable story.

Pool addresses are assigned dynamically, so only the gateway logs tie that address at that time to a named user and real origin. The pool IP is not a host to isolate, and blocking the pool cuts off all remote users.
