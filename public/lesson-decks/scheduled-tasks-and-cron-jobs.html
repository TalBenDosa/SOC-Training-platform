Section 1 of 7

Why scheduling exists

Backups, updates, log rotation and cleanup run so humans do not have to remember.

HACKTHESOCLesson 73Scheduled tasks and cron6 / 61

Four words to pin down before anything else

  • SchedulerThe part of the operating system that runs a chosen program automatically, without anyone launching it by hand.
  • TriggerWhen the job runs: a time, a recurring interval, or a system event such as startup or logon.
  • ActionWhat runs: usually a program, a script or a command.
  • Job / taskOne saved pairing of trigger and action. Windows calls it a scheduled task, Linux a cron job.
Students often blur trigger and action. Make them say both halves out loud for every example in this lesson.
HACKTHESOCLesson 73Scheduled tasks and cron7 / 61

Every scheduled job has two halves

When

Trigger

A time ("2:00 a.m. daily"), an interval ("every 15 minutes"), or a system event ("at startup", "at user logon").

  • Time: once or recurring
  • Interval: every N minutes or hours
  • Event: boot, logon, a log entry

What

Action

Usually a program, script or command. This is where a malicious job gives itself away, because the attacker must put their payload here.

  • A program path
  • A script
  • A command line with arguments
This applies identically to Windows and Linux, which is why the detection questions later are the same on both.
HACKTHESOCLesson 73Scheduled tasks and cron8 / 61

Legitimate jobs are everywhere, and that is the camouflage

Routine jobTypical triggerWhy it is scheduled
Nightly backupDaily at 2:00 a.m.Copies data while nobody is working
Software updatesDaily, or at startupKeeps the OS and apps patched without a user remembering
Log rotationDailyArchives old logs so disks do not fill up
Cleanup and health checksEvery N minutes or hoursRemoves temp files, checks that services are alive
A fresh Windows install already has dozens of tasks and every Linux box has cron jobs. A malicious one hides in that crowd, so 'there is a scheduled job' is never suspicious on its own.

Two intruder problems solved at once

Survive reboots

Persistence

A task set to run at startup relaunches malware on every boot, so a reboot or a logoff no longer removes the attacker.

Self-heal quietly

Stealth and resilience

An hourly task quietly re-establishes a connection or relaunches a killed payload, hiding among many legitimate scheduled jobs.

The capability is completely legitimate. That is exactly what makes it useful to attackers: nothing has to be exploited, only configured.

Section 2 of 7

Windows scheduled tasks

Task Scheduler pairs one or more triggers with one or more actions.

HACKTHESOCLesson 73Scheduled tasks and cron12 / 61

How a Windows task goes from definition to running process

  1. 1RegisteredThe task is saved as XML under C:\Windows\System32\Tasks and indexed in the Registry.
  2. 2WatchedThe Task Scheduler service tracks every enabled trigger for every registered task.
  3. 3Trigger firesThe time arrives, the machine boots, a user logs on, or a matching event is logged.
  4. 4Action launchedThe service starts the action's command under the task's chosen account.
  5. 5TelemetryEDR sees the action as a new process; registration itself left a 4698 and a 106 event.
Walk the chain once with a benign task, then once with the malicious one from section 7. The mechanism is identical; only the action and account differ.
HACKTHESOCLesson 73Scheduled tasks and cron13 / 61

Rich triggers are part of why tasks are abusable

TriggerExampleValue to an attacker
Time or recurring scheduleDaily, hourly, every N minutesTight intervals give a self-healing beacon
At system startupRuns on every bootFavourite for persistence: no user needs to log on
At user logonA particular user, or any user, signs inFires every time someone uses the machine
On a system eventA specific log entry appearsRuns only when a chosen condition happens
Startup and any-user logon give the broadest re-execution. Keep those two in mind when reading the XML in section 3.
HACKTHESOCLesson 73Scheduled tasks and cron14 / 61

Three ways a task is managed, and the same file underneath

  • Task Scheduler appThe graphical tool; shows a summary view that can hide details such as the running account or hidden tasks.
  • schtasks.exeThe command-line tool. schtasks /create is the CLI way to plant a task, and a common one in attacks.
  • PowerShellThe ScheduledTasks commands, such as Register-ScheduledTask, create the same task as objects.
  • StorageWhatever the tool, the definition ends up as an XML file under C:\Windows\System32\Tasks, referenced in the Registry.
Because all three routes end in the same file and the same events, detection on the result catches every route; detection on the command line tells you which route was used.

What attackers get, and the recurring giveaway

T1053.005

Why attackers use tasks

Automatic execution, a choice of boot, logon or interval, a chosen account including highly privileged ones, and camouflage among dozens of real tasks.

Read this first

The giveaway: the action

Legitimate maintenance runs a recognisable program. Malicious tasks run PowerShell with an encoded command, a script from a temp folder, or a suspicious binary.

Action, trigger and name together tell you whether a task belongs. The name is the easiest to fake, the action the hardest.

Anatomy of a task definition

The XML says when it runs, what it runs, and under what identity.

HACKTHESOCLesson 73Scheduled tasks and cron18 / 61
The XML is the truth. The GUI summary hides the principal.

The principal is the account and privilege level the action runs under. Reading the raw XML, as you do when triaging an alert, shows it plainly.

This is the one new concept in the section. Everything else is the trigger and action students already know, written as XML.

<Author>Free-text name of who or what created the taskA useful lead, but the creator can set it to anything; confirm with the 4698 Subject fields
<Triggers>Logon, Boot, Time, Calendar, Event triggersBoot/Logon give the broadest re-execution; EventTrigger fires on a log entry

Three different identities live around one task

Claimed

Author

Free text in the XML. Whoever registers the task can type any name here, so it is a lead, never proof.

Runs as

Principal

The account the action executes under, here SYSTEM. It is not necessarily the account that created the task.

Registered by

4698 Subject

SubjectUserName, SubjectDomainName, SubjectLogonId: filled by Windows from the session that registered the task. The reliable record.

The most common triage mistake is reading Author as the creator. Always pivot to the Subject fields and that logon session.
HACKTHESOCLesson 73Scheduled tasks and cron23 / 61

Where the task lives, and what that tells you

  1. 1Check the fileOne XML file per task, no extension, under C:\Windows\System32\Tasks\<TaskPath>.
  2. 2Check the RegistryThe task is indexed under HKLM\Software\Microsoft\Windows NT\CurrentVersion\Schedule\TaskCache.
  3. 3Compare bothTask persistence leaves a footprint in the filesystem and the Registry; a thorough investigation checks both.
  4. 4Infer the rightsA SYSTEM principal or any-user logon trigger needs admin rights, so admin was already in play on that host.
The admin-rights inference is a real pivot: an ordinary employee name on a SYSTEM task means either that account has admin it should not, or the attacker escalated first.

Section 4 of 7

Linux cron jobs

The cron daemon wakes every minute and runs whatever is due.

HACKTHESOCLesson 73Scheduled tasks and cron25 / 61

How cron decides what to run

  1. 1Wake upA background service, the cron daemon, wakes once every minute.
  2. 2Read the tablesIt reads the per-user crontabs, the system crontab and the cron directories.
  3. 3Compare the timeFor each line it checks whether the five time fields match the current minute.
  4. 4Run what is dueMatching commands run as the owning user, so a root crontab line runs as root.
Because of the one-minute tick, the tightest cron schedule is every minute. A per-minute line on a server is worth a second look.
HACKTHESOCLesson 73Scheduled tasks and cron26 / 61

Where cron jobs live, and attackers hide

Per-user crontabs

Each user has their own list. Edited with crontab -e, viewed with crontab -l. Runs as that user, including service accounts like www-data.

System crontab

/etc/crontab and files in /etc/cron.d/: system-wide jobs, often run as root.

Drop-in directories

/etc/cron.hourly/, daily, weekly, monthly: any script placed inside runs on that cadence, no time fields needed.

Also systemd timers and the at command for one-off runs. Attackers use these too.

Drop-in directories are easy to miss: there is no cron line to read, just a script file that appeared. File-integrity monitoring catches that.
HACKTHESOCLesson 73Scheduled tasks and cron27 / 61

Read the five time fields, then the command

  • Read left to right: minute, hour, day of month, month, day of week
  • An asterisk means every value of that field
  • Everything after the fifth field is the command
Have students read the order aloud: minute first, not hour. Swapping them is the classic misread.
HACKTHESOCLesson 73Scheduled tasks and cron28 / 61

Practise reading real cron lines

Cron lineWhen it runsReading
0 3 * * *At 03:00 every dayNormal maintenance cadence
0 2 * * * .../backup.shAt 02:00 every dayA documented backup script: benign
/10 * * *Every 10 minutesTight: check what the command does

An entry set to run every minute or every few minutes is a common beaconing and persistence pattern, especially when the command reaches the network.
HACKTHESOCLesson 73Scheduled tasks and cron29 / 61

Step syntax: */N counts inside its own field

  • */5 in minutesEvery 5 minutes.
  • */2 in hoursEvery other hour.
  • */35 in minutesMinutes 0 and 35 of each hour, because the step is evaluated inside 0-59 and resets each hour.
  • 0 /5 * *Every 5 hours at minute 0. Compare with /5 * * *, every 5 minutes.
The quiz tests exactly this: */5 in the first field is minutes, not hours.

Two more Linux schedulers to check

T1053.006

systemd timers

A timer unit activates a service unit on a schedule, doing cron's job through systemd. Listed with systemctl list-timers --all.

T1053.002

at

Schedules a one-off run at a set time. Useful to an attacker for a single delayed execution.

If a hunt only checks crontabs, a timer or an at job slips through. Name all three when you write a Linux persistence checklist.
HACKTHESOCLesson 73Scheduled tasks and cron32 / 61
One cron line can be self-healing persistence.

A job that pulls a script with curl ... | bash or reopens a connection every few minutes comes back even after you kill the process (T1053.003).

Killing the running payload is not remediation. The scheduler will start it again at the next tick; the job itself must be removed.

Same tool, two very different shapes

Built-in update task

Lives under \Microsoft\Windows\..., runs a signed system component, installed by Windows itself.

Planted task

A legitimate-sounding name at the root, an encoded PowerShell action, a boot trigger, and the SYSTEM account, created from a command line.

The planted task, as process telemetry shows it

  • A name chosen to sound legitimate
  • The payload is truncated Base64: decode it in your sandbox, not on the host
  • Every flag is also captured in the resulting Event 4698
A schtasks /create line in EDR process history is often the clearest evidence a task was deliberately planted rather than always there.

Reading those three listings

backup.sh at 02:00

A documented script in the application's own folder on a nightly cadence: matches the build documentation.

A web service account calling an external IP every two minutes, with the hostname in the URL so the server knows which host checked in.

The www-data job is a live beacon. The hostname parameter is the tell: the remote side is tracking which compromised hosts are alive.

Both platforms leave traces of creation and modification.

When 4698 is missing, the Operational log still talks

Rich detail, including the task name and action, but only when task auditing is enabled on the host.

On by default

On hosts where the 4698 family is not audited, the Operational log tells the same story with less detail.

Event 106 as it appears in the Operational log

  • Which task: the full task path to look up on disk

Linux: four places the evidence lives

  • File-integrity monitoringChanges to /etc/crontab, /etc/cron.d/, the cron.* drop-in folders and user crontabs. A core detection.
  • auditd or EDRA user running crontab -e, or a file written into a cron path by an unexpected process.
  • Cron's childrenThe cron daemon spawning bash, curl, or a script from /tmp.
  • Cron's own logEach run is logged with the user and command, in /var/log/cron or syslog CRON lines, depending on the distribution.
The cron log shows execution; FIM and auditd show creation. You want both: one proves it ran, the other proves who planted it.

What a cron beacon looks like in telemetry

  • The user in brackets is whose crontab it came from
  • cron as the grandparent of curl: a scheduled network call
  • Repeats every two minutes: count the lines to see the interval
Clustering CRON lines by command and counting them per hour is a quick way to surface beacon-like jobs across a fleet.

Legitimate job or planted persistence

Usually legitimate

Fits the build and the vendor's known tasks.

  • Installed by software or a deployment
  • Runs a recognisable program
  • Sensible schedule: daily, weekly
  • Name and path match the vendor

Planted persistence

Fails one or more of the three questions.

  • Created by an unexpected process or user
  • Hidden or encoded action
  • Aggressive interval, boot or logon
  • Odd or masquerading name
No single item convicts. Two or three red items together, plus a creation event you can tie to a session, is a strong case.
HACKTHESOCLesson 73Scheduled tasks and cron49 / 61

Three questions for any job, on either platform

  1. 1When does it run?Startup, logon, or a suspiciously tight interval.
  2. 2What does it run?A recognisable program, or encoded PowerShell, a temp-folder binary, a shell download.
  3. 3Who or what created it?A software install, or a suspicious process or user.

Treat job creation and modification as inherently interesting, then correlate with the process tree and file activity.

Legitimate jobs are installed by software and run recognisable programs on sensible schedules. Odd name, hidden action, aggressive interval: that is the persistence you want.

Excess rights

Hypothesis A

j.chen holds local admin rights it should not. Check the local Administrators group on the host.

Escalation

Hypothesis B

Key takeaways

  1. 01A scheduler runs an action on a trigger; Windows tasks and Linux cron are both abused for persistence (T1053).
  2. 02Task XML reveals Author, Triggers, Principal, Exec and Hidden; SYSTEM plus HighestAvailable is maximum privilege.
  3. 03Cron lives in user crontabs, /etc/crontab, /etc/cron.d and drop-in folders; @reboot is boot persistence.
  4. 04schtasks /create, Register-ScheduledTask, crontab -u and systemctl list-timers are what to look for.
  5. 05Detect with 4698 and 4699/4702, TaskScheduler 106/140/141, and cron FIM with auditd or EDR.
  6. 06Judge every job by when it runs, what it runs, and who created it: trust the 4698 Subject fields over Author.
