How cloud identities prove who they are

Human or machine, and the crucial split: long-lived versus temporary.

HACKTHESOCLesson 61Cloud auth and access keys6 / 78

Two kinds of identity

Human identities

Engineers in the AWS console, admins in the Azure portal. Username and password, ideally with MFA, increasingly through SSO.

Machine identities

Applications, VMs, scripts calling the cloud with no human present. They cannot type a password, so they use a key or a token.

Everything else in the lesson builds on this split.

Long-lived vs temporary credentials

Long-lived

Static until manually revoked. AWS access key: an ID starting AKIA plus a secret access key. Azure: a service principal with a client secret or certificate. Stolen, it works for the thief indefinitely.

Temporary

AWS STS issues keys starting ASIA that expire in minutes to hours. Azure issues short-lived tokens. A stolen one has a small window.

Prefer temporary, prefer platform-managed, and treat every long-lived key as a liability.

Best practice: attach a role and let the platform hand out rotating credentials. An EC2 instance or Azure VM with a managed identity never stores them on disk.
HACKTHESOCLesson 61Cloud auth and access keys9 / 78

How a role hands a workload temporary credentials

The mechanism behind "attach a role, store nothing".

  1. 1Attach a roleAn EC2 instance profile or an Azure managed identity binds an identity to the compute resource.
  2. 2Workload asks the platformThe SDK calls a local endpoint on the host, never a stored file.
  3. 3STS issues a sessionKey ID (ASIA), secret key, session token and an expiry time.
  4. 4SDK refreshes earlyBefore expiry the SDK fetches a fresh set; no human rotates anything.
  5. 5Nothing on diskThere is no long-lived secret to commit, copy or paste into chat.
This is why "prefer roles" is the first line of every key playbook. Section 8 shows the local endpoint (IMDS) and how it has been abused.
HACKTHESOCLesson 61Cloud auth and access keys10 / 78

What a temporary credential actually contains

  • ASIA prefix: an STS session, not a static key
  • Three parts travel together; the session token is required on every call
  • Expiration: after this time the stolen copy is useless
Contrast with an AKIA key: two parts only (ID and secret) and no expiry field at all. That missing Expiration line is the whole risk in one picture.

Section 2 of 10

Federation and single sign-on

How enterprises actually log in: one identity provider, trusted by everything else.

HACKTHESOCLesson 61Cloud auth and access keys12 / 78

Identity lives in exactly one place

  • FederationEvery system, AWS and Azure included, trusts the company's identity provider (IdP) instead of keeping its own password.
  • SSOOne authentication event unlocks email, internal apps and the cloud console.
  • SAML and OIDCSAML POSTs an XML assertion to the service provider; OIDC issues an ID token. Both prove identity without sharing a password.
  • Cross-account rolesA role's trust policy names which external principals may assume it; its permissions policy names what they can do.
A separate password per employee per cloud account does not scale, and every extra password is another place to leak and enforce MFA.
HACKTHESOCLesson 61Cloud auth and access keys13 / 78

SAML and OIDC carry the same promise in different envelopes

Older, XML-based

SAML

The IdP signs an XML assertion (who the user is, which roles, how long) and the browser POSTs it to the service provider, which checks the signature.

Modern, JSON tokens

OIDC on OAuth 2.0

The IdP issues a signed ID token (a JWT) with claims such as issuer, subject, audience and expiry. The app validates it; OAuth access tokens then call APIs.

Either way, the cloud never sees the user's password: it trusts a signature from the IdP.

Students do not need to implement either. They need to recognise that a SAML assertion and an OIDC token are both "a signed note from the IdP", and that whoever can obtain one is the user as far as the cloud is concerned.
HACKTHESOCLesson 61Cloud auth and access keys14 / 78

A SAML sign-in to AWS, step by step

  1. 1User signs in at the IdPPassword plus MFA happen here, at the corporate IdP, not at AWS.
  2. 2IdP builds an assertionSigned XML: user identity, permitted roles, session length.
  3. 3Browser POSTs it to AWSThe assertion travels to the AWS sign-in endpoint.
  4. 4AWS checks and calls STSSignature matched against the trusted IdP; AssumeRoleWithSAML runs.
  5. 5Temporary session opensSTS returns ASIA credentials; the console session starts.
Point out where MFA lives: step 1. If the IdP is fooled, steps 2 to 5 run exactly as for the real user, which is why the IdP is the front door.
HACKTHESOCLesson 61Cloud auth and access keys15 / 78

The federated session as it lands in CloudTrail

  • SAMLUser and identityProvider: the session came from the corporate IdP
  • roleArn: which role, and so which permissions, the user received
  • The returned ASIA key ID: pivot on it to see everything this session did
This is the seam between the IdP log and the cloud log. Join them on user name and time: a risky IdP sign-in followed by this event is the federated compromise path.

How federation looks in each cloud

Formerly AWS SSO

AWS IAM Identity Center

Connects to the IdP and grants temporary credentials for a role via AssumeRoleWithSAML (or the OIDC equivalent). The user never has an IAM password.

Is the IdP

Microsoft Entra ID

The identity provider for the whole Microsoft ecosystem. Most other applications federate into it.

Recognising AssumeRoleWithSAML in CloudTrail tells you a federated session started there.

The corporate identity provider is the front door to everything, cloud included.

A compromised IdP account or SSO session cascades into every trusting system, often with no cloud-native alert, because it looks like the real user.

So the SOC watches the IdP's own sign-in and MFA logs as closely as CloudTrail or Azure Activity. The compromise often happens one hop upstream of the cloud.
HACKTHESOCLesson 61Cloud auth and access keys19 / 78

A federated compromise leaves traces in two places

Upstream: the IdP log

The compromise itself happens here, so the earliest warning is here too.

  • Risky or unfamiliar sign-in
  • MFA prompt burst or new MFA method
  • Session token reused from a new IP

Downstream: the cloud log

The cloud sees a legitimate federated user and raises no cloud-native alert.

  • AssumeRoleWithSAML that looks normal
  • Roles the user rarely picks
  • Actions outside their usual pattern
The skill is the join: correlate the IdP sign-in with the cloud session that follows it. Either log alone looks harmless.

Section 3 of 10

Access keys: the credential that leaks

Convenient to paste into a script, which is exactly why they end up where they should not.

HACKTHESOCLesson 61Cloud auth and access keys21 / 78

Where keys leak, and what happens next

Where they leak

Static secrets end up in places they should never be.

  • Git commits, esp. public GitHub (bots scan for AKIA)
  • CI/CD logs and build output
  • Laptops, shared drives, chat messages
  • Container images and config files

What the thief does

No password to guess, no MFA prompt. The key is the proof of identity.

  • Enumerate what the key can do
  • Look for a path to escalate
  • Read data, launch resources (crypto-mining)
  • Persist: new users and keys
Attackers' bots often start using a leaked key within minutes of the push, so the first minutes matter.
HACKTHESOCLesson 61Cloud auth and access keys22 / 78

The stolen-key arc, as a sequence of CloudTrail events

What the analyst sees, call by call, when a leaked key is used.

  1. 1Who am I?GetCallerIdentity from a new IP: the thief checks whose key it is.
  2. 2EnumerateBursts of List, Describe, Get* calls across IAM, S3, EC2.
  3. 3Probe for escalationPolicy and user changes tried; many end in AccessDenied.
  4. 4Act on the goalGetObject on data, or RunInstances for mining.
  5. 5PersistCreateUser, CreateAccessKey: a way back in after revocation.
GetCallerIdentity needs no permissions, so it always succeeds; seeing it as the first call from an unfamiliar IP is a strong early signal. A cluster of AccessDenied errors is an attacker learning the key's limits.
HACKTHESOCLesson 61Cloud auth and access keys23 / 78

The first call from a leaked key

  • AKIA: a static key, so revoking it is on the table immediately
  • ci-deploy normally runs only from the CI runner's IP range
  • An unusual userAgent for this key is a second deviation
Fictional values. The point is that every field is compared with this key's own history, not with a global rule.

Defending access keys: a short, strict playbook

  • Prefer rolesUse temporary credentials and managed identities wherever possible.
  • RotateRotate keys that must exist; delete unused ones.
  • Scope tightlyLeast privilege makes a leaked key far less damaging.
  • Never commitScan repositories and CI logs for secrets.
  • Monitor usageFirst use from a new location should stand out.

An access key is a password that never changes, works from anywhere, and is often written down.

Treat it accordingly. This mental model explains every item on the playbook.

AKIA or ASIA in an alert: the first questions differ

AKIA: a static key

It works until someone revokes it, so ownership and location decide fast.

  • Should this key exist at all?
  • Who owns it, and where does it normally run?
  • Is this source IP in its history?
  • When was it last rotated?

ASIA: a session

It expires on its own, so the question is where it came from.

  • Who minted it? Read sessionIssuer.arn
  • Workload role or human federation?
  • Used after its expected lifetime?
  • Was the parent a stolen AKIA key?
ASIA is healthier, not automatically safe: a session minted from a stolen AKIA key is attacker-controlled for its whole lifetime.

Scoping a compromised credential

A stolen credential is only as dangerous as the policy behind it.

HACKTHESOCLesson 61Cloud auth and access keys33 / 78
Given this compromised identity, what is the worst that could have happened?

Do not stop at revoking the credential. Pull up its attached policies and read exactly what it could do.

The full mechanics of policy evaluation and least privilege live in the Cloud IAM and Privilege Escalation and Cloud Security Fundamentals lessons; here the point is the authentication one.
HACKTHESOCLesson 61Cloud auth and access keys34 / 78

What to read in the compromised identity's policies

  • Which resourcesWhich buckets and which regions were within reach.
  • Destructive actionsCould it call DeleteBucket, TerminateInstances or CreateUser?
  • Limiting conditionsDid a condition such as aws:MultiFactorAuthPresent or an aws:SourceIp lock constrain it?
That reading turns 'a key leaked' into an accurate, defensible scope statement for the incident report. The case study at the end puts it to work.
HACKTHESOCLesson 61Cloud auth and access keys35 / 78

Read a policy statement: effect, action, resource, condition

  • One action, read-only: no delete, no IAM changes
  • One bucket's objects: everything else is out of reach
  • Source IP condition: calls from attacker IPs fail even with the key
Every statement answers four questions. A stolen key behind this policy reads one archive, and only from the office range. Compare the wildcard version: Action star on Resource star, no condition.
HACKTHESOCLesson 61Cloud auth and access keys36 / 78

Scoping a compromised identity, in order

  1. 1Name the principalTake userIdentity.arn from the suspicious events.
  2. 2Collect every policyAttached, inline and group policies, plus any permission boundary.
  3. 3Read the AllowsWhich actions on which resources: the ceiling of possible damage.
  4. 4Apply Denies and conditionsAn explicit Deny always wins; conditions narrow when Allows apply.
  5. 5Compare with CloudTrailWhich calls succeeded, which hit AccessDenied: the actual damage.
  6. 6Write the scope statementCould do X, did do Y, blocked on Z.
Possible damage comes from the policy; actual damage comes from the log. A good incident report states both, separately.
HACKTHESOCLesson 61Cloud auth and access keys37 / 78

The policy usually decides contained vs catastrophic

Tightly scoped key

Contained

s3:GetObject on one archive bucket. A leak exposes one archive.

Wildcard key

Full account takeover

Action: on Resource: . A leak hands over every action on every resource.

The gap between these two keys, by itself, is usually what separates a contained incident from a full account takeover.
HACKTHESOCLesson 61Cloud auth and access keys38 / 78

What you seeWhat it meansScope impact

Students often count every event as damage. Splitting successes from denials is what makes the scope statement defensible.

Section 6 of 10

MFA, and the credentials it does not cover

High value for human sign-ins, with one boundary every analyst must know.

HACKTHESOCLesson 61Cloud auth and access keys40 / 78

What MFA covers, and what it does not

Protects

Interactive sign-ins with a second proof beyond the password. Not optional for AWS root and Azure Global Administrator, which can undo every other control.

Does not protect

Static keys and tokens. An AWS access key or Azure client secret authenticates with no MFA prompt, because it is a machine credential.

Policy condition aws:MultiFactorAuthPresent can require MFA for sensitive API actions, forcing a key-based caller to assume a role with MFA.

This is precisely why leaked access keys stay dangerous and why reducing long-lived keys matters even in an MFA-everywhere environment.
HACKTHESOCLesson 61Cloud auth and access keys41 / 78

MFA leaves a mark on console sign-ins, not on key calls

  • A successful console sign-in with MFAUsed: No on a privileged user is a finding
  • The key-based call has no MFA field at all: no prompt ever happened
Fictional records trimmed to the fields that matter. For role sessions, sessionContext.attributes.mfaAuthenticated carries the same fact.
HACKTHESOCLesson 61Cloud auth and access keys42 / 78

How attacks on MFA show up in identity logs

  • MFA fatiguePrompt bombing: many challenges in quick succession, mostly denied, then one approval.
  • AiTM phishingProxies the real login to steal and replay the post-MFA session token.
  • New MFA methodA new MFA-method registration is a common attacker persistence step.
  • What to push forPhishing-resistant MFA, hardware keys over SMS, on all human identities.
Also watch for token reuse from unexpected locations, the downstream trace of AiTM.

HACKTHESOCLesson 61Cloud auth and access keys44 / 78

Triaging an MFA fatigue alert

  1. 1Count the promptsHow many challenges, how many denied, over what window?
  2. 2Check the approved sign-inSource IP, device and location of the one that succeeded.
  3. 3Ask the user out of bandBy phone or chat, not by email to a possibly compromised mailbox.
  4. 4Contain if not themRevoke sessions, reset password, remove unknown MFA methods.
  5. 5Close the gapPush number matching or phishing-resistant MFA for this group.
The approval at the end of a burst is the moment of compromise; everything after it on that session belongs in scope.

Section 7 of 10

Detecting credential abuse

Baseline each identity, alert on deviation, confirm by correlation, contain decisively.

HACKTHESOCLesson 61Cloud auth and access keys46 / 78

High-value signals to hunt

Normal has a shape: source IPs, countries, active hours, API actions, regions.

  • First use from a new locationA CI-only key suddenly called from a foreign residential or hosting IP. Check source IP and User-Agent.
  • Impossible travelTwo distant sign-ins too close in time, or a new device/country combination.
  • Enumeration burstsMany list/describe calls in a short window right after access.
  • Sensitive identity actionsCreateUser, CreateAccessKey, powerful policies, new MFA methods.
  • MFA anomaliesDenied prompts then an approval, or single-factor success where MFA was required.
  • Anonymising infrastructureTor exit nodes or anonymising VPNs used for cloud authentication.
Each signal alone can be benign. The combination is what tells the story.
HACKTHESOCLesson 61Cloud auth and access keys47 / 78

Hunting an enumeration burst in CloudTrail

  • Read-only discovery calls, grouped per key and source IP
  • The threshold is a starting point: tune it to your own baseline
  • Each hit is a lead to check against that key's history
An Athena-style query over a CloudTrail table. Inventory tools and security scanners also produce bursts, so maintain an allowlist of their keys and IPs.

Revoking a stolen AKIA key is not enough if it already minted session credentials.

GetSessionToken or GetFederationToken mint ASIA credentials that stay valid until their own expiry, even after the parent key is disabled.

Hunt for these calls from a key that normally never makes them. To contain, also deactivate the IAM user and use the AWS 'revoke active sessions' flow, not just key deletion.
HACKTHESOCLesson 61Cloud auth and access keys50 / 78

Containing a stolen key that may have minted sessions

  1. 1Deactivate, do not deleteSet the key inactive: it stops working and stays as evidence.
  2. 2Find minted sessionsHunt GetSessionToken, GetFederationToken, AssumeRole by that key.
  3. 3Kill the sessionsDeny-all for tokens issued before now (aws:TokenIssueTime), or revoke sessions.
  4. 4Follow every ASIA keyPivot on each minted accessKeyId to see what it did.
  5. 5Hunt persistenceNew users, keys, roles, trust-policy edits, then delete the key.
The AWS revoke-active-sessions flow works by attaching a deny policy conditioned on token issue time, so sessions minted before the revocation stop working even though they have not expired.

  • IAM credential reportaws iam generate-credential-report: every user's key age, last-used date and MFA status in one CSV.
  • Usage dataGetAccessKeyLastUsed and Access Advisor show whether a key or permission is used; delete dormant keys.
  • AWSCompromisedKeyQuarantineV2AWS attaches it when a key is exposed publicly, e.g. via GitHub secret-scanning partner alerts.

A quarantine policy attached is itself an incident signal: AWS believes a key leaked. Do not simply detach it; investigate. The GuardDuty finding, full name UnauthorizedAccess:IAMUser/InstanceCredentialExfiltration.OutsideAWS, is the Capital One SSRF pattern.

Confirm by correlation, then respond in proportion

Confirm

A key from a new IP might be travel. The same key then enumerating IAM and creating a user is almost certainly compromise. Managed findings are leads; verify in raw logs.

Respond

Contain decisively once confirmed.

  • Revoke or deactivate the key
  • Human: reset password, revoke sessions/tokens
  • Rotate related secrets, review access
  • Hunt new users, keys, MFA methods
Managed findings are starting points, not verdicts: GuardDuty findings for anomalous IAM behaviour, and Entra ID Protection risky sign-ins and users.

How an SSRF flaw becomes stolen role credentials

Described as the chain of events a defender reconstructs.

Secrets management: vaults, not plaintext

Fetch the secret at runtime, leave a log entry

A plaintext key in a config file leaves no trail of who read it. A vault turns every retrieval into an identity-attributed, timestamped entry.
HACKTHESOCLesson 61Cloud auth and access keys66 / 78

Automatic rotation, step by step

The four steps a Secrets Manager rotation function performs.

  1. 1createSecretGenerate a new value and store it as version AWSPENDING.
  2. 2setSecretApply the new value to the resource, e.g. the database user.
  3. 3testSecretLog in with the pending value to prove it works.
  4. 4finishSecretMove AWSCURRENT to the new version; the old one becomes AWSPREVIOUS.
Apps always ask for AWSCURRENT, so they pick up the new value without a deploy. A failed rotation shows up as errors in the rotation function logs.
HACKTHESOCLesson 61Cloud auth and access keys67 / 78

Closing the loop on static secrets

Automatic rotation

Secrets Manager can invoke a Lambda on a schedule to generate a new value, update the resource (e.g. a DB password) and store it. No human copying passwords.

No key to open the vault

Grant an EC2 role or Azure managed identity access to a specific secret. The only credential is the compute resource's own auto-rotating identity.

New detection signal

GetSecretValue or Key Vault SecretGet from an identity or IP that never fetched that secret before is a strong lead.

There is no key to leak, because no key was ever issued.
