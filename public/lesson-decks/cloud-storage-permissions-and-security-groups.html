How cloud storage permissions work

S3 buckets and Azure Blob containers: cheap, limitless, internet-reachable, one setting from public.

HACKTHESOCLesson 63Storage and security groups6 / 57

Layers that control access to storage

  • Private by defaultNew buckets and containers are owner-only until someone grants more.
  • Resource policiesJSON bucket policies. Principal "*" or the AllUsers group makes the bucket public.
  • ACLsOlder per-object or per-bucket grants that can also open access, sometimes surprisingly.
  • GuardrailsAWS Block Public Access, Azure storage public-access settings: switches that prevent exposure regardless of policies.
  • Pre-signed URLs / SAS tokensTemporary, scoped access to one object: the correct way to share a single file.

Exposure = a policy or ACL grants AllUsers read and Block Public Access is off.

Then anyone on the internet, with no credential, can list and download. A scanner walking the internet finds it.
HACKTHESOCLesson 63Storage and security groups7 / 57

How a private bucket becomes public

Exposure needs two switches flipped, usually by different people at different times.

  1. 1Created privateOwner-only, with Block Public Access on by default.
  2. 2Guardrail turned offPutBucketPublicAccessBlock sets the blocking flags to false.
  3. 3Anonymous grant addedA policy with Principal: * or an ACL granting AllUsers.
  4. 4No credential neededAny internet request for an object now succeeds.
  5. 5Found by scannersPredictable names like -backup or -prod are probed constantly.
Each step is a logged API call. That is why change detection, covered in section 6, can catch exposure at step 2 or 3 instead of after step 5.

Sharing one file safely vs making a bucket public

Pre-signed URL / SAS token

The correct way to hand a file to someone outside.

  • One object (or a narrow scope)
  • Expires at a set time
  • Signed by a real credential
  • Permissions limited, e.g. read only

Public bucket or container

The same goal reached by opening the whole door.

  • Every object, including future uploads
  • No expiry at all
  • No identity behind the access
  • Often listable as well as readable
When an engineer says "I needed to share a file", the answer is a pre-signed URL or SAS token, never a public setting.
HACKTHESOCLesson 63Storage and security groups10 / 57

Reading a SAS URL before you trust it

  • sr=b one blob and sp=r read only: well scoped
  • se is the expiry: 2030 means this link works for years
  • Anyone holding the URL has the access: treat a leaked SAS like a password
Fictional URL. A SAS with a far-future expiry, or with broad permissions such as write and list, is a finding even though it is the "safe" sharing mechanism.

Turn the guardrail on and most public-bucket incidents become impossible.

Keep buckets private, keep Block Public Access on, share with pre-signed URLs or SAS tokens, and limit who can change these settings.

That is the defensive baseline for storage, in one sentence.

Security groups: the cloud firewall

AWS security groups and Azure NSGs decide who on the network may knock on a resource's door.

HACKTHESOCLesson 63Storage and security groups20 / 57

The core mechanics

  • RulesPermit traffic by protocol, port and source: e.g. TCP 443 from anywhere, TCP 22 from the office IP only.
  • AWS security groupsStateful and allow only: anything not explicitly allowed is denied.
  • Why stateful mattersThe reply to an allowed inbound flow is let back out automatically, so you write only the inbound rule, never a matching outbound one.
  • Azure NSGsAllow and deny rules, with priorities.
  • The dangerous value0.0.0.0/0: the entire internet.
  • Least exposureOnly needed ports, narrowest source, admin access behind VPN or bastion; restrict egress to limit exfiltration.
Every 0.0.0.0/0 on a sensitive port answers 'everyone' to the question of who may knock.
HACKTHESOCLesson 63Storage and security groups21 / 57

Stateful in practice: one RDP session through a security group

  1. 1Client connectsA VPN client opens TCP to port 3389 on the instance.
  2. 2Inbound rule matchesTCP 3389 from 10.20.0.0/16 allows it in.
  3. 3Flow is trackedThe security group remembers this connection.
  4. 4Reply goes outReturn packets are allowed automatically as part of that flow.
  5. 5No outbound rule neededYou write the inbound rule only; the reply is implied.
A stateless filter would need a second rule for the reply traffic. Stateful is why a single inbound rule is the whole exposure decision.

A low priority number wins over the default deny

DenyAllInBound would have kept the host safe, but the custom rule at 100 is evaluated first and punches a hole for RDP from the entire internet. Remove or scope it and the default deny takes over.

An NSG can sit on the subnet and on the NIC

Evaluated first inbound

Subnet NSG

Applies to every resource in the subnet.

Evaluated second inbound

NIC NSG

Applies to one network interface.

The analyst check

Both must allow

Inbound traffic reaches the VM only if both NSGs allow it. Read both before calling a port open.

A scary allow on the NIC may be blocked by the subnet NSG, and the reverse. Effective security rules in the portal show the combined result.

Identity policies vs resource policies

Two independent paths to the same door. Check both.

HACKTHESOCLesson 63Storage and security groups30 / 57

Two questions, two places

On a user or role

Identity-based

What is this principal allowed to do, anywhere it has access? A role allowed s3:GetObject on a bucket can read it.

On the resource itself

Resource-based

Who may reach this resource, from any account? A bucket policy with "Principal": "*" grants access independent of any IAM policy.

'The IAM policies look fine' never closes an exposure investigation on its own.

Other resource-based policies to check: KMS key policies, Lambda resource policies, and role trust policies.
HACKTHESOCLesson 63Storage and security groups31 / 57

Cross-account access needs both keys to turn

  1. 1Role in Account B asksIt calls s3:GetObject on a bucket in Account A.
  2. 2B checks its own sideDoes the role's identity policy allow that action on that bucket?
  3. 3A checks its sideDoes the bucket policy name Account B's role as a principal?
  4. 4Both yes: allowedEither one missing and the request is denied.
  5. 5Wildcard breaks itPrincipal: * makes A's side say yes to everyone.
This two-key design is a safety property. A wildcard principal removes the key on the resource side entirely.
HACKTHESOCLesson 63Storage and security groups32 / 57

A deliberate cross-account grant

  • The principal is in another account: 444455556666
  • That account must also allow the role in its own identity policy
  • Unknown account IDs in bucket policies deserve a question
During an exposure review, list every external account ID in resource policies and confirm each one is a known partner.

How AWS actually decides

StepPolicy typeRule
Start(default)Everything is implicitly denied
1Explicit Deny (any policy)Denied, full stop: overrides all allows
2Service Control Policies (SCPs)Must allow, but only for IAM users and roles inside the org
3Resource-based policy (e.g. bucket policy)An allow here can grant access
4Identity-based policy (user/role)An allow here can grant access
5Permission boundaries / session policiesMust also allow if present
Same account: an allow in either the resource or identity policy is enough. Cross-account: both must allow. Principal * satisfies the resource side for anyone, throwing away that two-key safety.
HACKTHESOCLesson 63Storage and security groups34 / 57
An SCP cannot stop an outsider from using a bucket that is already public.

SCPs restrict only principals inside your organization. Close the outside path with Block Public Access, a Deny in the bucket policy itself, or a Resource Control Policy (RCP).

An SCP can stop your own people from creating exposure, for example by denying s3:PutBucketPolicy, but an anonymous caller is never in its scope.

Beyond buckets and ports

The same open-setting mistake recurs on snapshots, databases, registries and queues.

HACKTHESOCLesson 63Storage and security groups37 / 57

Other places the door gets left open

Public snapshots

RDS and EBS snapshots marked public: a full database or disk downloadable by anyone. Azure managed disks via over-broad SAS.

Publicly accessible DBs

RDS and Azure SQL have their own flag. Behind a scoped security group, the DB is still reachable if it was given a public endpoint.

Registries and queues

Public ECR or Azure Container Registry leaks images and baked-in secrets. Loose SQS/SNS policies let outsiders read or inject.

A single public RDS snapshot can hand over an entire database at once, often more data than any single bucket, from one forgotten checkbox.

Publicly accessible and the security group are separate controls

Publicly accessible flag

Decides whether the database gets a public endpoint at all. If false, nothing on the internet can reach it.

Security group

Decides which sources may connect to that endpoint. A wide rule plus a public endpoint is full exposure.

Check both: a tight security group today can be widened tomorrow if the endpoint is already public.

Defence in depth: keep the flag false for anything that does not serve the internet, so a later security group mistake is not enough.

What is already open

Posture

Public buckets, Block Public Access off, sensitive ports from 0.0.0.0/0. AWS Config, Trusted Advisor, Security Hub, Macie; Azure Defender for Cloud secure score.

Section 7 of 7

Breach patterns and prevention at scale

No exploit, no malware, no stolen credential. Only a mistake, at cloud scale.

HACKTHESOCLesson 63Storage and security groups49 / 57

Found in minutes, made by accident

Discovery is fast

Continuous internet-wide scanners probe open ports and predictable bucket names (-backup, -prod). Minutes to hours, not days.

Why it recurs

Exposure is rarely a deliberate decision.

  • A default never changed
  • A test rule opened and forgotten
  • A template copied with a wildcard
A weekly review cannot keep up with that discovery speed, which is why change detection exists.
HACKTHESOCLesson 63Storage and security groups50 / 57

How a forgotten test rule becomes an incident

An illustrative timeline of the most common exposure story.

  1. 1A quick testAn engineer opens SSH from 0.0.0.0/0 "just for an hour".
  2. 2Scanners arriveLogin attempts from many IPs begin within minutes.
  3. 3Rule is forgottenThe test ends; the rule stays.
  4. 4A weak password winsOne attempt succeeds days later.
  5. 5Found by posture scanThe open rule is noticed only after the compromise.
A change alert at step 1 would have ended the story. That is the argument for change detection over periodic review.
HACKTHESOCLesson 63Storage and security groups51 / 57

Prevention has to be structural

  • Infrastructure as CodeTerraform or CloudFormation make exposure reviewable; policy-as-code scanners block 0.0.0.0/0 or Principal: * in a pull request.
  • Account-wide guardrailsAWS SCPs and Azure Policy hard-block the API call that creates exposure, e.g. PutBucketPolicy, by org principals.
  • Default-secure servicesS3 Block Public Access is now on by default for new buckets: exposure needs a deliberate, auditable action.

SCPs do not stop outsiders reading an already-public bucket: Block Public Access and RCPs cover that. Guardrails never replace the SOC.

Templates get exceptions, legacy resources predate the guardrails, and attackers probe for the gaps. The analyst's job: know what safe looks like, watch change events and posture findings, close the door fast.
HACKTHESOCLesson 63Storage and security groups52 / 57

A guardrail that blocks the exposure call itself

  • An SCP statement: no one in the org may change Block Public Access
  • Except the platform admin role, through a reviewed process
  • Blocked attempts appear in CloudTrail as AccessDenied: worth reviewing
This stops insiders creating exposure. It does not stop outsiders reading a bucket already public, which is why the guardrail itself must be on.

Key takeaways

  1. 01Storage is private by default; a policy or ACL granting AllUsers plus Block Public Access off makes it public.
  2. 02Security groups and NSGs are the cloud firewall; a sensitive port from 0.0.0.0/0 is the finding.
  3. 03Identity-based and resource-based policies are separate paths; a bucket policy can expose data when IAM looks fine.
  4. 04Explicit Deny wins only where a policy applies: SCPs bind in-org principals, not anonymous callers. NSGs: lowest number first.
  5. 05Exposure reaches snapshots, public databases, registries and queues; ask who can reach it and should they.
  6. 06Detect with posture tools and change events, close fast, and prevent with IaC scanning and SCP/Azure Policy guardrails.
