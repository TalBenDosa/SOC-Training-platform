Section 1 of 10

What living off the land means

Attackers increasingly use the tools already on the victim's machine, tools Windows itself relies on.

HACKTHESOCLesson 44LOLBins6 / 37

Four terms first

  • Binary / executableA program file the OS can run directly, an .exe or .dll. Windows ships hundreds for admin tasks.
  • Digitally signedMicrosoft cryptographically signs its executables. Security tools trust signed Microsoft code far more than unknown files.
  • Allowlist / blocklistPermit only specific files, or forbid specific files. Both check identity: name, hash or publisher.
  • FilelessAvoids writing a new malicious file to disk, so file-scanning antivirus has nothing to scan.
Each term sets up one reason LOLBins work: signed beats reputation, already present beats file scanning.
HACKTHESOCLesson 44LOLBins7 / 37
A LOLBin is a legitimate, Microsoft-signed, already-installed program repurposed to do something malicious.

Download a payload, run code, or hide from application control. MITRE tracks it mainly as T1218, System Binary Proxy Execution.

The defence has to shift from block the file to watch how it is used. That shift is the spine of the lesson.

Section 2 of 10

What LOLBins are and why they work

Signed, present, essential, and hidden among normal admin activity.

HACKTHESOCLesson 44LOLBins9 / 37

Four reasons LOLBins succeed

Signed and trusted

Valid Microsoft signatures wave them past controls that trust signed code or block unknown executables.

Already present

Nothing new on disk, so file reputation and first-seen detections have nothing to flag.

Blocklists fail

You cannot block rundll32.exe: Windows and countless apps depend on it. Essential and dangerous at once.

Blends in

Administrators use the same tools daily, so malicious use hides in a sea of legitimate use.

The LOLBAS project catalogues these binaries, their abusable functions, and example command lines.

The key mental shift: you cannot detect on the presence of the binary, only on how it is used: arguments, parent process, and following behaviour.

The T1218 proxy-execution catalogue

Using a trusted signed binary as a proxy to run attacker code. Fourteen sub-techniques.

HACKTHESOCLesson 44LOLBins14 / 37

T1218.001hh.exeRun a .chm help file that embeds script

HACKTHESOCLesson 44LOLBins15 / 37
Several of these are just formal IDs for tricks shown by name earlier.

Squiblydoo is T1218.010, mshta abuse is T1218.005, InstallUtil abuse is T1218.004. A sibling, T1216, covers signed scripts.

Knowing the full set means that when a signed executable behaves oddly, you can name the exact technique and pull the matching detection.

The LOLBAS taxonomy: three types

Abuse is not limited to .exe files; a mature strategy watches all three types.

HACKTHESOCLesson 44LOLBins17 / 37

Three types of living-off-the-land file

TypeWhat it isExample
LOLBinA signed executable (.exe)certutil.exe, mshta.exe, rundll32.exe
LOLScriptA signed Microsoft scriptSyncAppvPublishingServer.vbs, pubprn.vbs
LOLLibA signed library (.dll)comsvcs.dll (MiniDump), scrobj.dll
The LOLLib row is easy to overlook: comsvcs.dll's MiniDump export, invoked through rundll32, dumps process memory, the living-off-the-land way to read lsass without bringing a tool.

Section 6 of 10

Signed script proxy execution

Trusted scripting interpreters and signed scripts: T1216, with T1220 for the XSL variant.

HACKTHESOCLesson 44LOLBins20 / 37

WSH abusing a signed Microsoft script

  • A signed System32 script proxies PowerShell execution
  • The process tree shows only the trusted wscript.exe
wscript.exe and cscript.exe are the Windows Script Host for .vbs and .js. This sidesteps detections and execution-policy that watch powershell.exe directly.
HACKTHESOCLesson 44LOLBins21 / 37

WMIC and the Squiblytwo technique (T1220)

  • /FORMAT fetches a remote XSL and runs embedded JScript
  • The URL argument is the tell; the query looks unremarkable
msxsl.exe is another XSL processor; it is not installed by default, so its mere presence is a strong indicator. Also watch wscript/cscript spawned by Office or a browser.

Section 7 of 10

LOLDrivers and Bring Your Own Vulnerable Driver

The same borrow-something-trusted logic, pushed into the Windows kernel.

HACKTHESOCLesson 44LOLBins23 / 37
BYOVD brings a legitimately signed but vulnerable third-party driver, then exploits its flaw for kernel code.

Driver Signature Enforcement blocks unsigned drivers, but a genuine signature passes it. The vulnerability, not the signature, is the attack surface.

Maps to T1068 (Exploitation for Privilege Escalation), paired with T1685 (Disable or Modify Tools, formerly T1562.001) once kernel code can terminate EDR. LOLDrivers.io catalogues these drivers and hashes.
HACKTHESOCLesson 44LOLBins24 / 37

Event ID 6: a vendor-signed driver from an odd path

  • A vendor-signed driver loading from C:\Windows\Temp is the red flag
  • Legitimate driver installs almost never stage from a temp directory
Abused drivers include RTCore64.sys, gdrv.sys and mhyprot2.sys. The attacker then sends IOCTLs to trigger arbitrary kernel read/write and disable security processes.
HACKTHESOCLesson 44LOLBins25 / 37
Microsoft's vulnerable driver blocklist is the single most effective control against BYOVD.

Enabled by default with HVCI/Memory Integrity, it stops known-vulnerable drivers loading regardless of a valid signature.

Match loaded driver hashes against LOLDrivers and the Microsoft blocklist. Keeping it enabled and current closes the gap Driver Signature Enforcement alone leaves open.

Section 8 of 10

How LOLBin abuse appears in telemetry

Both data sources hinge on capturing command-line arguments.

HACKTHESOCLesson 44LOLBins27 / 37

Event ID 1: a phishing-to-execution chain

  • A Word document launched mshta, which launched certutil to download
  • Entirely built from signed Microsoft binaries
Event ID 1's valuable fields are Image, CommandLine, ParentImage, ParentCommandLine and User. Correlate with Event ID 3 showing certutil then reaching 198.51.100.20:80, abnormal for a certificate tool.
HACKTHESOCLesson 44LOLBins28 / 37
Windows Event ID 4688 carries the same CommandLine only if a Group Policy is enabled.

Without the include command line in process creation events setting, 4688 shows the process name with the arguments blank, useless for LOLBin detection.

Sysmon captures command lines with no extra policy, which is why most SOCs deploy it even alongside native auditing.

Section 9 of 10

Detecting LOLBin abuse

You cannot block these binaries, so detection focuses on anomalous usage.

HACKTHESOCLesson 44LOLBins30 / 37

High-value detection signals

  • Unusual argumentscertutil -urlcache or -decode; regsvr32 /i:http; mshta or rundll32 with a URL or javascript: protocol.
  • Unexpected parent-childOffice apps spawning mshta, rundll32, wscript, powershell or certutil: a textbook phishing chain.
  • LOLBins on the networkcertutil, bitsadmin, mshta or regsvr32 connecting to an external IP. msbuild outbound is almost never legitimate.
  • Odd locationsExecution from temp or user directories, or with obfuscated/encoded arguments.

Build detections from the LOLBAS command-line examples, then tune out your legitimate admin baseline.

Correlation beats single events: outlook to mshta to a certutil download to a new external connection tells a clear story though each binary is trusted.

Section 10 of 10

Defending against living off the land

Since removal is not an option, combine application control, telemetry and least privilege.

HACKTHESOCLesson 44LOLBins32 / 37

Three defensive levers

Application control

WDAC and AppLocker restrict how these binaries run. Microsoft publishes recommended block rules. ASR rules block Office from creating child processes.

Telemetry

Command-line logging everywhere (Sysmon EID 1 / 4688 with the GPO). Alert on parent-child and network anomalies.

Least privilege

Remove local admin where possible; many techniques are far more damaging with elevation. Constrain legacy script hosts and internet macros.

Threat hunting: sweep for certutil -urlcache, Squiblydoo and mshta http across the fleet, then triage with context.

The goal is not to eliminate the binaries but to make their malicious use noisy and visible.
HACKTHESOCLesson 44LOLBins33 / 37

Key takeaways

  1. 01LOLBins are signed, built-in Windows binaries abused for proxy execution and downloads (T1218 and relatives).
  2. 02Because they are trusted and essential you cannot blocklist them: detect on how they are used.
  3. 03Sysmon Event ID 1 (Image/CommandLine/Parent) and Event ID 3 (network) are the core telemetry.
  4. 04Windows Event 4688 captures command lines only when the include-command-line Group Policy is enabled.
  5. 05BYOVD brings a signed but vulnerable driver for kernel code; the Microsoft driver blocklist is the key control.
  6. 06Defend with WDAC/AppLocker recommended block rules, ASR rules, command-line logging and least privilege.

Check your understanding, question 1 of 3

You see outlook.exe spawn mshta.exe, which launches certutil.exe with a -urlcache argument pointed at an external URL. Why is blocking certutil.exe by name a poor primary defence?

Certutil is signed and Windows relies on it, so you detect abusive usage (a -urlcache download from an odd parent chain) instead of blocking it. It runs fine as a standard user. The rename point is true but not the real reason: Windows depends on certutil.

Check your understanding, question 2 of 3

Sysmon Event ID 1 shows wmic.exe invoked with a /FORMAT argument pointing at a remote .xsl file on an external host, from an unusual parent process. What is happening, and which technique is this?

WMIC's /FORMAT switch fetches and applies a remote XSL stylesheet, and adversaries embed script inside it: Squiblytwo, tracked as T1220. Squiblydoo uses regsvr32 and a .sct scriptlet, and SyncAppvPublishingServer.vbs is a different signed-script proxy (T1216).

Check your understanding, question 3 of 3

Event ID 6 shows a genuinely vendor-signed kernel driver (RTCore64.sys) loading from C:\Windows\Temp rather than System32\drivers, immediately followed by security processes terminating. What best explains this?

A signed but known-vulnerable driver loading from an odd path, then security tools dying, is BYOVD (T1068) paired with Disable or Modify Tools (T1685). The genuine signature passes Driver Signature Enforcement; the flaw grants kernel code.
