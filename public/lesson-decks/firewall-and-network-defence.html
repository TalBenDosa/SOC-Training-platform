An allow verdict does not mean the traffic was safe. It means it matched a rule that permits it.

A rule written to let a vendor agent out on 443 will just as happily allow an attacker's C2 beacon on the same port.

The firewall is not judging intent; it enforces policy, and policy is only as good as the humans who wrote it. Permitted versus benign is the mental shift this lesson builds toward.

What a firewall actually decides

A checkpoint enforcing a rule set across a boundary.

HACKTHESOCLesson 17Firewalls and network defence6 / 75

Vocabulary the rest of the lesson leans on

  • ZoneA logical grouping of interfaces: internal (trust), external (untrust), DMZ. Rules say allow 443 from internal to external.
  • Ingress / egressIngress is traffic entering from outside; egress is traffic leaving toward outside.
  • Five-tupleSource IP, source port, destination IP, destination port, protocol: the session table key.
A rule rarely just says allow port 443. It almost always includes the zones.
HACKTHESOCLesson 17Firewalls and network defence7 / 75

Stateless filter vs stateful firewall

Stateless packet filter

Checks every packet in isolation, no memory. Needs an explicit rule for return traffic. Logs tend to be per-packet: huge volume.

Stateful firewall

Checks the first packet against rules, then keeps a session table. Return traffic is auto-permitted. Logs per session.

Session-level logging, with aggregated byte and packet counts, is what makes byte-shape analysis possible.

With a stateless filter, a return rule that is slightly wrong breaks traffic; too permissive and you open a hole from the other direction.
HACKTHESOCLesson 17Firewalls and network defence8 / 75

One HTTPS connection through a stateful firewall

  1. 1First packet arrives10.20.4.117:51422 to 198.51.100.90:443, TCP. Checked against the rule base top to bottom.
  2. 2A rule matchesA session entry is created, keyed on the five-tuple.
  3. 3Later packets skip the rulesThey are matched against the session table instead.
  4. 4Replies are let back inReturn traffic belongs to an approved session, so no reply rule is needed.
  5. 5One log at the endA single session record with duration and bytes in each direction.
This is why one outbound allow rule is enough for browsing, and why you read one line per conversation instead of thousands of packets.
HACKTHESOCLesson 17Firewalls and network defence9 / 75

First match wins, implicit deny catches the rest

  • Rule order is not cosmetic: a broad rule shadows a narrower one
  • Implicit deny: anything without an explicit rule is dropped
  • Allow certifies rule-compliance, never safety
Default deny means safety depends on every legitimate flow having an explicit rule. Forgotten flows are blocked; over-permissive ones are allowed.
HACKTHESOCLesson 17Firewalls and network defence10 / 75

Two sessions a port-based firewall cannot tell apart

A browser loading a page

TCP to port 443, external destination, matched allow-outbound-https-generic. Logged as allow.

A C2 beacon

TCP to port 443 on a compromised web server, matched allow-outbound-https-generic. Logged as allow.

Same port, same protocol, same rule, same verdict. Only the metadata around the session can separate them.

The firewall evaluated port, protocol and address, not content or intent. The rest of the lesson is about the signals that remain.

Beyond the port: NGFW, IDS and IPS

Closing the gap a port-based decision leaves open.

HACKTHESOCLesson 17Firewalls and network defence12 / 75
App-ID identifies the real application, regardless of the port it runs on.

A next-generation firewall can say block BitTorrent or allow Salesforce but block generic file-sharing, which a classic firewall cannot express.

The term was popularized by Palo Alto Networks; the concept is now standard. NGFWs also bundle IPS, URL filtering and often TLS inspection.
HACKTHESOCLesson 17Firewalls and network defence13 / 75

Rules a classic firewall cannot write, and an NGFW can

IntentPort-based firewallNGFW with App-ID
Block BitTorrentCannot: it can run on any portIdentifies it by content, on any port
Allow Salesforce, block generic file-sharing SaaSBoth are HTTPS on 443Separate applications, separate rules
Spot a remote-access tool on 443Looks like ordinary web browsingClassified as the real application
App-ID inspects traffic content and signatures rather than trusting the port. That is the gap between 'port 443' and 'what is actually on port 443'.
HACKTHESOCLesson 17Firewalls and network defence14 / 75

IDS watches, IPS blocks

Passive, out of band

IDS

Inspects a mirrored copy (SPAN port or tap) against signatures and alerts. Cannot block anything.

Inline

IPS

Same detection, but in the path: drops, resets or blocks the instant a signature matches. Often built into the NGFW.

First field to check on an NGFW threat event: action alert or block (drop, reset). An alert-only hit on a high-confidence exploit means the traffic got through.
HACKTHESOCLesson 17Firewalls and network defence15 / 75

Why teams tune before they block

An IDS false positive is dismissed in seconds. An IPS false positive silently drops a payment callback.

  1. 1Deploy in alert-only modeRun the new signature against real production traffic.
  2. 2Observe false positivesOver a defined period.
  3. 3Promote to blockingOnly once confidence is established.
Signature tuning is one of the more overlooked but genuinely important jobs a SOC does over time.
HACKTHESOCLesson 17Firewalls and network defence16 / 75

Where each sits: inline vs out-of-band

Inline path

Internet to firewall or NGFW to IPS to internal network. Every packet crosses the IPS, so it can block automatically.

Mirrored copy

The firewall sends a copy to an out-of-band IDS. It alerts on the same signature but never touches the packet.

The inline position is exactly why a false-positive signature costs so much more on an IPS.
HACKTHESOCLesson 17Firewalls and network defence17 / 75

On an NGFW threat event, read the action first

ActionWhat it meansYour response
alertDetected but not stopped: the traffic reached its destinationUrgent on a high-confidence exploit signature: investigate the target
block, drop or resetStopped in flightLower immediate urgency; check for retries and other attempts from that source
Vendors word it differently, but the question is always the same: did it get through? That single field changes the whole response.

HACKTHESOCLesson 17Firewalls and network defence21 / 75

Deny and drop are different

Deny

Matched a reject rule and may answer with a TCP reset or ICMP unreachable, so the sender knows it was refused.

Drop

Silently discarded, no response. Offers a scanner no confirmation anything exists at that address.

A burst of drops from one source across many destination ports is consistent with a port scan.

That pattern is worth pivoting on before you look at any single connection.
HACKTHESOCLesson 17Firewalls and network defence22 / 75

Two byte shapes: beaconing and exfiltration

  • ~4 hours, tiny steady bytes: the long-polling beacon shape
  • 41 seconds, 812 MB out, 1.9 KB back: data pushed out
  • Ask: does 10.20.4.117 actually run the vendor agent?
Beaconing most often looks like many short sessions to one destination at a near-fixed interval with near-identical bytes; some C2 instead long-polls, as here. Neither shape is proof alone: backups and heartbeats look similar.
HACKTHESOCLesson 17Firewalls and network defence23 / 75

Traffic matching a rule named for a vendor integration, from a host with no relationship to that vendor, is an immediate anomaly.

Permitted, but permitted for a purpose that does not match who is actually using it.

Traffic logs are only one log type

PAN-OS

TRAFFIC (start, end, drop, deny) and THREAT, whose subtype names the engine: url, spyware, vulnerability, virus, wildfire. In THREAT, category is the URL category and threatid is "Name(ID)".

FortiGate

type="traffic" subtype="forward" for sessions; type="utm" with subtype webfilter, ips or virus for the security engines.

Check Point

product names the blade that wrote the log: VPN-1 & FireWall-1, URL Filtering, Anti-Bot, SmartDefense (IPS).

Join threat to traffic on the session ID within a short window. Session IDs are recycled, so never join on the ID alone across days.

Every PAN-OS URL log carries (9999) in threatid. Students often read category as the threat type; it is the URL category.
HACKTHESOCLesson 17Firewalls and network defence28 / 75

Joining a threat log to its traffic log

  1. 1Take the session IDFrom the THREAT (PAN-OS), UTM (FortiGate) or blade log.
  2. 2Search traffic logs for itSame session ID, within a short time window.
  3. 3Read the traffic sideBytes each way, duration, end reason: did anything move?
  4. 4Never join across daysSession IDs are recycled, so an old match is a different connection.
  5. 5Watch for HA failoverA long session can reappear with a fresh ID on the new active firewall.
The threat log says what the engine saw. The traffic log says what actually crossed. You need both to describe the event.
HACKTHESOCLesson 17Firewalls and network defence29 / 75

PAN-OS writes session_end_reason on every TRAFFIC end log.

One trap: after a high-availability failover, a long-lived session can reappear on the newly active firewall with a fresh session ID. If it lines up with a failover in the system log, it is the same connection.

Five questions for every session line

  • Is the rule scoped?A rule named for a purpose can be checked against the host. A generic rule gives no reassurance.
  • How long did it last?About an hour each, here: long-lived.
  • Bytes each way, across sessions?4180 / 3920 and 4176 / 3901: small and near-identical.
  • Is the destination known?91.203.44.19 has no established relationship to this host.
  • Any failed attempt nearby?A dropped outbound 3389 in the same window: another channel tried.
Run the five questions on each line, then on the set. The finding lives in the pattern across lines.
HACKTHESOCLesson 17Firewalls and network defence35 / 75

What the three lines add up to

Sessions 1 and 2

Same destination, about an hour apart, long and small, near-identical bytes: the beaconing shape. A generic rule name gives no reassurance about purpose.

Session 3

Outbound RDP to a different unknown IP, silently dropped. Nothing left, but in this window it reads like trying another channel.

Next: pull 24 hours of session history, check endpoint telemetry, look for 91.203.44.19 elsewhere.

The honest conclusion is not contain now. It is that the pattern across sessions justifies deeper pivoting. Read the shape across lines, never one line alone.
HACKTHESOCLesson 17Firewalls and network defence36 / 75

The next pivots, in order

  1. 1Pull 24 hours of historyEvery session from 10.20.7.44: how regular is the cadence?
  2. 2Check the destinationThreat intelligence on 91.203.44.19 and 198.51.100.7.
  3. 3Look for the same cadence elsewhereDoes any other host talk to 91.203.44.19 on the same rhythm?
  4. 4Ask the endpointEDR telemetry: which process holds that connection?
  5. 5Then decide on containmentWith evidence from more than one source.
This is a repeatable sequence: firewall shape first, then intel, then scope, then endpoint confirmation.

What to look for in VPN logs

  • SprayMany failures from one public_ip or remip across many usernames, then the first success from that address.
  • Stolen credentialsA success from a new country, or a machinename, hostid or serial that is not the user's laptop, such as DESKTOP-XXXXXXX.
  • Concurrent sessionsThe same user connected from two public IPs at once, with no logout in between.
  • Pivot inwardThe tunnel address becomes the user's source in every internal log: bound it by connect and logout times.
Search internal firewall, EDR and Windows logon events for the private_ip or tunnelip inside that window.

Egress filtering: the control most skip

Traffic leaving deserves as much scrutiny as traffic arriving.

HACKTHESOCLesson 17Firewalls and network defence45 / 75
Restricting outbound traffic is loud. Permissive outbound rules are silent.

A blocked SaaS integration raises a ticket in minutes; traffic that was allowed to leave raises nothing. So egress drifts toward allow almost everything.

DNS and HTTPS are almost always open outbound, which is exactly why most modern C2 rides HTTPS and DNS tunneling remains a durable exfiltration technique.
HACKTHESOCLesson 17Firewalls and network defence46 / 75

Why egress policy drifts toward allow everything

  1. 1Users need a lot outboundWeb, cloud services, DNS, updates, dozens of SaaS integrations.
  2. 2Allow-lists are hard workEvery legitimate destination must be known and maintained.
  3. 3A wrong block is loudA broken integration raises a help-desk ticket within minutes.
  4. 4A wrong allow is silentNobody complains about traffic that was allowed to leave.
  5. 5Over timeRules loosen until almost everything outbound is allowed.
Ingress gets years of careful review; egress rarely does. That asymmetry is what most C2 and exfiltration rely on.
HACKTHESOCLesson 17Firewalls and network defence47 / 75

Egress done well, and what to hunt

Good egress posture

Apply inbound rule discipline to outbound traffic.

  • Allow-list destinations, default deny
  • DNS forced through your own resolver
  • TLS inspection or SNI/cert logging
  • Servers barred from direct internet

What analysts hunt

Find the anomaly inside a sea of permitted traffic.

  • Server-class host initiating outbound
  • Newly registered domain, mismatched cert
  • DNS volume or length off baseline
  • No business relationship to destination
Barring servers from the internet alone removes a lot of attack surface cheaply, because their legitimate outbound needs are narrow.
HACKTHESOCLesson 17Firewalls and network defence48 / 75

The two protocols that are almost never blocked outbound

ProtocolWhy it stays openHow attackers use itWhat still shows
HTTPS 443The web and nearly every SaaS product need itMost modern C2 frameworks talk only over HTTPSSNI, certificate, byte shape, process
DNSNothing on the internet resolves without itDNS tunnelling: data in subdomain labelsQuery volume and length vs baseline
Neither protocol is suspicious in itself. The enormous legitimate volume of both is exactly what gives attacker traffic somewhere to hide.

Segmentation, NAT, and why the source IP lies

The logged source is sometimes the gateway, not the culprit.

HACKTHESOCLesson 17Firewalls and network defence50 / 75
What could this compromised host reach? Read the segment boundaries and their rules.

VLANs plus firewall policy turn a flat network into choke points that block lateral movement and log every attempt.

Workstations, servers, database tier, guest Wi-Fi and OT/IoT in separate zones. The real answer is the rules, not a diagram someone drew once.
HACKTHESOCLesson 17Firewalls and network defence51 / 75

Each segment boundary is a choke point and a log

VLANs (Virtual Local Area Networks) split the network at the switching layer; firewall policy enforces what crosses. Guest Wi-Fi and OT/IoT belong in their own zones too.
HACKTHESOCLesson 17Firewalls and network defence52 / 75

NAT vs PAT: what the far side sees

Network Address Translation

NAT

Rewrites the source (or destination) IP as traffic crosses a boundary, so private addresses can share a few public ones.

Port Address Translation

PAT

Also rewrites the source port, so many devices share one public IP at once, told apart only by the assigned port.

A destination-side log shows only 203.0.113.9 and a port: any of a hundred workstations could be behind it.

Same trap as X-Forwarded-For in web logs: the proxy or gateway appears as the source unless you look for the translation record.
HACKTHESOCLesson 17Firewalls and network defence53 / 75

Resolving the real source behind NAT/PAT

100 workstations share 203.0.113.9; the destination sees only that IP and an assigned port.

  1. 1Treat the source as provisionalIs there a NAT or proxy boundary between this log and the device?
  2. 2Pull the NAT translationPublic IP:port plus timestamp: 203.0.113.9:41220 is 10.20.4.117:51422.
  3. 3Map the internal IP to a hostDHCP lease log, EDR or asset inventory at the same timestamp.
  4. 4If translation records expiredDHCP alone cannot help. Use proxy, internal flow or EDR network telemetry for that destination and time.
DHCP answers only the second hop: which machine held an internal address. Same trap as X-Forwarded-For in web logs: the proxy's IP shows as source unless you look at the forwarded field.

Section 9 of 12

The firewall family tree, briefly

Why some devices log differently.

HACKTHESOCLesson 17Firewalls and network defence55 / 75

Read each log for what its architecture can see

Stateless

Packet filter

Checks each packet header against a static list, with no memory of the session.

SOCKS

Circuit-level gateway

Validates only that the session was set up correctly, then relays without inspecting. Its logs say a session was allowed and little about what crossed it.

Two legs

Application proxy

Terminates the client connection and opens a separate one to the server. Logs describe client to proxy and proxy to server, not one session.

Modern secure web gateways and forward proxies still log the two-leg way.

The stateful firewall this lesson treats as the baseline was the second of three 1990s architectures. Do not misread a proxy's two legs as two unrelated connections.
HACKTHESOCLesson 17Firewalls and network defence56 / 75

One web request, as each architecture logs it

ArchitectureWhat its log records
Packet filterIndividual packets allowed or denied by header, no session
Stateful firewallOne session: five-tuple, duration, bytes each way
Circuit-level gateway (SOCKS)A session was set up and relayed; little about what crossed
Application proxyTwo legs, client to proxy and proxy to server, with content detail
Secure web gateways and forward proxies log the two-leg way today. Correlate the legs by time and client, not as two separate events.

Matching the tool to the layer, and recognizing each log format.

NGFW, WAF and UTM do different jobs

The network

NGFW

Controls what talks to what across the whole network, application-aware, at the perimeter.

One application

WAF

A reverse proxy in front of one web app, parsing HTTP to catch SQL injection, cross-site scripting and path traversal.

One box

UTM

Firewall, IPS, antivirus, URL filtering and often VPN bundled for smaller sites. The line with NGFW has blurred.

None substitutes for another. An attack on a web app can pass an NGFW cleanly on 443 and only show up in the WAF log.

Perimeter architecture: DMZ and bastion hosts

Internet-facing services never share a segment with sensitive systems.

HACKTHESOCLesson 17Firewalls and network defence64 / 75

What lives in a DMZ, and why it is separate

What goes there

Anything that must be reachable from the internet: a public web server, a mail relay, a DNS server, a VPN termination point.

Why it is separate

Containment. Compromising a DMZ service gives a foothold on that isolated segment only, behind rules that keep DMZ-to-internal traffic narrow.

DMZ means demilitarized zone; the same idea is called a screened subnet.
HACKTHESOCLesson 17Firewalls and network defence65 / 75

A bastion host is assumed to be probed and possibly compromised, so it runs one service, disables everything else, patches aggressively, and holds nothing of real internal value.

Hardening a bastion host: assume it will be attacked

  • One service onlyIt runs the single application it exists to expose, nothing else.
  • Everything else offUnused ports and services disabled.
  • Aggressive patchingIt faces the internet, so it is patched first.
  • Nothing of value insideNo credentials or data of real internal value, so a full compromise yields little.
Bastion comes from fortification: the exposed strongpoint expected to take the assault so the rest does not have to.

Key takeaways

  1. 01Stateful firewalls track sessions and auto-permit return traffic; first match wins and implicit deny catches the rest.
  2. 02Allow certifies rule-compliance, not safety; IDS alerts out of band, IPS blocks inline after tuning.
  3. 03Regular small sessions to one destination suggest beaconing; short sessions with huge outbound bytes suggest exfiltration.
  4. 04Learn the vendor field mapping once, join threat to traffic logs on session ID, and read the session end reason.
  5. 05VPN logs expose spray and stolen-credential logins; egress is usually wide open on DNS and HTTPS.
  6. 06Behind NAT/PAT, resolve the translation first, then DHCP; if expired, use proxy, flow or EDR telemetry.
