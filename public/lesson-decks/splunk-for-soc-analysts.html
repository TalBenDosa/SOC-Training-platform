Time ranges and search modes

Two controls decide how much work a search does before you write a single pipe.

HACKTHESOCLesson 89Splunk for SOC analysts14 / 81

Relative time snaps backwards, never forwards

Sign, number, unit (s, m, h, d, w, mon, q, y); @ snaps down. Run at 14:35 on Wed 7 Oct:

ModifierWindow
earliest=-15m latest=now14:20 to 14:35
earliest=-24h@h14:00 yesterday to now (24 hours back, snapped down to the hour)
earliest=-24h@h latest=@h14:00 yesterday to 14:00 today, only complete hours
earliest=-1d@d latest=@dAll of yesterday, midnight to midnight
earliest=@dMidnight today to now
earliest=-7d@d latest=@dThe last seven complete days
earliest=-mon@mon latest=@monThe whole previous month

-2d is exactly 48 hours back; -2d@d is midnight two days ago.

The picker is a convenience; earliest and latest typed in the search override it. The picker follows your profile's time zone, so confirm it before quoting a time to a colleague.

All time is the most expensive click in Splunk: it makes every bucket a candidate.

Lead with index, sourcetype and an explicit window. Widen only when the evidence tells you to, never by default.

Reinforce the scoping order early; the Job Inspector section later shows the cost of ignoring it in hard numbers.

HACKTHESOCLesson 89Splunk for SOC analysts17 / 81

_time versus _indextime: when it happened vs when stored

_time

When the event actually occurred, parsed from the log. What the time picker and earliest/latest match on.

_indextime

When Splunk received and stored it. lag = _indextime - _time measures how late a source arrives.

A delayed source can make a tight scheduled search miss events that arrived after its window closed.

Bound by index time with _index_earliest / _index_latest when a source lags. The lag query on the next slide turns this into a number per host.
HACKTHESOCLesson 89Splunk for SOC analysts18 / 81

Type the window explicitly, and measure the lag

_time is when the event happened; _indextime is when Splunk stored it. A delayed source can make a scheduled search miss events; _index_earliest and _index_latest bound by index time. The habit: for an alert at 09:14, search 09:00 to 09:30 and widen only if evidence demands it.

Fields, indexes, and the Job Inspector

How Splunk stores what you search, and how to see why a search is slow.

HACKTHESOCLesson 89Splunk for SOC analysts20 / 81

Only a few fields exist in the index itself

Stamped on every event at index time.

FieldMeaning
indexThe named container the event lives in (e.g. wineventlog, sysmon, firewall)
sourcetypeThe kind of data, which decides how fields are extracted (e.g. pan:traffic)
sourceWhere it came from: a file path, a Windows channel, a network input
hostThe machine that produced it
_timeThe event timestamp
_rawThe original event text, untouched
_indextimeWhen Splunk stored it
Naming differs per environment. Current Windows add-on versions use sourcetype WinEventLog (or XmlWinEventLog) and name the channel in source, such as WinEventLog:Security. Older deployments used WinEventLog:Security as the sourcetype.
HACKTHESOCLesson 89Splunk for SOC analysts21 / 81

Most fields are extracted at search time

Index time

The default fields, plus any an admin chose to index. Answerable from the index alone; this is all tstats can use.

Search time

EventCode, user, src, dest, CommandLine: extracted from _raw by the add-on (TA). New extractions apply to old data, but Splunk must read events to test them.

Order of preference: index, then sourcetype or source, then a tight time window, then specific terms, then field filters.

Indexes are time-ordered buckets with a lexicon of terms. Time skips buckets, index picks the container, terms hit the lexicon. Everything after that costs CPU because events are read from disk and parsed.
HACKTHESOCLesson 89Splunk for SOC analysts22 / 81

How Splunk narrows before it reads anything

  1. 1Time picks bucketsIndexes are time-ordered, so the window skips whole buckets off disk.
  2. 2Index picks the containerindex= chooses which store to open, ignoring the rest.
  3. 3Terms hit the lexiconA plain keyword is matched against each bucket's word list, cheaply.
  4. 4Then events are readOnly surviving events are read from disk and parsed for field filters: the expensive part.
This four-step order is why the scoping advice is index, then sourcetype, then time, then terms, then fields. Everything after the lexicon costs CPU.
HACKTHESOCLesson 89Splunk for SOC analysts23 / 81

The Job Inspector tells you why a search is slow

Example header: returned 62 results by scanning 4,118,203 events in 31.4 seconds. Compare scanCount to eventCount.

SymptomLikely causeFix
scanCount in millions, eventCount tinyBase search too looseAdd index, sourcetype, a narrower time, a specific term
Large time in command.search.filterLate filtering on search-time fields, or a leading wildcardMove filters before the first pipe, add a plain keyword
Time dominated by a later commandtransaction, join or a big subsearchReplace with stats
Slow only in VerboseField discovery over many fieldsUse Smart or Fast
Execution costs break the time down: dispatch.fetch, command.search.index, command.search.rawdata, command.search.filter. Splunk's guidance: a healthy scan rate is around ten to twenty thousand events per second.
HACKTHESOCLesson 89Splunk for SOC analysts24 / 81

scanCount versus eventCount: the first number to read

scanCount

How many events Splunk read off disk. Millions here means the base search cast too wide a net.

eventCount

How many matched and came back. Tiny next to a huge scanCount is the classic 'loose base search' signal.

The fix

Tighten the base search: add index, sourcetype, a narrower time and a specific term so fewer events are scanned.

Splunk's rough health figure is 10,000 to 20,000 events per second scanned. A big gap between the two counts is where almost all slowness lives.
HACKTHESOCLesson 89Splunk for SOC analysts25 / 81

Discover what exists before you guess names

  • Generating commands start with a pipe and need no base search
  • Oldest last_seen at the top: the sources that went quiet
Never assume names. Run these on day one in a new environment.

SPL fundamentals

The pipeline, boolean logic, quoting, wildcards and case sensitivity.

HACKTHESOCLesson 89Splunk for SOC analysts27 / 81

Command types explain how SPL behaves

Everything before the first pipe is the base search; each command transforms the previous output.

TypeBehaviourExamples
GeneratingStarts a pipeline with no input eventsinputlookup, tstats, metadata, makeresults
StreamingHandles each event independently, cheapeval, where, rex, fields, search
TransformingTurns events into a results tablestats, chart, timechart, top, rare
Dataset processingNeeds the whole result set before it can outputsort, eventstats

After a transforming command only the table columns exist: | stats count BY src | where EventCode=4625 returns nothing.

This is why filters belong before the first transforming command whenever possible.
HACKTHESOCLesson 89Splunk for SOC analysts28 / 81

Anatomy of a pipeline: data flows left to right

  1. 1Base searchEverything before the first pipe. Pulls the candidate events as cheaply as possible.
  2. 2Each pipe transformsA command takes the previous output and hands its result to the next.
  3. 3Order changes costFilter early so later commands see fewer events; a filter after stats sees only columns.
  4. 4Read it as a sentence'Get these events, then compute this, then keep these rows, then sort.'
The mental model that unlocks SPL: it is a conveyor belt, not a query. Each stage only sees what the previous stage passed on.
HACKTHESOCLesson 89Splunk for SOC analysts29 / 81

Five traps in the base search

  • OR and NOT uppercaseAND is implied. NOT applies only to the term right after it.
  • OR binds before ANDIn search, but eval and where do AND first. Use parentheses or EventCode IN (4624,4625).
  • != versus NOTfield!=value drops events missing the field; NOT field=value keeps them.
  • Quote and escapeDouble quotes around spaces; double backslashes in paths: Image="*\\powershell.exe".
  • Leading wildcards*powershell.exe cannot use the lexicon. Add a plain keyword or TERM(192.0.2.5).
EventCode=4624 OR EventCode=4625 user=d.rosen means (4624 OR 4625) AND user. A bare word like failed matches anywhere in _raw: cheap pruning. Combine a keyword to narrow with fields to be exact.
HACKTHESOCLesson 89Splunk for SOC analysts30 / 81

Why OR precedence bites, and how to be explicit

  • In the base search and search, OR binds before the implied AND
  • eval and where do the opposite: AND before OR
  • Parentheses or IN(...) remove all doubt
This single precedence rule causes more wrong results than any other. Make students parenthesise until it is habit.
HACKTHESOCLesson 89Splunk for SOC analysts31 / 81

Case rules differ by where you write them

ThingCase rule
Field names (EventCode)Case sensitive. eventcode=4625 finds nothing
Values in the base search and searchCase insensitive. user=D.ROSEN matches d.rosen
Values in where, eval, rexCase sensitive
Operators OR, AND, NOTMust be uppercase
The classic beginner bug: the base search finds d.rosen, then a where clause with D.ROSEN silently drops everything.
HACKTHESOCLesson 89Splunk for SOC analysts32 / 81

Slow and wrong versus fast and right

  • index=* and no time: every bucket is a candidate
  • lower() makes the case-sensitive where comparison safe
  • The keyword powershell lets the lexicon prune first
Ask the class to spot every problem in the first block before revealing the second.
HACKTHESOCLesson 89Splunk for SOC analysts33 / 81
Filter before the first transforming command, because after it only the table columns exist.

| stats count BY src | where EventCode=4625 returns nothing: EventCode is gone once stats has run.

This is the rule the command-types table exists to justify. Put every filter you can ahead of stats, chart or timechart.

Aggregation: stats, eventstats, streamstats

Master stats and you answer most triage questions in one line.

HACKTHESOCLesson 89Splunk for SOC analysts35 / 81

The stats functions you will actually use

FunctionReturns
countNumber of events
dc(field)Distinct count
values(field)Unique values, sorted, as a multivalue field
list(field)All values in event order (up to 100)
earliest(_time) / latest(_time)First and last timestamp
min max avg sum stdevNumeric summaries

count(eval(EventCode=4625)) counts only matching events, so one query can compute failures and successes.

stats output is sorted by its BY field, not by count, so follow it with sort. Plain sort caps at 10,000 rows; sort 0 removes the cap.
HACKTHESOCLesson 89Splunk for SOC analysts36 / 81

How stats groups: BY names the key

  1. 1Pick the functionscount, dc(user), values(...): what you want computed per group.
  2. 2Pick the BY fieldsBY src makes one output row per source; BY src,user one per pair.
  3. 3Events become rowsThe raw events are gone; only the group key and computed columns remain.
  4. 4Sort the tablestats sorts by the BY field, so add sort 0 - count to rank by volume.
The BY clause is the single most important choice: it defines what 'one thing' means for the rest of the search.
HACKTHESOCLesson 89Splunk for SOC analysts37 / 81

One command, two attack shapes

Row one: about four passwords per account across 48 accounts, the signature of a spray. Row two: 38 attempts against one account, a classic brute force. Same command, two shapes.
HACKTHESOCLesson 89Splunk for SOC analysts38 / 81

Pick the right aggregation for the question

You needCommandWhy
One row per groupstatsSummarise and drop the raw events
A group stat on every eventeventstatsKeeps events, adds the aggregate as a field
A running total in time orderstreamstatsComputes across the event stream; sort first
The top few valuestop / rareRanked counts with percentages
Most broken searches fail the events-versus-rows question. Decide what your unit is before you choose the command.
HACKTHESOCLesson 89Splunk for SOC analysts39 / 81

stats discards events; its siblings keep them

stats

Collapses events into one row per group. The originals are gone.

eventstats

Same aggregation, but adds the result to every event: eventstats dc(user) AS users_per_src BY src then where users_per_src>=10.

streamstats

A running value in event order, such as the gap since the previous event. Sort first: it uses the order it receives.

After every command ask: is my unit now events or rows, and which columns survive?

Reshaping helpers: table, fields - _raw (drop early to save memory), rename, dedup user, top limit=5 user, rare, head 10. Most broken searches fail at the events-versus-rows question.
HACKTHESOCLesson 89Splunk for SOC analysts40 / 81

where uses eval syntax; search uses loose syntax

NeedUse
Keep rows where failures > 20where failures>20
Keep users beginning with svc_search user=svc_* or where like(user,"svc_%")
Compare two fieldswhere bytes_out > bytes_in
Test that a field has a valuewhere isnotnull(dest)
After the first pipe, search keeps keywords, wildcards and case-insensitive values. where gives numeric comparison, functions, field-to-field comparison and case-sensitive strings.

Lookups, transaction vs stats, subsearches

Enrich events with context and correlate them without killing the platform.

HACKTHESOCLesson 89Splunk for SOC analysts47 / 81

Lookups join context to your events by a key

  • inputlookupGenerating command that reads the whole table, to inspect it or feed a subsearch.
  • lookuplookup threat_ips ip AS dest_ip OUTPUT category confidence adds category and confidence.
  • CIDR matchingExact by default; match_type = CIDR(ip) in the definition lets subnets match single IPs.
  • Verify it workedWhitespace and case differences break matches silently. Check isnotnull(category).
  • outputlookupWrites results back to a lookup: how an allowlist or watchlist is maintained from SPL.
Most lookups are CSV files with a definition under Settings > Lookups; larger or writable ones live in the KV store.
HACKTHESOCLesson 89Splunk for SOC analysts48 / 81

stats does what transaction does, faster

transaction is memory heavy and does not parallelise across indexers well. Splunk's own documentation recommends stats when a unique key exists. Use transaction only for reused IDs, merged raw text or start and end markers.
HACKTHESOCLesson 89Splunk for SOC analysts49 / 81

transaction versus stats: when each is right

Use stats

A unique key exists (user, src). Faster, parallelises across indexers, and answers most correlation questions.

Use transaction

Only for reused IDs, merged raw text, or explicit start and end markers. It is memory heavy.

Splunk's own guidance is stats first. transaction gives duration and eventcount for free, which is its one real advantage.
HACKTHESOCLesson 89Splunk for SOC analysts50 / 81

A subsearch runs first and becomes OR-ed conditions

The field names the subsearch returns become the field names in the outer search; a field literally named search is inserted verbatim. Test the inner search alone and return one column.
HACKTHESOCLesson 89Splunk for SOC analysts51 / 81

Which correlation tool for which job

SituationTool
Add context from a listlookup / inputlookup
Several event types per keystats with count(eval(...))
Reused session IDstransaction
A short computed list of valuesa subsearch
The subsearch's silent 10,000-result and 60-second limits are why it is only for short lists, never a detection over many sources.
HACKTHESOCLesson 89Splunk for SOC analysts52 / 81
A subsearch stops at 10,000 results or 60 seconds, and it does so silently.

No error, just missing rows. In a detection the missing sources look clean. For thousands of values, use a lookup or a single stats search.

Rule of thumb from the lesson: list for context is a lookup, several event types per key is stats with count(eval()), reused-ID sessions is transaction, a short computed list is a subsearch.

Add-ons map vendor fields and tag events, so Windows, Linux, VPN and cloud logins share action, src, dest, user.

HACKTHESOCLesson 89Splunk for SOC analysts55 / 81

How accelerated data models make tstats fast

  1. 1Add-ons normaliseVendor fields are mapped to CIM names and events are tagged into a model.
  2. 2Acceleration summarisesSplunk pre-computes .tsidx summaries next to the buckets, refreshed about every 5 minutes.
  3. 3tstats reads summariesIt answers from the pre-computed index, not raw events, so it returns in seconds.
  4. 4The trade-offOnly summarised, tagged, indexed fields are available: no wildcards, no late data.
This is why tstats is fast and why it can miss things. The next slide is the list of ways it quietly lies.
HACKTHESOCLesson 89Splunk for SOC analysts56 / 81

tstats: one query, every vendor, seconds

A generating command. Fields carry the dataset prefix.

The helper macro drop_dm_object_name("Authentication") removes the dataset prefix from column names, an alternative to rename.
HACKTHESOCLesson 89Splunk for SOC analysts57 / 81

Where tstats quietly lies to you

  • summariesonly=trueEvents newer than the last refresh or older than the summary range are missing without warning.
  • summariesonly=falseComplete, but slower: falls back to raw data for the unsummarised range.
  • Untagged sourcesNever enter the model, so tstats returns nothing for them.
  • WHERE and BYAccept only indexed or model fields, and no wildcards.

If tstats and raw SPL disagree: is the model accelerated for my range, is my source tagged, is the newest data unsummarised?

Run the CIM health check from the previous slide whenever a new source is onboarded.
HACKTHESOCLesson 89Splunk for SOC analysts58 / 81
tstats is fast because it reads pre-computed summaries, not raw events.

That speed is exactly why it can miss the newest, the untagged and the unsummarised. Confirm with a raw search when a verdict depends on it.

Hold both facts together: reach for tstats to go fast across vendors, then verify the edges with raw SPL before you escalate.

Scheduled versus real-time alerts

Scheduled

Runs on a cron over a fixed window. Predictable, cheap, and the right default for almost every detection.

Real-time

Holds resources continuously to evaluate as events arrive. Reserve for the rare case that truly needs the instant.
