Why digital evidence needs special handling

A crime scene with tape, photos, and a log of every item moved.

HACKTHESOCLesson 57Evidence and custody6 / 57

Evidence: any data that helps establish what happened

Digital 'items' need the same rigor as a physical crime scene.

  • A hard driveFiles, deleted data and timestamps from the affected host.
  • A memory dumpWhat was running, connected and decrypted at that moment.
  • A log fileThe recorded actions of users, processes and systems.
  • A suspicious executableThe sample itself, for analysis and hashing.
The crime-scene officer tapes the room, photographs it, and logs every item moved. The reason is the same here: anyone challenging your conclusions can attack how you got them.
HACKTHESOCLesson 57Evidence and custody7 / 57

Two threats make digital evidence fragile

It can vanish

Some of the most valuable evidence lives only in a running computer's memory and disappears the instant it is turned off.

It can change silently

Copying, opening in the wrong tool, or booting an infected machine can alter data with no visible sign. You need mathematical proof.

Anyone challenging your conclusions can attack how you got them, not just what you found. A defence lawyer's whole strategy may be 'you cannot prove this was not altered'.

Order of volatility: collect the fragile first

Every second you delay, volatile data may be overwritten or lost.

HACKTHESOCLesson 57Evidence and custody11 / 57

From most to least volatile

PrioritySourceWhy it is fragile
1CPU registers, cacheOverwritten in microseconds
2RAM / memory, running processes, network connectionsLost on power-off or reboot
3Temporary files, swap/page fileRotated and overwritten during use
4Disk (hard drive / SSD)Persists across reboots
5Logs on remote serversRetained per policy, relatively stable
6Backups, archivesDesigned for long-term retention
RAM can hold decryption keys, fileless malware, active connections, injected code and clear-text credentials. None of it survives a shutdown.
HACKTHESOCLesson 57Evidence and custody12 / 57

Why RAM is a goldmine, and why it is lost on shutdown

What RAM can hold

Often the only record of how the attack actually worked.

  • Decryption keys
  • Fileless malware that never touched disk
  • Active network connections and injected code
  • Clear-text credentials

After power-off

None of it survives. A disk image taken later cannot bring it back, so memory capture comes first wherever it is safe.

Fileless malware is the clearest case: it lives only in memory, so a shutdown erases the attack itself.
HACKTHESOCLesson 57Evidence and custody13 / 57
Memory before disk before backups. 'Just turn it off' is often the mistake.

Powering down to stop the bleeding destroys RAM, possibly the only evidence of how the attack worked. Where safe, capture a memory image first.

Getting the sequence wrong means permanently losing evidence you can never recover.
HACKTHESOCLesson 57Evidence and custody14 / 57

RFC 3227's exact order

IETF Guidelines for Evidence Collection and Archiving, 2002, still cited by NIST and courts.

  • 1. Registers, cacheThe most fleeting.
  • 2. Kernel state and memoryRouting table, ARP cache, process table, kernel statistics, memory.
  • 3-4. Temp file systems, diskTemporary file systems, then the disk.
  • 5. Remote loggingMonitoring data about the host that lives on other systems.
  • 6. Physical config, topologyPhysical configuration and network topology.
  • 7. Archival mediaThe least volatile.
Network state like the ARP cache sits in tier 2 because it lives only in the running kernel and vanishes on reboot, just like RAM.
HACKTHESOCLesson 57Evidence and custody15 / 57

RFC 3227's collection rules

RuleWhat it means in practice
Proceed from volatile to less volatileFollow the order top to bottom
Minimise changes as you collectDo not update access times; write blockers; never the original
Collection before analysisImage and hash first, investigate the copy later
Run tools from trusted read-only mediaA vetted toolkit, not the suspect host's own binaries
Document each step, with times and clock driftIf the host clock was 47 seconds fast, every timestamp must be adjusted
Clock drift is the rule juniors miss: only a contemporaneous note of the offset lets you reconcile timestamps across systems later.

Section 3 of 8

Imaging and hashing: preserving integrity

Never investigate on the original.

HACKTHESOCLesson 57Evidence and custody18 / 57

A forensic image is not a file copy

Imaging

A bit-for-bit copy of RAM or a disk: allocated files, deleted-but-not-overwritten data, slack space, file-system metadata.

Write blocker

Hardware or software that allows reading the source drive while preventing any write. RAM needs a live acquisition tool instead.

The mere act of copying must not be able to alter the original.
HACKTHESOCLesson 57Evidence and custody19 / 57

The hashing workflow that proves a faithful copy

  1. 1Acquire the imageDisk through a write blocker; RAM with a live acquisition tool.
  2. 2Hash source and imageSHA-256 of both. They must match, proving the copy is exact.
  3. 3Record the valueWrite the hash and algorithm into your documentation.
  4. 4Re-hash any time laterStill matching means proof it was not altered since collection.
A hash reduces any amount of data to a fixed fingerprint; change one bit and the fingerprint changes completely.
HACKTHESOCLesson 57Evidence and custody20 / 57

A hash verification record

Acquire, hash source and image, record the value, and re-hash any time later. A match six months on proves nothing happened in storage.
HACKTHESOCLesson 57Evidence and custody21 / 57

Reading the hash verification record

LineWhat it establishes
Evidence: WORKSTATION-07, serial 8HX92Q2Exactly which physical device this is
Imaging tool, write-blocked acquisitionThe method: copying could not alter the source
SHA-256 of source diskThe fingerprint of the original at collection
SHA-256 of image fileThe fingerprint of your working copy
Result: MATCHMathematical proof the image is identical to the original
This turns 'trust me, I copied it carefully' into a claim you can defend.
HACKTHESOCLesson 57Evidence and custody22 / 57
'How do you know this file is what you found?' Your answer is the matching hash.

The digital equivalent of tamper-evident tape. Prefer SHA-256: MD5 and SHA-1 still appear in older tooling but are cryptographically weakened.

Even when specialists do full imaging, the SOC analyst often hashes a captured file, memory dump or sample and logs the value: the integrity baseline everything depends on.
HACKTHESOCLesson 57Evidence and custody23 / 57

Which hash algorithm to record

AlgorithmLengthStatus
MD532 hex charactersStill in older tooling; cryptographically weakened
SHA-140 hex charactersStill in older tooling; cryptographically weakened
SHA-25664 hex charactersPreferred: record this one
Whatever you compute, record the algorithm with the value: a hash without its algorithm cannot be re-verified.

Section 4 of 8

Chain of custody: who, what, when, how

An unbroken, documented trail from collection to presentation.

HACKTHESOCLesson 57Evidence and custody25 / 57

Four questions answered at every step

The chain of custody proves evidence was continuously accounted for from collection onward.

  • WhoThe person who handled it, by name and role.
  • WhatA precise description: device, serial number, hash value.
  • WhenThe date and time of each transfer or action.
  • HowHow it was handled, stored and transported, such as a sealed bag in a locked locker.
Every time evidence changes hands or location, both parties sign. The result is an unbroken timeline from collection to presentation.
HACKTHESOCLesson 57Evidence and custody26 / 57

A real chain-of-custody log

Every handler named, every location and transfer timestamped, and the hash re-verified at final storage: custody and integrity together. Both parties sign at every hand-off; if challenged, this log, not your memory, answers.

HACKTHESOCLesson 57Evidence and custody28 / 57

Broken chain versus defensible chain

What breaks it

An unexplained gap, evidence left unattended, a missing signature, no hash. Even sound evidence can be thrown out.

Habits that hold it

Document as you go, record the hash in the log, minimize handlers, store with restricted, logged access.

Admissibility requires showing evidence is authentic and unaltered. The same rigor makes findings defensible for HR, insurance and regulators.

The transfer block, filled every time evidence moves

  1. 1Date and timeWhen it happened, with the time zone labelled.
  2. 2Released byName and signature of the person handing it over.
  3. 3Received byName and signature of the person taking custody.
  4. 4Purpose or actionWhy it moved, or what was done to it.
  5. 5Storage locationLocker number or sealed bag ID after this step.

The header is filled once; this block repeats for every hand-off, examination or storage change.

One transfer row, blank and filled

Two rules: fill every field at the moment of the action, and re-verify the hash at each transfer. An empty field is exactly the gap an opposing party points to.

Containment vs. preservation

Stop the attacker now, or keep the scene intact? Usually both.

HACKTHESOCLesson 57Evidence and custody33 / 57
Move too aggressively and you destroy evidence. Too cautiously and the attacker keeps going.

Containment stops the attacker now. Preservation keeps the scene intact. The skill is getting both.

The flashpoint is almost always the impulse to pull the power or the cable on a compromised host.
HACKTHESOCLesson 57Evidence and custody34 / 57

Three ways to stop a compromised host

Pull the power

Stops on-host activity instantly, but destroys RAM: malware, sessions, keys, fileless artifacts. Can corrupt open files.

OS shutdown

Triggers logoff scripts and may let malware run cleanup or anti-forensic routines.

Network isolation

EDR contain, disabled switch port or quarantine VLAN. Cuts C2 and lateral movement while the host stays running.

Isolation gives you containment and preservation at the same time.
HACKTHESOCLesson 57Evidence and custody35 / 57

Three ways to isolate a host while it keeps running

MethodWhere it acts
EDR 'contain' or 'quarantine'On the endpoint agent: blocks the host's network traffic
Disable the switch portOn the network switch the host is plugged into
Move to a quarantine VLANOn the network: the host lands in an isolated segment

All three sever C2 and stop lateral movement while memory and live state stay available.

Which one you use depends on your tooling and playbook; the evidence benefit is the same.
HACKTHESOCLesson 57Evidence and custody36 / 57

A sound sequence in a serious incident

  1. 1IsolateCut the host from the network, leave it powered on.
  2. 2Capture volatile evidenceMemory image, processes, connections, by volatility.
  3. 3Image the diskThrough a write blocker.
  4. 4HashEverything, and record it.
  5. 5Keep custodyMaintain the chain at every step.
Exceptions exist: ransomware mid-encryption or a life-safety issue may justify immediate shutdown. That call usually belongs to an incident lead, not a lone first responder.
HACKTHESOCLesson 57Evidence and custody37 / 57

When an immediate shutdown can still be right

Possible exceptions

Shutdown may be the lesser evil when the system is actively destroying data.

  • Ransomware actively encrypting data
  • A life-safety issue

Who decides

Usually an incident lead, not a first responder alone. Follow the IR playbook and escalate when the stakes are high.

The default stays the same: resist the reflex to power off before evidence is safe.

Section 6 of 8

Common mistakes that break a case

Small, avoidable errors made under live-incident pressure.

HACKTHESOCLesson 57Evidence and custody39 / 57

Seven ways to destroy a solid case

  • Working on the originalAn AV scan or a 'quick look' can change timestamps or content.
  • Documenting from memoryNext-day reconstruction carries far less weight than contemporaneous notes.
  • Too many handsEvery handler is a link that can be questioned.
  • Skipping the hashCustody without a hash proves custody, not integrity.
  • Insecure storageA laptop on an unlocked desk 'for an hour' is an unexplained gap.
  • Reflexive power-offOften the most damaging early mistake. Also: mixing local time and UTC unlabelled.
None of these require malice. That is why custody procedures are a checklist: careful behaviour must be the default on your worst incident of the year.
HACKTHESOCLesson 57Evidence and custody40 / 57

Each mistake, and the habit that prevents it

MistakePreventing habit
Scanning or opening the originalWork only on the image
Notes written the next dayContemporaneous notes with exact timestamps
Many people handling the itemKeep the list of handlers as short as possible
No hash, or computed inconsistentlyRecord the hash in the custody log every time
Evidence left unattendedLocked storage with logged access between steps
Local time mixed with UTCOne labelled time zone, ideally UTC
A checklist makes the careful behaviour the default, even on your worst, most chaotic incident of the year.
HACKTHESOCLesson 57Evidence and custody41 / 57

Memory versus contemporaneous notes

Reconstructed next day

Approximate times, a missing storage location, no hash. Carries far less weight, and every gap is an opening for the other side.

Written as it happens

Exact timestamp, both names, purpose, storage and hash re-verified, recorded at the moment of the action.

Compare with the filled transfer row from section 4: every field was written at 10:15, not remembered later.

Legal admissibility: the Daubert standard

Will a judge even let the evidence reach a jury?

HACKTHESOCLesson 57Evidence and custody43 / 57

How a Daubert challenge plays out

  1. 1Expert evidence offeredYour forensic findings are presented as expert testimony.
  2. 2Reliability challengedThe other side argues the method is not reliable.
  3. 3Judge as gatekeeperThe judge weighs the Daubert factors against your methodology.
  4. 4Admitted or excludedDecided before the jury ever hears the evidence.
Daubert v. Merrell Dow Pharmaceuticals, 1993. It is not enough that the conclusion is correct: the method must be established and defensible.
HACKTHESOCLesson 57Evidence and custody44 / 57

The judge as gatekeeper weighs the method

Daubert factorThe question it asks of your forensic method
TestabilityCan the technique be, and has it been, empirically tested?
Peer review & publicationHas the method been published and reviewed by other experts?
Known or potential error rateIs there a documented rate of wrong results?
Standards controlling the techniqueAre there accepted professional standards for performing it?
General acceptanceIs it widely accepted in the forensic community?
From Daubert v. Merrell Dow Pharmaceuticals, 1993, used in most U.S. federal and many state courts. A few states still use the older Frye standard, general acceptance only.
HACKTHESOCLesson 57Evidence and custody45 / 57

Cross-examination, answered by method

A correct conclusion is not enough: the methodology must be established and defensible. An improvised, undocumented process is exactly what a Daubert challenge excludes.
HACKTHESOCLesson 57Evidence and custody46 / 57

Each answer maps to something the court weighs

What the analyst saidWhat it satisfies
Industry-standard tool, validated in thousands of casesGeneral acceptance; testability
Published error rates near zeroKnown or potential error rate
SHA-256 of source and image matched, reproducibleIntegrity, checkable by any other examiner
Custody log, hash re-verified at each transferContinuity: nothing altered or swapped
Every answer draws on something taught earlier. A modest analysis with rigorous, standard process survives; a brilliant improvised one may not.
HACKTHESOCLesson 57Evidence and custody47 / 57

Daubert and Frye: same lesson either way

Most US federal courts

Daubert

Testability, peer review, error rate, standards and general acceptance.

Older; a few state courts

Frye

General acceptance only, without Daubert's other factors.

Under both, standardized and well-documented methodology is what makes forensic evidence usable at all.

Live vs. dead acquisition, and the cloud

How collection happens, and why cloud breaks the old assumptions.

HACKTHESOCLesson 57Evidence and custody49 / 57

Dead versus live acquisition

Dead (static) acquisitionLive acquisition
System statePowered off before imagingStays running during collection
CapturesDisk contents onlyRAM, processes, network state, keys, plus disk
Best forStraightforward disk analysisFileless malware, active intrusions, encrypted volumes
Main riskLoses everything in memory permanentlyCollection tools alter some memory and state
NIST SP 800-86 frames this inside collection, examination, analysis, reporting: collection must be timely and repeatable by another examiner.
HACKTHESOCLesson 57Evidence and custody50 / 57

Choosing live or dead acquisition

Live

Suspected fileless malware or an active intrusion virtually requires it: powering off destroys the evidence you need.

Dead

A machine already off when found, or a case where a pristine disk image matters more than volatile state.

Neither is universally correct; the case decides.
HACKTHESOCLesson 57Evidence and custody51 / 57

NIST SP 800-86 places collection in a wider workflow

  1. 1CollectionTimely, because volatile data does not wait.
  2. 2ExaminationProcess the collected data to surface what is relevant.
  3. 3AnalysisDraw conclusions from what the examination found.
  4. 4ReportingPresent findings and the method used to reach them.

Repeatable: another examiner following your documented steps should reach the same result.

Repeatability is the same standardized-methodology theme the Daubert section depends on.
HACKTHESOCLesson 57Evidence and custody52 / 57

Why cloud evidence is harder

  • No physical accessCollection runs through the provider's API: e.g. aws ec2 create-snapshot --volume-id vol-... images an EBS volume, not a write-blocked drive.
  • Shared responsibilityHypervisor and physical host logs may simply be unavailable to you.
  • True ephemeralityA container or serverless function can run a payload and vanish in seconds.
  • Provider retentionLogs can age out before an investigation starts unless retention was extended or exported.
  • Multi-tenancyOther customers on the same hardware limit how invasively you can investigate.

Configure cloud logging and monitoring before an incident; no write blocker or hash can substitute afterwards.

Cloud shifts order-of-volatility urgency even earlier: the volatile state may be gone before the alert reaches you.

Key takeaways

  1. 01Digital evidence can vanish or change silently, so collect fragile data first and prove integrity.
  2. 02Follow the order of volatility, memory before disk before backups, per RFC 3227, and note clock drift.
  3. 03Work on a write-blocked image; matching SHA-256 hashes prove the copy is exact and unchanged.
  4. 04Keep an unbroken chain of custody (who, what, when, how) with the hash re-verified at every hand-off.
  5. 05Prefer network isolation over pulling power: containment and preservation together.
  6. 06Standard, documented methods survive Daubert; cloud evidence needs logging configured in advance.
