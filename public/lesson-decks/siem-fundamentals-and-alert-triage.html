What a SIEM is and the ingestion pipeline

The central nervous system of a SOC: signals from everywhere, correlated in one place.

HACKTHESOCLesson 05SIEM and alert triage6 / 80

Five stages, five silent failure modes

Splunk, Sentinel, Elastic Security, QRadar and Google Security Operations (formerly Chronicle) differ in query language and pricing, but the pipeline underneath is the same.
HACKTHESOCLesson 05SIEM and alert triage7 / 80

The five stages, and how each fails without a sound

Each stage can break quietly, leaving a rule that looks healthy but can never fire. These are the failure modes the figure names.

StageWhat it doesHow it fails silently
CollectionForwarders, syslog, API polling or agents ship raw logs to the SIEMA dead forwarder: the source goes quiet and no one is told
ParsingSplits each raw line into the right fields for that source formatA broken parser leaves a field empty, so rules that filter on it never match
NormalizationRenames vendor fields to one schema, such as src to source.ipUnmapped fields: the same data becomes unsearchable across sources
EnrichmentAdds context: geo-IP, asset owner, threat-intel reputationMissing context: the alert lacks what an analyst needs to judge it
Correlation and alertRules run across stored events and raise an alert on a matchNo rule, or an uncollected source: a real attack raises nothing
The next slide traces one real firewall event through collect, parse, normalize, store and search so these stages stop being abstract.
HACKTHESOCLesson 05SIEM and alert triage8 / 80

Four ways logs reach the SIEM

A log source is any system that produces logs. At this stage the data is raw: nothing is standardized yet.

  • ForwardersSoftware on the host ships its logs, e.g. a Splunk Universal Forwarder.
  • SyslogThe device pushes events over the network, e.g. a firewall to a collector on UDP/514.
  • API pollingThe SIEM pulls from a cloud service, e.g. Sentinel pulling Entra ID sign-ins via Microsoft Graph.
  • AgentsA collection agent such as an Elastic Beat reads and sends events.
Ask of every source: which of these four, and who would notice if it stopped? A gap here is the most common cause of a blind spot.

Normalization: one query that works across every vendor

ECS

Elastic Common Schema

Calls the source address source.ip. Fields like user.name and event.action are ECS-style.

Common Information Model

Splunk CIM

Calls the same thing src. Different name, same job: one query across many sources.

Open Cybersecurity Schema

OCSF

Moves normalization upstream: sources emit one shared JSON schema. Amazon Security Lake stores OCSF.

Without normalization you would need a different query for every vendor's idea of how to name an IP address.

Which parser runs depends on how the source shipped: plain syslog, CEF, LEEF, JSON from an API, or Windows XML.

Before you trust an empty search, check three things

  1. 1Is the source ingested?Search for any event at all from that host or source in the last day.
  2. 2Is the field populated?A broken parser leaves the field you filter on empty, so the filter matches nothing.
  3. 3Is the time range retained?Hot storage covers 30 to 90 days; older data may sit in a cold tier or be gone.
  4. 4Only then: cleanIf all three pass and nothing matches, the absence means something.
This checklist is quiz material and a habit worth drilling: most frustrating triage moments are pipeline questions, not attacker questions.
HACKTHESOCLesson 05SIEM and alert triage12 / 80
An empty search does not always mean a clean host.

A query only sees what was collected, correctly parsed, and still within retention. First ask: is this source even ingested, and does my time range cover it?

A gap in collection is the most common cause of a blind spot: if a critical server is not forwarding, no rule downstream can ever fire on it.

How an alert is born: detection rules

The shape of the rule tells you what an alert can and cannot prove.

HACKTHESOCLesson 05SIEM and alert triage14 / 80

Four families of detection logic

Detection typeHow it worksWhat it catches
SignaturesMatches a known-bad hash, command line, User-Agent or domainKnown threats; high precision, low recall. One changed byte slips past
ThresholdsCounts events and fires when a count crosses a line in a windowBrute force, enumeration, scanning: behaviour defined by volume
CorrelationJoins events from different sources on user.name or source.ipMulti-step stories no single source could tell; highest fidelity
Scheduled analyticsRuns a saved query on a schedule, one alert per resultHow most KQL and SPL detections run in production
Threshold art: too low and you drown, too high and a slow-and-low attacker walks under. Ask whether the volume looks like an attack or a batch job, a login storm after an outage, or a scanner.
HACKTHESOCLesson 05SIEM and alert triage15 / 80

Threshold rules: the art is in the number

E.g. ten failed logons for one account in five minutes, or 50 hosts contacted on 445 in ten minutes.

Too low

You drown in false positives and stop reading the alerts.

Too high

A slow-and-low attacker stays under the line and never fires it.

Lookalikes to rule out

Volume that is not an attack.

  • A batch job
  • A login storm after an outage
  • A vulnerability scanner
When you triage a threshold alert, first find the threshold, then ask whether the volume looks like an attacker or like one of the lookalikes.
HACKTHESOCLesson 05SIEM and alert triage16 / 80

A correlation story no single source could tell

  1. 1VPN: a failed loginFrom a new country. On its own: noise.
  2. 2VPN: then a successSame account, shortly after.
  3. 3Office 365: a forwarding ruleThe mailbox starts forwarding mail outward.
  4. 4The rule joins on user.nameIt fires only when the whole combination appears: a credential-compromise story.
Correlation is only possible across data that lives together, which is why identity, endpoint and cloud logs must reach the same SIEM.

Section 3 of 11

True positive, false positive, and triage

Avoid the two career-limiting mistakes: closing a real intrusion, chasing a phantom.

HACKTHESOCLesson 05SIEM and alert triage21 / 80

Alert versus incident: two words worth pinning down

Alert

One detection firing: one rule matched, one moment, one entity.

Incident (or case)

The container grouping related alerts into the story of what happened. One intrusion can raise identity, endpoint and network alerts that all belong to it.

You triage alerts; you escalate into, or open, an incident once you see they connect.

Sentinel calls the container an incident; other platforms call it a case. What you open in the queue is usually the incident.
HACKTHESOCLesson 05SIEM and alert triage22 / 80

Five dispositions to know precisely

DispositionWhat it means
True positiveCorrectly identifies genuinely malicious or unauthorized activity
False positiveFired, but the underlying activity is not malicious
True negativeThe silent, correct non-alert: nothing bad happened, nothing fired
False negativeSomething bad happened and no alert fired at all: invisible in your queue
Benign true positiveThe rule correctly caught the behaviour, but it is authorized and harmless
An alert is one rule firing once. An incident (or case) groups related alerts into the story of what happened. False negatives are why threat hunting and detection engineering exist.
HACKTHESOCLesson 05SIEM and alert triage23 / 80

Choosing the disposition, in order

  1. 1Malicious or unauthorized?And the rule meant to catch it: true positive. Investigate or escalate.
  2. 2Real but authorized?Pentest, admin task, approved scanner: benign true positive, with the change ticket.
  3. 3Did not occur as described?False positive: close and consider tuning the rule.
  4. 4Cannot cite the evidence?Then you may not choose a benign label. Keep digging or escalate.
The guardrail is the last step. A ticket, a baseline or an owner's confirmation is evidence; 'it's probably fine' is not.
HACKTHESOCLesson 05SIEM and alert triage24 / 80

Label an approved pentest correctly

Wrong: false positive

Implies the rule is broken and invites someone to tune it down, weakening a detection that worked.

Right: benign true positive

'Benign true positive, authorized pentest, ticket CHG-4471.' The rule worked; the activity was sanctioned.

A pentester will trip dozens of lateral-movement and credential-access rules. Those are true positives in the technical sense.
HACKTHESOCLesson 05SIEM and alert triage25 / 80

The dispositions on real situations

SituationDispositionWhy
A real password spray from an external IPTrue positiveMalicious activity, correctly detected
A vulnerability scanner trips a port-scan ruleFalse positiveFired, but the activity is not malicious
An approved pentest trips lateral-movement rulesBenign true positiveRule worked; activity was sanctioned
An attacker moves through a source nobody collectsFalse negativeNever in your queue: hunting finds it
Some teams treat the scanner case as benign positive too. Whatever your SOC's convention, the label must say whether the rule was right.
HACKTHESOCLesson 05SIEM and alert triage26 / 80
A false positive costs minutes. A missed true positive costs an intrusion.

Before closing as benign, point to the specific evidence: a ticket, a baseline, owner confirmation. 'It's probably fine' is not evidence.

This does not mean escalate everything: an analyst who escalates every alert is as useless as one who closes everything. When you cannot find the evidence quickly, keep digging or escalate.

Section 4 of 11

Reading the alert object, and tuning the rule

An alert is a structured object. The parts beginners scroll past are the ones that matter in triage.

HACKTHESOCLesson 05SIEM and alert triage28 / 80

Reading an alert object in triage order

  1. 1Read the titleA good rule's title already names the user or IP (alert details override).
  2. 2Check the entitiesAccount, Host, IP, File, URL, Mailbox: what you can pivot on in one click.
  3. 3Read the custom detailsThe counts the author surfaced, e.g. FailedAttempts, TargetedAccounts.
  4. 4Open the raw eventsThe alert is the rule's summary; the events are the evidence.
  5. 5Open the rule queryExactly what condition it checked, and what it did not.
Beginners read the title and severity and stop. The parts they scroll past are the ones that decide the verdict.
HACKTHESOCLesson 05SIEM and alert triage29 / 80

What the alert carries besides a title

In Sentinel, a scheduled rule writes alerts to SecurityAlert and incidents to SecurityIncident.

  • EntitiesFields mapped to typed objects (Account, Host, IP, File, URL, Mailbox), up to ten per rule. They drive pivoting and incident grouping.
  • Custom detailsExtra query columns the author surfaced, such as FailedAttempts or TargetedAccounts, shown in ExtendedProperties.
  • Alert details overridePuts a result value in the title, which is why a good rule's title already names the user or IP.
  • Link to raw eventsSentinel re-runs the rule query over the alert window; a Splunk ES notable carries a drill-down search.

Always open the raw events. The alert is the rule's summary of what it saw, and the summary can be wrong.

An unmapped IP is an IP nobody can pivot on. Entity mapping is what makes one-click investigation possible.
HACKTHESOCLesson 05SIEM and alert triage30 / 80

Why the same rule produces one incident or fifty

Event grouping

"Group all events into a single alert" (the default, one alert per run) or "Trigger an alert for each event" (one alert per result row).

Alert grouping

Incident settings fold up to 150 alerts into one incident, for example only when all mapped entities match, within a time frame you set.

Forty identical incidents for one password spray is a grouping configuration problem to report, not forty investigations.

Work the activity as one incident and ask for alert grouping on matching entities so one spray becomes one incident.
HACKTHESOCLesson 05SIEM and alert triage31 / 80

Tuning levers, from narrow to blunt

LeverWhat it doesThe risk if done carelessly
Narrow exclusionExclude one exact value, such as the scanner's IP, usually via a watchlistLow, provided the value is specific and owned
Raise the thresholdFire at 20 failures instead of 15A slower attacker now stays under the line
Throttle or suppressSentinel pauses the rule up to 24 hours; Splunk ES throttles by window and fieldsA second, different attack during the pause is missed
Automation ruleAuto-close incidents matching set conditions, such as a known test accountHides real activity from that entity, so give it an expiry date
Disable the ruleNothing firesEvery future true positive becomes a false negative

Prefer the narrowest lever, put the reason and an expiry date in the change, keep the exclusion list reviewable.

Sentinel's throttle setting is "Stop running query after alert is generated". The follow-up to closing a false positive or benign positive is a tuning request.
HACKTHESOCLesson 05SIEM and alert triage32 / 80

The spray rule, tuned the narrow way

  • Entity mapping IP -> IPAddress; custom details FailedAttempts, TargetedAccounts
  • Alert name "Password spray from {{IPAddress}}": one alert per spraying IP
  • Alert grouping: one incident if all entities match, within 5 hours
A watchlist the query reads with _GetWatchlist can be audited. A hard-coded IP buried in line 40 of a query usually cannot.
HACKTHESOCLesson 05SIEM and alert triage33 / 80

Querying for triage: the data model, real KQL and SPL

Know what you are querying against, then a small set of operators does the work.

HACKTHESOCLesson 05SIEM and alert triage35 / 80

Same query, two dialects

Learn the rhythm once and you can triage in any SIEM after a day of learning its dialect.
HACKTHESOCLesson 05SIEM and alert triage36 / 80

Know the data model before you trust a result

ConceptSplunkMicrosoft Sentinel
Where events liveindex plus sourcetype (azure:aad:signin, WinEventLog:Security)A table: SigninLogs, SecurityEvent, CommonSecurityLog, Syslog, DeviceProcessEvents
Event time (time picker)_timeTimeGenerated
Arrival time_indextimeingestion_time()
Field extractionMostly at search time by the sourcetype; only host, source, sourcetype, _time at index timeMostly at ingestion; ASIM parsers like _Im_Authentication normalize at query time

If an expected field is empty, suspect the parser before you conclude the activity did not happen.

Always name index and sourcetype: a search without index= scans your role defaults, slow and can silently miss data. A rule that looks back 15 minutes every 15 minutes never sees an event that arrived 20 minutes late, which is why Sentinel rules usually look back a little further than they run.
HACKTHESOCLesson 05SIEM and alert triage37 / 80

Event time versus arrival time

_time / TimeGenerated

Event time

When it happened on the source. The time picker and most rules filter on this.

_indextime / ingestion_time()

Arrival time

When the SIEM indexed it. Drifts from event time when a forwarder backs up or an API delivers late.

Missed alerts

The cost of drift

A rule looking back 15 minutes every 15 minutes never sees an event that arrived 20 minutes late.

That is why Sentinel rules usually look back a little further than they run.

If an alert seems 'late', compare the two times before assuming the attacker was slow.

Narrow to time and entity, aggregate with stats or summarize, shape with table or project. Then:

In SPL prefer stats over transaction and join: transaction is memory-hungry and slow on large ranges, and subsearch joins are truncated at a result limit by default, so a join can quietly drop rows. Did any spraying IP also get in? A join of failures against successes answers it.

Did any spraying IP also get in? A join answers it

  • First block: IPs that failed against 10+ accounts in the last hour
  • Second block: successful sign-ins, kept only if the IP is in that list
  • Any row returned = a sprayer that guessed correctly at least once
In SPL prefer stats over join where you can: subsearch joins are truncated at a result limit by default and can quietly drop rows.

The rhythm of every triage query

  1. 1NarrowTime window and entity: earliest=-24h or where TimeGenerated > ago(24h).
  2. 2Aggregatestats or summarize: count, distinct count, values, min and max, by a field.
  3. 3Shapetable or project the columns you need, then sort.

The next query applies all three to one suspicious account's history.

Learn the rhythm once and any SIEM is a day of learning its dialect away.

Enrichment and escalation

A raw alert is a hypothesis. Context turns it into a verdict.

HACKTHESOCLesson 05SIEM and alert triage44 / 80

Three kinds of context change the stakes

CMDB, inventory

Asset

Test VM or domain controller? Internet-facing? Business owner? In scope for cardholder data?

IdP, HR

User

Standard user, admin or service account? Normal hours, travel, systems? On leave or recently terminated?

IP, domain, hash

Threat intel

Tor exit, hosting provider, residential proxy, active C2? Newly registered domain? Hash flagged on VirusTotal?

Threat intel sharpens probability but never decides alone: a benign cloud IP can host an attacker.

A service account logging in interactively at 3 a.m. is far more alarming than a human doing the same. A login from Brazil is fine for a Brazilian user, disastrous for a Kansas employee who badged in an hour ago.

AlertContext A: shrugContext B: fire drill

The enrichment worksheet's verdict logic

  • Pseudocode, not executable: the order of checks is the lesson
  • A success after failures outranks everything else
  • The default is keep investigating, never close
Threat intel sharpens probability but never decides alone: a benign cloud IP can host an attacker, and a clean hash can be brand-new malware.
HACKTHESOCLesson 05SIEM and alert triage47 / 80

Close, keep investigating, or escalate

  • CloseOnly when evidence affirmatively shows benign activity, and you can point to it.
  • Keep investigatingThe picture is incomplete but not alarming.
  • EscalateConfirmed malicious, a high-value asset, hands-on-keyboard, multiple hosts or accounts, or you cannot say it is contained.
  • The packageWhat fired, what you enriched, what you confirmed, what you could not, and your recommended action.
Before escalating, answer: is it real, is it contained, who and what does it touch, what happens if I am wrong? A good escalation is not a panicked forward of the raw alert.
HACKTHESOCLesson 05SIEM and alert triage48 / 80

Four questions to answer before you escalate

  1. 1Is it real?What evidence confirms it, beyond the rule firing?
  2. 2Is it contained?If you cannot say yes, that alone is a reason to escalate now.
  3. 3Who and what does it touch?Accounts, hosts, data: one, or several (a sign of spread)?
  4. 4What if I am wrong?The cost of a missed true positive outweighs a wasted escalation.
Answering these four is what turns a forwarded alert into an escalation package.

Enrichment changed the stakes

Before enrichment

A spray from one IP, and one account that succeeded. Serious, but it could still be a test account.

After enrichment

The success is a finance manager with AP and vendor-payment access. The IP is a Tor exit node on the feed. No MFA challenge was recorded.

No MFA challenge means either MFA is disabled for the account or the attacker satisfied it.

Either explanation is bad, and both are for Tier 2 to resolve. The analyst's job is to state it, not to guess which.

Detection-as-code and Sigma

Write once, review, test, share: rules as engineering artifacts.

HACKTHESOCLesson 05SIEM and alert triage57 / 80

Detection-as-code, and the coverage truth

Every SIEM speaks its own language: KQL for Sentinel, SPL for Splunk, a DSL for Elastic. A great detection written in one is trapped there.
HACKTHESOCLesson 05SIEM and alert triage58 / 80

Why Sigma plus git beats console clicks

Sigma is a vendor-neutral, YAML-based rule format; a converter turns it into KQL, SPL or Elastic.

  • Version controlEvery rule is a text file with history: who changed what, when, why. Roll back a bad edit.
  • Reviewed and testedA careless rule does not silently flood the SOC or get disabled into a blind spot.
  • SharedInherit thousands of community rules for known techniques and contribute your own.
A rule hand-typed into a UI by an analyst who has since left is fragile and invisible. Detection engineering is one of the most valued specialisations an analyst can grow into.
HACKTHESOCLesson 05SIEM and alert triage59 / 80

From a Sigma rule to a running detection

  1. 1Write the rule in SigmaYAML describing 'this pattern in this log source', with no product syntax.
  2. 2Commit it to gitThe rule now has a history: who changed what, when and why.
  3. 3Review and testLike code, before it can flood the SOC or go blind.

One rule, many back-ends: migrating SIEMs no longer means rewriting every detection.

SOAR: the machine does the first ten minutes

Volume and repetition drown a SOC, not slow analysts.

HACKTHESOCLesson 05SIEM and alert triage62 / 80

An enrichment playbook: the first ten minutes, done for you

SOAR = Security Orchestration, Automation and Response. A playbook is an automated workflow an alert triggers.

  1. 1The alert triggers the playbookSeconds after the rule fires.
  2. 2Threat intel for every indicatorIP, domain and hash reputation.
  3. 3User contextRole and recent logins from the identity provider.
  4. 4Endpoint statusWhat the EDR says about the host.
  5. 5Case assembledThe analyst opens an alert with its context already attached.
This is the gathering half of SOAR, and it is almost always safe to automate: collecting context harms nothing.

Automate the gathering aggressively, the deciding cautiously

Orchestration and enrichment

A playbook queries threat intel, pulls user role and logins, checks EDR status, and assembles the case before a human looks. Almost always safe.

Automated response

Isolate an endpoint, disable an account, block an IP, sandbox a file. Real business risk: keep a human in the loop for consequential actions.

Automation amplifies whatever you point it at: a bad playbook automates a mistake at machine speed.

SOAR changes the job rather than removing it. The human reaches the judgment call sooner, which moves MTTR. Full automation is for narrow, high-confidence, low-blast-radius cases.

The silent precondition under every rule in this lesson.

UEBA: the anomaly nobody wrote a rule for

A fifth detection family: baseline normal, score the deviation.

HACKTHESOCLesson 05SIEM and alert triage72 / 80

How UEBA turns small deviations into one risk score

UEBA = User and Entity Behavior Analytics. It learns normal per entity, then scores deviation.

  1. 1Learn a baselineTypically 30 days: login hours, countries, file volume, servers, peer group.
  2. 2Score new activityEach event is compared with this entity's own history.
  3. 3Add small incrementsUnusual hour: a little. Unfamiliar destination: more. Huge downloads: more still.
  4. 4Cross the thresholdThe cumulative score surfaces as an alert, with the indicators that drove it.
This is how a patient attacker who never trips any single threshold can still surface over days or weeks.

Key takeaways

  1. 01Every alert ends a pipeline; an empty result may mean the source is not ingested or out of retention.
  2. 02Read the rule query and the alert object: entities, custom details, and the raw events behind the summary.
  3. 03Label authorized activity a benign true positive, and tune with the narrowest lever, not a disabled rule.

  5. 05Enrich with asset, user and intel context; escalate a concise package when the evidence warrants.
