Section 1 of 10

Two independent choices: placement and detection

Where the sensor sits and how it decides are separate questions that describe any deployment.

HACKTHESOCLesson 49IDS vs IPS6 / 62

Keep two questions separate

Where does it sit?

Out-of-band watching a copy, or inline on the real traffic. Placement decides whether it only alerts (IDS, intrusion detection system) or can also block (IPS, intrusion prevention system).

How does it decide?

Match known-bad patterns (signatures), flag deviations from a learned baseline (anomaly), or check traffic against a protocol's legal behaviour.

The same Suricata engine and rules run as an IDS from a SPAN port or as an IPS inline; only alert.action (allowed vs blocked) changes.

The two choices are independent and combine to describe any real IDS/IPS. The lesson takes placement first, then detection, then what you do with the alerts.
HACKTHESOCLesson 49IDS vs IPS7 / 62

Same engine, same rules: placement decides IDS or IPS

Follow one Suricata sensor through both deployments.

  1. 1Fed a copy from a SPAN portThe engine sees duplicated packets. The originals have already been forwarded to the server.
  2. 2Rule matches, it can only logThere is nothing to drop, so the EVE record says alert.action: allowed. That is an IDS.
  3. 3Placed inline insteadOn Linux through NFQUEUE, or AF_PACKET in inline mode: the real packets flow through the engine.
  4. 4Rule matches, it can stop the packetA drop rule discards it before it reaches the server, and the record says alert.action: blocked. That is an IPS.

Detection method (signature, anomaly, protocol) is a separate dial: any of them can run in either placement.

Students often think IDS and IPS are different products. Show that the only visible difference in the output is one field value, then move on to detection as the second, independent choice.

Section 2 of 10

Detection vs prevention

Out-of-band watches a copy and alerts; inline sits in the path and can block.

HACKTHESOCLesson 49IDS vs IPS9 / 62

The clean IDS vs IPS distinction

IDSIPS
PlacementOut-of-band (copy)Inline (in the path)
Primary actionAlert / logAlert and block/drop/reset
Effect on trafficNone (passive)Can stop packets in real time
Risk if it failsLoses visibility onlyCan disrupt legitimate traffic

An IDS is a security camera: it records and alarms but cannot lock the door. An IPS is the guard at the door.

Many products are the same engine in either mode. Detect or prevent comes down to deployment and configuration.
HACKTHESOCLesson 49IDS vs IPS10 / 62

Camera vs guard changes how you investigate

Investigate after the fact

IDS alert

The packet already passed when the alert fired. Your question is whether the attempt worked: check the target's response and the host itself.

  • Packet reached the target
  • Failure only costs visibility

Investigate and verify

IPS alert

The sensor may have acted. Your questions are what exactly it did to the connection, whether that worked, and whether earlier or later stages got through.

  • Packet may have been stopped
  • Failure can disrupt real traffic
This is the 'analyst posture' row of the lesson's table. A blocked alert is not a closed case: it contained one connection.
HACKTHESOCLesson 49IDS vs IPS11 / 62

Block is not one action (NIST SP 800-94)

ActionWhat the IPS doesEffect
DropSilently discards the packetsAttacker sees no response
Reject / resetSends TCP RST or ICMP unreachableConnection torn down, both sides know
Block / shunBlocks all traffic from the source for a timeStops follow-on attempts, not just this packet
Rate-limitThrottles rather than fully blockingBlunts floods and brute force
NormalizeStrips the malicious part, forwards the restE.g. removing an infected attachment

It can also reconfigure a firewall upstream, or run alert-only as a safe first setting.

This matters in triage: a drop leaves no connection to analyse, a reset leaves tell-tale RSTs, a shun means later attempts are missing entirely.
HACKTHESOCLesson 49IDS vs IPS12 / 62

Each action leaves different evidence behind

Knowing which response fired tells you what you will and will not find downstream.

Drop

No connection reaches the target, so there is nothing to analyse on the server or in its logs for that packet.

Reject / reset

Tell-tale TCP RST packets appear, for example in the firewall log, because the connection was actively torn down.

Block / shun

Later attempts from that source are missing entirely for the block period. Silence afterwards is the block, not a quiet attacker.

Alert-only

The packet was forwarded unchanged. Treat it exactly like an IDS alert: the target received it.

Ask students which of these explains 'the alert fired but the web server log has no matching request': a drop. Which explains RSTs in the firewall log: a reset.

Section 3 of 10

NIDS, HIDS, NIPS, HIPS, and EDR/NDR

The split that matters most is where the sensor gathers its evidence.

HACKTHESOCLesson 49IDS vs IPS14 / 62

Network-based vs host-based

Network (NIDS/NIPS)

NIDS/NIPS (network IDS/IPS): watches traffic crossing a segment, fed by a tap or SPAN, seeing every packet past a chokepoint regardless of host.

Host (HIDS/HIPS)

HIDS/HIPS (host IDS/IPS): an agent on one host watching file integrity, process creation, local logs and registry, things a network sensor cannot see.

NIST also names Network Behavior Analysis for traffic-flow anomalies like DDoS.

HIDS sees what happens after traffic is decrypted inside the OS, or a local privilege escalation that never touches the network. NIPS/HIPS are just the inline, blocking versions.
HACKTHESOCLesson 49IDS vs IPS15 / 62

Each family and its modern descendant

TypeSeesCannot seeDescendant
NIDSTraffic at a chokepointHost-internal, encrypted payloadsNDR
HIDSA host's processes, files, logsTraffic on segments it is not onEDR
NIPSSame as NIDS, plus blocks inlineSame as NIDSNext-gen firewall
HIPSSame as HIDS, plus blocks on hostSame as HIDSEDR with isolation

EDR = endpoint detection and response; NDR = network detection and response: the richer modern successors.

Ask which family an alert came from: a NIDS/NDR alert says what crossed the wire, not what the process did; a HIDS/EDR alert says what ran on the host, not traffic elsewhere. Strong IR pulls both together.
HACKTHESOCLesson 49IDS vs IPS16 / 62

Triage by family: what each alert can and cannot tell you

  1. 1Name the familyDid this come from a network sensor (NIDS/NDR) or a host agent (HIDS/EDR)? It sets the limits of the evidence.
  2. 2Network alert: what crossed the wireIt shows the connection and payload at a chokepoint, but not what the process did once the traffic landed.
  3. 3Host alert: what ranEDR shows process trees and command lines on that host, but nothing about segments the host never touched.
  4. 4Corroborate across bothPivot from a network alert to the host EDR, or from a host alert to network logs, so each confirms the other.
EDR is the tool most analysts live in daily; it is HIDS/HIPS grown up, with isolation as the 'guard at the door for one host'. NDR adds behavioural analytics on top of NIDS signatures.

Section 4 of 10

Signature-based vs anomaly-based detection

Independent of placement, two philosophies for deciding what is malicious.

HACKTHESOCLesson 49IDS vs IPS18 / 62

Known patterns vs learned normal

Signature-based

Matches traffic to a database of known attack patterns. Precise, explainable, low false positives for known threats. Misses novel or obfuscated attacks. Needs constant updates.

Anomaly-based

Builds a baseline of normal and flags deviations. Catches previously unseen attacks, at a higher false-positive rate because unusual is not the same as malicious.

A backup job or a new app rollout can trip an anomaly rule; it is rare, not malicious.

Good programs run both: signatures for cheap high-confidence detection of known bad, anomaly for the unknown signatures cannot see.
HACKTHESOCLesson 49IDS vs IPS19 / 62

Signature vs anomaly, side by side

Signature-basedAnomaly-based
Detects byMatching known patternsDeviation from a learned baseline
Catches novel attacks?No: only what someone wrote a rule forYes: no rule needed
False positivesLowerHigher: unusual is not malicious
Alert explainabilityHigh: a named rule and referenceLower: a statistical score
UpkeepConstant signature updates, like AV definitionsA baseline that must reflect current normal
The two are mirror images: each one's strength is the other's weakness, which is why good programs run both.
HACKTHESOCLesson 49IDS vs IPS20 / 62

What anomaly detection flags, and its benign look-alikes

Anomaly asks 'is this unusual for this network?', not 'is this a known attack?'.

  • Unexpected protocol on a portTraffic that does not fit what normally runs on that port. Could be tunnelling, or a newly deployed application.
  • Far more data than usualA host suddenly sending much more than its baseline. Could be exfiltration, or a legitimate backup job.
  • Spike in connectionsA burst well above normal. Could be scanning or a flood, or a new application rollout talking to many peers.

Each needs the host's baseline and a benign explanation ruled out before it becomes an incident.

The examples and benign causes come straight from the lesson. Make students say the benign hypothesis out loud before the malicious one.
HACKTHESOCLesson 49IDS vs IPS21 / 62
The detection type shapes how you triage.

A signature alert hands you a named rule: confirm the match was real. An anomaly alert hands you a statistical outlier: establish what normal looks like for that host.

Start a signature alert by checking a benign string did not happen to fit the pattern. Start an anomaly alert by finding the baseline and any benign explanation.

Section 5 of 10

A third method: stateful protocol analysis

NIST SP 800-94 names a third methodology every serious IDPS relies on.

HACKTHESOCLesson 49IDS vs IPS23 / 62
Many protocols have a state machine: legal steps that must happen in order.

TCP must complete SYN, SYN-ACK, ACK before data; FTP opens a data channel only after specific commands. The engine flags illegal sequences.

Example: an FTP client sending data-channel commands before authenticating. It tracks states using protocol profiles, not local history.
HACKTHESOCLesson 49IDS vs IPS24 / 62

How a stateful engine follows a session

  1. 1Load a protocol profileVendor or standards-based profiles describe which commands are legal at each stage of a protocol.
  2. 2Track the current stateHas TCP completed SYN, SYN-ACK, ACK? Has the FTP client authenticated on the control channel?
  3. 3Check each transitionEvery new command or packet is compared with what the profile allows from the current state.
  4. 4Flag illegal sequencesA step that fits no legitimate transition raises an alert, even if the packet itself is well formed.
No local baseline is needed here, only the specification of the protocol. That is the key difference from anomaly detection.
HACKTHESOCLesson 49IDS vs IPS25 / 62

Legal vs illegal: the same commands in a different order

Legal FTP session

Client opens the control channel, authenticates, then issues the commands that open a separate data channel.

  • Order matches the protocol
  • No alert

Illegal sequence

Client sends data-channel commands before ever authenticating. Each packet is valid on its own; the order is not.

  • Content looks normal
  • Rate looks normal
  • Sequence violates the protocol

Another example from the lesson: a client trying to renegotiate TLS in a way no legitimate implementation would.

This is the case content matching and volume anomaly both miss: nothing about the bytes or the rate is wrong, only the sequence.
HACKTHESOCLesson 49IDS vs IPS26 / 62

How the three methods differ

SignatureAnomalyStateful protocol
QuestionKnown bad pattern?Unusual for this network?Obeys the protocol's rules?
Needs a local baseline?NoYesNo, needs a spec
CatchesKnown attacksStatistical outliersProtocol-logic violations
WeaknessMisses unknownsMore false positivesResource-intensive
It catches a well-formed single packet whose sequence is illegal, which content matching and volume anomaly both miss. Real Snort/Suricata run all three layered.

Reading a real signature rule

Signature detection is easiest to understand by reading an actual Snort/Suricata rule.

HACKTHESOCLesson 49IDS vs IPS28 / 62

A simplified EternalBlue rule

  • alert is the action; an IPS rule might say drop instead
  • -> $HOME_NET 445 matches TCP to our net on the SMB (Server Message Block) port
  • content |FF|SMB are literal header bytes; |..| is hex, quotes wrap text
The content is simplified: |FF|SMB is the genuine SMB1 header literal, the second is a placeholder. msg is the queue text; reference ties it to the CVE behind EternalBlue/WannaCry; sid and rev track which rule version fired.
HACKTHESOCLesson 49IDS vs IPS29 / 62

Reading the rule, part by part

HACKTHESOCLesson 49IDS vs IPS30 / 62
The msg, content and reference fields are your starting context: exactly what matched and why.

The explainable, low-false-positive property signatures are praised for: a named rule, a matched pattern, a CVE (Common Vulnerabilities and Exposures) reference, not just a deviation score.

Treat the rule as a lead to check, not a black box. This illustrates the trade-off between the two detection philosophies.
HACKTHESOCLesson 49IDS vs IPS31 / 62

Keywords that change what a match means

  • flowbits builds multi-stage detections: download first, callback later
  • A flowbits alert depends on an earlier packet you must also pull
  • detection_filter turns one failed-login pattern into brute-force detection
Also mention pcre: a regex for what content cannot express. Engines run the cheap content match first, so good rules always pair a pcre with a content anchor.
HACKTHESOCLesson 49IDS vs IPS32 / 62

The first word of a rule: four actions

alert

Log an alert and let the packet go. The only action an out-of-band IDS can really carry out.

pass

Stop inspecting this traffic. Used for known-good exceptions, so a pass rule can hide traffic from other rules.

drop

IPS mode: discard the packet and alert. On an IDS-mode sensor a drop rule just alerts, because there is nothing to drop.

reject

Send a TCP reset or ICMP unreachable so the connection is torn down, which leaves RSTs in other logs.

When a rule you expected to fire is silent, check for a pass rule covering that traffic. When you read a drop rule's alert, check the sensor's mode before assuming anything was blocked.

You see Suricata's EVE (Extensible Event) JSON record, not the rule; flow_id is your pivot key.

HACKTHESOCLesson 49IDS vs IPS34 / 62

Rejected attempt or a host to examine?

A few hundred bytes to the client and a 400 or 403 in the http record. A true positive for the attempt, but nothing was returned.

  • Here: 403, 199-byte body
  • Still check server version

A large response and a 200 status. The request may have returned what it asked for: move to the host and escalate.

  • Large bytes_toclient

The verdict for the example is 'true positive, attempt failed'. That is a precise finding, not a dismissal.
HACKTHESOCLesson 49IDS vs IPS38 / 62

Getting the packets, in order of convenience

An alert is a claim about packets. Confirming it ideally means looking at them.

  1. 1Payload in the alert itselfWith payload or packet logging on, the EVE record carries the matched packet in base64 plus a printable form.
  2. 2Suricata's own captureWith pcap-log enabled, filter the rolling PCAP files by the alert's 5-tuple and timestamp.
  3. 3Full packet capture platformArkime indexes sessions: retrieve one by IPs, ports, time or community_id, then open it in Wireshark.
  4. 4None of these?You are left with metadata, and your verdict should say so explicitly.
Students should write 'verdict based on metadata only' when no packets exist. It tells the next reader how much weight the conclusion carries.
HACKTHESOCLesson 49IDS vs IPS39 / 62

The encryption blind spot: what a sensor still sees in TLS

Hidden without decryption

The HTTP inside TLS: URLs, headers, bodies. Content rules against them simply never fire on HTTPS.

  • URL and body content rules
  • File content in the session

Still visible: the handshake

Rules can match these directly, which is how sensors catch known malware families and self-signed C2 certificates.

  • tls.sni: the requested hostname
  • Cert subject, issuer, validity
  • JA3/JA3S, and JA4 in recent Suricata

Seeing the payload needs TLS inspection at a proxy or NGFW, usually limited by policy (banking and health sites are often excluded).

A quiet HTTPS sensor is expected, not reassuring. Ask whether the segment sits behind TLS inspection before reading anything into silence.

Section 8 of 10

Placement, taps, and SPAN

Where you put the sensor determines what it sees, and how you feed it differs by mode.

HACKTHESOCLesson 49IDS vs IPS41 / 62

Two ways to feed an out-of-band IDS

Network tap

A hardware device in the link that passively duplicates every packet to a monitoring port. Reliable, no drops under load. The preferred feed.

SPAN / mirror port

SPAN (Switched Port Analyzer): a switch feature copying selected ports or VLANs to a mirror port. Cheap and flexible, but can drop mirrored packets under heavy load.

The IDS analyses a duplicate and never touches the originals, which is exactly why it cannot block.

An IPS, by contrast, is spliced directly into the link: the real traffic passes through it, so it can drop packets.
HACKTHESOCLesson 49IDS vs IPS42 / 62

Tap, SPAN, inline: how each sensor gets its traffic

FeedWhat the sensor receivesWeak pointCan it block?
Network tapA passive duplicate of every packetHardware must be inserted in the linkNo: it sees a copy
SPAN / mirror portCopies of chosen ports or VLANsDrops mirrored packets under loadNo: it sees a copy
InlineThe real traffic, passing through itLatency and a point of failureYes: it is on the path
If an IDS fed by SPAN missed something during a traffic peak, the feed itself is a possible cause. SPAN may also not capture certain error frames.
HACKTHESOCLesson 49IDS vs IPS43 / 62
Inline sensors go at chokepoints: the perimeter, and the crossings between trust zones.

The most valuable locations are the boundaries you already care about, where an attacker's traffic must pass and one sensor sees the most.

Internal boundaries (user VLAN to server/DMZ) watch east-west lateral movement. A perimeter sensor firing inbound tells a different story than an internal one firing on a workstation reaching a server subnet.
HACKTHESOCLesson 49IDS vs IPS44 / 62

Read the sensor's vantage point as part of the alert

Perimeter sensor, inbound

Internet traffic arriving at the edge. Usually an external source probing or attacking an exposed service.

  • Where ingress and egress converge
  • Often inline with the edge firewall

Internal boundary sensor

A workstation reaching into a server subnet or DMZ. East-west traffic that may mean lateral movement from an internal foothold.

  • User VLAN to server/DMZ
  • In front of sensitive assets
The same signature means different things from these two sensors. An internal hit implies something inside is already behaving badly.

Section 9 of 10

Fail-open vs fail-closed, and evasion

What happens when the sensor breaks, and how attackers sneak past a healthy one.

HACKTHESOCLesson 49IDS vs IPS46 / 62

If an inline IPS dies

Fail-open

Traffic keeps flowing unfiltered. Preserves availability at the cost of all inspection during the outage. Common at internet-facing chokepoints.

Fail-closed

Drops all traffic rather than pass it uninspected. Preserves security at the cost of availability. Chosen for highly sensitive segments.

Know which mode is configured: a sensor going quiet means the network is wide open, or that it went dark.

Most internet-facing IPS choose fail-open with redundant sensors and fast alerting so the gap is brief and visible.
HACKTHESOCLesson 49IDS vs IPS47 / 62
When an inline sensor goes quiet, first ask which failure mode it is configured for.

Fail-open: traffic is flowing with no inspection, so the network is temporarily wide open. Fail-closed: traffic is stopped, so the business just went dark.

Production internet-facing IPS mostly fail open, with redundant sensors and fast health alerting so the gap is short and visible.
HACKTHESOCLesson 49IDS vs IPS48 / 62

How fragmentation evasion works

  1. 1Payload split into piecesThe attack is spread over many small IP fragments or TCP segments, sometimes overlapping or out of order.
  2. 2Two reassembliesOperating systems handle overlapping fragments differently, so the sensor and the host can rebuild different streams.
  3. 3The mismatchThe sensor sees something benign while the host builds the real attack, or the sensor wastes effort on data the host discards.
  4. 4The defenceSerious engines do protocol-aware reassembly and normalization before matching, instead of inspecting raw fragments.
Formalised in Ptacek and Newsham's 1998 paper on insertion and evasion. The analyst-level takeaway is in the next slide.
HACKTHESOCLesson 49IDS vs IPS49 / 62

Two evasion families, one analyst rule

Fragmentation

Split the payload across small, overlapping or reordered fragments. If the sensor reassembles differently than the host, it sees benign while the host builds the real attack.

Encoding

URL encoding, Unicode, or XOR-encoded shellcode so the malicious bytes never appear in the form a signature expects, but execute once decoded.

First described in Ptacek and Newsham, 1998. Serious engines reassemble and normalize before matching.

The lesson for an analyst: a clean sensor log does not always mean clean traffic. Corroborate NIDS/IPS silence with host-based evidence when stakes are high.

Section 10 of 10

False positives, tuning, and working alerts

A sensor is only as useful as its tuning, where analyst judgment meets engineering.

HACKTHESOCLesson 49IDS vs IPS51 / 62

A disciplined alert workflow

  1. 1Read the ruleWhat fired, and what is it meant to detect? Name, ID and reference are your context.
  2. 2Confirm true positiveExamine the traffic. Did the pattern indicate an attack, or did benign data just match?
  3. 3Establish contextWhich host, sensor, direction, reputation? Pivot to firewall, DNS and endpoint logs.
  4. 4For IPS, verify the blockConfirm the drop succeeded. A block is containment of one connection, not a solved threat.
  5. 5Feed tuning backReport recurring false positives; a confirmed true positive may justify a tighter rule.
A fresh sensor with default rules is noisy. On an IPS a false positive blocks legitimate business traffic, which is why blocking rules often run alert-only first. Tuning is never set-and-forget.
HACKTHESOCLesson 49IDS vs IPS52 / 62

Where the rules come from

Most SOCs subscribe to rulesets and tune on top, rather than writing most signatures.

A 30-day delay matters: a Registered-tier Snort sensor will not have rules for last week's vulnerability.
HACKTHESOCLesson 49IDS vs IPS53 / 62

Tuning lives in small policy files

Disable everywhere, suppress for one host, or rate-limit the alert.

A bare SID on its own line in disable.conf disables one rule. modify.conf or drop.conf change a rule's action. Each entry should have a recorded reason.
HACKTHESOCLesson 49IDS vs IPS54 / 62

The tuning toolkit, bluntest to most precise

Most SOCs subscribe to rulesets (ET Open, ET Pro, Snort Talos) and tune on top.

  • Disable a SIDA line in disable.conf drops a rule everywhere. Use only for rules that can never matter in your environment.
  • Suppress for one hostthreshold.config suppress keeps the rule alive for everyone else, silencing it only for a known-good source like a scanner.
  • Rate-limit the alertthreshold type limit keeps the first alert per source per hour, so a chatty but real detection does not flood the queue.
  • Change the action or rewritePromote a clean alert rule to drop, demote a misfiring drop back to alert, or tighten the content/flow logic locally.

Record why each suppression exists and review it: a suppressed IP later reassigned to a workstation is a blind spot you created.

suricata-update merges the daily ruleset refresh with your local policy files, so tuning survives the update instead of being overwritten.

The four detection outcomes

OutcomeSensor saidRealityConsequence
True positiveMaliciousMaliciousThe win: a real threat caught
False positiveMaliciousBenignWasted time; on IPS, blocked good traffic

Precision is hurt by false positives; recall/detection rate is hurt by false negatives.

Loosening a rule cuts false positives but risks false negatives; tightening does the reverse. The false negative is most dangerous because nobody is alerted, which is why host EDR corroboration matters.
HACKTHESOCLesson 49IDS vs IPS56 / 62

Every tuning change trades one error for another

Loosen or suppress

Fewer false positives and less alert fatigue, but more risk of a false negative: a real attack that raises nothing.

  • Helps precision
  • Hurts recall

Tighten or add rules

More real attacks caught, but more benign matches to work, and on an IPS more legitimate traffic blocked.

  • Helps recall
  • Hurts precision

That is why blocking rules run alert-only first, and why host EDR is the safety net for network false negatives.

Key takeaways

  1. 01An IDS is out-of-band (tap or SPAN), only alerts, never touches traffic; an IPS is inline and can block in real time.
  2. 02Signatures catch known threats explainably; anomaly detection catches the unknown at the cost of false positives.
  3. 03A signature rule names its match pattern, a CVE and a sid: read those fields, do not treat the alert as a black box.
  4. 04NIDS/NDR see the wire, HIDS/EDR see the host; triage each differently and corroborate across both.
  5. 05Stateful protocol analysis catches illegal command sequences neither signatures nor anomaly detection are built to see.
  6. 06Fresh sensors are noisy; tuning and alert-only-first keep an IPS from blocking legitimate business traffic.
