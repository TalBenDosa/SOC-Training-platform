SSO and federation in plain terms: IdP, SP and trust

The vocabulary, how trust is established, and why the SP only believes what it is told.

HACKTHESOCLesson 128Federation, SAML and SSO6 / 48

Six terms every federation discussion uses

TermMeaningExample
Identity provider (IdP)Authenticates the user and issues the signed statementAD FS, Microsoft Entra ID, Okta
Service provider (SP)Consumes the statement and grants access; also a relying partyMicrosoft 365, Salesforce, ServiceNow
Assertion or tokenThe signed statement about the userA SAML assertion in XML
Claim or attributeOne fact inside the statementUPN, group, role, authentication method
MetadataXML describing endpoints, bindings, certificatesThe AD FS federation metadata document
TrustEach side accepts the other's certificate and endpointsA relying party trust in AD FS

One product can play both roles: for a federated Microsoft 365 user, Entra is the SP and AD FS is the IdP.

SSO means the user proves who they are once. Federation makes that work across boundaries because the application never holds the password.
HACKTHESOCLesson 128Federation, SAML and SSO7 / 48

Trust is one exchange of metadata and one private key

The SP learns the IdP's sign-in URL, issuer name and public token-signing certificate.

  • What the SP checksOnly the signature, the timing and the audience. It never asks the IdP if an assertion is genuine.
  • Everything rests onOne private key, held by the IdP.
  • Why federateOne place for password rules, lockout and MFA; fewer passwords; reuse of AD FS; fast offboarding.
  • Analyst questionWhich system authenticated this user, which holds the signing key, and what did the SP simply believe?

The SP's log records what it was told, not what really happened. That gap is where federation attacks live.

Offboarding works because disabling one account removes access at the next sign-in. The same single point is also the single point of failure.

The SAML 2.0 flow: SP-initiated and IdP-initiated

The browser is the courier, and each message rides a binding.

HACKTHESOCLesson 128Federation, SAML and SSO9 / 48

Two common bindings carry the messages

A binding is the rule for how a message is encoded into an HTTP request.

BindingHow the message travelsTypical use
HTTP RedirectDeflated and encoded into the URL query string as SAMLRequestAuthnRequest from SP to IdP
HTTP POSTBase64 in an auto-submitting HTML form field named SAMLResponseResponse and assertion from IdP to SP, carries the signature

A third binding, HTTP Artifact, sends a small reference and resolves it over a back channel. It is rarer.

SAML 2.0 is an OASIS standard. The SP and IdP rarely talk to each other directly; every message passes through the user's browser.
HACKTHESOCLesson 128Federation, SAML and SSO10 / 48

SP-initiated flow, the usual one, in five steps

  1. 1User opens a protected URLThe user has no session at the SP.
  2. 2SP sends an AuthnRequestID, issuer and ACS address; the browser goes to the IdP, RelayState keeps the URL.
  3. 3IdP authenticates the userIf there is no IdP session: password, MFA, Kerberos, smart card.
  4. 4IdP returns a signed ResponseAuto-submitting POST to the ACS URL; InResponseTo echoes the AuthnRequest ID.
  5. 5SP validates and opens a sessionChecks signature, time window, audience, InResponseTo, then sets its own cookie.
ACS is the Assertion Consumer Service, the address where the SP wants the answer. After step 5 the SP uses its own cookie, so a short assertion lifetime does not end a long session.
HACKTHESOCLesson 128Federation, SAML and SSO11 / 48

A request and its trace

The first request goes to the IdP, the second delivers the answer to the SP.

In a proxy or browser trace you can decode the SAMLResponse value from Base64 to read the assertion.
HACKTHESOCLesson 128Federation, SAML and SSO12 / 48

SP-initiated versus IdP-initiated

Request first

SP-initiated

The SP built an AuthnRequest, so it can check that InResponseTo matches a request it really sent.

    Unsolicited Response

    IdP-initiated

    The user clicks a tile at the IdP portal. No AuthnRequest exists, so the SP cannot check InResponseTo.

    • Many security teams prefer SP-initiated

    Ask: was this sign-in SP-initiated or IdP-initiated, and does the logged InResponseTo match a real request?

    Microsoft detail: Entra ID ignores the Conditions element in an incoming AuthnRequest and can be set to require signed requests (isSignedAuthenticationRequestRequired).

    Anatomy of a SAML assertion

    Six elements, what each states, and what the analyst checks.

    HACKTHESOCLesson 128Federation, SAML and SSO14 / 48

    The elements, in the order you meet them

    ElementWhat it statesWhat the analyst checks
    IssuerWhich IdP created the assertionIs it the IdP the SP expects? An unknown issuer is a red flag
    SignatureXML Signature made with the token-signing private keyVerifies against the trusted certificate; says nothing about who requested it
    Subject and NameIDThe user, plus SubjectConfirmation with Recipient, InResponseTo, expiryWhich identifier format: UPN, email, opaque value?
    ConditionsNotBefore, NotOnOrAfter and an AudienceRestrictionWindow length: hours or days is unusual
    AuthnStatementAuthnInstant, SessionIndex, AuthnContextClassRefDoes AuthnInstant make sense relative to the sign-in time?
    AttributeStatementClaims: UPN, ImmutableID, groups, roles, MFA indicatorsDo roles and identifiers match the real account?
    Investigations often hand you a decoded assertion or the claims extracted from one. Every element is defined in the SAML 2.0 core specification.
    HACKTHESOCLesson 128Federation, SAML and SSO15 / 48

    A sanitised assertion, trimmed to what teaches

    Subject and the ImmutableID attribute are omitted here to fit the slide. Ask students to find the window, the audience and the MFA claim before you move on.
    HACKTHESOCLesson 128Federation, SAML and SSO16 / 48

    Reading it: window, audience, ImmutableID, MFA, bearer

    • WindowNotOnOrAfter is 60 minutes after NotBefore, the common default. A 24-hour window or odd seconds is a forgery hint.
    • Audienceurn:federation:MicrosoftOnline is the Microsoft 365 value. An assertion for another audience must be refused.
    • ImmutableIDTies the assertion to one cloud account; must match what Entra Connect stored. A forger needs it for the target.
    • MFA claimmultipleauthn is the IdP's statement that MFA happened. The SP cannot verify it, only believe it.
    • BearerWhoever presents the assertion is treated as the user, so a signature and a clock are the only defences.
    One hour is the baseline that MITRE and CISA both treat as normal.

    Section 4 of 9

    How the SP validates, and why the signing cert matters

    The checklist shows what a forger must satisfy and what they can ignore.

    HACKTHESOCLesson 128Federation, SAML and SSO18 / 48

    Six checks, and none asks if the user really authenticated

    1. 1SignatureMust verify with the public key of the trusted token-signing certificate.
    2. 2IssuerMust match the configured IdP.
    3. 3AudienceMust name this SP.
    4. 4Time windowNow is between NotBefore and NotOnOrAfter; SubjectConfirmationData not expired.
    5. 5Recipient and InResponseToAddressed to this ACS; in SP-initiated flows it answers a request the SP made.
    6. 6ReplayA good SP remembers assertion IDs and refuses repeats.

    If the signing key leaks, an attacker satisfies every check with a document they wrote themselves.

    That the user really authenticated exists only in the IdP's own logs. This is why the analyst must look at the IdP side.
    HACKTHESOCLesson 128Federation, SAML and SSO19 / 48

    The token-signing certificate and its rollover

    An X.509 certificate whose private key signs assertions. AD FS creates one by default, self-signed.

    PropertyBehaviour
    Public part published at/federationmetadata/2007-06/federationmetadata.xml, read by Entra
    Rollover in EntraTries to fetch a new certificate 30 days before expiry, then checks the metadata daily
    Stored in Entra assigningCertificate and nextSigningCertificate, base64 of the public part
    Private key in AD FSProtected by DKM, the Distributed Key Manager
    Optional hardeningKeep the signing key in a hardware security module (HSM)
    AD FS generates a new certificate automatically before the old one expires. Ask: has anyone exported or replaced it recently?
    HACKTHESOCLesson 128Federation, SAML and SSO20 / 48

    DKM: the lock and the key sit in the same place

    The private key

    The encrypted token-signing key lives in the AD FS configuration database.

      The protecting key

      A symmetric key kept in the DKM container in Active Directory.

        Who can read it

        The AD FS service account, domain admins, and an attacker holding either can decrypt the signing key from a copy of the database.

          Microsoft calls AD FS "the LSASS for the cloud" and recommends dropping the federated trust for Microsoft 365 where possible.

          Ask where the organisation keeps its signing key: software, DKM or an HSM. A stolen signing certificate lets its holder impersonate any federated user.

          Section 5 of 9

          AD FS and Entra ID: managed vs federated domains

          The authentication type of a domain decides who checks the password.

          HACKTHESOCLesson 128Federation, SAML and SSO22 / 48

          Managed or federated: who validates the password

          Password hash synchronization

          Managed: PHS

          Entra Connect copies a hash of the on-premises hash; Entra validates the password. Simplest, and feeds the leaked-credentials report.

            Pass-through authentication

            Managed: PTA

            Entra passes credentials to an on-premises agent that validates against AD. Disabled account and sign-in hours apply each time.

              Entra stops validating

              Federated

              Entra redirects the browser to the federation service such as AD FS, receives a signed token and accepts it.

                Microsoft advises enabling password hash synchronization as a backup even under federation, so an on-premises outage does not lock everyone out.
                HACKTHESOCLesson 128Federation, SAML and SSO23 / 48

                What each model trusts, and what a key theft means

                QuestionManaged (PHS or PTA)Federated (AD FS)
                Who validates the passwordEntra ID or its PTA agentThe on-premises IdP
                What Entra trustsIts own validationA signed token from the IdP
                On-premises dependencyNone for PHS, agents for PTAAD FS farm plus Web Application Proxy
                Signing-key theft meansNot applicableForged token for any federated user
                Typical reasonSimplicity, resilienceThird-party MFA, smart cards, existing AD FS
                The row to dwell on is the fourth: under federation Entra accepts the token purely on signature.
                HACKTHESOCLesson 128Federation, SAML and SSO24 / 48

                What a conversion changes, and where OIDC fits

                • Federation configurationissuerUri, passiveSignInUri, metadataExchangeUri, signingCertificate, preferredAuthenticationProtocol.
                • Reading and changing itRead via the Graph internalDomainFederation resource. Changing needs Global Administrator or Domain Name Administrator.
                • OpenID ConnectBuilt on OAuth 2.0; the IdP returns a signed JWT ID token. SAML signs XML, OIDC signs a JWT, both accepted on signature.

                Section 6 of 9

                Where MFA is enforced: claims and federatedIdpMfaBehavior

                Does Entra believe a claim that says MFA already happened?

                HACKTHESOCLesson 128Federation, SAML and SSO26 / 48

                The MFA claim travels inside the assertion

                • The claimauthnmethodsreferences with value http://schemas.microsoft.com/claims/multipleauthn.
                • What Entra doesIf allowed, treats the Conditional Access MFA requirement as satisfied.
                • In the sign-in logAn authentication step met by a token claim, not a prompt shown by Entra.
                • supportsMfaOlder setting: a single yes or no on whether the IdP's MFA is honoured.
                • federatedIdpMfaBehaviorNewer, on internalDomainFederation. When set, Entra ignores supportsMfa; if neither is set, accept is used.
                With a managed domain Entra runs the MFA prompt. With a federated domain it can happen at the on-premises IdP or in Entra.
                HACKTHESOCLesson 128Federation, SAML and SSO27 / 48

                Three behaviours of federatedIdpMfaBehavior

                ValueBehaviour
                acceptIfMfaDoneByFederatedIdpAccept MFA from the IdP; if the IdP did not do MFA, Entra performs it
                enforceMfaByFederatedIdpAccept MFA from the IdP; if it did not, send the user back to the IdP
                rejectMfaByFederatedIdpAlways perform Entra MFA and ignore any MFA claim from the IdP

                The default accepts the IdP's word.

                Microsoft's AD FS hardening guidance highly recommends reject unless a third-party MFA provider handles MFA for federated users.
                HACKTHESOCLesson 128Federation, SAML and SSO28 / 48

                Reading the setting for a federated domain

                An analyst reading this knows an MFA claim from sts.contoso.example is accepted as is.

                Ask: what is federatedIdpMfaBehavior for each federated domain, and has it changed recently? Does Conditional Access require MFA for admin roles, and is it met by Entra or by a claim?
                HACKTHESOCLesson 128Federation, SAML and SSO29 / 48
                With rejectMfaByFederatedIdp, even a perfectly forged assertion still meets an Entra MFA prompt that a forger cannot answer.

                The most important mitigation for the MFA-bypass part of Golden SAML. A cloud-only Global Administrator cannot be impersonated through a forged AD FS token.

                A forged claim never involves the user at all. Phishing of the MFA step and AiTM session theft are separate lessons.

                What the analyst sees in the logs

                AD FS, Entra sign-in and Entra audit: learn what each one proves.

                HACKTHESOCLesson 128Federation, SAML and SSO31 / 48

                AD FS audit events that record each step

                Event IDMeaning
                1202Fresh credential validation succeeded (user just typed credentials)
                1203Fresh credential validation failed
                1200App token issued; for SAML-P and WS-Fed, logged when an SSO artifact (SSO cookie) was used
                1201Application token issuance failed
                1204 / 1205Password change succeeded or failed
                1206 / 1207Sign-out succeeded or failed

                Only if auditing is on: default Basic; None, Basic, Verbose via Set-AdfsProperties -AuditLevel. Check Get-AdfsProperties.

                The Security log also needs the Application Generated audit subcategory and Success and Failure ticked in Federation Service properties. A silent log may mean a silent server or auditing never configured. Events of one request share an Activity ID.
                HACKTHESOCLesson 128Federation, SAML and SSO32 / 48

                Entra SigninLogs fields that show who vouched

                • TokenIssuerTypeAzureAD or ADFederationServices; the latter means a federated IdP vouched; TokenIssuerName names the IdP
                • IncomingTokenTypeFor example a saml assertion or a primary refresh token
                • AuthenticationProtocolsaml20, wsFederation and others
                • AuthenticationProcessingDetailsIncludes server or farm name for federated authentication
                • AuthenticationDetailsPer step result; a step met by a claim rather than a prompt
                • AuthenticationRequirementHighest level needed; do not rely on it alone, it ignores earlier MFA claims

                Join keys and context: CorrelationId, IPAddress, UserPrincipalName.

                For a federated user the log shows the sign-in the cloud service saw, not what the IdP did.
                HACKTHESOCLesson 128Federation, SAML and SSO33 / 48

                Alerting on federation changes in Entra audit logs

                Category DirectoryManagement. Microsoft publishes a query matching the first two activity names.

                Other activity names: Add verified domain, Add unverified domain, Verify domain. Such changes are rare in a stable tenant, so match every hit to a change ticket.

                Every federated cloud sign-in should have a matching issuance on the IdP.

                A 1200 or 1202 for the same user at nearly the same time, from the same client IP the proxy recorded. A sign-in with no partner event is the gap forgery produces.

                This correlation is the backbone of the worked investigation in section 9.

                Section 8 of 9

                Attacks on federation: Golden SAML and trust modification

                Two techniques attack the trust itself rather than the user.

                HACKTHESOCLesson 128Federation, SAML and SSO36 / 48

                Two techniques that target the trust, not the user

                MITRE T1606.002

                Golden SAML

                Holding a valid token-signing certificate, the adversary forges tokens with any claims and lifetime. They never existed on the IdP.

                • Named by CyberArk researchers in 2017
                • Needs privileged access to AD FS first
                • SolarWinds: CISA advisory AA20-352A

                MITRE T1484.002

                Trust modification

                Add or change a trust so an attacker's IdP is accepted.

                • AADInternals converting a domain to federated
                • SolarWinds actor trusting its own certificate
                • Storm-0501: new federated domain via Global Admin
                • Scattered Spider: added IdP to an SSO tenant

                Two paths to the same end: extract the signing certificate, or change the trust to one the attacker controls.

                CISA reports the actor compromised the SAML signing certificate with escalated AD privileges and used valid tokens against cloud mail and file storage.
                HACKTHESOCLesson 128Federation, SAML and SSO37 / 48

                Detection ideas and where each comes from

                IdeaSignalSource
                Sign-in with no IdP issuanceSAML sign-in in Entra with no 1200 or 1202 and no Kerberos 4769MITRE DET0148
                Abnormal tokenLifetime over one hour, issuer or claim mismatch, missing MFA claimCISA AA20-352A
                Federation changeSet federation settings on domain, Set domain authenticationMicrosoft, MITRE DET0458
                DKM accessAccess requests to the AD FS DKM container in ADMandiant hardening paper
                Key extraction on the hostMicrosoft.IdentityServer.ServiceHost.exe spawning werfault.exe or csc.exeMicrosoft Security blog
                New federated domainAdd domain events followed by federation settingsMandiant, MITRE

                Event 4662 behind DKM detections appears only if a SACL is set on the container.

                A SACL is a system access control list, an auditing rule. Defender alerts such as AD FS private key extraction attempt also belong in this list.
                HACKTHESOCLesson 128Federation, SAML and SSO38 / 48

                Response and prevention for suspected forgery

                • Rotate twiceRotate the token-signing certificate twice in quick succession to invalidate tokens signed with the old ones (M1015).
                • Rebuild AD FSIsolate and rebuild the AD FS servers; restrict AD FS administration to privileged workstations.
                • Consider an HSMKeep the signing key in hardware.
                • Treat the trust as compromisedPer CISA, fixing single accounts will not be enough.
                The campaign most defenders know is SolarWinds, attributed by CISA to a Russian state actor.

                Worked investigation: night-time Global Admin sign-in

                At 02:14 UTC a Global Administrator signs in with MFA shown as satisfied, from a hosting IP.

                HACKTHESOCLesson 128Federation, SAML and SSO40 / 48

                The artifact: SIEM alert on a privileged sign-in

                Rule: Privileged role sign-in outside business hours.

                Work in order; each step either narrows the case or closes it. Do not conclude from the cloud log alone.
                HACKTHESOCLesson 128Federation, SAML and SSO41 / 48

                Five steps from the alert to a verdict

                1. 11. Domain and account typeCloud-only on managed: federated token refused. Synced on federated: forgery possible.
                2. 22. Partner event on the IdPSearch AD FS for 1202 or 1200 for the UPN. First confirm auditing was on.
                3. 33. On-premises activityDCs for 4768, 4769, 4624. None plus no issuance: no one used the front door.
                4. 44. Inspect the assertionA 24-hour window, no matching AuthnInstant, or an MFA claim without registered MFA.
                5. 55. What came nextFederation changes, new domains, SP credentials, role assignments, then DKM access on AD FS.
                In step 1 note federatedIdpMfaBehavior. In step 5 also look for mailbox access, key extraction alerts, new certificates and unusual child processes of the AD FS service.

                Decision table: what each observation points to

                ObservationPoints to
                1202 or 1200 for same UPN, same IP, plausible AuthnInstantReal sign-in via AD FS: account or MFA compromised; treat as account takeover

                Key takeaways

                1. 01The SP checks only signature, issuer, audience, time and replay, so whoever holds the signing key can forge any assertion.
                2. 02The SP's log shows what the IdP claimed, not what happened; always look for the matching 1200 or 1202 on the IdP.
                3. 03Set federatedIdpMfaBehavior to rejectMfaByFederatedIdp so a forged multipleauthn claim still meets an Entra MFA prompt.
                4. 04Golden SAML (T1606.002) and trust modification (T1484.002) attack the trust; watch federation changes and DKM access.
                5. 05A cloud sign-in with no IdP event is a forgery clue only when AD FS auditing is confirmed on.

                Check your understanding, question 1 of 3

                A federated Global Administrator signs in to Entra with MFA satisfied by a token claim. The AD FS Security log has no 1200 or 1202 for that user nearby, and auditing is on. Best interpretation?

                With auditing on, a real federated sign-in leaves a 1200 or 1202 on the IdP, so no partner event matches the forged-assertion pattern (T1606.002). Entra logs what the IdP claimed, and a cached session would still produce a 1200.

                Check your understanding, question 2 of 3

                An organisation wants Entra ID to always run its own MFA for federated users, even when the assertion carries a multipleauthn claim. Which configuration achieves this?

                Reject makes Entra perform its own MFA and ignore any IdP MFA claim, so a forged claim no longer helps. Accept and enforce both honour the claim, and leaving both unset defaults to accept.

                How does a service provider decide whether to accept a SAML assertion, and what does that imply for defenders?

                The SP only validates the document against the trusted certificate, issuer, audience and timing and never calls back to the IdP, so anyone holding the private signing key can write an assertion that passes every check.
