FTP is a loading dock between two warehouses, built before anyone worried about thieves.

One job, moving files in bulk in both directions. Simple, still common on older systems, and dangerously insecure in its classic form.

Two reasons an analyst cares: it is a hygiene concern, and its purpose matches exactly what an attacker wants to do with your data.

Section 1 of 8

What FTP is and why it exists

File Transfer Protocol: one of the internet's original protocols, older than the web.

HACKTHESOCLesson 86FTP explained6 / 48

Where FTP still shows up and how it is used

  • WhereLegacy systems, some website management, automated business transfers, older internal tools.
  • HowA dedicated client or command-line ftp, username and password, then put (upload) and get (download).
  • Anonymous FTPAnyone connects with a generic 'anonymous' login. Convenient for public downloads, but access without real authentication.
Understanding FTP is partly recognising a legacy protocol that should often be replaced, and partly knowing why outbound FTP deserves a second look.
HACKTHESOCLesson 86FTP explained7 / 48

One FTP session, start to finish

  1. 1ConnectThe client opens the control channel to the server on TCP port 21.
  2. 2AuthenticateIt sends USER then PASS. The server replies with a numeric code at each step.
  3. 3NavigateCWD changes directory, LIST shows what is there: moving around the remote tree.
  4. 4TransferRETR downloads a file to the client; STOR uploads one to the server.
  5. 5CloseQUIT ends the session and the control channel closes.
Put the five verbs in order early: every transcript later in the lesson is built from exactly these commands.
HACKTHESOCLesson 86FTP explained8 / 48

Authenticated versus anonymous access

Authenticated

A real username and password identify who connected, so server logs name an accountable person or service.

login: anonymous

Anonymous

Any client logs in as the generic anonymous user, often giving an email as the password. No real identity behind the session.

Anonymous access is not an attack by itself, but the server's logs then cannot tell you who actually connected: a real limitation during an investigation.

Section 2 of 8

How FTP works: two channels and its ports

Unlike most protocols, FTP uses two separate connections at once.

HACKTHESOCLesson 86FTP explained10 / 48

Commands on one channel, file data on another

TCP 21

Control channel

Commands and responses: login, listing, requesting transfers. Open for the whole session.

20 active / ephemeral passive

Data channel

The actual file contents during a transfer. Port 20 in active mode; a high ephemeral port in passive mode.

Port 21 is the one you will most associate with FTP; the data channel is separate and short-lived per transfer.
HACKTHESOCLesson 86FTP explained11 / 48
FTP opens a second connection just for the file bytes, and that is what firewalls trip over.

A firewall may allow the control channel on port 21 yet block the separately negotiated data channel, so a login works but the transfer hangs.

This two-connection design is the single most common FTP troubleshooting issue and the reason active and passive modes exist.
HACKTHESOCLesson 86FTP explained12 / 48

Active versus passive mode

Active mode

The server opens the data connection back to the client, traditionally from port 20. Client firewalls see an unexpected inbound connection.

Passive mode

The client opens the data connection to a port the server specifies. Works better through firewalls; the common default today.

Who opens the data connection is the whole difference, and it decides which firewall sees an inbound surprise.
HACKTHESOCLesson 86FTP explained13 / 48

Reading the PASV reply: six numbers become an IP and port

  • The server, not the client, chooses the data port in passive mode
  • 201,14 is not two ports: one number split into high and low bytes
  • This lets you match a control session to its data connection in a capture
Students often misread the last two numbers as a range. Walk the high*256+low arithmetic once and it sticks.
HACKTHESOCLesson 86FTP explained14 / 48

The ports to know, at a glance

PortChannelProtocol
21/tcpControl: commands and repliesFTP and FTPS
20/tcpData in active modeFTP
ephemeralData in passive modeFTP and FTPS

Seeing port 21 outbound is the FTP tell. Seeing 22 is SSH or SFTP, a different protocol entirely.

The full FTP command set and reply codes

On plaintext FTP, an analyst can read the whole transcript straight from a capture.

HACKTHESOCLesson 86FTP explained17 / 48

A full passive-mode upload, nothing hidden

  • 331 then 230 around PASS: a successful plaintext login
  • 227 carries the passive IP and port, as on the previous slide
  • STOR sends a file out; 150 then 226 bracket the transfer
That transparency is the analyst's advantage and the protocol's fatal weakness at the same time.
HACKTHESOCLesson 86FTP explained18 / 48

Reply codes, read by first digit like SMTP

CodeMeaning
150About to open the data connection (1yz preliminary)
220Service ready (opening banner)
226Transfer complete, closing data connection
227Entering Passive Mode: server returns its data IP and port
230User logged in, proceed
331Username OK, password needed (3yz intermediate)
530 / 550Not logged in / file unavailable or permission denied (5yz)
1yz preliminary, 2yz success, 3yz needs more, 4yz try again, 5yz permanent failure: the same first-digit rule as SMTP.
HACKTHESOCLesson 86FTP explained19 / 48

The two replies that carry the credentials

331 after USER

Username accepted, password required. The next line the client sends is PASS, in clear text on classic FTP.

230 after PASS

Logged in. A 230 following a PASS you can read proves the credentials just crossed the wire unprotected.

530 repeated

Not logged in: wrong credentials or a command before auth. Repeated 530 from one source is guessing.

Tie the codes to the security story: 331 then 230 is a login an attacker sniffing the link also captured.
HACKTHESOCLesson 86FTP explained20 / 48
RETR pulls a file toward the client; STOR pushes one to the server. The verb is the direction.

In exfiltration the internal host is the client issuing STOR, so bytes leave your network. Read the verb before anything else.

The single most common misreading is treating STOR to /incoming/ as a download. STOR always means the client is sending.

Section 4 of 8

The plaintext problem and secure alternatives

Credentials and file contents travel unencrypted.

HACKTHESOCLesson 86FTP explained22 / 48
In a capture of plain FTP you can literally read USER admin and PASS Summer2026!

Plain FTP should not be used over untrusted networks. Finding it is a hygiene finding, much like discovering Telnet.

Recall the Wireshark lesson: anyone able to capture the traffic reads the login and the files.
HACKTHESOCLesson 86FTP explained23 / 48

FTPS and SFTP: similar names, different technologies

FTP + TLS

FTPS

Classic FTP wrapped in TLS, the same kind of encryption HTTPS uses. Keeps FTP's two-channel design.

Over SSH, port 22

SFTP

Not FTP at all. A different protocol running over SSH, inheriting its encryption and authentication. The common modern choice.

Plain FTP on port 21 reaching external destinations is both a hygiene concern and a possible exfil channel.

Both solve the plaintext problem, on different ports. Students mix these up constantly.
HACKTHESOCLesson 86FTP explained24 / 48

FTP, FTPS and SFTP side by side

ProtocolEncryptionPortsChannels
FTPNone, all plaintext21 and 20 or ephemeralTwo
FTPSTLS, like HTTPS21 or 990 plus dataTwo
SFTPSSH22 onlyOne
SFTP's single encrypted channel on port 22 is the giveaway that it is a different protocol, not FTP with encryption bolted on.

Section 5 of 8

FTP bounce and other legacy weaknesses

Old servers accumulate old flaws.

HACKTHESOCLesson 86FTP explained26 / 48

How the FTP bounce attack works

  1. 1PORT names the targetIn active mode, PORT tells the server which IP and port to send data to.
  2. 2Attacker picks a third machineNothing in the original protocol forces it to be the client's own address.
  3. 3Server connects for themThe FTP server becomes a relay to scan or reach systems the attacker cannot.
  4. 4Source is disguisedTraffic appears to come from the FTP server, not the attacker.
Modern FTP servers restrict PORT to the connecting client's own address, which closes this.
HACKTHESOCLesson 86FTP explained27 / 48

More legacy weaknesses scanners flag

  • Directory traversal../ sequences reach files outside the intended directory, the same idea as in HTTP.
  • Anonymous by defaultMany servers historically shipped with anonymous access enabled.
  • World-writable uploadsDirectories anyone can write to, used to stage malware or deface content.

The fix is to retire plain FTP for FTPS or SFTP, not to patch each flaw.

Treat the mere presence of an old, unmaintained FTP service as a finding on its own.
HACKTHESOCLesson 86FTP explained28 / 48

Retire, do not patch around

Patch each flaw

Disable anonymous, restrict PORT, fix permissions. Still leaves credentials and files in plaintext on the wire.

Retire plain FTP

Move to FTPS or SFTP. Encryption removes the whole class of sniffing and most legacy exposure at once.

Vulnerability reports tempt analysts into flaw-by-flaw fixes. The durable answer is replacing the protocol.
HACKTHESOCLesson 86FTP explained29 / 48

How a scanner reports these flaws

  • ftp-anon ... 230 means anonymous login succeeded
  • ftp-bounce working confirms PORT can target a third host
  • An old named version like 1.3.3 is itself a finding to check for CVEs
This is what lands in a vulnerability report. The remediation is almost always retire plain FTP, not patch each line.

Section 6 of 8

FTP in MITRE ATT&CK: C2 versus exfiltration

Same protocol, same port 21, two distinct techniques.

HACKTHESOCLesson 86FTP explained31 / 48

What FTP carries versus why FTP was chosen

Command and Control

T1071.002

File-transfer protocols (FTP, FTPS, SMB, TFTP) as the channel itself: commands and tools, often inbound. E.g. a stager pulling its second stage via RETR.

Exfiltration

T1048

Stolen data sent over a different protocol than the main C2, e.g. HTTP C2 but files uploaded by FTP to evade detections tuned to the C2.

Direction, content and context decide the classification, not just 'FTP was observed'.

ATT&CK notes FTP often passes firewalls with less deep inspection than HTTP, because organisations invest more in web proxies and WAFs.
HACKTHESOCLesson 86FTP explained32 / 48

T1071.002 covers more than FTP

  • FTP / FTPSThe classic file-transfer channel, plaintext or TLS-wrapped.
  • SMBWindows file sharing on 445, often abused for tool transfer inside a network.
  • TFTPTrivial FTP on UDP 69, no auth, historically used by devices and by some malware.
  • The common threadAll are ordinary file-transfer traffic attackers hide inside, which is why baselining matters.
ATT&CK groups these because defenders should watch the behaviour, not one protocol. The others appear in their own lessons.
HACKTHESOCLesson 86FTP explained33 / 48

Which technique is it? Let direction and content decide

  1. 1Which way is data moving?Mostly inbound RETR pulling tools onto the host points to C2 (T1071.002).
  2. 2Is there a separate C2?Outbound STOR of data while C2 runs over another protocol points to exfiltration (T1048).
  3. 3What is the content?Executables and commands suggest C2; bulk business files suggest exfiltration.
  4. 4Classify and respondThe same port 21 can be either or both; the label drives which detections apply.
Resist labelling from the port alone. ATT&CK splits these deliberately because the response differs.
HACKTHESOCLesson 86FTP explained34 / 48

A process that has no business speaking FTP

An unrelated illustrative host, not the worked-example incident in section 8.

  • A Word macro spawned PowerShell, which opened an FTP connection
  • Fits a second-stage pull (T1071.002) or staging data out (T1048)
  • Baseline the small known list of hosts and processes that legitimately use FTP
Neither winword.exe nor powershell.exe has any legitimate reason to be an FTP client. Process lineage turns a routine port-21 connection into an incident.

Section 7 of 8

Why FTP matters to a SOC analyst

A weakness when present, and an exfiltration path by design.

HACKTHESOCLesson 86FTP explained36 / 48

Two reasons FTP earns SOC attention

Weakness and hygiene

Attackers scan the internet for such servers to steal data or host malware.

  • Plaintext credentials harvestable by sniffing
  • Anonymous or weak servers exposing files
  • Old servers with known vulnerabilities

Attack channel

Exfiltration is the primary reason to watch FTP.

  • Uploading stolen data to attacker servers
  • Hosting malware or pulling tools down
Plain FTP prompts 'why is this still here?'. Outbound FTP to an unknown destination prompts 'is data leaving?'.
HACKTHESOCLesson 86FTP explained37 / 48
Baseline the few hosts and processes that legitimately speak FTP, then alert on everything else.

In most networks only backup jobs, a named integration server or two, and a short list of accounts ever use FTP. Anything outside that list is worth a look.

This single detection idea catches both the C2 and the exfiltration case, because both involve an unexpected process opening port 21.
HACKTHESOCLesson 86FTP explained38 / 48

What the SOC watches

  • Outbound to the unknownFTP to external or unfamiliar servers, especially large transfers.
  • Plain FTP at allPort 21 unencrypted: hygiene and credential exposure.
  • Anonymous and known-badAnonymous access, connections to known-bad FTP hosts.
  • Visible credentialsCredentials readable in captured FTP traffic confirm exposure.
Each watch item maps to either the weakness side or the exfiltration side.

Worked example: FTP exfiltration in logs

Three lines of Zeek ftp.log at the internet edge, a clear case for escalation.

HACKTHESOCLesson 86FTP explained40 / 48

What the edge sensor saw: one STOR record from Zeek ftp.log

Classic FTP's control channel is plaintext, so Zeek reads every command.

  • id.orig_h is our internal workstation, the FTP client
  • id.resp_h on port 21 is an unfamiliar external server we do not run
  • password is masked <hidden>, but Zeek saw it in clear text
This is evidence the SOC owns: we will never see the external server's own logs. The other two records share the same uid, user and server.
HACKTHESOCLesson 86FTP explained41 / 48

Three uploads in about three minutes, over 500 MB out

tsSTOR arg (file)conn.log orig_bytes
22:41:07Z/incoming/Q3_financials_master.xlsxabout 4.2 MB
22:41:22Z/incoming/customer_export_full.csvabout 188 MB
22:41:58Z/incoming/contracts_backup.zipabout 340 MB

Each STOR answered with reply code 226. STOR means upload: data going out.

Common mistake: reading /incoming/ as the source. It is a directory on the remote server; the source is the workstation itself.
HACKTHESOCLesson 86FTP explained42 / 48

Could this be legitimate? What would change the verdict

Points to exfiltration

Everything here matches the pattern this lesson flagged as FTP's primary SOC concern.

  • Unfamiliar external destination
  • Out of hours, 22:41
  • Customer and contract data
  • Plain FTP, data readable

Would soften it

Check these before escalating: context, not the protocol alone, decides.

  • Known partner address in prior logs
  • A documented scheduled backup
  • A role that handles these exports
Teach the discipline of looking for the benign explanation. Here none of them hold, which is what makes this a clean escalation.

Questions this raises immediately

  1. 1Who was at the workstation?Who was logged on to 10.14.22.108 at 22:41, and are they an active, authorised contractor?
  2. 2Does the role fit?Does that person's role plausibly involve exporting customer and contract data at all?
  3. 3Who is the destination?An approved business partner, or an address with no prior relationship?
  4. 4Was it encrypted?A sensor read the username and every command, so plain FTP: the data was readable too.

Every element traces back to the lesson: STOR, volume and destination, and plaintext credentials.

Key takeaways

  1. 01FTP exists only to move files; it is legacy and sometimes allows anonymous access.
  2. 02Control on TCP 21, data on port 20 (active) or ephemeral ports (passive, firewall-friendly).
  3. 03Classic FTP sends USER, PASS and files in plaintext; use FTPS (FTP + TLS) or SFTP (over SSH, port 22).
  4. 04Legacy flaws include FTP bounce via PORT, directory traversal, and anonymous or world-writable defaults.
  5. 05STOR is upload: large outbound FTP to an unfamiliar server is a classic exfiltration pattern.
  6. 06ATT&CK: T1071.002 when FTP carries C2 or tools, T1048 when it is a separate exfil channel.

Check your understanding, question 3 of 3

A vulnerability report flags an old FTP server for allowing the FTP bounce technique via the PORT command. What does this let someone do?

In active mode PORT tells the server where to send data; unrestricted, it can target a third machine and hide the source. ../ paths are directory traversal and anonymous login is weak defaults, both separate. Credentials travel in USER and PASS, not PORT.
