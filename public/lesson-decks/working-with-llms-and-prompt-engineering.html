How one LLM call really works

A stateless function from text in to text out: completeness of the request is your job.

HACKTHESOCLesson 119Working with LLMs6 / 54

Three roles tag every message in a chat-style call

Chat-style APIs take a list of messages, each tagged with a role.

RolePurposeTypical SOC content
systemStanding rules, persona and output contract set by whoever builds the workflowYou are a tier-1 triage assistant. Answer only from the supplied data.
userThe current request plus the data to work onThe alert, the log excerpt, the question
assistantEarlier replies sent back to continue a thread, or a prefilled start of the next replyPrevious summary, or the opening of a JSON object

Durable behavior (tone, scope, refusal rules, exact output format) belongs in the system message.

Putting the rules in every user message works but is repetitive and easy to forget. The assistant role can also hold a prefilled start, such as the opening brace of a JSON object.
HACKTHESOCLesson 119Working with LLMs7 / 54

No memory between calls, and a token budget to plan

A chat window feels continuous only because the client re-sends the whole message list on every turn.

  • Not in the request, not knownIf a fact is not in the current request, the model does not know it.
  • New chat means zeroStarting a new chat means starting from zero.
  • History costs more each turnLong conversations get slower and more expensive because the full history travels with each turn.
  • Tokens, not charactersModels read word pieces of about 3 to 4 English characters. Hashes, base64 and long URLs burn many tokens.
  • The context window is a budgetInput plus output share one limit: plan system prompt, instructions, data and room for the answer.

Pre-process before you paste: extract fields, deduplicate, cut noise. Models recall the start and end of long inputs best.

Use the follow-up example: a bare 'what about the second host?' in a fresh call contains no information about which hosts were discussed. Ask: what does the model need that it cannot possibly know?
HACKTHESOCLesson 119Working with LLMs8 / 54

Temperature: match the randomness to the task

Near deterministic

0 to 0.2

Extraction, classification, query writing, and any summary that should look the same tomorrow.

    Some variety

    0.5 to 0.8

    Rewording a stakeholder email or brainstorming hypotheses.

      Creative and unstable

      Above 0.8

      Rarely right for security work.

        Even at temperature 0, identical output is not guaranteed across runs, hardware or model versions.

        Never build a process that depends on byte-exact responses. Change one sampling setting at a time and set a maximum output length so a runaway answer cannot burn budget.
        HACKTHESOCLesson 119Working with LLMs9 / 54

        A complete, self-contained request

        Model, sampling settings, and the message list that makes up one call.

        • A low temperature and a max length keep reruns alike and cost bounded
        • The system message holds standing rules; the user message holds task and data
        Before sending, ask two questions: what does the model need that it cannot know, and how many tokens will this cost?

        Prompt engineering patterns that earn their keep

        Write the input so the output is reliably useful, like a clear ticket for a capable but literal new hire.

        HACKTHESOCLesson 119Working with LLMs11 / 54

        Patterns 1 to 4: say what, to whom, and in what shape

        PatternWhat it isUse it whenPitfall
        Clear instructionOne explicit task verb: summarize, classify, extract, rewriteAlwaysStacking five tasks in one sentence
        ContextWho the audience is, what environment, what already happenedThe answer depends on situationDumping irrelevant history
        Output formatExact structure: headings, JSON keys, word limitsOutput feeds a person or a parserLeaving format open and getting prose
        Few-shot examplesTwo to five input and output pairs shown inside the promptFormat or judgment is hard to describeAll-alike examples bias toward one answer
        For few-shot, show one clear high, one clear low and one tricky medium with the reason. Vary the examples so the model learns the rule, not the surface pattern.
        HACKTHESOCLesson 119Working with LLMs12 / 54

        Be specific and positive, and give the reason

        The model cannot read your mind, your tools or your last meeting: anything not written down is a guess.

        Vague

        Make it short.

          Specific

          At most 120 words, three bullets, no jargon. State what to do, not only what to avoid.

            With the reason

            Do not speculate about attribution, because this goes to legal. The reason lets the model apply the rule to cases you did not anticipate.

              Have students rewrite a vague prompt of their own into the middle column, then add a reason to the rule that is least obvious.
              HACKTHESOCLesson 119Working with LLMs13 / 54

              Patterns 5 to 8: reasoning, perspective, safety, and honesty

              PatternWhat it isUse it whenPitfall
              Step-by-step reasoningAsk the model to work through the problem before the final answerMulti-step logic, timelines, mathTreating the shown reasoning as proof
              Role promptingAssign a perspective, such as an incident-response leadTone and depth need to be setBelieving a role adds knowledge it lacks
              DelimitersWrap data in tags or fences, separate from instructionsAny pasted dataAssuming delimiters make hostile text safe
              Permission to say unknownExplicitly allow insufficient evidence as an answerFactual or evidence-bound tasksOmitting it, which invites invention
              Permission to say unknown is the cheapest anti-hallucination line you can add. Delimiters get a full section next.
              HACKTHESOCLesson 119Working with LLMs14 / 54

              Three cautions: reasoning text, roles, and untested prompts

              • Reasoning text is a narrativeReasoning models think internally, so state the problem plainly. Printed reasoning is a plausible narrative, not an audit trace.
              • A role shifts register, not factsAn incident handler writing for executives emphasizes different things than a malware analyst, but gains no knowledge it lacks.
              • Iterate like codeKeep prompts in version control, change one thing at a time, and test against a fixed set of sample inputs.

              A prompt that worked on one example is a hypothesis, not a finished tool.

              Best prompts are explicit about task, audience, evidence, format, and what to do when evidence is missing. Verify the conclusion against the data, not against the model's explanation of itself.

              Section 3 of 9

              Separating data from instructions, structured output

              The model sees one stream of text, so make it obvious what is instruction and what is material.

              HACKTHESOCLesson 119Working with LLMs16 / 54

              Delimit the data and say how to treat it

              Wrap each input in clearly named tags and tell the model what the tags mean.

              • A named tag can be referred to later, such as the contents of <proxy_log>
              • The instruction declares the content to be data, not commands
              In security work you almost always paste data: logs, emails, command lines, tickets. The model receives one stream of text, so the separation has to be explicit.
              HACKTHESOCLesson 119Working with LLMs17 / 54

              Delimiters reduce accidents, not attacks

              • Named tags beat quotesYou can refer to them, and they stay readable when the data itself contains quotation marks.
              • Pick an unlikely delimiterIf an attacker controls the text, they can include a fake closing tag.
              • Not a security boundaryText between the tags can still try to influence the model. Pair delimiters with limited privileges and human review.
              • Order mattersFor long inputs put the data first and the question and format rules last, or repeat the key instruction after the data.
              Models weight the end of the prompt heavily, and an instruction buried before 20,000 tokens of logs is easy to lose. How hostile text hijacks a model is covered in the AI-attacks lessons.
              HACKTHESOCLesson 119Working with LLMs18 / 54

              Ask for structure when software consumes the answer

              Request JSON with named keys and allowed values.

              • Allowed values give your code something concrete to validate
              • The evidence key forces the model to point at text in the input
              Requesting evidence, not just conclusions, turns an opaque answer into a checkable one. A reviewer verifies each quote in seconds.
              HACKTHESOCLesson 119Working with LLMs19 / 54

              Treat the structured result like any untrusted input

              1. 1Parse it properlyUse a real JSON parser on the response.
              2. 2Validate the valuesCheck that verdict is in the allowed set: a well-formed object can still hold a wrong value.
              3. 3Check the quotesEvery evidence quote must exist in the source. One that does not is an instant hallucination signal.
              4. 4Handle failureRetry, or route the case to a person.

              Keep one job per prompt: extract fields, classify, then draft, with a deterministic check such as an IP regex between steps.

              Use the platform's structured-output or JSON-schema mode when available, but still validate. Ask: could a parser, or a person in ten seconds, tell if this output is wrong?

              Section 4 of 9

              Grounding and retrieval-augmented generation (RAG)

              Make the answer rest on supplied evidence, not on what the model remembers.

              HACKTHESOCLesson 119Working with LLMs21 / 54

              Two sources for every answer

              In the weights

              Parametric memory

              Patterns baked in during training. Frozen at a cutoff date, impossible to audit, and the source of confident errors.

                In the prompt

                Supplied evidence

                Whatever you put in the request. Grounding forces the answer to rest on this instead of on memory.

                  RAG (Lewis and colleagues, 2020) fetches the relevant passages at question time and places them in the prompt.

                  Instead of hoping the model remembers your runbook, you fetch the right passages when the question arrives.
                  HACKTHESOCLesson 119Working with LLMs22 / 54

                  Embeddings: similar meaning lands close together

                  • Text becomes a vectorAn embedding model turns text into a list of numbers so that texts with similar meaning sit near each other.
                  • Meaning, not wordsDisable the compromised account and lock out the breached user end up close though they share few words.
                  • A vector indexStores one vector per document chunk and returns the chunks nearest to the query vector.
                  • Cosine similarityThe usual measure of closeness.
                  • Semantic plus keywordThis is semantic search, as opposed to keyword search. Many production systems combine both.
                  Concept level only: students do not need the math, just the idea that closeness in number space stands in for closeness in meaning.
                  HACKTHESOCLesson 119Working with LLMs23 / 54

                  The RAG flow: index ahead of time, retrieve at question time

                  • Each stored chunk carries a source id and an access label
                  • Step 5 filters by permissions; step 7 makes not found a legal answer
                  Why it reduces hallucination: the model reads and restates evidence instead of recalling it, the material is current because you update the index, and every claim can point to a chunk. It lowers the rate; it does not remove it.
                  HACKTHESOCLesson 119Working with LLMs24 / 54

                  Where RAG fails in practice

                  FailureWhat goes wrongWhat to do
                  Retrieval missThe right chunk never reaches the prompt, so the model improvisesMeasure retrieval separately from generation
                  Bad chunkingA procedure split in half loses its meaningChunk along headings and keep steps together
                  Stale or conflicting sourcesAn old runbook ranks beside the new oneStore dates and owners, and prefer recent
                  Permission leakageA mixed index can surface documents the asker should not seeEnforce access control at retrieval, not in the prompt
                  Poisoned contentAnyone who can edit an indexed document can influence answersTreat the corpus as part of your attack surface

                  Cite sources: name the chunk id and quote the supporting sentence. If the cited chunk lacks the quote, reject the answer.

                  The model can still misread a chunk, merge two chunks wrongly, or answer from memory despite instructions. Ask: did retrieval bring the right evidence, and does each claim trace to it?

                  Section 5 of 9

                  Tools, function calling, and agents with least privilege

                  The model proposes actions; your application decides what actually runs.

                  HACKTHESOCLesson 119Working with LLMs26 / 54

                  Function calling: the model asks, the application acts

                  An agent is this loop run repeatedly: plan, call a tool, read the result, decide the next step, until done or at a limit.

                  • The model never runs anything itself, it only requests a call
                  • The application validates, executes, and sends the result back as a message
                  Agents are powerful for multi-step enrichment: pull the alert, look up the IP, check recent sign-ins, draft a note. They are also where mistakes become actions.
                  HACKTHESOCLesson 119Working with LLMs27 / 54

                  Least privilege: the riskier the tool, the stronger the

                  TierExample toolsControls
                  Read-only, narrowLook up an IP, fetch one alert by id, search a knowledge baseScoped read token, rate limit, log every call
                  Read-only, broadRun free-form searches across all logsAllowlisted data sources, query timeouts, result size caps
                  Reversible writeAdd a ticket comment, tag an alertHuman glance after the fact, audit trail
                  Consequential writeIsolate a host, disable an account, block an address, delete dataExplicit human approval before execution, every time
                  Same principle as service accounts: the minimum access needed for the task, and no more.
                  HACKTHESOCLesson 119Working with LLMs28 / 54

                  Six rules that follow from least privilege

                  • No run-any-command toolOffer specific functions with typed, validated parameters.
                  • Give the tool its own credentialsScoped to the minimum, never the analyst's full session or an admin token.
                  • Validate arguments in codeThe model may produce an out-of-range value, a wrong identifier, or text that came from untrusted data.
                  • Separate read from writeKeep write tools disabled unless the workflow requires them.
                  • Cap the loopSet a maximum number of steps, a maximum cost, and a timeout.
                  • Log the full chainRequests, arguments and results, so an investigator can reconstruct what happened.
                  Walk the six rules against the agent in the quiz: which ones does a generic tool with the lead analyst's session break?
                  HACKTHESOCLesson 119Working with LLMs29 / 54
                  The model proposes, your code disposes.

                  A model reading untrusted content while holding powerful tools is a confused deputy: log or email text can steer actions taken with your credentials.

                  Ask: if this model made the worst plausible choice with every tool it holds, how bad is the result? Limiting what tools can touch limits the damage of a hallucination, an ambiguous request or hostile input.

                  Section 6 of 9

                  Reliability: hallucination, verification, review

                  Fluency is not accuracy. Build habits that show you when the output is wrong.

                  HACKTHESOCLesson 119Working with LLMs31 / 54

                  Fluency is not accuracy: six verification habits

                  Hallucination is fluent output not supported by the input or reality: invented CVEs, flags, log fields, IOCs, ATT&CK IDs.

                  HabitIn practice
                  Check against the sourceIf the model says a host contacted a domain, find that line in the log
                  Require quoted evidenceThen confirm the quote exists in the input
                  Validate identifiersCVE in the vulnerability database, technique ID in the framework, command in a lab
                  Use deterministic checksA JSON schema, a regex for IP format, a query syntax validator
                  Compare repeated runsThree runs at moderate temperature disagree: under-specified question or weak evidence
                  Grant the exitAllow insufficient evidence as an answer so the model is not pushed to invent
                  The wording of a hallucination is usually confident, which is exactly why it passes casual review. Plausible is not the same as true.
                  HACKTHESOCLesson 119Working with LLMs32 / 54

                  Evaluation: measure instead of trusting impressions

                  1. 1Build a golden set30 to 100 realistic inputs with answers labeled by an experienced analyst.
                  2. 2Include hard casesAmbiguous logs, benign-but-odd activity, and inputs with missing data.
                  3. 3Score each prompt versionRecord accuracy, false positives, false negatives, and format failures.
                  4. 4Re-run on every changePrompt, model or retrieval index: small edits can silently shift behavior.
                  The same golden set is how you notice later that a model update changed behavior.
                  HACKTHESOCLesson 119Working with LLMs33 / 54

                  LLM-as-judge scales review, with known pitfalls

                  A second model call grades outputs against a rubric when humans cannot read everything.

                  Position bias

                  The judge favors the answer shown first. Test both orders.

                    Verbosity bias

                    Longer answers score higher regardless of quality.

                      Self-preference

                      A model rates text in its own style more favorably.

                        Shared blind spots

                        If the judge has the same knowledge gaps as the writer, both miss the same error.

                          Vague rubrics give noise: use specific yes or no criteria. Calibrate against human labels; use for triage and trends, not final authority.

                          Example criterion: every claim has a quote from the log. If judge scores climb steadily as outputs get longer, suspect verbosity bias before you suspect improvement.
                          HACKTHESOCLesson 119Working with LLMs34 / 54

                          Human in the loop: decide by impact, not by confidence

                          • Reading and summarizingCan run with spot checks.
                          • Anything that changes stateDisabling an account, isolating a host, an external notification, closing as benign: a named person reviews and approves.
                          • Make approval meaningfulShow the person the evidence and the proposed action, not just a green button.
                          • Beware automation biasRotate sampling reviews and track how often reviewers overturn the model.

                          Ask: how would I know if this were wrong, and who signs for the action?

                          A confidence score is not a gate. The decision to require approval depends on what the action can break.

                          Security and privacy when using LLMs at work

                          A prompt sent to a third-party service leaves your boundary: treat it as an external disclosure.

                          HACKTHESOCLesson 119Working with LLMs36 / 54

                          Never paste these into an unapproved model

                          Secrets

                          Passwords, API keys, session cookies, bearer tokens, private keys, connection strings, recovery codes.

                          • Hidden in URL query strings
                          • Hidden in Authorization headers

                          Personal data (PII)

                          Names, emails, phone numbers, national ID numbers, health or financial details of employees or customers.

                            Customer and contract data

                            Customer data and contract-confidential material.

                              Non-public incident details

                              Unpatched vulnerability information and internal network layouts, especially in a live investigation or under legal hold.

                                Logs and config files often contain secrets in places you do not expect. Scan before you paste.
                                HACKTHESOCLesson 119Working with LLMs37 / 54

                                Retention and training differ by service: do not assume

                                • Consumer chat productsMay keep conversations, let staff review them, or use them to improve models unless you opt out.
                                • Business and API offeringsOften add contractual limits on retention and training, data-region choices, and audit logs.
                                • Read the termsCheck the data-processing terms with your security and legal teams.
                                • Approved tools onlyPasting work data into a personal account is a data leak even if no one ever misuses it.
                                • More exposureShared conversation links and browser extensions add further exposure.
                                Ask three questions: is this tool approved, what does it retain, and does the model truly need the real values?
                                HACKTHESOCLesson 119Working with LLMs38 / 54

                                Redact and pseudonymize before sending

                                Replace identifiers with consistent placeholders, keep the mapping locally, restore names in the answer.

                                • Consistent placeholders let the model still reason about relationships
                                • The mapping never leaves your machine; the token is gone entirely
                                USER_1 appearing on both hosts is the relationship the model needs. For high volume, put an automated redaction step in front of the model rather than relying on people to remember.
                                HACKTHESOCLesson 119Working with LLMs39 / 54

                                Untrusted content in, unreviewed output out

                                SituationHabit
                                Model reads content you do not control: email, web page, filename, User-Agent fieldMark it untrusted and keep high-privilege tools out of that context
                                Model output that looks like an actionNever auto-execute it; review before acting
                                Generated commandsRead them; run first in a lab or with a dry-run flag
                                Generated codeCheck dependencies for nonexistent or typo-squatted package names
                                AI-assisted work in reportsFollow your labeling policy; you remain accountable for every statement you sign

                                The attack techniques are in the AI-attacks lessons; here we record only the working habits.

                                Never paste a generated script into a production console unreviewed. Text in a log or email may carry instructions aimed at the model rather than at you.

                                Practical SOC uses, with the verification caveat

                                Strong at transforming and explaining text you give them, weak at recalling precise facts.

                                HACKTHESOCLesson 119Working with LLMs41 / 54

                                Six analyst uses: what makes the prompt work, how you verify

                                UseWhat makes the prompt workHow you verify
                                Summarize logs or an alertPaste a filtered excerpt, ask for a timeline with timestamps and quoted linesSpot-check every timestamp and identifier against the source

                                HACKTHESOCLesson 119Working with LLMs42 / 54

                                Where to lean on the model and where not to

                                Lean on it

                                Transforming and explaining text you give it: summaries, drafts, explanations, translation between query languages.

                                  Verify every time

                                  Anything that recalls precise facts: CVE numbers, flags, field names, technique IDs. Check an authoritative source.

                                    Keep with a human

                                    Final severity calls, attribution, legal conclusions, and attacker intent. The model organizes evidence; the analyst decides.

                                      Use the model to speed up reading and writing, never to replace checking.

                                      Ask: what would I check if a junior colleague handed me this?
                                      HACKTHESOCLesson 119Working with LLMs43 / 54

                                      A detection-query prompt that supplies the schema

                                      The common failure is invented field names. Prevent it by listing the fields.

                                      • Only the listed fields may be used, so none can be invented
                                      • The explanation exposes wrong logic; the test cases are a ready validation plan
                                      Then run the query on a known-positive and a known-negative dataset and inspect real hits. A query that executes without error is not necessarily a query that detects.
                                      HACKTHESOCLesson 119Working with LLMs44 / 54

                                      Encoded PowerShell: the explanation is a map, not the

                                      1. 1Ask for structure and purposeHave the model explain the structure and likely purpose. Say do not execute.
                                      2. 2Decode it yourselfUse a trusted local tool, because a model may paraphrase an encoded string it cannot truly decode.
                                      3. 3Read the decoded contentConfident wording from the model is not evidence.
                                      4. 4Confirm against documentationVerify flags in official docs before you rely on any claim.

                                      Drafting reports: use only the facts below, mark anything uncertain as unconfirmed, then delete what you cannot trace to your notes.

                                      Cleanliness hides error. Models write clean prose, which makes them good at the last mile of reporting and dangerous when unchecked.

                                      Key takeaways

                                      1. 01Every LLM call is stateless and self-contained: if a fact is not in the request, the model does not know it.
                                      2. 02Good prompts state task, audience, evidence, format, and an allowed answer of insufficient evidence.
                                      3. 03Delimit data, demand machine-checkable JSON with quoted evidence, and still treat the output as untrusted.
                                      4. 04RAG swaps recall for reading: cited chunks make answers checkable, but retrieval can still miss or go stale.
                                      5. 05The model proposes, your code disposes: narrow tools, scoped credentials, and human approval for consequential actions.
                                      6. 06Fluency is not accuracy: verify against sources, redact before sending, and use approved tools only.
