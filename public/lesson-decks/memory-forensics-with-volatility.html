Why memory is the richest evidence

The live, working state of everything happening on the machine.

HACKTHESOCLesson 78Memory forensics6 / 63

RAM is the whiteboard, the disk is the filing cabinet

RAM (volatile)

Shows what is being worked on right now. Wipe it and that working state is gone forever. Some things only ever existed here.

Disk (persistent)

Permanent records that survive being closed and reopened. A disk investigation reads the filing cabinet.

A diagram sketched, discussed and rubbed out before being filed only ever existed on the whiteboard.
HACKTHESOCLesson 78Memory forensics7 / 63

What can exist in memory and nowhere on disk

  • Running processesIncluding ones an attacker tried to hide from the normal process list.
  • Injected codeMalware running inside a legitimate process, not as a file.
  • Fileless malwarePowerShell or scripts living entirely in memory, invisible to file scanning.
  • Live network connectionsActive connections to a C2 server at the moment of capture.
  • Decrypted data and credentialsEncrypted on disk, but decrypted in memory to be used.
  • Command historyWhat was actually run.
As intruders go fileless and inject into trusted processes, reading memory has moved from niche to essential Tier-2 capability.

Order of volatility: collect the most fleeting evidence first. Memory before disk.

Power a suspicious machine off before capturing RAM and you may permanently lose the only evidence of a fileless or injected attack.

A reboot destroys memory while the disk survives, which is why the rule is counter-intuitive to beginners who reach for the power button.
HACKTHESOCLesson 78Memory forensics10 / 63

What happens to the evidence at power-off

  1. 1Machine runningProcesses, injected code, live connections and decrypted secrets all sit in RAM.
  2. 2Power cut or rebootRAM loses its contents within moments.
  3. 3Disk survivesFiles, registry hives and logs are still there.
  4. 4What is lostAnything that only ever existed in memory is gone, with no copy anywhere.
This is the whole argument for capturing RAM first: the disk can wait, memory cannot.

Capturing a memory image

Copy RAM to a file while disturbing the evidence as little as possible.

HACKTHESOCLesson 78Memory forensics12 / 63

How a memory image gets made

Windows tools

WinPmem, DumpIt, FTK Imager, Magnet RAM Capture. A raw image, often several GB, analysed offline.

  • winpmem.exe C:\Evidence\WKS-DESKTOP07_mem.raw

Linux

LiME (Linux Memory Extractor), kernel-module based, dumps RAM to a file or over the network.

Virtual machines

Take a snapshot or save state: the hypervisor writes the VM's RAM to a file you analyse directly.

Virtualised environments are convenient for both incident response and training for exactly this reason.
HACKTHESOCLesson 78Memory forensics13 / 63

What a capture tool actually does

StageActionWhy it matters
Load the toolA trusted capture tool runs on the live machineChoose one that alters as little memory as possible
Read physical RAMIt copies memory page by pageCaptures the live state, not a filtered view
Write the imageA raw image, often several GB, goes to external storageNever write to the suspect's own disk
Analyse offlineThe machine is left alone; work happens on the copyThe original evidence stays untouched
The tool itself occupies a little memory, an unavoidable disturbance you minimise and document.
HACKTHESOCLesson 78Memory forensics14 / 63

The golden rules of acquisition

  1. 1Do not power off firstShutdown or reboot destroys memory. Capture RAM before anything else touches the machine.
  2. 2Minimise your footprintThe capture tool runs in memory and changes a little of it. Use trusted tools and document it.
  3. 3Hash on capturecertutil -hashfile WKS-DESKTOP07_mem.raw SHA256
  4. 4Analyse a copyStore securely under chain of custody so findings stand up to scrutiny.
Once you have a sound image, the live state is frozen in a file you can examine repeatedly. But it is just raw bytes until a tool understands the OS layout.
HACKTHESOCLesson 78Memory forensics15 / 63

Hashing an image and the chain of custody

  • Capture to external evidence storage, not the suspect's own disk
  • The SHA-256 hash proves the image did not change afterwards
  • Record who captured it, when, and where it was stored
Hash at capture, then analyse a copy. If a later hash matches, the evidence is intact and findings stand up to scrutiny.

Volatility basics: your first plugin

Reconstruct the machine's state at the moment of capture.

HACKTHESOCLesson 78Memory forensics18 / 63

How Volatility 3 understands an arbitrary image

  • Symbol tablesIt needs the exact layout the OS used for internal structures. In Volatility 3 the format is ISF, Intermediate Symbol Format.
  • Automatic in the common caseIt inspects the image, identifies the OS build, and fetches or uses matching symbols.
  • One command shapepython3 vol.py -f <image> <plugin>: point at the image, name the question.
You may still meet the older Volatility 2 with a slightly different command style. Section 8 compares them.
HACKTHESOCLesson 78Memory forensics19 / 63

From raw image to readable processes

  1. 1Point at the imagevol.py -f WKS-DESKTOP07_mem.raw.
  2. 2Identify the buildVolatility inspects the image and works out the exact OS build.
  3. 3Load symbolsIt fetches or uses the matching ISF symbol table for that build.
  4. 4Run the pluginThe named plugin reads the structures and prints a table.
ISF is the Intermediate Symbol Format. In Volatility 2 you had to supply the build yourself with --profile; section 8 compares the two.

Section 4 of 9

Core process and network plugins

Landscape, concealment, and who was talking to whom.

HACKTHESOCLesson 78Memory forensics23 / 63

pstree shows lineage; psscan catches what hid

  • * and ** indentation show parent-child relationships
  • psscan scans memory for process structures directly
  • PID 4180 in psscan but never in pslist: deliberate concealment
Some malware unlinks itself from the OS's active-process list, a classic rootkit technique. psscan still finds the structure, and also terminated processes.
HACKTHESOCLesson 78Memory forensics24 / 63

Two ways to list processes, and why you need both

Walk the OS list

pslist / pstree

Follow the operating system's own active-process list. Fast and structured, but a rootkit can unlink itself from it.

Scan memory directly

psscan

Search memory for process structures regardless of the list. Finds unlinked and already-exited processes.

A PID that psscan finds but pslist does not is the classic sign of a process hidden by unlinking.
HACKTHESOCLesson 78Memory forensics25 / 63

netscan ties a process to a live connection

  • The suspicious powershell.exe from pstree
  • Established to an external IP on 443 at the moment of capture
  • A plausible C2 channel and a concrete IP to pivot on
One output row, split across two lines to fit. Three commands in, you have a short list of suspect processes and their network activity.

Section 5 of 9

Finding injection and fileless malware

Is there code hiding inside an otherwise legitimate process?

HACKTHESOCLesson 78Memory forensics28 / 63

malfind flags executable memory with no file behind it

Two details: PAGE_EXECUTE_READWRITE is rarely legitimate, since writable plus executable is exactly what injection needs. And 4D 5A is MZ, the start of a Windows executable: a whole embedded PE inside powershell.exe with no file on disk.
HACKTHESOCLesson 78Memory forensics29 / 63

What makes the malfind region suspicious

ObservationWhy it matters
Protection PAGE_EXECUTE_READWRITEWritable and executable at once: rarely legitimate, exactly what injection needs
No file backs the regionNormal code is mapped from a file on disk; this is not
Starts with 4D 5A (MZ)The header of a Windows executable, embedded in memory
Host is powershell.exeA whole PE living inside PowerShell, with no file on disk
Any one is a lead; all four together describe injected, fileless code.
HACKTHESOCLesson 78Memory forensics30 / 63

cmdline shows how the process was really launched

  • -w hidden: hidden window
  • -enc: a Base64-encoded command
  • Not what a user typing at a prompt would produce
Also: windows.dlllist shows loaded DLLs, and windows.ldrmodules cross-checks them against OS module tracking. A mismatch suggests a reflectively loaded or unlinked module.
HACKTHESOCLesson 78Memory forensics31 / 63

Two more plugins for loaded modules

  • windows.dlllistLists the DLLs a process loaded, with their paths. An unexpected path like a Temp folder stands out.
  • windows.ldrmodulesCross-checks the loaded modules against the OS's three module-tracking lists.
  • The mismatchA module missing from a list it should be in suggests a reflectively loaded or unlinked DLL.
These matter for the DLL-injection case in section 7, which malfind usually does not flag.
HACKTHESOCLesson 78Memory forensics32 / 63

Four outputs prove a fileless, injected intrusion

  1. 1pstreepowershell.exe running under explorer.exe.
  2. 2netscanConnected to an external IP.
  3. 3malfindAn embedded executable with RWX permissions in its memory.
  4. 4cmdlineLaunched hidden with an encoded command.
A file-based antivirus scan would likely have missed all of this, because none of it exists as a file on disk.

Why an open handle is good evidence

File handle

An open handle to evil.ps1 ties this process directly to the dropped file.

Mutant (mutex)

A named mutex malware uses so it does not run twice. A strong, specific pivot value to hunt across the fleet.

Registry key

A handle to the Run key corroborates the persistence entry found on disk with RECmd.

Handles show what a process was actively using, not just what it loaded at start.

Section 7 of 9

Process hollowing vs DLL injection

Adding code beside a process vs replacing it, and which plugin sees each.

HACKTHESOCLesson 78Memory forensics42 / 63

How the code got there decides which plugin sees it

Process Injection (T1055); DLL injection (T1055.001) runs in addition to the process's normal code.

File-backed

LoadLibrary DLL injection

Loads a real DLL from disk (classically CreateRemoteThread + LoadLibrary), so malfind generally does not flag it.

  • Look in windows.dlllist / windows.ldrmodules
  • Unexpected DLL path, e.g. C:\Users\Public\ or %TEMP%

No file behind it

Shellcode, PE, reflective DLL

Code written straight into memory without a backing file. That is malfind's signature: an executable, unbacked region, often PAGE_EXECUTE_READWRITE.

  • Look in windows.malfind
Common mistake: assuming malfind catches every injection. A classic LoadLibrary DLL is file-backed, so hunt it in the module lists instead.
HACKTHESOCLesson 78Memory forensics43 / 63

How process hollowing works (T1055.012)

  1. 1Launch suspendedA legitimate exe like svchost.exe via CreateProcess with CREATE_SUSPENDED.
  2. 2Hollow it outUnmap its legitimate code with NtUnmapViewOfSection.
  3. 3Write malicious codeInto the empty space with VirtualAllocEx / WriteProcessMemory.
  4. 4Redirect and resumeSetThreadContext to the malicious code, then ResumeThread.
It runs under the name, PID and command line of a trusted process, defeating checks that trust a name. A long-standing favourite of TrickBot and ransomware loaders.
HACKTHESOCLesson 78Memory forensics44 / 63

What each technique does to the target process

T1055.001

DLL / code injection

The legitimate code stays and runs; malicious code runs in addition to it, inside an existing process.

T1055.012

Process hollowing

A fresh, suspended process is created, its legitimate code removed, and malicious code written in its place: it keeps the name and PID, but is entirely malicious.

Reporting 'code was injected into svchost.exe' understates hollowing, where the whole process was replaced behind a trusted name.
HACKTHESOCLesson 78Memory forensics45 / 63

The tell: memory does not match the file on disk

  • malfind + vadinfowindows.vadinfo lists a process's Virtual Address Descriptors, so you compare what should be mapped against what is.
  • PEB vs mapped imageThe PEB claims C:\Windows\System32\svchost.exe, but memory at the base address does not match that file.
  • Purpose-built toolspe-sieve and Hollows Hunter automate the comparison; on live systems Sysmon Event ID 25 flags image changes.
These complement core Volatility for this specific technique.
HACKTHESOCLesson 78Memory forensics46 / 63

Telling the two apart in your notes

DLL / code injection (T1055.001)Process hollowing (T1055.012)
Legitimate codeStill present, runs alongside injected codeRemoved, replaced entirely
Process identityAn existing process is the targetA fresh, suspended process created to be hollowed
Volatility signalLoadLibrary DLL: dlllist / ldrmodules. Shellcode, PE, reflective: malfindmalfind + vadinfo (claimed vs actual image)

Reporting accuracy: 'code was injected into svchost.exe' understates hollowing. The attacker replaced it while keeping its name and PID as camouflage. It also decides which sub-technique and detections apply.
HACKTHESOCLesson 78Memory forensics47 / 63

Confirming hollowing with two plugins

  1. 1malfindFlags an executable region that does not match the backing file.
  2. 2vadinfoLists the process's memory regions and what should back each one.
  3. 3CompareThe PEB claims svchost.exe, but the mapped image at the base does not match that file.
  4. 4Corroboratepe-sieve or Hollows Hunter automate it; on live hosts Sysmon Event 25 flags image changes.
The claimed-versus-actual image mismatch is the signature of hollowing, distinct from an extra injected region.

Section 8 of 9

Reading a memory image in an investigation

The right plugins, in the right order.

HACKTHESOCLesson 78Memory forensics49 / 63

When memory forensics is the right tool

Reach for it

Little found on disk but the host acts compromised.

  • Fileless or in-memory malware
  • Process injection (malfind)
  • Hidden processes, rootkits (psscan)
  • Live C2, volatile secrets (netscan)

Then corroborate

Memory answers what was live at this instant. Prefetch, Amcache and BAM show if the loader ran, the timeline shows when, firewall or proxy logs show the C2 IP.

Volatility turns opaque RAM into the kind of story EDR gives, for a machine with no EDR or for activity EDR missed.
HACKTHESOCLesson 78Memory forensics50 / 63

The broad-to-narrow plugin rhythm

  1. 1Confirm the imagewindows.info verifies Volatility identified the build.
  2. 2Map the processespslist and pstree for the landscape and lineage.
  3. 3Find what hidpsscan for unlinked or exited processes.
  4. 4Drill innetscan, malfind and cmdline on the suspects.
  5. 5Scope and corroboratehandles, credentials, registry, then artifacts and network logs.
Start broad so you do not miss a hidden process, then focus only on what looks wrong.

Section 9 of 9

Limits, anti-memory-forensics, and corroboration

A powerful niche, with real limits that attackers know.

HACKTHESOCLesson 78Memory forensics55 / 63

A single snapshot, and attackers who know it

One instant, not a history

A process that ran and exited an hour earlier may leave little or nothing. Capture early, before ordinary activity overwrites evidence.

Evasion attempts

Re-linking to reduce psscan hits, avoiding RWX pages that malfind flags, short-lived in-memory payloads that deallocate quickly.

Like timestomping, evasion raises the bar rather than making an attacker invisible; the attempt is often itself an anomaly.

Structural inconsistencies between pslist and psscan, or unusual memory permissions, are detectable.
HACKTHESOCLesson 78Memory forensics56 / 63

Re-link or partially unlinkReduce psscan hitspslist and psscan still disagree
Avoid RWX pagesDodge malfind's permission checkUnusual permission sequences, still detectable
Short-lived in-memory payloadShrink the capture windowWhy you capture early, before it deallocates

HACKTHESOCLesson 78Memory forensics57 / 63

Practical and technical limits

  • Version and symbolsUnusual or very new OS builds can occasionally need extra setup.
  • Size and timeServer memory can be tens or hundreds of GB, so capture and analysis take real time and space.
  • Human interpretationPlugins surface candidates; deciding malicious vs rare-but-legitimate needs judgement and corroboration.

Capture RAM early, start broad with pstree/psscan, drill in with malfind/netscan/cmdline, corroborate everything.

This is the essential Tier-2 discipline for attacks designed to leave nothing on disk.

Key takeaways

  1. 01RAM holds hidden processes, injected code, fileless malware, live C2 and decrypted credentials; capture it first.
  2. 02Capture live with WinPmem, DumpIt, FTK Imager or a VM snapshot; hash it and analyse a copy.
  3. 03Volatility 3: vol.py -f <image> <plugin>; start with pslist/pstree, then psscan for hidden processes.
  4. 04netscan ties PIDs to connections, malfind flags unbacked executable memory, cmdline shows how it launched.
  5. 05Hollowing replaces a trusted process's code; spot it with malfind plus vadinfo, unlike DLL injection.
  6. 06An image is one snapshot; corroborate with artifacts, timeline and network logs before concluding.

Check your understanding, question 1 of 3

You suspect shellcode was written straight into a legitimate process's memory, with no file on disk behind it. Which Volatility plugin is built to find that, and what does it look for?

malfind flags executable memory not backed by a file, often PAGE_EXECUTE_READWRITE: exactly what raw shellcode leaves. ldrmodules catches odd or unlinked DLLs, cmdline shows launch arguments, and handles lists open objects, not memory regions.

Check your understanding, question 2 of 3

windows.pslist shows nothing unusual, but windows.psscan returns PID 4180, PPID 3312, svchost.exe, ExitTime '-'. PID 4180 never appears in pslist. What does this most likely indicate?

pslist walks the active-process list malware can unlink from; psscan scans memory directly. No ExitTime means it was still running, and its parent 3312 is powershell.exe. Hollowing keeps a process visible, unlike unlinking.

Check your understanding, question 3 of 3

svchost.exe has the expected PID and command line, but windows.vadinfo shows its base region does not match the real file on disk, and malfind flags an unbacked executable region at that base. Which technique is this?

Hollowing (T1055.012) keeps a trusted name, PID and command line while the base image no longer matches the file. LoadLibrary DLLs are file-backed and show in dlllist/ldrmodules; unlinking hides, it does not change code; ASLR changes where, not what.
