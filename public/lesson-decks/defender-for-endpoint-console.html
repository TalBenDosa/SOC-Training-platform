Classify the alert: expected activity is not a false positive

True positive

Real malicious activity, recorded with a threat type.

Informational, expected

An accurate detection of sanctioned activity, such as a red team or security test. You want it to keep firing on real attackers.

False positive

Fired with no malicious activity at all. This feeds detection-quality tuning.

Tune alert does not apply to custom detection alerts: fix noisy custom rules in their KQL.

Manage alert sets status (New, In progress, Resolved), assignment and classification. Tune alert, formerly suppression, can hide, resolve or set matching alerts as behaviours.

Working the timeline: five practical moves

Past 30 days by default; the calendar switches to a day, a week or a custom range.

  • SearchA file name, IP or command-line fragment.
  • FlagFlag key events, then enable Flagged events in Filters to rebuild a clean breach timeline.
  • Hunt for related eventsOpens Advanced Hunting with that event plus everything around it on the same device.
  • Additional informationRemediation unsuccessful, Active threat detected, Warning bypassed by user change the story.
  • ExportUp to seven days at a time.

When the question becomes "where else did this happen", move to Advanced Hunting.

Hunt for related events is the fastest bridge from point-and-click to KQL. Warning bypassed by user means the user clicked through a SmartScreen warning.

The InitiatingProcess family: three generations in one row

  • InitiatingProcess* = the process that caused the event, not its subject
  • In DeviceNetworkEvents, InitiatingProcessFileName opened the socket
  • InitiatingProcessSignatureStatus describes the parent, not the new process
Mixing these up is the most common reason a hunt returns the wrong rows. To check the new process's signature, join its SHA1 to DeviceFileCertificateInfo or enrich with FileProfile().

Section 4 of 11

KQL patterns that do the work

A pipeline of operators. Cheapest, most selective filters first: time, ActionType, exact names, then text.

HACKTHESOCLesson 14Defender for Endpoint26 / 89

Order the pipeline: cheapest filters first

KQL is a table, then one | operator per line, each transforming the last output.

  1. 1TableStart from the one table that records the event you want.
  2. 2Timewhere Timestamp > ago(7d): the cheapest cut.
  3. 3ActionTypeMost tables mix event types; keep only the one you mean.
  4. 4Exact names=~ or in~ on file names and accounts.
  5. 5Text matchinghas for whole terms, contains only when you must.
  6. 6Shape the outputsummarize, project: fewer rows and columns, under 64 MB.
Putting a contains on the command line before the time filter makes the engine scan everything. Same answer, far more CPU quota spent.
HACKTHESOCLesson 14Defender for Endpoint27 / 89

Pick the string operator on purpose

OperatorBehaviourUse it for
==Exact, case sensitiveIDs, ActionType
=~Exact, case insensitiveFile names: FileName =~ "rundll32.exe"
in~ (...)Case-insensitive list matchA set of process names
has / has_anyWhole-term match, fast (uses the term index)Command-line tokens: has "-EncodedCommand"
containsSubstring anywhere, slowerFragments that are not whole terms
startswith / endswithPrefix or suffixPaths: FolderPath startswith @"C:\Users\Public\"
Prefix Windows paths with @ to make the string verbatim, otherwise every backslash must be doubled.
HACKTHESOCLesson 14Defender for Endpoint28 / 89

Aggregate, shape and enrich

  • summarizecount(), dcount(), make_set(x, 20), min/max(Timestamp) for first and last seen.
  • bin + rendersummarize count() by bin(Timestamp, 1h), then render timechart.
  • arg_max(Timestamp, *)The latest full row per key, e.g. one current row per device from DeviceInfo.
  • let / extendName a list or subquery once; parse_json(AdditionalFields) turns JSON into fields.
  • projectKeep only needed columns, which also keeps you under the 64 MB limit.
  • invoke FileProfile()Adds GlobalPrevalence, GlobalFirstSeen, Signer, SignatureState. Up to 1,000 rows, best on SHA1.
A DLL with single-digit global prevalence, first seen yesterday and unsigned, is a strong lead. A file seen millions of times and signed by its vendor usually is not.
HACKTHESOCLesson 14Defender for Endpoint29 / 89

Encoded PowerShell, counted per device and parent

Hunting output is a candidate list, not a verdict. The jump host runs a signed management script every morning; the Word-spawned single run is the lead. Read the surrounding columns, never the match alone.

Section 5 of 11

Beyond processes: file, registry, load, logon

The evidence that confirms or kills a lead usually sits in the other Device tables.

HACKTHESOCLesson 14Defender for Endpoint35 / 89

Four tables, four questions

Where from?

DeviceFileEvents

FileOriginUrl / FileOriginIP for downloads; PreviousFileName for renames; RequestSourceIP for SMB writes from another host.

Persistence?

DeviceRegistryEvents

RegistryValueSet on \CurrentVersion\Run keys; PreviousRegistryValueData separates new from updated.

What got loaded?

DeviceImageLoadEvents

rundll32 or regsvr32 loading a DLL from a user-writable path, or a signed binary side-loading.

Who, and how?

DeviceLogonEvents

LogonType: Interactive, RemoteInteractive (RDP), Network, Batch, Service. IsLocalAdmin flags admin.

An empty SHA1 in DeviceFileEvents is not suspicious by itself: the file can be locked, remote or virtual.

Logon shapes to remember: many failures from one RemoteIP across many accounts is spraying; one account suddenly making Network logons to many servers is lateral movement.
HACKTHESOCLesson 14Defender for Endpoint36 / 89

Where did it come from, and does it start at logon?

  • FileOriginUrl names the download source of a new executable
  • Empty PreviousRegistryValueData: a brand-new autostart, not an update
  • Exclude trusted installers by InitiatingProcessFileName after one look
Renames show in PreviousFileName and PreviousFolderPath: a DLL renamed to .txt, or a ransomware mass rename. RunOnce keys grant autostart too.
HACKTHESOCLesson 14Defender for Endpoint37 / 89

HACKTHESOCLesson 14Defender for Endpoint38 / 89

Two control-event traps that flip a conclusion

Audited ASR is not blocked

An ...Audited Attack Surface Reduction event means the behaviour was logged and allowed to run. Treat it as evidence the behaviour happened.

ConnectionSuccess can lie

Network protection blocks after the TCP handshake, so DeviceNetworkEvents may still show ConnectionSuccess. Look for ExploitGuardNetworkProtectionBlocked in DeviceEvents.

Both traps lead to the wrong statement in a case note: 'ASR stopped it' when it did not, or 'the C2 connection worked' when it was blocked.

Section 6 of 11

Joins and the alert tables

Single tables answer narrow questions. Joins answer the compound ones.

HACKTHESOCLesson 14Defender for Endpoint42 / 89

Three join rules that keep results honest

  • Process to network keysDeviceId plus ProcessId = InitiatingProcessId. PIDs are reused, so guard with creation time or ProcessUniqueId.
  • Bare join = inneruniqueIt de-duplicates the left side on the key and silently drops rows. Write kind=inner, leftouter or leftanti.
  • Filter both sides firstTime and ActionType inside each side, project early, smaller side on the left.
  • AlertInfo + AlertEvidenceJoin on AlertId to turn alerts into IOCs and to find hosts where an alerted artifact has no alert.
A join of two unfiltered 30-day tables is the classic way to hit the 10-minute timeout or the CPU quota. leftanti answers 'in the left table but never in the right'.
HACKTHESOCLesson 14Defender for Endpoint43 / 89

Join flavours: always name one

kind=ReturnsUse it for
(none) = inneruniqueLeft side de-duplicated on the key first, then matchedAlmost never what you meant: rows vanish silently
innerEvery matching pairProcess plus its network events
leftouterAll left rows, matched or notProcesses with no network activity
leftantiLeft rows that never match the rightAlerted artifacts never seen elsewhere, or the reverse
The symptom of innerunique is fewer rows than you expected with no error. Quiz 2 tests exactly this.
HACKTHESOCLesson 14Defender for Endpoint44 / 89

Office child processes that reached a public IP in 2 minutes

Point at the three guards: the explicit kind=inner, DeviceId plus PID, and the equal creation times. This shape cannot run as an NRT detection because it joins two tables.
HACKTHESOCLesson 14Defender for Endpoint45 / 89

The guards that make that join correct

  1. 1Name the flavourkind=inner, so no left rows are silently dropped.
  2. 2Join on device plus PIDDeviceId and ProcessId == InitiatingProcessId.
  3. 3Guard against PID reuseEqual creation times, or ProcessUniqueId, so a later process with the same PID cannot match.
  4. 4Bound the timeNetwork within 2 minutes of process creation.
  5. 5Filter both sides firstTime, ActionType and project inside each side; smaller side on the left.
Because it joins two tables, this shape cannot run as a continuous (NRT) detection. Split it or run it hourly.
HACKTHESOCLesson 14Defender for Endpoint46 / 89

Alerts into IOCs: every file and IP in today's alerts

  • AlertInfo: one row per alert, from every Defender product
  • AlertEvidence: the entities of each alert; join on AlertId
  • The output is a hunt list of hashes and IPs, not a verdict
EvidenceRole in AlertEvidence says whether an entity was impacted or only related. Filter on it when you only want what was actually hit.
HACKTHESOCLesson 14Defender for Endpoint47 / 89

Two alert tables, two jobs

AlertInfo

One row per alert: AlertId, Title, Category, Severity, ServiceSource, DetectionSource, AttackTechniques.

AlertEvidence

The entities of each alert: EntityType, EvidenceRole (impacted or related), and entity columns such as SHA1, RemoteIP, AccountName.

Joined on AlertId

Turn alerts into IOCs, then hunt those IOCs in the Device tables to find hosts where the artifact exists but nothing fired.

That last use is how you measure scope beyond what alerted, shown on the next slide with the DLL.

From hunt to custom detection rule

A hunt you trust should not depend on someone remembering to run it.

HACKTHESOCLesson 14Defender for Endpoint51 / 89

Creating a custom detection rule, in order

  1. 1Run and validate the huntIn Advanced Hunting, then choose Create detection rule.
  2. 2Alert detailsName, frequency, title, severity, category, MITRE techniques, description, recommended actions.
  3. 3Impacted assetsMap DeviceId, AccountSid or InitiatingProcessAccountUpn.
  4. 4ActionsNone for a new rule: alert-only first.
  5. 5ScopeAll devices, or chosen device groups.
  6. 6CreateIt runs immediately and first checks the past 30 days.
Managing rules needs Security settings (manage) or Security Administrator, plus permission over every device in the rule's scope.
HACKTHESOCLesson 14Defender for Endpoint52 / 89

What the rule query must do

  • Return the key columnsTimestamp, DeviceId, ReportId from the same event: alert time, device-group scope, process tree.
  • Survive summarizeAggregation drops them; recover with arg_max(Timestamp, ReportId) per entity.
  • Map the assetAlso return a strong identifier: DeviceId, AccountSid or InitiatingProcessAccountUpn.
  • Skip the time filterThe service prefilters by lookback and evaluates ingestion_time(), so late events are not missed.
  • Stay under 150Each run creates at most 150 alerts. Tune out normal activity before you save.
Create from Advanced Hunting with Create detection rule after running the query, so you validate results first. Managing rules needs Security settings (manage) or Security Administrator, plus permission over every device in scope.
HACKTHESOCLesson 14Defender for Endpoint53 / 89

An aggregated rule that keeps the required columns

  • A plain summarize would drop Timestamp and ReportId
  • arg_max keeps them from the latest matching event per device
  • No time filter: the service applies the rule's lookback itself
Without Timestamp, DeviceId and ReportId from the same event, the alert cannot land in the right device group or build its process tree.
HACKTHESOCLesson 14Defender for Endpoint54 / 89

Actions a rule can take, and the discipline

from DeviceId

Devices

Isolate, collect investigation package, run AV scan, initiate investigation, restrict app execution.

from SHA1

Watch a week of alerts, tune the KQL until every alert is one you would act on, and only then attach isolation.

HACKTHESOCLesson 14Defender for Endpoint59 / 89

Full or selective isolation

Full isolation

Cuts all network access except the Defender service. You can still investigate and run Live Response. Offline devices get it retried for up to three days.

Selective isolation

Keeps Outlook and Teams working. Use it where PAC, WPAD or static web proxies are in play, because a fully isolated device behind a proxy may not recover.

Key takeaways

  1. 01Work outside in: Incidents queue and Attack story for scope, alert story for lineage, device timeline for host detail.
  2. 02Advanced Hunting: 30 days, UTC, 100,000 rows, 10 minutes. Filter time and ActionType first, pivot on SHA1, not SHA256.
  3. 03InitiatingProcess columns are the process that caused the event. Always state the join kind: a bare join is innerunique.
  4. 04Custom detections return Timestamp, DeviceId and ReportId; NRT needs one table with no joins. Start every rule alert-only.
  5. 05Stop and quarantine is a one-off clean-up; an indicator is the lasting block. Isolation keeps Live Response working.
  6. 06Live Response allows one session per device. Check Action center Pending before closing: pending actions expire in 7 days.
