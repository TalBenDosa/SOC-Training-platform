Section 1 of 8

What DHCP is and why it exists

Dynamic Host Configuration Protocol: settings handed out automatically.

HACKTHESOCLesson 81DHCP explained6 / 51
DHCP is a hotel check-in desk: you arrive with nothing and leave with a room, directions and a set number of nights.

Room number = IP address. Front desk = gateway. Hotel directory = DNS. Nights = the lease. When you leave, the room returns to the pool.

Without DHCP an administrator would configure 5,000 laptops by hand, and again every time one moved.
HACKTHESOCLesson 81DHCP explained7 / 51

Without DHCP, every setting is typed by hand

Manual configuration

An administrator types an IP, mask, gateway and DNS on each device. 5,000 laptops means 5,000 configurations, repeated every time one moves.

With DHCP

The device asks on connect and receives everything in under a second. Automatic, temporary and centrally managed.

Centrally managed is the word that matters for a SOC: one server sees and records every assignment.
HACKTHESOCLesson 81DHCP explained8 / 51

Four essentials, on a time-limited lease

  • IP addressThe device's identity on the network.
  • Subnet maskWhich nearby addresses count as local.
  • Default gatewayThe door out to the rest of the network and the internet.
  • DNS server addressesSo the device can translate names into addresses.

Automatic, temporary and centrally managed: the foundation of why its logs matter.

Devices renew before the lease expires, so a laptop may keep an address for days, then get a different one after a long absence.
HACKTHESOCLesson 81DHCP explained9 / 51

Each essential, and what breaks without it

SettingIf it is missing or wrong
IP addressNo identity: the device cannot talk on the network at all
Subnet maskIt misjudges which addresses are local and sends traffic the wrong way
Default gatewayLocal devices work, but nothing beyond the subnet or on the internet
DNS serversAddresses work but names do not: "the internet is down" while IPs still reach
The last two rows matter later: a rogue DHCP server changes exactly the gateway and DNS, and everything still appears to work.

Section 2 of 8

The DORA exchange and its ports

Four messages, UDP, server on 67, client on 68.

HACKTHESOCLesson 81DHCP explained11 / 51

DORA: four steps the instant a device joins

  1. 1DiscoverThe device broadcasts: is there a DHCP server out there? It does not yet know who the server is.
  2. 2OfferA DHCP server replies with an IP address, gateway and DNS.
  3. 3RequestThe device accepts, broadcasting so other servers know their offers were declined.
  4. 4Acknowledge (ACK)The server confirms and records the lease: which address went to which device, for how long.

UDP, server listens on port 67, client on port 68: fixed ports let broadcasts find their way before the client has an identity.

Behind the scenes the server identifies devices by MAC address and keeps a scope (its address pool) and a lease table.
HACKTHESOCLesson 81DHCP explained12 / 51

DORA as a packet capture shows it

  • Source 0.0.0.0: the device has no address yet
  • Destination 255.255.255.255: a broadcast to everyone on the segment
  • Client always on UDP 68, server on UDP 67
Four packets in this order is the signature of a successful join. The Request is broadcast too, so any other server that offered learns it was declined.
HACKTHESOCLesson 81DHCP explained13 / 51

What the DHCP server keeps track of

MAC address

The network card's hardware address: how the server recognises a device and can offer a returning one the same IP.

Scope

The pool of addresses this server is allowed to hand out.

Lease table

Every current assignment: MAC to IP to time. This running record is what answers the analyst's question.

Once students see the server keeps MAC, IP and time together, the SOC value of DHCP logs is obvious before you say it.
HACKTHESOCLesson 81DHCP explained14 / 51

Defined in RFC 2131. Later RFCs add DHCPFORCERENEW (RFC 3203) and the DHCPLEASEQUERY family (RFC 4388).
HACKTHESOCLesson 81DHCP explained15 / 51

Four short stories told by message types

Healthy join

DISCOVER, OFFER, REQUEST, ACK.

Address conflict

The client probes the offered address, finds it in use, and sends DECLINE.

Stale request

Wrong subnet or expired lease: the server answers NAK and the client starts over.

Clean exit

A device shutting down cleanly sends RELEASE to give the address back early.

Option 53 carries the number. Reading the value is faster than reading the description in a capture.

Section 3 of 8

The lease lifecycle: renewal and rebinding

An ACK starts a clock, governed by timers T1 and T2.

HACKTHESOCLesson 81DHCP explained17 / 51

From bound to expired

  1. 1BOUNDHolding a valid lease, doing nothing about it yet.
  2. 2RENEWING at T1 (50%)Unicast DHCPREQUEST to the original server only. Quiet, invisible to others.
  3. 3REBINDING at T2 (87.5%)Original server silent: broadcast DHCPREQUEST to any server on the segment.
  4. 4EXPIREDNo answer by end of lease: give up the address and restart full DORA.
Most DHCP traffic in a day is quiet unicast T1 renewals, not fresh broadcasts.
HACKTHESOCLesson 81DHCP explained18 / 51

Timer arithmetic for common lease lengths

Defaults: T1 = 50% of the lease, T2 = 87.5%. Options 58 and 59 can set them explicitly.

Lease (option 51)T1: start renewingT2: start rebinding
24 hours (86400 s)12 hours (43200 s)21 hours (75600 s)
8 hours (28800 s)4 hours (14400 s)7 hours (25200 s)
8 days (691200 s)4 days (345600 s)7 days (604800 s)
Knowing the lease length tells you how often a healthy client should appear in the log. A client showing up far more often is the anomaly.
HACKTHESOCLesson 81DHCP explained19 / 51

A 24-hour lease, renewed and then rebound

  • T1 renewal goes only to the server that issued the lease
  • T2 rebinding broadcasts to any server
  • Frequent rebinding or full DORA: is the usual server down, or was it rogue?
An orphaned client whose rogue server disappeared is forced back onto the open segment to find a new one.
HACKTHESOCLesson 81DHCP explained20 / 51

Normal renewal traffic versus a pattern worth checking

Normal

Quiet unicast T1 renewals between each device and its known server. Most DHCP activity in a day looks like this.

Worth checking

A device jumping to broadcast REBINDING, or running full DORA far more often than its lease predicts.

Possible causes

Its usual server is unreachable or unstable, or it was a rogue server that has since disappeared.

The orphaned-client case is subtle: a client that suddenly rebinds may be recovering from a rogue lease, which means it was exposed earlier.

Far more than the basic four, and how leases cross subnets.

HACKTHESOCLesson 81DHCP explained23 / 51

Options 43 and 66: provisioning, or redirection

Legitimate use

Zero-touch provisioning: point access points at a wireless controller, VoIP phones at a provisioning server, PXE clients at a boot image.

Abuse by a rogue server

The same options point new devices at an attacker-controlled provisioning server instead.

When reviewing a suspicious Offer, check 43 and 66, not only the gateway and DNS.

These options decide where a device fetches its configuration or boot image from, so a wrong value can control the device from its first boot.
HACKTHESOCLesson 81DHCP explained24 / 51

A relay agent carries broadcasts across subnets

A router stands in for the client so a central server can lease a subnet it cannot reach by broadcast.

  • Routers do not forward broadcasts; the relay unicasts instead
  • giaddr picks the scope and is the reply's return address
  • An unexpected giaddr or a far-off server-id deserves a second look
The relay agent is almost always the local router or Layer-3 switch.
HACKTHESOCLesson 81DHCP explained25 / 51

Relay details that matter in an investigation

  • giaddr picks the scopeThe server uses the relay's address to choose which subnet's pool to offer from.
  • giaddr is the return pathThe reply goes back to the relay on port 67, which delivers it on the client's segment.
  • Unexpected giaddrAn Offer naming a router you do not expect on that path deserves a second look.
  • Distant server-idAn Offer from a server far outside the local subnet is also worth checking.
In a branch office with no local server, every lease you see in the central server's log arrived through a relay.

Section 5 of 8

What DHCP looks like in practice

Invisible day to day, but real and observable.

HACKTHESOCLesson 81DHCP explained27 / 51

Three places to see DHCP

On the wire

DHCP Discover from 0.0.0.0 to 255.255.255.255, then Offer, Request, ACK. Four packets in order: a successful join.

On a device

ipconfig /all, or ip addr / nmcli on Linux: IP, DHCP server, lease times, gateway, DNS. ipconfig /release and /renew drive DORA by hand.

On the server

The lease table: IP, MAC, hostname, lease start and expiry. With its event log, the artifact that matters most to a SOC.

Over a day, that log is a timeline of which devices were present and what address each held, whether or not anyone is watching.
HACKTHESOCLesson 81DHCP explained28 / 51

On the device: what DHCP handed out

  • DHCP Server: which server granted this lease. Compare it with the inventory
  • Lease Obtained / Expires: a 24-hour lease, so T1 falls at 21:00
  • Default Gateway and DNS Servers: exactly what a rogue server would change
On Linux, ip addr or nmcli shows the same facts. ipconfig /release and /renew drive the DORA exchange by hand.

Section 6 of 8

DHCP snooping against rogue servers

A switch-level, preventive control.

HACKTHESOCLesson 81DHCP explained32 / 51

Trusted and untrusted ports

Trusted port

Connected to the real, authorised DHCP server. Offers and ACKs may come from here.

Untrusted port

Every ordinary port where end users plug in. A DHCP Offer from here is silently dropped.

This single rule closes off the rogue-server threat at the network layer, before it reaches a victim.
HACKTHESOCLesson 81DHCP explained33 / 51

What a snooping switch does with each DHCP packet

  1. 1Classify the portTrusted (toward the real server) or untrusted (every user port).
  2. 2Is it server traffic?An Offer or ACK is server traffic; a Discover or Request is client traffic.
  3. 3Offer or ACK on untrusted?Silently dropped. The client never sees the rogue reply.
  4. 4Record legitimate leasesEach real ACK adds IP, MAC and port to the binding table.
The rule is simple, which is why it is effective: no signatures, just which port is allowed to speak as a server.
HACKTHESOCLesson 81DHCP explained34 / 51

The binding table powers more defenses

Snooping records the IP, MAC and port of every legitimate lease it observes.

  • Dynamic ARP InspectionStops attackers forging address-resolution replies.
  • IP Source GuardStops a device sending traffic from an IP it was never leased.
  • Option 82Records which switch and port a Discover came from: per-area pools, and a lease tied to a physical location.

Snooping prevents, it does not monitor. Verifying it is enabled on access switches is a valuable SOC or audit finding.

A switch without snooping, or a segment outside its coverage, is still exposed, so keep watching DHCP logs.
HACKTHESOCLesson 81DHCP explained35 / 51

One binding, four packets, four outcomes

Binding table entry: 10.20.5.66 / A4:5E:60:B1:C2:D3 / access port 12.

Packet seen by the switchControlOutcome

Section 7 of 8

Why DHCP matters to a SOC analyst

The IP-to-device Rosetta Stone, plus a few abuses to watch.

HACKTHESOCLesson 81DHCP explained37 / 51
Which actual machine was 10.4.2.17 at 2:14 a.m.? The DHCP lease log tells you.

Alerts name IPs, but IPs are leased temporarily and reused. The lease log ties that IP to a MAC address and hostname at that time.

This pivot is routine and essential in nearly every investigation.
HACKTHESOCLesson 81DHCP explained38 / 51

One IP, two machines in one day

Lease log lines for 10.4.2.17. The alert fired at 02:14 on 08/25.

  • Morning: LAPTOP-HR03 held the address, then released it at 17:30
  • 22:51: the same IP assigned to a different MAC, WKS-DEV11
  • At 02:14 the lease belonged to WKS-DEV11: that is the machine to examine
A common mistake is to search for the IP and take the first hostname that appears. That would send the investigation to the wrong laptop.
HACKTHESOCLesson 81DHCP explained39 / 51

The IP-to-device pivot, step by step

  1. 1Note the IP and exact timeNormalise the alert time to the log's time zone first.
  2. 2Open the right logThe audit file for that weekday, or the same data in the SIEM.
  3. 3Find the last assign or renewThe most recent ID 10 or 11 for that IP before the alert time.
  4. 4Check nothing ended itNo release (ID 12) or expiry between that line and the alert.
  5. 5Read MAC and hostnameThen confirm the MAC against the asset inventory.
Windows writes one audit file per weekday, so the file for a given day is reused the following week. Ship the logs to the SIEM so the history outlives the file.
HACKTHESOCLesson 81DHCP explained40 / 51

Three DHCP abuses to watch

Rogue DHCP server

Clients accept the first offer, so a rogue server hands out a malicious gateway or DNS: man-in-the-middle. Red flag: more than one server offering.

DHCP starvation

Flood fake Discovers with spoofed MACs until the pool is exhausted: denial of service, sometimes setup for a rogue server.

Unexpected devices

A lease requested by an unknown MAC can reveal something new and unwanted plugged into the network.

A rogue server may be planted by an attacker or be a misconfigured router.
HACKTHESOCLesson 81DHCP explained41 / 51

Worked example: a rogue DHCP server

One client, a few seconds of a packet capture on its network segment.

HACKTHESOCLesson 81DHCP explained43 / 51

Two offers, two server IDs

  • 10.4.2.250, not in the asset inventory, answers first
  • 10.4.0.1, the known authorised server, answers a moment later
  • The client took the first Offer: its lease came from the unauthorised device
Why a capture: your own DHCP server logs only the messages it sent and received, so it would never contain another server's Offer or ACK. From this moment the client's gateway and DNS were whatever the rogue chose.

Questions the analyst asks next

  1. 1Authorised?Is 10.4.2.250 a known DHCP server in the inventory? If not, confirmed rogue.
  2. 2Which port?Where did its traffic originate, and does DHCP snooping cover that port?
  3. 3What was handed out?Recover the gateway and DNS from the client's config: was traffic redirected?
  4. 4Who else?Which other clients on the segment got offers from 10.4.2.250? It broadcasts to everyone.

Key takeaways

  1. 01DHCP automatically gives a device its IP, subnet mask, gateway and DNS on a time-limited lease.
  2. 02DORA (Discover, Offer, Request, ACK) runs over UDP 67/68; Option 53 names eight message types.
  3. 03Clients renew by unicast at T1 (50%) and rebind by broadcast at T2 (87.5%).
  4. 04Relay agents unicast across subnets using giaddr; options 43 and 66 can redirect new devices.
  5. 05The lease log maps an IP to a MAC and hostname at a moment: the SOC's IP-to-device pivot.
  6. 06Watch for multiple servers, pool exhaustion (ID 14) and unknown MACs; DHCP snooping prevents rogues.

A DHCP client reaches T1 (50% of the lease) with no reply from its server, then reaches T2 (87.5%) still without a DHCPACK. What does the client do at each stage?

T1 is RENEWING: a quiet unicast to the issuing server. T2 is REBINDING: a broadcast so any server can renew. Restarting DORA happens only at full expiry, and DHCPRELEASE gives an address back rather than keeping it.
