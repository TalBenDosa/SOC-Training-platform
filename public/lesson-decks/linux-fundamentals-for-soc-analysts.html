Four words everything else builds on

Shell

The program that reads what you type and runs it. bash is the most common.

Permissions

Rules for who may read, write or execute a file. Misreading them is how attackers escalate.

Daemon

A program running in the background with nobody at the keyboard. Names end in d: sshd, crond, systemd.

Process

One running instance of a program right now, the thing ps lists.

Pin these four down before anything else. The goal is investigative depth, not sysadmin depth.

The Linux filesystem and where things live

One tree under /, no drive letters, and a handful of directories that carry the evidence.

HACKTHESOCLesson 09Linux for SOC analysts8 / 85

Reading a permission string at a glance

  • Three classes: owner, group, others. r=4, w=2, x=1 summed per class
  • Leading character is the type: - file, d directory, l symlink
  • Others with w (666, 777) means any user can modify it
Walk the example -rwxr-xr-- = 754 aloud first, then this one. A world-writable script in /tmp owned by the web user is a classic tampering vector.
HACKTHESOCLesson 09Linux for SOC analysts9 / 85

Turn rwx into 754 at a glance

ClassBitsAdds up to
Ownerrwx4 + 2 + 1 = 7
Groupr-x4 + 0 + 1 = 5
Othersr--4 + 0 + 0 = 4
r=4, w=2, x=1 per class, summed. The leading character is the type: - file, d directory, l symlink. Read it left to right.
HACKTHESOCLesson 09Linux for SOC analysts10 / 85

Two permission patterns that should trigger instinct

-rw-rw-rw- / drwxrwxrwx

World-writable

Any user can modify it. A classic tampering and privilege-escalation vector.

-rwsr-xr-x

setuid

An s in the owner execute slot: the program runs with the owner's privileges whoever launches it. A setuid-root shell copy, or a setuid-root binary in an odd place, screams escalation.

Example from the lesson: a root-owned, setuid copy of a shell sitting in /tmp. Learn to read these at a glance and the filesystem tells you where the attacker has been.
HACKTHESOCLesson 09Linux for SOC analysts11 / 85

Four directories to grep first in any triage

  • /etcSystem config in plain text: passwd, sshd_config, cron. Auth or boot changes leave a fingerprint here.
  • /var/logPrimary evidence: auth.log/secure, syslog/messages, web logs, audit/audit.log.
  • /tmp and /dev/shmWorld-writable staging ground. An executable running from here should always make you look twice.
  • /home and /root.bash_history, ~/.ssh/authorized_keys and dropped tools: gold during an investigation.
Linux puts almost all forensic weight in a handful of directories. Knowing which holds what is seconds versus grepping blindly.

Users, sudo, and privilege

The whole security model turns on one number: the uid, and uid 0 is root.

HACKTHESOCLesson 09Linux for SOC analysts13 / 85

Root versus regular users, and how sudo bridges them

  • Root (uid 0)Reads any file, kills any process, changes any config, loads kernel modules.
  • Regular usersConfined to their own files and whatever they were explicitly granted.
  • sudoAdmins log in as themselves and elevate specific commands. Rules live in /etc/sudoers and /etc/sudoers.d/.
  • Every sudo is loggedRecords the human who elevated and the exact command they ran.
  • Abuse signssudo -l to enumerate elevation; sudoers rules allowing an editor, interpreter or shell as root.
A sudo rule letting a user run /usr/bin/find or /usr/bin/vi as root is effectively a root shell. Read sudoers with that lens.
HACKTHESOCLesson 09Linux for SOC analysts14 / 85

uid 0 is the whole game

root (uid 0)

The superuser: reads any file, kills any process, loads kernel modules. Admins log in as themselves and use sudo for attribution.

Benign

Exactly one uid-0 account, root. Service accounts carry /usr/sbin/nologin as their shell.

Backdoor

A second account with uid 0, or a service account whose shell changed from nologin to /bin/bash.

An attacker's whole objective is to reach uid 0. Any uid-0 account besides root is a backdoor, full stop.
HACKTHESOCLesson 09Linux for SOC analysts15 / 85

Reading /etc/passwd: scan the uid and shell fields

  • Any uid-0 account other than root is a backdoor
  • A service account with a real shell is a tampering indicator
  • The x means the hash lives in /etc/shadow, readable only by root
If a normal user can read /etc/shadow, permissions are badly wrong. If an attacker exfiltrates it, they can crack the hashes offline.
HACKTHESOCLesson 09Linux for SOC analysts16 / 85

Reading /etc/passwd: the seven fields

FieldExampleWhat to check
usernamesvc-webA service account that should not log in

Scan the uid field and the shell field first. Those two carry almost all the investigative value in this file.
HACKTHESOCLesson 09Linux for SOC analysts17 / 85

Identity questions come first on any Linux host

  • Are there any uid-0 accounts besides root?
  • Did a service account's shell change from nologin to a real shell?
  • Who is in the sudo or wheel group, and did membership change recently?
  • What did sudo actually run, and by whom, in the incident window?
  • Was there a burst of sudo -l or failed sudo attempts?
Privilege on Linux is concentrated in uid 0, so the attacker's objective is usually to reach it. These files and logs record every path there.

Section 3 of 12

Processes, shells, and persistence

Read the process tree to catch live execution, and read the disk to catch what survives a reboot.

HACKTHESOCLesson 09Linux for SOC analysts19 / 85

The command line is where the truth lives

Inspect with ps and top. Four fields matter.

  • PIDThe process ID.
  • PPIDThe parent PID: what launched it.
  • USERThe account it runs as.
  • Full command lineA benign-looking name can hide a malicious command line, so always read the full args.
Reading parentage, what spawned what, is one of the highest-value skills in Linux triage.
HACKTHESOCLesson 09Linux for SOC analysts20 / 85

A shell's parent is the whole story

Benign

bash whose parent is sshd or a login session: a human working. Normal, expected, attributable to a real user.

Alarm

/bin/bash whose PPID is nginx, apache2, java or php-fpm: a network-facing service spawned a shell. Textbook web-exploit to command execution.

Process parentage, what spawned what, is the single highest-value Linux triage signal. The name bash is innocent; the parent is not.
HACKTHESOCLesson 09Linux for SOC analysts21 / 85

A shell under a web server is the alarm

  • A shell is normal in a human session, not under nginx, apache or java
  • PPID 1122 is the nginx worker: a web-facing service spawned bash
  • A shell wired to a network socket is a reverse shell, full stop
In the lesson's listing the next child of this shell opens an outbound connection to an attacker IP. That is the reverse shell; we cover how to catch it in section 6.
HACKTHESOCLesson 09Linux for SOC analysts22 / 85

Where attackers persist, and where you look

SpotLocationMITRE
cron/etc/crontab, /etc/cron.d/, /etc/cron.{hourly,daily}/, /var/spool/cron/T1053.003

Execution is temporary; persistence is how attacker code survives a logout or reboot. Unlike a live process, it sits on disk waiting for you to read it.
HACKTHESOCLesson 09Linux for SOC analysts23 / 85

Check the persistence hotspots in order

  1. 1cronSystem and per-user crontabs. A job running from /tmp or fetching a raw IP on a timer is persistence (T1053.003).
  2. 2systemd units.service files in /etc/systemd/system/. A unit pointing at an unusual binary is a common persistence mechanism (T1543.002).
  3. 3shell rc files~/.bashrc, /etc/profile. One appended line re-launches a payload on every login.
  4. 4authorized_keysA key added to ~/.ssh/authorized_keys is passwordless re-entry (T1098.004). Check modification times.
Execution is temporary; persistence sits on disk waiting for you to read it. Compare modification times against the incident window.
HACKTHESOCLesson 09Linux for SOC analysts24 / 85

Inspecting the persistence hotspots

  • Check modification times: did anything change in the incident window?
  • Red flag: a job that references /tmp, a raw IP, or download-and-execute
  • Red flag: an SSH key no admin recognizes
The lesson's example cron line runs every minute as root, fetching a script from a raw IP and piping it straight into a shell. Describe it, then ask: does any admin recognize this job?

The logs that matter: syslog, auth.log, auditd

Know which source answers which question and you can rebuild an attack in order.

HACKTHESOCLesson 09Linux for SOC analysts26 / 85

Match the log to the question

Log sourceWhat it answers
/var/log/auth.log (Debian/Ubuntu) or /var/log/secure (RHEL/CentOS)Authentication and sudo: SSH logins and failures, sudo and su, PAM events
/var/log/syslog (Debian/Ubuntu) or /var/log/messages (RHEL/CentOS)Service and kernel context: kernel messages, service start/stop, daemon output
auditd (/var/log/audit/audit.log)Command execution and file access: execve records at command level
journald (read with journalctl)Structured per-service history, filterable by unit, time or boot
last (wtmp) / lastb (btmp)Session history: successful logins and reboots (wtmp), failed logins (btmp)
All plain text under /var/log except the journal, so grep, awk and the SIEM work directly. journald filters by unit (journalctl -u ssh), time (--since) or prior boot (-b -1).
HACKTHESOCLesson 09Linux for SOC analysts27 / 85

One auth.log format, three outcomes

Point at each labelled field. The sequence matters more than any single line.
HACKTHESOCLesson 09Linux for SOC analysts28 / 85

Reading auth.log: failures, and the sudo audit trail

  • invalid user = the account does not exist (enumeration)
  • Plain Failed password = account exists, wrong password (brute force, spray)
  • sudo records who, the tty, the working dir, as whom, and the exact COMMAND
This mirrors the Windows wrong-password versus no-such-user distinction. A success looks like: Accepted password for alice from 10.0.0.5.
HACKTHESOCLesson 09Linux for SOC analysts29 / 85

'invalid user' versus 'Failed password': two stories

Line says 'invalid user'

The account does not exist. A burst of these is username enumeration: the attacker is guessing names and mostly missing.

Plain failed password

The account exists, the password was wrong. A burst is brute force or spray against real accounts, far more serious.

This mirrors the Windows wrong-password versus no-such-user distinction. The exact wording in auth.log tells you which one you are watching.
HACKTHESOCLesson 09Linux for SOC analysts30 / 85

auditd execve: every command, tied to the real human

  • a0, a1, a2: the executable and every argument
  • uid=33 is www-data, but auid=1000 is alice: the original human
  • Captures the command even when no shell history survives
auth.log tells you who logged in, not every command that ran. auditd hooks the kernel; the execve rule gives command-level visibility, including non-interactive commands from services and scripts.
HACKTHESOCLesson 09Linux for SOC analysts31 / 85

Reading an auditd execve record

FieldWhat it holdsWhy it matters
a0, a1, a2 ...Each argument of the commandThe full command even if history is cleared
uidThe effective userWho the command ran as at the time
auidThe audit login uidTies the action to the original human after sudo/su
syscall59 on x86-64execve: a program was executed
auid is the field that survives a privilege change. It answers which real person is behind an action, even after sudo or su.
HACKTHESOCLesson 09Linux for SOC analysts32 / 85

journalctl -u ssh: the same story, structured

  • -u ssh filters to one unit; --since bounds the window
  • Structured per-service history when auth.log is rotated or absent
  • The same Accepted-login evidence, read from journald instead
journald is the fourth named log source. This completes the match-log-to-question promise: all four are now read on a slide, not just described.
HACKTHESOCLesson 09Linux for SOC analysts33 / 85

last, wtmp and btmp: who logged in, and who failed

  • last (wtmp)Reads /var/log/wtmp: the login-session history, who logged in, from where, and for how long.
  • lastb (btmp)Reads /var/log/btmp: failed login attempts, a quick view of brute-force pressure on the host.
  • Why it mattersFor SSH-compromise triage, session history is core evidence beside auth.log and auditd.
wtmp and btmp are easy to forget, but for a login-based intrusion they place the attacker in a session with times and a source.

Reading Linux attack artifacts: what to ask

Each intrusion pattern leaves an artifact. Learn the indicator and the question.

HACKTHESOCLesson 09Linux for SOC analysts35 / 85

SSH brute force, then the success that matters

  • T1110.001: a flood of failures from one source against root, admin, oracle
  • An Accepted line from the same source right after the flood is the compromise
  • Next: what did that session do? Check auditd and history
Internet-facing SSH is attacked constantly, so failures alone are noise. Watch for Accepted password or Accepted publickey from that same source.
HACKTHESOCLesson 09Linux for SOC analysts36 / 85

Four Linux attack patterns and their artifacts

PatternArtifact you readThe question
SSH brute force (T1110.001)auth.log flood, then one AcceptedHow many failures, then a success?
Reverse shell (T1059.004)A shell parented by a web serviceWhat outbound IP and port?
Suspicious cron (T1053.003)Cron entry pulling from /tmp or an IPWhen was it last modified?

Each pattern pairs an indicator with the question that turns an alert into a conclusion. Learn both halves, not just the indicator.
HACKTHESOCLesson 09Linux for SOC analysts37 / 85

Three more patterns and the questions they raise

T1059.004

Reverse shell

A shell parented by a web or service process, opening a socket out.

  • What is the PPID?
  • Which outbound IP and port, known-bad?
  • Matching exploit in the access log?

T1053.003

Suspicious cron

A job that runs from /tmp, names a raw IP, or downloads and executes.

  • When was the file modified?
  • Does any admin recognize it?
  • Does it explain network beaconing?

T1105

Malicious download

wget or curl to an external IP, writing to /tmp, then made executable and run.

  • URL or IP reputation?
  • Was the file made executable and run?
  • Launched by a human or a web service?
A cron job that re-fetches a payload on an interval also explains beaconing you may see at the network layer.
HACKTHESOCLesson 09Linux for SOC analysts38 / 85

After an Accepted login, what to pull next

  1. 1Confirm identityauth.log gives who and from where. A service account logging in interactively is already odd.
  2. 2Check the sessionps -ef --forest shows whether the shell is live and what it has spawned since.
  3. 3Check the networkss -tnp on that PID shows any outbound session, and to where.
  4. 4Recover the commandsauditd execve records the exact commands even if .bash_history was cleared.
An Accepted login is not an incident by itself. What the session did next is what decides it.
HACKTHESOCLesson 09Linux for SOC analysts39 / 85

A malicious download as auditd records it

  • Download to /tmp, chmod +x, execute: the T1105 sequence
  • Recorded even when bash history was cleared
If the parent of curl is a web service rather than a human shell, the download itself means remote code execution.
HACKTHESOCLesson 09Linux for SOC analysts40 / 85

The meta-questions for any Linux investigation

  • Parent process?Parentage exposes web-exploit-to-shell chains a flat process list hides.
  • Anything in /tmp or /dev/shm?Legitimate software rarely runs from there.
  • New setuid or uid 0?That is escalation.
  • What changed on disk?New or modified cron jobs, systemd units, authorized_keys, rc files.
  • Does the auid name a human?Or did a service account do something it never should?
auth.log for the door, auditd for the hands, the filesystem for the footprints. Read them together.

Reverse shells and reading outbound connections

The victim dials out, so the inbound firewall never sees it.

HACKTHESOCLesson 09Linux for SOC analysts42 / 85

A reverse shell travels outbound, past the inbound firewall

Servers sit behind firewalls that block inbound, so the attacker makes the victim connect out instead.
HACKTHESOCLesson 09Linux for SOC analysts43 / 85

Why the firewall misses it, and what stops it

How it works

A built-in bash feature opens a network connection and wires an interactive shell over it. Nothing is installed. The attacker just waits with a listener.

Why inbound rules fail

The connection is outbound, initiated by the victim, so the inbound firewall never applies.

The control

Egress filtering. A web server has almost no legitimate reason to connect out to a random internet address on a high port.

This is why the lesson calls outbound the interesting direction on a server. Inbound noise is constant and mostly blocked.
HACKTHESOCLesson 09Linux for SOC analysts44 / 85

ss -tnp: the outbound session you hunt

  • An ESTABLISHED session going OUT to an unfamiliar IP on an odd port
  • Owned by bash: a shell has no business holding a network socket
  • From the PID, ps gives the parent, a web server or cron is the tell
On a server, outbound is the interesting direction. Inbound noise is constant and mostly blocked; a shell reaching out is the shape of a live compromise.
HACKTHESOCLesson 09Linux for SOC analysts45 / 85

Three live-host commands to catch it

  1. 1ss -tnp (or netstat -tnp)TCP connections with the owning process. Hunt an ESTABLISHED session out to an odd IP and port, owned by a shell or nc.
  2. 2lsof -i :4444Ties a specific port to a PID, and from the PID you get the parent.
  3. 3ps -ef / the process treeThe parent is the tell: a bash parented by a web server or cron job is not someone working.

Confirmation: a shell-to-socket redirect, nc, socat or a python -c one-liner in the command history or auditd records.

A server reaching out to a strange host, especially from a shell process, is the shape of a live compromise.
HACKTHESOCLesson 09Linux for SOC analysts46 / 85

Outbound is the interesting direction

SignalUsually benignSuspicious
Owner processA browser, apt or a package managerA shell (bash, sh) or nc
DestinationA known update or API hostAn unfamiliar IP on a high port
ContextA workstation, a user sessionA server, parented by a web service
Egress filtering matters because a web server has almost no legitimate reason to dial out to a random host on a high port.

Living off the Linux land

Trusted, pre-installed tools used in ways that blend into admin work.

HACKTHESOCLesson 09Linux for SOC analysts48 / 85

The recurring shapes to know on sight

Download piped to a shell

A script fetched with curl or wget and fed straight into a shell, so it never touches disk. Installers do it too, which is why attackers hide in it.

Base64 blobs

The Linux equivalent of PowerShell -enc: the real command is encoded to dodge keyword matching, then decoded into a shell.

Interpreter one-liners

python3 -c, perl -e, php -r spawning a shell from a language runtime. A web process launching one is a classic tell.

/tmp and /dev/shm

World-writable. /dev/shm lives in memory and leaves less on disk. Execution there is suspicious by default.

A server fetching and executing a script from an unfamiliar host deserves a hard look, even though legitimate installers use the same pattern.
HACKTHESOCLesson 09Linux for SOC analysts49 / 85

The living-off-the-land shapes to know on sight

ShapeWhat it doesThe tell
curl ... piped to bashRuns a script without saving it to diskA server fetching and running from an unfamiliar host
base64 -d piped to a shellHides the real command from keyword matchingDecode-then-execute, like PowerShell -enc

You cannot blocklist curl, python or find; the system needs them. Judge context: who ran it, what was out of character, and from where.
HACKTHESOCLesson 09Linux for SOC analysts50 / 85
GTFOBins: a boring utility behaving like a shell is the anomaly.

find, vim, awk, tar, less all have documented tricks to spawn a shell or read protected files. With elevated rights, such as a SUID root find, that means root.

Do not memorise the list. Internalise the pattern: spawning sh, opening a socket, or reading /etc/shadow from a utility is out of character.
HACKTHESOCLesson 09Linux for SOC analysts51 / 85

The tool is innocent; the use is what you judge

You cannot blocklist curl, python or find. The system needs them.

  • Who ran itA web-server user? A service account?
  • What it didFetched a remote script, decoded a blob, spawned a shell.
  • Where from/tmp or /dev/shm.

Recognisable artifact: a SUID-root find run with -exec /bin/sh spawns a root shell from an innocent file search.

This mirrors the Windows LOLBins lesson: detection is about context and behaviour, not the binary name.
HACKTHESOCLesson 09Linux for SOC analysts52 / 85

GTFOBins in the logs: a SUID utility acting like a shell

  • A SUID-root find ran /bin/sh: the boring utility behaved like a shell
  • uid=0 euid=0 from a non-root auid: setuid elevated the real user
  • mode 04755 is the setuid bit, which is why it ran as root
You do not memorize GTFOBins; you internalize the pattern. A plain utility spawning sh, opening a socket or reading /etc/shadow is the anomaly.

Web shells and the www-data tell

When the web-server user starts executing commands, the server is almost certainly compromised.

HACKTHESOCLesson 09Linux for SOC analysts54 / 85
A web shell lets an attacker run OS commands by visiting a URL. The host analyst catches it in the process tree.

It is planted through a vulnerable upload, an unpatched app, or an injection flaw. The web-application lesson covers that half.

Many Linux server compromises begin with a web shell, not a stolen password.
HACKTHESOCLesson 09Linux for SOC analysts55 / 85

Identity plus ancestry is the lens

www-data, apache, nginx

Normal

A deliberately low-privilege service account whose job is to serve pages. Its workers sit under the web server.

nginx > sh > whoami

Compromise signal

The same account launching a shell, running whoami, using curl, or reading /etc/passwd. It has no legitimate reason to do any of these.

bash is normal. bash whose parent is nginx, apache2 or php-fpm is not.

Another ancestry from the lesson: apache2 > bash > curl. The parent-child relationship is the alarm, exactly as with the Windows process tree.
HACKTHESOCLesson 09Linux for SOC analysts56 / 85

A web-shell recon burst under www-data

  • The nginx worker has spawned sh: a web service launching a shell
  • The commands are recon: id, uname -a, whoami in a burst
  • www-data exists to serve pages, it has no reason to run these
Identity plus ancestry is the lens. whoami is harmless; whoami run by www-data under nginx is a live intrusion in its early minutes.
HACKTHESOCLesson 09Linux for SOC analysts57 / 85

How a web-shell intrusion unfolds under www-data

  1. 1Reconnaissance firstwhoami, id, uname -a, ls. A burst of these under www-data is a live intrusion in its early minutes.
  2. 2A reverse shell nextOften the step to a more comfortable, interactive session.
  3. 3Living off the landDownloading tooling with the trusted utilities from section 7.
  4. 4Privilege escalationAn attempt to get from www-data toward root.
whoami is harmless as a command. It is suspicious because of who ran it and what spawned them.

Worked example: live triage of an SSH compromise

Alert: unusual outbound connection from host web03. Three commands, one story.

HACKTHESOCLesson 09Linux for SOC analysts60 / 85

Three questions, three commands

  1. 1Who, and from where?grep sshd /var/log/auth.log: establish identity and entry point before anything else.
  2. 2Is it live, what did it spawn?ps -ef --forest: confirm the session is alive and see the child processes.
  3. 3What is it talking to now?ss -tnp on the PID: the current outbound connection and its destination.
Each command answers a different question: who, what, and where-to. The order matters: identity first, then behavior, then network.
HACKTHESOCLesson 09Linux for SOC analysts61 / 85

Three commands: who, what, and where to

  • auth.log: a backup-only service account logged in interactively at 03:14
  • ps: its live shell spawned a second, unexplained bash (PID 9014)
  • ss: PID 9014 holds an outbound session to an external IP on port 4444
Run them in this order: identity and entry point, then is the session live and what did it spawn, then what is it doing right now.

Mandatory Access Control: SELinux and AppArmor

A second, kernel-enforced layer that even root cannot bypass by default.

HACKTHESOCLesson 09Linux for SOC analysts65 / 85
rwx permissions are discretionary: the owner decides, and root overrides everything.

Under MAC, every process runs in a security context and a system-wide policy, not the owner and not root, decides what it may touch.

If an attacker reaches root or compromises a process root launched, the traditional model has nothing left to say. MAC still does.
HACKTHESOCLesson 09Linux for SOC analysts66 / 85

Discretionary versus mandatory access control

DAC (rwx)

Discretionary: the file owner decides access, and root overrides everything. If an attacker reaches root, DAC has nothing left to say.

MAC (SELinux/AppArmor)

Mandatory: a system-wide policy the kernel enforces, which even root cannot bypass by default. Each process runs in a confined context.

MAC is the second, independent layer. It is why a web shell that executes can still be blocked the instant it tries to read /etc/shadow.

An AVC denial: the exploit worked, MAC stopped the next step

HACKTHESOCLesson 09Linux for SOC analysts72 / 85

Userland versus kernel rootkit: where they hook

T1574.006

Userland (LD_PRELOAD)

A malicious shared library hooks libc functions like readdir() so tools such as ls never see the attacker's files. Persisted via /etc/ld.so.preload.

T1014

Kernel (LKM)

A loadable kernel module intercepts syscalls inside the kernel, so even a statically-linked tool is lied to. The host cannot be trusted to report on itself.

Defeat the userland kind with a statically-linked tool that bypasses the hooked library. The kernel kind needs an external view.
HACKTHESOCLesson 09Linux for SOC analysts73 / 85

Rootkit-hunting stops on a live host

  • /etc/ld.so.preload is small, rarely checked, and system-wide
  • /proc/PID/maps shows which libraries a process really loaded
  • The /proc vs /sys diff catches lazy LKMs; a competent kernel rootkit hides from both
A fully kernel-compromised host cannot be trusted to report on itself. The most reliable view is from outside: memory forensics (e.g. Volatility linux.check_modules, linux.hidden_modules), a hypervisor view, or an EDR whose kernel hooks predate the rootkit.

When an intrusion looks unusually clean, that absence of evidence is itself worth a second look.

A rootkit is the attacker betting you never question whether the OS answers honestly. On a host with other signs of compromise, suspect the tools themselves.

This is the meta-lesson of the section: every earlier technique assumes ps, ls and ss tell the truth. A rootkit breaks that assumption.

Containers on a Linux host and escape (T1611)

A container shares the host kernel, so a broken boundary lands the attacker on the real host.

HACKTHESOCLesson 09Linux for SOC analysts76 / 85

A container is not a virtual machine

Namespaces

A private view of PIDs, network, mounts and hostname. Broken by escaping the mount namespace via a host bind-mount.

cgroups

Limits on CPU, memory and I/O. Not a security boundary by itself.

Hypervisor (VM)

Hardware-enforced isolation with its own kernel. Containers have neither.

T1611, Escape to Host, is adversaries breaking the namespace and cgroup boundary to reach the underlying host directly.
HACKTHESOCLesson 09Linux for SOC analysts77 / 85

MechanismWhat it providesHow it breaks

A container shares the host kernel; isolation is software, not hardware. That is exactly the boundary T1611 (Escape to Host) breaks.
HACKTHESOCLesson 09Linux for SOC analysts78 / 85

The escape paths to recognise

/var/run/docker.sock

Mounted Docker socket

The daemon runs as root on the host. A container that can reach its socket can ask it to start a new container with the host filesystem mounted in. No kernel exploit needed.

--privileged

Grants every capability and host device access and drops seccomp/AppArmor confinement. Barely different from a root shell on the host.

Dangerous capabilities

CAP_SYS_ADMIN allows mounting filesystems; CAP_SYS_MODULE allows loading a kernel module onto the host.

Mounting the socket inside a container is a common convenience in CI/CD runners and monitoring tools. That is exactly why it is dangerous.

What to watch: socket access and privileged containers

  • Any process inside a container connecting to docker.sock is worth an alert
  • Inspect running containers for --privileged or unexpected host bind mounts
  • Watch dockerd/containerd/runc spawning outside your normal pipeline
Treat the Docker socket like a credential to root. A container launched by an API call that did not come from Kubernetes or CI/CD is the shape T1611 takes in the logs.

Key takeaways

  1. 01Evidence lives in /var/log, /etc and /home; anything executing from /tmp or /dev/shm deserves a second look.
  2. 02Privilege turns on uid 0: hunt extra uid-0 accounts, service accounts with real shells, and risky sudo rules.
  3. 03Parentage is the top triage signal: a shell under nginx, apache or java means a web exploit reached execution.
  4. 04Match log to question: auth.log/secure for logins and sudo, auditd execve (with auid) for commands, journald per service.
  5. 05On a server outbound is the interesting direction: chain auth.log, ps --forest and ss -tnp into one story.
  6. 06SELinux/AppArmor denials, ld.so.preload, and docker.sock access are high-value signals beyond the basic logs.
