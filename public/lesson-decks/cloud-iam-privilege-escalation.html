Section 1 of 9

The IAM primitives this lesson abuses

A fast refresher on the exact pieces the escalation paths turn on, and why each call is logged.

HACKTHESOCLesson 52Cloud IAM escalation6 / 46

The pieces an escalation turns on

  • PermissionPairs an action (s3:GetObject, iam:CreateUser) with a resource. A policy is the JSON document granting them.
  • UserA persistent identity with credentials.
  • RolePermissions an identity assumes temporarily via sts:AssumeRole, which returns short-lived STS keys.
  • Trust policyDefines who may assume a role. A role is only as safe as its trust policy is tight.
  • Access key vs temporaryA long-lived access key works until manually revoked; a temporary credential expires on its own.
Roles plus temporary credentials are the healthy pattern. A long-lived key left in code is the dangerous one.
HACKTHESOCLesson 52Cloud IAM escalation7 / 46

A least-privilege policy: one bucket, read only

Read it as a sentence: allow GetObject and ListBucket, only on reports-bucket. No delete, no other bucket. This is the principle of least privilege.
HACKTHESOCLesson 52Cloud IAM escalation8 / 46
Every control-plane call is authenticated and logged.

Creating a user, attaching a policy, launching a server: each is an API call with a name, a timestamp and a caller identity, sitting in a log you can read.

Unlike a traditional network where lateral movement may leave no trace, cloud escalation leaves a named API trail.
HACKTHESOCLesson 52Cloud IAM escalation9 / 46

The shared-responsibility line

Provider

Security of the cloud

Physical hardware, hypervisor, managed-service infrastructure.

Customer

Security in the cloud

Your data, your configuration, and critically your IAM policies.

An exposed bucket or an abused over-broad policy is a customer-side failure no provider control will catch for you.

IAM is squarely on the customer side, which is why misconfigured permissions are among the most common and impactful cloud risks.

Common privilege-escalation paths

Five recurring ways any valid credential climbs upward.

HACKTHESOCLesson 52Cloud IAM escalation11 / 46

Over-permissive policy: a master key disguised as a door pass

  • The holder calls iam:AttachUserPolicy or iam:PutUserPolicy
  • and grants itself AdministratorAccess
Compare it with the tight single-bucket policy from section 1. Wildcard Action * on Resource * is worse still.
HACKTHESOCLesson 52Cloud IAM escalation12 / 46

iam:PassRole abuse: borrow a role through Lambda

A modest permission, create Lambda functions, plus PassRole on one powerful role becomes full admin, because the attacker's function runs as DataPipelineAdminRole.
HACKTHESOCLesson 52Cloud IAM escalation13 / 46

Five paths, five attacker actions

PathAttacker action
Over-permissive policySelf-attach admin policy
iam:PassRolePass a powerful role to a launched resource
Loose trust policyAssumeRole into higher privilege
Access-key theftReuse a stolen long-lived key from code, CI logs, laptops or repos
Metadata SSRFSteal instance role credentials from 169.254.169.254
Metadata SSRF is MITRE T1552.005. IMDSv2, which requires a session token, was introduced to blunt it; IMDSv1 instances remain exposed. Most real escalations chain two or more paths.

Reference catalog: documented AWS escalation methods

The individually published methods, most famously by Rhino Security Labs, in four families.

HACKTHESOCLesson 52Cloud IAM escalation15 / 46

Families 1 and 2: edit the rules or take over an identity

MethodPermission requiredMechanism
New policy versioniam:CreatePolicyVersionPublish attacker permissions with --set-as-default; no SetDefaultPolicyVersion needed
Roll back policyiam:SetDefaultPolicyVersionReactivate an older, more-permissive version

HACKTHESOCLesson 52Cloud IAM escalation16 / 46

Families 3 and 4: borrow compute that runs a powerful role

MITRE T1548.005

3: PassRole to new compute

Launch a resource, hand it a role you cannot use, run your code inside it.

  • ec2:RunInstances
  • lambda:CreateFunction + invoke, permission or trigger
  • cloudformation:CreateStack, glue:CreateDevEndpoint
  • Data Pipeline, SageMaker notebook, CodeStar

No PassRole needed

4: Hijack existing compute

The role is already attached; just change what the resource runs.

  • lambda:UpdateFunctionCode
  • lambda:UpdateFunctionConfiguration (layer)
  • glue:UpdateDevEndpoint (swap SSH key)
  • Pre-signed URL to an existing SageMaker notebook
Family 4 is the easily missed one: a defence that only locks down PassRole misses all of it.
HACKTHESOCLesson 52Cloud IAM escalation17 / 46

Two lessons hidden in the catalog

  • Least privilege is granularGiving a service account iam:CreateLoginProfile 'just for automation' silently hands it a path to admin.
  • PassRole is the top controlScoping which roles each identity may pass, to which services, collapses nine methods at once.
  • Update* deserves scrutinyFamily 4 escalates through roles already legitimately attached to compute.
  • Detection is the sameEach row is a named eventName in CloudTrail from a caller whose baseline never makes it.
Restricting PassRole, CreateAccessKey and policy-editing actions is not generic hardening: those exact verbs are the catalog's most common entries.

Section 4 of 9

Detection with CloudTrail and Azure Activity

The management-plane log trail is the analyst's primary weapon.

HACKTHESOCLesson 52Cloud IAM escalation19 / 46

A service account attaches AdministratorAccess to itself

  • requestParameters.userName matches userIdentity.userName: self-escalation
  • A service account, an unfamiliar IP, raw aws-cli instead of its automation
Together these are close to a textbook confirmed compromise. Azure's source is the Activity Log and Entra audit logs; GCP's is Cloud Audit Logs.
HACKTHESOCLesson 52Cloud IAM escalation20 / 46

What to watch in the audit trail

  • IAM-mutating callsCreateUser, CreateAccessKey, AttachUserPolicy, PutUserPolicy, CreateRole, UpdateAssumeRolePolicy, CreatePolicyVersion.
  • Azure role changesAdding a principal to Owner or User Access Administrator, in the Activity Log administrative category.
  • New access keysOn accounts that already have keys, or followed by unfamiliar activity from a new IP and User-Agent.
  • AssumeRole and PassRoleFirst-ever role assumptions; requestParameters shows which role ARN was passed.
  • Metadata theftInstance role keys suddenly used from an external IP.
GuardDuty, Defender for Cloud and Entra ID Protection raise similar alerts. Treat them as leads and confirm in the raw audit trail.
HACKTHESOCLesson 52Cloud IAM escalation21 / 46

The highest-fidelity signal: an identity that edits itself

  • requestParameters.userName = userIdentity.userName is self-escalation
  • Also alert on CreatePolicyVersion with setAsDefault=true: no separate event
The same logic works in Sentinel KQL over AWSCloudTrail. CreatePolicyVersion with setAsDefault true silently makes an attacker-written policy version live without a SetDefaultPolicyVersion event.
HACKTHESOCLesson 52Cloud IAM escalation22 / 46

Three more patterns worth hunting

  • Enumeration burstsA spike of AccessDenied across many distinct eventNames from one principal in minutes is the fingerprint of Pacu, enumerate-iam or PMapper.
  • User-agent fingerprintA raw aws-cli or Boto3 agent from a principal whose baseline is a specific automation SDK is worth surfacing on its own.
  • Role-chaining forensicsPivot on accessKeyId (ties a session), sessionIssuer.arn (the assumed role), and sourceIdentity to attribute a hop back to the caller.
PassRole never appears as its own event; you see it through the CreateFunction/RunInstances call that passed the role. Follow AssumeRole to sessionIssuer to accessKeyId to reconstruct a chain.

A worked escalation chain, start to finish

One SSRF to full account administrator in eight minutes.

HACKTHESOCLesson 52Cloud IAM escalation24 / 46

From SSRF to a new admin user

TimeEventWhat it means
09:14SSRF to 169.254.169.254/.../webapp-roleServer fetches its own role credentials for the attacker
09:15Role keys used from an external IPStrongest single tell that theft occurred
09:16GetCallerIdentity, ListAttachedRolePoliciesReconnaissance: who am I, what can webapp-role do
09:19CreateFunction with role = DataPipelineAdminRolePassRole is checked inside this call; the new function runs as full data-pipeline admin
09:22AttachUserPolicy grants AdministratorAccessA brand-new admin user for persistent access
No exploit after the first step: only IAM misconfiguration chained step by step. CloudTrail writes no separate PassRole event; the passed role is visible only in CreateFunction's requestParameters.role.
HACKTHESOCLesson 52Cloud IAM escalation25 / 46
No single event looks catastrophic. The sequence and timing are the incident.

Alert on role credentials used from a new external IP followed within minutes by any IAM-mutating call, not on either event alone.

CreateFunction happens constantly; AttachUserPolicy happens during onboarding. userIdentity and sourceIPAddress prove it was one continuous actor moving faster than change management.

Mapping the chain to MITRE ATT&CK

Temporary elevation versus durable persistence.

HACKTHESOCLesson 52Cloud IAM escalation27 / 46

The full chain, labelled

Worked-chain stepMITRE technique
SSRF reaches the metadata endpointT1552.005, Unsecured Credentials: Cloud Instance Metadata API
Stolen credentials used from an external IPT1078.004, Valid Accounts: Cloud Accounts
iam:PassRole onto DataPipelineAdminRoleT1548.005, Temporary Elevated Cloud Access
AttachUserPolicy grants a new user adminT1098.003, Additional Cloud Roles
MITRE calls out PassRole by name for T1548.005 in AWS; in GCP the equivalent is the iam.serviceAccountUser role.
HACKTHESOCLesson 52Cloud IAM escalation28 / 46

T1098.001: minting additional cloud credentials

  • T1098.001: add attacker-controlled credentials, e.g. CreateAccessKey
  • T1098.003: add roles or permissions, e.g. a new administrator
T1098.001 is the mirror image of key theft: instead of stealing a key, the attacker mints a new one.
HACKTHESOCLesson 52Cloud IAM escalation29 / 46

Why the distinction matters to responders

Temporary

T1548.005

Borrowing a role's privileges for one action. Revoking the Lambda function's role may be enough.

Durable

T1098.003

A new, permanently privileged identity. A backdoor account must also be found and removed.

MITRE notes a compromised admin gained this way can reset the passwords of other admins.

GuardDuty flags the caller behaving unusually for itself, not the API being called.

Escalation-capable APIs are called constantly in a healthy account; the model's value is the per-identity baseline.

Section 8 of 9

Defence: least privilege and guardrails

Several of these would have broken the worked chain at different points.

HACKTHESOCLesson 52Cloud IAM escalation34 / 46

Least privilege and no long-lived keys

  • Scope tightlySpecific actions on specific resource ARNs, not wildcards. Prune with access analysers and last-used data.
  • Guard sensitive verbsRestrict iam:PassRole, iam:CreateAccessKey and policy-editing actions, and on which roles.
  • Roles over keysWorkload identities the platform rotates; federated SSO with short sessions for humans.
  • If keys must existRotate, scope, monitor, never commit to source control, and scan repos and CI logs.
If webapp-role had never been allowed to PassRole on DataPipelineAdminRole, the chain would have failed outright.
HACKTHESOCLesson 52Cloud IAM escalation35 / 46

Guardrails that hold even when a policy is wrong

SCPs

Organisation-level Service Control Policies deny dangerous actions in every account, e.g. disabling CloudTrail.

Permission boundaries

Cap the maximum privilege an identity can ever hold, even after a self-attached admin policy.

PIM

Azure Privileged Identity Management: just-in-time activation, no standing high privilege.

Every guardrail should have a matching alert for attempts to violate it, so the SOC learns when someone probes the boundary.
HACKTHESOCLesson 52Cloud IAM escalation36 / 46

Harden the chain's exact paths

  1. 1Enforce IMDSv2Defeats metadata SSRF: this alone stops the chain at 09:14.
  2. 2Tighten trust policiesOnly intended principals can assume each role.
  3. 3Require MFAFor sensitive operations.
  4. 4Protect the audit trailCloudTrail in all regions, logs to a separate restricted account, alert on stop or delete.
Least privilege shrinks the surface, no long-lived keys removes the easiest target, guardrails stop one policy mistake becoming full takeover.

HACKTHESOCLesson 52Cloud IAM escalation39 / 46

Azure escalation verbs to hunt by name

  • roleAssignments/writeroleAssignments/write lets an identity assign itself Owner. Alert on a principal granting itself Owner or User Access Administrator.
  • VM Run CommandrunCommand/action runs code on a VM; if the VM has a managed identity, the code reads its IMDS token and acts as it.
  • App credential addAttaching a client secret or certificate to a privileged app registration (Entra audit log) is the analogue of iam:CreateAccessKey.
  • Tier-0 directory rolesApplication Administrator, Privileged Role Administrator and Privileged Authentication Administrator: assignment into any is a tier-0 event.
These show up in the Activity Log administrative category and Entra audit logs. A managed identity is Azure's name for what AWS calls an instance role.
HACKTHESOCLesson 52Cloud IAM escalation40 / 46

GCP escalation permissions to hunt

  • serviceAccounts.actAsThe direct analogue of iam:PassRole: attach a service account to a resource you launch, borrowing its privileges.
  • serviceAccounts.getAccessTokenMints a short-lived token for a more-privileged service account to impersonate. Alert on GenerateAccessToken outside baseline.
  • projects.setIamPolicy*.setIamPolicy on any resource rewrites IAM bindings to add your own member to a higher role.
The concepts map across clouds; only the verb names change. Alert on SetIamPolicy that adds the caller to a privileged role.
HACKTHESOCLesson 52Cloud IAM escalation41 / 46
Identify the identity, the permission granted, the action taken, and whether it fits the baseline.

PassRole, AttachUserPolicy and CloudTrail fields are the concrete example. Reading a control-plane log to rebuild a chain transfers to every cloud.

The Azure equivalent of PassRole abuse is giving a workload a managed identity with broader rights than it needs.

Key takeaways

  1. 01An identity holds permissions (action plus resource) in a JSON policy; least privilege grants only the doors needed.
  2. 02Escalation paths: over-permissive policies, PassRole, loose trust, stolen keys, metadata SSRF (T1552.005).
  3. 03Many catalog methods need one permission; iam:PassRole gates a whole family, and Update* hijacks existing compute.
  4. 04Read userIdentity, requestParameters and sourceIPAddress in CloudTrail to rebuild a chain, not isolated events.
  5. 05Detect sequences: role keys from an external IP followed by IAM-mutating calls within minutes.
  6. 06Defend with least privilege, no long-lived keys, SCPs, permission boundaries, IMDSv2 and PIM.

An EC2-hosted web app is vulnerable to SSRF. CloudTrail shows the instance role's temporary credentials making calls from an external IP the workload never used. What most likely happened?

SSRF against 169.254.169.254 exposes the role's credentials, which then appear from an external IP. IAM and instance config are customer-side, rotation does not cause external use, and a developer copy is far less likely given the SSRF.

EC2 with an instance profile, Lambda create-and-invoke, CloudFormation CreateStack and Glue CreateDevEndpoint all share one required permission. Restrict it and the family collapses. Which is it?
