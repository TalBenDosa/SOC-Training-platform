Start here: what a forensic artifact is

A byproduct of the operating system doing its job, not a log someone chose to enable.

HACKTHESOCLesson 77Windows forensic artifacts6 / 76
A hotel's front-desk log can go missing. The minibar restock, the 2 AM keycard and the parking camera still prove who was where.

Windows artifacts are the digital equivalent of those side-effect traces: records of programs run, files opened, folders browsed.

The front-desk log is like a security event log, deliberately kept. Artifacts are side effects nobody chose to record.

HACKTHESOCLesson 77Windows forensic artifacts8 / 76

Two terms for the rest of the lesson

The registry

Windows' central configuration database, organised into files called hives: SYSTEM, SOFTWARE, each user's NTUSER.DAT. Amcache, Shimcache, ShellBags, UserAssist and BAM/DAM live here and need a parser.

NTFS

The file system most Windows drives use. It keeps a master index of every file, the MFT, and is why Windows tracks file timestamps so precisely.

You cannot open hive artifacts in Notepad. The parsing-tools section shows how.
HACKTHESOCLesson 77Windows forensic artifacts9 / 76

Why artifacts matter when you already have logs and EDR

  • They surviveNumerous, scattered and often unknown to the attacker, so they remain after deliberate log-clearing or on a host with no EDR.
  • They fill logging gapsWithout specific auditing, Windows may not log that a program ran, but Prefetch records it anyway.
  • They defeat anti-forensicsAttackers rarely know every place Windows recorded them. One forgotten artifact can expose the operation.
Think of artifacts by the question they answer: did it run, did the file exist, what did the user open, which folders did they browse.
HACKTHESOCLesson 77Windows forensic artifacts10 / 76

Think of artifacts by the question they answer

Did the file exist?

Execution artifacts: proving a program ran

The most-asked forensic question, and the catch in each answer.

HACKTHESOCLesson 77Windows forensic artifacts12 / 76

Prefetch: strong evidence of execution

C:\Windows\Prefetch\PROGRAM.EXE-XXXXXXXX.pf, created to make launches faster.

  • Run count and the last several run times
  • A timestamp you can anchor other evidence around
  • Enabled by default on workstations, often disabled on servers
Read as a sentence: this executable ran three times, most recently at 09:41 UTC on 14 August.
HACKTHESOCLesson 77Windows forensic artifacts13 / 76

Reading the parsed Prefetch file line by line

FieldValueWhat it tells you
Executable nameMIMIKATZ.EXEA credential-theft tool's name: worth immediate attention
Run count3It ran more than once
Last run2026-08-14 09:41:02 UTCThe anchor timestamp for the rest of the timeline
Other run times13 Aug 22:05, 12 Aug 18:12Activity over three days, not a single event
Directory referenced\WINDOWS\SYSTEM32Locations the program touched while loading
The file is named like PROGRAM.EXE-XXXXXXXX.pf. A name match alone is a lead; confirm with the hash from Amcache.
HACKTHESOCLesson 77Windows forensic artifacts14 / 76

Four more ways Windows records a program

Amcache

Amcache.hve hive: paths, SHA-1 hashes, timestamps. Ties an executed file to threat intel even if the file is gone.

Shimcache

AppCompatCache in SYSTEM: path, size, last-modified. Shows presence, which does not by itself guarantee execution.

UserAssist

In NTUSER.DAT: programs launched from the GUI, with run count and last run. ROT13-obfuscated, reversed by parsers.

BAM / DAM

SYSTEM hive, Windows 10+: full path and last-execution time per user SID. Easy to parse, often survives cleanup.

Background/Desktop Activity Moderator records execution as a side effect of managing background app activity.
HACKTHESOCLesson 77Windows forensic artifacts15 / 76

Know exactly what each execution artifact proves

ArtifactProvesBonus data
PrefetchExecution (strong)Run count, last run times
AmcachePresence/executionSHA-1 hash, path, time
ShimcachePresence (not guaranteed execution)Path, size, modified time
UserAssistGUI-launched executionRun count, last run time
BAM/DAMExecution, per userFull path, last-execution time

Prefetch + a known-bad Amcache hash + a matching BAM/DAM time beats any one alone.

When an attacker deletes their tool, these artifacts can still prove it was there and ran.
HACKTHESOCLesson 77Windows forensic artifacts16 / 76

How to word it in a report: presence versus execution

Shimcache only

"The file was present on the system at this path, with this size and last-modified time." Not "it ran".

Prefetch, Amcache, BAM/DAM

"The program executed, most recently at this time, under this user's SID, with this SHA-1 hash."

Overstating Shimcache as execution is the classic mistake, and the lesson quiz tests it.
HACKTHESOCLesson 77Windows forensic artifacts17 / 76

Building a solid execution finding

  1. 1PrefetchShows the tool ran, how often, and when last.
  2. 2AmcacheGives the SHA-1 hash, checkable in threat intel even if the file is gone.
  3. 3BAM/DAMConfirms a matching last-execution time and which user SID ran it.
  4. 4MFTShows when the file appeared on disk.
One artifact is a lead; three or four that agree is a finding.

The MFT, MACB timestamps, and deleted files

A timestamped ledger of every file, including ones since deleted.

HACKTHESOCLesson 77Windows forensic artifacts19 / 76

Every MFT record carries MACB timestamps

$MFT holds a record for every file and folder: name, size, location, timestamps.

  • M: ModifiedWhen the file's content last changed.
  • A: AccessedLast read; updates are sometimes disabled for performance, so less reliable.
  • C: ChangedWhen the MFT record (metadata) last changed, distinct from content.
  • B: BornWhen the file was created on the volume.

Modified earlier than created is suspicious: the file likely arrived already built, or was copied.

Deleted files' records often persist until overwritten, and the MFT is the backbone of timeline analysis.
HACKTHESOCLesson 77Windows forensic artifacts20 / 76

Reading MACB patterns

PatternWhat it suggestsNext step
Born at the intrusion timeThe file arrived during the attackPlace it on the timeline
Modified earlier than BornArrived already built, or was copiedFind where it was copied from
Changed later than ModifiedMetadata altered without a content changeCheck for renames or timestamp edits
Accessed time looks oddPossibly nothing: updates may be disabledDo not build a conclusion on A alone
C is the MFT record change time, not content change. Students often confuse C with M.
HACKTHESOCLesson 77Windows forensic artifacts21 / 76

Two timestamp structures expose timestomping

$STANDARD_INFORMATION

What most tools and users see. Ordinary programs can change it, so attackers backdate it to blend in with old system files.

$FILE_NAME

Harder for normal software to alter. Most timestomping tools do not bother with it, or cannot easily reach it.

When the two disagree, that mismatch is a strong, specific signal of tampering.

This duplication is a gift to investigators.
HACKTHESOCLesson 77Windows forensic artifacts22 / 76

How a timestomp gets caught

  1. 1Attacker backdatesThe file's $STANDARD_INFORMATION times are set to look years old.
  2. 2FN left alone$FILE_NAME keeps the real times; most tools do not or cannot reach it.
  3. 3Parser shows bothMFTECmd outputs both timestamp sets for each record.
  4. 4CompareSI says 2019, FN says the intrusion day: a strong, specific tamper signal.
Section 5 adds a third, independent check from the USN journal.
HACKTHESOCLesson 77Windows forensic artifacts23 / 76

A parsed MFT record with a stomped timestamp

Accessed and Changed are trimmed here; Created and Modified are the two that expose the stomp.

  • $STANDARD_INFORMATION claims the file is over six years old
  • $FILE_NAME, the one attackers forget, shows the intrusion window
  • That contradiction is the tell
The MFT recovers deleted files, anchors a timeline, and exposes hiding. Every other artifact gets more powerful lined up against it.

Section 4 of 10

User activity: LNK, Jump Lists, ShellBags and more

Not just what ran, but what a person touched and where they went.

HACKTHESOCLesson 77Windows forensic artifacts27 / 76

What the user opened and browsed

  • LNK filesTarget path, timestamps, volume serial, even if the file or drive is gone. E:\stolen_data.xlsx proves an open from E:.
  • Jump ListsRecent files per application: what did this person open with Word?
  • RecentDocsNTUSER.DAT key: recent files overall and per file extension.
  • ShellBagsFolders browsed in Explorer, even on shares or removed devices that no longer exist.
  • USBSTOR / MountedDevicesMake, model, serial of USB storage and first/last connected times.
If an insider claims they never opened a sensitive folder, ShellBags may say otherwise. USB history proves which physical device a LNK's drive letter was.
HACKTHESOCLesson 77Windows forensic artifacts28 / 76

LNK plus USB history: proving a file came off a drive

  1. 1User opens a fileE:\stolen_data.xlsx is opened from a removable drive.
  2. 2LNK is writtenIt records the target path, timestamps and volume serial.
  3. 3Drive is removedThe file and the drive are gone; the LNK stays.
  4. 4USBSTOR names the deviceMake, model and serial, with first and last connected times.
  5. 5setupapi pins the timeThe driver install log shows when it was first plugged in (section 6).
Each artifact answers one piece: which file, which device, and when.
HACKTHESOCLesson 77Windows forensic artifacts29 / 76

ArtifactAnswers

Recycle Bin: two files per deleted item

Written into C:\$Recycle.Bin\<SID>\, per user. Parsed with RBCmd.

e.g. $IAB12CD.docx

$I file

Metadata: original full path, original size, and the exact deletion date and time.

e.g. $RAB12CD.docx

$R file

The actual content of the deleted file, often recoverable outright.

C:\Projects\customer_list.xlsx deleted at 17:58 in a departing employee's SID folder: direct, dated evidence.

This applies to deletes to the Recycle Bin, not shift-delete.

Windows Timeline: an activity diary attackers forget

  • WhereActivitiesCache.db under AppData\Local\ConnectedDevicesPlatform\<id>\, per user, since Windows 10.
  • What each entry holdsThe application, the file or URL opened, and start and end times.
  • Why it helpsIndependent timestamps that corroborate LNK, Jump List and RecentDocs evidence.
  • Why it survivesComparatively obscure, so attackers scrubbing better-known traces often leave it. Parsed with WxTCmd.
It is the Task View activity feed, stored as evidence.

An insider case told entirely by user artifacts

  1. 1BrowseShellBags show the user navigated to the sensitive folder.
  2. 2OpenLNK, Jump Lists and RecentDocs show the files opened.
  3. 3Copy outUSBSTOR and setupapi.dev.log show a USB drive attached.
  4. 4Clean upRecycle Bin $I files show what was deleted, and when.

Browse to it (ShellBags), open it (LNK, Jump Lists, RecentDocs), copy it to a USB drive (USBSTOR).

Section 5 of 10

NTFS journals: $UsnJrnl and $LogFile

Records of file-system activity itself, catching what the MFT misses.

HACKTHESOCLesson 77Windows forensic artifacts36 / 76

How the USN change journal records a change

  1. 1A change happensA file or folder is created, written, renamed or deleted.
  2. 2A record is appendedNTFS writes it to the $J stream of C:\$Extend\$UsnJrnl.
  3. 3Record contentsTimestamp, MFT and parent reference numbers, file name, reason flags.
  4. 4The journal wrapsOld records drop off after days to weeks, depending on activity.
USN stands for Update Sequence Number. The $MAX stream holds journal metadata; $J holds the records analysts read.
HACKTHESOCLesson 77Windows forensic artifacts37 / 76

$UsnJrnl: a running log of every change

C:\$Extend\$UsnJrnl. $MAX holds metadata; $J holds the change records, with reason codes.

Reason flagMeaning
FILE_CREATEThe file or directory was created
FILE_DELETEThe file or directory was deleted
DATA_OVERWRITEThe file's data was overwritten
DATA_EXTENDData was appended (the file grew)
RENAME_OLD_NAME / RENAME_NEW_NAMEThe file was renamed, before and after
BASIC_INFO_CHANGEAttributes or timestamps were changed
Each $J record carries a timestamp, MFT and parent reference numbers, the file name and reason flags, which combine bitwise.
HACKTHESOCLesson 77Windows forensic artifacts38 / 76

The journal remembers a file the attacker deleted

  • Created and written at 14:05:02, deleted 98 seconds later
  • Survives after the MFT entry is overwritten
  • A FILE_CREATE from last week vs an MFT claiming years ago: tampering
MFTECmd joins $J to $MFT on the parent entry number to rebuild full paths. Often the journal is the only remaining proof the file existed.
HACKTHESOCLesson 77Windows forensic artifacts39 / 76

Two jobs the journal does that the MFT cannot

Deleted files

Once a file's MFT entry is reused, the MFT forgets it. A FILE_CREATE / FILE_DELETE pair in $J may still prove it existed and when it was removed.

Timestomp cross-check

$J keeps its own timestamps. An MFT claiming years ago next to a FILE_CREATE from last week is independent proof of tampering.

That is two independent confirmations of timestomping: SI vs FN, and SI vs the journal.
HACKTHESOCLesson 77Windows forensic artifacts40 / 76

$LogFile: the finest and most perishable record

  • PurposeNTFS's crash-recovery log: each low-level change is written here first so it can be redone or undone.
  • DetailPer-operation records (RCRD blocks), finer than $UsnJrnl.
  • RetentionFixed size, commonly around 64 MB, so typically only the last few hours.
  • ConsequenceImage suspect disks early, or this view of the intrusion is gone.
Parsed with LogFileParser or MFTECmd's $LogFile support.
HACKTHESOCLesson 77Windows forensic artifacts41 / 76

MFT, $UsnJrnl and $LogFile together

StructureWhat it showsLastsBest for
$MFTCurrent metadata, both timestamp setsWhile the file existsBaseline, SI vs FN comparison
$UsnJrnl ($J)Creates, deletes, renames, overwritesDays to weeksDeleted files, second time check
$LogFileLow-level per-operation recordsHours, sometimes lessFreshest, most granular detail
$LogFile is NTFS's crash-recovery log, commonly around 64 MB, so it overwrites itself fast. Image suspect disks early. Correlating all three is sometimes called a TriForce.

Section 6 of 10

SRUM, persistence, and setupapi.dev.log

Execution after deletion, how attackers come back, and when a USB arrived.

HACKTHESOCLesson 77Windows forensic artifacts43 / 76

SRUM proves execution even after the file is gone

C:\Windows\System32\sru\SRUDB.dat, an ESE database, since Windows 8.

What it records

CPU, network and energy per application, built for battery and network-usage reporting. Written roughly hourly and at shutdown, about 30 to 60 days retained (environment-dependent).

Why it matters

Application Resource Usage shows execution windows; Network Usage shows bytes sent and received per app, per network, including the Wi-Fi SSID.

SrumECmd.exe -f "E:\collected\C\Windows\System32\sru\SRUDB.dat" --csv "E:\out"

Even if Prefetch and Amcache were cleaned, SRUM may still show the tool ran and how much it sent out: strong for exfiltration questions.
HACKTHESOCLesson 77Windows forensic artifacts44 / 76

The two SRUM tables an analyst reads first

TableWhat it recordsQuestion it answers
Application Resource UsagePer-program activity, in roughly hourly windowsDid this tool run, and when?
Network UsageBytes sent and received per app, per network, with the Wi-Fi SSIDHow much did it send out, and over which network?
A process with an unusually large bytes-sent figure in a specific window is strong corroboration for an exfiltration question.
HACKTHESOCLesson 77Windows forensic artifacts45 / 76

Why SRUM survives the clean-up

  1. 1Tool runsSRUM records its resource use in SRUDB.dat, roughly hourly and at shutdown.
  2. 2Attacker cleans upThe tool is deleted, and its Prefetch file and Amcache entry too.
  3. 3SRUM still holds itThe rolling window keeps about 30 to 60 days of history.
  4. 4Analyst parses itSrumECmd shows the program ran and how many bytes it moved.
SRUM is an ESE (Extensible Storage Engine) database, present since Windows 8.

To come back after a reboot, an attacker has to write it down somewhere predictable.

Run keys, task files, service entries, the Startup folder and the WMI repository can all be read later from a disk image, with no EDR at all.

WMI subscriptions leave no Run-key trace, so check them separately with a WMI-repository parser.

C:\Windows\inf\setupapi.dev.log, written every time a device driver installs.

Search for the serial from the USBSTOR entry. Local system time, append-only back to installation unless tampered with. It turns 'used at some point' into 'plugged in at 14:12:07', matching LNK evidence minutes later.

Registry hives and event log artifacts

Which files hold the evidence, and the log that records its own clearing.

HACKTHESOCLesson 77Windows forensic artifacts51 / 76

Registry hives are files you can collect

Hive fileHolds (among other things)
SYSTEMShimcache, BAM/DAM, USBSTOR, MountedDevices, services
SOFTWAREInstalled software, some persistence keys, OS version
SAM / SECURITYLocal accounts and groups / security policy, cached credentials

System hives sit in C:\Windows\System32\config and are locked while Windows runs, so KAPE uses shadow copies or raw reads. Each has a .LOG transaction file, like SYSTEM.LOG1.
HACKTHESOCLesson 77Windows forensic artifacts52 / 76

Two collection details that trip people up

  • Hives are lockedSYSTEM, SOFTWARE, SAM and SECURITY are in use while Windows runs, so a plain copy fails. KAPE uses shadow copies or raw reads.
  • Transaction logsEach hive has a .LOG file, like SYSTEM.LOG1, that may hold very recent changes not yet committed.
The .LOG files are the registry's own version of NTFS's $LogFile. Collect them with the hive.

Event IDs that recur in artifact investigations

.evtx files under C:\Windows\System32\winevt\Logs\, one per channel.

Event IDChannelMeaning
4624 / 4625SecuritySuccessful / failed logon
4688SecurityNew process created (needs process-creation auditing)
4720SecurityA user account was created

Event logs are artifacts too: byproducts of auditing that can be read, correlated, and checked for tampering.
HACKTHESOCLesson 77Windows forensic artifacts54 / 76
Destroying log evidence itself becomes a log entry.

1102 is logged whenever the Security log is cleared, regardless of audit policy, with the account that did it. Clearing Security leaves System untouched.

1102 with no matching logon or business justification is a strong indicator of compromise. An attacker who forgets System leaves a second trail via 104.
HACKTHESOCLesson 77Windows forensic artifacts55 / 76

Clearing one channel leaves the others talking

Security channel cleared

Leaves event 1102, with the account that cleared it, whatever the audit policy.

Other channels cleared

Leave event 104 in System. Forget to clear System and its 7045 service installs survive.

An attacker who clears Security but not System leaves a second trail.

Section 9 of 10

Using artifacts in an investigation

From clues to a coherent, corroborated account.

HACKTHESOCLesson 77Windows forensic artifacts63 / 76

Four principles for reliable assembly

  • CorroborateOne artifact is a lead; three or four that agree is a finding. Shimcache may not prove execution, timestamps can be stomped.
  • Fill visibility gapsOn unmanaged hosts or after log-clearing, artifacts may be your primary evidence.
  • Watch for anti-forensicsMissing Prefetch where expected, or SI vs FN anomalies, mean someone tried to hide. MITRE: Indicator Removal (T1070; log-clear is T1685.005).
  • Build one narrativeNot a pile of parser outputs, but a story you could defend in a report or in court.
Treat the absence of expected artifacts as suspicious rather than reassuring.

Key takeaways

  1. 01Artifacts are traces Windows writes for convenience; they survive log-clearing and fill logging gaps.
  2. 02Prefetch, Amcache, UserAssist and BAM/DAM show execution; Shimcache shows presence only. Correlate several.
  3. 03A $STANDARD_INFORMATION vs $FILE_NAME mismatch exposes timestomping; $UsnJrnl confirms it independently.
  4. 04LNK, Jump Lists, RecentDocs, ShellBags, USBSTOR, $I/$R and SRUM show what a person touched and moved.
  5. 05Event 1102 logs the clearing of the Security log itself, and System-channel entries like 7045 survive it.
  6. 06KAPE collects, Zimmerman tools parse to CSV, and corroborated rows become one defensible narrative.

Check your understanding, question 1 of 3

Why do experienced analysts treat a Shimcache (AppCompatCache) entry differently from a Prefetch file when trying to prove that a program executed?

Shimcache proves presence (path, size, last-modified time), not execution, so corroborate with Prefetch, Amcache or BAM/DAM. Its timestamp is last-modified, not run time; the SYSTEM hive is not tamper-proof; GUI launches are UserAssist.

A Security log shows Event ID 1102 shortly before intrusion evidence disappears, yet the System channel still shows Event ID 7045 (new service installed) from the same window. What is the correct reading?

1102 means the Security log was cleared, with the account that did it. System is untouched, so the 7045 is a second trail; clearing System leaves Event 104 instead. 1102 is logged regardless of audit policy.
