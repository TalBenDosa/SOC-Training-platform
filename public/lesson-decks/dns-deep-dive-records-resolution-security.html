A phone book lists names next to numbers. You know the name, look it up, and dial the number.

Humans remember www.example.com; the network only routes to a numeric IP. DNS, the Domain Name System, is the automated phone book between them.

DNS runs invisibly before almost every connection. Open with the literal phone-book picture before any mechanics.

Section 1 of 8

Why we need DNS at all

Resolving a name is asking what IP it points to, and getting an answer before any connection.

HACKTHESOCLesson 48DNS deep dive6 / 47

Names for humans, numbers for the network

What people use

A name like www.example.com, easy to remember, share and type. Names change address without the user noticing.

What the network uses

A numeric IP address, the only thing routers can actually forward traffic to. Every connection needs one.

DNS bridges the two, automatically, before almost every single connection on the internet.

This gap is why DNS exists. Plant it before the mechanics: a name must become a number first, every time.
HACKTHESOCLesson 48DNS deep dive7 / 47

Name in, address out, with an expiry

  • The query is the question, the response is the answer
  • TTL (Time To Live) is how long a resolver may reuse the answer before re-asking
That is the whole idea in miniature. TTL is what makes DNS fast on repeat lookups, and TTL values matter later for fast-flux.

Section 2 of 8

How resolution works, end to end

The client asks one recursive question; the resolver does the legwork across the hierarchy.

HACKTHESOCLesson 48DNS deep dive9 / 47

The players in a lookup

  1. 1The clientAny process that needs a name resolved. It asks exactly one question and waits for one answer.
  2. 2The recursive resolverThe configured DNS server (corporate, or a public one like 8.8.8.8) that does the legwork and returns the final answer.
  3. 3Root and TLD serversThe root points to the .com servers; the .com TLD server points to the domain's authoritative servers.
  4. 4The authoritative serverHolds the real records for the domain and returns the definitive answer.
Name the roles before the trace so the five hops on the next slide read as a conversation between known parties.
HACKTHESOCLesson 48DNS deep dive10 / 47

A resolution trace, spelled out

  • The client talks only to the resolver: one question in, one answer out
  • The resolver does five iterative hops behind the scenes
If the resolver has the answer cached it responds at once. This is why the recursive resolver is the single point that saw every step.
HACKTHESOCLesson 48DNS deep dive11 / 47

Why the resolver, not the authoritative server, is your log source

Recursive resolver

Saw every internal host's every lookup, cache hits and all. One central point, one uniform log. This is where you hunt.

Authoritative server

Saw only the queries that reached it for its own zones, and only from resolvers, not from your clients. A narrow view.

The client only ever experienced the final answer; the resolver experienced every step to build it.

This is the structural reason DNS logging lives at the resolver. Everything in the hunting section depends on this single vantage point.
HACKTHESOCLesson 48DNS deep dive12 / 47
DNS travels on port 53: UDP by default, TCP when answers are large.

A small question and answer fits one UDP packet, capped historically at 512 bytes. Big responses and zone transfers switch to TCP 53.

A sudden rise in TCP/53 or oversized responses can mean zone transfers or data pushed through DNS rather than ordinary lookups.
HACKTHESOCLesson 48DNS deep dive13 / 47

RCODEs you will read in logs

RCODE is the response code the server returns; it tells you how the lookup ended.

RCODENameWhy an analyst cares
0NOERRORNormal resolution, an answer was returned
2SERVFAILOften a DNSSEC validation failure or unreachable server
3NXDOMAINDGA (domain generation) signal: malware cycling many domains in bulk
5REFUSEDPolicy block, or a failed zone-transfer attempt on a hardened server

FORMERR (1) is a malformed query; NOTIMP (4) an unsupported type.

NXDOMAIN is the one to memorise: humans rarely trigger it, automated malicious tools generate it in bulk.

The record types you will see in logs

Each record answers a different question; the type is a clue to a host's intent.

HACKTHESOCLesson 48DNS deep dive15 / 47

Common records and their relevance

RecordPurposeAnalyst relevance
A / AAAAName to IPv4 / IPv6 addressThe most common lookup: what host is being reached
CNAMEAlias to another nameRedirection chains, used by CDNs and some abuse
MXMail exchanger for a domainWhere email is delivered; odd from a non-mail host
TXTArbitrary text (SPF, DKIM)Also abused to smuggle data or C2 payloads
NSDelegates a zone to name serversWho controls a domain's records
PTRReverse: IP back to a nameEnrichment, naming an address
Reading zone data is rare for Tier 1, but recognising the shape helps when dig or nslookup output lands in an investigation.
HACKTHESOCLesson 48DNS deep dive16 / 47

What records look like in a zone

  • Each line: owner name, TTL, class IN, type, value
  • The PTR owner is the IP reversed, under in-addr.arpa
  • TXT holds free-form text, which is why attackers like it
Recognising this shape helps when a report, dig or nslookup output lands in front of you. IN is the internet class, essentially always present.
HACKTHESOCLesson 48DNS deep dive17 / 47
You are reading the questions a host asks, and the questions often reveal purpose before any payload moves.

A burst of A/AAAA for random hostnames hints at a DGA; unusual TXT volume hints at tunneling; MX from a non-mail host hints at a spam bot.

The record type is a clue to intent. CNAME alias chains are routine to follow; TXT is an attacker favourite because it holds arbitrary strings.

Section 4 of 8

SOA, SRV, and CAA: records behind the scenes

Zone metadata, service location, and certificate authorisation, plus zone transfers.

HACKTHESOCLesson 48DNS deep dive19 / 47

The SOA timing fields

SOA (Start of Authority) is one record per zone, holding its administrative metadata.

FieldMeaning
SerialVersion number; secondaries compare it to know if they need an update
RefreshHow often a secondary checks the primary for a new serial
RetryHow long to wait before retrying a failed refresh
ExpireWhen a secondary must stop answering if it cannot reach the primary
MinimumNegative-caching TTL: how long resolvers may cache an NXDOMAIN

An unexpected Serial bump corroborates a recent zone edit. MNAME is the primary server; RNAME the admin email.

A Tier-1 rarely queries SOA, but an unexpected Serial bump corroborates that a zone was recently edited during a suspected unauthorized change.
HACKTHESOCLesson 48DNS deep dive20 / 47

SRV and CAA, worked

  • SRV (service record): priority weight port target; lower priority wins
  • CAA (CA Authorization) lists which CAs may issue certs; none set means any CA can
Domain-joined machines find DCs, LDAP and Kerberos entirely through SRV. Missing CAA widens the brand-impersonation surface.
HACKTHESOCLesson 48DNS deep dive21 / 47

Why SRV lookups matter for AD defence

Legitimate

A domain-joined machine resolves _ldap._tcp.dc._msdcs to find a domain controller to authenticate against. Routine, constant, from managed hosts.

Reconnaissance

An unusual host enumerating many _ldap, _kerberos and _msdcs SRV names early in an intrusion is mapping the domain-controller topology before an AD attack.

The same lookup is normal from a workstation and suspicious from a freshly compromised foothold.

SRV is how AD clients locate services, which is exactly why SRV enumeration is a precursor the defender can catch early.
HACKTHESOCLesson 48DNS deep dive22 / 47
A server that permits AXFR (full zone transfer) from anyone hands an attacker a full map of the domain at once.

AXFR copies the whole zone, IXFR only the changes since an SOA serial, both over TCP 53. A hardened server answers REFUSED.

An inbound AXFR from an unexpected source, or a spike of TCP/53 to authoritative servers, is textbook early reconnaissance.

Section 5 of 8

DNS security: DNSSEC, DoH, and DoT

Classic DNS is plaintext UDP with no authentication, inviting tampering and eavesdropping.

HACKTHESOCLesson 48DNS deep dive24 / 47

Two problems plaintext DNS invites

  • TamperingAnyone who can forge an answer redirects a victim to an attacker's IP: cache poisoning and spoofing. An integrity problem.
  • EavesdroppingAnyone on the path reads which names you look up: a privacy problem. The lookup itself reveals intent.

DNSSEC addresses the first; DoT and DoH address the second. They are not interchangeable.

Separate the two problems first, so students see why DNSSEC and DoH/DoT solve different things and affect visibility differently.
HACKTHESOCLesson 48DNS deep dive25 / 47

Integrity vs privacy, and the visibility cost

Integrity

DNSSEC

DNS Security Extensions. Signs records so a resolver can verify the answer was not altered. Does not encrypt: queries stay visible. Reduces poisoning risk, does not change what you log.

Privacy

DoT

DNS over TLS. Encrypts the query to the resolver on dedicated port 853, so at least the traffic is identifiable on the network.

Visibility killer

DoH

DNS over HTTPS. Wraps DNS in HTTPS on port 443, indistinguishable from web traffic. External DoH means your resolver never sees the lookup.

Responses: force clients to the internal logged resolver, detect external DoH/DoT, and lean on endpoint (EDR) DNS telemetry.

A double-edged sword: good for user privacy, but it can blind the network DNS monitoring analysts depend on.
HACKTHESOCLesson 48DNS deep dive26 / 47

The DNSSEC record chain

RecordRole
DNSKEYHolds a zone's public signing keys
RRSIGThe signature over a record set, proving it was not altered
DSSits in the parent zone, fingerprints the child's DNSKEY
NSEC / NSEC3Authenticated denial; NSEC3 hashes names to resist enumeration

Trust runs top-down: root signs the TLD's DS, the TLD signs the domain's DS, the domain signs its own records.

A failed link returns SERVFAIL, so a wave of SERVFAIL on a working domain can be a DNSSEC misconfiguration rather than an attack.
HACKTHESOCLesson 48DNS deep dive27 / 47
External DoH is the setting that decides what a missing log line means.

If endpoints can use external DoH, the absence of a lookup in your DNS logs may mean the host resolved through a channel you cannot see, not that it stayed quiet.

Knowing whether your environment permits external DoH is essential context for interpreting gaps in DNS telemetry.

Section 6 of 8

Cache poisoning, hijacking, and fast-flux

Three ways attackers subvert the resolution path.

HACKTHESOCLesson 48DNS deep dive29 / 47
Cache poisoning is winning the race to lie first.

An attacker guesses the 16-bit transaction ID and source port and injects a forged response before the real one arrives, caching their IP for the TTL.

The 2008 Kaminsky attack showed this was far more practical than assumed. DNSSEC was built to close exactly this integrity gap by signing legitimate answers.
HACKTHESOCLesson 48DNS deep dive30 / 47

Why a poisoned cache is so damaging

One lie, many victims

The forged answer is cached at the resolver, so every client that asks it for that name, until the TTL expires, is silently redirected to the attacker's server.

The fix

DNSSEC signs legitimate answers so a forged one fails validation. A wave of SERVFAIL can be that failure, not a server outage.

The cache is shared, which is what turns a single injected answer into a broad redirection.

Connect it back to DNSSEC from the previous section: this integrity attack is precisely what signing defends against.
HACKTHESOCLesson 48DNS deep dive31 / 47

DNS hijacking: four places to attack the same trust

TypeWhereMechanism
Local (hosts file)The victim's machineMalware edits the hosts file or DNS settings, bypassing DNS
RouterThe home/office routerWeak credentials or firmware flaws change configured DNS servers
Registrar / authoritativeThe domain's real recordsCompromised registrar or name server edits legitimate records
On-path / MITMBetween client and resolverOpen Wi-Fi interceptor forges the response in transit
The layer changes the response: a poisoned hosts file is an EDR finding; a registrar compromise means contacting the registrar and validating every record in the zone.
HACKTHESOCLesson 48DNS deep dive32 / 47

Fast-flux hides infrastructure in constant motion

T1568.001

Mechanism

Extremely low TTL (often under 300s) rotating a large pool of IPs, frequently other compromised bots, every few minutes. Double-flux also rotates the name servers.

The signature

One domain resolving to many different A records in a short window, tiny TTLs, IPs spanning diverse unrelated networks.

Fast-flux is one domain succeeding over and over; DGA is many domains mostly failing.

IP blocklisting becomes useless: by the time you block one IP the domain has moved on. The domain name is the only stable artifact.
HACKTHESOCLesson 48DNS deep dive33 / 47

Fast-flux in the DNS log

  • One domain name, a different A-record answer each time
  • TTL pinned at 60s forces constant re-resolution
  • IPs span unrelated networks, not one hosting provider
This is the shape to recognise: stable name, rotating IPs, tiny TTL. Contrast it with the DGA shape in the worked example.

Section 7 of 8

Why DNS is the first place investigations look

The reasons are structural, not habit.

HACKTHESOCLesson 48DNS deep dive35 / 47

Two structural advantages

Records intent early

A name lookup precedes the connection, so DNS logs capture what a host intended to reach even if the connection fails or is encrypted.

Compact and central

One recursive resolver logs every host's lookups in a small uniform format, far lighter than packet capture and available almost everywhere.

A workstation that resolves a known-malicious domain has already told you something, regardless of what happened next.
HACKTHESOCLesson 48DNS deep dive36 / 47

Three hunting patterns and their telemetry

PatternWhat the logs showEnrichment
Newly registered domainsLookups for domains created hours or days agoDomain-age feed flags very young domains
DGA domainsHigh-entropy names, most returning NXDOMAINEntropy scoring plus the NXDOMAIN rate
DNS tunnelingEndless unique subdomains on one parent, heavy TXTSubdomain length and per-domain query volume

DNS turns a host's intentions into log lines you can search: an early-warning system that fires before payload moves.

Each pattern is a measurable shape in resolver logs. The enrichment column is what turns the raw lookup into an alert.
HACKTHESOCLesson 48DNS deep dive37 / 47
Master the record types, domain ages, entropy and query volumes, and DNS becomes the first pivot and the last word.

Because the lookup precedes the payload, a host's intent is in the log before a single byte of data moves.

This is the throughline of the lesson: DNS logs are intent, logged early, in a form you can search at scale.

Section 8 of 8

Worked example: a DGA and a tunnel in raw logs

Recognising the shape in an actual export is the skill that matters.

HACKTHESOCLesson 48DNS deep dive39 / 47

Baseline browsing vs a suspected DGA

  • Baseline: short readable domains, resolving successfully
  • DGA: dozens of high-entropy names, bursts, almost all NXDOMAIN
The failure rate is the tell. A human never types dozens of nonsense domains a minute; malware cycling a DGA list does, not yet knowing which one is registered today.
HACKTHESOCLesson 48DNS deep dive40 / 47

DGA vs tunneling: reading the two shapes

DimensionDGADNS tunneling
Domain namesMany different parent domainsOne parent domain reused
SubdomainsNot the point; the domain itself variesA new unique subdomain every query
Typical RCODEMostly NXDOMAIN (name not registered)Mostly NOERROR (the parent resolves)
Common recordA / AAAATXT (and long encoded labels)

DGA is trying many doors; tunneling is hammering one door with endless different knocks.

This interpreting slide sits between the two log reads on purpose: name the distinguishing dimensions before seeing the tunnel log.
HACKTHESOCLesson 48DNS deep dive41 / 47

Suspected DNS tunneling: the mirror image

  • Long base64-looking subdomains: data encoded inside the query
  • The same parent domain reused, a different subdomain every query
DGA looks like trying many different domains; tunneling looks like hammering one domain with endless unique subdomains. Telling the two apart at a glance is a high-value skill.
HACKTHESOCLesson 48DNS deep dive42 / 47
Three shapes, three ATT&CK IDs, so you can escalate precisely.

Many domains mostly NXDOMAIN is DGA (T1568.002). One domain, endless unique subdomains is tunneling (T1071.004). One domain, many rotating IPs, tiny TTL is fast-flux (T1568.001).

DGA is deterministic and seeded, so malware and operator generate the same candidate list; the operator registers only one at a time.

Key takeaways

  1. 01DNS turns names into IPs before almost every connection; the resolver does root to TLD to authoritative hops.
  2. 02The recursive resolver logs each host's intent early and centrally: the first pivot in an investigation.
  3. 03Record types reveal intent: A/AAAA what is reached, TXT a tunneling channel, MX mail, PTR reverse lookups.
  4. 04DNSSEC protects integrity not privacy; DoH/DoT encrypt lookups and can blind network DNS monitoring.
  5. 05NXDOMAIN is the DGA signal; humans rarely trigger it, automated tools generate it in bulk.
  6. 06DGA is many domains mostly failing; tunneling is endless subdomains on one domain; fast-flux is one domain, many IPs.
