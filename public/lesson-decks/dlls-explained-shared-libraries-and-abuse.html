Section 1 of 7

What is a DLL?

A Dynamic Link Library: shared code linked to a program at run time.

HACKTHESOCLesson 70DLLs and DLL abuse6 / 54

Unpacking the name: Dynamic Link Library

  • LibraryA file of reusable functions and data that many programs can share.
  • LinkConnected to a program so the program can call those functions.
  • DynamicLinked at run time, not baked into the program when it was built.
  • In practiceCommon jobs such as drawing windows, opening files or making network connections live in DLLs.
A typical Windows host has thousands of DLLs. You only need to know the handful that appear everywhere, and the rule that tells a real one from a borrowed name.
HACKTHESOCLesson 70DLLs and DLL abuse7 / 54

Windows' shared toolbox

Instead of every worker owning identical tools, everyone shares one well-stocked toolbox.

Dynamic linking

The Windows norm. A small .exe pulls in shared DLLs when it runs. Saves disk and memory; one fix repairs every program.

Static linking

The program bundles all the code it needs directly into its own .exe.

The core Windows API itself is delivered as DLLs, so almost anything a program does is a call into one.
HACKTHESOCLesson 70DLLs and DLL abuse8 / 54

What happens when a program starts

  1. 1The .exe is loadedWindows maps the executable into a new process.
  2. 2Its DLL list is readDLLs listed in the executable are needed at load time.
  3. 3Each DLL is mapped inkernel32.dll, ntdll.dll and friends join the process memory.
  4. 4Code calls into themAlmost anything the program does is a call into one of these DLLs.
The result is the key idea of the lesson: the process is the executable plus every DLL loaded into it, and any of those DLLs runs with the process's identity.

Same famous name, two very different files

Genuine version.dll

What every process expects to load.

  • In C:\Windows\System32
  • Signed by Microsoft
  • Invisible background noise

Borrowed name

Not the real version.dll, whatever its name says.

  • In an application folder
  • Unsigned or wrong publisher
  • Loaded by a trusted program
Attackers borrow familiar names precisely because analysts tune them out. The name is never the check; location and signature are.

Four more core DLLs you will meet

Section 2 of 7

How programs load DLLs, and the search order

When only a name is given, Windows searches a fixed sequence.

HACKTHESOCLesson 70DLLs and DLL abuse13 / 54

Two ways a DLL gets in, two LOLBins to run one

Implicit linking

DLLs listed in the executable load automatically when the program starts.

Explicit loading

LoadLibrary loads a DLL on demand at run time, how plugins work.

rundll32 / regsvr32

rundll32.exe runs a function inside a DLL; regsvr32.exe registers DLLs. Both are abused to run malicious DLL code.

If an attacker places helper.dll where Windows checks before the real one, the program loads it believing it got the real thing. Nothing is exploited; it is tricked.
HACKTHESOCLesson 70DLLs and DLL abuse14 / 54
When a program asks for a DLL by name only, the first file Windows finds wins.

Plant a same-named DLL where Windows looks before the real one, and the program loads it believing it got the genuine file.

Nothing is exploited in the traditional sense. The program is tricked by where a file sits.
HACKTHESOCLesson 70DLLs and DLL abuse15 / 54

The search order with Safe DLL Search Mode

  1. 1Redirection and manifestsAPI sets and SxS manifests; then the already-loaded module list.
  2. 2KnownDLLsProtected core DLLs always load from System32.
  3. 3The application's folderSearched before System32. This is why hijacking works.
  4. 4System foldersSystem32, the 16-bit system folder, then C:\Windows.
  5. 5Current working directoryMoved late by Safe DLL Search Mode, on by default.
  6. 6PATH foldersEach folder in the system PATH, left to right.
Without safe mode, the current directory would sit right after the app folder, which is far more dangerous.
HACKTHESOCLesson 70DLLs and DLL abuse16 / 54

The search order through an attacker's eyes

PositionLocationCan a planted DLL win here?
1-2Redirection, SxS manifests, already-loaded modulesResolved before any folder is searched
3KnownDLLsNo: always loaded from System32
4The application's own folderYes: searched before System32, the classic hijack spot

Position 4 is the single most important line for a defender. A same-named DLL beside the program beats the system copy.
HACKTHESOCLesson 70DLLs and DLL abuse17 / 54

Where attackers can and cannot win

Cannot hijack

KnownDLLs

Listed at HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\KnownDLLs. ntdll.dll and kernel32.dll always come from System32.

Fill the empty slot

Phantom DLL hijacking

A program tries to load a DLL that does not exist anywhere. The attacker supplies it, with zero conflict.

ATT&CK Hijack Execution Flow (T1574): search order, phantom and side-loading all sit under T1574.001 (DLL).

Real search-order attacks target less-famous helper DLLs not on the KnownDLLs list, or names that do not exist on the system. Side-loading was T1574.002 until ATT&CK v17 merged it into T1574.001, so older reports still cite it; in v19 the family sits under the Stealth and Execution tactics.
HACKTHESOCLesson 70DLLs and DLL abuse18 / 54

Phantom DLL hijacking, step by step

  1. 1A missing referenceA program tries to load a DLL that exists nowhere, e.g. a leftover optional component.
  2. 2Normally harmlessThe load simply fails and the program carries on.
  3. 3The slot is filledAn attacker creates a DLL with that missing name in a searched folder.
  4. 4Loaded without conflictNext run, the program loads it; no legitimate file competes.
  5. 5What you seeSysmon 7 for a DLL that has no business existing at all.
Also called ghost DLL hijacking. Tracked under T1574.001 together with search-order hijacking and side-loading.

Section 3 of 7

How attackers abuse DLLs

Every technique chases one goal: execution under a trusted identity.

HACKTHESOCLesson 70DLLs and DLL abuse20 / 54

Three techniques that matter most

Search-order hijacking

Drop a malicious DLL with the expected name into a folder Windows checks first, usually the app's own directory.

Sideloading

Bring a legitimate, signed .exe known to load a DLL, and plant the malicious DLL beside it. Launders code through a reputable program.

Injection

Force a DLL into an already-running process, which inherits its identity, network reputation and privileges.

A rundll32 command line pointing at an unusual DLL or odd path is a classic hunting lead.

Signature-based defences focus on the .exe and often miss this, because the malice lives in the DLL.
HACKTHESOCLesson 70DLLs and DLL abuse21 / 54

Sideloading, step by step

  1. 1Pick a signed programA legitimate vendor .exe known to load a particular DLL.
  2. 2Plant the DLL beside itThe malicious DLL carries the expected name, in the same folder.
  3. 3Run the signed programIts own folder is searched first, so it loads the planted DLL.
  4. 4Execution is launderedThe code runs inside a genuinely signed, reputable process.
Trust checks that look at the .exe pass, because the .exe really is signed. The malice sits in the DLL next to it.
HACKTHESOCLesson 70DLLs and DLL abuse22 / 54

Hijacking versus sideloading: who brings the program?

Search-order hijacking

Abuses a program already on the machine, by dropping a DLL into a folder it searches first.

Sideloading

The attacker ships a signed program alongside the DLL, choosing one known to load that name.

Both leave the same trace: a well-known DLL name loaded from the wrong folder, often unsigned.

For detection the distinction matters less than the shared signal; for scoping, a new signed .exe appearing in an odd folder points to sideloading.
HACKTHESOCLesson 70DLLs and DLL abuse23 / 54

DLL injection: forcing a DLL into a running process

  1. 1Choose a running targetA normal browser or system process already trusted by tools.
  2. 2Open and allocateMemory is allocated inside the target process.
  3. 3Force the loadThe target is made to load the malicious DLL, e.g. LoadLibrary via a remote thread.
  4. 4Inherit everythingThe code runs with the target's identity, network reputation and privileges.
Injection happens after load time, unlike hijacking and sideloading. It belongs to the broader process injection family (T1055).
HACKTHESOCLesson 70DLLs and DLL abuse24 / 54

Two built-in binaries worth hunting

  • rundll32.exeIts job is literally to run a function inside a DLL, so attackers use it to look like normal Windows activity.
  • regsvr32.exeRegisters DLLs, and can be abused the same way to execute code.
  • The hunting leadEither one pointing at an unusual DLL, an odd path or suspicious arguments.
These are living-off-the-land binaries: legitimate, signed Windows tools. Their command lines, not their names, carry the signal.

Section 4 of 7

DLL proxying

Keep the application working while hiding malicious code.

HACKTHESOCLesson 70DLLs and DLL abuse27 / 54

The export table: a DLL's menu of functions

  • What it isPart of the DLL's PE file header listing the named functions other code may call.
  • How programs use itThe application calls functions by name, e.g. GetFileVersionInfoW in version.dll.
  • The attacker's problemA fake DLL missing those exports makes the app error, crash or misbehave.
  • Why that helps defendersUsers notice and report a broken app. Proxying exists to remove that glitch.
PE stands for Portable Executable, the file format of Windows .exe and .dll files.
HACKTHESOCLesson 70DLLs and DLL abuse28 / 54

How a proxy DLL keeps the app working

  1. 1Copy the export namesThe malicious DLL exposes the same names as the real one.
  2. 2Forward every callEach export points to the real DLL, renamed alongside it.
  3. 3Keep the real one nearbyGenuine version.dll becomes version_real.dll in the same folder.
  4. 4Run the payload at loadDllMain executes the attacker's code the moment it loads.
  5. 5Nothing visibly breaksThe app gets correct answers from the forwarded calls.
Proxying is favoured when the target is an application users interact with and would notice breaking.
HACKTHESOCLesson 70DLLs and DLL abuse29 / 54

A proxy DLL forwards every export to the real one

  • The genuine Microsoft version.dll is renamed to version_real.dll in the same folder
  • UpdateHelper.exe works exactly as before; the payload runs from DllMain at load
Plain hijacking breaks the app if the fake lacks the expected exports, and users notice. Proxying removes that glitch.
HACKTHESOCLesson 70DLLs and DLL abuse30 / 54

Plain hijack versus proxy: what changes for the analyst

Plain hijackProxy DLL

Proxying takes away the behavioural signal, so the static checks on the next slide become the main line of defence.
HACKTHESOCLesson 70DLLs and DLL abuse31 / 54

Did it break? is no longer a signal

  • SignatureA proxy DLL is still unsigned, or signed by the wrong publisher.
  • LocationIt still sits outside the path Windows would normally load it from.
  • Export tableStatic inspection shows forwarded exports pointing at a renamed sibling, version_real.dll, that has no reason to exist.
Static tools that dump exports and flag forwarding to an unusual filename are the most direct catch for this variant.

Section 5 of 7

Reflective DLL injection

When even the Windows loader is bypassed.

HACKTHESOCLesson 70DLLs and DLL abuse33 / 54

Three ATT&CK IDs at the stealthy end of the spectrum

The further right, the less the OS loader and the disk see of it.

T1574.001

On-disk hijack / side-load

The malicious DLL is a real file. Windows' own loader reads it with LoadLibrary, so it appears as a Sysmon Event 7 image load, just from an odd path or unsigned.

T1055.001

Classic DLL injection

A DLL on disk is forced into a running process: memory is allocated in the target, then LoadLibrary is called there via CreateRemoteThread. Still a file, still an image load.

T1620

Reflective code loading

No LoadLibrary, often no file. A bundled mini loader maps the image into memory itself, so the OS logs no conventional load at all.

T1620 Reflective Code Loading (ATT&CK, Stealth tactic): code is allocated and run directly in process memory, not backed by a disk file.

Confirmed on MITRE ATT&CK: T1620 is Reflective Code Loading. T1055.001 (Dynamic-link Library Injection) covers the classic remote case; the loader-bypass mechanism itself is T1620. Cobalt Strike's default DLL loading is reflective.
HACKTHESOCLesson 70DLLs and DLL abuse34 / 54

How reflective code loading maps a DLL with no loader

The payload does for itself the work Windows' loader normally does.

  1. 1The image is delivered into memoryThe DLL image is placed in the process's memory rather than written to disk as a file.
  2. 2A bundled loader does the loader's jobA small reflective loader parses the image headers and resolves its imports itself.
  3. 3No LoadLibrary, no Sysmon Event 7The OS loader is skipped, so no image-load event fires and no DLL file exists on disk to find.
  4. 4Execution starts in the host processThe mapped code runs with the trusted process's identity, leaving only memory artifacts.

This is why file-only detection misses it. Contrast on-disk T1574.001 side-loading, which does leave a file and a Sysmon 7 image load.

The whole point of T1620 is that the module is never conventionally loaded, so coverage has to shift to memory and injection telemetry below.

HACKTHESOCLesson 70DLLs and DLL abuse36 / 54

What modern EDR watches instead

  • Memory allocation patternsLarge executable memory regions that did not come from a normal module load.
  • Cross-process threadsCreateRemoteThread / QueueUserAPC calls between processes (Sysmon Event ID 8).
  • Unusual ProcessAccessOne process opening a suspiciously powerful handle to another (Sysmon Event ID 10).
DLL abuse sits on a spectrum: file and image-load telemetry for the first half, process memory and injection telemetry for the second.
HACKTHESOCLesson 70DLLs and DLL abuse37 / 54
A clean disk does not mean a clean process.

DLL abuse runs from file-based and loud to memory-only and near-invisible. File telemetry covers the first half; memory and injection telemetry the second.

Cobalt Strike's default DLL loading is reflective, so this end of the spectrum is common in real intrusions, not exotic.

Seeing DLL abuse in your telemetry

Loading a DLL and dropping one on disk are both observable.

HACKTHESOCLesson 70DLLs and DLL abuse39 / 54

Sysmon Event ID 7: hunt for anomaly

  • Unusual pathA legitimate-sounding DLL in Downloads, Temp, or an app folder where it does not belong.
  • Unsigned or wrong vendorLoaded into a trusted process.
  • Well-known name, wrong placeThe fingerprint of search-order hijacking and sideloading.
  • Supporting signalsSysmon 11 DLL writes before the load; rundll32/regsvr32 from odd locations; remote-thread events.
Baseline normal DLL loading for critical apps, then hunt deviations. Tie finds back to the process tree: a sideloaded DLL often comes with a freshly dropped exe and a suspicious parent.
HACKTHESOCLesson 70DLLs and DLL abuse40 / 54

Baseline: a genuine version.dll load

  • ImageLoaded in System32: where the genuine copy lives
  • Signed true with a Microsoft Signature: the expected publisher
  • Compare every suspicious load against this shape
Show this before the worked investigation so students can spot the three differences on sight.

The chained hunt: a drop, then a load

  1. 1Sysmon 11A DLL written into an application folder by a non-installer process.
  2. 2Sysmon 7 seconds laterThat same file loaded, unsigned, into a signed process.
  3. 3Check the launchersrundll32 or regsvr32 from odd locations, with odd arguments.
  4. 4Tie to the treeA freshly dropped exe and a suspicious parent strengthen the case.
  5. 5No file at all?Pivot to Sysmon 8 and 10 for injection instead.
Two events on the same path, seconds apart, is hijacking or sideloading caught in the act.
HACKTHESOCLesson 70DLLs and DLL abuse43 / 54

Sysmon 7 must be switched on deliberately

The catch

ImageLoad is disabled by default: every DLL load in every process is an enormous volume.

The approach

Enable it with filters, baseline normal DLL loading for critical apps, then hunt the deviations.

If a SOC says "we have Sysmon", ask whether Event 7 is on. Without it, the hijacking half of this lesson is invisible.

Step 1: is this DLL supposed to be here?

  • Wrong location: the app folder, not System32
  • Wrong signature: unsigned, where the genuine one is Microsoft-signed

Step 2: find the drop

  • Written about ninety seconds before it was loaded: the setup step

Expected writer

Observed writer

Key takeaways

  1. 01A DLL is shared code loaded at run time; a process is its .exe plus every DLL loaded into it.
  2. 02The app folder is searched before System32, so a same-named DLL there wins; KnownDLLs cannot be hijacked.
  3. 03Hijacking, phantom hijacking, sideloading and injection all aim for execution under a trusted identity.
  4. 04Proxying forwards exports so nothing breaks; check signature, location and the export table.
  5. 05Reflective code loading (T1620) skips the loader and disk, so no Sysmon 7 fires; watch memory, Sysmon 8 and Sysmon 10.
  6. 06Hunt with Sysmon 7 for odd paths and unsigned DLLs, chained with Sysmon 11 drops just before.
