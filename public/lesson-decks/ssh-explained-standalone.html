SSH is a secure remote control for a machine you will never physically touch.

Administrators type into servers in data centres and clouds all day. Everything between them and the server is scrambled and protected.

Open with the scale: thousands of servers managed by people who never see them. SSH is what makes that safe, and what attackers want.

Section 1 of 8

What SSH is and why it replaced Telnet

Secure Shell: remote login and control with the whole session encrypted.

HACKTHESOCLesson 82SSH explained6 / 38

Same job, very different exposure

Telnet

Remote login that sends everything, including usernames and passwords, as plain readable text. Anyone capturing the traffic reads the credentials directly.

SSH

The same remote-login job with the entire session encrypted. An interceptor sees only meaningless ciphertext.

SSH almost entirely replaced Telnet. Finding Telnet still in use is itself a security concern.

Make the point that the problem SSH solved was credential theft by simple sniffing.
HACKTHESOCLesson 82SSH explained7 / 38

What administrators actually do over SSH

  • Run commandsExecute commands, restart services, check logs.
  • Edit configurationChange config files directly on the remote machine.
  • Copy filesscp and sftp run over the same encrypted SSH channel.
  • Manage fleetsThe primary way Linux and Unix servers, and increasingly network devices and Windows, are managed.
SSH grants a real, interactive foothold on a machine. That is why both admins and analysts must understand it.

Section 2 of 8

How SSH works: handshake, keys and port 22

Encryption goes in place before any secret is ever sent.

HACKTHESOCLesson 82SSH explained9 / 38

Five steps from TCP connect to shell

Client/server protocol listening on TCP port 22.

  1. 1Connect and negotiateClient opens TCP to port 22; both agree on algorithms.
  2. 2Key exchangeA shared secret is established. From here on, everything is encrypted.
  3. 3Server authenticationClient checks the server's host key to rule out an impostor.
  4. 4Client authenticationOnly now does the user prove who they are.
  5. 5SessionA shell, a command or a file transfer, until logout.
The 'authenticity of host can't be established' prompt on first connect comes from step 3.
HACKTHESOCLesson 82SSH explained10 / 38

Two ways to log in, two very different risks

Password

User types a password, sent inside the already-encrypted channel. Simple, but vulnerable to guessing (brute force).

Public key

The professional standard. Client holds a secret private key, server holds the matching public key. The client proves possession without ever sending it.

Public-key login is far stronger and cannot be brute-forced the same way.

This choice is the crux of SSH security. Most real compromises come through the password path.
HACKTHESOCLesson 82SSH explained11 / 38
To a network monitor, SSH is an opaque encrypted tunnel.

You can see that a connection happened, from where, how long and how much data moved. You cannot see the commands inside.

That property is exactly what makes SSH secure for admins and attractive to attackers.

Transport, authentication, connection

Read it bottom up. Everything above the transport layer is already protected.

HACKTHESOCLesson 82SSH explained15 / 38
Shell, file transfer and tunnels all travel inside one TCP connection to port 22.

From outside they are indistinguishable. Profile SSH sessions by volume and duration, not just source and destination.

The Connection Protocol multiplexes many channels: shell, exec (used by scp and automation), subsystem (SFTP) and forwarded connections. An unusually large or long-lived session is one of the few external clues.

Section 4 of 8

Port forwarding: local, remote and dynamic tunnels

A legitimate admin feature and one of the most effective attacker pivots (MITRE T1572).

HACKTHESOCLesson 82SSH explained17 / 38

Three tunnel modes

Local -L

A port on your machine forwards to a destination reachable from the server. Like asking a switchboard operator to connect you to an internal extension.

Remote -R

Opens a port on the server that forwards back to your machine. A firewalled host dials out and creates a reverse-access backdoor.

Dynamic -D

Turns the SSH client into a SOCKS proxy. Any tool using it reaches anything the server can reach, not one fixed destination.

Remote is the one attackers prize most: the firewall only ever sees the victim's own outbound connection. Dynamic is the most flexible and, for defenders, the most dangerous.
HACKTHESOCLesson 82SSH explained18 / 38

What each tunnel looks like on the command line

  • -R 9000:localhost:22: the VPS port 9000 now reaches the victim's own port 22
  • -D 1080: point browser or proxychains at 127.0.0.1:1080
  • AllowTcpForwarding no is the most direct fix where tunnels are not needed
GatewayPorts no is the default. It keeps a remote-forwarded port on localhost rather than exposed to the whole network.
HACKTHESOCLesson 82SSH explained19 / 38

Fingerprints of a tunnel you cannot decrypt

  • Long and heavyA session with unusually long duration and high data volume compared with a typical interactive login.
  • Outbound and held openAn internal host suddenly making an outbound SSH connection to an external IP and keeping it open.

The contents stay encrypted. The detection angle is behavioural.

Ask the class: which of the three modes produces the outbound-and-held-open pattern? Remote forwarding.

Section 5 of 8

SSH in practice: logins, keys and config

The commands, files and log lines worth recognising.

HACKTHESOCLesson 82SSH explained21 / 38

The files that shape SSH on a server

ssh-keygen

Key pair

Private key stays on the client, often ~/.ssh/id_rsa or id_ed25519. Connect with ssh user@server.

~/.ssh/authorized_keys

authorized_keys

The list of public keys allowed to log in as that user. An attacker who adds a key gets durable, password-free access.

/etc/ssh/sshd_config

sshd_config

Server posture: password login, PermitRootLogin, listening port, who may connect.

Adding a key to authorized_keys is a common persistence technique. Watch that file.
HACKTHESOCLesson 82SSH explained22 / 38

DirectiveDefaultHardenedWhat it controls
PermitRootLoginprohibit-passwordnoDirect login by the root account

Port is often left at 22: moving it only reduces noise, not real risk. PubkeyAuthentication stays yes, PermitEmptyPasswords and X11Forwarding stay no.
HACKTHESOCLesson 82SSH explained23 / 38

A minimal hardened block

  • Keys only, no root, no tunnels, three tries then disconnect
  • Only members of sshusers may connect at all
  • Eliminates password brute force and direct root compromise in one file
Have students read it aloud as a sentence. That is how an auditor reads it.

Reading sshd lines in the auth log

/var/log/auth.log (Debian/Ubuntu), /var/log/secure (RHEL), or journalctl -u ssh.

Log message patternSOC significance
Accepted publickey for USER from IPThe good case, but confirm the key and source IP are expected
Accepted password for USER from IPOn a key-only server it should never appear
Failed password for USER from IPA few are normal; many from one IP = brute force
Failed password for invalid user USER from IPStrong brute-force and username-enumeration signal
Connection closed by IP [preauth]Often scanners probing whether port 22 is open
Disconnecting: Too many authentication failuresMaxAuthTries firing against a guesser
POSSIBLE BREAK-IN ATTEMPT!Forward/reverse DNS mismatch; corroborate, do not panic
The most valuable pattern is the transition: a long run of failures from one IP followed by Accepted from that same IP. That is a brute force that succeeded.

Section 6 of 8

Host keys and trust on first use

How the client knows it is talking to the right server.

HACKTHESOCLesson 82SSH explained26 / 38

Trust On First Use (TOFU)

  1. 1First connectionSSH shows the server's key fingerprint and asks you to confirm it.
  2. 2Saved to known_hostsIf you accept, the fingerprint is stored in your local known_hosts file.
  3. 3Every later connectionThe client silently compares the presented key with the saved one.
  4. 4MismatchREMOTE HOST IDENTIFICATION HAS CHANGED: the client refuses to connect automatically.
The important prompt is not the first-time question. It is the warning after a key is already saved.
HACKTHESOCLesson 82SSH explained27 / 38

Why did the host key change?

Legitimate

The server was rebuilt or reconfigured, ideally on a known maintenance window.

Attack

You are routed to an impostor doing a man-in-the-middle attack, capturing credentials while the channel still looks encrypted.

Large organisations avoid TOFU by distributing host keys centrally or using a CA-signed host certificate.

Warn against the reflex of deleting the old entry and reconnecting. The first question is why the key changed.

Section 7 of 8

Why SSH matters to a SOC analyst

A successful SSH login is someone gaining a command shell on a machine.

HACKTHESOCLesson 82SSH explained29 / 38

What analysts hunt for in SSH data

  • Brute forceFloods of failed password logins on port 22 from one source; worse if one then succeeds.
  • Unusual sourcesSuccess from an unfamiliar country, odd hour, or a server the source never administered.
  • Unexpected exposurePort 22 reachable from 0.0.0.0/0 instead of admin networks: a classic finding.
  • Tunnelling and pivotingLong-lived sessions carrying unexpected traffic to reach deeper internal systems.
  • New keys, weaker configNew authorized_keys entries or a weakened sshd_config: persistence or defense impairment.
Each item maps back to an earlier section: auth log, exposure, tunnels, keys, config.
HACKTHESOCLesson 82SSH explained30 / 38
Treat SSH authentication logs as a priority feed.

Baseline who connects to what, from where, using which method. Alert on the deviations: the brute force, the foreign login, the newly added key.

The stakes make even a single anomalous SSH login worth investigating.

Worked example: reading an SSH auth log

Volume, then success: the shape of a brute force that worked.

HACKTHESOCLesson 82SSH explained32 / 38

Hundreds of failures, then one success

  • Too fast and repetitive for a person: an automated brute-force tool
  • Accepted password from the same IP: the guessing worked
  • session opened for user root: an interactive shell as the most privileged account
Walk it line by line. The pattern change at 03:20:47 is the whole story.
HACKTHESOCLesson 82SSH explained33 / 38

The questions this log demands next

  1. 1What did the session do?Check shell history and commands logged for that session.
  2. 2Who is 198.51.100.23?Known admin IP or unfamiliar? Look up geolocation and reputation.
  3. 3Should this be possible?Harden sshd_config: PermitRootLogin no, disable password auth.
  4. 4Was a key planted?Check ~/.ssh/authorized_keys for entries added during or after the session.
An attacker with a shell often plants a key immediately so they can return even after the password is changed.

Key takeaways

  1. 01SSH gives encrypted remote control over TCP port 22 and replaced plaintext Telnet.
  2. 02Key exchange encrypts the channel first, the host key proves the server, then the user authenticates.
  3. 03Public-key login beats passwords; keyboard-interactive carries MFA; authorized_keys and sshd_config set posture.
  4. 04Local, remote and dynamic tunnels hide inside port 22; spot them by duration and volume.
  5. 05A run of failed passwords then an Accepted line from the same IP is a brute force that succeeded.
  6. 06A host-key-changed warning can mean a rebuild or a man-in-the-middle: investigate, never dismiss.

Check your understanding, question 1 of 3

On an internet-facing Linux server you see hundreds of 'Failed password for root' entries from one IP over a few minutes, then a single 'Accepted password for root' from the same IP. What most likely happened?

Many password failures against one account from one IP, ending in 'Accepted', is a brute force that succeeded. Stuffing and spraying both spread across many accounts, and well-configured automation uses keys, not repeated failed root passwords.

Check your understanding, question 2 of 3

A compromised internal workstation, behind a firewall that blocks all inbound connections, is later reachable by an external attacker over SSH. Which SSH feature most likely made this possible, and how?

ssh -R is the classic reverse tunnel: an allowed outbound connection opens a listener on attacker infrastructure that forwards back in. ssh -L would still need inbound reach, -D is an outbound SOCKS pivot, and the scenario says inbound is blocked.

Check your understanding, question 3 of 3

Servers are supposed to be key-only, yet /var/log/auth.log shows 'Accepted password for backup' after a burst of username-guessing failures from the same IP. Which single sshd_config change would have prevented that login?

PasswordAuthentication no turns off password logins across the board. PermitRootLogin only constrains root, MaxAuthTries just caps attempts per connection, and AllowUsers limits which accounts connect, not how they authenticate.
