Section 1 of 9

The valet key handed to the wrong person

One analogy frames the whole attack.

HACKTHESOCLesson 54OAuth consent phishing6 / 56

OAuth is a valet key for your account

Your password

Master key

Opens everything. OAuth never hands it over.

A token

Valet key

Limited, specific access: a scope such as 'read my mail', proven by a token the provider issues to the app.

OAuth lets you grant an application limited access to your data without handing over your password.
HACKTHESOCLesson 54OAuth consent phishing7 / 56

Password vs token, as an analyst reads them

Master key (password)Valet key (token)
GrantsEverything the account can doOnly the scopes consented, e.g. Mail.Read
Who holds itThe user aloneAny app the user approved
Revoked byA password resetRevoking the grant / sessions, not a reset
Seen in logsSign-in eventsConsent and app-activity events
This table is why the response differs from credential theft: a password reset touches the master key, not the valet key the attacker holds.
HACKTHESOCLesson 54OAuth consent phishing8 / 56

How the valet key is cut and handed over

  1. 1RedirectYour browser goes to the provider's own genuine consent screen, listing the scopes the app wants.
  2. 2AcceptYou click Accept: the moment of decision.
  3. 3Token issuedThe provider issues the app a token proving it holds exactly those scopes.
  4. 4offline_accessAlso grants a refresh token: the valet key that never has to be returned, so access is durable.
The refresh token is what turns a one-off grant into lasting access; it comes back in the response section.
HACKTHESOCLesson 54OAuth consent phishing9 / 56
The danger is a legitimate victim voluntarily handing a valet key to a fake attendant.

Nothing in OAuth is broken. The failure is the victim's judgement about who to trust, which is why defences built around the password alone miss it.

This one sentence is the whole lesson. Return to it at the response section.

What OAuth consent phishing is

An illicit consent grant: MITRE ATT&CK T1528, Steal Application Access Token.

HACKTHESOCLesson 54OAuth consent phishing11 / 56

Scopes chosen for durability and reach

  • offline_accessGrants a refresh token: new access tokens indefinitely, the key that never has to be returned.
  • Mail.Read / Mail.ReadWriteRead or write access to the entire mailbox.
  • Files.Read.All, User.ReadPlus contact and calendar scopes to expand reach.

The same consent-phishing pattern targets Google Workspace OAuth, with equivalent scopes.

The victim's password is never involved. From the identity provider's view the user made a valid, authenticated choice to delegate access.
HACKTHESOCLesson 54OAuth consent phishing12 / 56

Why these scopes, and what each buys the attacker

ScopeGrantsWhy the attacker wants it
offline_accessA refresh tokenDurability: new access tokens indefinitely, no user present
Mail.Read / Mail.ReadWriteRead or write the whole mailboxThe payload: email contents and the ability to send
Files.Read.All, User.ReadFiles, profile, contacts, calendarReach: expand from mail to the rest of the account
offline_access is the one that turns a one-off read into lasting access. Flag it with any mail scope as a high-value combination.
HACKTHESOCLesson 54OAuth consent phishing13 / 56

The consent link points to Microsoft's real domain

  • Decoded scope: Mail.Read offline_access Files.Read.All
  • Only the redirect_uri belongs to the attacker
  • The victim reads the scopes on the consent screen's plain-language list, not this raw URL
Shown split at the parameters for readability; it is one URL. To the user it looks like authorising a productivity add-in, and with offline_access plus Mail.Read the app reads mail around the clock.
HACKTHESOCLesson 54OAuth consent phishing14 / 56

Why the link passes the checks users are taught

What looks safe

The host is login.microsoftonline.com, Microsoft's genuine consent endpoint. URL filtering and 'check the domain' training both pass it.

  • Real domain
  • Real consent screen

What is actually hostile

Only the redirect_uri is the attacker's, buried in a long encoded string, and the scopes being requested.

  • redirect_uri to attacker
  • Over-broad scopes
The user is not fooled about the domain; they are fooled about the app. That is why domain-based training does not catch this.

Section 3 of 9

How the attack works step by step

Five stages, each leaving a trace.

HACKTHESOCLesson 54OAuth consent phishing16 / 56

From app registration to persistence

  1. 1RegisterA malicious app in a throwaway tenant requesting the scopes, named e.g. 'Mail Sync Helper'.
  2. 2LurePhishing email with the consent link. The genuine domain passes URL-reputation checks.
  3. 3ConsentVictim authenticates (MFA satisfied) and clicks Accept. Access plus refresh token issued.
  4. 4UseThe app calls Microsoft Graph to read mail and files. Authorised; no suspicious login.
  5. 5PersistRefresh token keeps access. Forwarding rules, data search, business email compromise.
In classic credential phishing the fake login lives on an attacker domain. Here only the redirect_uri does, easy to miss in a long encoded link.
HACKTHESOCLesson 54OAuth consent phishing17 / 56

Classic phishing vs consent phishing: what is fake

Credential phishing

A fake login page on an attacker domain captures the password. Reset the password and the attacker is out.

  • Fake page
  • Steals the password

Consent phishing

The real provider page, the real login, real MFA. Only the app and its redirect_uri are hostile. A reset changes nothing.

  • Genuine page
  • Steals a token
Draw the contrast explicitly: here there is no fake page to spot and no password to reset, which is exactly why detection and response differ.

StageAttacker actionAnalyst artefact

Section 4 of 9

Where consent phishing sits in the OAuth flow

It rides the legitimate authorization code flow, exactly as designed.

HACKTHESOCLesson 54OAuth consent phishing20 / 56

Two channels in the authorization code flow

Through the browser

Front channel

The user approves the consent screen; the provider hands back a short-lived authorization code.

Server to server

Back channel

The app's backend trades the code at the token endpoint for the real access token and refresh token.

The malicious app completes the identical sequence, so its tokens are mechanically indistinguishable from any legitimate app's.
HACKTHESOCLesson 54OAuth consent phishing21 / 56

Front channel to back channel, step by step

  1. 1Front: approveThe user approves the consent screen in the browser.
  2. 2Front: code returnedThe provider hands back a short-lived authorization code to the redirect_uri.
  3. 3Back: exchangeThe app's backend trades that code at the token endpoint, server to server.
  4. 4Back: tokens issuedIt receives the access token and, with offline_access, the refresh token.

The malicious app runs this identical sequence, so its tokens are indistinguishable from any legitimate app's.

There is no exploit to detect in the flow itself. The signal is the consent event and what the app does afterward.
HACKTHESOCLesson 54OAuth consent phishing22 / 56
Nothing is exploited. The only failure is the human decision to approve the wrong app.

The malicious app's tokens are real and valid, indistinguishable from those of any legitimate app completing the same flow.

This takes the valet-key framing one level deeper.
HACKTHESOCLesson 54OAuth consent phishing23 / 56

Device-code phishing: no app to spot

RFC 8628

How it works

The device grant serves TVs and CLI tools. The attacker starts the flow on their own machine and sends the victim the user-code and the genuine verification URL.

  • Victim enters the code
  • Tokens bind to the attacker's session

Why it is harder to catch

No malicious app is registered, so there is no new service principal to triage. The victim approves a real Microsoft prompt.

  • No service principal
  • Still a genuine consent page
The full grant-type catalogue is in the dedicated OAuth material. Auth-code consent, device-code, and refresh-token persistence are all this lesson needs.
HACKTHESOCLesson 54OAuth consent phishing24 / 56
The refresh token is the persistence engine.

Granted by offline_access, it silently mints fresh access tokens without the user present and survives a password reset.

This is why the response section revokes sessions rather than trusting a reset. Keep returning to the refresh token as the thing that must be killed.

Delegated vs application permissions

Whose data the app can reach changes the blast radius.

HACKTHESOCLesson 54OAuth consent phishing26 / 56

Same scope name, very different reach

Delegated permissionApplication permission
Acts asThe signed-in userThe application itself, unattended
Effective accessIntersection of the grant and that user's own accessFull scope across the tenant
Who can consentSometimes the end user; admin for high-privilege scopesAlways an administrator
Consent-phishing targetYes: the lure in this lessonRare via an ordinary user lure
Mail.Read reachOne mailbox: the consenting user'sEvery mailbox in the organisation
One car's valet key versus a master key to every car in the garage. Application permissions are also called app roles.
HACKTHESOCLesson 54OAuth consent phishing27 / 56

Why the same scope reaches one mailbox or all of them

  1. 1Delegated: app plus userThe app acts on behalf of the signed-in user.
  2. 2Delegated: the intersectionEffective access is the overlap of the grant and what that user could already reach: one mailbox.
  3. 3Application: app aloneThe app acts as itself, with no user present.
  4. 4Application: the full scopeMail.Read as an application permission reads every mailbox in the tenant.

One car's valet key versus a master key to every car in the garage.

The intersection rule is the key idea: delegated Mail.Read cannot exceed the consenting user's own reach, however the app is coded.
HACKTHESOCLesson 54OAuth consent phishing28 / 56

Know which event you are reading before you scope

Delegated

Principal

On Consent to application: one user consented for themselves only. One mailbox.

Still delegated

AllPrincipals

An admin consented to delegated scopes for every user. ConsentContext.IsAdminConsent and OnBehalfOfAll read True.

Application permission

App role assignment

A separate Add app role assignment to service principal event naming the role, e.g. full_access_as_app. Tenant-wide.

Delegated grants also log an Add delegated permission grant event alongside the consent.

Common mistake: AllPrincipals is not the marker of an application permission; it is delegated access pre-approved for everyone.
HACKTHESOCLesson 54OAuth consent phishing29 / 56

Three consent signatures in the audit log

Audit signaturePermission typeReach
Consent to application, ConsentType PrincipalDelegated, one userThat user's mailbox
Consent to application, AllPrincipals + IsAdminConsent TrueDelegated, admin for everyoneEvery user, but still user-scoped
Add app role assignment to service principalApplication permissionTenant-wide, no user needed
The common mistake is reading AllPrincipals as an application permission. It is delegated access pre-approved for everyone; the app-role event is the tenant-wide one.
HACKTHESOCLesson 54OAuth consent phishing30 / 56
Tenant-wide access needs an administrator, so admin consent is the checkpoint.

Treat consent initiated by a privileged account with extra scrutiny. An admin consent workflow puts a human review in front of the single-mailbox to entire-tenant jump.

The attacker must get an administrator to approve, or exploit a tenant configured for broader self-service consent than it should allow.

Real-world case: Midnight Blizzard (APT29)

Microsoft's own corporate email, November 2023 to January 2024.

HACKTHESOCLesson 54OAuth consent phishing32 / 56

From password spray to every mailbox

  1. 1Initial accessPassword spray on a legacy, non-production test tenant without MFA.
  2. 2The pivotA legacy test OAuth app there held application permissions into the corporate environment.
  3. 3EscalationNew malicious apps and a user; admin consent to their own apps, an app role assignment event.
  4. 4The payloadExchange Online full_access_as_app: an application permission to every mailbox.
  5. 5ObjectivesEmails from senior leadership and security staff; secrets, certificates, credentials.
Midnight Blizzard is also APT29, NOBELIUM, Cozy Bear, acting for Russia's SVR. The escalation was the admin-consented application-permission path, not a single user's delegated Principal grant.

Lesson conceptHow Midnight Blizzard used it
Application permission acts tenant-widefull_access_as_app read every mailbox, no user signed in
Application permissions need admin consentThe actor compromised a legacy app that could grant it

Entry was a classic spray on an MFA-less test tenant; the escalation and impact were entirely OAuth app governance.

Password and MFA controls did not stop it. It was an app-governance failure.

After the spray, the attacker lived entirely in application permissions and OAuth grants. A standing, over-permissioned, unreviewed app was the root cause.

Periodic grant review is not box-ticking; it is the exact control that would have contained the most serious cloud-identity breach on record.

Section 7 of 9

Why it is so dangerous

It sidesteps the defences organisations trust most.

HACKTHESOCLesson 54OAuth consent phishing36 / 56

Five properties of a quiet, durable compromise

  • Survives password resetsThe attacker never had the password; the refresh token is untouched by a reset.
  • Survives MFAMFA was completed before consent; background API calls are never re-prompted.
  • Blends into trafficSame APIs as legitimate add-ins, valid tokens, no failed logins, no impossible travel.
  • Trustworthy linkGenuine consent domain passes URL filtering and 'check the domain' training.
  • Broad and persistentContinuous exfiltration and BEC from a genuinely trusted colleague's mailbox.
The standard first-response reflex, reset the password, fails. If the analyst does not revoke the consent, access continues.
HACKTHESOCLesson 54OAuth consent phishing37 / 56

Why the usual first responses fail here

Reset the password

The attacker never had it. The refresh token is untouched and keeps minting access.

  • Does nothing to the grant

Re-prompt for MFA

MFA was satisfied before consent. Background API calls are never challenged again.

  • No sign-in to challenge

Watch for login anomalies

No failed logins, no impossible travel. The app uses valid tokens and the same APIs as real add-ins.

  • Nothing anomalous at the identity layer
The correct response is to revoke the grant and the sessions. This slide is the bridge to the detection and response sections.

Detection: reading the consent audit log

Detection centres on consent and app-permission events, not sign-in anomalies.

HACKTHESOCLesson 54OAuth consent phishing39 / 56

The audit event when the victim clicks Accept

  • initiatedBy.user.userPrincipalName names the victim
  • targetResources[0].displayName names the app
  • modifiedProperties holds the exact scopes granted
This single event is ground truth: what happened, when, to whom, and to what extent.
HACKTHESOCLesson 54OAuth consent phishing40 / 56

Reading the consent event in order

  1. 1What happenedactivityDisplayName: Consent to application, result success.
  2. 2To whominitiatedBy.user.userPrincipalName names the victim who clicked Accept.
  3. 3Which apptargetResources[0].displayName: the app, here Mail Sync Helper.
  4. 4How muchmodifiedProperties holds the exact scopes: Mail.Read offline_access Files.Read.All.
This one event answers what, when, who and how much. Everything else in the investigation pivots off the app named here.
HACKTHESOCLesson 54OAuth consent phishing41 / 56

Signals to hunt

  • Consent eventsSpikes across many users, or grants to an app no one recognises.
  • Sensitive scopes togetherMail.Read, Mail.ReadWrite, offline_access, Files.Read.All in modifiedProperties.
  • Suspicious appsLow prevalence, generic or brand-imitating names, unverified publishers, unfamiliar redirect_uri.
  • Campaign patternMany users consenting to the same unfamiliar app in a short window.
  • CorrelationA phishing email wave, then the app accessing Graph mail data.
Defender for Cloud Apps, OAuth app governance and risky OAuth app detections give leads; confirm in the audit log field by field.

Section 9 of 9

Defence and response

Remove the click, review the grants, revoke the tokens.

HACKTHESOCLesson 54OAuth consent phishing46 / 56

Prevention and governance

Restrict user consent

Users cannot freely consent, or only to verified publishers for low-risk permissions. The single most effective control.

Admin consent workflow

Requests beyond the baseline go to administrators for review before any grant.

Review and educate

Audit existing grants and remove unused or unrecognised apps. Teach that a trustworthy domain does not mean a trustworthy app.

The domain proves the mechanism is genuine, not that the requester is.
HACKTHESOCLesson 54OAuth consent phishing47 / 56

Where each control stops the attack

ControlStage it stopsHow
Restrict user consentThe clickAn untrained user can no longer approve a third-party app
Admin consent workflowTenant-wide grantsA human reviews the app and scopes before any grant
Periodic grant reviewStanding exposureFinds and removes over-permissioned or unknown apps, the Midnight Blizzard gap
Restricting user consent removes the moment of decision from the user entirely, which is why it is the single most effective control.
HACKTHESOCLesson 54OAuth consent phishing48 / 56

Hunt existing risky grants in Sentinel

mv-apply picks the scopes entry by displayName, not position, because the ConsentContext flags usually come first. Run it on a schedule to answer: has anyone already granted a risky app broad mailbox access?
HACKTHESOCLesson 54OAuth consent phishing49 / 56

Enumerate grants that already exist

  • Get-MgOauth2PermissionGrantEvery delegated grant: which app, which scopes, which user or AllPrincipals.
  • App role assignmentsGet-MgServicePrincipalAppRoleAssignment: every application permission, e.g. full_access_as_app.
  • Enterprise applicationsThe Permissions blade shows admin- and user-consented grants per app.
  • Detect app role assignmentAlert on Add app role assignment to service principal, the Midnight Blizzard event.
The audit log shows events; enumerating live state also finds grants that predate your log retention. High-privilege app roles deserve immediate review.
HACKTHESOCLesson 54OAuth consent phishing50 / 56

Events versus live state: hunt both

Audit events

Consent to application and Add app role assignment show grants as they happen, within log retention.

  • Catches new campaigns

Live enumeration

Get-MgOauth2PermissionGrant and app-role assignments list grants that already exist, including ones older than your logs.

  • Catches standing risk
  • Predates retention
A breach can predate your log window. Enumerating live grants is how you find the over-permissioned app that was consented months ago.
HACKTHESOCLesson 54OAuth consent phishing51 / 56

Responding to a confirmed incident

  1. 1Remove grant and appRemove-MgOauth2PermissionGrant, drop app-role assignments, disable the service principal.
  2. 2Kill the tokensRevoke-MgUserSignInSession per affected user, so the refresh token cannot mint access tokens.
  3. 3Confirm silenceCheck that the app's MicrosoftGraphActivityLogs go quiet afterward.
  4. 4Hunt persistenceForwarding and inbox rules the app created; document what was read via MailItemsAccessed.
  5. 5Feed blocklistsThe app's AppId, reply URL and owner tenant, for the next campaign.
A password reset alone is insufficient. Disable the service principal with Update-MgServicePrincipal -AccountEnabled:$false, then remove it once scoped.

Key takeaways

  1. 01OAuth is a valet key: scoped tokens via a genuine consent screen, without sharing the password.
  2. 02Consent phishing (T1528) lures users to approve offline_access and Mail.Read on a real Microsoft domain.
  3. 03Token access survives password resets and MFA and blends into legitimate API traffic.
  4. 04AllPrincipals is still delegated; application permissions log as app role assignments and reach every mailbox.
  5. 05Detect via 'Consent to application', then scope by AppId with MailItemsAccessed and Graph activity logs.
  6. 06Restrict user consent, review grants, then remove the grant and app and revoke the refresh tokens.

The attacker never needs the password: the app holds a refresh token, and a reset does not revoke the grant. They use the app's own tokens, not the user's browser session or a sign-in, and the consent page is Microsoft's real page.
