Section 1 of 11

Reading email headers like a forensic investigator

The hidden metadata that records how a message got to you and what checks it passed.

HACKTHESOCLesson 20Phishing investigation6 / 89

What an email actually is

Body

What the mail client shows: text, images, formatting.

Headers

Hidden metadata: every server hop plus SPF, DKIM and DMARC results. Tells you in 60 seconds if a message is legitimate, spoofed or from a compromised account.

Attachment

A file bundled with the message, stored and inspected separately from the body.

SMTP is the postal handoff between mail servers; every handoff is stamped in a Received header.

Many juniors skip headers because they look intimidating. They are just a structured log of the message's journey.
HACKTHESOCLesson 20Phishing investigation7 / 89

How the Received chain gets written

  1. 1Each server adds a stampEvery mail server that handles the message writes its own Received header on top of the pile.
  2. 2Newest on topThe topmost header is your own mail server; the bottommost is the originating server.
  3. 3Three parts per stampA from clause (what the sender claimed), a by clause (the receiver) and usually a bracketed IP.
  4. 4Read bottom-upStart at the earliest hop and trust the bracketed IP, not the announced name.
  5. 5Reverse-resolve the IPDoes it belong to the claimed domain, or to a residential ISP in another country?
The from name is whatever the sending server announced, so it can be spoofed trivially. The IP was observed by the receiving server, which is why it is authoritative.
HACKTHESOCLesson 20Phishing investigation8 / 89

One Received header, read part by part

  • from mail.attacker.com: the name the sending server announced; trivially spoofed
  • [203.0.113.45]: the IP the receiver actually saw connect; the authoritative value
  • by inbound.contoso.com: the server that received the message and wrote this stamp
Students should be able to label these three parts on any Received line before moving on to a full chain.
HACKTHESOCLesson 20Phishing investigation9 / 89

Five header checks, in order

  • Received chainRead bottom-up. The bracketed IP is authoritative; the from name can be spoofed. Reverse-resolve the IP.
  • Authentication-ResultsWant spf=pass dkim=pass dmarc=pass. Watch spf=softfail and dmarc=none: weak policy, delivered anyway.
  • From vs Return-PathDisplayed sender versus the SMTP envelope sender. Mismatch is a phishing hallmark (mailing lists aside).
  • Message-IDDomain should match a real mail server. @localhost.localdomain is a phishing-kit default.
  • X-headersX-Mailer (Gophish, Evilginx), X-Originating-IP; AuthAs=Anonymous on internal-looking mail is a tell; SEG = secure email gateway verdict stamps.
Habit: open every suspicious message in 'view source' or 'show original' before clicking anything.

HACKTHESOCLesson 20Phishing investigation11 / 89

From and Return-Path disagree: when it matters

From is what the user sees; Return-Path is the envelope sender SMTP actually used.

Legitimate mismatch

Mailing lists and bulk senders routinely use a different envelope sender, for example a bounce-handling address at their sending service.

Phishing hallmark

From: CEO <ceo@yourcompany.com> with a Return-Path of attacker@cheap-vps-provider.ru. No business reason connects the two.

Mail clients hide the Return-Path by default, so you must open the headers to see it.

A mismatch is a question, not a verdict: ask whether a known sending service explains it.

Worked example: spot the spoof

A finance employee thinks the CFO wants an urgent wire approved.

HACKTHESOCLesson 20Phishing investigation15 / 89

The raw header block

  • Bottom hop is the true origin: freehosting-mx.net at 185.220.101.47
  • spf=pass is the trap: it passed for freehosting-mx.net, not contoso.com
  • dmarc=fail on your own real domain: strong evidence of spoofing
Long Received lines are trimmed for the slide; the hop order and IPs are exactly as in the lesson.
HACKTHESOCLesson 20Phishing investigation16 / 89

Why spf=pass here is the trap

SPF checks the envelope sender (smtp.mailfrom, the Return-Path domain), not the visible From.

spf=pass

For freehosting-mx.net, the attacker's own domain, whose SPF record authorizes its own server. contoso.com's SPF record was never consulted.

dkim=none

The message carries no signature at all.

dmarc=fail

DMARC needs an aligned pass. SPF passed for a domain that does not match header.from=contoso.com, and there is no DKIM to align.

Passing SPF on an unrelated domain plus DMARC failing on your own domain is the gap DMARC was built to close.

This is exact-domain From spoofing: the attacker forged the address itself, so DMARC on contoso.com can catch it. Contrast display-name spoofing, where the address is openly foreign (d.cohen.cfo@gmail.com) and DMARC on contoso.com never applies.
HACKTHESOCLesson 20Phishing investigation17 / 89

Fromd.cohen@contoso.com, the real CFO's exact addressWhat the employee saw: forged
Return-Pathalerts@freehosting-mx.netThe real SMTP sender: unrelated domain
Reply-Tod.cohen.finance@outlook.comA careful 'reply to check' goes to the attacker

Who really sent it, does it check out, where would a reply go: answered before any sandbox or click.
HACKTHESOCLesson 20Phishing investigation18 / 89

Exact-domain spoof versus display-name spoof

This example

Exact-domain spoof

The address itself is forged: d.cohen@contoso.com. Because it claims contoso.com, DMARC on contoso.com applies and can catch it.

Covered later

Display-name spoof

"David Cohen - CFO" <d.cohen.cfo@gmail.com>. The address is openly foreign, DMARC on contoso.com never applies, and only the name lies.

Look at the address, not the name the mail client displays.

Many mail clients show only the display name, which is why display-name spoofing works on busy staff.

Section 3 of 11

SPF, DKIM and DMARC deep dive

What each proves, what it does not, and how attackers use the gaps.

HACKTHESOCLesson 20Phishing investigation21 / 89

Three standards, three limits

StandardWhat it verifiesKey limitation
SPFSending IP against a TXT record in the envelope-sender (MAIL FROM) domain's DNSChecks only the envelope sender, not the visible From; often breaks on forwarding
DKIMSignature from the domain's private key, checked with its public key in DNSFails as dkim=none, dkim=neutral or dkim=fail
DMARCAlignment of SPF/DKIM domain with the visible From, plus a policyOnly as strong as the policy; many large brands use p=none
Misunderstanding authentication is the most common reason juniors misclassify phishing as legitimate. Example SPF record: v=spf1 ip4:198.51.100.0/24 include:_spf.google.com -all.
HACKTHESOCLesson 20Phishing investigation22 / 89

How an SPF check runs

  1. 1Owner publishes a recordA TXT record such as v=spf1 ip4:198.51.100.0/24 include:_spf.google.com -all.
  2. 2Message arrivesThe receiver notes the SMTP MAIL FROM domain, not the visible From.
  3. 3DNS lookupThe receiver fetches that domain's SPF record.
  4. 4Compare the IPIs the connecting server's IP in the authorized list?
  5. 5Verdictpass, fail, or a softer softfail or neutral.

The gap: an attacker passes SPF with a Return-Path domain they own while spoofing the visible From.

The example record says only that /24 range and Google's senders may send for example.com; -all says everything else fails.
HACKTHESOCLesson 20Phishing investigation23 / 89

What a valid DKIM signature does and does not prove

It proves

An authorized server for the signing domain sent it, and the signed headers and body were not altered in transit.

  • Survives forwarding, unlike SPF
  • Binds content to the signing domain

It does not prove

That the signing domain is the one the user sees, which is DMARC's job, or that the sender is honest: a compromised real account signs perfectly.

Failure stamps: dkim=none (no signature), dkim=neutral (cannot verify), dkim=fail (invalid).

DKIM uses a private key held by the sender and a public key published in DNS for receivers to check against.
HACKTHESOCLesson 20Phishing investigation24 / 89

DMARC passes only when SPF or DKIM passes for the same domain as the visible From.

MessagePassed forVisible FromDMARC

Row three is the trap that leads to the next slide: alignment only proves the mail matches the domain it claims, and the attacker owns that domain.
HACKTHESOCLesson 20Phishing investigation25 / 89

When authentication passes and it is still phishing

Lookalike domain

Attacker owns micros0ft.com, rnicrosoft.com or microsoft-support.help and passes all three checks. Catch with content heuristics, typosquat intel and judgment.

Compromised real account

Sent by an authorized server with the real signing key, so everything passes. Detect behavior: style, timing, recipients, wire or gift-card requests.

Pass does not mean legitimate. The compromised-account case is the core of BEC detection.

This is the hardest phishing to catch because it bypasses every control that depends on domain authentication.

Attachment sandboxing and payload analysis

T1566.001: decide if a file is malicious without ever opening it on your workstation.

HACKTHESOCLesson 20Phishing investigation28 / 89

Weaponized attachment types you will meet

  • Office with macrosThe document launches a script when macros run.
  • ISO and IMG containersMounted files skip mark-of-the-web warnings.
  • OneNote filesEmbedded scripts behind a "click to view" lure.
  • HTML smugglingJavaScript builds the payload inside the browser.
  • Password-protected ZIPsThe gateway cannot open them to scan the contents.
  • LNK filesShortcuts that launch a hidden command.
The goal is the same for all of them: get a verdict without opening the file on your own workstation, then extract IOCs to hunt other victims.
HACKTHESOCLesson 20Phishing investigation29 / 89

From hash to verdict

  1. 1Start with metadataEmailAttachmentInfo: FileName, FileType, SHA256, FileSize, ThreatTypes. Pivot on SHA256 first.
  2. 2Known hash?Flagged in TI, VirusTotal or MalwareFamily: skip to scoping. Novel hashes in bulk are more suspicious.
  3. 3DetonateSafe Attachments, Joe Sandbox, ANY.RUN, Hybrid Analysis or Cuckoo. Never your endpoint.
  4. 4Read the reportNew domains, cmd or powershell from the document process, startup folder or Run key writes.
Weaponized types you will see: macro documents, ISO/IMG, OneNote, HTML smuggling, password-protected ZIPs, LNK files.
HACKTHESOCLesson 20Phishing investigation30 / 89

Reading a sandbox report: what to flag

Report sectionRed flag

Safe Attachments detonates automatically; you can also submit manually to Joe Sandbox, ANY.RUN, Hybrid Analysis or an in-house Cuckoo. Never on your endpoint.
HACKTHESOCLesson 20Phishing investigation31 / 89

Three payload chains to recognize

Macro chain

WINWORD.EXE spawns cmd or powershell, downloads a second stage, writes to %APPDATA% or %TEMP%. T1059.001 with T1204.002.

ISO / IMG

Mounted files lack the Zone.Identifier ADS, so MOTW checks skip. A LNK runs a hidden script that runs a DLL via rundll32 (T1218.011).

HTML smuggling

Base64 JavaScript rebuilds the binary in the browser. Look for atob() with Blob and URL.createObjectURL.

Sysmon Event ID 1 or EDR captures the macro chain. Correlate ISO attachments with DeviceFileEvents to see if files were extracted.
HACKTHESOCLesson 20Phishing investigation32 / 89

The macro chain as endpoint telemetry

  • A word processor should not be the parent of PowerShell: the IOA
  • The child then writes an executable into %APPDATA%: the second stage landing
  • Maps to T1059.001 (PowerShell) with T1204.002 (User Execution: Malicious File)
Illustrative event pair. Sysmon Event ID 1 captures the chain; EDRs such as Defender for Endpoint, CrowdStrike or SentinelOne show the same parent-child tree.
HACKTHESOCLesson 20Phishing investigation33 / 89

Where to hunt each question about a bad file

QuestionTable to query
Who received the campaign?EmailEvents and EmailUrlInfo
Where did the file land on disk?DeviceFileEvents
Where did it actually execute?DeviceProcessEvents
Did it call out?DeviceNetworkEvents

Then block the hash in your EDR and document the campaign so the next analyst resolves it in seconds.

Landing on disk is not execution. Students often stop at DeviceFileEvents and report the wrong conclusion.
HACKTHESOCLesson 20Phishing investigation34 / 89

Scope a confirmed malicious hash tenant-wide

This finds every recipient and every device where the file landed on disk. To confirm execution, run the same SHA256 filter against DeviceProcessEvents, then block the hash in your EDR.

T1566.002: safe-detonate the link, then find everyone who clicked.

FieldWhat it tells you
ActionType ClickAllowedSafe Links let the click through

Safe Links rewrites every inbound URL to route through Microsoft's verdict service, which is why each click is logged here.
HACKTHESOCLesson 20Phishing investigation37 / 89

Safe Links, safe tools, and page hallmarks

  • UrlClickEventsActionType (ClickAllowed, ClickBlocked, ClickAllowedByEndUser), Url, NetworkMessageId, AccountUpn.
  • Detonate safelyInvestigation VM, browser isolation, urlscan.io (screenshot, resources, shareable), VirusTotal, ANY.RUN.
  • The URLReal Microsoft logins live under login.microsoftonline.com or login.live.com. Flag domains under 30 days old.
  • The page sourceCopied HTML with the form action pointing at the attacker. Trace where credentials are POSTed.
  • The parametersA base64-encoded victim email in the URL, used to pre-fill the form, is a strong signal, e.g. ?e=dXNlckBjby5jb20=.
UrlClickEvents is gold: confirm the URL is bad and you immediately have the list of accounts to reset.
HACKTHESOCLesson 20Phishing investigation38 / 89

Real Microsoft login versus a harvesting page

Real sign-in hosts

Microsoft logins live under a small set of known hosts or tenant-branded subdomains.

  • login.microsoftonline.com
  • login.live.com

Harvesting hosts

Anything else that claims to be a Microsoft login is almost certainly phishing, especially if registered in the past 30 days.

  • login-microsoft-secure.com
  • microsoft.login-secure-portal.com
  • microsoft365-account-verify.com
Enrich the URL with WHOIS and flag young domains. Then check the page source: the form action shows where the credentials would really go.
HACKTHESOCLesson 20Phishing investigation39 / 89
AiTM phishing proxies the real login and steals the session cookie after MFA.

Evilginx, Modlishka, Muraena. The victim sees a normal login; the attacker gets post-MFA access. Look for odd sign-ins minutes after a click.

Signal: successful sign-in from a Tor exit, hosting provider IP, or never-seen country within minutes of a Safe Links click.
HACKTHESOCLesson 20Phishing investigation40 / 89

What an AiTM phish leaves in your logs, in order

  1. 1The clickUrlClickEvents: ClickAllowed for the user, to a look-alike login domain.
  2. 2A normal-looking sign-inThe user's own sign-in succeeds with MFA, so nothing fails or alerts.
  3. 3A second sessionAADSignInEventsBeta: success for the same account from a hosting, Tor or new-country IP.
  4. 4Minutes apartClick and foreign sign-in sit within the same short window: the correlation.
  5. 5Follow-on activityNew inbox rules or OAuth consents from that new IP.

Read the context, not the result: the password and MFA were both correct.

AiTM means adversary-in-the-middle: a proxy relays the real login and keeps the session cookie issued after MFA. The KQL on the next slide joins steps 1 and 3.
HACKTHESOCLesson 20Phishing investigation41 / 89

Clicks joined to suspicious sign-ins

IPAddress1 is the sign-in IP after the join. A click followed by a sign-in from elsewhere within two hours is the AiTM pattern.
HACKTHESOCLesson 20Phishing investigation42 / 89

Containment for a credential-harvesting URL

  1. 1BlockTenant block list and web proxy.
  2. 2Find clickersUrlClickEvents, at least the past 14 days.
  3. 3Reset and revokePassword reset and session revocation via Graph or Entra admin center.
  4. 4Check sign-insAADSignInEventsBeta for successful malicious sign-ins.
  5. 5Rules and appsNew inbox rules (T1564.008) and OAuth consents (T1528).
  6. 6Purge and briefEmail purge in Threat Explorer; brief leadership if widespread.
Attackers routinely create inbox rules to hide their tracks right after a successful phish.

Section 6 of 11

Business email compromise end to end

Often no link, no attachment: just a crafted request, so judgment carries detection.

HACKTHESOCLesson 20Phishing investigation44 / 89

The CEO fraud pattern

The ask

"CEO" to finance: urgent wire to a new vendor. "I'm in a meeting, can't talk, need this in the next hour."

The sender

Lookalike (ceo@yourc0mpany.com), free-mail display-name spoof, or the CEO's real compromised account.

Per the FBI's IC3, BEC is one of the costliest cybercrime categories: roughly $2.7 to 2.9 billion in reported losses a year.

With no payload to detonate, BEC bypasses every control that depends on payload analysis. In recent IC3 reports it is second only to investment fraud.
HACKTHESOCLesson 20Phishing investigation45 / 89

Three BEC senders, three different tells

Sender typeExampleWhat authentication shows
Lookalike domainceo@yourc0mpany.comPasses for the lookalike. Read the domain letter by letter
Display-name spoof"Jane Doe (CEO)" <jane.doe.ceo@gmail.com>Passes for gmail.com. The address is not yours
Compromised real accountThe CEO's actual mailboxPasses everything. Only behavior gives it away
The third row is the hardest case and the reason BEC detection relies on analyst judgment.
HACKTHESOCLesson 20Phishing investigation46 / 89

Behavioral signals when authentication passes

  • A sudden change in the sender's writing style
  • Mail sent at unusual times for this person
  • Unusual recipients, such as several finance staff at once
  • Links to credential-harvesting pages from a trusted colleague
  • Requests for wire transfers or gift cards, with urgency pressure
These are the only signals left once the attacker controls a real mailbox, so compare against how this person normally writes and who they normally email.
HACKTHESOCLesson 20Phishing investigation47 / 89

The BEC investigation sequence

  1. 1Confirm metadataHeaders, true sender domain and IP, auth results, real address or lookalike.
  2. 2Determine scopeEmailEvents by SenderIPv4 or SenderMailFromAddress, 30 days.
  3. 3Investigate compromiseAADSignInEventsBeta: when, from what IP and country.
  4. 4Inbox rulesNew-InboxRule, Set-InboxRule moving replies to RSS Feeds or hidden folders.
  5. 5OAuth consentsNew apps granted Mail.ReadWrite; revoke in Enterprise Applications.
  6. 6RemediatePurge, reset, revoke, halt wires, IC3.gov within the 72-hour window.
BEC often hits several finance employees in parallel, hoping one complies.
HACKTHESOCLesson 20Phishing investigation48 / 89

Inbox rules created after a risky sign-in

Rules with 'subject contains wire transfer' and a delete or hide action are textbook BEC persistence.
HACKTHESOCLesson 20Phishing investigation49 / 89

Reading an inbox rule: housekeeping or cover-up?

Typical user rule

Moves newsletters from a known sender into a folder the user actually reads.

BEC persistence rule

Created right after a risky sign-in, it hides the replies to the fraud so the real user never sees them.

  • Condition: subject contains "wire transfer"
  • Condition: from contains "CFO"
  • Action: move to RSS Feeds or Conversation History
  • Action: delete
Look for New-InboxRule and Set-InboxRule in the mailbox audit log over the past 30 days. Timing relative to the sign-in matters as much as content. Technique T1564.008.
HACKTHESOCLesson 20Phishing investigation50 / 89

If a wire may already have been sent

  1. 1Halt the paymentTell finance and treasury to stop any wire started in response to the request.
  2. 2Call the receiving bankIf money left, contact the receiving bank immediately.
  3. 3File with IC3.govFunds can sometimes be recovered within the 72-hour window.
  4. 4Brief and learnInform leadership, legal and any regulators; review both the detection gap and the process gap.
Speed is everything here. The technical clean-up (purge, reset, revoke) runs in parallel, not first.
HACKTHESOCLesson 20Phishing investigation51 / 89

Long-term BEC defense

Technical controls

Make spoofing and account takeover harder.

  • DMARC at p=reject for your domains
  • Lookalike-domain monitoring
  • Phishing-resistant MFA (FIDO2)
  • Conditional access on risky sign-ins

Process controls

Make a convincing request fail anyway.

  • Out-of-band verification of payment requests
  • Dual approval for wires above a threshold
  • Finance training on urgency pressure
Feed detection findings back into the process side so the organization becomes more resilient.

The triage workflow: report, verdict, purge

The repeatable path from a user's report to a closed, contained case.

HACKTHESOCLesson 20Phishing investigation53 / 89

Three stages, always in order

  1. 1Receive and prioritisePreserve the raw message; note who reported it and whether they clicked or typed a password.
  2. 2Examine three layers safelyHeaders and authentication, links in a sandbox, the attachment by hash and sandbox. Never click live.
  3. 3Reach a verdictBenign, spam or malicious phish: a clear disposition that drives the response.
Phishing is the most common alert type most SOCs handle, so making this flow automatic is one of the highest-value habits you can build.
HACKTHESOCLesson 20Phishing investigation54 / 89

Phishing triage is a pipeline

Stopping at 'yes, it's phishing' is the analysis, not the job.
HACKTHESOCLesson 20Phishing investigation55 / 89

A malicious verdict starts four actions

  • BlockThe sender, sending domain, URL and attachment hash, so future copies stop.
  • Purge tenant-wideRemove the message from every mailbox that received it, not only the reporter's.
  • Scale to the userMatch the depth of response to what the user actually did (next slide).
  • TuneFeed the confirmed indicators into detection so the next copy is caught automatically.
Beginners neglect this stage, and it is the one that actually protects the organization.
HACKTHESOCLesson 20Phishing investigation56 / 89

Section 8 of 11

Quishing, callback phishing, modern lures

Phishing designed to carry no payload your tools can detonate.

HACKTHESOCLesson 20Phishing investigation58 / 89

Four lures to know on sight

  • QuishingURL hidden in a QR image, scanned on an often unmanaged phone. Decode the image to get the URL.
  • Callback (TOAD)No link, no file: a pretext and a phone number. A human talks the victim into remote access.
  • HTML smugglingPayload assembled in the browser by JavaScript, so nothing bad crosses the gateway.
  • Thread hijackingA reply inside a genuine thread from a compromised mailbox, with real history.

The signal moves from the payload to the pretext and the anomaly.

A clean attachment scan does not clear an HTML-smuggling file or a hijacked thread.
HACKTHESOCLesson 20Phishing investigation59 / 89

Why each lure slips past tooling, and what you do

LureWhy the tools miss itWhat the analyst does
QuishingLink scanners see only an image; the code is scanned on a phoneDecode the QR image to extract the URL, then analyse it
Callback (TOAD)No link and no file: nothing to detonateTreat a lone phone number with an urgent pretext as a lead
HTML smugglingThe bad file does not exist until the browser builds itA clean scan does not clear it; inspect the HTML content

TOAD stands for Telephone-Oriented Attack Delivery. In every row the signal has moved from the payload to the pretext and the anomaly.
HACKTHESOCLesson 20Phishing investigation60 / 89

Callback phishing: what each data source shows

The lure is a fake invoice plus a phone number; a human on the call does the rest.

  1. 1Mail logsA delivered message with no URL in EmailUrlInfo and no attachment: nothing to detonate.
  2. 2The user reportOften the only signal: "I called the number about a $499 renewal."

Hunting the campaign

One reported email is almost never one email.

HACKTHESOCLesson 20Phishing investigation63 / 89

Pivot to recipients, then to interactions

Who received it?

Each pivot expands one email into the full recipient list.

  • Same sender address, IP or domain
  • Same or similar subject
  • Same URL or domain
  • Same attachment hash

Who interacted?

The credential question is the most urgent one.

  • Opened or clicked: mail and proxy logs
  • Entered credentials: odd sign-ins after
  • Ran the file: EDR hash search
The reporter did the right thing because they did not fall for it. The real risk is the quiet recipients.

Three ways a URL hides its destination

  • Redirect chainsSafe Links wrapper, then an open redirect on a trusted site, then the payload. The final landing domain decides.
  • URL shortenersbit.ly, tinyurl.com, t.co hide the domain from reputation filters. Expand only in a sandbox.
  • IDN homographsPunycode xn-- domains can render as apple.com, e.g. 2017's xn--80ak6aa92e.com. Hard stop for review.

DMARC anatomy, alignment and ZAP

Read a real DMARC record, and know when Defender already cleaned up.

HACKTHESOCLesson 20Phishing investigation77 / 89

A well-configured DMARC record

  • p=none only logs failures: the domain is still spoofable in practice
  • Missing or weak sp= leaves subdomains open even when root is p=reject
  • adkim=s strict alignment; r relaxed (default) allows the org domain
rua gets daily aggregate XML reports, ruf per-message failure reports, fo=1 reports if either SPF or DKIM fails. pct was removed by RFC 9989.
HACKTHESOCLesson 20Phishing investigation78 / 89

DMARC tags, read for an investigation

TagMeaningWhy the analyst cares
p=Policy for failing mail: none, quarantine or rejectp=none means the domain is still spoofable in practice
sp=Policy for subdomainsMissing or weak sp= leaves mail.example.com open
rua=Address for daily aggregate XML reportsHow owners see who sends as their domain

The three DMARC policies, and why owners start weak

p=none

Failures are logged, then delivered. Owners start here on purpose to observe all their legitimate senders through rua reports.

p=quarantine

Failing mail is delivered to junk. The usual middle step once known senders are fixed.

p=reject

Failing mail is dropped. The goal, but jumping straight to it can silently break marketing, HR and ticketing mail.

Microsoft and every major mailbox provider recommend this staged rollout.

Zero-hour auto purge: retroactive remediation

What ZAP does

Re-scans delivered messages when a URL or file is reclassified later, moving them to Quarantine or Junk without notifying the user. Covers Inbox, Deleted Items, and since 2026 Teams links on Plan 1.

Its limit

Only messages delivered in the last 48 hours. A phish that sat undetected for a week will not be swept up by ZAP alone.

Check EmailPostDeliveryEvents first: ActionType 'Phish ZAP', 'Malware ZAP' or 'Manual remediation', plus ActionTrigger, DeliveryLocation, SourceLocation.
