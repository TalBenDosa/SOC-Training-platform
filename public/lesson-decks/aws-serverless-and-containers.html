Renting a kitchen, ordering a meal kit, or ordering delivery: AWS compute is a choice of how much cleanup you own.

EC2 gives full control and full cleanup. Containers give a standard box and someone else's stove. Serverless means you specify the dish and pay per meal.

Open with the meal analogy and come back to it. Each compute model trades control for less operational work.

The compute spectrum: what you manage

Every choice answers one question: how much of the stack do you want to run yourself?

HACKTHESOCLesson 111Serverless and containers6 / 47

Three models, three levels of responsibility

Renting a kitchen

EC2 (virtual machines)

You pick the instance type, AMI and network placement, and own everything above the hypervisor: OS patching, runtimes, agents, scaling, capacity.

  • Pay per second while running (Linux)
  • Legacy, GPUs, large memory, licensing

A meal kit

Containers

Code and dependencies packaged in an image that runs the same everywhere. You decide how many copies run and how much CPU and memory each gets.

  • Run on EC2 hosts you manage
  • Or on Fargate, where AWS manages hosts

Delivery

Serverless (Lambda)

You upload a function. AWS scales execution environments from zero to thousands and bills only for the milliseconds your code runs.

  • You manage code, memory, timeout, permissions
  • And event wiring, nothing below that
EC2 for legacy software, special hardware, licensing constraints, or very steady and heavy workloads where reserved capacity is cheapest.

Serverless does not mean no security work.

With Fargate and Lambda, AWS takes the OS and host layer. You still own code, dependencies, IAM permissions and data.

With EC2 the customer secures the guest OS and everything above. A frequent beginner mistake is assuming serverless removes security work. Questions to ask: how long does a unit of work run, is traffic steady or spiky, who patches?

Lambda: events, execution model, limits

A trigger produces an event, Lambda hands it to your handler, and the handler returns.

HACKTHESOCLesson 111Serverless and containers10 / 47

Three trigger families decide who waits and who retries

The caller waits

Synchronous

API Gateway, Application Load Balancer and direct SDK invokes. Errors go back to the caller.

    The caller hands off

    Asynchronous

    S3, SNS and EventBridge. Lambda queues the event and retries failures twice by default.

    • Attach a dead-letter queue
    • Or an on-failure destination

    Event source mapping

    Poll-based

    Lambda itself polls SQS, Kinesis, DynamoDB Streams or Kafka and invokes your function with batches of records.

      Async retries mean your function can run twice for the same event, so it must be idempotent. Remember this for the pipeline at the end.
      HACKTHESOCLesson 111Serverless and containers11 / 47

      Cold start: the life of an execution environment

      Typically tens to hundreds of milliseconds for Node.js or Python, often longer for Java, .NET or large packages.

      1. 1Init phase (cold start)Download the code, start the runtime, run code outside the handler.
      2. 2Handler runsYour code processes the event and returns.
      3. 3Environment kept warmIt stays alive for a while after the invoke.
      4. 4Later invocations reuse itThey skip init. Each environment handles exactly one request at a time.
      The one-request-at-a-time rule drives concurrency: 300 simultaneous requests need 300 environments.
      HACKTHESOCLesson 111Serverless and containers12 / 47

      Concurrency, knobs and limits to memorize

      SettingValue or behaviourWhy it matters
      Default concurrency1,000 concurrent executions per regionA soft limit you can raise
      Reserved concurrencyCaps and guarantees a function's shareProtects the function and the downstream database it calls
      Provisioned concurrencyPre-initialized environmentsAvoids cold starts on latency-sensitive paths, at an hourly cost
      Memory128 MB up to 10,240 MBCPU scales with memory, so CPU-bound code can run cheaper at higher memory
      TimeoutMaximum 900 seconds (15 minutes)A hard limit, not a design target
      Payload and storageAbout 6 MB synchronous, 512 MB /tmp by defaultZip: 50 MB zipped, 250 MB unzipped; container images up to 10 GB
      PricingPer request plus duration in GB-secondsAbout 20 cents per million requests; free tier 1M requests, 400,000 GB-seconds

      Idle costs nothing: superb for spiky work, expensive for a function that runs hot 24/7.

      GB-seconds are memory multiplied by billed time. Pitfalls: treating 15 minutes as a target, opening a database connection per invocation and exhausting the database in a burst.

      A handler and what lives outside it

      • Outside the handler: runs once per cold start, ideal for SDK clients
      • The counter is per environment: warm calls keep counting up
      Show that the counter climbs on warm invocations and resets on a new environment. That is the cold start made visible.

      API Gateway and the serverless web pattern

      A managed front door: TLS, routing, throttling and authorization before your backend.

      HACKTHESOCLesson 111Serverless and containers15 / 47

      Pick the API type that matches the job

      Feature-rich

      REST API

      Request validation, usage plans and API keys, caching, WAF integration, request and response transformation, private endpoints.

        Leaner, cheaper, faster

        HTTP API

        Proxies to Lambda or HTTP backends with built-in JWT authorizers. Most new simple APIs start here.

          Two-way

          WebSocket API

          Persistent two-way connections for chat or live dashboards.

            With Lambda proxy integration the whole HTTP request goes into the event and your code owns the contract.

            Think of API Gateway as a receptionist. Authorization options: IAM with SigV4 for service-to-service, Cognito user pools or JWT authorizers for end users, Lambda authorizers for custom logic.
            HACKTHESOCLesson 111Serverless and containers16 / 47

            The serverless web pattern: no servers to patch

            • Each layer scales independently and bills per use
            • Ten visitors a day costs almost nothing; the same stack survives a spike
            A classic three-tier app with no capacity planning. Ask students which hop enforces authentication here.
            HACKTHESOCLesson 111Serverless and containers17 / 47

            Four pitfalls on the serverless web path

            • Time limitAPI Gateway times out at about 29 seconds (REST) and 30 seconds (HTTP), far below Lambda's 15 minutes.
            • Throttling chainAPI Gateway, Lambda concurrency and DynamoDB capacity each throttle. Set limits deliberately and return clear 429s.
            • Cold start on the user pathUse lightweight runtimes, small packages, provisioned concurrency where it matters, lazy initialization.
            • DynamoDB designNot relational: model access patterns first (partition key and sort key). Large scans are slow and costly.
            Questions to ask: what is the p99 latency target, what happens when the database throttles, can any request take longer than 29 seconds?
            HACKTHESOCLesson 111Serverless and containers18 / 47

            Long work: accept now, process later

            A Lambda that can run 15 minutes still cannot hold a synchronous HTTP request open that long.

            1. 1Return 202 with a job IDAnswer the caller immediately.
            2. 2Enqueue the workA queue holds the job until a worker takes it.
            3. 3Client polls or gets a callbackThe result is delivered after processing finishes.
            This accept-then-process pattern reappears in the final pipeline, where the queue carries the work.

            Containers: images, ECR, ECS, launch types

            Build once, run identically on a laptop, in CI and in production.

            HACKTHESOCLesson 111Serverless and containers20 / 47

            A container image starts from a Dockerfile

            An image is an immutable, layered snapshot. A container is a running instance of it.

            • Containers share the host kernel, so they start in seconds
            • USER 1000: do not run as root inside the image
            Containers are isolated by kernel namespaces and cgroups, which is why they are far lighter than VMs.
            HACKTHESOCLesson 111Serverless and containers21 / 47

            ECR and the four words of ECS

            • ECRPrivate image registry: IAM push and pull, vulnerability scanning, lifecycle policies, replication.
            • Task definitionThe blueprint: containers, image, CPU and memory, ports, environment, logging, IAM roles.
            • TaskOne running instance of a task definition.
            • ServiceKeeps N tasks running, replaces failed ones, rolls out deployments, registers with a load balancer.
            • ClusterThe logical grouping of capacity.
            Deploy by immutable digest or a unique tag, never latest. Lambda container images also live in ECR.
            HACKTHESOCLesson 111Serverless and containers22 / 47

            Two IAM roles beginners mix up

            Used by ECS itself

            Task execution role

            Lets ECS pull the image from ECR and write logs.

              Used by your code

              Task role

              What your application uses to call AWS APIs such as S3.

                Also avoid: the latest tag, plain-text secrets in environment variables, and tasks sized too small.

                Secrets belong in Secrets Manager or Parameter Store. Undersized tasks get killed for out-of-memory.

                EKS and when to choose it over ECS

                Managed Kubernetes: AWS runs the control plane, you attach the workers.

                HACKTHESOCLesson 111Serverless and containers25 / 47

                Kubernetes in five words

                AWS runs and patches the control plane (API server, etcd, scheduler) across multiple Availability Zones.

                • PodThe smallest unit: one or more containers.
                • DeploymentKeeps N replicas of a pod running.
                • ServiceGives pods a stable address.
                • IngressRoutes external traffic.
                • NamespaceDivides a cluster.

                Configuration is declared in YAML manifests and applied with kubectl or a GitOps tool.

                Kubernetes is the open-source industry standard orchestrator, with a very large ecosystem of tools, operators and skills.
                HACKTHESOCLesson 111Serverless and containers26 / 47

                Four ways to supply worker capacity in EKS

                Managed node groups

                EC2 instances AWS provisions and upgrades for you.

                  Self-managed nodes

                  Maximum control, maximum effort.

                    Fargate profiles

                    Pods on serverless capacity, no nodes to patch. No DaemonSets and no GPUs.

                      Karpenter or Auto Mode

                      Automatic node provisioning sized to pending pods.

                        The control plane adds a flat hourly fee per cluster (about 10 cents an hour). ECS has none.

                        The fee is on top of the compute you use. It is one reason small teams should not reach for EKS by default.
                        HACKTHESOCLesson 111Serverless and containers27 / 47

                        ECS versus EKS

                        AspectECSEKS
                        TechnologyAWS-proprietary, simpleOpen-source Kubernetes
                        Learning curveGentle: tasks, servicesSteep: pods, controllers, networking, RBAC
                        PortabilityAWS onlySame manifests run on other clouds and on-premises
                        EcosystemAWS-integratedHuge: Helm, operators, service meshes, CNCF tools
                        Control plane costNonePer-cluster hourly fee
                        Ops overheadLowHigher: version upgrades, add-ons, cluster security
                        Typical fitTeams that want containers running quicklyOrganizations standardized on Kubernetes
                        Kubernetes releases a minor version every few months and old versions go out of support. Someone has to own those upgrades.
                        HACKTHESOCLesson 111Serverless and containers28 / 47

                        Choose EKS for a reason, not for fashion

                        EKS fits when

                        You need what only Kubernetes brings.

                        • The organization already has Kubernetes skills
                        • You need multi-cloud or hybrid portability
                        • You depend on operators, Helm or a service mesh
                        • A large platform serves many teams

                        ECS is better when

                        A small team runs a handful of services, needs deep AWS integration and has no Kubernetes investment. ECS on Fargate is the lowest-effort first path.

                          If you cannot name a feature you need that ECS lacks, you probably do not need Kubernetes.

                          Kubernetes is a platform for building platforms. Ask: who will upgrade the cluster, and do we need to leave AWS for real or is portability just a comfort?

                          Orchestration and messaging

                          Put a buffer or a router between services so one slow service cannot break another.

                          HACKTHESOCLesson 111Serverless and containers30 / 47

                          SQS is a durable queue: four ideas to know

                          • BufferingA burst of 50,000 messages is absorbed while consumers work at a safe rate.
                          • Visibility timeoutA received message is hidden; if not deleted in time it reappears. For Lambda, at least six times the function timeout.
                          • Dead-letter queueAfter N failed receives a message moves to a DLQ, so one poison message cannot block everything.
                          • Standard vs FIFOStandard: at-least-once, best-effort order, near-unlimited throughput. FIFO: ordered per group, deduplicated, lower throughput.
                          Coupling is the enemy: if A calls B directly, B being slow or down breaks A. A queue in between is decoupling.
                          HACKTHESOCLesson 111Serverless and containers31 / 47

                          SQS, SNS or EventBridge: pick by message flow

                          Work queue with retries

                          SQS

                          Producers send, consumers poll and process. Choose it when you need a work queue with retries.

                            Publish and subscribe

                            SNS

                            One message to a topic, a copy to every subscriber: SQS, Lambda, HTTPS, email, SMS. Choose it for simple high-throughput fan-out.

                            • Fan-out: one SNS topic to several SQS queues

                            Rule-based routing

                            EventBridge

                            Events from AWS, your apps or SaaS partners arrive on a bus; JSON pattern rules route them to targets. Choose it when routing depends on content.

                            • Also schedules and a schema registry
                            EventBridge schedules replace a server running cron. Fan-out lets each consumer process the same event independently at its own pace.
                            HACKTHESOCLesson 111Serverless and containers32 / 47

                            Step Functions: Standard versus Express workflows

                            A state machine in Amazon States Language: sequencing, Choice, Parallel, Map, Wait, Retry and Catch.

                            AspectStandardExpress
                            Maximum durationUp to one yearUp to five minutes
                            Execution semanticsExactly-onceAt-least-once
                            PricingPer state transitionBy count and duration
                            StrengthFull execution historyVery high rate, high-volume event processing
                            Instead of one giant Lambda that calls others and tracks its own state, the workflow engine records every step.
                            HACKTHESOCLesson 111Serverless and containers33 / 47

                            Why orchestration matters: the refund step is explicit

                            • Retry with backoff and Catch are built in, not hand-coded
                            • The compensation step is visible, not hidden in nested try blocks
                            Pitfalls: assuming exactly-once delivery from SQS standard or SNS (write idempotent consumers), a visibility timeout shorter than processing time, and forgetting a DLQ so failures vanish silently.

                            Rules of thumb that hold up in practice

                            • Highest abstraction firstPrefer the highest abstraction that meets the requirement: Lambda, then Fargate, then EC2.
                            • Do the arithmetic100 million runs a month at 200 ms and 512 MB may cost more than a small always-on container. 20,000 a day costs pennies.
                            • Mixed is normalFargate core API, Lambda for resizing and cleanup, SQS between them, Step Functions for the ordering workflow.
                            • Avoid premature KubernetesAnd premature microservices: a modular single service on ECS beats twenty functions calling each other synchronously.
                            • Watch hidden constraintsLambda in a VPC needs the right subnets and NAT or endpoints; container tasks need image pull access to ECR.
                            Check the pricing calculator rather than guessing. The breakeven between Lambda and an always-on container depends on duration, memory and call rate.
                            HACKTHESOCLesson 111Serverless and containers37 / 47
                            Before deciding, ask how long one unit of work runs and what it costs at 10 times the load.

                            Also: what is the peak-to-average traffic ratio, what latency can users tolerate on the first request, and who operates this at 3 AM?

                            These five questions are the decision framework. Give students a workload and have them answer each before naming a service.

                            Worked example: a serverless image pipeline

                            Bursty uploads, an idle night: the textbook serverless shape.

                            HACKTHESOCLesson 111Serverless and containers39 / 47

                            The pipeline: S3, SQS, Lambda, three outputs

                            Users upload photos; the system makes a thumbnail, records metadata and notifies the owner.

                            • The queue absorbs a spike and keeps Lambda concurrency bounded
                            • Uploads use short-lived pre-signed URLs, never your servers
                            Every service in this diagram was taught in an earlier section. Ask students which section each box came from.
                            HACKTHESOCLesson 111Serverless and containers40 / 47

                            Six pieces, each with one job

                            1. 1S3 uploads bucketDurable source of events; uploads go via pre-signed URLs.
                            2. 2Event notification to SQSBuffering, retry control and a DLQ; protects DynamoDB.
                            3. 3Lambda function1,024 MB or more, timeout above worst case (60 s), visibility timeout 6x that.
                            4. 4Separate thumbnails bucketOutput to the trigger bucket means an infinite loop and a big bill.
                            5. 5DynamoDB metadata tableImage ID as partition key; fast lookups, nothing while idle.
                            6. 6SNS topic image-processedAdd analytics or moderation later without touching resize code.
                            The output-bucket loop is the most common mistake in this pattern. If you need one bucket, use a separate prefix with a filtered trigger.
                            HACKTHESOCLesson 111Serverless and containers41 / 47

                            The Lambda handler, trimmed to its core

                            Keys arrive URL-encoded, so decode them. Same-key DynamoDB writes are idempotent.

                            Imports and the s3, db and sns clients are created outside the handler so warm invocations reuse them. A duplicate delivery just overwrites the same item.
                            HACKTHESOCLesson 111Serverless and containers42 / 47

                            Failure, operations and cost shape

                            Failure handling

                            A corrupt image raises an exception, the message returns after the visibility timeout, and after a few attempts it lands in the DLQ. Nothing is lost.

                            • One bad file does not stop the line

                            Operations

                            Logs go to CloudWatch Logs. Alarm on errors, throttles, duration near the timeout and DLQ depth.

                            • Least privilege: only the actions and resources used

                            Cost shape

                            Zero when no one uploads, proportional to uploads otherwise. For huge steady load, swap in a Fargate worker reading the same queue.

                              The swap is possible only because the queue decoupled the stages.

                              Close the loop: decoupling pays off when requirements change. Nothing upstream needs to change when the processing step moves from Lambda to Fargate.

                              Key takeaways

                              1. 01Every compute choice asks how much of the stack you run yourself: EC2, then containers, then Lambda, each with less to manage.
                              2. 02Lambda scales per request and bills per millisecond, but caps at 15 minutes and serves one request per environment.
                              3. 03API Gateway times out near 29 to 30 seconds, so long work needs accept-then-process with a queue.
                              4. 04Start containers on ECS with Fargate; choose EKS only for Kubernetes skills, tooling or portability.
                              5. 05SQS buffers, SNS fans out, EventBridge routes by content, Step Functions orchestrates; consumers must be idempotent.
                              6. 06Prefer the highest abstraction that fits, and decouple stages with a queue so any step can be swapped later.
