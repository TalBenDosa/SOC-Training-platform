HACKTHESOCLesson 29Web application attacks4 / 59
A web application turns untrusted internet input into a database query, a page, or a file operation.

Every attack here exploits the gap between the input a developer expected and what it can be made to contain. Together they map to T1190, Exploit Public-Facing Application.

You cannot run a business without something listening on the internet, which is why this stays one of the most common initial-access vectors. In real investigations you often have only an access log, so the pattern of status codes and sizes is the evidence.

Where each attack fits, and reading the raw access log

Web server or proxy (often behind a WAF), then the app, then a query, file, page or outbound request.

HACKTHESOCLesson 29Web application attacks6 / 59

Each attack abuses one stage of the lifecycle

AttackStage it targets
SQL injectionWhen the application builds a database query from user input
Cross-site scripting (XSS)When the application renders user input back into an HTML page
Path traversal / LFIWhen the application uses user input to construct a filesystem path
SSRFWhen the application makes its own outbound request to a user-supplied destination
File uploadWhen the application accepts and stores a file, then later executes or serves it
Every attack targets one of these moments, and the moment decides which log holds the evidence. The web server or WAF access log is the source every one of them touches first.

Read the raw access line without a parser

FormatWhat the line holdsWatch for
Apache / Nginx combinedIP, identity, user, [timestamp], "METHOD /path?query PROTOCOL", status, bytes, Referer, UANo response time unless the admin added %D (Apache, µs) or $request_time (Nginx, s)

IIS time-taken being on by default matters for time-based SQL injection later. On Apache or Nginx, check whether timing was logged before you rely on it.

Decode before you judge

Payloads almost always arrive URL-encoded. Recognise the common ones on sight.

EncodedDecoded
%27 / %22' / "
%3C / %3E< / >
%20 or +A space
%2F / %2e%2e%2f/ / ../
%3B / %7C; / |
%252e%252e%252fDouble encoding (%25 is a literal %): decode again until the string stops changing

Use the tooling, not your head: urldecode() in Splunk, url_decode() in KQL, or CyberChef's URL Decode.

Double encoding exists specifically to slip past a filter that decodes once. An analyst who reads payloads encoded will miss half of them.
HACKTHESOCLesson 29Web application attacks9 / 59

Read the User-Agent column before the payload

  • Tools announce themselvesBy default: sqlmap/1.x, Nikto/2.x, gobuster/3.x, WPScan v3.x, Nmap Scripting Engine.
  • What a tool UA tells youThe traffic is automated, and which tool's payload style to expect.
  • Absence proves nothingsqlmap can randomise its agent, and serious attackers swap in a normal browser string.
  • Then read the shapeWithout the header, the tell is volume, timing and payload shape.
A clean browser User-Agent is not evidence of a human. Fall back to rate, regularity and what the requests contain.

Section 2 of 13

SQL injection: union, blind, and time-based

Input reaches a query without parameterisation and changes its structure. Each flavour gets its answer back differently.

HACKTHESOCLesson 29Web application attacks11 / 59

Three variants, three access-log footprints

VariantHow the answer comes backAccess-log footprint
Union-basedExtracted data embedded in the pageA burst of 500s while guessing the column count, ending in one 200 with a large body
Boolean blindOne bit at a time from true/false differencesHigh volume of near-identical GETs, all 200, differing only in small fragments
Time-based blindPurely from how long the response takesResponse times clustering around round numbers like 5, 10 or 15 seconds
A working boolean blind attack often produces no errors at all, so an analyst watching only for error codes will miss it. Hundreds or thousands of paired requests is the tell.
HACKTHESOCLesson 29Web application attacks12 / 59

Union-based: the 500 storm ends in one large 200

  • Same source IP, same endpoint, a SQL clause in each id value
  • Identical 500 612 responses: the column-count guesses failed
  • 200 9841: the body jumps in size, so the extraction worked
Response size is what separates success from failure here. The 500s are probing; the large 200 is data leaving. Treat that one request as the start of a confirmed incident.
HACKTHESOCLesson 29Web application attacks13 / 59

Time-based blind: response time is the attack

Normal traffic

Requests to the endpoint resolve in tens or hundreds of milliseconds.

Time-based SQLi

The attacker injects a conditional delay, a sleep or wait function, and reads the answer from the delay. Same source, same endpoint, times clustering near 5, 10 or 15 seconds.

Round-number response times that match common sleep payloads are close to a fingerprint.

This is the one case where the response-time field is not a performance metric. Have students sort an endpoint's requests by time taken and look for the cluster.

Section 3 of 13

Cross-site scripting: reflected, stored, and DOM-based

Unencoded input runs as script in another user's browser: it attacks the victim's session, not the database.

HACKTHESOCLesson 29Web application attacks15 / 59

Three variants, three different evidence trails

In the request

Reflected

The payload travels in a query parameter and is echoed straight back. An encoded script tag in url.query with a 200 is the textbook signature. Hunt for angle brackets, script tags and script URIs in parameters.

In the database

Stored

Planted once by a POST to a comment or profile field, then runs for every viewer. Often the only log evidence is that one POST; later victim GETs look normal.

In the browser

DOM-based

Runs entirely in page JavaScript, often from the URL fragment after #, which browsers never send to the server. Can leave no server trace at all.

Stored XSS is usually found from application-layer evidence: the database content or a WAF that inspects response bodies. DOM-based needs client-side telemetry such as EDR-observed browser behaviour or the victim's browser history and console.
HACKTHESOCLesson 29Web application attacks16 / 59
"The access log looks clean" does not mean XSS did not happen.

For DOM-based XSS the server only ever sees a normal request for the page. Investigate with client-side telemetry instead of server logs.

This is a common closing mistake. If a victim's session cookie was stolen while viewing a normal-looking page, a clean server log is consistent with DOM-based XSS.

Section 4 of 13

Path traversal, LFI, and SSRF

When user input controls a file path, or a request the server itself makes.

HACKTHESOCLesson 29Web application attacks18 / 59

Traversal reads files; LFI executes them

Path traversal

User input controls part of a file path and walks outside the intended directory. In the log: repeated directory-up sequences in the path or query, often URL-encoded to evade filters.

  • Targets: /etc/passwd, /etc/shadow
  • web.config, win.ini, connection-string files

Local File Inclusion

The traversed file is not just read but included and executed, common in PHP apps that include a page named by a parameter. A file-read flaw becomes remote code execution once attacker content reaches disk.

A classic LFI combination is log poisoning: the attacker puts code in their User-Agent so it is written into the web server log, then includes that log file. That is why an odd User-Agent followed by an include of a log path is worth correlating.
HACKTHESOCLesson 29Web application attacks19 / 59

Two 403s, then a 200: the filter bypass worked

  • Plain, then encoded, then obfuscated traversal, all aimed at /etc/passwd
  • 403 287 twice: the filter blocked the first two attempts
  • 200 1731: a different body size, so the file was most likely returned
Blocked attempts return the same small error body. The success is the request whose status and size change. Escalate the 200 and check what that file exposes.
HACKTHESOCLesson 29Web application attacks20 / 59

SSRF: the server makes the request for the attacker

  • What it isThe application fetches an attacker-supplied URL: link previews, webhook setup, PDF-from-URL features.
  • Why it matters in cloudThe instance metadata endpoint 169.254.169.254 can hand back temporary IAM credentials for the instance role.
  • ImpactA web bug becomes full cloud account compromise, with no database or filesystem access needed.
  • Where the evidence isThe app's own outbound / egress logs, not the public access log. Inbound-only investigations miss it.
The request that matters is the one the server makes, not the one that triggered it. Ask for egress logs or the application's record of fetched URLs.
HACKTHESOCLesson 29Web application attacks21 / 59

Attempt or compromise? Check IMDS and credential use

IMDSv2 needs a session token from a PUT first, which breaks GET-only blind SSRF.

  1. 1Do not relax on IMDSv2Many estates run both versions; older instances and images often still allow v1.
  2. 2Check the enforced versionWhich metadata version does this instance enforce? A permissive hop limit can expose v2 to containers.
  3. 3Check credential useWere the instance role's credentials used from an address that is not the instance?
  4. 4DecideCredential use from elsewhere is the evidence that turns an attempt into a compromise.
Treat IMDSv2 as a question to ask, not a reason to close the alert.

Section 5 of 13

Status codes as evidence, and upload to web shell

Read the sequence, not the single request. Then follow a file upload to command execution.

HACKTHESOCLesson 29Web application attacks23 / 59

The status code alone never proves what happened

A scanner or fuzzer makes a storm of 400s and 500s; the request to escalate is the single 200, or a 302 somewhere unexpected, from the same source to the same endpoint. Pair it with size, timing and follow-on activity.
HACKTHESOCLesson 29Web application attacks24 / 59

Upload, then commands sent to the uploaded file

  • A POST to the upload endpoint returns 200
  • Later, requests to the uploaded file itself, a script extension in an image folder
  • Odd query parameters an image never receives: they are the shell's commands
The gap can be seconds or days if the shell sits dormant. Web shell is T1505.003; the upload flaw itself is T1190. On the host, look for the web server process spawning a shell or system utilities.
HACKTHESOCLesson 29Web application attacks25 / 59

A web shell runs as the app-pool account, not SYSTEM

What the attacker has

Command execution (T1059) as the web worker identity: IIS APPPOOL\DefaultAppPool on IIS, www-data or similar on Linux. Deliberately low privilege.

What they still need

Privilege escalation, credential theft and lateral movement are separate phases. That window is where an early catch stops a full compromise.

Juniors often assume a dropped web shell means root or SYSTEM. Scope it correctly: contain the host, remove the shell, and hunt for the next phase rather than declaring domain compromise.
HACKTHESOCLesson 29Web application attacks26 / 59

Confirm the web shell on the host, not just in the log

Two host-side signals carry most of the weight: a web worker (w3wp.exe, php-fpm, httpd, java) spawning a shell or recon tool, and a new .aspx, .php or .jsp file in the web root created by that worker. When the file creation lines up with the upload POST, you have both ends of the chain.
HACKTHESOCLesson 29Web application attacks27 / 59

Before you call it a pentest, confirm it

Scans, pentests, bug bounty, your own tools and post-deploy crawlers all make the same errors-then-success shape.

  1. 1Match the sourceCompare against the tester's notified address range in writing, not from memory.
  2. 2Match the windowTraffic outside the authorised start and end time is not covered, whoever sent it.
  3. 3Check what succeededA test that found a working path found a real vulnerability. Hand it to the application owner.
"It is probably the pentest" is one of the most reliable ways for a real intrusion to be closed as noise, because attacker traffic looks identical and often arrives during the announced test week.

Reading WAF logs: rule IDs, actions, and limits

The access log says what the app returned; the WAF log says which rule matched and what the WAF did.

HACKTHESOCLesson 29Web application attacks29 / 59

In OWASP CRS, the rule ID names the attack class

First three digits = attack family (ModSecurity or Coraza running the Core Rule Set).

Rule IDAttack family
920xxxProtocol enforcement: malformed requests
913xxxScanner detection
930xxx / 931xxxLocal file inclusion and path traversal / remote file inclusion
932xxx / 933xxxRemote command execution / PHP injection
941xxx / 942xxxXSS / SQL injection
949110Inbound Anomaly Score Exceeded: the rule that actually blocks

Anomaly scoring: critical 5, error 4, warning 3, notice 2 points; blocked when the total reaches the threshold (5 by default).

So a blocked SQL injection usually shows one or more 942xxx matches followed by 949110. The 942xxx lines tell you what the payload was; 949110 tells you it was blocked.
HACKTHESOCLesson 29Web application attacks30 / 59

One blocked request: the 942 match, then the 949110 block

ModSecurity plus CRS error-log lines, trimmed. The 942100 line names the attack class; the 949110 line with a total score of 10 is the block decision for that one request.
HACKTHESOCLesson 29Web application attacks31 / 59

AWS WAF: the managed rule matched, and the request was allowed

Trimmed; the httpRequest.args field holding the query string is omitted here. Read action, terminatingRuleId and nonTerminatingMatchingRules first: the rule group runs in Count, so the WAF recognised SQL injection and let it through. Go to the access log for 203.0.113.55 on /product and check for a large 200.
HACKTHESOCLesson 29Web application attacks32 / 59

Three WAF pitfalls

Count is not protection

Count mode or detection-only CRS logs the match and lets the request through. 942xxx with COUNT or ALLOW means the attempts reached the app.

A block is one request

The next variation, another encoding or parameter, may not match. Pivot on source IP or token for the first unblocked request with a large 200.

A match is not a success

Rule IDs describe the payload, not the outcome. Status, size and timing, and host evidence such as web-shell signals, decide whether it worked.

The most common mistake is reading the WAF log as if it were the access log, or the reverse. Triage needs both.

Broken access control and IDOR: the number-one risk

No injection at all: the attacker asks for data that is not theirs, and the server hands it over.

HACKTHESOCLesson 29Web application attacks34 / 59

IDOR is a missing authorization check

Broken Access Control is ranked #1 in the OWASP Top 10; IDOR is its most common form.

Who are you?

Authentication

Your invoice loads at GET /api/invoice?id=1001. The session is valid, so this check passes.

Is this yours?

Authorization

Change it to id=1002 and someone else's invoice comes back. The app never asked whether 1002 belongs to you.

Hold this distinction firmly: a valid session proves identity, not permission for a specific record.
HACKTHESOCLesson 29Web application attacks35 / 59

One session walking sequential IDs is the tell

Walk the right-hand panel: one identity, many object IDs, all 200 OK. That is enumeration, not browsing.
HACKTHESOCLesson 29Web application attacks36 / 59

Why IDOR matters, and how to fix it

  • Trivial to exploitSequential or guessable IDs, a predictable UUID or an email in a URL invite simple incrementing.
  • Scales to a breachA script iterating id=1..100000 quietly downloads every user's records.
  • BOLA on APIsBroken Object Level Authorization, the top API risk, because APIs expose object references directly.
  • The fixServer-side ownership validation on every object access. Obscurity is not authorization.
APIs are often wrongly assumed to be internal. Recommend ownership checks to the application owner, not harder-to-guess IDs.

Worked example: an IDOR walkthrough

From a one-character edit to the access-log pattern that gives it away.

HACKTHESOCLesson 29Web application attacks38 / 59

Same session, sequential IDs, no errors anywhere

Each request carried the same session cookie. The first line is the user's own invoice; the next two are someone else's. A human does not request three IDs in three seconds; a script does. Unlike SQLi's error storm, IDOR is a well-formed request answered 200 every time: one identity, many object IDs, consistent success.

Authentication and session attacks

The session token is your identity for its lifetime, so attackers steal or forge it instead of the password.

HACKTHESOCLesson 29Web application attacks40 / 59

Three ways to take over a logged-in state

AttackHow it worksDefence
Session hijackingSteal the cookie or token and replay it: via XSS, sniffing unencrypted traffic, or malwareHttpOnly and Secure cookie flags, HTTPS
Session fixationAttacker sets a known session ID before login; the app keeps it after loginRotate the session ID on every privilege change, especially login
JWT weaknessesAccepting the unsigned alg: none option, crackable secrets, trusting unverified claimsVerify the signature server-side; a JWT is readable, not encrypted
Tie hijacking back to XSS: a stolen session cookie is often the goal of the XSS covered earlier. The token deserves the same care as the password it replaced.
HACKTHESOCLesson 29Web application attacks41 / 59

Signals of impossible or inconsistent session use

  • The same session token from two very different IPs or geographies at once: a hijacked session used in parallel
  • A session that suddenly switches user-agent or device mid-life
  • Authentication succeeding with no preceding login event
Response: invalidate the session, force re-authentication, and look for how the token was taken, such as XSS or malware on the user's device.

Section 10 of 13

Command injection: web input to an OS shell

Like SQL injection, but it tricks the operating system, often a straight path to RCE.

HACKTHESOCLesson 29Web application attacks43 / 59

Why command injection sits at the severe end

Unsanitised input passed into a system shell command lets the attacker chain their own commands.

Immediate RCE

Injected commands run on the host: the foothold every later stage builds on.

Runs as the web user

Executes as www-data, apache or nginx: the service account spawning a shell signature.

Output comes back

Results often return in the HTTP response, so exploitation is fast and interactive.

The classic setup is a 'ping this host' feature that shells out to an OS tool. From there attackers read files, add users, or launch a reverse shell.
HACKTHESOCLesson 29Web application attacks44 / 59

Detect it on two layers

Web tier

Shell metacharacters such as command separators, pipes and command substitution in parameters, and requests to features that invoke system utilities.

The confirming signal

Host (EDR)

The web server process spawning sh, bash, whoami or curl. That child process confirms execution, not just an attempt.

Defence: never pass user input into a shell. Use parameterised APIs and a strict allowlist.

A metacharacter in a request is an attempt. A web server parent with a shell child is a success: isolate the host and treat it as an intrusion.

Section 11 of 13

CSRF and clickjacking: abusing browser trust

Nothing injected, nothing read: the victim's own authenticated browser performs the action.

HACKTHESOCLesson 29Web application attacks46 / 59

CSRF and XSS work in almost opposite directions

XSS

Attacker script runs inside the victim's page on the target site to read data out.

CSRF

No script on the target site. The victim's browser visits an attacker page that submits a request; the browser attaches the session cookie automatically (ambient authority).

A CSRF against a bank's /transfer endpoint never needs to see the response. The transfer either happens or it does not.
HACKTHESOCLesson 29Web application attacks47 / 59

Valid session, wrong origin

  • A state-changing POST with a valid session cookie
  • Origin and Referer point at an unrelated domain: hunt for this
  • A missing Origin / Referer on such a POST is also worth a look
Most access-log pipelines already capture these headers but rarely alert on them. The access log line here showed 200 44, so the server processed the transfer.
HACKTHESOCLesson 29Web application attacks48 / 59

The defences are configuration you can check

SameSite cookies

Lax (increasingly default) or Strict stops the browser attaching cookies to cross-site requests. Defence in depth only.

CSRF token

A random value in every form validated server-side (synchronizer token), or a double-submit cookie or custom header for APIs.

Clickjacking defence

The real site is framed invisibly to steal a click. Send CSP frame-ancestors; X-Frame-Options is the legacy fallback.

A site sending neither framing header can be framed by anyone. That is the one configuration check to run before assuming clickjacking is not a risk.

XXE, SSTI, and insecure deserialization

Input that reaches a parser or interpreter the application trusts.

HACKTHESOCLesson 29Web application attacks50 / 59

Three parser attacks and what each can lead to

AttackWhere the input landsWhat it can lead to
XXEAn XML parser resolving external entities in a DOCTYPE declarationLocal file read, or SSRF to an internal URL
SSTIA template engine (Jinja2, Twig, FreeMarker, Velocity) evaluating input as template sourceExpression evaluation, escalating to file reads or a shell: effectively RCE
Insecure deserializationJava, PHP or Python reconstructing an object from an untrusted byte streamRCE via a gadget chain on load (OWASP A08:2021)
Many Java XML parsers ship with external entity resolution enabled by default. OWASP's only fully reliable XXE fix is disabling DTD processing entirely.
HACKTHESOCLesson 29Web application attacks51 / 59

Hunt for input that does not belong in the field

Worth escalating from a WAF or application log even before you confirm success.

  • XXEAn XML body with a DOCTYPE declaration using the SYSTEM keyword to point at a file or internal URL.
  • SSTITemplate syntax in a form field, and a page that shows an evaluated result instead of the literal text.
  • Java deserializationMagic bytes AC ED 00 05 in hex, rO0AB in base64, in a field that should not carry binary data.
  • PHP deserializationA PHP serialized-object prefix starting O: in a request parameter.
The success test for SSTI is in the response: literal text back means the input was treated as data, an evaluated result means it ran as code.

API attacks: the OWASP API Top 10 in the logs

Machine-to-machine traffic, usually JSON over HTTP with no HTML, has its own risk ranking.

HACKTHESOCLesson 29Web application attacks53 / 59

OWASP API Security Top 10: the risks to know

RiskWhat it means
API1:2023 BOLAThe IDOR pattern on APIs; behind roughly 40% of real-world API attacks
API2:2023 Broken AuthenticationStolen tokens, no rate limit on login (credential stuffing), unverified JWTs

HACKTHESOCLesson 29Web application attacks54 / 59

API abuse is the browser attacks with the HTML stripped away

Nginx access log with $request_time appended, one line per record (wrapped to fit). Aggregate on the token or API key, not the source IP: mobile clients and partners share NAT addresses and cloud egress ranges. API6 shows as the same purchase call repeated faster than a person could click.

Key takeaways

  1. 01Decode payloads until they stop changing; a tool User-Agent confirms automation, its absence proves nothing.
  2. 02Read sequences: a 500 storm ending in a large 200, near-identical 200s, or round-number response times.
  3. 03DOM-based XSS and SSRF can leave the public access log clean; check client telemetry and egress logs.
  4. 04A WAF rule ID names the attack class, but Count matches reached the app and no match proves success.
  5. 05A web shell runs as the low-privilege app-pool account; confirm it by the web worker spawning a shell.
  6. 06IDOR is one session enumerating IDs with 200 OKs; in APIs, aggregate on the token, not the source IP.
HACKTHESOCLesson 29Web application attacks56 / 59

Check your understanding, question 1 of 3

Twelve requests to /product?id= from one IP in a minute, each with a slightly different payload appended to the id. The first eleven return 500; the twelfth returns 200 with a body about 15 times larger than normal. What is this?

The 500s are failed guesses at the column count and the oversized 200 is extracted data coming back in the page. Boolean blind is quiet with steady 200s, time-based shows in response time, and traversal would not need a column count.

Choose an answer, or press R to reveal it.

HACKTHESOCLesson 29Web application attacks57 / 59

Check your understanding, question 2 of 3

On a cloud VM, confirm whether the app server itself sent a request to the instance metadata service after receiving an attacker-supplied URL. Whether the credentials were misused comes next. Which evidence answers this?

In SSRF the server makes the request, so proof it reached the metadata service is in its own egress or fetch log. The inbound log shows only the trigger, 169.254.169.254 is an IP with no lookup, and audit logs answer the next question.

Choose an answer, or press R to reveal it.

Check your understanding, question 3 of 3

A web shell is confirmed on a public-facing IIS server: GET /uploads/img_48213.aspx with a command parameter returned 200, and the response body reads iis apppool\defaultapppool. What is the attacker's current level of access?

A web shell runs with the privilege of its host process, here the low-privilege IIS APPPOOL\DefaultAppPool identity. Execution is real (T1059), but anything more needs a separate escalation or credential-theft step: the window to stop it.
