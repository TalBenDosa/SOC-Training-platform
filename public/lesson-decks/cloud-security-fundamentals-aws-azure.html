Section 1 of 11

What the cloud really means

Someone else's computers, rented over the internet and configured entirely through software.

HACKTHESOCLesson 60Cloud security fundamentals6 / 71

The cloud: someone else's computers, rented by the minute

  • Who builds itCompanies like Amazon and Microsoft run enormous data centres of servers, storage and networking.
  • What you getSlices of that capacity on demand, paying only for what you use.
  • How fastA server in seconds with a few clicks or a command, instead of weeks to buy and install hardware.
That speed is the first thing that changes for a defender: resources, and mistakes, appear just as fast.
HACKTHESOCLesson 60Cloud security fundamentals7 / 71

Three properties that matter to a defender

On-demand and elastic

Resources appear and disappear in seconds. One mistaken command can create, or delete, a hundred servers. Speed cuts both ways.

Software-defined

No cables. Networks, firewalls, disks and permissions are configuration, so a misconfiguration is the typical cause of a cloud breach.

Reachable over the internet

Control interfaces face the internet, so identity and access become the real perimeter. Steal the right credential and you just log in.

Ask: if there is no wire to cut, what breaks? Answer: settings and credentials.
HACKTHESOCLesson 60Cloud security fundamentals8 / 71

Service models: who controls what

ModelWhat you rentSOC relevance
IaaSRaw building blocks: virtual machines and disksCustomer controls configuration, owns much of the security
PaaSA ready-made platform to run applications, no server managementCustomer still controls configuration
SaaSA finished application you just use (web email, CRM)Less of what you investigate in AWS and Azure
Most of what a SOC analyst investigates in AWS and Azure sits in the IaaS and PaaS layers.

AWS and Azure: a vocabulary map

Same jobs, different names. An alert will speak one dialect or the other.

HACKTHESOCLesson 60Cloud security fundamentals10 / 71

The container that holds everything

AWS

The top-level container is an account. Large organisations group many accounts under AWS Organizations.

Azure

Resources live in a subscription, under management groups. Identity is Microsoft Entra ID, formerly Azure Active Directory.

Regions such as us-east-1 or West Europe matter: activity in a region your company never uses is itself suspicious.

Attackers sometimes create resources in unused regions precisely to avoid notice. Each region is divided into isolated availability zones.

Three ways people touch the cloud

Console, CLI and API all funnel down to the same underlying API calls.

HACKTHESOCLesson 60Cloud security fundamentals16 / 71

Three interfaces, one log

InterfaceWho uses itWhy the SOC cares
Web consoleHumans pointing and clickingConsole logins, especially root or Global Administrator, are prime events
CLI and SDKsEngineers, scripts, automationMany attacker tools live here: scripting is faster than clicking
The API directlyEverything, underneath the other twoEach call is what the provider actually logs
The console and CLI are friendlier wrappers around the API, which is why one activity log can see all three.
HACKTHESOCLesson 60Cloud security fundamentals17 / 71

Every interface collapses into an API call

  1. 1Web consolePoint and click. Console logins are a prime event, especially root or Global Administrator.
  2. 2CLI and SDKsaws and az commands. Automation lives here, and so do many attacker tools.
  3. 3The API directlyUnderneath it all, a defined request: create this VM, read this object.
  4. 4Logged as one entryWho, which action, on what resource, from which IP, and whether it succeeded.
Whether an attacker clicked or scripted, CloudTrail or the Azure Activity Log captures the API call underneath. That is the single most important fact about cloud monitoring.
HACKTHESOCLesson 60Cloud security fundamentals18 / 71
Identity is the new perimeter.

An engineer in a coffee shop and an attacker on another continent hit the same API endpoint. What separates them is a valid credential and its permissions.

Traditionally, reaching a server meant being on the network. In the cloud, the credential gates access, not network location.

Section 4 of 11

Who secures what, and where the SOC looks

The shared responsibility model, and the data sources that carry the signal.

HACKTHESOCLesson 60Cloud security fundamentals20 / 71

Security of the cloud vs security in the cloud

Security of the cloud

Provider

Physical data centres, hardware, the hypervisor, and managed services' underlying infrastructure.

Security in the cloud

Customer

Data, configurations, identities and permissions, network rules, application code.

A public bucket, a leaked key, a firewall rule open to the internet: the provider will not stop it and did nothing wrong.

No provider control will alert you that your own team misconfigured your own resource. That detection is yours to build.
HACKTHESOCLesson 60Cloud security fundamentals21 / 71

Whose job was it? Test the line on real cases

What happenedWhose sideWhy
An S3 bucket left publicCustomerConfiguration of your own resource
An access key leaked in codeCustomerYour identity and credential management
A firewall rule open to the internetCustomerYour network rules
Data-centre physical securityProviderSecurity of the cloud itself
The hypervisor running virtual machinesProviderUnderlying infrastructure
The first three are the classic cloud breaches, and all sit on the customer side. Nobody else will alert you to them.
HACKTHESOCLesson 60Cloud security fundamentals22 / 71

Where a cloud SOC actually looks

  • Management/activity logsCloudTrail and the Azure Activity Log: API calls that create, change and delete resources. The backbone.
  • Identity logsEntra sign-in and audit logs, AWS IAM/console sign-in: who authenticated, from where, with what risk.
  • Network and flow logsVPC flow logs and NSG flow logs show connections in and out.
  • Storage and data-access logsWho read or wrote to buckets and blobs.
  • Managed detectionGuardDuty and Defender for Cloud raise findings you confirm in the raw logs.
The mindset shift: from which packet crossed the wire to which identity made which API call, from where, and should they have.
HACKTHESOCLesson 60Cloud security fundamentals23 / 71

Which log answers which question

QuestionWhere to look
Who created, changed or deleted this resource?CloudTrail / Azure Activity Log
Who signed in, from where, with what risk?Entra sign-in and audit logs; AWS console sign-in events
Did this machine talk to that IP?VPC flow logs / NSG flow logs
Who read or wrote this bucket or blob?Storage and data-access logs
Is there a ready-made finding?GuardDuty / Defender for Cloud, then confirm in raw logs
Start from the question, not the tool. That habit carries across every cloud.

Section 5 of 11

IAM basics: principals, policies and roles

Before the provider does anything, it asks: is this principal allowed to do this?

HACKTHESOCLesson 60Cloud security fundamentals25 / 71

Every request passes one gate first

  1. 1A principal makes a callA console click, a CLI command or an API request.
  2. 2The provider checks policiesIAM: is this principal allowed to do this action on this resource?
  3. 3Default denyNothing is allowed unless a policy explicitly allows it.
  4. 4Allowed, run, loggedThe action happens and the call is recorded.
IAM is Identity and Access Management. Its three building blocks, principal, policy and role, come next.
HACKTHESOCLesson 60Cloud security fundamentals26 / 71

Principal: whoever or whatever is asking

AWS

Users and roles are the principals you will see in CloudTrail.

  • IAM user: a named, usually long-lived identity
  • Role: assumed temporarily, owned by no one

Azure

Principals are granted roles at a scope.

  • User or group
  • Service principal: an application's identity
  • Managed identity: Azure-managed, no secret to leak
Managed identities are worth highlighting: no secret exists, so none can be leaked.
HACKTHESOCLesson 60Cloud security fundamentals27 / 71

A policy: default deny, allow only what is written

  • Read it as a sentence: read and list the finance-reports bucket, nothing else
  • The opposite of a sprawling allow-everything-on-everything policy
Nothing is allowed unless a policy explicitly allows it. In Azure, the same idea is expressed through role definitions.
HACKTHESOCLesson 60Cloud security fundamentals28 / 71

Reading the policy line by line

LineWhat it says
"Effect": "Allow"This statement grants, rather than denies
s3:ListBucketList what is in the bucket: applies to the bucket ARN
s3:GetObjectRead objects: applies to finance-reports/*, the objects inside
ResourceOnly the finance-reports bucket and its objects
What is missingNo write, no delete, no other bucket: all denied by default
The last row is the lesson: everything not written is denied. Read a policy for what it leaves out as much as for what it grants.
HACKTHESOCLesson 60Cloud security fundamentals29 / 71

Roles are permissions you borrow, not own

  • AWS roleA policy with no permanent key; a trusted principal assumes it and gets short-lived credentials that expire on their own.
  • Azure RBACRole definitions (Owner, Contributor, Reader, many more) assigned to a principal at a scope.
  • ScopesManagement group, subscription, resource group, or a single resource.
  • Least privilegeStolen credentials inherit exactly the policy's permissions. "Action": "" on "Resource": "" means full takeover.

One of your first moves in a cloud incident: read the compromised principal's policy. It bounds the damage.

Roles let an EC2 instance, an Azure VM, or a person crossing accounts get exactly the access needed, for exactly as long as needed, without a static secret.
HACKTHESOCLesson 60Cloud security fundamentals30 / 71

Same stolen credential, two very different incidents

Tightly scoped policy

Read and list one bucket. The attacker gets those reports and nothing else: a contained, minor incident.

Action: on Resource:

Every action on every resource. The same theft becomes a full account takeover.

Least privilege: grant only the specific actions on the specific resources a principal needs.

The policy, not the attacker's intent, bounds the damage. That is why you read it first.

FieldQuestionValue here
eventTimeWhen?09:14:02 UTC, 16 August 2026

Every cloud event, from any vendor, answers the same questions. Assemble them into one plain sentence.
HACKTHESOCLesson 60Cloud security fundamentals34 / 71
At 09:14 UTC, d.rosen successfully logged into the AWS console from 203.0.113.77.

Then ask: is that IP normal for this user? Is 09:14 within their hours? Does d.rosen normally use the console at all?

Every cloud event answers the same five questions. A single event rarely proves an incident, but a fluently read event lets you notice the one that does not fit.
HACKTHESOCLesson 60Cloud security fundamentals35 / 71

Does it make sense? Three checks on the sentence

Fits the pattern

Routine: note it and move on.

  • An IP this user normally uses
  • Inside their working hours
  • d.rosen uses the console regularly

Does not fit

Same event, now worth a closer look.

  • An IP never seen for this user
  • Middle of their night
  • d.rosen only ever uses automation
A single event rarely proves an incident. Fluent reading is what lets you notice the one that does not fit.

What attackers actually target in the cloud

Repeatable patterns catalogued in the MITRE ATT&CK Cloud Matrix.

HACKTHESOCLesson 60Cloud security fundamentals37 / 71

MITRE ATT&CK: a shared map of attacker behaviour

  • What it isA public knowledge base that names and numbers real-world attacker behaviour.
  • TacticThe attacker's goal at a stage, such as Initial Access or Persistence.
  • TechniqueHow they reach it, with an ID such as T1078 for Valid Accounts.
  • Cloud MatrixThe subset of techniques that apply to cloud environments.
You do not need the whole matrix. Recognising its shape tells you what to hunt for next.
HACKTHESOCLesson 60Cloud security fundamentals38 / 71

The typical cloud attack arc (part 1)

TacticExample techniqueWhat it looks like
Initial AccessValid Accounts (T1078.004)Sign-in or API call with a stolen password or leaked key, no exploit needed
DiscoveryCloud Infrastructure Discovery (T1580)A burst of List/Describe/Get* calls mapping users, buckets, roles
PersistenceCreate Account (T1136.003)A new IAM user, access key or role to get back in after revocation
Privilege EscalationAbuse Elevation Control MechanismAttaching an admin policy to a low-privilege identity
Discovery is often followed by escalation within minutes.
HACKTHESOCLesson 60Cloud security fundamentals39 / 71

Illustration: discovery, then escalation, in CloudTrail

  • A burst of List / Describe / Get* calls maps the account: T1580
  • Minutes later, a policy is attached: privilege escalation
Illustrative sequence. Each call is permitted and ordinary alone; the burst from one identity, then a policy change, is the arc in motion.
HACKTHESOCLesson 60Cloud security fundamentals40 / 71

The typical cloud attack arc (part 2)

TacticExample techniqueWhat it looks like
Defense ImpairmentDisable or Modify Cloud Log (T1685.002)Turning off CloudTrail or Azure diagnostic logging
ExfiltrationTransfer Data to Cloud Account (T1537)Copying data, snapshots or backups to attacker-controlled storage
ImpactResource Hijacking (T1496)Launching many compute instances, usually for cryptocurrency mining
Use the arc as a mental checklist: which stage does this alert represent? T1685.002 was formerly T1562.008. Initial access and persistence deserve the fastest response.
HACKTHESOCLesson 60Cloud security fundamentals41 / 71
Every stage of the arc happens on the customer side of shared responsibility.

No provider vulnerability needed: a stolen credential, ordinary permitted API calls, and whatever the credential happens to allow.

Every stage is smaller, slower and easier to catch against tightly scoped policies and well-monitored logs.
HACKTHESOCLesson 60Cloud security fundamentals42 / 71

Use the arc to triage any cloud alert

  1. 1Name the stageWhich row of the arc does this alert represent?
  2. 2Set urgencyInitial access and persistence deserve the fastest response.
  3. 3Look aheadDiscovery is often followed by escalation within minutes.
  4. 4Bound the damageRead the principal's policy: what could it do next?
The arc is a checklist, not a script: real intrusions skip and repeat stages.

Section 8 of 11

Control plane vs data plane

Management actions vs usage. Mixing them up is a common blind spot.

HACKTHESOCLesson 60Cloud security fundamentals44 / 71

Two layers of activity on every resource

Management

Control plane

Calls that create, configure or delete: CreateBucket, PutBucketPolicy, RunInstances, DeleteUser. AWS management events; Azure Resource Manager (ARM).

Usage

Data plane

What flows through a resource once it exists: reading or writing an object, a packet on a network, a request to a running app.

Control-plane calls change the shape of the environment. Data-plane activity changes nothing about configuration, only the data moving through it.
HACKTHESOCLesson 60Cloud security fundamentals45 / 71

The door was opened vs did anyone walk through

Control planeData plane
Example actionPutBucketPolicy (make a bucket public)GetObject (download a file from it)
Logged by default in AWS?Yes: CloudTrail management eventsNo: requires enabling CloudTrail data events
What it revealsThat a bucket was made publicWhether anyone downloaded from it
Azure equivalent logAzure Activity Log (ARM operations)Storage Analytics / diagnostic logs on the resource
Data events are a separate, separately billed setting because the volume is far higher than management activity.
HACKTHESOCLesson 60Cloud security fundamentals46 / 71

The same bucket, two planes

'The bucket was misconfigured' is incomplete. 'These objects were downloaded by this external IP' is the answer, and only data-plane logging gives it.
HACKTHESOCLesson 60Cloud security fundamentals47 / 71

Answering 'was anything actually taken?'

  1. 1Find the door openingThe PutBucketPolicy time, from management events.
  2. 2Check data eventsWere CloudTrail data events enabled for this bucket?
  3. 3If yes, list the readsGetObject calls during the public window, by which external IPs, for which keys.
  4. 4If no, say soRecord that downloads can be neither proven nor ruled out.
'The bucket was misconfigured' is incomplete. The real answer names the objects and the IPs, and only data-plane logs give it.

CSPM, CWPP and CNAPP: the tooling map

The acronyms map onto control plane, data plane and the workload itself.

HACKTHESOCLesson 60Cloud security fundamentals49 / 71

Which layer is the tool watching?

Posture: the control plane

CSPM

Scans configuration via read-only Describe/List/Get* calls: public buckets, 0.0.0.0/0 groups, broad policies, missing MFA. AWS Security Hub, Defender for Cloud posture.

Inside the workload

CWPP

VMs, containers, serverless: vulnerabilities, malware, risky processes, unpatched software. Defender for Cloud server/container plans.

The consolidation

CNAPP

CSPM + CWPP + CIEM (excess or unused permissions) + IaC (infrastructure-as-code) scanning in one view.

Gartner tracks consolidation toward CNAPP because a public bucket, an over-privileged role and a vulnerable internet-facing VM are one attack path, not three alerts. Dedicated CSPM vendors include Wiz, Orca and Prisma Cloud.
HACKTHESOCLesson 60Cloud security fundamentals50 / 71

Read a finding's layer to know the fix

FindingCategoryRemediation
Bucket publicly readableCSPM: a settingFix the policy
Vulnerable package on an internet-facing VMCWPP: a running workloadPatch the workload
Role holds admin permissions it never usesCIEM: who could reach whatTighten the permission
CIEM is Cloud Infrastructure Entitlement Management: it analyses IAM policies for excess or unused permissions.
HACKTHESOCLesson 60Cloud security fundamentals51 / 71
A public bucket, an over-privileged role and a vulnerable VM are one attack path, not three alerts.

That connection is why the market is consolidating into CNAPP: one view across posture, workload and identity.

Ask students to draw the path: VM compromised, role used, bucket read.
HACKTHESOCLesson 60Cloud security fundamentals52 / 71

The baselines these tools check against

Security pillar

AWS Well-Architected

Design principles such as 'implement a strong identity foundation' and 'enable traceability'. Azure and GCP publish equivalents.

Numbered checklist

CIS Benchmarks

A common language between a SOC and an auditor.

  • MFA on root / Global Administrator
  • No 0.0.0.0/0 inbound to SSH 22 or RDP 3389
  • Buckets not publicly readable

A setting = CSPM. A running process or vulnerable package = CWPP. Who could reach what = CIEM.

The category tells you the remediation: fix a policy, patch a workload, or tighten a permission.

Cloud vs on-premises: what actually changes

Several on-prem instincts stop applying, or apply differently.

HACKTHESOCLesson 60Cloud security fundamentals54 / 71

On-premises vs cloud (part 1)

DimensionOn-premisesCloud
PerimeterPhysical building + edge firewallIdentity and API permissions, reachable from anywhere
Physical securityYour team (badges, cameras, locked racks)Entirely the provider's
Provisioning speedDays to weeksSeconds to minutes via API, for defenders and attackers
Typical breach causeExploited vulnerability, phishing, physical intrusionMisconfiguration: the single most common root cause
Rapid provisioning enables both legitimate agility and attacker resource abuse such as mass crypto-mining launches.
HACKTHESOCLesson 60Cloud security fundamentals55 / 71

How one infrastructure-as-code mistake spreads

  1. 1A template is writtenSay, a firewall rule allowing 0.0.0.0/0 inbound.
  2. 2The pipeline deploys itAutomatically, with no manual ticket in between.
  3. 3Hundreds of resourcesEvery resource built from the template carries the same hole.
  4. 4Fix the sourceCorrect the template, not each resource one by one.
On-prem, a misconfigured server is one server. In the cloud, change control is often code, so mistakes multiply instantly.
HACKTHESOCLesson 60Cloud security fundamentals56 / 71

On-premises vs cloud (part 2)

DimensionOn-premisesCloud
Primary evidencePacket captures, host endpoint logsIdentity and API logs (CloudTrail, Activity Log, sign-ins)
Change controlOften manual, ticketed, slowerOften automated infrastructure-as-code, deployed instantly
Scaling as riskA misconfigured server is one serverOne bad IaC template misconfigures hundreds of resources
Cost as attacker incentiveRarely a direct goalResource hijacking runs up the victim's bill

On-prem defends a place. Cloud defends permissions and configurations anyone can reach with the right credential.

This lets an experienced on-prem analyst translate their instincts, instead of looking for a broken lock on a door that was never there.

Key takeaways

  1. 01The cloud is rented, software-defined, internet-reachable computing; misconfiguration, not broken hardware, causes most breaches.
  2. 02AWS and Azure name the same categories differently; place an alert by category first, then look up the product.
  3. 03Console, CLI and API all collapse into logged API calls: who, what, where, success or failure.
  4. 04The provider secures the cloud; the customer secures data, config, identities and network rules, and the SOC watches them.
  5. 05Policies grant actions on resources, roles lend temporary permissions, and least privilege bounds a stolen credential.
  6. 06The cloud attack arc rides stolen credentials and permitted API calls; StopLogging and CreateAccessKey are top signals.

A new analyst assumes Amazon is responsible for making sure none of the company's storage buckets are accidentally left public. Why is this wrong?

Under shared responsibility the customer secures data, configuration, identities and access rules. Even on a managed service the customer sets who may access its data, and bucket access is set by bucket and IAM policies, not security groups.

A bucket policy was changed to allow public read, and the default trail recorded PutBucketPolicy. What must be true to learn whether anyone downloaded files while it was public?

PutBucketPolicy is a control-plane event logged by default; GetObject is data-plane and needs data events enabled. Flow logs show IPs and ports, not objects, and a policy says what is allowed, not what happened.
