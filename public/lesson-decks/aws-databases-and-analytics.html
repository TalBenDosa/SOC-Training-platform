Three ways to store data

Tables and SQL

Relational

Fixed schema, tables linked by keys, answers in SQL. ACID transactions: the whole order is saved or none of it. Think of an accountant's ledger.

    Scale and flexibility

    Non-relational (NoSQL)

    Drops some rules for scale. Items can differ and access is by key. Think of a hotel key-card system: one room number, one instant answer.

      Engine matches the pattern

      Purpose-built

      Graph for relationships, time-series for timestamped measurements, in-memory for microsecond answers. Do not force one engine to do everything.

        ACID = Atomicity, Consistency, Isolation, Durability.

        Use the two analogies: the ledger must balance, the key-card system answers one question fast at any volume but never builds a report across all rooms.

        A managed service takes the heavy lifting, not the design

        Self-managed on EC2 means you install, patch, back up, script failover and size the disks yourself.

        • PatchingOperating system and database engine patching is done for you.
        • BackupsAutomated backups and point-in-time recovery.
        • High availabilityReplication and automatic failover.
        • Hardware and storageHardware provisioning and storage scaling.
        • MonitoringIntegration with CloudWatch.

        You still own the schema, queries, indexes, access design and cost: the shared responsibility model applied to data.

        AWS runs the platform, you design how data is used. Students often assume managed means no design work left.
        HACKTHESOCLesson 110AWS databases and analytics8 / 49

        Four questions before you name any service

        1. 1What is the access pattern?Lookups by key, complex joins, scans over billions of rows, or graph traversals?
        2. 2How big and how fast?Gigabytes at moderate traffic, or terabytes at millions of requests per second?
        3. 3How strict is consistency?Money transfers need ACID; a leaderboard can tolerate slightly stale reads.
        4. 4Who runs the queries?An application doing thousands of tiny reads, or analysts running a few heavy reports?
        This is the framework analysts reuse for every scenario in the lesson. Ask all four before saying a service name.

        Amazon RDS: managed relational databases

        Multi-AZ and read replicas are the most commonly confused pair in the database domain.

        HACKTHESOCLesson 110AWS databases and analytics11 / 49

        RDS runs the engine; you choose the sizing

        • EnginesAurora, MySQL, PostgreSQL, MariaDB, Oracle Database, Microsoft SQL Server and Db2.
        • What you chooseInstance class (CPU and memory), storage type and storage size.
        • What AWS handlesPatching windows, backups and failover.
        • The price of managedNo operating system access to the host.
        No OS access is the trade for being managed. It is why parameter groups exist, covered later in this section.
        HACKTHESOCLesson 110AWS databases and analytics12 / 49

        Multi-AZ and read replicas solve different problems

        AspectMulti-AZ deploymentRead replica
        PurposeHigh availability and durabilityScale read traffic
        ReplicationSynchronous to a standbyAsynchronous to a replica
        FailoverAutomatic, same endpoint nameNot automatic; you promote manually
        Serves reads?Standby does not (instance deployment)Yes, has its own endpoint
        LocationDifferent Availability Zone, same RegionSame AZ, other AZ or other Region
        Data lagNone, writes are committed in bothPossible replica lag

        A newer Multi-AZ DB cluster uses two readable standbys across three zones, but the idea is the same: surviving failure.

        Walk the table row by row and ask students to say which column answers an outage and which answers slow reads.
        HACKTHESOCLesson 110AWS databases and analytics13 / 49

        Pick by symptom: outage tolerance or slow reads

        Survive failure

        Multi-AZ

        Every write is committed to both copies before it is acknowledged. If the primary fails, RDS flips the DNS name to the standby, usually in one to two minutes.

          Scale reads

          Read replica

          A separate instance fed asynchronously. Your app must send reads to the replica endpoint, and a just-saved row may not be visible there yet.

            Do not swap them

            The pitfall

            A read replica is not high availability: nothing fails over automatically. Multi-AZ will not make a slow reporting query faster.

              Many exam questions describe only a symptom. Outage tolerance means Multi-AZ, slow reads means a read replica. Replicas in another Region also help distant users and disaster recovery planning.
              HACKTHESOCLesson 110AWS databases and analytics14 / 49

              Backups restore into a new instance

              • Automated backupsDaily snapshots plus transaction logs: point-in-time recovery, retention 1 to 35 days. Deleted with the instance unless kept.
              • Manual snapshotsTaken on demand and kept until you delete them. Suits long-term retention before risky changes.
              • RestoreAlways creates a new instance with a new endpoint; it does not rewind the existing one.
              • Parameter groupsNamed engine settings such as connection limits or character sets. Some changes need a reboot, so use a maintenance window.
              • Option groupsEnable optional engine features, such as native backup to S3 for SQL Server or extra Oracle features.
              The restore-creates-a-new-instance point is a common surprise: the application must be pointed at the new endpoint.

              Amazon Aurora: a cloud-built relational engine

              Compute and storage are separate, which changes failover and read scaling.

              HACKTHESOCLesson 110AWS databases and analytics16 / 49

              Aurora separates compute from storage

              MySQL and PostgreSQL compatible: existing drivers, tools and most application code work unchanged.

              • ClusterOne writer instance plus up to 15 Aurora Replicas (readers).
              • Shared cluster volumeSix copies of the data spread across three Availability Zones.
              • Automatic growthGrows in 10 GiB steps up to 128 TiB, so there is no disk to pre-provision.
              • Small replica lagReplicas read the same storage instead of receiving a copy, so lag is often milliseconds.
              • Fast failoverIf the writer fails, a replica is promoted, commonly in well under a minute.
              • Replicas do two jobsRead scaling and high availability, unlike classic RDS read replicas.
              AWS cites up to five times the throughput of standard MySQL and three times that of standard PostgreSQL, but real results depend on the workload.
              HACKTHESOCLesson 110AWS databases and analytics17 / 49

              Use endpoints, not instance names, for transparent failover

              EndpointPoints to
              Cluster endpointAlways the writer
              Reader endpointLoad balances across the Aurora Replicas
              Custom endpointsOptional additional endpoints

              Using endpoints instead of instance names is what makes failover transparent to the application.

              If an app hardcodes an instance name, a promotion breaks it. The cluster endpoint follows the writer wherever it moves.
              HACKTHESOCLesson 110AWS databases and analytics18 / 49

              Other Aurora capabilities worth recognising

              Automatic sizing

              Serverless v2

              Adjusts compute continuously in ACUs (Aurora Capacity Units) between a minimum and maximum you set. Pay for capacity used.

                Cross-Region

                Global Database

                Replicates to other Regions with low lag, for cross-Region reads and disaster recovery.

                  MySQL edition

                  Backtrack

                  Rewinds a cluster to an earlier moment without restoring from a backup.

                    Continuous

                    Backup and cloning

                    Continuous backup to S3 with point-in-time restore. Fast cloning shares storage until data diverges.

                      Serverless v2 still is a relational cluster with the same SQL behaviour: only the sizing is automatic.

                      Serverless v2 suits spiky, unpredictable or infrequently used databases, such as a development environment or a new application with unknown traffic.
                      HACKTHESOCLesson 110AWS databases and analytics19 / 49
                      Aurora costs more per instance hour than RDS, and buys faster failover and more read headroom.

                      For a small internal tool with light traffic, standard RDS is often cheaper and perfectly adequate. Both stay relational.

                      Neither solves a workload that is fundamentally key-value at massive scale. That is the cue for the next section.

                      Section 4 of 8

                      Amazon DynamoDB: key-value and document at any scale

                      Serverless, single-digit millisecond responses, designed around exactly how the app reads.

                      HACKTHESOCLesson 110AWS databases and analytics21 / 49

                      Tables hold items, and the primary key decides placement

                      • ItemsLike rows, made of attributes. Items need not share attributes; up to 400 KB each.
                      • Partition key onlyA single attribute, such as UserId.
                      • Partition key plus sort keyE.g. CustomerId plus OrderDate: one query fetches a customer's orders in date order.
                      • HashingThe partition key is hashed to pick the physical partition: the source of its scale and its best-known pitfall.
                      • Good fitShopping carts, session stores, user profiles, game state, IoT device state: simple lookups at huge scale.
                      • Poor fitComplex multi-table joins, ad hoc reporting, unknown or constantly changing access patterns.
                      There are no joins and no ad hoc SQL. You design the table around the exact reads first. Forcing a deeply relational model in leads to painful redesigns.
                      HACKTHESOCLesson 110AWS databases and analytics22 / 49

                      Hot partitions: a low-cardinality key throttles one

                      Few values

                      Keys that cause trouble

                      One partition gets a disproportionate share of requests and is throttled while others sit idle.

                      • Status with only three possible values
                      • Date or country when traffic is concentrated
                      • A single celebrity product ID

                      High cardinality

                      Keys that spread load

                      Choose a partition key with many distinct values and even access, so load spreads across partitions.

                      • UserId for a shopping cart
                      • OrderId instead of order Status
                      This is the best-known DynamoDB pitfall and a likely exam question. Ask: how many distinct key values are there, and is traffic even across them?
                      HACKTHESOCLesson 110AWS databases and analytics23 / 49

                      On-demand or provisioned: how you pay for capacity

                      ModeHow it worksBest for
                      On-demandPay per request, no capacity planning, scales instantlyNew, spiky or unpredictable workloads
                      ProvisionedYou set read (RCU) and write (WCU) capacity units; optional auto scalingSteady, predictable traffic where cost optimisation matters

                      Exceeding provisioned capacity without auto scaling causes throttling.

                      On-demand is the safe default when you do not know the traffic. Provisioned can be cheaper at a steady high load.
                      HACKTHESOCLesson 110AWS databases and analytics24 / 49

                      Reads, caching and global reach

                      Two read modes

                      Consistency

                      Eventually consistent reads are the default and cheaper. Strongly consistent reads return the latest data at higher cost.

                        In-memory cache

                        DAX

                        Built for DynamoDB. Cuts read latency from milliseconds to microseconds; just point to the DAX endpoint.

                          Multi-active

                          Global tables

                          Replicate a table across Regions. Users write locally and changes propagate, for low latency and Regional resilience.

                            Streams, TTL, PITR

                            Other features

                            Streams emit a change feed to trigger Lambda. TTL expires old items. Point-in-time recovery guards against accidental deletion.

                              DAX needs no application redesign beyond the new endpoint. Do not confuse it with ElastiCache, which is the general-purpose cache covered next.

                              ElastiCache and the purpose-built databases

                              In-memory speed, plus the engines whose data model matches their name.

                              HACKTHESOCLesson 110AWS databases and analytics26 / 49

                              The cache sits in front of a slower database

                              ElastiCache keeps data in RAM, so reads return in microseconds.

                              1. 1Check the cache firstThe application asks ElastiCache before the database.
                              2. 2A hit is answered fastThis reduces load on the database and improves response times.
                              3. 3A miss reads the databaseThe application falls back to the slower disk-based engine.
                              4. 4Store it for next timeE.g. cache an expensive product-listing query, with a time-to-live.
                              Decide how stale cached data may become, so users do not see outdated prices. That is what the time-to-live controls.
                              HACKTHESOCLesson 110AWS databases and analytics27 / 49

                              Redis OSS and Valkey, Memcached and MemoryDB

                              EngineCharacteristicsTypical use
                              Redis OSS / ValkeyLists, sets, sorted sets, replication, persistence, pub/subLeaderboards, session stores, queues, real-time counters
                              MemcachedSimple key-value, multi-threaded, no persistence or replicationPlain object caching where loss on restart is acceptable
                              Amazon MemoryDBRedis-compatible and durableUsed as a primary database, not a disposable cache

                              A cache holds copies: if it is the only home for important data, a restart or eviction loses it.

                              Memcached is the simple one. If the question mentions persistence, replication or leaderboards, think Redis or Valkey.
                              HACKTHESOCLesson 110AWS databases and analytics28 / 49

                              Purpose-built engines: the name implies the data model

                              The Cloud Practitioner exam expects you to recognise the use case behind each name.

                              • Amazon NeptuneGraph database for connected data: friends of friends, fraud rings, recommendation paths.
                              • Amazon DocumentDBJSON-like documents with MongoDB compatibility: ideal for migrating a MongoDB application.
                              • Amazon TimestreamTime-series: IoT sensor readings or metrics, with built-in time functions and tiering of old data.
                              • Amazon KeyspacesManaged wide-column storage compatible with Apache Cassandra.
                              • OpenSearch ServiceSearch and log analytics over text-heavy data.
                              Shortcut: graph relationships mean Neptune, MongoDB means DocumentDB, sensor streams mean Timestream, microsecond caching means ElastiCache, key-value at scale means DynamoDB.
                              HACKTHESOCLesson 110AWS databases and analytics29 / 49
                              Purpose-built does not mean use everything.

                              Each extra engine adds knowledge, monitoring and cost. Small teams often start with one relational database and add others when a bottleneck appears.

                              The point of the portfolio is that when a bottleneck does appear, you can reach for a tool designed for it instead of bending a general-purpose one.

                              Analytics: warehouse, query-in-place, ETL, BI, streaming

                              Operational databases answer small questions fast; analytics answers large ones across huge volumes.

                              HACKTHESOCLesson 110AWS databases and analytics31 / 49

                              Redshift loads the data; Athena queries it where it sits

                              Data warehouse

                              Amazon Redshift

                              Columnar storage with massively parallel processing. A query on three columns of a billion-row table touches only those columns.

                              • Load curated, structured data
                              • Serverless option removes cluster sizing
                              • Spectrum extends queries to files in S3

                              Serverless over S3

                              Amazon Athena

                              Point it at CSV, JSON, Parquet or ORC files in S3, define a table, run standard SQL. Nothing to provision or load.

                              • Pay per amount of data scanned
                              • Parquet and date partitions cut scanned bytes

                              Never run heavy scans on the production OLTP database: it competes with customer traffic and slows the application.

                              Columnar is why aggregations are dramatically faster than in a row-oriented OLTP engine. Compressed Parquet and date partitions can cut Athena cost by a large factor.
                              HACKTHESOCLesson 110AWS databases and analytics32 / 49

                              Redshift versus Athena

                              AspectRedshiftAthena
                              ModelProvisioned or serverless warehouseServerless query engine
                              Data locationLoaded into warehouse storageStays in S3
                              PricingCompute capacity (or serverless usage)Per TB of data scanned
                              Best forFrequent, complex, high-concurrency reporting on curated dataOccasional ad hoc queries, log exploration, quick investigation
                              Setup effortHigher (schema, loading, tuning)Minimal (define table over files)
                              Frequency is the deciding variable. Frequent heavy reports go to Redshift, occasional investigation goes to Athena. A security analyst exploring logs in S3 is the Athena case.
                              HACKTHESOCLesson 110AWS databases and analytics33 / 49

                              Glue, QuickSight and Kinesis round out the pipeline

                              • AWS GlueServerless ETL. Crawlers register S3 data in the Glue Data Catalog; jobs clean, convert (CSV to Parquet) and move data.
                              • Amazon QuickSightServerless BI for dashboards. Connects to Athena, Redshift, RDS; business users see charts without writing SQL.
                              • Kinesis Data StreamsIngests and buffers continuous events for custom consumers.
                              • Amazon Data FirehoseDelivers streams to S3, Redshift or OpenSearch with little code.
                              • Amazon EMRManaged Hadoop and Spark for large-scale custom processing.
                              The Glue Data Catalog is the shared table definition that Athena and Redshift Spectrum read from.
                              HACKTHESOCLesson 110AWS databases and analytics34 / 49

                              A typical lake pipeline, left to right

                              1. 1KinesisEvents flow in as they arrive.
                              2. 2S3The files land in object storage.
                              3. 3GlueCatalogs the data and converts it.
                              4. 4AthenaQueries the files ad hoc.

                              Trace one event end to end. Each service does one job: ingest, store, prepare, explore, report, visualise.

                              Six selection pitfalls

                              • RDS when DynamoDB fitsBillions of simple key lookups outgrow a single relational writer, and you end up managing replicas and sharding.
                              • DynamoDB for relational dataReporting, joins and constantly changing queries become painful and expensive.
                              • Replica treated as HAOn classic RDS a read replica is a scaling tool, not a failover mechanism.
                              • Analytics on productionOffload to a replica, Athena or Redshift so customer traffic is not affected.
                              • Redshift for a monthly queryA provisioned warehouse is overkill; Athena over S3 is usually cheaper at low frequency.
                              • Ignoring Athena data formatsLarge uncompressed CSV scans everything and costs more than partitioned Parquet.
                              Each pitfall maps to a lesson from earlier sections. Ask students to name the section that warned about it.

                              Worked example: databases for an online store

                              Three data needs, three access patterns, three different answers.

                              HACKTHESOCLesson 110AWS databases and analytics41 / 49

                              Match each need to its access pattern

                              Relational OLTP

                              Profiles and orders

                              Orders reference customers and products, finance needs transactional integrity, support runs joins. Choice: Aurora PostgreSQL, or RDS if cost leads.

                                Key-value, spiky

                                Shopping cart

                                Read and written on almost every page view, accessed only by user ID, no joins, traffic can multiply tenfold in flash sales. Choice: DynamoDB.

                                  Two patterns

                                  Analytics

                                  Occasional clickstream investigation and recurring executive reports. Choice: S3 with Athena for ad hoc, Redshift with QuickSight for recurring.

                                    If the traffic profile is unknown at launch, Aurora Serverless v2 avoids guessing instance size. Multi-AZ covers availability, read replicas cover read growth.
                                    HACKTHESOCLesson 110AWS databases and analytics42 / 49

                                    The cart design, choice by choice

                                    • Partition keyUser ID: high cardinality spreads load evenly. Avoid date or product category.
                                    • On-demand capacityFlash sale traffic is unpredictable, so there is nothing to plan.
                                    • TTLExpires abandoned carts automatically.
                                    • DAX, if reads get hotAdd the in-memory cache when cart reads become extremely hot.
                                    • Why not relationalIt works at first but puts spiky traffic on the same writer that processes payments.
                                    Every choice is justified by the access pattern. Optional extras: an ElastiCache layer for the product catalogue, and Neptune if recommendations are added later.
                                    HACKTHESOCLesson 110AWS databases and analytics43 / 49

                                    An analytics path that never touches production

                                    1. 1Firehose to S3Clickstream events flow through Kinesis Data Firehose into S3.
                                    2. 2Glue convertsCrawls the data and converts it to Parquet, partitioned by date.
                                    3. 3Athena investigatesThe engineer queries the files directly, with no loading.
                                    4. 4Redshift reportsLoaded nightly from the operational database for recurring reports.
                                    5. 5QuickSight showsDashboards on top for business users.

                                    None of this analytic load touches the production Aurora cluster.

                                    Redshift Serverless is an alternative to a provisioned warehouse. Partitioned Parquet keeps Athena scans cheap.

                                    Key takeaways

                                    1. 01Match the service to the access pattern: relational for OLTP with joins, DynamoDB for key lookups at scale, analytics services for heavy
                                    2. 02Multi-AZ is synchronous high availability with automatic failover; a read replica is asynchronous read scaling you promote manually.
                                    3. 03Aurora shares one six-copy, three-AZ volume across a writer and up to 15 replicas, giving fast failover and small replica lag.
                                    4. 04DynamoDB needs a high-cardinality partition key to avoid hot partitions; on-demand capacity suits unpredictable traffic.
                                    5. 05Athena queries S3 in place and bills per data scanned; Redshift is the columnar warehouse for frequent, complex reports.
                                    6. 06Keep analytics off the production database, and add caches or purpose-built engines only when a bottleneck appears.

                                    A production RDS for MySQL database must survive the loss of an Availability Zone with minimal downtime and no manual action. Which feature should they enable?

                                    Multi-AZ keeps a synchronous standby in another AZ and fails over automatically. A read replica is asynchronous and promoted by hand, a bigger instance does not survive losing a zone, and snapshot restores are slow and lose recent data.

                                    A security analyst occasionally needs to run SQL against several terabytes of log files already in S3, a few times per month, with no loading or infrastructure to manage. Which service fits best?

                                    Athena is serverless, queries S3 files in place with SQL and charges by data scanned, so rare queries cost little. Redshift needs loading and idle compute, ElastiCache is a cache, and RDS is transactional, not built for large scans.

                                    Check your understanding, question 3 of 3

                                    A DynamoDB table uses order Status (pending, shipped, delivered) as its partition key, and most new traffic is for pending orders. What is the likely problem and the remedy?

                                    Only three key values exist and most requests hit one, so a single partition is overloaded and throttles while others idle; a high-cardinality key like OrderId spreads load. DAX caches reads, and failover and capacity mode do not fix uneven keys.
