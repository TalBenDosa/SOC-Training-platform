Six stages carry an event from source to search, and a fault in any of them looks like silence.

Six stages, and each one fails differently

Every event you search has travelled through all six.

StageWhat happensTypical failureHow it shows up
1. SourceOS, app or device writes an eventAuditing off, log overwrittenEvent never existed
2. CollectionAgent reads it, or SIEM pulls or receives itAgent stopped, credentials expiredSource goes quiet
3. TransportBytes move over UDP, TCP or TLSUDP loss, firewall block, TLS cert expiredGaps, bursts after reconnect
4. ParsingRaw text becomes named fields (src_ip, user)No parser, wrong parser, format changeEvents stored, fields empty
5. Index and storeEvents written, compressed, retainedDisk full, licence cap, queue overflowDelayed or dropped events
6. SearchAnalyst or rule queries the storeWrong time range, skewed timestampsEvents exist but are not found
Ingestion matters more than any single detection. Different teams own different stages: Windows admins the source, network engineers the firewall rules, the SIEM team the collector.

Two timestamps travel with every event

Analysts confuse them constantly.

On the source

Event time

When the thing happened on the source. The timeline of an incident should follow this one.

    In the SIEM

    Receive (index) time

    When the SIEM stored the event.

      The difference

      Ingestion latency

      Healthy: seconds. Minutes or hours: a rule over the last five minutes misses real activity, and a timeline built on receive time is in the wrong order.

        Ask students which timestamp their last search used. Latency is also the first thing to check when a fresh alert looks late.
        HACKTHESOCLesson 115Log ingestion and collection8 / 48

        Five questions that isolate the broken stage

        Ask them in order whenever a log source looks wrong.

        1. 1Was the event generated?Is auditing enabled and the log large enough to keep it?
        2. 2Did it leave the host?Agent running, right channel, credentials valid?
        3. 3Did it arrive?Transport: UDP loss, firewall block, expired TLS certificate.
        4. 4Was it parsed?Fields populated, or stored as an empty blob?
        5. 5Is the timestamp correct?Compare event time with receive time.

        Answering these in order finds the broken stage in minutes rather than hours.

        If the tank is empty you do not stare at the tank. You walk the pipe backwards until you find the leak.

        Agent versus agentless and the common collectors

        Software on the source or none at all, and the collectors you will meet most often.

        HACKTHESOCLesson 115Log ingestion and collection10 / 48

        Two shapes of collection: agent or no agent

        Installed on the source

        Agent-based

        Software on the source reads events locally and ships them.

        • Windows and Linux servers, endpoints
        • Needs deployment and patching on every host

        Nothing extra on the source

        Agentless

        The source pushes events itself (syslog, an API webhook), or the SIEM pulls them (WMI or RPC polling, an SSH session, a cloud API such as an S3 bucket of audit files).

        • Firewalls, switches, cloud services, legacy devices
        The analyst's job is to know which method a given source uses, because the failure modes differ.
        HACKTHESOCLesson 115Log ingestion and collection11 / 48

        Agent versus agentless: the trade-offs

        AspectAgent-basedAgentless
        Install footprintSoftware on every host; needs deployment and patchingNone on the source
        ReliabilityLocal buffering, survives outages, tracks log positionUDP push can lose events; pull needs credentials and reachability
        FilteringCan drop noise at the source before it uses bandwidthUsually everything is sent; filtering happens later
        SecurityRuns privileged: attack surface and tamper targetFewer binaries, but pull needs a powerful remote account
        CoverageOnly hosts where the agent is installedAppliances, routers, SaaS where no agent is possible

        Neither wins universally. A mature estate uses both.

        Servers and endpoints deserve an agent for buffering, filtering and tamper evidence. Appliances cannot run your agent, so syslog or an API is the only option.
        HACKTHESOCLesson 115Log ingestion and collection12 / 48

        The collectors you will meet most often

        • WEF with a WEC serverWindows, built in. WS-Management over HTTP 5985 (Kerberos) or HTTPS 5986. No third-party agent; the collector forwards onward.
        • WinCollectQRadar, Windows. Syslog to an Event Collector on TCP 514 or TLS. Managed (central config) or standalone.
        • Splunk Universal ForwarderWindows, Linux, Unix. TCP 9997, optional TLS. Lightweight, persistent queue, indexer acknowledgement.
        • Winlogbeat, FilebeatElastic Beats. To Logstash (5044) or Elasticsearch (9200). Position tracked in a registry file.
        • rsyslog, syslog-ngLinux, Unix. UDP or TCP 514, TLS 6514. Daemons that receive local and remote syslog and relay it.
        • OpenTelemetry CollectorCross-platform. OTLP over gRPC 4317 or HTTP 4318. Vendor-neutral receivers, processors and exporters.
        Do not ask students to memorise ports. Ask which port to open on the firewall when a new source is onboarded.
        HACKTHESOCLesson 115Log ingestion and collection13 / 48
        Before onboarding a source: can it run an agent, what does the agent need, what if the network is down, and where is the bookmark?

        The last two questions decide whether an outage costs you minutes of delay or a permanent hole in the evidence. The agent needs credentials, ports and a service account.

        The bookmark is the position the agent remembers in the log. It comes back in the duplicates discussion later.

        Windows collection: WEF/WEC, WinCollect and channels

        Windows stores events in channels; collection means choosing which to read and how to move them.

        HACKTHESOCLesson 115Log ingestion and collection15 / 48

        Two subscription types: pull or push

        Windows Event Forwarding sends events from sources to a Windows Event Collector over WS-Management.

        Collector pulls

        Collector-initiated

        The collector pulls from a named list of sources. Fine for a handful of servers.

          Clients push

          Source-initiated

          Group Policy tells each client where the collector is, and it pushes by itself. Scales to thousands of machines.

          • Sources need the WinRM service running
          • Network service account joins Event Log Readers
          Channels are the named logs in Event Viewer: Security, System, Application, and hundreds of operational channels.
          HACKTHESOCLesson 115Log ingestion and collection16 / 48

          Pointing clients at the collector with Group Policy

          Source side by Group Policy, collector side by two commands.

          Read the Server= value aloud: the collector name, port 5985 and a Refresh of 60. Also confirm the network service account on the source can read the Security log via Event Log Readers.
          HACKTHESOCLesson 115Log ingestion and collection17 / 48

          Tuning the subscription and the agent

          • XPath filterThe subscription filters at the source, e.g. Security IDs 4624, 4625, 4672, 4688, 4720 and 1102.
          • ForwardedEvents sizeEvents land here on the collector. Its default size is small: raise it or events are overwritten before your agent reads them.
          • Delivery modeNormal, Minimize Bandwidth or Minimize Latency. Choose Minimize Latency so batching never delays detections.
          • WinCollect, managed modeQRadar Console holds and pushes the config, so channels change centrally. Standalone keeps config on the host.
          • WinCollect as remote pollerReads other Windows hosts: convenient, but concentrates credentials and load on one box.

          Microsoft's guidance is roughly 4000 sources per collector; beyond that, add collectors.

          Standalone WinCollect suits isolated networks without console access but is painful to change at scale. Check the vendor's support lifecycle before building a new design on any agent.
          HACKTHESOCLesson 115Log ingestion and collection18 / 48

          The channel you pick decides what you can see

          ChannelKey eventsWhat it adds
          Security4624, 4625, 4672, 4688, 4720, 4728, 1102Logons, privilege use, process creation (if enabled), account changes, log clearing
          Sysmon/Operational1, 3, 7, 10, 11, 22Process with hashes and parent, connections, image loads, LSASS reads, files, DNS
          PowerShell/Operational4104Script block text: exposes obfuscated commands that run in memory

          Security alone tells you who logged on, not what malware did afterwards.

          4624 is a logon success and 4625 a failure. Missing Sysmon is one of the most common reasons a real intrusion has no visible middle.

          Section 4 of 8

          Syslog: transports, facilities and severities

          The common language of network devices and Unix systems, and where its reliability is decided.

          HACKTHESOCLesson 115Log ingestion and collection20 / 48

          Reading an RFC 5424 message and its PRI

          RFC 3164, the older looser BSD format, is still sent by plenty of devices.

          • Fields: PRI, version, timestamp, host, app, PID, msg ID, structured data, text
          • The dash after ID47 means no structured data
          • PRI packs facility and severity into one number
          The message is one line on the wire, wrapped here to fit. To decode a PRI, divide by 8: the quotient is the facility and the remainder is the severity.
          HACKTHESOCLesson 115Log ingestion and collection21 / 48

          Facility says what kind of process sent it

          FacilityNameTypical source
          0kernKernel messages
          1userUser-level processes
          3daemonSystem daemons
          4authLogin and security
          10authprivPrivate authentication, such as sshd and sudo on many Linux builds
          16 to 23local0 to local7Free for applications and devices; firewalls and switches often use one
          The sshd failure above sits under auth in the example PRI. On many Linux builds the same daemon logs under authpriv.
          HACKTHESOCLesson 115Log ingestion and collection22 / 48

          Severity is the sender's opinion, not yours

          • A firewall deny may be Informational while a failed admin login is Warning
          • Never filter on severity alone and assume you kept the important events
          Severity cannot exceed 7, which is why the PRI decode works with a remainder.
          HACKTHESOCLesson 115Log ingestion and collection23 / 48

          Transport decides whether syslog is reliable

          No acknowledgement

          UDP 514

          Connectionless: no retransmission and no buffer. A busy collector or congested link silently drops datagrams, and long messages are truncated.

          • RFC 5424 requires receivers to accept 480 octets
          • Many accept 1024 or more

          Ordered and retransmitted

          TCP 514 (or 601)

          Reliable delivery, but a plain connection can still lose whatever sat in the sender's memory when the link broke.

            Encrypted and authenticated

            TLS 6514 (RFC 5425)

            Mutual authentication: nobody can read or inject events in transit, and forged events cannot reach your SIEM.

              On Linux, rsyslog and syslog-ng filter by facility and severity and forward to the SIEM. Easy to send, easy to forget to monitor.

              Ask for any syslog source: which transport, port, facility, timestamp format and time zone, and is the sending IP the real device or a relay. A gap in exactly the busiest hour on a UDP source means suspect loss before an attacker.

              Parsing and normalization: from raw text to evidence

              Raw text becomes named fields, and every detection, dashboard and correlation runs on them.

              HACKTHESOCLesson 115Log ingestion and collection25 / 48

              Parsing extracts fields; normalization names them alike

              Extract

              Parsing

              Pulls named fields out of the raw text. A Windows 4625, a Linux sshd failure and a firewall deny use different words and positions.

                Map

                Normalization

                Maps those names onto a common schema, so source IP is called the same thing whether it came from a Cisco ASA or a Linux server.

                  All three describe a failed or blocked connection. Without normalization each needs its own rule and its own dashboard.
                  HACKTHESOCLesson 115Log ingestion and collection26 / 48

                  Where parsing happens depends on the product

                  ProductHow it parses and normalizes
                  QRadarDevice Support Modules (DSMs), plus custom properties for fields the DSM misses
                  SplunkSourcetype, field extractions and add-ons that map to the Common Information Model
                  ElasticIngest pipelines, Logstash filters and the Elastic Common Schema
                  OpenTelemetryProcessors and the log data model
                  OCSFAn emerging open schema for the same purpose
                  The vocabulary differs; the job is identical. Learn what your own platform calls its parser.
                  HACKTHESOCLesson 115Log ingestion and collection27 / 48

                  A grok pattern turns the sshd line into fields

                  A grok pattern is a readable regular expression with names.

                  A Windows event is already structured XML: EventData holds TargetUserName, IpAddress and LogonType. There the work is mapping, not extraction.
                  HACKTHESOCLesson 115Log ingestion and collection28 / 48

                  An unparsed log is stored but nearly invisible

                  • Present but uselessIt uses storage and licence and looks present on the health page, but searches can only match words, not fields.
                  • Detections never fireMany failures for one user from one source needs the user and source fields. Empty fields mean no alert.
                  • Dashboards and joins failA logons-by-country chart shows nothing, and correlating firewall and endpoint events on a shared IP fails.
                  • Nothing errorsCoverage looks green while the data is useless. QRadar shows Unknown or Stored; others a generic sourcetype or parse-failure tag.
                  • Parsers break over timeA firmware upgrade, a new language or a new Windows field turns parsed events into unparsed ones overnight.

                  Check five known events (successful login, failed login, policy change) for populated fields, and track the unparsed ratio per source.

                  Also beware the wrong parser: Linux logs accepted as a generic syslog source work but without authentication fields. Treat a sudden rise in the unparsed ratio as an incident in the pipeline itself.

                  What to collect: coverage, volume, licensing and time

                  Coverage is the ceiling of your detection, volume is the bill, and time is part of the data.

                  HACKTHESOCLesson 115Log ingestion and collection30 / 48
                  You cannot detect what you do not collect, and collecting everything costs money and drowns signal.

                  If PowerShell script block logging is off, no rule sees an encoded payload. If Sysmon is missing, no rule sees a process access to LSASS.

                  A technique is only visible if some log source records it. Coverage reviews against ATT&CK turn this into a map of gaps.
                  HACKTHESOCLesson 115Log ingestion and collection31 / 48

                  Licensing turns a technical choice into a budget

                  Some products license on events per second (EPS), others on gigabytes ingested per day.

                  • A single chatty source can double that
                  • Filtering Platform 5156 and 5158: thousands of events per host per hour
                  • Object access 4663 and 4662 on a file server can swamp everything else
                  When the licence cap is hit, products queue, drop events or stop searching, usually in the busiest and most interesting period.
                  HACKTHESOCLesson 115Log ingestion and collection32 / 48

                  Collect by purpose, starting from the questions you must

                  AreaSources and events
                  IdentityDomain controller Security logs (4768, 4769, 4771, 4776), VPN and single sign-on logs
                  EndpointSecurity (4624, 4625, 4688 + command line, 4697, 7045), Sysmon, PowerShell 4104, EDR
                  NetworkFirewall allow and deny, DNS queries, proxy logs, DHCP leases (map IP to host)
                  Cloud and emailControl-plane audit logs, mail gateway and mailbox audit

                  Filter at the source where you can, but each filter is a decision to be blind to something: write it down and review it.

                  Source-side filters: an XPath query in a WEF subscription, a blacklist in a forwarder, a Sysmon config that excludes known-good, an rsyslog rule that drops debug.
                  HACKTHESOCLesson 115Log ingestion and collection33 / 48

                  Clock errors reorder an attack

                  Detection correlates events across systems by timestamp, so every source must keep accurate time.

                  Where time comes from

                  Accuracy

                  Domain members follow the domain hierarchy (the PDC emulator syncs to reliable NTP). Linux uses chrony or ntpd. Network devices need explicit NTP servers.

                    Parsed wrongly

                    Time zone and format

                    A firewall logging local time without an offset, parsed as UTC, puts events hours into the future or past.

                      Even one minute

                      Clock skew

                      A fast attack chain is reordered: the process launch appears after the connection it caused, and a 30 second join rule fails.

                        Best practice: log in UTC, include the offset, and store event time and receive time separately.

                        Check three things on every source: clock accuracy, time zone and format.

                        Section 7 of 8

                        Operational concerns: buffering and pipeline health

                        A pipeline that works on day one breaks quietly by month three: design so failure costs delay, not evidence.

                        HACKTHESOCLesson 115Log ingestion and collection35 / 48

                        What each tool does when the destination is down

                        ToolBuffering behaviour
                        Splunk Universal ForwarderIn-memory queues, optional disk queues; useACK resends if receipt is unconfirmed
                        WinlogbeatIn-memory queue, optional disk queue; records its position in a registry file
                        rsyslogAction queues; queue.type LinkedList with a queue.filename makes it disk-assisted
                        syslog-ngOffers disk-buffer
                        Plain UDP syslogNo buffer at all: if the receiver is not listening at that millisecond, the event is gone

                        With useACK, delivery moves from at-most-once to at-least-once.

                        A good agent keeps events and resumes. The question to ask of every source is what happens to its events during an outage.
                        HACKTHESOCLesson 115Log ingestion and collection36 / 48

                        Back-pressure: when the destination is slower than the

                        Something must give: block the producer, spill to disk, or drop.

                        Block the producer

                        Can hurt production: a firewall or busy application stalls because the log pipe is full.

                          Spill to disk

                          Many designs choose disk-buffer for servers, so events wait instead of vanishing.

                            Drop

                            Many designs choose drop for devices, protecting the device at the cost of evidence.

                              A port scan or attack storm is peak volume, so pipelines fail when you need them most. Size for peaks, not averages.

                              Know which of the three your pipeline does for each source type.
                              HACKTHESOCLesson 115Log ingestion and collection37 / 48

                              How events get lost, doubled or looped

                              • Security log wrapsThe log is too small and wraps before the agent reads it. Windows default sizes are modest: enlarge them.
                              • Parser rejects, licence exceededMalformed events are rejected, and the SIEM drops events once over its licence.
                              • Log clearing is an event1102 for Security and 104 for System are worth alerting on, since attackers clear logs.
                              • Replay after reinstallDeleting the position file makes an agent re-read everything: old events look new, with receive time far from event time.
                              • Double countingOverlapping subscriptions, or an agent plus a WEF feed on one host, break threshold rules.
                              • LoopsA relay forwarding to a collector that forwards back, or SIEM syslog output sent to an input it reads, explodes volume.

                              Add a deduplication check and keep a diagram of who forwards to whom.

                              Replay is the one students meet first: a reinstall floods the SIEM with old events that look new and trip count-based rules.
                              HACKTHESOCLesson 115Log ingestion and collection38 / 48

                              Monitor the pipeline as a system

                              CheckWhat it catches
                              Silent sourceA source that normally sends events has sent none for a set period
                              Volume baselineSudden drops (broken) and spikes (flood or loop) per source
                              LatencyThe median gap between receive time and event time grows
                              Queue depth and agent statusForwarder queues filling, collector CPU, disk space
                              Parse healthThe unparsed ratio per source type
                              Inventory reconciliationSIEM source list compared with the asset database (CMDB): hosts never onboarded

                              A missing log source is a finding.

                              An agent that went offline at 02:00 on a domain controller may be tampering. Ask the Windows team before assuming a patch window.

                              Worked example: onboarding a Windows server

                              WEB-SRV07 joins the estate: get Security and Sysmon in, then prove they arrive and parse.

                              HACKTHESOCLesson 115Log ingestion and collection40 / 48

                              Six moves to onboard WEB-SRV07

                              A new Windows Server 2022 web server, using a Splunk Universal Forwarder.

                              1. 1Make the source generate eventsAdvanced audit policy, command line in 4688, bigger Security log.
                              2. 2Install SysmonApproved config; it writes to Microsoft-Windows-Sysmon/Operational.
                              3. 3Install and configure the forwarderinputs.conf and outputs.conf, port 9997 with useACK, outbound TCP 9997 open.
                              4. 4Verify at the sourceForwarder connected, no connection errors, channel has events.
                              5. 5Verify at the SIEMGenerate test events, search by host, check fields, latency and clock.
                              6. 6Close the loopSource list, silent-source alert, filters, Sysmon version, expected volume.

                              The same steps apply with Winlogbeat, WinCollect or WEF; only the configuration syntax differs.

                              Step 1 audit coverage: Logon, Process Creation, Account Management and Policy Change. Step 6 sets a silent-source alert of 15 minutes.
                              HACKTHESOCLesson 115Log ingestion and collection41 / 48

                              Install Sysmon and point the forwarder at both channels

                              • Sysmon writes to Microsoft-Windows-Sysmon/Operational
                              • outputs.conf: indexer on port 9997 with useACK = true
                              • Open outbound TCP 9997; run the forwarder under an account that can read the channels
                              The sysmonconfig.xml can be a community baseline tuned for your estate. The inputs.conf stanzas go on the forwarder.
                              HACKTHESOCLesson 115Log ingestion and collection42 / 48

                              What a pass looks like at each check

                              CheckPass looks like
                              Forwarder connectionThe forward-server list shows the indexer as active; no errors in the forwarder log
                              Channel has eventsRecent Sysmon events are returned at the source
                              Both sources arriveHost WEB-SRV07 shows Security and Sysmon, counted by source and EventCode

                              Most onboarding failures are found at the source check or the SIEM check: a blocked port, a missing channel permission, a disabled audit subcategory, or a parser never installed.

                              Key takeaways

                              1. 01Six stages carry every event: source, collection, transport, parsing, index, search. A fault in any of them looks like silence.
                              2. 02Agents buffer and filter on servers; agentless syslog or API covers appliances. Know which method each source uses.
                              3. 03Choose Windows channels on purpose: Security shows who logged on, Sysmon and PowerShell show what ran.
                              4. 04UDP syslog drops events silently under load; TCP adds retransmission and TLS on 6514 adds protection.
                              5. 05An unparsed log is stored but nearly invisible: check that fields are populated and track the unparsed ratio.
                              6. 06Monitor the pipeline itself: silent sources, volume, latency, queues and parse health. A missing source is a finding.
                              HACKTHESOCLesson 115Log ingestion and collection45 / 48

                              Check your understanding, question 1 of 3

                              Your firewall sends syslog over UDP 514. During a port scan the SIEM shows far fewer deny events than the firewall's own console. Most likely cause and best fix?

                              UDP syslog has no acknowledgement, retransmission or buffer, so bursts and congestion silently lose datagrams. TCP or TLS (6514) adds ordered, retransmitted delivery. A wrong parser leaves empty fields, not fewer events.

                              A new Windows server's 4625 events are searchable, but the dashboard counting failed logons by user and source IP shows nothing for it. What should you check first?

                              Events searchable as text but missing from a field-based dashboard are the signature of missing or wrong parsing: the user and source fields are empty. Check sample events and the assigned sourcetype or DSM.

                              Check your understanding, question 3 of 3

                              After reinstalling the forwarder on a busy server, a burst of events arrives with event times two weeks old and receive times of today, and thresholds fire. What explains it, and what do you do?

                              Reinstalling or deleting the bookmark makes the agent re-read from the oldest event, so old events get today's receive time and trip count rules. Confirm by comparing event and receive time, then deduplicate or exclude the range.
