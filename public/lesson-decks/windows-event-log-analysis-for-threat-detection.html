Event logs are the closest thing Windows has to a security camera.

Almost everything an attacker does on a host, logging on, spawning a process, installing a service, creating an account, leaves a matching event.

Frame the lesson: the goal is to take any compromised host and rebuild what the attacker did, in order: when, from where, with what credentials, what they ran, and how they persisted.

Password spray: one source, many usernames

4625 SubStatus: 0xC000006A wrong password, 0xC0000064 no such user, 0xC0000234 locked out.

  • Group by IpAddress, count distinct users: password spraying (T1110.003)
  • Group by TargetUserName over time instead: brute force (T1110.001)
  • A high 4625 to 4624 ratio from one source is a recon signal
Spraying is many users, few tries each; brute force is many tries against one user. Same event, different aggregation.

Process, task, account and service events: what to flag

  • 4688 process creationpowershell.exe from winword.exe, certutil.exe downloading remote files, wmic.exe spawning cmd.exe remotely.
  • 4698 scheduled taskRandom names, privileged commands at logon, scripts from %TEMP% or %APPDATA%. Pair with 4702 updated, 4699 deleted.
  • 4720 account createdCombine with 4732 local group add; on DCs 4728 global and 4756 universal group adds.
  • 7045 service installedRandom names, ImagePath in %APPDATA% or %TEMP%, or running cmd.exe or powershell.exe directly.
7045 is the single most important event for catching lateral movement and persistence on servers: PsExec, Impacket smbexec and custom backdoors all install services. Built-in tasks under Microsoft\Windows are usually noise.

A 4688 process-creation record, read field by field

  • NewProcessName spawned by winword.exe: Office launching a LOLBIN is the smell
  • CommandLine is present only when the process-command-line GPO is enabled
  • TokenElevationTypeFull means the process ran with an elevated token
4688 is the native fallback when Sysmon is absent. It is the one memorize-list event ID the deck otherwise never shows raw.
HACKTHESOCLesson 08Windows event log analysis12 / 87

Benign vs malicious process creation

Usually benign

A signed binary under System32 spawned by its normal parent, such as services.exe starting svchost.exe, during business hours by an expected user.

Worth a look

A LOLBIN such as certutil.exe, rundll32.exe or mshta.exe making a network connection, or spawned by an Office application.

Likely malicious

powershell.exe as a child of winword.exe, or a script engine run from %TEMP% by a user who never uses one.

The parent and the path, not the binary name alone, decide suspicion. Build the benign baseline first so the odd parent stands out.

Why Sysmon 1 beats Security 4688

Security 4688

NewProcessName, ParentProcessName, SubjectUserName, TokenElevationType. CommandLine only if the GPO is on.

Sysmon Event 1

Image, CommandLine always, User, LogonId, ProcessGuid, Hashes (SHA1, MD5, SHA256, IMPHASH), ParentImage and ParentCommandLine.

  • IMPHASH groups related malware families
  • ParentCommandLine shows how the process was spawned
ParentCommandLine is what you cannot get from native logging. It is how you catch a macro spawning cmd.exe with obfuscated PowerShell.
HACKTHESOCLesson 08Windows event log analysis16 / 87

A Sysmon Event 1, read field by field

  • ParentCommandLine is the field native 4688 cannot give you
  • ProcessGuid is the join key: one value pulls all of this process's events
  • IMPHASH groups malware families by their imported DLLs
Sysmon 1 is the richer twin of 4688. ParentCommandLine and ProcessGuid are exactly why serious Windows shops deploy it everywhere.

Network, file and registry: what to hunt

  • Event 3rundll32.exe, regsvr32.exe, mshta.exe or any LOLBIN making external connections is almost always malicious.
  • Event 11Executables written to %TEMP%, %APPDATA%, C:\Users\Public\ or the Startup folder. Pair with Event 1 for drop and execute.
  • Event 13Run keys (T1547.001), Image File Execution Options (T1546.012), AppInit_DLLs (T1546.010), Winlogon Userinit and Shell.

Pivot a whole investigation off one ProcessGuid

  1. 1Grab the GUIDAny suspicious Sysmon 1, 3, 10, 11 or 13 event carries a ProcessGuid. Copy it.
  2. 2Pull every eventQuery all Sysmon events with that GUID: files, connections, registry writes and DLL loads for that process.
  3. 3Climb the treeUse ParentProcessGuid to find the parent, and the GUID as a parent to find the children.
  4. 4Build the timelineOrdered by time, that single thread is the investigation: what ran, what it touched, what it spawned.
This pivot is the single most used Sysmon skill. Make it a saved macro and you will reach for it on every host investigation.

Privilege escalation and valid-account abuse

T1078: detect the behavior that follows privileged credential use, not the use itself.

HACKTHESOCLesson 08Windows event log analysis22 / 87

Six behavioral detections after credential theft

The usual escalation is not an exploit: the attacker gets valid admin credentials (T1078) and uses them.

  • Anomalous admin logonsDomain Admin 4624 on a host outside the baseline of jump boxes, PAWs and SCCM servers. Confirm with 4672.
  • Admin tooling abusepsexec.exe, paexec.exe, wmic.exe /node:, sc.exe \\target, reg.exe \\target from non-allow-listed users or hosts.
  • LSASS accessSysmon 10 on lsass.exe with 0x1010 or 0x143A; exclude MsMpEng.exe and alert on the rest.
  • New privileged accounts4720 then 4728 or 4732 into Domain, Enterprise or Schema Admins or Administrators within minutes.
  • Service-account abuseLogonType 5 on unusual hosts, or LogonType 2 or 10 at all: service accounts should not log on interactively.
  • RID hijackingSysmon 13 writing a low-priv account's RID to 000001F4 (500) in SAM, so Windows then authorizes it as Administrator.
Local Administrator with LogonType 3 from another workstation is the textbook pass-the-hash or shared-local-credential signature. Treat new-admin creation as one correlated rule, not two alerts.
HACKTHESOCLesson 08Windows event log analysis23 / 87

Anomalous admin logon: baseline vs out of baseline

Baseline, benign

A Domain Admin 4624 on a known jump box, PAW or SCCM server, confirmed by a 4672 for the same logon, during a change window.

Out of baseline

The same account, or local Administrator with LogonType 3 from another workstation, on a host that never hosts admin logons: textbook pass-the-hash or shared-credential lateral movement.

Build the baseline of where admin logons legitimately happen first. The detection is then simply any admin 4624 outside it.

Correlate create then elevate into one alert

  • Two event types from one actor within 600 seconds
  • Only privileged groups count, which keeps it high fidelity
Temporal proximity plus specific groups is what makes this reliable for T1136 and T1078.002.

HACKTHESOCLesson 08Windows event log analysis26 / 87

RID hijacking: why a registry write becomes Administrator

The mechanism

Windows authorizes by RID, the tail of the SID, and the built-in Administrator is always RID 500. An attacker rewrites a low-privilege account's RID in the SAM to 500 (000001F4).

What you then see

Later 4624 logons for that ordinary account are authorized as Administrator, so the logs read like the real Administrator and confuse investigators.

The detection

Sysmon 13 writing 000001F4 under SAM\SAM\Domains\Account\Users\. Rare, but worth a standing rule.

This is the slide that turns the matched value into a mechanism: the registry write re-labels the account at the authorization layer.

HACKTHESOCLesson 08Windows event log analysis29 / 87

Triage a Golden Ticket suspicion from telemetry

  1. 1No birth eventA Golden Ticket is forged offline, so no 4768 is logged at its creation. You cannot catch the issuance.
  2. 2An odd ticket in useThe first trace is a 4769 whose TGT has an implausible lifetime or an account-to-group mismatch.
  3. 3Correlate the accountPrivileged service access with no matching 4768 or 4624 authentication chain on the DC.
  4. 4RespondIf krbtgt compromise is suspected, rotate the krbtgt password twice, since it keeps one generation of history.
Detection is downstream and correlative, never at creation. That is why the response is to protect and rotate krbtgt upstream.
HACKTHESOCLesson 08Windows event log analysis30 / 87

Pass-the-hash: both ends of the connection

Event 4624

Target host

LogonType 3, AuthenticationPackageName NTLM, one account authenticating from many source hosts in a short window. Add 4672 to focus on privileged accounts.

Event 4624, LogonType 9

Source host

NewCredentials, LogonProcessName seclogo, package Negotiate. TargetUserName is the signed-in account; Network Account Name is the hash being used.

Modern environments should use Kerberos for almost everything; widespread NTLM is itself a misconfiguration.

Legitimate runas /netonly makes the same LogonType 9 shape, so the tell is a privileged or unexpected Network Account Name, ideally near Sysmon 10 on lsass.exe. 4648 records explicit credentials (runas, a mapped drive): useful context, not the pass-the-hash fingerprint.
HACKTHESOCLesson 08Windows event log analysis31 / 87

Kerberoasting: bursts of RC4 service tickets

  • Modern AD defaults to AES: 0x11 AES128, 0x12 AES256
  • Many distinct SPNs with RC4 from one source in 10 minutes
The attacker requests tickets for user accounts with SPNs and cracks them offline. The DC sees only normal-looking ticket requests, so volume and encryption type are the tell.
HACKTHESOCLesson 08Windows event log analysis32 / 87

RC4 service tickets: benign vs a roasting burst

Benign RC4

A single legacy application that genuinely needs RC4 requests one or two 4769 tickets for its own SPN, steadily, from its own host.

T1558.003

Kerberoasting

One account requests many 4769 tickets in RC4 (0x17) for many distinct high-value SPNs in a short window, with no matching application activity.

The cipher alone is not the verdict; the spread of SPNs from one requester is.

Read the code slide before this, then this slide tells you how to decide benign from malicious on the same event.
HACKTHESOCLesson 08Windows event log analysis33 / 87

DCSync and WMI lateral movement

  • DCSyncImpersonates a DC to replicate hashes via DRSUAPI. Hunt 4662 with GUID 1131f6aa-... or 1131f6ad-... from a non-DC account.
  • DCSync prerequisiteWithout MDI, enable detailed Directory Services auditing on every DC and parse 4662.
  • WMI (T1047)On the target: 4624 LogonType 3, then Sysmon 1 with ParentImage WmiPrvSE.exe.
  • WMI ruleAlert when WmiPrvSE.exe spawns cmd.exe, powershell.exe, mshta.exe or any scripting engine.
Full GUIDs: 1131f6aa-9c07-11d1-f79f-00c04fc2dcd2 and 1131f6ad-9c07-11d1-f79f-00c04fc2dcd2. DCSync is the canonical way to get the KRBTGT hash that a Golden Ticket needs.
HACKTHESOCLesson 08Windows event log analysis34 / 87

A 4662: the DCSync tell, read field by field

  • SubjectUserName is not a domain controller account: that is the anomaly
  • Properties 1131f6ad = Replicating Directory Changes-All (pulls secrets)
  • AccessMask 0x100 is Control Access, the right being exercised
Replication is normal between DCs. The same right exercised from a non-DC computer account is the DCSync signature (T1003.006).

Two shapes of event-log detection

Single-event rules

Fire on something almost never benign.

  • 7045 ImagePath with cmd.exe, powershell.exe or %TEMP%
  • Sysmon 10 on lsass.exe, high GrantedAccess, unexpected source
  • Sysmon 1: Office ParentImage, script engine Image

Correlation rules

Need a sequence on one host or one identity.

  • 4720 then 4728/4732 within minutes
  • 4624 type 3 NTLM, then WmiPrvSE or services.exe spawns a shell
  • Sysmon 11 exe drop, then Sysmon 1 runs it, same ProcessGuid family

Join keys: LogonId (4624 TargetLogonId, reused as SubjectLogonId later) and ProcessGuid / ParentProcessGuid.

These two keys come back again and again in this lesson. The query that follows walks a process tree with ProcessGuid.

Walk a suspect process tree by ProcessGuid

The subsearch finds gen-1 children, then renames their ProcessGuid to ParentProcessGuid so the outer search pulls gen-2.

  • Generation 1 filters Sysmon 1 on the suspect ParentProcessGuid
  • The subsearch renames gen-1 ProcessGuid to ParentProcessGuid
  • So the outer search pulls gen-2: the children of those children

Account and group lifecycle: a backdoor in four events

Quiet individually, because IT does this all day. Read them as a sequence.

HACKTHESOCLesson 08Windows event log analysis42 / 87

Create, elevate, use: the correlation is the finding

Stronger still outside change-control hours, or when the actor is not a legitimate IT admin.
HACKTHESOCLesson 08Windows event log analysis43 / 87

The four-event backdoor pattern, in order

  1. 14720 account createdA new account appears. On its own, this is routine IT work.
  2. 24728 or 4732 group addThe same Subject adds that account to Domain Admins or local Administrators, often minutes later.
  3. 34672 special privilegesThe new account logs on and is assigned sensitive privileges such as SeDebugPrivilege.
  4. 44624 the account is usedIt authenticates somewhere, frequently LogonType 3 to a sensitive host.
No single event is alarming. The sequence, same Subject, same account, minutes apart, is the finding.

HACKTHESOCLesson 08Windows event log analysis45 / 87

Benign new account vs a planted backdoor

Benign

A named user account created through the IT workflow, added to a role group that fits the person's job, with a matching change ticket.

Backdoor

A service-sounding name like svc-printmgmt created by a helpdesk identity and added straight to Domain Admins, with no ticket and outside hours.

The cover name and the actor, not the event type, separate these. 4720 plus a fast group add is the correlation to alert on.

The volume problem: filtering and repeatable hunts

The evidence is rarely missing. It is buried in an ocean of routine noise.

HACKTHESOCLesson 08Windows event log analysis61 / 87

Why volume is the real enemy

The problem

A busy domain emits millions of 4624 and Sysmon 1 events a day. A rule that fires on raw volume drowns the analyst in false positives.

The fix

Filter first on cheap, high-signal fields (account type, host role, LogonType, path), then read only what survives.

The volume problem is why detection engineering is baselining: the filter is where your knowledge of normal lives.
HACKTHESOCLesson 08Windows event log analysis62 / 87

Filter first, read second

  1. 1Filter by Event IDPull just the 4625 failures or the 4728/4732 group changes, not every logon.
  2. 2Filter by field with XPathEvent Viewer and wevtutil filter on contents: an account, a source IP, a target group.
  3. 3Scope by time and hostBound the query to the incident window and the hosts in scope.
  4. 4Stack for outliersAggregate and count: rarest processes, top failing sources, accounts touching most machines.
  5. 5Save the huntA good filter becomes a saved search, scheduled query or detection rule.
A single busy server can generate hundreds of thousands of events a day; a domain generates billions.

AMSI: the chokepoint attackers try to break

What AMSI does

Lets PowerShell, WSH, Office VBA and .NET hand code to Defender or another registered EDR right before execution, even if it never touches disk.

Bypass attempts

Patching AmsiScanBuffer in memory, flipping the amsiInitFailed flag via reflection, or downgrading to the PowerShell v2 engine that predates AMSI.

What you see

Event 400 with EngineVersion 2.0. A 1116 with no 1117 means a detection Defender did not remediate: treat it as still live.

A modern host legitimately running the v2 engine is rare and worth investigating on its own.

  • 4104 logs after decoding, so obfuscation does not hide the real text
Script Block Logging records what actually ran, which is why attackers target the logging itself rather than hope to evade it.

Channels, providers, EVTX and audit policy

Why an Event ID exists at all, and where it lives on disk.

HACKTHESOCLesson 08Windows event log analysis72 / 87

Every event lives in a channel

Security, System (7045, 104) and Application are the big three; Sysmon adds Microsoft-Windows-Sysmon/Operational.

  • SetupWindows Setup and servicing: did an update really install at the claimed time?
  • ForwardedEventsWhere WEF events land on a WEC server. Check it there, not just local Security.
  • Applications and ServicesTaskScheduler, WMI-Activity, Windows Defender, TerminalServices, PowerShell Operational channels.
  • ProvidersSecurity events come from Microsoft-Windows-Security-Auditing; Sysmon has Microsoft-Windows-Sysmon.
Local logs are fragile: destroyed with a wiped or ransomed host, cleared or shrunk by an admin-level attacker, rolled over within days on a busy server. WEF to a collector, or an agent shipping to the SIEM, copies each event off the host as it is written, so the evidence and the 1102 or 104 survive. Sysmon Event ID 1 and Security Event ID 1 are different providers' vocabularies.

EVTX on disk, and the policy that fills it

System32\winevt\Logs

EVTX files

Binary, XML-based, chunked. Copy off a live or dead host and open in Event Viewer, wevtutil, python-evtx or EvtxECmd. Max size commonly 20 MB to 4 GB; default overwrites the oldest.

About 60 subcategories

Advanced Audit Policy

Replaces nine legacy categories. Kerberos Service Ticket Operations drives 4769 independently of Audit Logon for 4624. auditpol /get is the ground truth.

Object-level auditing

SACLs

Put on a sensitive file, key or AD object to emit 4663 on access. Silent unless Audit File System or Audit Registry is also on.

Checklist: confirm the subcategory is enabled on the relevant hosts, especially DCs, for both Success and Failure. Legacy and advanced settings can silently conflict.
HACKTHESOCLesson 08Windows event log analysis75 / 87
A detection is only as good as the audit policy behind it.

If the subcategory that emits an event is off on a host, your rule cannot fire there no matter how well written. Verify coverage per host, then query.

This closes the loop with the coverage slide: policy is the plumbing every rule silently depends on.

Log clearing: 1102 and 104, benign vs malicious

1102 Security cleared

The Security log itself was cleared. Almost never legitimate on a server mid-day, and a strong anti-forensics signal (T1685.005).

104 a channel cleared

A specific channel such as Sysmon/Operational was cleared. Suspicious when it targets the exact channel that would hold the evidence.

A 104 clearing Sysmon with no matching 1102 suggests selective cleanup, not a full wipe.

The pairing is the tell: which channel was cleared, and whether the Security log clear (1102) accompanies it.
HACKTHESOCLesson 08Windows event log analysis80 / 87

Detect log clearing and long-lived network sessions

A network logon that never closes, or persists far longer than the file-share or WMI operation it was for, is a signal. A session ending abnormally may produce only 4634, with no 4647.
