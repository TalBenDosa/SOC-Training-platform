One stolen account opens everything it touches

M365 concentrates the valuable data and the valuable identities in one place.

Mail

The user's Exchange mailbox and calendar: invoices, contracts, password-reset mails, conversations to hijack.

Files

Everything they can reach in OneDrive and SharePoint, often far more than their own documents.

Trust

A real internal mailbox and Teams identity, so the next phish to colleagues comes from inside and looks genuine.

This concentration is why one account takeover is treated as a whole-suite incident, not a mailbox problem. Ask: what could this identity read, and who trusts it?

The attacks that dominate M365 incidents

  • Account takeoverPhishing, password spray or token theft: the entry point for most of the rest.
  • Business email compromiseUsing a real, trusted mailbox to defraud or phish others.
  • Malicious inbox rulesA hidden rule to auto-forward or delete mail, keeping stealthy access to the conversation.
  • OAuth consent phishingTricking a user into granting a malicious app standing access to mailbox and files.
  • Data exfiltrationMass-downloading from SharePoint and OneDrive.
Account takeover is the doorway; the other four are what the attacker does once inside.
HACKTHESOCLesson 67M365 and Microsoft Graph9 / 61

How the dominant attacks chain together

Account takeover is the doorway; the rest is what happens once inside.

  1. 1Take over the accountPhishing, password spray or a stolen token gives the attacker a valid session.
  2. 2Hide in the mailboxA blandly named inbox rule forwards or deletes mail so the owner never notices.
  3. 3Abuse the trustBEC: the real mailbox is used to defraud partners or phish colleagues.
  4. 4Keep standing accessConsent phishing grants a malicious app access that survives a password change.
  5. 5Take the dataMass download from SharePoint and OneDrive.
Not every incident runs every step, but when you find one, look for the others. An inbox rule usually means a takeover came first; a consented app means a password reset will not be enough.

It all happens in the cloud, over legitimate protocols, often from a valid but stolen session. The evidence lives in M365's own records.

This is why the unified audit log and Microsoft Graph are the analyst's essential windows into the suite.

An ordinary operation in a suspicious combination

  • A blandly named rule that forwards mail to an external address
  • DeleteMessage True hides the forwarded mail from the owner
  • ClientIP does not match the user's normal location
Each event has who, what, when (UTC), where from, and target. No single field proves compromise; the combination is the classic hijacked-mailbox fingerprint.
HACKTHESOCLesson 67M365 and Microsoft Graph15 / 61

Same operation, two very different stories

New-InboxRule alone proves nothing. The combination decides.

Ordinary rule

Plenty of users create rules to organise their inbox.

  • Descriptive name for sorting mail
  • Moves mail to an internal folder
  • No external forwarding, no delete
  • Created from the user's usual IP

Hijack fingerprint

None of these alone proves compromise; together they are the classic stealthy-access pattern.

  • Bland name such as "Archive"
  • ForwardTo an external address
  • DeleteMessage True to hide it
  • ClientIP outside the normal location
This is the core analyst skill for the UAL: weigh the combination, not one field. Then confirm with the user's sign-in history for that IP.
HACKTHESOCLesson 67M365 and Microsoft Graph16 / 61

Operations an analyst hunts for

  • New-InboxRule / Set-InboxRuleCreating or modifying mail rules, a top signal of a compromised mailbox.
  • Add-MailboxPermissionSomeone reading a mailbox that is not theirs.
  • File and sharing operationsMass access or external sharing in SharePoint and OneDrive: possible exfiltration.
  • Consent to applicationAlso Add service principal: fingerprints of OAuth consent phishing.
  • UserLoggedInCorrelated with Entra sign-in logs for impossible travel and risky sign-ins.
Two cautions: logging must be enabled and retained before the incident, and for behavioural endpoint or email detail you also use Advanced Hunting.

Hunting mailbox persistence: narrow before you read

  1. 1Set a time windowBound the search to the suspected compromise period, as in any SIEM query.
  2. 2Filter RecordTypeExchangeAdmin, so only admin cmdlets against mail are scanned.
  3. 3Filter OperationNew-InboxRule and Set-InboxRule: a short, reviewable list.
  4. 4Read the ParametersLook for ForwardTo to an external domain and DeleteMessage True.
  5. 5Check the sourceCompare ClientIP with the user's known locations and sign-in logs.
Two filters turn a tenant-wide firehose into a handful of rules. The same pattern works for any workload: RecordType first, then Operation.

Microsoft Graph: one API for everything

If the console is how a human clicks through M365, Graph is how code reads and changes it.

HACKTHESOCLesson 67M365 and Microsoft Graph22 / 61

What an API is, and why Graph matters

  • APIApplication programming interface: a defined way for software to ask a system for data or an action, with no human clicking a screen.
  • Microsoft GraphThe single unified API for almost all of M365. The console is how a human clicks; Graph is how code reads and changes.
  • One endpointgraph.microsoft.com reaches mail, files, calendars, users, groups, devices and security data alike.
  • Access tokens and scopesEvery call carries a token whose granted scopes decide what it may read or change.
Students who know only the portals miss that tools, scripts and attackers' apps all reach the same data through this one API.
HACKTHESOCLesson 67M365 and Microsoft Graph23 / 61

Reading a Graph request piece by piece

  1. 1VerbGET reads; DELETE, POST and others change state.
  2. 2Host and versiongraph.microsoft.com/v1.0, the stable endpoint (beta can change).
  3. 3Resource pathusers/{upn}/mailFolders/inbox/messageRules: one user's inbox rules.
  4. 4Authorization headerBearer <access token>: who is asking, with which scopes.
  5. 5JSON responseResults come back in a value array, one object per item.
Once students can split a URL into these parts, every Graph call in the lesson reads like a sentence.
HACKTHESOCLesson 67M365 and Microsoft Graph24 / 61

The same reach cuts both ways

Defender's tool

Pull sign-ins, list inbox rules, enumerate consented apps, gather externally shared files, programmatically and consistently.

Attacker's surface

In consent phishing, Mail.Read, Files.Read.All and offline_access are Graph scopes. The malicious app calls Graph with tokens, not a password.

Understanding Graph is understanding what a consented app can actually do to a mailbox.
HACKTHESOCLesson 67M365 and Microsoft Graph27 / 61

How consent phishing turns Graph against you

  1. 1A consent promptThe user is tricked into approving a malicious app's permission request.
  2. 2Graph scopes grantedThe app asks for scopes such as Mail.Read, Files.Read.All, offline_access.
  3. 3Tokens, not a passwordThe app receives tokens tied to those scopes.
  4. 4Graph callsIt reads the victim's mail and files through Graph like any legitimate tool.
  5. 5Access persistsIts access is independent of the password, so a reset alone does not end it.
The artefact left behind is an app with a permission grant, not a suspicious sign-in. That is why hunting consented apps is a separate task.
HACKTHESOCLesson 67M365 and Microsoft Graph28 / 61

Delegated versus application permissions

Delegated

The app acts as a signed-in user, limited to what that user could do themselves.

Application

The app acts on its own, tenant-wide, with no signed-in user present. More dangerous if abused.

X.Read reads, X.ReadWrite also changes, .All means across the whole tenant.

An unfamiliar app with broad, application-level mail and file scopes is exactly the artefact consent phishing leaves behind.
HACKTHESOCLesson 67M365 and Microsoft Graph29 / 61

Decode a scope name in four parts

  • X.ReadRead access to resource X, for example Mail.Read.
  • X.ReadWriteRead and change X: Mail.ReadWrite enables tampering, not just theft.
  • .All suffixAcross the whole tenant, not just the signed-in user's own objects.
  • Delegated or applicationThe same scope as an application permission is far more dangerous: no user limits it.
With these four rules a student can rate an unfamiliar scope without memorising the whole list.
HACKTHESOCLesson 67M365 and Microsoft Graph30 / 61

Without it

Can we still see the initial compromise?

  1. 1List affected accountsWhich users were compromised or touched by the attacker.
  2. 2Check each user's licenceE5 or the Purview Audit add-on means Audit (Premium); otherwise Standard.
  3. 3Work out the windowPremium: one year for Exchange, SharePoint, OneDrive, Entra. Standard: 180 days.
  4. 4Check the exceptionsTeams, Power Platform, Defender: 180 days unless a custom policy exists.
  5. 5Compare with the timelineIf the breach began before the window, that evidence is gone.
Run this reasoning per user, because Premium retention is per licensed user, not tenant-wide.

From a single-record lookup to a proactive, tenant-wide hunting platform.

A single-mailbox lookup does not scale to thousands of users. OData parameters turn Graph into a tenant-wide hunting platform.

Read the sign-in hunt clause by clause

  1. 1Pick the collectionauditLogs/signIns: sign-in records.
  2. 2Lower time boundcreatedDateTime ge 2026-08-14T00:00:00Z.
  3. 3Upper time boundcreatedDateTime le 2026-08-15T00:00:00Z: a 24-hour window.
  4. 4Keep the risky onesriskState eq 'atRisk': Identity Protection flagged them.
  5. 5Page the results$top=100, then follow @odata.nextLink for the rest.
The ge and le operators mean greater-or-equal and less-or-equal. Forgetting nextLink silently drops results beyond the first page.
HACKTHESOCLesson 67M365 and Microsoft Graph53 / 61

Bound every sign-in hunt by time

  • An unbounded query against a large tenant's sign-ins will simply time out
  • riskyUsers requires Entra ID P2; run it at shift start as a proactive hunt
  • Large results return @odata.nextLink, which must be followed for the next page
Read the first query top to bottom: sign-ins in this 24-hour window where risk state is atRisk, 100 at a time.

Graph hunts current state, KQL hunts history

Graph OData

Current state of identity, mail and app objects: who is risky now, which rules exist now, which apps are consented now. Then take action.

Advanced Hunting KQL

Raw historical telemetry tables such as DeviceEvents, EmailEvents, IdentityLogonEvents to rebuild the full timeline.

Consent phishing leaves a service principal with an OAuth2 grant, not a sign-in. Hunt servicePrincipals for odd names, recent createdDateTime.

A mature investigation uses both. Red flags on apps: an unfamiliar name, an unusually recent creation date, or a name mimicking a well-known brand.
