Section 1 of 7

The management plane vs the data plane

Managing resources vs using the data inside them. Logged differently, and often separately.

HACKTHESOCLesson 62Cloud audit logs6 / 55

Who changed the locks vs which documents left the cabinet

Logged by default

Management plane

Create a VM, change a permission, open a firewall rule, delete a bucket. Administrative calls about the infrastructure. Where an attacker's structural moves appear.

Often must be enabled

Data plane

Read an object, query rows, invoke a function. Far higher volume and can be costly, so many organisations do not capture all of it.

Data-plane visibility is a coverage decision, made before the incident.

The management plane is always kept; the data plane only if you installed the extra cameras. Knowing which plane your evidence lives in shapes every investigation.

HACKTHESOCLesson 62Cloud audit logs8 / 55

Before answering a data question, check the evidence exists

  1. 1Name the resourceWhich bucket, table, vault or storage account does the question concern?
  2. 2Check what was loggedWere data events or a diagnostic setting configured for that resource?
  3. 3Check whenWas it enabled before the incident window, not after the alert?
  4. 4Look for other sourcesIf not: storage access logs, network flow volumes, application logs.
  5. 5State the gapWrite it in the report and raise it as a coverage fix.
An honest "we cannot prove which objects were read" is better than a guess. The fix after the incident is to turn data logging on for sensitive resources.

Section 2 of 7

CloudTrail architecture: trails and where they live

Whether a trail exists, where it delivers and how long it keeps data decide if evidence exists at all.

HACKTHESOCLesson 62Cloud audit logs10 / 55

Event History is not a trail

Automatic

Event History

The last 90 days of management events in the console. Useful for a quick look; no alerting.

Configured

Trail

Continuously delivers gzip-compressed JSON log files to an S3 bucket, optionally streamed to CloudWatch Logs for near-real-time alerting.

Coverage

Multi-region / organization

A multi-region trail captures every region. An organization trail at the Organizations root captures every account; none can opt out.

Attackers deliberately operating in a region nobody checks is a real evasion tactic, which is why multi-region matters.
HACKTHESOCLesson 62Cloud audit logs11 / 55

How a CloudTrail event reaches the analyst

  1. 1An API call happensConsole, CLI, SDK or an AWS service calls an AWS API.
  2. 2CloudTrail records itThe event appears in Event History for 90 days.
  3. 3The trail batches itEvents are written as gzip JSON files, typically within minutes.
  4. 4Files land in S3One folder per account, region and day.
  5. 5SIEM or CloudWatch reads itAlerting and hunting happen here, not in the console.
Delivery is not instant: allow a few minutes of lag before deciding something did not happen. Without a trail, steps 3 to 5 do not exist.
HACKTHESOCLesson 62Cloud audit logs12 / 55

Where the files land in the S3 bucket

  • Account ID and region are in the path: one folder per region
  • A folder for a region you never use is itself worth opening
  • Each file is gzip JSON holding a Records array of events
Fictional file names in the standard layout. With a multi-region trail every region gets a folder; with a regional trail, activity elsewhere never arrives.

HACKTHESOCLesson 62Cloud audit logs14 / 55

Insights, Azure retention, and the analyst's question

  • CloudTrail InsightsOptional. Flags unusual spikes in call volume or error rates, e.g. a burst of RunInstances. A lead to confirm in raw events.
  • Azure Activity LogKept 90 days automatically. A diagnostic setting routes it to a Log Analytics workspace (KQL), Storage for archive, or Event Hub.
  • Ask every timeIs there a trail covering this account and region, where does it deliver, and how long is it retained?
If a trail was only regional, recently created, or retention already expired, the evidence may not exist. Flag and fix that gap, do not just work around it.
HACKTHESOCLesson 62Cloud audit logs15 / 55

What an Insights event looks like

  • ApiCallRateInsight: call volume left its normal range (ApiErrorRateInsight for errors)
  • Baseline vs insight average: from almost none to about four calls a minute
  • state: Start opens the anomaly; a matching End event closes it
Trimmed, fictional values. An Insight says something unusual happened, not who did it: the next step is to pull the raw RunInstances events in that window and read userIdentity and sourceIPAddress.

Anatomy of a CloudTrail event

Who, what, when, where, and with what result, in a consistent set of fields.

HACKTHESOCLesson 62Cloud audit logs18 / 55

Field reference: what happened, where, how

FieldWhat it tells youWhy it matters
eventTimeWhen the call happened, always UTCAnchors and orders the timeline
eventNameThe exact API action calledThe single most important field: what happened
eventSourceThe service called, e.g. iam.amazonaws.comNarrows which subsystem was touched
awsRegionThe region the action ran inActivity in an unused region is inherently suspect
sourceIPAddressOrigin IP, or an AWS service nameFastest anomaly check against the baseline
userAgentThe tool, SDK or CLI usedaws-cli, an SDK or attacker toolkit vs the console
errorCode / errorMessagePresent only on failure (AccessDenied)A burst = probing what a stolen credential can do
Assemble the fields into a sentence: at this time, this identity, from this IP, using this tool, called this action, and it succeeded or was denied.
HACKTHESOCLesson 62Cloud audit logs19 / 55

Trust what AWS recorded, question what the caller claimed

Recorded by AWS

Set by the service from the authenticated request. Reliable.

  • eventTime, eventSource, awsRegion
  • userIdentity: the credential that signed
  • errorCode: the actual outcome

Supplied by the client

Useful for profiling, but a userAgent can be set to anything, including the console's.

  • userAgent: any string the tool sends
  • requestParameters: what was asked for

sourceIPAddress shows a service name such as ec2.amazonaws.com when an AWS service made the call for you.

A matching userAgent does not clear an event; a mismatching one is still a good lead. Identity and outcome are the fields you can stake a conclusion on.
HACKTHESOCLesson 62Cloud audit logs20 / 55

Field reference: who, targeting what, with what result

FieldWhat it tells youWhy it matters

userIdentity.arnThe caller's full ARNNames precisely who acted
userIdentity.accessKeyIdThe access key used, if anyPins the exact credential, vital when a key is stolen

eventID is a unique GUID for the event, a stable handle to cite the exact record in a ticket.
HACKTHESOCLesson 62Cloud audit logs21 / 55

A self-granted admin, read as one sentence

  • A service account attached AdministratorAccess to itself
  • Unfamiliar IP, CLI instead of the console it normally uses
  • No errorCode: the call succeeded
Every clause of the narrated sentence is one field. The combination is what makes this single line jump off the screen. The full event also has awsRegion us-east-1, responseElements null, readOnly false (a change) and an eventID.

Azure records the same idea under different names

Azure Activity Log

Management activity across the subscription.

  • Operation name: the action
  • Caller and Caller IP address
  • Status: success or failure
  • Event category, Resource, timestamp

Entra logs

Sign-in and identity events live alongside in the Entra sign-in and audit logs.

Same analytic move in both clouds: actor, action, origin, outcome. Does that combination make sense for this identity?

Students who learn the AWS fields first can map them onto Azure in minutes; the concepts do not change.

Section 4 of 7

Reading the Azure Activity Log with KQL

Query the Log Analytics workspace instead of scrolling the portal one event at a time.

HACKTHESOCLesson 62Cloud audit logs25 / 55

Who made the most successful changes in the last day?

  • Bound the time window, keep only successful calls
  • Operation names embed the verb (.../WRITE, .../DELETE), so a substring match finds changes
  • summarize is the stats / GROUP BY instinct from other SIEMs
KQL is the same language used across Azure Monitor, Sentinel and Defender. The result is a short table to scan for an unfamiliar caller or IP.
HACKTHESOCLesson 62Cloud audit logs26 / 55

The query, one line at a time

LineWhat it does
AzureActivityStart from the Activity Log table in the workspace
where TimeGenerated > ago(24h)Bound the window to the last 24 hours
where ActivityStatusValue == "Success"Keep only calls that worked; harmless failures drop out
where OperationNameValue has "write" or ... "delete"Keep changes and removals; the verb is part of the name
summarize count() by Caller, CallerIpAddress, ...Collapse to one row per caller, IP and operation
order by count_ descBusiest first, so outliers are easy to scan
The same narrow-then-read rhythm as SPL or SQL. The output is small enough to read in full, which is the point.
HACKTHESOCLesson 62Cloud audit logs27 / 55
Activity Log tells you what changed. The Entra ID sign-in log tells you how the caller authenticated.

UserPrincipalName, IPAddress, AppDisplayName, ConditionalAccessStatus, and a risk level from Entra ID Protection.

A resource change by a caller whose sign-in was flagged risky is a far stronger signal than either fact alone.
HACKTHESOCLesson 62Cloud audit logs28 / 55

Joining a change to a risky sign-in

  • risky: users Entra ID Protection scored medium or high in the last day
  • Keep only successful changes made by those same users
  • Each row pairs "how they signed in" with "what they changed"
For a user, Caller holds the user principal name, which is what makes this join work. Service principals appear by ID and need a different join.
HACKTHESOCLesson 62Cloud audit logs29 / 55

Activity Log categories: two carry the weight

Administrative

Every create, update, delete and action through Azure Resource Manager, plus all Azure RBAC role changes. The primary hunting ground.

Security

Alerts and events raised by Microsoft Defender for Cloud. Ready-made detections to correlate against raw activity.

The rest

ServiceHealth, ResourceHealth, Alert, Autoscale, Recommendation, Policy. They mostly help you exclude benign explanations.

ServiceHealth rules out a platform outage, Autoscale explains sudden resource-count changes, Policy shows when a guardrail blocked a change, Recommendation is posture guidance not evidence.

Section 5 of 7

Hunting patterns in the activity log

Baseline each identity, alert on deviation, confirm by correlation.

HACKTHESOCLesson 62Cloud audit logs33 / 55

Five hunts with the highest value

  • EnumerationMany List/Describe calls (ListUsers, GetAccountAuthorizationDetails) in a short window, often with AccessDenied.
  • Escalation and persistenceCreateUser, CreateAccessKey, AttachUserPolicy, UpdateAssumeRolePolicy; Azure Owner or User Access Administrator grants.
  • Anomalous originUnusual IP, country, region or User-Agent. A workload role now calling from an external IP suggests SSRF-stolen credentials.
  • Attack-goal resource actionsRunInstances in an unused region, mass deletion of backups, snapshots shared to an external account.
  • Suspicious authenticationImpossible travel, anonymising IPs, root or Global Admin console logins.
GuardDuty and Defender for Cloud encode many of these patterns and are excellent leads, but you confirm and scope in the raw activity log.
HACKTHESOCLesson 62Cloud audit logs34 / 55

Building a baseline for one identity

  1. 1Pick the identityOne user, role or service principal, by its ARN or Caller.
  2. 2Learn where it comes fromUsual source IPs and user agents over the last 30 days.
  3. 3Learn what it doesThe set of eventNames or operations it normally calls.
  4. 4Learn when and whereUsual hours and regions.
  5. 5Alert on departuresA new IP, new action, new region or odd hour is a lead.
  6. 6Correlate before escalatingSeveral departures together turn a lead into an incident.
Service accounts have the tightest baselines, which is why they make the best detections: almost any change is meaningful.
HACKTHESOCLesson 62Cloud audit logs35 / 55

Actions this identity has never made before

  • The inner query is the 30-day baseline of this identity's actions
  • The outer query keeps only actions from the last day not in that set
  • For svc-reporting, any IAM write here is worth an immediate look
An Athena-style query over a CloudTrail table. The same "new for this identity" logic works for source IPs and regions.
HACKTHESOCLesson 62Cloud audit logs36 / 55

Alert-worthy events by ATT&CK stage

StageAWS eventNameAzure equivalent
Initial AccessConsoleLogin (esp. root or a service account)Interactive sign-in for a non-interactive identity
DiscoveryListUsers, ListBuckets, ListRoles, Describe* bursts with AccessDeniedMicrosoft.Authorization/.../read bursts, directory enumeration
PersistenceCreateUser, CreateAccessKey, CreateLoginProfile, UpdateAssumeRolePolicyAdd service principal / app credential, add owner
Privilege EscalationAttachUserPolicy, PutUserPolicy, AddUserToGroup, AttachRolePolicyAssign Owner or User Access Administrator
Defense ImpairmentStopLogging, DeleteTrail, UpdateTrail, PutBucketPublicAccessBlock (off)Delete/modify diagnostic setting, disable Defender for Cloud
Credential AccessGetSecretValue, GetParameter (SSM), GetPasswordDataKey Vault SecretGet, KeyList bursts
Exfiltration / ImpactCreateSnapshot + ModifySnapshotAttribute, unused-region RunInstances, mass Delete*Disk snapshot share, unusual VM creation, bulk delete

Any one row can be benign. Several stages, in sequence, from one unfamiliar origin, is the incident.

Memorise the shape, not every name. Persistence means a way back in that survives a password reset; escalation is a low-privilege identity granting itself admin.
HACKTHESOCLesson 62Cloud audit logs37 / 55

Rule out the benign story before you escalate

Common benign explanations

Each has a check: a change ticket, the engineer, the scanner's known IPs.

  • A new automation or pipeline went live
  • An engineer travelling or on a new VPN
  • Planned onboarding: new users and keys
  • A security scanner enumerating on schedule

What breaks the benign story

Any of these moves the case from "lead" to "incident".

  • No ticket and the owner did not do it
  • Several ATT&CK stages from one origin
  • A service account behaving like a human
  • Logging changed in the same window
Writing the benign hypothesis down and testing it is what makes the final verdict defensible, either way.

Narrating it as a story

  1. 1What kind of identity?svc-reporting is a service account. A ConsoleLogin is already a raised eyebrow.
  2. 2Is the source normal?Baseline is the reporting server's fixed IP; 41.203.88.12 breaks it.

Section 7 of 7

When the attacker attacks the logs

Here the act of disabling logging, or the absence of logs, is the alarm.

HACKTHESOCLesson 62Cloud audit logs45 / 55

Going dark, in each cloud

AWS

Explicit API calls against CloudTrail.

  • StopLogging: turn a trail off
  • DeleteTrail
  • UpdateTrail: weaken or redirect
  • Disable or delete the log storage

Azure

MITRE: Disable or Modify Cloud Log (T1685.002, formerly T1562.008), under Impair Defenses (Defense Impairment).

  • Disable diagnostic settings
  • Delete or modify Log Analytics workspaces
  • Turn off Defender for Cloud
With logging off, data theft and resource creation leave no management-plane trail. The window until discovery is the attacker's cover.
HACKTHESOCLesson 62Cloud audit logs46 / 55

The act of going dark is itself an event

  • cloudtrail.amazonaws.com acting on itself: the trail is being turned off
  • Same identity and IP as the escalation three minutes earlier
  • Record the time: everything after it may be missing from this trail
Fictional continuation of the worked case. This last event before the silence is the one to alert on immediately.
HACKTHESOCLesson 62Cloud audit logs47 / 55

EventEffectSeverity cue

UpdateTrailChanges destination, regions or settingsCheck what changed: e.g. multi-region turned off

Not every change is a full stop: a quieter attacker narrows what is captured. That is why UpdateTrail and PutEventSelectors deserve alerts too.
HACKTHESOCLesson 62Cloud audit logs48 / 55

Hunting diagnostic-setting changes in Azure

  • Diagnostic settings decide where Azure logs go; changing them can blind you
  • DELETE stops the flow; a WRITE can quietly redirect it
  • Compare Caller and IP with the platform team's change records
The Azure counterpart of alerting on StopLogging and UpdateTrail.
HACKTHESOCLesson 62Cloud audit logs49 / 55

Turn the tampering against the attacker

StopLogging and its kin are themselves recorded.

  • Alert on any changeStop, delete or modify logging: top priority, regardless of who did it.
  • Alert on gapsA trail that goes silent when it normally is not is suspicious.
  • Protect integrity by designDeliver to a separate, access-restricted account or immutable store; log all regions; tightly limit who can disable logging.

Your telemetry is itself a target. Monitor the pipeline, not just the logs.

This echoes protecting Windows event logs on-prem. An attempt to go dark becomes the event that lights them up.
HACKTHESOCLesson 62Cloud audit logs50 / 55

Detecting a trail that went silent

  1. 1Know the normal rateBusy accounts log events every minute; quiet ones less often.
  2. 2Track last event timePer account and region, record when the latest event arrived.
  3. 3Alert on silenceNo events for longer than normal is a lead, even with no tampering event.
  4. 4Check the trail statusGetTrailStatus: is IsLogging true, is delivery recent?
  5. 5Escalate the gapTreat unexplained silence as an incident until it is explained.
Silence catches what a tampering alert can miss, for example a broken pipeline or a destination bucket the attacker made unwritable.
HACKTHESOCLesson 62Cloud audit logs51 / 55

Key takeaways

  1. 01Management-plane calls are logged by default; data-plane reads are high-volume and must be enabled before an incident.
  2. 02Event History is 90 days with no alerting; a multi-region or organization trail to S3 is what makes evidence durable.
  3. 03Read a CloudTrail event as one sentence: eventName, userIdentity, sourceIPAddress, userAgent, region, errorCode.
  4. 04Azure mirrors it: Operation, Caller, Caller IP, Status, category; query it with KQL and pair it with Entra sign-ins.
  5. 05Hunt by baseline and deviation, and confirm by correlation: one identity moving through several ATT&CK stages.
  6. 06StopLogging, DeleteTrail and diagnostic-setting changes are top-priority alerts; protect log integrity by design.
