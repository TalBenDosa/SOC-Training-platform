The family: credentials someone left reachable

Distinct from active dumping (T1003): here nothing has to be broken open.

HACKTHESOCLesson 95Where credentials hide6 / 38

Two families, two different log sources

T1003

Active dumping

Actively reads material from a store the OS deliberately protects: LSASS memory, the locked SAM/NTDS.dit, the replication protocol.

  • Met in earlier lessons
  • Not repeated here

T1552 and T1555

Exposed or stored

Nothing is broken open. T1552 finds a secret left reachable by convenience. T1555 reaches a vault, or its unlock key, not its cryptography.

  • This lesson
  • Tactic: Credential Access TA0006

Confusing the two families sends an analyst to the wrong log source entirely.

T1552 examples: a plaintext password in a config file, a passphrase-less private key, a GPP XML with a decryptable password. T1555 examples: the macOS Keychain, a browser's saved-password DB, a cloud secrets manager.

Credentials in files and Group Policy Preferences

T1552.001 and T1552.006: secrets left in plain sight for convenience.

HACKTHESOCLesson 95Where credentials hide11 / 38

Where plaintext secrets actually live

  • App configuration.env, appsettings.json, web.config, database.yml, often a connection string with a plaintext password.
  • Automation and CI/CDAnsible vars, Jenkinsfiles, .gitlab-ci.yml, Terraform .tfvars, often holding cloud credentials.
  • Shell history.bash_history, PowerShell ConsoleHost_history.txt: a password typed once on a command line stays indefinitely.
  • Source codeA hardcoded API key committed to a public or private Git repository.
  • Malware collectionTrickBot modules harvest saved credentials from Outlook, FileZilla, OpenSSH, WinSCP configs; LaZagne automates dozens of apps.
Attackers find these with an ordinary recursive text search for words like password. Reading a file is unremarkable by design, which is why host telemetry here is thin.
HACKTHESOCLesson 95Where credentials hide12 / 38

Group Policy Preferences: encryption with a public key

T1552.006, a specific and historically damaging case of files hiding credentials.

The mechanism

GPP once pushed local-account passwords to many machines via files like Groups.xml in SYSVOL, 'encrypted' with AES-256.

Why it fails

Microsoft published that AES key in its own docs. Any domain user can read SYSVOL and decrypt the cpassword value. The cipher is not broken, the key is simply public.

The lingering gap

MS14-025 (2014) stopped setting new cpassword values. It did not purge old XML files already in SYSVOL, so they stay findable for years.

This is why a cpassword attribute dated after the patch is still a live risk: the patch is not retroactive and the key was never changed.
HACKTHESOCLesson 95Where credentials hide13 / 38

What the defender watches for, not the search

  • Reading a file leaves almost no host trace, so catch it at commit, at the share, or by sweep
  • A confirmed exposure means the secret is compromised: rotate it
The strongest signals here are preventive and content-based, not host-access logs. Stress the rotation rule: deletion alone assumes the secret was never read.

Private keys: SSH, TLS and cloud credential files

T1552.004: the secret half of a key pair grants access with no guessing.

HACKTHESOCLesson 95Where credentials hide15 / 38

Key file types an analyst should recognize

ExtensionTypical use
.pem, .keyGeneric PEM-encoded private key (TLS, SSH or application)
.ppkPuTTY's own private-key format, saved by Windows SSH users
.p12, .pfxPKCS#12 bundle: private key plus certificate, often password-protected
.pgp, .gpg, .ascGPG/PGP key material or encrypted messages
.cer, .p7bCertificates (public side, but often stored beside the private key)
SSH keys live by convention in ~/.ssh (id_rsa, id_ed25519). Cloud CLI files are a close cousin: ~/.aws/credentials holds long-lived key pairs in plaintext, and losing it is as good as losing a private key.
HACKTHESOCLesson 95Where credentials hide16 / 38
A well-configured private key is itself encrypted with a passphrase, so stealing the file alone is not enough.

The attacker must still recover the passphrase by offline cracking. That converts an instantly usable credential into one that buys time for detection and rotation.

This is why passphrase-protect your keys is real advice, not theater. An unprotected key grants immediate, direct access with no further step.
HACKTHESOCLesson 95Where credentials hide17 / 38

The highest-fidelity signature in the lesson

  • Legitimate key use flows through the SSH client, not a text editor or an archiver
  • A key-block string in a commit or upload is the single highest-fidelity tell here
Walk the content signature first: it is provider-agnostic and almost never a false positive. The behavioral tell matters because the file read itself is otherwise invisible.

A .kdbx file, an answer file with a password, or an autologon DefaultPassword is an exposed secret. Rotate it.

Exactly like any other exposed credential: you cannot know who already read it.

Raiding the macOS Keychain and other stores

T1555: unlock one vault and every credential inside it comes at once.

HACKTHESOCLesson 95Where credentials hide22 / 38

macOS ships three keychains

T1555.001, the built-in encrypted credential vault.

Login keychain

Per-user, holds most saved passwords, Wi-Fi and app tokens at ~/Library/Keychains/login.keychain-db. Unlocked automatically at login, because its password matches the account password by default.

System keychain

OS-level items shared across users.

Local / iCloud

Credentials synced across a user's own Apple devices.

The login keychain unlocking automatically at login is the key fact: an attacker with a live session already has it open.
HACKTHESOCLesson 95Where credentials hide23 / 38
Keychain theft usually follows a captured login password from an earlier stage.

Extracting a secret needs the vault already unlocked, or the login password supplied. A spoofed reauthentication dialog is a textbook way to capture that password first.

This lesson's angle is the second half of the chain: once an attacker has a live shell or the login password, one keychain dump turns it into every other saved credential.
HACKTHESOCLesson 95Where credentials hide24 / 38

Detecting keychain and password-store access

  • It is the parent process and the sequence that betray theft, not the access itself
  • Chrome/Edge Login Data is SQLite encrypted with an OS key: DPAPI or the Keychain
Tie browser stores back to the Keychain case: the detection logic is identical, legitimate owner process versus a foreign reader. LaZagne and SharpChrome automate the browser side.

When the vault itself is a cloud API call

T1555.006 and T1552.005: reach the secret, or skip it entirely for the role credential.

HACKTHESOCLesson 95Where credentials hide26 / 38

How a cloud identity reaches the vault

  1. 1An app retrieves a secretVia an authenticated API call, not a file on disk: a real improvement over plaintext configs.
  2. 2The problem shiftsEverything now rests on one question: who may call that API, and is the permission scoped tightly?
  3. 3A compromised identity calls itget-secret-value, keyvault secret show, secrets versions access: the same call the app makes.
  4. 4Real intrusions do thisHAFNIUM pivoted on-prem to steal Azure Key Vault secrets; Shai-Hulud swept Secrets Manager across accounts.
The call always needs an identity already permitted to make it, usually obtained from an earlier stage in this same chain, a leaked key or an over-permissioned role.
HACKTHESOCLesson 95Where credentials hide27 / 38
The metadata API hands out a role's temporary credentials with no secrets-manager call at all.

T1552.005: a process queries link-local 169.254.169.254 and gets the instance's IAM credentials. The 2019 Capital One breach: SSRF reached IMDSv1. AWS answered with IMDSv2.

The point for detection: this leaves no CloudTrail Secrets Manager entry, because the metadata service is not a logged management-plane API. Posture check: enforce IMDSv2 (HttpTokens: required) fleet-wide and watch the CloudWatch MetadataNoToken metric; any non-zero value flags an instance still open to blind-SSRF credential theft.

Why a volume threshold fails, and what works

  • Baseline who reads what, not how many: count rules drown in legitimate bursts
  • A honeytoken secret turns any read into a high-confidence alert
This is the detection-engineering heart of the lesson: separating an application's routine secret access from an attacker's comes down to the identity-and-secret pairing, not raw volume.

Section 7 of 7

NTDS.dit telemetry, and a cross-store detection program

One file-access tell for the ultimate store, then five practices that span the whole lesson.

HACKTHESOCLesson 95Where credentials hide31 / 38

Why reading NTDS.dit needs a workaround

  1. 1It holds every hashThe Active Directory database on every DC, with the password hash of every account in the domain.
  2. 2The live file is lockedC:\Windows\NTDS\ntds.dit is held exclusively by AD DS while the DC runs. Nobody can copy it directly.
  3. 3Extraction routes through VSSA Volume Shadow Copy snapshot exposes the locked file as a readable copy at a shadow-copy device path.
  4. 4That path is the tellNo routine DC process reads NTDS through a shadow-copy device path. An attacker's extraction does.
The extraction commands are taught in the sibling dumping lesson. Here we only need the shape: live file locked, so every method goes through a snapshot.
HACKTHESOCLesson 95Where credentials hide32 / 38

Reading a 4663 record on the domain controller

  • SYSTEM reading the LIVE path continuously is routine AD DS operation
  • A named account reading the shadow-copy path once, off-hours, is the escalate case
Contrast the two: SYSTEM on the live path all day is the service itself; one named-admin read of the device path is the extraction. The detection only exists where SACL auditing was turned on first.
HACKTHESOCLesson 95Where credentials hide33 / 38

Five controls that span every store in this lesson

  • Continuous secret-scanningSource-control commits and endpoint/file-share sweeps catch T1552.001/.004/.006 before an attacker searches.
  • Short-lived credentialsCloud IAM roles and managed identities over static keys and files shrink the T1552.004/.005 surface.
  • Honeytokens everywhereA canary file, private key and cloud secret no legitimate process reads: any access is a high-confidence alert.
  • Baseline who reads whatBefore any volume threshold: CI/CD, autoscaling and backups burst legitimately.
  • Rotate on any exposureNever just delete or revoke access to the copy found.
No single control catches every technique here, because each store has its own legitimate access path. You can never be certain how many times a credential was already read before you found it.
HACKTHESOCLesson 95Where credentials hide34 / 38

Key takeaways

  1. 01T1552 and T1555 reach a secret already exposed, or a vault via its own path, not a store the OS protects. Tactic: Credential Access TA0006.
  2. 02Files (T1552.001) and GPP (T1552.006) are caught by scanning and DLP. GPP cpassword uses a public AES key; MS14-025 is not retroactive.
  3. 03A private key grants immediate access unless passphrase-protected. A BEGIN PRIVATE KEY string where it should not be is the top signature.
  4. 04Password stores (Keychain, browsers, Credential Manager, KeePass): unlock one vault, get every secret. Watch for a foreign parent process.
  5. 05T1552.005 leaves no secrets-manager trail; GuardDuty InstanceCredentialExfiltration.OutsideAWS flags role credentials used outside AWS.
  6. 06NTDS.dit extraction routes through a Volume Shadow Copy. A 4663 shadow-copy device path in ObjectName is the tell, if SACL auditing is on.

Check your understanding, question 1 of 3

A Groups.xml file in SYSVOL contains a cpassword attribute, dated well after MS14-025 was applied domain-wide. Is this still a live risk, and why?

MS14-025 stopped new cpassword values going forward. It does not purge or re-encrypt files already in SYSVOL, and the public AES key never changed. A file timestamp is not proof of origin; either way it remains decryptable.

An application's database credentials were used by an unfamiliar process, but an exhaustive CloudTrail search finds zero secretsmanager:GetSecretValue calls around the breach. What does this strongly suggest?
