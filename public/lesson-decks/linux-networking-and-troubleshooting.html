Section 1 of 9

Interfaces and addresses with ip

An interface is the kernel's handle for one network attachment. The tool to read it is ip from iproute2.

HACKTHESOCLesson 101Linux host networking6 / 54

UP and LOWER_UP are two different facts

Read the flags in angle brackets before anything else.

state UP

UP and LOWER_UP

The interface is administratively enabled and the layer below has carrier. This is the healthy state.

    state DOWN or NO-CARRIER

    UP, no LOWER_UP

    Enabled, but nothing is on the other end: an unplugged cable, a dead switch port, or a disconnected virtual NIC in the hypervisor.

      administratively down

      No UP flag at all

      Someone or something ran ip link set down. The interface is switched off in software.

        UNKNOWN state is normal for lo and some virtual devices.

        Interfaces can be physical (eth0, ens18, enp3s0), wireless (wlan0) or virtual (lo, docker0, br0, veth, tun0, wg0). Warn students not to confuse enabled with connected.
        HACKTHESOCLesson 101Linux host networking7 / 54

        Reading one interface, left to right

        ip -br link and ip -br addr give one brief line per interface. This is the full detail.

        • UP is enabled, LOWER_UP is carrier. mtu 1500 is standard Ethernet
        • link/ether is the MAC, the layer 2 identity
        • dynamic plus valid_lft: the address came from DHCP and expires unless renewed
        The /24 tells the kernel which addresses are local. The inet6 fe80:: address is link-local and not routable beyond the segment. Every IPv6-enabled interface has one.
        HACKTHESOCLesson 101Linux host networking8 / 54

        Four signals that point straight at a cause

        • 169.254.x.x addressThe host gave up on DHCP and self-assigned a link-local address. Look at the DHCP server or the VLAN.
        • No inet line at allNo address was ever configured.
        • Rising errors, dropped, overrunCheck ip -s link. Points to a bad cable, duplex mismatch, ring buffer exhaustion or a saturated host.
        • Large transfers hangThe classic MTU mismatch: small requests work. Tunnels and some cloud networks use 1450 or 1420 instead of 1500.
        Each of these is diagnostic by itself, before you run another command. Counters tell you whether the link is healthy under load.
        HACKTHESOCLesson 101Linux host networking9 / 54

        Old ifconfig habits and their ip equivalents

        Old runbooks still use net-tools, which is often not installed and sees only part of the picture.

        Old habitModern equivalent
        ifconfigip addr, ip -br addr
        ifconfig eth0 upip link set eth0 up
        ifconfig eth0 10.0.0.5/24ip addr add 10.0.0.5/24 dev eth0
        arp -aip neigh
        route -nip route

        Runtime changes vanish at reboot. Never take down the only interface over SSH without console access.

        Persistent configuration belongs to NetworkManager (nmcli), systemd-networkd, netplan on Ubuntu or ifupdown. Downing the only interface cuts off the session you need to bring it back up.

        The routing table and longest prefix match

        Every outgoing packet asks the kernel one question: which interface and which next hop? ip route answers it.

        HACKTHESOCLesson 101Linux host networking11 / 54

        Each route line is a rule: destination, then how to reach it

        • Connected route: made by the kernel, no via, delivered directly using ARP
        • Default route (0.0.0.0/0): the gateway must itself be on a connected network
        • linkdown on docker0: the bridge has no active ports, normal with no containers
        proto dhcp tells you who installed the default route. src is the source address the kernel puts on packets using that route. Metric breaks ties: lowest wins, so Wi-Fi at 600 and Ethernet at 100 can send traffic out an unexpected interface.
        HACKTHESOCLesson 101Linux host networking12 / 54

        Longest prefix match: the most specific route wins

        A packet to 10.50.3.7 with these three routes in the table:

        most specific

        10.50.3.0/24

        Matches 10.50.3.7 with the longest prefix, so this route is used.

          also matches

          10.50.0.0/16

          Loses to the /24 because it is less specific.

            last resort

            default

            Used only when nothing more specific matches.

              Order in the table is irrelevant. Metric only breaks ties between equally specific routes.

              A common wrong answer is that the default route is tried first or that insertion order matters. Neither is true. Confirm any argument with ip route get.
              HACKTHESOCLesson 101Linux host networking13 / 54

              Ask the kernel instead of guessing the path

              • via present: off-link, the packet goes to the gateway
              • No via: on-link, the host ARPs for the destination directly
              • FAILED or INCOMPLETE: ARP got no reply, a layer 2 problem
              REACHABLE and STALE are fine, STALE only means not recently confirmed. If your gateway entry is FAILED, the problem is layer 2, not routing. Policy routing (ip rule) and rp_filter can silently drop replies on multi-homed hosts.
              HACKTHESOCLesson 101Linux host networking14 / 54

              The error message itself narrows the cause

              Four messages, four different failures.

              MessageMeaning
              connect: Network is unreachableNo route matches the destination; typically the default route is missing
              No route to hostA route exists, but ARP failed or an ICMP unreachable came back
              Connection timed outPackets left but nothing came back: drop, filter or dead path
              Connection refusedThe host answered with a TCP reset: it is up but nothing listens, or a REJECT rule exists

              Forwarding between interfaces needs net.ipv4.ip_forward set to 1: routers, VPN gateways, container hosts.

              Teach students to read the message before touching anything. Timed out and refused are the pair they will meet most often.

              Section 3 of 9

              Name resolution: hosts, nsswitch, resolv.conf, resolved

              Most 'the network is down' reports are really name resolution failures. Learn the real path a name takes.

              HACKTHESOCLesson 101Linux host networking16 / 54

              The path a name takes through the C library

              The first source that answers wins.

              1. 1Application calls getaddrinfo()Used by ping, curl, ssh and most daemons.
              2. 2glibc reads /etc/nsswitch.confThe hosts line defines the order of sources.
              3. 3files: /etc/hostsAn entry here overrides DNS for every C library program.
              4. 4resolve: systemd-resolvedLocal stub listener at 127.0.0.53, configured per interface.
              5. 5dns: /etc/resolv.confThe classic resolver: up to three nameservers, tried in order.
              Walk the nsswitch line aloud: hosts: files mymachines resolve [!UNAVAIL=return] dns. That ordering is why a hosts entry beats DNS.
              HACKTHESOCLesson 101Linux host networking17 / 54

              The three files that decide a lookup

              • files comes first, so a hosts entry beats DNS
              • search appends domains: ssh db01 is tried as db01.corp.example
              • 127.0.0.53 is the resolved stub: do not edit the file, it is overwritten
              The options line can include ndots. Kubernetes pods commonly use ndots:5, which makes a lookup of api.partner.com generate several wasted queries before the real one.
              HACKTHESOCLesson 101Linux host networking18 / 54

              resolvectl status shows DNS per interface

              • Per-interface settings make split DNS possible
              • A routing domain such as ~corp.example sends only those names to the corporate resolver
              • A VPN adding its own link and DNS explains: internal names resolve only on VPN
              Companion commands: resolvectl query shows which link and server answered, resolvectl flush-caches clears the local cache after a DNS change, resolvectl statistics shows cache hits and DNSSEC counters.
              HACKTHESOCLesson 101Linux host networking19 / 54

              getent and dig take different paths

              The most important diagnostic distinction in name resolution.

              same path as the application

              getent hosts name

              Goes through the full NSS path exactly as applications do. Honors /etc/hosts and nsswitch order.

                straight to a DNS server

                dig, host, nslookup

                Talk to a DNS server directly. Ignore /etc/hosts and nsswitch.

                  getent works, dig does not: look for a hosts entry. dig works, getent fails: check nsswitch, resolv.conf or the resolved link.

                  This is why a name can work in ping and curl yet return NXDOMAIN in dig, or the reverse. Questions to ask: which source answered, which server was asked, and is a cached answer hiding a recent change?

                  Section 4 of 9

                  Querying DNS with dig, host and nslookup

                  dig asks a DNS server a precise question and shows its raw answer, so you can reason about it.

                  HACKTHESOCLesson 101Linux host networking21 / 54

                  Reading a dig answer

                  • Read status first, then flags, then the counts
                  • Answer columns: name, TTL, class, type, data. TTL counts down in a cache
                  • SERVER and Query time show who answered and how slowly
                  qr is a response, rd means recursion was requested, ra means the server offers it. aa appears only when the answering server owns the zone, so its absence means a resolver or cache answered. A CNAME pointing to a name that does not exist is a common misconfiguration.
                  HACKTHESOCLesson 101Linux host networking22 / 54

                  The header status tells you what kind of failure this is

                  StatusWhat it means
                  NOERRORThe query worked
                  NXDOMAINThe name does not exist
                  SERVFAILThe server could not get an answer: upstream failure, broken DNSSEC validation, lame delegation
                  REFUSEDThe server will not answer you (access control)
                  NOERROR, zero answers (NODATA)The name exists but has no record of that type, such as AAAA on an IPv4-only host

                  On NXDOMAIN and NODATA the AUTHORITY section carries the SOA, whose minimum field sets negative caching (RFC 2308).

                  Slow DNS often looks like a slow application, so check Query time as well. The AUTHORITY section is empty on a positive answer.
                  HACKTHESOCLesson 101Linux host networking23 / 54

                  The dig options you will actually use

                  host and nslookup are shorter front ends for one-liners (host -t MX example.com, nslookup api.example.com 1.1.1.1). nslookup is considered legacy on many systems. None of the three consults /etc/hosts.
                  HACKTHESOCLesson 101Linux host networking24 / 54

                  Timed out is a network problem, SERVFAIL is a DNS problem

                  Two failures that look similar in the application.

                  ;; no servers could be reached

                  communications error

                  You never reached the resolver: routing, firewall, or the server is down. This is a network problem.

                    resolver reached

                    status: SERVFAIL

                    You reached the resolver and it failed internally. This is a DNS problem.

                      Ask two servers and compare. Internal answers but public gives NXDOMAIN, or the reverse: split DNS or a stale cache.

                      If all servers agree but the answer is wrong, the record itself is wrong. This is the technique students should reach for first when a name misbehaves.

                      Section 5 of 9

                      Connectivity testing: ping, traceroute, mtr

                      Interface, route and name look sane. Now test whether packets actually flow.

                      HACKTHESOCLesson 101Linux host networking26 / 54

                      What each part of a ping tells you

                      • time: under 1 ms on a LAN, 10 to 30 ms in a country, 100 ms or more across oceans
                      • ttl 57 from a likely start of 64 suggests about 7 hops: a hint, not proof
                      • High mdev (jitter) means an unstable path
                      Initial TTL defaults: commonly 64 for Linux and macOS, 128 for Windows, 255 for many network devices. Intermittent loss points to congestion, a bad link or Wi-Fi. Steady 0 percent is healthy.
                      HACKTHESOCLesson 101Linux host networking27 / 54

                      ICMP blocked does not mean host down

                      Silence from ping is ambiguous. Test the real protocol.

                      Ping fails

                      Many firewalls, cloud security groups and hardened servers drop echo requests while serving TCP perfectly.

                        Ping works

                        Ping only proves IP-level reachability. The service itself can still be dead.

                          Test the real protocol

                          Check that the actual service answers.

                          • nc -zv 203.0.113.25 443
                          • curl -sI https://203.0.113.25 -k --connect-timeout 5
                          • sudo traceroute -T -p 443 203.0.113.25
                          Never conclude it is down from a failed ping alone. The traceroute -T variant traces using TCP SYN to port 443.
                          HACKTHESOCLesson 101Linux host networking28 / 54

                          traceroute shows where a path breaks

                          Probes carry increasing TTL (1, 2, 3, ...). Each router that reaches zero reveals itself.

                          • Each router returns ICMP Time Exceeded when TTL reaches zero
                          • * * * with later hops answering: the router filters ICMP, harmless
                          • Stars forever: the path breaks at or after the last answering hop
                          Remember the return path can differ from the forward path (asymmetric routing), so a trace is evidence, not proof.
                          HACKTHESOCLesson 101Linux host networking29 / 54

                          Error messages and the other path tools

                          • Destination Host UnreachableFrom your own IP: ARP failed locally. From a router's IP: that router has no route.
                          • Network is unreachableYour own routing table has no matching route.
                          • tracepathWorks without root and also reports the path MTU.
                          • mtr -rwn -c 50 203.0.113.25Ping plus traceroute. Loss at one middle hop only is ICMP rate limiting. Loss continuing to the end is real.
                          • ping -M do -s 1472 hostDo-not-fragment test. A reply at 1472 bytes (1500 on the wire) but not larger shows the MTU limit.
                          The mtr rule is the one students get wrong most. Clean downstream hops prove the traffic passed through, so a lossy middle hop is not a real problem.

                          Section 6 of 9

                          Ports and sockets: ss, netstat and lsof

                          If the host can reach the destination, ask: is something listening, and which process owns the port?

                          HACKTHESOCLesson 101Linux host networking31 / 54

                          ss -tulpn: who is listening, on which address

                          Flags: t TCP, u UDP, l listening only, p process, n numeric (no lookups). Add a for all states.

                          On a LISTEN socket Recv-Q is the current accept queue and Send-Q its maximum backlog. Recv-Q persistently near Send-Q means the app is not calling accept() fast enough. Without root the Process column is empty, which is not the same as no process.
                          HACKTHESOCLesson 101Linux host networking32 / 54

                          Local Address decides who can connect

                          Local AddressWho can connect
                          127.0.0.1:8080Only processes on this host. Remote clients get Connection refused though the service runs
                          0.0.0.0:22All IPv4 addresses of the host
                          [::]:443All IPv6 addresses; normally IPv4 too (dual-stack) unless the app set IPV6_V6ONLY
                          10.20.5.14:5432Only that specific address

                          Works on the server but not from outside: the fix is the application's bind setting, not the firewall.

                          A service on loopback while clients connect from elsewhere is probably the single most common cause of the works-on-the-server bug. This column causes the most outages.
                          HACKTHESOCLesson 101Linux host networking33 / 54

                          Refused is instant, timed out is slow

                          The client-side error already points to the cause.

                          returns immediately

                          Connection refused

                          The host answered with a TCP RST: nothing listens on that address and port, or a firewall REJECT rule exists.

                            takes tens of seconds

                            Connection timed out

                            Packets are silently discarded: firewall DROP, security group, wrong route or dead host.

                              Listening correctly but remote clients fail? Check nft list ruleset, iptables -S, ufw status, firewall-cmd --list-all.

                              After the host firewall, check any network firewall or cloud security group between the hosts. For Address already in use (EADDRINUSE), find the holder with ss -ltnp and decide which of the two to stop or reconfigure.
                              HACKTHESOCLesson 101Linux host networking34 / 54

                              Targeted ss queries and the older tools

                              Once you have a PID, ps -fp 1450 and systemctl status 1450 tie it back to a service unit. ss reads kernel data directly and replaces netstat.

                              Section 7 of 9

                              Talking to services: curl, openssl s_client, nc

                              A port that accepts connections can still serve the wrong thing. Test above layer 4.

                              HACKTHESOCLesson 101Linux host networking36 / 54

                              curl -v is a ladder: see how far the request climbed

                              • was resolved: DNS worked
                              • Trying then Connected: TCP worked. Stuck at Trying means packets are dropped
                              • 503 with retry-after: layers 1 to 6 are fine, the server problem looks temporary
                              Knowing exactly how far the ladder got is the entire point. The TLS lines show protocol and certificate, and the final status line is the application's answer.
                              HACKTHESOCLesson 101Linux host networking37 / 54

                              Timing variables and exit codes name the failing layer

                              Use -w timing variables to find the slow phase, and exit codes in scripts.

                              SignalMeaning
                              Large time_namelookupDNS is slow
                              Large time_connectThe network is slow
                              Large gap before time_starttransferThe server is thinking
                              curl exit code 6Could not resolve host
                              curl exit code 7Failed to connect
                              curl exit code 28Timeout
                              curl exit code 35 or 60TLS handshake failure, or certificate not trusted

                              Status classes: 2xx success, 3xx redirect (-L), 4xx client error, 5xx server error (502 and 504 are gateway failures).

                              401 and 403 are authentication and authorization, 404 is the wrong path, 429 is a rate limit. Check http_proxy, https_proxy and no_proxy too: a proxy can cause a failure no direct network test reveals.
                              HACKTHESOCLesson 101Linux host networking38 / 54

                              curl options that isolate one layer at a time

                              --resolve pins a name to an address, bypassing DNS while keeping the correct Host header and TLS name. That lets you separate a DNS problem from a server problem.
                              HACKTHESOCLesson 101Linux host networking39 / 54

                              Checking the certificate and probing a port

                              • -servername sends SNI. Without it a multi-site server may return the wrong cert
                              • Verify return code 20: missing intermediate or CA. Code 10: expired
                              • nc: -z sends no data, -v verbose, -w timeout. Success means the TCP handshake completed
                              Also check the system clock: a skewed clock makes valid certificates look expired. If nc is missing, bash can probe with timeout 3 bash -c with /dev/tcp. UDP checks (nc -zvu) are unreliable because silence is also what an open UDP port looks like.

                              Section 8 of 9

                              Watching traffic with tcpdump

                              When tools disagree or only say 'timed out', look at the packets themselves.

                              HACKTHESOCLesson 101Linux host networking41 / 54

                              Four habits: pick the interface, filter hard, skip lookups

                              • -i picks the interface (any loses link-layer detail). -nn skips name lookups
                              • host, net, port, src, dst, joined with and, or, not, form the capture filter
                              • -c stops after a count, -w writes a pcap for Wireshark, -r reads one back
                              -nn also prevents tcpdump from generating its own DNS traffic. Use -A or -X for payload only when you must, and treat capture files as sensitive: they may hold credentials and personal data.
                              HACKTHESOCLesson 101Linux host networking42 / 54

                              A failing DNS lookup on the wire

                              Three identical queries, growing gaps, no response. The resolver or the path to it is not answering.

                              Nothing in the application can fix this. The host is asking, and nobody replies. Note the same query ID and the 1 and 2 second gaps.
                              HACKTHESOCLesson 101Linux host networking43 / 54

                              TCP flags tell the story of a connection

                              [S] SYN, [S.] SYN-ACK, [.] ACK, [P.] data, [F.] FIN, [R] or [R.] RST.

                              What you seeWhat it means
                              [S] repeated at about 1, 2, 4 seconds, no replySYN is dropped: firewall DROP, security group, bad route or dead host
                              [S] followed immediately by [R.]Host is up but nothing listens, or a REJECT rule: Connection refused
                              [S], [S.], [.] then data, then long silenceHandshake fine; the application or a later device is the problem
                              Many [P.] repeated with the same sequence numbersRetransmissions: packet loss on the path, or an MTU blackhole
                              [R] arriving mid-connectionSomething (server, firewall, IPS) is tearing the session down
                              This table is the one to memorize. It maps directly onto the timed out versus refused pair from the sockets section.
                              HACKTHESOCLesson 101Linux host networking44 / 54

                              Capture on the correct side, and capture responsibly

                              Which side you see

                              tcpdump sees packets before the host firewall evaluates them. SYN arrives but no SYN-ACK leaves: local firewall or app. No SYN at all: the network before the host.

                                Both ends

                                Capturing on both ends and comparing is the strongest technique.

                                  Operational care

                                  Always use a filter, a count or time limit, and a disk with free space. On busy servers rotate with -C and -W and write to a file.

                                    Run as root or with the appropriate capability.

                                    Incorrect cksum warnings on outbound packets are checksum offload to the NIC and are harmless. Warn students so they do not chase them.

                                    A layered method and a worked example

                                    Walk up the stack and stop at the first layer that fails. Each step proves a layer healthy or isolates the fault.

                                    HACKTHESOCLesson 101Linux host networking46 / 54

                                    Layers 1 to 4: link, address, gateway, path

                                    LayerCommandHealthy signIf it fails
                                    1 Link: up with carrier?ip -br link, ip -s linkUP and LOWER_UP, no errorsCable, switch port, vNIC, driver
                                    2 Address: right IP?ip -br addrExpected inet and prefixDHCP, static config, 169.254 address
                                    3 Gateway: next hop?ip route, ip neigh, ping GATEWAYDefault route, gateway REACHABLEMissing route, VLAN, ARP failure
                                    4 Path: beyond my LAN?ping IP, mtr, tracerouteReplies, sane RTTRouting, upstream filtering

                                    Change one thing at a time, note what you did, and compare against a known-good host.

                                    Each step either proves a layer healthy so you never revisit it, or isolates the fault. This is the discipline that makes the method fast.
                                    HACKTHESOCLesson 101Linux host networking47 / 54

                                    Layers 5 to 8: DNS, port, TLS, application

                                    LayerCommandHealthy signIf it fails
                                    5 DNS: name resolves, via whom?getent hosts, resolvectl query, digExpected addressResolver down, split DNS, hosts override
                                    6 Port: TCP connects?nc -zv, curl -v, ss on the targetConnectedFirewall drop, refused, wrong bind
                                    7 TLS: certificate OK?openssl s_client, curl -vverify okExpired, missing CA, SNI, clock
                                    8 Application: answers right?curl -i, logsExpected 2xxApp error, auth, rate limit
                                    Always test what the application actually does: same name, same port, same user, same proxy settings. A test that differs from the real path proves nothing.
                                    HACKTHESOCLesson 101Linux host networking48 / 54

                                    Worked example: app01 cannot reach the partner API

                                    app01 (10.20.5.14) fails to reach https://api.partner-example.com. The log only says connection error.

                                    1. 1Steps 1 to 3: link, address, gatewayens18 UP at 10.20.5.14/24, route via 10.20.5.1, gateway REACHABLE, ping works.
                                    2. 2Step 4: pathping 1.1.1.1 replies at 9 ms, so this is not a general outage.
                                    3. 3Step 5: DNSgetent exits 2, dig to 10.20.5.2 times out, dig @1.1.1.1 returns 203.0.113.80.
                                    4. 4Fix DNS, keep evidenceResolver 10.20.5.2 is down; 10.20.5.3 answers. resolvectl dns ens18 10.20.5.3 fixes it.
                                    5. 5Step 6: portnc to 203.0.113.80:443 times out. tcpdump shows SYN retransmissions, no SYN-ACK.
                                    6. 6Locate the droptraceroute -T dies at hop 2, the site firewall. nft allows 443 out, so the drop is upstream.

                                    Hand off destination, port, source address, timestamps, tcpdump lines and the traceroute.

                                    Two failures were stacked: a dead resolver and a dropped egress path, probably a missing allow rule for the partner address. A report with that evidence is resolved in minutes, while 'the API is not working' is not. Always ask what changed recently.
                                    HACKTHESOCLesson 101Linux host networking49 / 54

                                    The evidence behind steps 5 and 6

                                    • Exit 2: not found. dig times out: a network failure, not NXDOMAIN or SERVFAIL
                                    • A public resolver answers: the name exists, the configured resolver is unreachable
                                    • A timeout, not a refusal: packets are dropped somewhere along the path
                                    The same nc from another subnet's host succeeds, which separates a path problem from a destination problem. Test the port by IP to keep DNS out of the variables.
                                    HACKTHESOCLesson 101Linux host networking50 / 54

                                    Key takeaways

                                    1. 01UP means enabled and LOWER_UP means carrier: UP without LOWER_UP points at the cable, switch port or virtual NIC.
                                    2. 02The kernel uses the longest matching prefix, and ip route get shows the exact interface, gateway and source address.
                                    3. 03getent hosts follows the real application path, while dig skips /etc/hosts and nsswitch. Use both to find overrides.
                                    4. 04A failed ping proves little because ICMP is often blocked. Test the real protocol with nc, curl or traceroute -T.
                                    5. 05Connection refused is instant (RST, nothing listening, loopback bind). Timed out means packets are silently dropped.
                                    6. 06Walk link, address, gateway, path, DNS, port, TLS, application. Stop at the first failure and hand off specific evidence.
                                    HACKTHESOCLesson 101Linux host networking51 / 54

                                    Check your understanding, question 1 of 3

                                    The table has default via 10.20.5.1, 10.50.0.0/16 via 10.20.5.254 and 10.50.3.0/24 via 10.20.5.8. Where does a packet for 10.50.3.7 go?

                                    The kernel picks the most specific match, so the /24 beats the /16 and the default. Insertion order is irrelevant, the default is a last resort, and only metric breaks ties between equal routes. Confirm with ip route get 10.50.3.7.

                                    Choose an answer, or press R to reveal it.

                                    HACKTHESOCLesson 101Linux host networking52 / 54

                                    Check your understanding, question 2 of 3

                                    ping db01 and curl http://db01 work because /etc/hosts maps db01 to 10.20.5.30, but dig db01.corp.example returns NXDOMAIN. Why?

                                    Applications use getaddrinfo and the nsswitch order, where files comes before dns; dig never reads the hosts file. NXDOMAIN is a definite answer about the name, not an intermittent fault or host state. Use getent hosts to test the app path.

                                    Choose an answer, or press R to reveal it.

                                    HACKTHESOCLesson 101Linux host networking53 / 54
