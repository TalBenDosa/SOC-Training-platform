Start here: what the cloud actually is

Four words the rest of the lesson assumes you already have.

HACKTHESOCLesson 11Cloud security for the SOC6 / 76

Four terms you will use constantly

  • The cloudSomeone else's data center, rented by the hour. AWS, Azure and GCP rent you slices of real servers over the internet.
  • RegionA geographic location such as us-east-1 (Northern Virginia) or eu-west-1 (Ireland), chosen for latency and data residency.
  • IAMIdentity and Access Management: the users, roles and permissions that decide who may do what. The entire access-control layer.
  • CloudTrail / Activity LogThe searchable log of every API call: who did what, when, from where. Often the only evidence that exists.
The one picture: your data lives in someone else's rented data center, split across regions, guarded by IAM permissions, with every action recorded by CloudTrail.
HACKTHESOCLesson 11Cloud security for the SOC7 / 76

Cloud and region in plain words

The cloud

Someone else's data center, rented by the hour. AWS, Azure and GCP own the servers; you rent a slice over the internet instead of racking your own.

A region

A specific geographic data-center cluster like us-east-1. You choose it for latency and data residency, and it rides along on almost every cloud log.

The servers still exist, in a real building; they just belong to someone else and you reach them over the internet. That removes most of the mystery.

Shared responsibility: provider vs you

Security of the cloud is the provider's job. Security in the cloud is yours.

HACKTHESOCLesson 11Cloud security for the SOC11 / 76

The split shifts with the service model

EC2, Azure VM

IaaS

Provider: physical host and hypervisor. You: guest OS, patching, apps, network rules. Closest to on-prem.

App Service, Beanstalk, RDS

PaaS

Provider also patches the OS and runtime. You: application code, data, access configuration.

M365, Salesforce, Workspace

SaaS

Provider runs nearly everything. You: data, users and how access is configured.

The provider's slice grows up the stack, but yours never reaches zero.

Every provider publishes an explicit responsibility matrix per service. Knowing where to find it is a practical SOC skill.
HACKTHESOCLesson 11Cloud security for the SOC12 / 76

Security of the cloud versus security in the cloud

LayerProvider secures (of)You secure (in)
Physical and hypervisorYesNo
Guest OS and patchingPaaS and SaaS onlyIaaS: yours
Your data and configNoAlways yours
Who has access (IAM)NoAlways yours
As you move IaaS to PaaS to SaaS the provider's slice grows and yours shrinks, but identity, config and data never reach zero.
HACKTHESOCLesson 11Cloud security for the SOC13 / 76

Who owns which layer

Identity and data handling never leave the customer column, and that is exactly where most real breaches occur.
HACKTHESOCLesson 11Cloud security for the SOC14 / 76
"The cloud is secure" is a dangerously incomplete sentence.

A public S3 bucket of customer records is not an AWS failure. AWS provided the controls; someone in your organization did not apply them.

First question on any cloud incident: which side of the line? An unpatched hypervisor is a provider failure; a public-read bucket policy is yours, and it changes the root-cause conversation with leadership.
HACKTHESOCLesson 11Cloud security for the SOC15 / 76

Which side of the line is this incident?

  1. 1Name the service modelIaaS, PaaS or SaaS decides how much the provider secured for you.
  2. 2Locate the failureAn unpatched hypervisor is a provider failure; a public bucket is a config failure you owned.
  3. 3Set the root causeThe answer changes both your incident response and the conversation with leadership.
Knowing this stops you hunting hypervisor attacks that essentially never surface, and points you at identity, config and data every time.

Section 4 of 12

Identity is the new perimeter

Valid credentials with the right permissions reach everything, from anywhere.

HACKTHESOCLesson 11Cloud security for the SOC21 / 76

Three IAM primitives

User

Persistent identity for a human or service, often with a long-lived access key and secret. Leaked, it stays valid until rotated.

Role

Temporary identity something assumes for a limited time. Credentials expire in minutes or hours. The preferred direction.

Policy

The JSON permission document of allowed and denied actions on resources, attached to a user, group or role.

Keys leak into public GitHub repos, client-side JavaScript, CI/CD logs, container images and phished laptops. Scanners hunt them, and abuse often follows within minutes.
HACKTHESOCLesson 11Cloud security for the SOC22 / 76

User, role, policy: the three IAM primitives

PrimitiveWhat it isWhy it matters
UserA persistent identity, often with long-lived keysA leaked key can be valid indefinitely until rotated
RoleA temporary identity something assumesCredentials expire in minutes to hours, far safer
PolicyA JSON document of allowed/denied actionsAttached to a user, group or role, the actual permission
The industry push is toward roles and temporary credentials over long-lived user keys, because the key is the top real-world compromise vector.
HACKTHESOCLesson 11Cloud security for the SOC23 / 76

Privilege escalation through IAM

The cloud's version of Windows token abuse. A low-privilege service account attaching AdministratorAccess to itself from an unfamiliar IP is escalation, not routine admin work.
HACKTHESOCLesson 11Cloud security for the SOC24 / 76

An IAM policy-attach event: benign or escalation

Benign

An admin identity, from a known IP, attaches a scoped policy during a change window, consistent with its six-month history.

Escalation in progress

A low-privilege service identity attaches AdministratorAccess to itself from an unfamiliar IP, having never done so before. Treat it like Windows token abuse.

A CloudTrail event showing an identity attaching a policy to itself, or creating a key for another user, deserves the scrutiny of a token-impersonation alert.
HACKTHESOCLesson 11Cloud security for the SOC25 / 76
The first cloud triage question is not what host, but what identity, and is this normal for it?

A service role that called three APIs for six months and suddenly calls CreateAccessKey beats almost any network indicator.

Identity behavior baselining is the cloud equivalent of host-based baselining on-prem. Most of your investigative attention belongs here.
HACKTHESOCLesson 11Cloud security for the SOC26 / 76

Baseline the identity before you judge the call

  1. 1Ask what identityThe first cloud triage question is not what host, but what identity performed this action.
  2. 2Pull its historyA role that called three actions for six months, suddenly calling CreateAccessKey, is a sharp deviation.
  3. 3Compare to normalIs the behavior consistent with its pattern? The deviation is worth more than the event itself.
Identity behavior baselining is the cloud equivalent of host-based behavior baselining on-prem, and it is where most of your attention belongs.

Anatomy of a cloud credential compromise

A stolen key moves through a recognizable chain within minutes.

HACKTHESOCLesson 11Cloud security for the SOC28 / 76

From leaked key to impact

  1. 1Leaked access keyFound in a public repo.
  2. 2Authenticate to the APIDirectly, with the owner's rights. No exploit needed.
  3. 3Recon callsListBuckets, GetCallerIdentity to orient.
  4. 4Privilege escalationAttachUserPolicy to self.
  5. 5Disable loggingStopLogging, if the attacker is disciplined.
  6. 6ImpactExfiltration or cryptomining.
Placing a CloudTrail event on this chain tells you both what already happened and what to expect next.
HACKTHESOCLesson 11Cloud security for the SOC29 / 76

A stolen key does not sit unused

Within minutes

A leaked key authenticates directly to the cloud API with the same rights its owner had. No further exploit is needed at all.

The disciplined attacker

Orients with read-only recon, reaches for broader permissions, then blinds the audit trail before doing anything destructive.

Automated scanners trawl public repos for keys; the time from a key being pushed to it being abused is often measured in minutes.
HACKTHESOCLesson 11Cloud security for the SOC30 / 76

StageCloudTrail tellWhat it means
AuthenticateGetCallerIdentityThe key works and reveals the identity held

Section 6 of 12

The cloud audit trail

CloudTrail and Azure Activity Log: often the only record of what happened.

HACKTHESOCLesson 11Cloud security for the SOC32 / 76

What every CloudTrail event records

  • eventNameThe API action, like CreateAccessKey or PutBucketPolicy.
  • eventTime, eventSourceWhen, and which service, e.g. s3.amazonaws.com.
  • userIdentityUser, role or assumed-role session, plus account and access key ID.
  • sourceIPAddress, userAgentWhere and how the call originated.
  • requestParametersWhat was asked for; responseElements is what happened.
  • errorCode / errorMessagePopulated when a call was denied.

Azure Activity Log is the parallel (operationName, caller, resourceId, status); GCP Cloud Audit Logs are the third-provider equivalent.

Azure Activity Log is parallel: operationName, caller, resourceId, status and correlation IDs. Entra ID sign-in and audit logs track identity events separately.
HACKTHESOCLesson 11Cloud security for the SOC33 / 76

A CloudTrail event, field by field

  • eventName plus eventSource say what action, on which service
  • userIdentity is who; sourceIPAddress is from where
  • errorCode null means the call succeeded, not a near-miss
Every CloudTrail event carries this consistent shape. With no hosts to image, this is frequently the only record of what happened.
HACKTHESOCLesson 11Cloud security for the SOC34 / 76

Anatomy of a StopLogging event

Walk the call-outs field by field, then point out that no single field convicts; the sequence does.
HACKTHESOCLesson 11Cloud security for the SOC35 / 76

Management events vs data events

Management events

Control-plane actions: creating a user, changing a security group, modifying a bucket policy. Logged by default, low volume.

Data events

Object-level operations like every S3 GetObject and PutObject, or Lambda invocations. Opt-in, high volume, costly, often off.

A missing object-level log may mean the feature was never enabled, not that the attacker covered tracks.

Know this before you investigate a suspected S3 exfiltration, so you do not misread a logging gap.
HACKTHESOCLesson 11Cloud security for the SOC36 / 76
StopLogging deserves the same urgency as a ransomware alert.

Attackers disable logging only when they are about to do something they do not want recorded. Alert on it from a path they cannot also disable.

Many organizations replicate CloudTrail to a separate account so even full control of the primary account cannot erase the record. Investigation pattern: pull all events for the userIdentity, order by time, read auth, recon, escalation, impact.
HACKTHESOCLesson 11Cloud security for the SOC37 / 76

Read a caller's events as a narrative

  1. 1Pull by identityGather every event for the relevant userIdentity or caller, ordered by time.
  2. 2Find authenticationThe session opens; a stolen key often starts with GetCallerIdentity.
  3. 3Then recon, then escalationListBuckets or DescribeInstances, then AttachUserPolicy or a new key.
  4. 4Then impactThe action that caused harm. Read it like a process tree on an endpoint.
The audit trail rarely lies about what was called; your job is to decide whether the calling identity's behavior is normal.

Has this identity ever called ListBuckets before?

In 90 days it only called GetObject and PutObject on one bucket, nightly, and never from 198.51.100.23. The baseline made the case.

This is where a junior analyst stops looking and a trained one keeps going. Any one of these calls could be a real admin; the combination from a new IP is not.
HACKTHESOCLesson 11Cloud security for the SOC42 / 76

Contain immediately, do not wait and see

  1. 1Disable the access keyCut the stolen credential off.
  2. 2Revoke active sessionsFor the compromised identity.

HACKTHESOCLesson 11Cloud security for the SOC43 / 76

errorCode null versus AccessDenied

errorCode null

The call succeeded. A successful privilege escalation is an active compromise, not a near-miss. Contain now.

errorCode AccessDenied

The call was blocked. Still worth noting for detection tuning, and as a sign of what the attacker was reaching for.

Read errorCode on every escalation event. It is the difference between they did it and they tried.

Section 8 of 12

Exposure by configuration

Most cloud breaches are misconfigurations, not exploits.

HACKTHESOCLesson 11Cloud security for the SOC45 / 76

Misconfigurations that need zero exploitation

Public object storage

Bucket policy or ACL grants read or write to everyone. Internet-wide scanners enumerate bucket names and find it.

Open management ports

Security group allows 22 (SSH) or 3389 (RDP) from 0.0.0.0/0. Probed within hours, then brute-forced.

Excessive IAM

Wildcard grants like "Action": "*". Turns one compromised function into a full-account compromise.

Shared snapshots

RDS or EBS snapshots shared with all instead of one account ID.

Speed is the cloud's power and its risk: a developer can make a bucket public in seconds. AWS S3 Block Public Access exists because this was so common.
HACKTHESOCLesson 11Cloud security for the SOC46 / 76

Three misconfigurations that need no exploit

MisconfigurationWhy it is dangerousThe fix
Public S3 bucketAnyone who guesses the name reads itBlock Public Access, default-deny
Security group 0.0.0.0/0 on 22/3389Internet-wide SSH/RDP, brute-forced in hoursRestrict the source ranges
Wildcard IAM on a functionAmplifies any foothold massivelyLeast privilege, scoped actions
None of these needs a vulnerability or a stolen credential, just a permission set incorrectly and a scanner or opportunist who found it.
HACKTHESOCLesson 11Cloud security for the SOC47 / 76

Hunting the top misconfigurations

Other recurring errors: managed databases with public endpoints and default credentials, and serverless functions granted wildcards because a developer did not diagnose a permission error.
HACKTHESOCLesson 11Cloud security for the SOC48 / 76
Shift left: find the exposure before an attacker or scanner does.

Cloud Security Posture Management (CSPM) continuously checks for public buckets, open security groups and excessive permissions.

That shift, from what happened after the breach to what exposure exists right now, separates a mature cloud program from one that is always reacting.
HACKTHESOCLesson 11Cloud security for the SOC49 / 76

Shift left: hunt exposure before the scanner does

  1. 1Scan configuration continuouslyCSPM checks for public buckets, open security groups and wildcard permissions.
  2. 2Prioritize the internet-facingOpen 22 or 3389 to the world is a top-priority finding to remediate fast.
  3. 3Fix before exploitationMove attention from what happened after a breach to what exposure exists right now.
Because misconfiguration is the dominant root cause, continuous configuration monitoring is often higher-leverage than incident response.

HACKTHESOCLesson 11Cloud security for the SOC53 / 76

Two patterns that turn one flaw into account access

IMDS / SSRF

The metadata service at 169.254.169.254 hands an instance its role credentials. An SSRF flaw lets an attacker request them. IMDSv2 needs a session token via PUT.

OAuth consent abuse

A phished user grants a malicious app OAuth permissions. Access survives a password reset. Revoke the grant, not just the password.

Junior analysts frequently miss the OAuth revocation step. After any cloud-hosted web app compromise, check the instance role's CloudTrail activity right after.

Container and Kubernetes security

A thinner wall between the workload and the host.

HACKTHESOCLesson 11Cloud security for the SOC56 / 76

Kubernetes building blocks

  • PodSmallest deployable unit: containers sharing network and storage.
  • NodeMachine that runs pods, managed by the kubelet.
  • API serverThe front door. Every action passes through it and can be logged.
  • etcdKey-value store of cluster state; in misconfigured clusters, plaintext secrets.
  • NamespaceLogical partition; the closest thing to a boundary, far weaker than a VM.
Containers share the host kernel and are isolated by namespaces and cgroups, not a hypervisor. That is why escape is a realistic category.
HACKTHESOCLesson 11Cloud security for the SOC57 / 76

A container is not a VM

VM isolation

A hypervisor separates the VM from its host, a boundary hardened over decades of engineering.

Container isolation

Kernel namespaces and cgroups, a far thinner wall. A --privileged container or a hostPath mount erases it (T1611, Escape to Host).

A compromised container's other moves are T1610 Deploy Container, T1613 Discovery and T1612 Build Image on Host, the containerized echo of CloudTrail recon.
HACKTHESOCLesson 11Cloud security for the SOC58 / 76

ATT&CK containers techniques to recognize

IDTechniqueWhat it looks like
T1611Escape to HostPrivileged pod or hostPath mount to the host root filesystem
T1610Deploy ContainerAttacker stands up own pod, often a DaemonSet on every node
T1613Container and Resource DiscoveryEnumerating pods, nodes and secrets via the API
T1612Build Image on HostBuild locally to evade registry-pull monitoring
Kubernetes RBAC is separate from cloud IAM. A ClusterRoleBinding granting cluster-admin is the analogue of IAM escalation, and readable secrets can hold cloud keys.
HACKTHESOCLesson 11Cloud security for the SOC59 / 76

A privileged pod in the Kubernetes audit log

  • A CI service account that never created a privileged pod before
  • privileged: true plus hostPath sets up T1611
  • The K8s equivalent of AttachUserPolicy to AdministratorAccess
Treat it like CloudTrail: pull every event for the identity, order by time, look for recon then escalation.
HACKTHESOCLesson 11Cloud security for the SOC60 / 76

Investigate a container compromise like CloudTrail

  1. 1Use the Kubernetes audit logThe API-server equivalent of CloudTrail: caller, verb, target object, source IP, response code.
  2. 2Pull every event for the identityOrder by time and read the same recon-then-escalation pattern.
  3. 3Watch RBAC grantsA ClusterRoleBinding to cluster-admin is the Kubernetes analogue of IAM escalation.
A pod that can read secrets across namespaces can pivot straight into cloud IAM keys if those secrets hold access keys.

HACKTHESOCLesson 11Cloud security for the SOC62 / 76

Data protection: encryption, KMS, secrets

Whether unauthorized access automatically means readable data.

HACKTHESOCLesson 11Cloud security for the SOC67 / 76

Envelope encryption in KMS

  1. 1A data key encrypts the dataFast symmetric encryption of the bulk data.
  2. 2The CMK encrypts the data keyThe customer master key lives in KMS and never leaves it.
  3. 3Decrypt goes through KMSCaller sends the encrypted data key; KMS unwraps it and returns the plaintext key.
  4. 4Every unwrap is loggedDecrypt and GenerateDataKey appear in CloudTrail with the caller.
Encryption in transit is close to universal by default; encryption at rest is easy but not always on. An unencrypted volume is worth flagging even if never exposed.
HACKTHESOCLesson 11Cloud security for the SOC68 / 76

Envelope encryption: two keys, one logged

The data key

A fast symmetric key encrypts the bulk data. It is itself encrypted by the slower master key.

The customer master key

Held in KMS, tightly access-controlled, and never leaves it. Every use to unwrap a data key is logged in CloudTrail.

This is why a kms:Decrypt call by the attacker's identity matters: encryption at rest is meaningless if the stolen credentials could also unwrap the key.
HACKTHESOCLesson 11Cloud security for the SOC69 / 76

Could the attacker read what they stole?

  • errorCode: null: the compromised identity could decrypt
  • The attacker had the door key and the safe key
'The data was encrypted' is a different finding from 'encryption stopped this attacker'. Always check kms:Decrypt in the trail.

Secrets management fixes key leakage

AWS Secrets Manager, Azure Key Vault, HashiCorp Vault.

  • Never in source controlApps fetch secrets at runtime via an authenticated API call, not a hardcoded file.
  • Every retrieval loggedYou can see which identity pulled which secret and when.
  • Automatic rotationShrinks a leaked secret's valid window from months to days or hours.
Add two questions to every data-exposure checklist: was it encrypted at rest, and did the compromised identity hold kms:Decrypt on that key?

Key takeaways

  1. 01Security of the cloud is the provider's; security in it is yours, and identity, config and data are where breaches happen.
  2. 02Identity is the perimeter: a leaked key or IAM escalation path can beat an RCE exploit.
  3. 03CloudTrail and Activity Log record every control-plane call; StopLogging deserves ransomware-tier urgency.
  4. 04Most cloud breaches are misconfigurations: public buckets, 0.0.0.0/0 rules, wildcard IAM.
  5. 05Know the confirming fields for impossible travel, cryptomining, S3 exfil, IMDS/SSRF and OAuth abuse.
  6. 06Encryption only protects data if the attacker cannot also call kms:Decrypt.

The compromised identity successfully called kms:Decrypt on the bucket's KMS key just before downloading the encrypted objects. What does this tell you?

Envelope encryption only protects data if the holder cannot also unwrap the key. The CMK never left KMS, but KMS decrypted for the attacker because the identity was authorised. TLS protects data on the wire from third parties, not from an authorised caller.
