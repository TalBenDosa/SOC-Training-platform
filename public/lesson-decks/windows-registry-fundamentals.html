Behind almost every setting on Windows sits the Registry.

From the wallpaper to which programs start at boot, it is a map of how a system is configured and a prime place for attackers to survive a reboot.

The Registry is both evidence of a system's state and a hunting ground for footholds. Both halves run through the lesson.

Section 1 of 9

What the Registry is

A central, hierarchical database of configuration for Windows and everything on it.

HACKTHESOCLesson 71Windows Registry6 / 51

A settings database, not a single file

  • What it storesConfiguration for the OS, hardware, installed apps and user preferences: millions of settings.
  • The analogyA giant, organised settings filing cabinet for the whole computer.
  • Always in useInstalls write to it, boot reads it, a setting change lands in it, usually unseen by the user.
  • How you view itregedit presents it as a browsable tree, much like folders and files.
Students picture one file. Stress that it is a live, constantly read-and-written database, which is why its current state is evidence.
HACKTHESOCLesson 71Windows Registry7 / 51

Two reasons the Registry matters to security

Think of it as a giant settings filing cabinet that programs read and write constantly.

It controls what runs

Write to the right place and malware launches automatically, or a security setting weakens, all through configuration.

It survives reboots

Memory-only code dies at restart. A Registry entry that relaunches malware at boot gives persistence.

Most Registry activity is invisible: installs write to it, boot reads it, setting changes land in it. regedit shows it as a browsable tree.

Section 2 of 9

Hives, keys and values

Three levels of structure, like a filing system.

HACKTHESOCLesson 71Windows Registry9 / 51

Where a setting lives and what it is

Hives

The top-level branches the whole tree is divided into.

Keys

Containers, like folders, nesting many levels: HKEY_LOCAL_MACHINE\Software\Microsoft\Windows.

Values

The settings themselves, like files. Each has a name, a type and data.

A key is where a setting lives; a value is the setting.
HACKTHESOCLesson 71Windows Registry10 / 51

Read any Registry path in three parts

  1. 1HiveThe leftmost branch: whole machine (HKLM) or one user (HKCU)?
  2. 2Key pathThe folders in between, nesting down to the setting.
  3. 3ValueThe setting itself: a name, a type, and its data.
  4. 4Why it helpsYou can judge scope and privilege from the path alone, before looking anything up.
Walk the class through HKLM\Software\Microsoft\Windows out loud: machine-wide, inside Microsoft's software settings.
HACKTHESOCLesson 71Windows Registry11 / 51

The five hives, and the two that matter most

HiveAbbreviationWhat it holds
HKEY_LOCAL_MACHINEHKLMSystem-wide settings for the whole machine and all users
HKEY_CURRENT_USERHKCUSettings for the currently logged-on user
HKEY_USERSHKUSettings for all user profiles on the machine
HKEY_CLASSES_ROOTHKCRFile associations and program registrations
HKEY_CURRENT_CONFIGHKCCThe current hardware profile
HKLM normally needs admin rights; HKCU can be changed by the user. Which one persistence lands in hints at the attacker's privilege level.
HACKTHESOCLesson 71Windows Registry12 / 51

Which hive it lands in hints at the attacker's access

HKLM write

Affects the whole machine and normally needs administrator rights, so a change here suggests privileged access.

HKCU write

Affects only the current user and needs no admin, so persistence here suggests user-level access only.

This read is free and immediate: the hive in a persistence path is a first clue to how far the attacker has climbed.

Registry value types

The type tells Windows, and you, how to interpret the bytes.

HACKTHESOCLesson 71Windows Registry14 / 51

Six value types to recognise

TypeMeaningTypical use
REG_SZFixed, null-terminated stringPlain text settings, file paths
REG_EXPAND_SZString with environment variables like %AppData%Paths that resolve per user or machine
REG_MULTI_SZA list of strings in one valueE.g. several DLLs to load
REG_DWORD32-bit numberFlags, often 0 = off, 1 = on
REG_QWORD64-bit numberLarger integers, timestamps, sizes
REG_BINARYRaw binary shown as hexHardware data, or a smuggled encoded payload

Fileless case: where a short path belongs, a large REG_BINARY or an oversized base64 REG_SZ is a smuggled payload.

Be suspicious of REG_BINARY, or an oversized REG_SZ, where a short setting should be: large high-entropy data fits the fileless payload technique.
HACKTHESOCLesson 71Windows Registry15 / 51

Two value types worth a second look

REG_EXPAND_SZ

A string with variables like %AppData%. Common in persistence because the path resolves for any user, exactly as legitimate installers use it.

Oversized REG_BINARY or REG_SZ

Large, high-entropy data where a short setting belongs: consistent with a smuggled, encoded payload (the fileless technique).

The type is not metadata to skim. It tells you whether a value is a path to follow or data to carve out and analyse.
HACKTHESOCLesson 71Windows Registry16 / 51

Reading the type is part of reading the value

  • REG_EXPAND_SZ: a string Windows will expand and then execute
  • %AppData% resolves for any user, and tells you where to pull the payload
Attackers use REG_EXPAND_SZ for portability, exactly as legitimate installers do.

Why you cannot just copy a hive

  • Transaction logs.LOG1 / .LOG2 files keep the hive consistent through a power loss, like a database write-ahead log.
  • Locked while runningWindows locks the hive files, so live collection uses a Volume Shadow Copy or an offline disk image.
  • Credential dumpersTarget SAM and SECURITY directly rather than going through the API.
A key path becomes something you can locate, image and hand to a forensic tool.
HACKTHESOCLesson 71Windows Registry20 / 51
SAM and SECURITY hold password hashes and cached secrets.

They are backed by real files on disk, so any unexpected process reading them, even read-only, is a serious signal.

This is why a key path mapping to a concrete file matters: it turns an abstract location into something you image, and something you alert on.

Section 5 of 9

The Registry locations that matter for security

A short list of places where a change should draw your eye.

HACKTHESOCLesson 71Windows Registry22 / 51

Four categories worth watching

Autorun keys

...\CurrentVersion\Run and RunOnce in HKLM (boot) and HKCU (logon). The classic persistence spot.

Service config

HKLM\System\CurrentControlSet\Services: a service can run malware at boot with high privilege.

Security settings

Values that turn off protections, weaken authentication, or disable logging.

Activity evidence

Recently run programs, connected USB devices, user activity: timeline material.

Attackers rely on the Registry being enormous and noisy. Your advantage is knowing the short list.
HACKTHESOCLesson 71Windows Registry23 / 51
Your advantage is the short list.

Attackers rely on the Registry being enormous and noisy. A change to a known-important location stands out only because you know which places matter.

Autorun keys, service config, security settings and activity evidence are the four categories to internalise.

HACKTHESOCLesson 71Windows Registry25 / 51

Autoruns: see every autostart point at once

The problem

Watching only Run and RunOnce misses Winlogon, IFEO, COM, BootExecute and the Startup folders, where attackers deliberately hide.

The tool

Sysinternals Autoruns enumerates every ASEP in one view, which is why it is a first-stop triage tool on a suspect host.

ASEP = Auto-Start Extensibility Point: any location Windows will launch code from.

The Startup folders are non-Registry cousins checked in the same breath; anything there runs at logon like a Run-key entry.

Five artifacts, each answering a slightly different question.

HACKTHESOCLesson 71Windows Registry27 / 51

What each artifact proves

ArtifactWhereWhat it reveals
ShimCacheSYSTEM: ...\Session Manager\AppCompatCacheExecutables seen on disk, with last-modified time; a file existed, not proof it ran

HACKTHESOCLesson 71Windows Registry28 / 51

ShimCache versus AmCache: presence or execution?

ShimCache

Built for application compatibility, not forensics. Shows a file was seen on disk with its modified time: evidence of presence, not proof it ran.

AmCache

Designed to record what ran. Gives the path, first-execution time and a SHA-1 hash you can check against threat intel without the file.

Students conflate the two. The distinction decides what you can actually claim: existed, versus executed.
HACKTHESOCLesson 71Windows Registry29 / 51

RunMRU: what was typed into Win+R, in order

  • MRUList = ba: value b was typed most recently, before a
  • The hidden, encoded PowerShell command is recorded almost verbatim
With no EDR, just an offline hive from a compromised laptop, RunMRU can turn guessing into reading.

Reading Registry activity in telemetry

Persistence, stealth and defense impairment leave observable writes.

HACKTHESOCLesson 71Windows Registry32 / 51

Three sources of Registry telemetry

Sysmon

12 key created/deleted, 13 value set, 14 key renamed. Event 13 captures target path and data.

Security auditing

4657 when a value is modified, once object-access auditing is configured.

Process telemetry

reg.exe or PowerShell writing the change, tied back to a process and its parent.

A value set under a Run key is exactly the kind of high-value event to alert on.

Sysmon 12 / 13 / 14Key create/delete, value set, key renameSysmon installed and configured

Sysmon Event 13 carries the target path and the data written, which is why a value set under a Run key is a high-value alert.

Hunt the short list, not everything

  • Run / RunOnce writesNew or modified values, especially pointing at Temp, Downloads, or scripts.
  • Service definitionsChanges under the Services key.
  • Security settingsDisabled protections or logging.
  • Suspicious writersreg.exe or PowerShell writing autostart or security keys under a suspicious parent.
Baseline and deviation applied to configuration. Normal software writes to the Registry; you look for writes that match attacker behaviour.

Normal software writes to the Registry constantly, so the goal is not to flag every change but to recognise writes that match attacker behaviour.

Persistence in an autorun key, a defence quietly disabled, a service pointed at a suspect binary: deviation from a known-good baseline.

Section 8 of 9

Tools for viewing and editing the Registry

regedit for one-offs, reg.exe and PowerShell for scripts and attacks.

HACKTHESOCLesson 71Windows Registry37 / 51

A viewer shows now; a log shows what changed

Manual query

reg query or Get-ItemProperty shows the current state of a key: useful once you suspect a specific location.

Historical telemetry

Sysmon and Event 4657 show what changed, when, and by which process: the moment of compromise.

Live investigation pairs the two: the query checks a hypothesis, the log shows who did it and when.
HACKTHESOCLesson 71Windows Registry38 / 51

The command shape attackers use to plant persistence

The query shows a legitimate OneDrive entry. The reg add targets the Run key, points at user-writable AppData\Roaming, and /f forces it silently. In command-line telemetry that is close to a direct alert.
HACKTHESOCLesson 71Windows Registry39 / 51

What to noticeIn the eventWhy it is suspicious
Target keyA Run key under HKCUA classic autostart location

Read the fields, not the intent: name, data path, flags and the writing process together make the call.
HACKTHESOCLesson 71Windows Registry40 / 51

PowerShell treats the Registry as a drive

Get-ItemProperty reads, the investigator's tool. New-ItemProperty writes, the same action as reg add.

Script-block logging, Event ID 4104, can show the exact line that wrote a persistence value. Queries show current state only; logs answer what changed, when, and by which process.
HACKTHESOCLesson 71Windows Registry41 / 51
Script-block logging shows the exact line that wrote a value.

PowerShell Event ID 4104 is the companion to registry telemetry: it records the command that set a persistence value, not just that the value changed.

Where Sysmon 13 says a value was set, 4104 can show how and by what script, closing the gap between change and cause.

Section 9 of 9

Case study: fileless persistence, stealth, impairment

The Run key is only the beginning.

HACKTHESOCLesson 71Windows Registry44 / 51

Four subtler Registry techniques

T1546.015

COM hijacking

Repoint a CLSID's InprocServer32 to an attacker DLL. A frequently invoked CLSID fires constantly and blends in.

T1546.012

IFEO Debugger

A Debugger value for sethc.exe runs the attacker's program instead, reachable from the logon screen. Overlaps Accessibility Features, T1546.008.

T1685

Disable defenses

Values under HKLM\Software\Policies\Microsoft\Windows Defender can turn off scanning.

Fileless payloads

Encoded or encrypted PowerShell stored as value data; a tiny loader runs it in memory. File AV never sees it.

Security-product key changes are high severity: they often precede other malicious activity as the attacker clears the path. T1685 Disable or Modify Tools was formerly T1562.001; in ATT&CK v19 Modify Registry (T1112) also sits under Defense Impairment.
HACKTHESOCLesson 71Windows Registry45 / 51

Each technique asks a different detection question

  • COM hijackingDid a CLSID's InprocServer32 get repointed to an unexpected DLL?
  • IFEO DebuggerDoes a program under Image File Execution Options have a Debugger value it should not?
  • Defense impairmentDid a security-product policy key change to turn protection off?
  • Fileless payloadIs there large encoded data where a short value belongs, with a tiny loader reading it?
Same detection toolkit, different key. Each is an unexpected write to a place that controls what runs or how the system defends itself.
HACKTHESOCLesson 71Windows Registry46 / 51
Every technique is the same act: an unexpected write to a security-relevant key.

The key differs, but the signal is the same: an unexpected write, from an unexpected process, to a place that controls what runs or how the system defends itself.

That is why Sysmon 12/13/14 and Event 4657 against the short list generalises across all of them.

Key takeaways

  1. 01The Registry stores configuration, controls what runs, and survives reboots: evidence source and persistence spot.
  2. 02Read paths as hive, key, value; HKLM needs admin, HKCU does not, which hints at attacker privilege.
  3. 03Hives are files on disk; SAM and SECURITY hold hashes and secrets, and reg save of them is credential theft.
  4. 04Run and RunOnce are only two ASEPs; check Winlogon, IFEO, COM CLSIDs, BootExecute and Startup folders.
  5. 05Detect with Sysmon 12/13/14, Event 4657, and reg.exe or PowerShell writes tied to their parent process.
  6. 06COM hijacking, IFEO debuggers, defense tampering and fileless payloads are all unexpected writes.

Check your understanding, question 1 of 3

Malware wrote a value pointing to itself under HKCU\Software\Microsoft\Windows\CurrentVersion\Run. What is it achieving, and what does HKCU rather than HKLM suggest?

A Run key value relaunches the program at logon, classic persistence. HKLM changes normally need admin, so HKCU suggests user-level rights. Run keys do not encrypt, affect only the current user in HKCU, and do not store audit logs.

HKLM\...\Image File Execution Options\sethc.exe has a Debugger value pointing to cmd.exe. What does this achieve?

An IFEO Debugger value redirects execution of the named program, so invoking sethc.exe from the logon screen launches cmd.exe without logging in (T1546.012). It does not delete files or affect every program.

Run and RunOnce are clean, yet the host clearly relaunches malware at logon. What is the correct reasoning?

Winlogon Userinit/Shell (T1547.004), Policies\Explorer\Run, BootExecute, IFEO (T1546.012), COM InprocServer32 (T1546.015) and the Startup folder all auto-launch code. A clean Run key clears nothing, which is why Autoruns enumerates the whole set.
