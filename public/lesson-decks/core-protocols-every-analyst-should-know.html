What a protocol actually is

An agreed set of rules for how two computers talk, plus the two ideas that recur: client/server and ports.

HACKTHESOCLesson 58Core protocols6 / 52

Two ideas you will use on every slide

Client and server

The client starts the request (your laptop asking for a page). The server waits and responds. The same computer can be a client in one conversation and a server in another.

Ports

One IP address, many services. A port number is a labelled door on the building: web knocks on 443, email on another door, file sharing on another.

A protocol is like the routine of a phone call: hello, take turns, goodbye, in a shared language.

Memorising well-known port numbers is one of the fastest ways to read network logs fluently.

DNS: the internet's phonebook

Turns a name you can remember into an IP address the network can use, on port 53.

HACKTHESOCLesson 58Core protocols10 / 52

Your device asks once; a resolver walks the chain

  1. 1Client asks the resolverYour device asks its configured DNS resolver (company or ISP): what is the IP for this name?
  2. 2Resolver walks the chainIf not cached: a root server points to the TLD server (.com), which points to the authoritative server.
  3. 3Authoritative server answersIt officially holds the domain's records and returns the final IP address.
  4. 4Resolver returns and cachesIt hands the IP back and remembers it for the record's TTL, so the next lookup is instant.
The whole round trip usually takes a few milliseconds, and it happens before almost every connection: every website, app and update check.
HACKTHESOCLesson 58Core protocols11 / 52

DNS shows intentions before the payload lands

  • C2 lookupsMalware must look up its command-and-control name, so suspicious or newly-registered domains are an early warning.
  • DNS tunnellingAttackers smuggle data out in tiny pieces inside DNS traffic.
  • DGAA domain generation algorithm produces thousands of random-looking names to stay reachable.
  • UDP vs TCP 53DNS normally uses UDP 53; TCP 53 carries large responses and zone transfers. TCP-53 zone transfers to an unexpected host are worth a look.
DNS is a goldmine and a target at the same time, precisely because it runs before almost everything else.

DHCP: the automatic address desk

The hotel check-in desk for computers: settings handed out automatically, on a lease.

HACKTHESOCLesson 58Core protocols15 / 52

DORA: four steps the moment a device connects

The server gives an IP address, subnet mask, default gateway and DNS servers, all leased.

  1. 1DiscoverThe device broadcasts: is there a DHCP server out there? It has no address yet.
  2. 2OfferA DHCP server replies with an address it can use, plus the gateway and DNS.
  3. 3RequestThe device says: yes please, I will take that offered address.
  4. 4AcknowledgeThe server confirms and records the lease: which address went to which device, for how long.

Server listens on port 67, client on port 68. Leases are renewed before they expire.

That is why the same laptop may keep one address for days, or get a new one after a long weekend.
HACKTHESOCLesson 58Core protocols16 / 52
DHCP logs are the map from an IP address to an actual device at a moment in time.

Alerts name an IP, but IPs get reused. Which machine was 10.4.2.17 at 2 a.m.? Check the lease records.

Also watch for a rogue DHCP server handing out settings to hijack traffic, and for unexpected devices suddenly requesting leases.

SSH: the secure remote control

Log into and control another computer, with the whole session encrypted, on port 22.

HACKTHESOCLesson 58Core protocols18 / 52

How an SSH login happens

  1. 1Client connectsThe admin's laptop opens a connection to the server on port 22: I want to log in.
  2. 2Agree on encryptionA handshake sets up a shared secret before any password or command is sent.
  3. 3Client proves identityA password, or far better a key pair: prove you own the private key without ever sending it.
  4. 4ShellOnce authenticated, the admin works on the remote machine until logging out.
SSH replaced Telnet precisely because Telnet sent everything, passwords included, as plain readable text. Key-based login is the professional standard.
HACKTHESOCLesson 58Core protocols19 / 52

Full control makes SSH a prime target

  • Brute forceA flood of failed logins on port 22 is an attempt to guess a password.
  • Unusual sourceA workstation that never administers servers, or a foreign login at 3 a.m., can signal a compromised account.
  • PivotingAttackers tunnel through a foothold over SSH to reach deeper systems.

Successful and failed SSH logins are among the highest-value events an analyst reviews.

Normal SSH is many times a day in any real environment, so the question is always whether this source and this account make sense together.

SMB: the shared office filing cabinet

Windows file and printer sharing on port 445, and one of the most abused protocols in serious incidents.

HACKTHESOCLesson 58Core protocols21 / 52

How a share is used

  1. 1Server advertises sharesA file server, or even an ordinary Windows PC, exposes named folders or printers and enforces permissions.
  2. 2Client connects on 445It asks to access a share, named with a UNC path like server\share.
  3. 3Server checks permissionsIf allowed, the client browses, opens, edits, saves files or prints.
  4. 4Continuous in office workEvery touch of a network folder or shared printer is SMB traffic.
SMB is what makes a shared drive appear as just another folder on your own machine.
HACKTHESOCLesson 58Core protocols22 / 52

File sharing is also a way to move and spread

Lateral movement

Copy tools onto other machines and run them: the technique behind tools like PsExec.

Ransomware

Reach and encrypt shared drives across the whole company at once.

WannaCry

Spread through the SMB vulnerability EternalBlue, MS17-010.

Red flag: SMB crossing between network zones, or one machine suddenly connecting to many others on 445.

The fan-out shape is what to hunt. It comes back in the worked example at the end of the lesson.

HTTP and HTTPS: request and response

The web's conversation, port 80 in plain text and port 443 wrapped in TLS.

HACKTHESOCLesson 58Core protocols24 / 52

Who does what in a web request

  1. 1Client sends a requestA method (GET, POST), a path (/login), and headers like User-Agent, Referer, Cookie.
  2. 2TLS handshake (HTTPS)Both sides agree on encryption and the server presents a certificate, before any HTTP data.
  3. 3Server respondsA status code (200, 301/302, 403, 404, 500), headers, and the content.
  4. 4Repeat per resourceOne page load can trigger dozens of separate HTTP requests.
Almost every application uses HTTP today, from mobile apps to malware phoning home.
HACKTHESOCLesson 58Core protocols25 / 52

The most common transport for C2

It blends in with browsing and passes firewalls that allow outbound web.

  • BeaconingA host requesting the same destination at unnaturally regular intervals.
  • User-AgentUnusual or minimal User-Agent strings.
  • TLS certificatesSelf-signed, newly issued, or matching known malware infrastructure.
  • Domain reputationNewly-registered or low-reputation domains, tying back to the DNS lookups before them.

HTTPS hides the content, so defenders rely on metadata: destination, timing, certificate details, TLS fingerprints.

Stress the shift: with encryption everywhere, you read around the payload, not the payload itself.
HACKTHESOCLesson 58Core protocols26 / 52

RDP: remote desktop, full graphical control

The whole screen, mouse and keyboard of another machine, on port 3389.

HACKTHESOCLesson 58Core protocols29 / 52

Useful admin tool, heavily attacked service

How it works

Client connects on 3389. NLA (since Windows Server 2012) authenticates before a full desktop session exists. The server then streams every keystroke and screen update.

How it is attacked

Internet-exposed RDP is a top ransomware initial-access vector: scan for 3389, then brute-force or credential-stuff. BlueKeep (CVE-2019-0708) needed no credentials at all.

BlueKeep was a wormable remote code execution flaw in older Windows RDP implementations.
HACKTHESOCLesson 58Core protocols30 / 52

What RDP looks like in Windows logs

  • Watch 4624 Type 10 from unexpected geographies or at unusual hours
  • 4624 Type 10 preceded by a burst of 4625 suggests brute force
Logon Type 10 is the specific marker of an RDP session. Students will see it again in Windows event log lessons.

SPF and DKIM: proving who sent an email

Anyone can write any name in the From line. These two checks ask the domain itself.

HACKTHESOCLesson 58Core protocols32 / 52

Two independent checks, both published in DNS

The guest list

SPF

The domain publishes which mail servers may send for it. The receiving server checks the delivering server against the list. Not on it: SPF fails.

  • Validates the sending server, not the contents
  • Can break when mail is forwarded

The wax seal

DKIM

The sending server signs each message with a private key; the public key sits in DNS. The receiver verifies it.

  • Proves the message comes from that domain
  • Proves it was not modified in transit
Spoofing a From address like ceo@yourcompany.com is the engine behind most phishing and business email compromise (BEC).
HACKTHESOCLesson 58Core protocols33 / 52

DMARC ties them together, and headers show the result

  • DMARC policyTells receivers what to do on failure: nothing, quarantine to spam, or reject outright.
  • AlignmentRequires the authenticated domain to align with the visible From address.
  • In the headersSPF, DKIM and DMARC results are recorded in the message headers.
  • Triage moveA 'CEO' email with spf=fail and dkim=fail is very likely spoofed.
Reading these three results is one of the first, fastest moves in a phishing investigation.

SMTP: how email actually travels

SPF and DKIM verify the sender. SMTP is the trucks and sorting centres that move the letter.

HACKTHESOCLesson 58Core protocols35 / 52

Three ports, two jobs

Relay

Port 25

Server-to-server traffic moving a message between providers, e.g. your mail server to Gmail.

Submission

Port 587

A mail client hands a new message to its own outgoing server, typically upgraded mid-connection via STARTTLS.

Implicit TLS submission

Port 465

Same job as 587, but encrypted from the very first byte.

Plain port-25 relay is unencrypted by default unless both ends negotiate STARTTLS.
HACKTHESOCLesson 58Core protocols36 / 52

Hop by hop, with a chain of custody

  1. 1Client submitsThe sender's mail client hands the message to its outgoing server (587/465), with its credentials.
  2. 2Server looks up MXIt finds the recipient domain's mail servers via a DNS MX record and relays on port 25.
  3. 3Each hop adds ReceivedEvery server adds a Received header: origin, timestamp, handling server.
  4. 4Final deliveryThe recipient server delivers the message to the mailbox.
Reading the stacked Received headers reverse-engineers the true path, often exposing a mismatch between the claimed sender and the real origin, which corroborates SPF/DKIM.
HACKTHESOCLesson 58Core protocols37 / 52
Open relays and compromised mail servers let phishing blend into normal-looking traffic.

An open relay forwards mail for anyone, hiding the true origin. That is why SPF and DKIM matter for trust, not just transport.

SMTP long predates modern security concerns, which is the root of why the authentication layers were bolted on top.

Quick reference: LDAP, Kerberos and NTP

Three more protocols to recognise on sight. LDAP and Kerberos power Active Directory.

HACKTHESOCLesson 58Core protocols39 / 52

Purpose, port and SOC relevance

389, or 636 for LDAPS

LDAP

Queries and updates a directory like Active Directory. BloodHound enumerates users, groups and permissions over LDAP: a burst of queries from one host is a classic signal.

Port 88

Kerberos

Prove identity once to a Domain Controller, get a time-limited ticket, present it to each resource. Abnormal ticket requests underpin Kerberoasting, Pass-the-Ticket, Golden Ticket detections.

UDP 123

NTP

Synchronises clocks, typically to within milliseconds. Small queries can trigger large responses, abused for NTP amplification DDoS.

LDAP and Kerberos get the full mechanical walkthrough in the dedicated Active Directory and Domain Controllers lesson.
HACKTHESOCLesson 58Core protocols40 / 52
Kerberos fails if a client's clock drifts beyond the maximum skew, 5 minutes by default.

Ticket timestamps are how Kerberos detects replay, so NTP is quietly load-bearing for every logon.

For widespread authentication failures, check whether the domain's time source has simply drifted before assuming a more exotic cause.

Key takeaways

  1. 01A protocol is a shared rulebook with a well-known port, and its logs reveal both normal work and attacker activity.
  2. 02DNS turns names into IPs; DHCP hands out IP, gateway and DNS via DORA and maps IPs to devices.
  3. 03SSH (22) is encrypted remote control; SMB (445) shares files and is the lateral-movement and ransomware highway.
  4. 04HTTP methods and status codes tell a story even when HTTPS hides the content; RDP shows as 4624 Logon Type 10.
  5. 05SPF, DKIM and DMARC results in headers expose spoofed email; SMTP Received headers show the true path.
  6. 06Real detections chain DHCP, DNS, SSH and SMB into one timeline: sequence and fan-out beat any single event.

Check your understanding, question 1 of 3

A brand-new laptop gets an IP address, gateway and DNS servers within a second, with nobody typing anything. Which protocol did this, and in what order?

DHCP configures a new device through DORA, client asking and server leasing. The scrambled order is impossible, Request then Acknowledge is a renewal shortcut, not a first-time exchange, and DNS resolves names, not addresses or gateways.

One workstation suddenly connects to dozens of other machines on port 445 within a few minutes. Which protocol is in use, and why is it suspicious?

Port 445 is SMB, and rapid fan-out on 445 is the classic shape of lateral movement or ransomware reaching shared drives. RDP is 3389, LDAP is 389, and DNS is 53; DGA shows as many domain lookups.

Check your understanding, question 3 of 3

A web-server log shows hundreds of POST requests to /login answered mostly with 401, then a single 302. What does this most likely represent?

A flood of 401s ending in a 302 is credential stuffing that broke in. A real user tries a handful, scanners probe for flaws rather than mass logins, and health checks are lightweight GETs, not credential POSTs.
