One hash idea, then the three stores and the replication trick an analyst must know.

What a hash is, and what it is not

A hash

The one-way output of a function: feed in a password, get a fixed-length scrambled string you cannot reverse. The same input always gives the same output.

Not the password

You cannot read the password back out of the hash. Windows stores only the hash, so a database theft does not hand over plaintext directly.

Define hash cleanly before anything else. The whole lesson rests on the gap between a hash and a plaintext password.
HACKTHESOCLesson 45Credential dumping7 / 50

How Windows checks a login with a hash

  1. 1You type a passwordThe plaintext exists only for a moment, in memory.
  2. 2Windows hashes itIt runs the same one-way function over what you typed.
  3. 3It compares hashesThe new hash is checked against the stored hash for your account.
  4. 4Match means successIf they are equal, you are in. The plaintext was never stored or compared directly.
This is the normal, benign flow. The attack twist comes next: for NTLM the stored hash alone is enough.
HACKTHESOCLesson 45Credential dumping8 / 50
For NTLM, a valid hash is enough to authenticate: no cracking needed.

Because the protocol proves knowledge of the hash, not the plaintext, stealing the hash is functionally stealing the credential. This is Pass-the-Hash.

This is the single most important mechanism in the lesson. If a hash is as good as the password, then dumping stored hashes is the whole game.
HACKTHESOCLesson 45Credential dumping9 / 50

Why LSASS memory is the richest target

What LSASS holds

At login, the Local Security Authority Subsystem Service needs your credentials in usable form and caches material for as long as you stay logged in: hashes, Kerberos tickets, sometimes cleartext under legacy settings.

Why it is the prize

It is the only store that holds live, immediately reusable secrets for every user currently logged on to that machine, not just a stored hash to crack later.

Dump LSASS is one of the first moves an attacker toolkit attempts after a foothold.

LSASS expands to Local Security Authority Subsystem Service. Say the full name once, then use LSASS.
HACKTHESOCLesson 45Credential dumping10 / 50
This is the difference between one compromised laptop and logging in as anyone, anywhere.

MITRE groups it all under T1003, OS Credential Dumping, usually the single most consequential step in an intrusion.

Which is exactly why detecting it fast matters so much.

Where Windows credentials live

Three principal stores, each a MITRE sub-technique, plus a stealthy replication trick.

Three treasure chests and DCSync

StoreIDWhat it yieldsWhere
LSASS memoryT1003.001Live-session hashes, tickets, sometimes cleartextlsass.exe, any host
SAM databaseT1003.002Local account hashes, incl. AdministratorHKLM\SAM, any host
NTDS.ditT1003.003Every domain account hashC:\Windows\NTDS, a DC only

The map tells you which host to look at (any host for LSASS/SAM, a DC for NTDS/DCSync) and which telemetry matters. DCSync needs no malware on the DC: just a rogue replication request.
HACKTHESOCLesson 45Credential dumping13 / 50

Local hashes vs the whole domain

SAM: this machine only

The Security Account Manager holds local account hashes for one host: the local Administrator and local users. Useful if that password is reused elsewhere.

NTDS.dit: the entire domain

The Active Directory database on a Domain Controller holds every domain account hash, including Domain Admins. One read is the whole kingdom.

SAM expands to Security Account Manager; NTDS.dit is the NT Directory Services database file.

Drive the scale difference: SAM is a house key, NTDS.dit is the master key to the whole building.
HACKTHESOCLesson 45Credential dumping14 / 50
DCSync steals hashes by pretending to be a Domain Controller, not by reading a file.

It sends a legitimate replication request (DRSUAPI) that asks a real DC to hand over account secrets. No malware on the DC, no file touched.

This is why DCSync is so dangerous and so quiet: it abuses a feature DCs are built to answer. Detection lives in who is allowed to ask.

How LSASS memory is dumped

The most attacked store, because it holds live session secrets.

HACKTHESOCLesson 45Credential dumping16 / 50
Whatever the tool, some process must open a handle to lsass.exe with memory-read rights.

That handle-open is the golden detection opportunity: legitimate software almost never reads LSASS memory.

This is the defender's structural advantage. Keep it front and centre before naming any technique.
HACKTHESOCLesson 45Credential dumping17 / 50

Three ways in, one shared signal

ApproachWhat the analyst seesStill needs
Signed LOLBin (comsvcs.dll MiniDump)rundll32.exe with a handle to lsass.exeA read handle to LSASS memory
Admin dump utility (e.g. ProcDump)The utility opening lsass.exe, a .dmp writtenA read handle to LSASS memory
Direct memory reader (Mimikatz-style)An unknown process reading LSASSA read handle to LSASS memory

The last column is identical: all three must open lsass.exe and read it.

Attackers prefer the signed comsvcs path so the tree shows rundll32.exe, not a named hacking tool. The handle-open is the common denominator you detect on.
HACKTHESOCLesson 45Credential dumping18 / 50

The signal: a handle to lsass.exe (Sysmon ProcessAccess, EID 10)

  • 0x1410 carries PROCESS_VM_READ: the right to read LSASS memory
  • SourceImage rundll32.exe is not a security product: that is the anomaly
  • A dump file written nearby is the follow-on to correlate
Legacy WDigest could leave cleartext in LSASS; modern Windows does not by default. The point for the analyst is the handle-open, not the tool name.
HACKTHESOCLesson 45Credential dumping19 / 50

LSASS read: benign or an attack

Benign

The SourceImage is a known AV or EDR engine (MsMpEng.exe, MsSense.exe) running from System32. These read LSASS constantly and are baselined out.

Investigate

The SourceImage is rundll32, a Temp-folder binary, or anything unexpected, holding a VM_READ handle to lsass.exe, especially with a .dmp written afterward.

Same event, same target; the SourceImage and the follow-on decide the verdict.

This is the exact judgement the first quiz tests. Baseline the security products, then treat what remains as a lead.

How SAM and NTDS.dit are dumped

Both files are locked while Windows runs, so attackers copy around the lock.

HACKTHESOCLesson 45Credential dumping21 / 50
SAM and NTDS.dit are locked open by the OS, so they cannot be copied directly.

Attackers work around the lock using built-in Windows features, which is exactly why those features appearing in telemetry is the signal.

The lock is why the techniques below exist. Each one is a legitimate admin capability turned to theft.
HACKTHESOCLesson 45Credential dumping22 / 50

How the lock is bypassed, and what fires

MethodWhat it doesTelemetry it produces
Volume Shadow CopySnapshots the volume so the locked file can be read from the copyvssadmin / shadow-copy creation, Event 8222
reg save of hivesExports HKLM\SAM and HKLM\SYSTEM to filesEvent 4688: reg.exe save HKLM\SAM
ntdsutil IFMCreates an Install From Media dump of NTDS.dit on a DCEvent 4688: ntdsutil, files written under a dump path
DCSyncSkips files entirely, pulls hashes by replicationEvent 4662 on the DC (covered in section 8)
SAM needs the SYSTEM hive too, which holds the boot key that decrypts it. Remote tooling automates the reg/shadow steps over the network.
HACKTHESOCLesson 45Credential dumping23 / 50

What locked-store copying looks like in native logs

  • reg.exe saving the SAM hive is rare enough to be a strong lead
  • ntdsutil on a DC outside a maintenance window warrants a call
  • SubjectUserName names the account to pivot from
These are built-in admin tools, so their mere presence in a log is the detection. Correlate with the SYSTEM hive save and any shadow-copy creation in the same window.
HACKTHESOCLesson 45Credential dumping24 / 50
Shadow-copy creation on a DC, ntdsutil execution, and reg save of hives are rare in normal operations.

That rarity is exactly what makes them strong detections: each is a high-signal lead worth investigating on sight.

Normal admins rarely run these specific commands. Confirm against your change calendar before escalating, but treat each as a lead.

LSA Secrets, cached creds, and Linux files

Three more T1003 stores every analyst should recognise: two Windows, one Linux.

HACKTHESOCLesson 45Credential dumping26 / 50

Two more Windows stores

T1003.004

LSA Secrets

HKLM\SECURITY\Policy\Secrets: service-account and auto-logon passwords, the machine account password, DPAPI keys. Dumped by saving the SECURITY and SYSTEM hives.

T1003.005

Cached domain creds

HKLM\SECURITY\Cache: DCC2 (MSCache v2) hashes for offline logon. Cannot be used for Pass-the-Hash: must be cracked offline first.

Service-account passwords from LSA Secrets are a common lateral-movement lever: over-privileged, rarely rotated.

DPAPI is the Data Protection API. The DCC2 distinction is critical: it was never a network credential, only a local fallback check.
HACKTHESOCLesson 45Credential dumping27 / 50
A DCC2 cached hash is inert until cracked; an LSA Secret may be a live password.

That is why the two stores sit together but earn very different urgency: one is a crackable fallback, the other can be a reusable service-account secret.

Teach the contrast: both come from HKLM\SECURITY, but what they yield changes your response completely.
HACKTHESOCLesson 45Credential dumping28 / 50

The Linux equivalent: /etc/shadow (T1003.008)

  • The $6$ prefix marks a SHA-512 crypt hash
  • Readable only by root, so unexpected reads are the signal
  • Offline cracking (unshadow + a wordlist) recovers the plaintext
Detect with auditd read-watches on /etc/shadow, or unexpected cat/cp/scp of it in EDR process telemetry. On Windows, a reg save of HKLM\SECURITY is as abnormal as one of HKLM\SAM.
HACKTHESOCLesson 45Credential dumping29 / 50

Detecting the secondary stores

  • LSA Secrets / DCC2A reg save of HKLM\SECURITY (plus SYSTEM), the same reg.exe signal as SAM theft.
  • /etc/shadowAn auditd watch on the file, or a non-root-context read appearing in EDR process telemetry.
  • Follow the accountA dumped service-account password means pivot: where else does that account log on?
The theme across stores: the read is rare, so the read is the detection. Then follow what the stolen material unlocks.

What you actually steal, and how it is reused

A dump yields several kinds of material, and the kind decides the attacker's next move.

HACKTHESOCLesson 45Credential dumping34 / 50

Reuse without the password: T1550

  • Pass-the-HashT1550.002: present a stolen NT hash to authenticate over NTLM. No cracking, no plaintext.
  • Pass-the-TicketT1550.003: present a stolen Kerberos TGT or service ticket as that user.
  • Overpass-the-HashA use of T1550.003: turn a stolen NT hash or AES key into a fresh Kerberos TGT, so Pass-the-Hash-only detections miss it.

An analyst who can name the artifact can predict the attacker's next move.

Overpass-the-Hash matters because it defeats detections that only watch NTLM: the reuse now looks like ordinary Kerberos.

An NT hash or ticket from LSASS is a live weapon the moment it is stolen; a DCC2 hash is inert until cracked. That is why LSASS is the crown jewel.

Detecting credential dumping

Different stores leave different telemetry; LSASS access is the highest-value signal.

HACKTHESOCLesson 45Credential dumping38 / 50

GrantedAccess masks seen reading LSASS

MaskIncludesReading
0x1410QUERY_LIMITED + QUERY_INFO + VM_READClassic read handle: can scrape memory
0x1010QUERY_LIMITED + VM_READRead access, leaner mask
0x1438Adds VM_WRITE and moreRead plus write: injection-adjacent
0x1000QUERY_LIMITED onlyBenign enumeration, no memory read
VM_READ (0x0010) is the bit that matters: it lets the source read LSASS memory. 0x1010/0x1410/0x1438 are the classic Mimikatz-style masks.
HACKTHESOCLesson 45Credential dumping39 / 50

SAM theft and DCSync in native logs

  • reg.exe saving a hive is rare enough to be a strong indicator
  • The two Properties GUIDs are the Get-Changes replication rights: DCSync
  • The request comes from j.intern, not a DC machine account
The replication rights ride in Properties, not ObjectType (domainDNS). 4662 only fires if a SACL is set on the domain object. Normal replication only comes from a DC's own machine account.
HACKTHESOCLesson 45Credential dumping40 / 50

DCSync: legitimate replication vs an attack

Legitimate

The Get-Changes rights are requested by a Domain Controller's own machine account, as part of normal AD replication between DCs.

DCSync

The same rights requested by a user or service account that is not a DC. There is no benign reason for j.intern to replicate the directory.

The deciding field is who asked, not what was asked for.

This is the second quiz. The rights themselves are normal; the requester being a non-DC is the whole tell.
HACKTHESOCLesson 45Credential dumping41 / 50

Turning raw signals into real detections

  • Allow-list the LSASS huntLegit AV/EDR read LSASS constantly. Baseline those SourceImages, exclude them, treat what remains as a lead.
  • NTDS read pathWith a SACL on ntds.dit, Event 4663 ObjectName shows a shadow-copy device path, not the live C:\Windows\NTDS file.
  • Remote extractionEvent 5145 on IPC$ plus the winreg pipe, with 4624 Logon Type 3 from an odd host, flags remote SAM/NTDS pulls.
  • Verify, do not assumeA GPO that sets RunAsPPL or Credential Guard is not proof. Check boot Event 12 and the running-state query.

Map these to vendor alerts like 'Suspicious access to LSASS service' and 'Suspected DCSync attack'.

The theme: high-value signals are noisy until tuned. Build allow-lists from observed data and confirm hardening actually loaded.
HACKTHESOCLesson 45Credential dumping42 / 50

The tuned LSASS hunt: allow-list, then alert

  • OpenProcessApiCall is Defender's equivalent of Sysmon Event ID 10
  • binary_and(Access, 0x10) keeps only handles that carry PROCESS_VM_READ
  • The System32 and AV engine filters are the allow-list
Written in Microsoft Defender Advanced Hunting (KQL). Build the exclusion list from your own AV/EDR engine names and review it whenever tooling changes.

Section 9 of 9

Defence

Controls that attack every stage: remove the target, limit who can try, harden the DC.

HACKTHESOCLesson 45Credential dumping44 / 50

Layered controls

Remove the target

Credential Guard isolates LSASS secrets in a VBS enclave so even admin malware cannot read them. LSASS as PPL blocks unauthorized handle-opens.

Limit who can try

Least privilege: remove local admin, tightly control domain admin. Most dumping needs elevation first.

Harden the DC

Restrict interactive logon, monitor shadow copies and ntdsutil, audit who holds replication rights so DCSync is minimized and alerted.

Also disable WDigest cleartext caching and enable the ASR rule blocking LSASS credential theft.

VBS is virtualization-based security; PPL is Protected Process Light. Credential Guard and PPL are the strongest technical controls against LSASS dumping.

Key takeaways

  1. 01A hash is a one-way scramble of a password, and NTLM Pass-the-Hash accepts it without the plaintext.
  2. 02T1003 targets LSASS memory (.001), the SAM (.002), NTDS.dit (.003) and, via replication, DCSync (.006).
  3. 03SAM and NTDS.dit are locked, so attackers copy them via reg save, shadow copies or ntdsutil.
  4. 04LSASS dumping needs a read handle to lsass.exe: any non-security process doing so is suspicious.
  5. 05An NT hash or ticket from LSASS is instantly reusable; a DCC2 cached hash must be cracked first.
  6. 06Detect with Event ID 10 read masks, reg/vssadmin/ntdsutil process creation, and Event 4662 from non-DCs.

A non-security process opens a handle to lsass.exe with GrantedAccess 0x1410, and Event ID 1 shows rundll32.exe calling comsvcs.dll MiniDump against the LSASS PID. What is happening?

Check your understanding, question 2 of 3

On a Domain Controller, Event ID 4662 shows a DS-Replication-Get-Changes request from a regular user account that is not a domain controller. Which technique should you suspect?

Replication requests should come only from domain controllers, so a regular user account requesting DS-Replication-Get-Changes is DCSync (T1003.006), pulling hashes via the replication protocol. 4662 logs object access, not failed passwords.

Check your understanding, question 3 of 3

An attacker steals a DCC2 cached domain credential hash from a laptop, then immediately tries Pass-the-Hash against a file server, but it fails. Why?

DCC2 (MSCache v2) hashes exist only to let a domain account log on locally when a DC is unreachable. Unlike NTLM hashes from LSASS they cannot be replayed via Pass-the-Hash and must be cracked offline to recover the plaintext.
