HACKTHESOCLesson 65Defender XDR7 / 51

One intrusion, seen by five sensors in turn

An illustrative attack and the sensor that sees each stage.

  1. 1Phishing email (MDO)An invoice email with a link reaches r.katz; the click is recorded.
  2. 2Stolen sign-in (Entra)The harvested password is used from an unfamiliar IP.
  3. 3Code on the laptop (MDE)A macro document starts PowerShell on FIN-LAPTOP-07.
  4. 4Directory probing (MDI)The account queries Active Directory for service accounts.
  5. 5Mass download (MDCA)Hundreds of SharePoint files pulled in minutes.
Each product alone sees one stage and raises one alert. Only correlation shows it is one attacker moving through five stages.
HACKTHESOCLesson 65Defender XDR8 / 51
Which of these alerts are actually the same attack?

Every alert names its entities: a device, a user, a file, an IP. When an MDO phish, an Entra risky sign-in and an MDE PowerShell alert name the same user, they become one incident.

That is the difference between drowning in alerts and understanding an attack: one case instead of three disconnected tickets in three consoles.
HACKTHESOCLesson 65Defender XDR9 / 51

Correlation keys: the entity both alerts name

Shared entityNamed in alert ANamed in alert B
User r.katzMDO: recipient who clicked the URLEntra: account with unfamiliar sign-in
Device FIN-LAPTOP-07MDE: host where PowerShell ranMDE: host where update.exe was dropped
A URL or IPMDO: the URL in the emailMDE: the network connection from PowerShell
A file hashMDO: attachment detonated as maliciousMDE: same hash written to disk
Correlation is only as good as the entities in each alert. Vague or missing entities leave alerts as orphans the analyst must link by hand.

Alerts: a single detection

The atomic unit of detection, and only a fragment of the picture.

HACKTHESOCLesson 65Defender XDR11 / 51

A simplified alert

  • category aligns to an ATT&CK tactic; mitreTechniques names the technique
  • entities are what let this alert link to others
  • detectionSource says which Defender product raised it
The full alert also carries classification (null until triaged) and lastActivity. Is this an admin script or the middle of an intrusion? The alert alone cannot say.
HACKTHESOCLesson 65Defender XDR12 / 51

The alert fields and how you use them

FieldWhat it isHow you use it
title / categoryWhat was detected; the ATT&CK-aligned tactic bucketFirst read on what happened and where it fits
severityInformational / Low / Medium / HighFirst cut at urgency
status / classificationNew, In Progress, Resolved; analyst verdictWorkflow state; verdict set on close
detectionSourceWhich Defender product raised itWhich telemetry to pivot into
mitreTechniquesTechnique IDs, e.g. T1059.001Precise technique for hunting and reporting

An alert with vague or missing entities is an alert that cannot be correlated. alertId is the unique handle to cite the exact detection.
HACKTHESOCLesson 65Defender XDR13 / 51

The same alert title, two very different stories

Likely benign

"Suspicious PowerShell command line" from routine administration.

  • Launched by an admin tool or scheduled task
  • Signed script from a known IT path
  • Runs on the admin's usual host

Likely malicious

The same title in the middle of an intrusion.

  • Parent process is WINWORD.EXE
  • Encoded command line (-enc)
  • Followed by an outbound connection
The title is identical in both cases. The parent process and what happened next decide it, which is why the timeline exists.
HACKTHESOCLesson 65Defender XDR14 / 51

Severity is a triage priority, not a verdict

SeverityRough meaningTypical queue behaviour
HighStrong indication of a real, damaging threatWork first, often page on-call
MediumSuspicious; plausibly malicious, needs reviewWork in priority order
LowWeak or common signal; often benignBatch/triage when higher cleared
InformationalNoteworthy but not itself a threatContext, tuning, rarely actioned alone
A High-severity alert can still turn out to be an authorised red-team test. Triaging alerts one at a time is how analysts burn out and miss real attacks.
HACKTHESOCLesson 65Defender XDR15 / 51

The first five minutes with one alert

  1. 1Read what and how badTitle, category, severity: what kind of activity, how urgent.
  2. 2Open the entitiesWhich device, user, process; are they high value?
  3. 3Find its incidentIs it already correlated with other alerts? Work the incident.
  4. 4Look at the evidenceProcess tree, command line, what happened right after.
  5. 5DecideBenign and close, escalate, or contain now.
Step 3 is the habit that separates incident-driven SOCs from alert-driven ones: never close an alert without checking what it is linked to.

Incidents: the correlated attack story

Related alerts grouped by shared entities or a recognised attack sequence.

HACKTHESOCLesson 65Defender XDR17 / 51

Three products, one incident

Phishing click, then anomalous sign-in, then suspicious PowerShell on the user's device: the story end to end, in one case. The incident also carries a classification field, null until closed.

Reading the incident: each alert adds a chapter

AlertSourceWhat it adds to the story
Malicious URL clickedDefender for Office 365How the attacker got in: a phishing click
Unfamiliar sign-in propertiesEntra ID ProtectionThe account is being used by someone else
Suspicious PowerShell command lineDefender for EndpointCode is now running on the user's laptop
Read the alerts in time order and name the stage each one represents. The incident name, "Multi-stage attack involving r.katz", already summarises it.
HACKTHESOCLesson 65Defender XDR19 / 51

What an incident gives you that alerts cannot

  • Attack story / graphWhat happened, in what order, across email, endpoint and identity. Often the fastest way to grasp scope.
  • All involved assetsEvery device, user and mailbox touched: how far it spread.
  • Consolidated evidenceFiles, processes, IPs and URLs from all member alerts in one place.
  • One severityAggregated from its alerts, so the queue is prioritised as cases, not fragments.
Mature Defender SOCs work the incident queue, not the raw alert firehose.
HACKTHESOCLesson 65Defender XDR20 / 51

The incident triage workflow

  1. 1Read the attack storyUnderstand what happened.
  2. 2Check the scopeWhich users and devices are involved.
  3. 3ConfirmIs it a true positive?
  4. 4ContainIsolate a device, disable or reset an account, purge mail.
  5. 5Classify and closeFeed the outcome back to improve detections.

Alerts are evidence; the incident is the case.

This only works because each underlying alert named its entities clearly enough to be correlated.
HACKTHESOCLesson 65Defender XDR21 / 51

Correlation can merge too much or too little

Over-merged

Unrelated alerts joined because they share a busy entity, such as an admin jump host or a shared service account. Unlink the alert that does not belong.

Under-merged

One attack split across two incidents because no entity overlapped. Merge them; the absorbed incident shows status Redirected.

Correlation is automatic, not infallible. Checking that the incident boundary matches the real attack is part of triage.

Section 4 of 7

Automated Investigation and Response (AIR)

A playbook that runs the repetitive first pass the moment a supported alert fires.

HACKTHESOCLesson 65Defender XDR23 / 51

What AIR does on its own

  1. 1Examine entitiesFiles, processes, persistence mechanisms involved in the alert.
  2. 2Check intelligenceCompare the evidence against threat intelligence.
  3. 3Expand outwardE.g. does the same malicious file exist on other devices in the org?
  4. 4Render verdictsMalicious, suspicious, or no threat found, per piece of evidence.
AIR is a capability of Defender for Endpoint, integrated across XDR. It mirrors what a human analyst would do on the first pass.
HACKTHESOCLesson 65Defender XDR24 / 51

Verdicts drive the proposed remediation

VerdictMeaningTypical AIR response
MaliciousEvidence confirmed badPropose/execute: quarantine file, kill process, remove persistence, quarantine service
SuspiciousNot conclusive but concerningFlag for analyst review; may propose action
No threat foundEvidence judged cleanNo action; recorded for the investigation trail
Persistence removal covers a Run key, scheduled task or service.
HACKTHESOCLesson 65Defender XDR25 / 51

A pending AIR action, as the analyst sees it

  • Which alert started the investigation, and what AIR proposes
  • Verdict Malicious with status Pending: semi-automation waiting for you
  • "Also found on": the reach AIR checked; compare with the incident's devices
Illustrative layout of the information shown in the Action center. The last line is where the "AIR cleaned one device, the user touched three" gap is spotted.
HACKTHESOCLesson 65Defender XDR26 / 51

Automation level decides whether actions wait for you

Full

AIR remediates malicious artifacts automatically, no approval needed.

Semi

Some actions auto-run; others, e.g. in non-temp folders or on core files, need approval.

No automated response

AIR investigates and recommends, but takes no action without a human.

Your job either way: review the graph, approve or reject pending actions, and check AIR covered every affected asset.

Example from the lesson: AIR cleaned one device, but the incident shows the same user signed into three others. That gap is for the analyst to catch.
HACKTHESOCLesson 65Defender XDR27 / 51

Before you approve or reject an AIR action

CheckWhy it matters
Is the file a known business application?Line-of-business tools are a common false positive
How critical is the device?Quarantining a file on a server can break a service
Does the action cover every affected device?AIR scope can be narrower than the incident
Is the evidence tied to this incident's story?Do not approve actions you cannot explain
Approving is an analyst decision with consequences. Rejecting needs a reason in the comments, just like approving.

Device timeline: what happened on a machine

The microscope you reach for after the incident shows which device to examine.

HACKTHESOCLesson 65Defender XDR29 / 51

FIN-LAPTOP-07, second by second

Start from the moment an alert fired, then scroll backwards to what led up to it and forwards to what followed.
HACKTHESOCLesson 65Defender XDR30 / 51

How to read a device timeline

  1. 1AnchorJump to the time the alert fired: 13:00:53, the encoded PowerShell.
  2. 2Go backWhat led here? Word wrote a macro document, then started PowerShell.
  3. 3Go forwardWhat followed? A connection out, a file dropped, a Run key.
  4. 4Note the indicatorsFile names, hashes, the remote IP, the Run-key name.
  5. 5PivotSearch the fleet for each indicator in the hunting tables.
Students tend to read forward from the alert only. The root cause is almost always a few seconds or minutes earlier.
HACKTHESOCLesson 65Defender XDR31 / 51

Three questions the timeline answers

QuestionEvidenceWhat it reveals
How did this get here?WINWORD.EXE spawns powershell.exeMalicious macro: initial access via phishing, execution
What did it do next?Outbound TLS, then update.exe dropped in %TEMP%Command and control and a payload drop
Did it try to stay?New Run key SysHelperPersistence: intends to survive a reboot
The incident tells you that a device was involved; the timeline gives the frame-by-frame proof: patient zero, execution chain, blast radius.
HACKTHESOCLesson 65Defender XDR32 / 51

Reproduce the parent-child chain in Advanced Hunting

  • Same device and a five-minute window around the alert
  • InitiatingProcessFileName is the parent: Word
  • FileName and ProcessCommandLine show what Word launched
The timeline view and this table hold the same events. The query is what lets you repeat the check across every device.
HACKTHESOCLesson 65Defender XDR33 / 51

Each timeline event kind has a hunting table

Event kindAdvanced Hunting tableQuestion it answers
Process: launches, command lines, parent-childDeviceProcessEventsWhat ran, and what launched it?
File: created, modified, deleted, with hashesDeviceFileEventsWhat was dropped or changed on disk?
Network: connections and destinationsDeviceNetworkEventsWho did it talk to (C2, exfil)?

Every detail you note (command line, C2 IP, Run-key name) becomes a hunting term for other devices.

The parent-child relationship in DeviceProcessEvents is the single most valuable feature: it is what exposes Word spawning PowerShell.
HACKTHESOCLesson 65Defender XDR34 / 51

Did any other device talk to the same server?

  • The remote IP from the 13:00:55 timeline row becomes the search term
  • One row per device and process that reached it
  • The earliest FirstSeen may reveal an earlier patient zero
Repeat for the dropped file hash in DeviceFileEvents and the Run-key name in DeviceRegistryEvents. That is how one timeline scopes the whole fleet.

Section 6 of 7

Severity, classification, and closing the loop

An incident is not finished until it is classified and closed.

HACKTHESOCLesson 65Defender XDR36 / 51

Three fields that are often confused

Automated

Severity

Defender's estimate of how dangerous it looks, from its alerts. A triage priority, not a verdict.

Human judgment

Classification

True positive, False positive, or Informational, expected activity.

The specific reason

Determination

E.g. malware, phishing, compromised account, security testing. Records why, for metrics and reporting.

Repeated false positives inform detection tuning. True positives with determinations feed metrics like how many BEC attempts this quarter.
HACKTHESOCLesson 65Defender XDR37 / 51

Incident status values

ValueMeaning
ActiveOpen, not yet worked to conclusion
InProgressActively being investigated
ResolvedClosed with a verdict
RedirectedMerged into another incident
Use the exact enumerated values Defender accepts, not a paraphrase.
HACKTHESOCLesson 65Defender XDR38 / 51

Determinations allowed for each classification

True positive

MultiStagedAttack, MaliciousUserActivity, CompromisedUser, Malware, Phishing, UnwantedSoftware, Other

Informational, expected

SecurityTesting, LineOfBusinessApplication, ConfirmedUserActivity, Other

False positive

Clean (not malicious), InsufficientData, Other

A determination can only be set once a classification is chosen.

True positive with no determination throws away most of the value of closing the incident.

HACKTHESOCLesson 65Defender XDR40 / 51

The closing checklist

  • Every involved device and user remediated, or explicitly assessed as unaffected
  • Any pending AIR actions approved or rejected
  • Classification and determination set
  • A brief comment (and tags) recording what happened and what was done

The incident queue is the SOC's single source of truth: what happened and what we did about it.

Clean closure builds the dataset every future tuning decision, audit and metric depends on.
HACKTHESOCLesson 65Defender XDR41 / 51

A closing comment another analyst can trust

  • What happened, in order, with the evidence named
  • What was checked beyond the first device, and the result
  • Every action taken, so nobody has to redo the work
Illustrative comment for the running example. A good closing note lets an auditor or the next shift understand the case without reopening it.

The incident graph and advanced features

A visual replay of the attack, and the tenant switches that decide how much is done for you.

HACKTHESOCLesson 65Defender XDR43 / 51

Reading the incident graph

  • Nodes and edgesEntities (devices, users, mailboxes, apps) as nodes, connected by the alerts and evidence linking them.
  • Left to rightThe leftmost node is the root cause, the initial access; branches show lateral movement and impact.
  • Select to focusAn alert highlights only its entities; an entity opens a pane (device risk and exposure, user sign-ins).
  • Play backReplay the incident node by node, in the order events actually occurred.
Playback is often the fastest way to brief a second analyst or a manager without them reading every alert.
HACKTHESOCLesson 65Defender XDR44 / 51

  1. 1EmailThe phishing message: the root cause on the far left.
  2. 2User r.katzLinked by the URL click and by the risky sign-in.
  3. 3Device FIN-LAPTOP-07Linked by the PowerShell alert on r.katz's laptop.
  4. 4Remote IP and update.exeEvidence nodes branching from the device: C2 and payload.
Ask the class to point at where containment should start: the device and the user, while the email node tells you who else to check.
HACKTHESOCLesson 65Defender XDR45 / 51

Advanced features: Settings > Endpoints

AIR level

From fully automatic to approval for every action, or off.

Live response

A remote shell on an enrolled device: collect artifacts, run scripts, remediate live.

EDR in block mode

MDE blocks and remediates even when a third-party AV is primary and Defender AV is passive.

Tamper protection

Stops malware or a local admin attacker disabling Defender mid-attack.

Know the switches before you open an incident: they tell you how much work is already done.

Full AIR plus Live Response: incidents arrive largely pre-remediated with rich forensics. Approval-required with features off: much more manual work for the same intrusion.

Key takeaways

  1. 01Defender XDR fuses MDE, MDO, MDI, MDCA and Entra ID Protection signals in one portal, correlated across products.
  2. 02An alert is one detection and only a fragment; its entities are the keys that link it to others.
  3. 03An incident groups related alerts into the attack story, assets and evidence; work the incident queue, not alerts.
  4. 04AIR investigates and remediates automatically or pending approval; review its graph and check its reach.
  5. 05The device timeline reconstructs process trees, files, network, registry and logons back to root cause.
  6. 06Close with status, classification and a specific determination; they power tuning, audits and metrics.

Check your understanding, question 1 of 3

Within two hours, MDO flags a malicious URL click by r.katz, Entra ID Protection flags an unfamiliar sign-in for r.katz, and MDE flags suspicious PowerShell on FIN-LAPTOP-07, where r.katz is signed in. What will you find?

Defender automatically groups alerts that share entities (user, device, file, IP) into one incident, across products. The alerts stay separate detections inside it, and the incident carries a severity aggregated from them.

Check your understanding, question 2 of 3

An incident flags update.exe in %TEMP% on a laptop. You want to establish how the file got there and what launched the chain. Which pivot most directly answers that?

Process events carry parent-child links, so you walk back from the file creation to its writer (e.g. powershell.exe) and its parent (e.g. WINWORD.EXE). Tags classify, logons give context, and network events alone do not show which program acted.
