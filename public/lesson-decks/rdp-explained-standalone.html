Section 1 of 10

What RDP is and why it is used

Remote Desktop Protocol: Microsoft's protocol for full graphical control of a Windows machine.

HACKTHESOCLesson 87RDP explained6 / 60

SSH gives a prompt, RDP gives a desktop

SSH

A text command line to a remote machine, mostly Linux.

RDP

A full graphical desktop: windows and applications mirrored to you, responsive to your keyboard and mouse.

Connect with the built-in mstsc.exe or other clients, enter the address, authenticate with a Windows username and password.
HACKTHESOCLesson 87RDP explained7 / 60

What actually travels over an RDP connection

  1. 1Screen updatesThe server sends the changing parts of the desktop as compressed graphics, not a video stream.
  2. 2Input eventsYour keyboard and mouse actions go back to the server, which runs them on the real machine.
  3. 3Virtual channelsOptional side channels carry clipboard, drives, printers and audio between the two ends.
  4. 4The effectYou operate the remote Windows session as if sitting at it, over one TCP connection.
The desktop runs entirely on the server; only pixels and input cross the wire. That is why a compromised session is the attacker at the real machine.
HACKTHESOCLesson 87RDP explained8 / 60

Legitimate RDP is everywhere

  • Remote administrationIT staff managing Windows servers and desktops without walking to them.
  • Remote workEmployees reaching their office PC or a virtual desktop from home.
  • Servers and jump boxesAdministering Windows servers in data centres and clouds.

High value plus how often RDP is carelessly exposed to the internet make it one of the most attacked protocols.

That high value, combined with how often RDP is carelessly exposed to the internet, makes it one of the most consequential protocols in modern intrusions.
HACKTHESOCLesson 87RDP explained9 / 60

Client and server: who is who

mstsc.exe

RDP client

The machine you sit at. It opens the connection, sends input, and draws the remote desktop it receives.

Remote Desktop Services

RDP server

The target Windows machine. It runs the session, validates the logon, and streams the desktop back.

In an intrusion the attacker's machine is the client and your server is the target: the inbound connection on 3389 is to your server.

Section 2 of 10

How RDP works and its port

Client/server on TCP 3389, and UDP 3389 for performance.

HACKTHESOCLesson 87RDP explained11 / 60

The basic RDP flow

  1. 1ConnectThe RDP client connects to the target on port 3389.
  2. 2NegotiateSession settings including encryption, which can use TLS.
  3. 3AuthenticateWindows credentials, ideally behind Network Level Authentication (NLA).
  4. 4StreamDesktop updates flow to the client, keyboard and mouse input flow back.
Optional features like shared clipboard and drive redirection carry their own security considerations, covered later.
HACKTHESOCLesson 87RDP explained12 / 60

The port and its two transports

TransportPortCarries
TCP3389The core session: setup, auth, screen and input
UDP3389Optional performance path for graphics over good links
HTTPS443RDP tunnelled through an RD Gateway, covered later
TCP 3389 is the one to know. UDP 3389 is a performance add-on; inbound 3389 of either kind to a server is the thing a SOC watches.
HACKTHESOCLesson 87RDP explained13 / 60
RDP is full desktop control over port 3389, gated only by Windows authentication.

That is the whole threat model in one line: if 3389 is reachable and the password is weak, the desktop is one guess away.

Keep this framing in mind through the logging sections: every detection exists to catch someone reaching that gate from the wrong place.
HACKTHESOCLesson 87RDP explained14 / 60

Two settings dominate RDP's safety

Exposure

Is port 3389 reachable from the internet? An RDP port reachable from anywhere is an open invitation.

Authentication

Are NLA and strong authentication, and MFA, enforced? Without them RDP is protected only by a guessable password.

Sessions and logons are recorded in Windows event logs: the raw material for SOC detections.

RDP equals full desktop control over port 3389, gated only by Windows authentication.
HACKTHESOCLesson 87RDP explained15 / 60

Inbound 3389 as the firewall records it

  • A long, high-byte session is an interactive desktop in use
  • Many tiny 2-second sessions from one IP are probing or brute force
  • The destination 10.0.4.15:3389 is your RDP server
Firewall or NetFlow data on 3389 is the outside view that pairs with the Windows event logs later: shape and duration tell real sessions from probes.

Section 3 of 10

NLA and CredSSP: authenticate before the session

One of the highest-value RDP settings a SOC checks.

HACKTHESOCLesson 87RDP explained17 / 60

Without NLA versus with NLA

Without NLA

The server allocates a full session and logon screen before credentials are checked. Thousands of unauthenticated connections can exhaust resources.

With NLA

Authentication moves earlier via CredSSP. No desktop session or logon UI for a connection that never proves who it is.

The exposed logon screen is also extra surface for an attacker to explore or exploit.
HACKTHESOCLesson 87RDP explained18 / 60

How NLA authenticates

  1. 1TLS channel firstEncrypted before any Remote Desktop session logic runs.
  2. 2CredSSP passes credentialsSecurely, inside that encrypted channel.
  3. 3Server validatesAgainst local SAM or Kerberos/AD, without allocating a desktop.
  4. 4Then the sessionOnly after success is the interactive session allocated and streamed.
NLA is a specific, checkable setting: the 'Require Network Level Authentication' policy.
HACKTHESOCLesson 87RDP explained19 / 60

What NLA stops, and what it does not

ThreatNLA onStill possible
Unauthenticated session allocationBlocked: no session until creds passn/a
Resource exhaustion from connectsGreatly reducedVolumetric floods on the port
Password brute forceStill reaches auth, but no desktopGuessing valid credentials
Stolen or stuffed credentialsNo help: they are validFull logon with real creds
NLA is about when authentication happens, not how strong the password is. It does not stop an attacker who already has valid credentials.
HACKTHESOCLesson 87RDP explained20 / 60

The settings a SOC actually checks

  • UserAuthentication = 1 is NLA required: the high-value setting
  • SecurityLayer = 2 forces TLS so the server is authenticated
  • AllowEncryptionOracle = 0 refuses unpatched CredSSP peers
These three values are what an audit or a configuration query reads. A host with NLA off or SecurityLayer not TLS is a finding before any log is pulled.
HACKTHESOCLesson 87RDP explained21 / 60
CVE-2018-0886: the protocol built to protect early authentication could itself be relayed.

A man-in-the-middle relayed CredSSP to run code. Fix = patch plus Encryption Oracle Remediation policy: 'Force updated clients' refuses unpatched peers, 'Mitigated' still connects to them.

Patched March 2018. The policy is the registry value AllowEncryptionOracle. Patching alone is sometimes not enough; unpatched or misconfigured CredSSP is a scan and audit finding.

Section 4 of 10

RDP's three security layers

Why 'encrypted' is not one setting.

HACKTHESOCLesson 87RDP explained23 / 60

The session security layer, negotiated at connect

LayerHow the session is securedVerdict
RDP Security Layer (native)Old RC4 encryption; server not properly authenticated to the clientLegacy and weak: avoid
TLS (SSL)Standard TLS; server certificate the client can validateStrong: preferred
NegotiateHighest layer both support, ideally TLSGood, if it lands on TLS
Native RDP is technically encrypted yet still man-in-the-middleable, because the client has no proof it is talking to the real server. The negotiated layer is visible in the RdpCoreTS/Operational log.
HACKTHESOCLesson 87RDP explained24 / 60

Why native RDP encryption is still man-in-the-middleable

The gap

Native RDP Security Layer encrypts with RC4 but does not prove the server's identity to the client.

The consequence

A machine on the path can pose as the server, decrypt, and relay: encrypted traffic, no proof of who is on the other end.

The fix

TLS adds a server certificate the client validates, so the client knows it reached the real server.

Encrypted is not the same as authenticated. The certificate is what closes the man-in-the-middle door, which is why TLS is preferred.
HACKTHESOCLesson 87RDP explained25 / 60

Two independent hardening knobs

NLA answers when authentication happens. The security layer answers how the session is protected. Both must be set.

Why exposed RDP is so dangerous

A leading entry point for ransomware.

HACKTHESOCLesson 87RDP explained27 / 60

How attackers get in through open 3389

and credential stuffing

Brute force

Millions of guesses across the internet daily. Weak or reused passwords fall quickly. Many ransomware incidents start with brute-forced or purchased RDP credentials.

CVE-2019-0708

BlueKeep

A 'wormable' flaw allowing remote code execution against unpatched systems without any credentials.

Inside, attackers disable defences, steal credentials, move laterally, and deploy ransomware.

Attackers continuously scan the entire internet for open port 3389, then attack what they find.
HACKTHESOCLesson 87RDP explained28 / 60

Brute force versus credential stuffing

TechniqueHow it looks in logsTell
Brute forceA flood of failed logons from one or few IPsMany 4625 then maybe one success
Credential stuffingLeaked user/password pairs tried once eachFew or no failures, then a clean success
Stuffing is quieter than brute force: the valid pair may succeed on the first try, so you see success without the failure flood.
HACKTHESOCLesson 87RDP explained29 / 60

The defensive lessons

  1. 1Never expose RDP directlyPut it behind a VPN, a bastion/jump host, or a Remote Desktop Gateway.
  2. 2Enforce NLA and MFASo a guessed password alone is not enough.
  3. 3Patch RDPClose known vulnerabilities like BlueKeep.
  4. 4Lock out and alertOn repeated failed logons.
Exposed RDP plus weak authentication equals ransomware's favourite front door.

Section 6 of 10

Shadowing, redirection and the RD Gateway

Legitimate admin features whose misuse blends in.

HACKTHESOCLesson 87RDP explained31 / 60

Three features, three security angles

Session shadowing

View or control another active session. Great for IT support; lets a privileged attacker silently watch or hijack a user without their credentials.

Drive and clipboard

Share local drives and clipboard. An attacker can pull files off through the RDP session itself, missed by controls watching only FTP or HTTP.

RD Gateway

Wraps RDP inside HTTPS on 443. Users authenticate to the Gateway, which relays internally. 3389 is never reachable from outside.

With a Gateway you stop seeing inbound 3389 at the perimeter; its own TerminalServices-Gateway log becomes the detection source.

The shared lesson, as with SMB admin shares: compare use of these features against who is supposed to use them, and how.
HACKTHESOCLesson 87RDP explained32 / 60

How an RD Gateway changes what the SOC sees

  1. 1User hits the GatewayThe client connects to the Gateway over HTTPS on 443, not to 3389.
  2. 2Gateway authenticatesIt checks the user and policy, then opens the internal RDP connection on the user's behalf.
  3. 33389 stays internalThe perimeter never sees inbound 3389, so your old detection on it goes quiet.
  4. 4New log sourceThe TerminalServices-Gateway operational log becomes where you watch who connected and from where.
Deploying a Gateway is good security but moves the evidence. If your detections still watch perimeter 3389, retune them to the Gateway log.
HACKTHESOCLesson 87RDP explained33 / 60

What the RD Gateway log records

  • 302 a Gateway connection was authorised: who, from where, to which internal host
  • ClientIP is the real external source, preserved at the Gateway
  • 303 closes the session: pair them to measure session length
This is the detection source once 3389 is no longer at the perimeter. The ClientIP here plays the role the firewall's source IP did before.

Session vs console, and the full RDP Event IDs

RDP sessions do not simply log on and log off.

HACKTHESOCLesson 87RDP explained35 / 60

Console, sessions, and the disconnect trap

  • ConsoleThe session tied to the machine's own keyboard and screen. mstsc /admin attaches to it instead of creating a new one.
  • SessionsEvery other RDP connection gets its own numbered session.
  • DisconnectedClosing the window with X leaves the session running. Reconnecting still requires authenticating again (NLA or logon screen).
Since Vista, services run in Session 0 and the first interactive logon is typically Session 1. /admin was formerly /console.
HACKTHESOCLesson 87RDP explained36 / 60

The three logon types the back half depends on

Security 4624/4625 carry a LogonType number. Three of them do all the RDP analysis.

LogonTypeWhat it meansIn RDP terms
10 RemoteInteractiveA brand-new interactive logon over the networkA fresh RDP desktop session opening
7 UnlockAn existing session was unlocked or reconnectedReconnecting to a disconnected RDP session
3 NetworkNetwork auth with no interactive desktop allocatedA failed RDP guess under NLA, checked before any session
Memorise these three numbers: 10 = new remote desktop, 7 = reconnect/unlock, 3 = pre-session network check. Every event table ahead leans on them.
HACKTHESOCLesson 87RDP explained37 / 60

New session, reconnect, or failed guess

Type 10

New session

A fresh RemoteInteractive logon: a desktop opening for the first time this connection.

Type 7

Reconnect

Returning to a session left disconnected. Re-authenticates, but no new session is created.

Type 3

Failed under NLA

A guess rejected at the network check before any desktop exists, so it logs as Network, not Remote.

This is the bridge between the logon-type numbers and the event-ID table: each number maps to one of these three stories.
HACKTHESOCLesson 87RDP explained38 / 60

Four Security-log events that track RDP sessions

Event IDMeaningDistinct from

A rule that only alerts on LogonType 10 logons opening a new session silently misses an attacker who disconnects and comes back later as 4778 plus a type 7 4624.

Disconnected for three days, back from a new IP

  • No new type 10 session: the return is a type 7 4624 plus 4778

A strong hijacking indicator, visible only because the analyst tracked 4778/4779 and every 4624 logon type alongside 4625.

Contrast with the normal reconnect, which always re-authenticates. Session hijacking skips that step entirely, which is why the 4778 context matters.

The complete RDP event-log map: four channels

Each channel records a different stage of the same connection.

HACKTHESOCLesson 87RDP explained42 / 60

Which channel answers which question

ChannelKey Event IDsWhat it tells you
Security4624, 4625, 4634/4647, 4778/4779Authentication outcome and account; LogonType 10 = RemoteInteractive
RemoteConnectionManager/Operational1149Network-level auth succeeded (valid creds): source IP + username. Not a completed logon
LocalSessionManager/Operational21, 22, 23, 24, 25Session logon, shell start, logoff, disconnect, reconnect

Full channel names are TerminalServices-RemoteConnectionManager, TerminalServices-LocalSessionManager and RemoteDesktopServices-RdpCoreTS.
HACKTHESOCLesson 87RDP explained43 / 60

Walk one connection channel by channel

  1. 1RdpCoreTS131 the connection was accepted at the transport, 140 a bad-credential failure.
  2. 2RemoteConnectionManager1149 the network-level credential check passed: valid creds, source IP and user.
  3. 3Security4624 LogonType 10 the interactive logon completed; 4625 a failed attempt.
  4. 4LocalSessionManager21 session logon, 22 shell start: the desktop is now in front of someone.
One successful RDP logon writes to all four. Correlating them by source IP and time gives a minute-by-minute account no single channel shows.
HACKTHESOCLesson 87RDP explained44 / 60

1149 says valid creds; 4624 says they got a desktop

RemoteConnectionManager

Event 1149

Network-level credential check passed. On modern Windows, written only for valid credentials, never for a failed guess.

Security

4624 Type 10

The interactive logon completed and a desktop opened. This is the confirmation that someone is actually in.

Many 1149 with few matching 4624 Type 10 means many valid authentications that did not all finish a logon: investigate.

The two answer different questions. 1149 is 'the password was right'; 4624 Type 10 is 'they reached the desktop'. Failed guesses are 4625 and 1150, not 1149.
HACKTHESOCLesson 87RDP explained45 / 60
Event 1149 'User authentication succeeded' means the network-level credential check passed, not that the interactive logon completed.

On modern Windows it fires only for VALID credentials, never for failed guesses. So many 1149 from one IP means many successful auths, not a brute force. Confirm with 4624 Type 10.

A classic false friend: the name says 'succeeded' but it marks NLA credential validation, not a finished session. Failed guesses show as 4625 (and 1150), not 1149.

Section 9 of 10

Why RDP matters to a SOC analyst

An RDP logon is someone taking interactive control of a Windows desktop.

HACKTHESOCLesson 87RDP explained48 / 60

What analysts hunt for

  • Brute forceMany 4625: commonly type 3 under NLA, type 10 without it. A type 10 4624 after them is a likely compromise.
  • Internet-exposed 3389A critical finding in itself, flagged as a priority to close.
  • Unusual sourcesRemoteInteractive logon from an odd country, hour or server: context is the red flag.
  • Lateral movementOne internal host RDPing to many, or between machines that never connect.
  • Related indicatorsNew local accounts, defences disabled, RDP right before ransomware.
Hunt type-3 4625 floods that coincide with inbound 3389 traffic, not just type 10. Data sources: Security logs, Terminal Services operational logs, and firewall logs on 3389.
HACKTHESOCLesson 87RDP explained49 / 60

Benign RDP versus a session worth chasing

Usually benign

Matches the baseline of who uses RDP, from where, to what.

  • Known admin, business hours
  • From a management subnet
  • To servers they always use

Worth chasing

Deviations from that baseline, especially after a failure flood.

  • Foreign IP or odd hour
  • Built-in Administrator
  • Internal host RDPing to many
The judgement is almost always baseline versus deviation, not the presence of RDP itself. Context is the alert, not the protocol.
HACKTHESOCLesson 87RDP explained50 / 60
Baseline who uses RDP, to which machines, from where. Alert on the deviations.

The brute force, the success after many failures, the foreign source, the internal fan-out.

Combined with the rule that RDP never faces the internet unprotected, this is one of the most impactful ways a SOC stops ransomware before it starts.
HACKTHESOCLesson 87RDP explained51 / 60

A fast triage runbook for an RDP alert

  1. 1Source and directionIs the source external or an unusual internal host? External to 3389 is already a finding.
  2. 2OutcomeDid it reach 4624 Type 10, or only failures? A success after failures is the priority.
  3. 3Account and timeWhich account, built-in Administrator? Business hours or 2 AM?
  4. 4What happened nextCheck 4688 process events after the logon for dumping, disabled tools or staging.
This ordering gets you to escalate-or-not quickly: get in, from where, as whom, then what they did.

Worked example: RDP brute force in event logs

Forty minutes of failures, one success, then a command prompt.

HACKTHESOCLesson 87RDP explained53 / 60

From 4625 flood to cmd.exe

  • Type 3 failures (NLA on) cycling account names; confirm RDP via inbound 3389
  • Type 10 4624 from the same source: a real desktop session, Administrator fell
  • 4688 cmd.exe from explorer.exe: the attacker is actively working
With NLA the password is checked before any session exists, so failures log as type 3, which can also be SMB. Match them to inbound port-3389 connections from the same IP. Same shape as the SSH auth-log example.

The single type 10 4624 among hundreds of type 3 4625 is the pivot from attempt to compromise. Everything after it is post-exploitation.

Questions this sequence demands

  1. 1External or internal source?If external, RDP is internet-reachable: pull it behind a VPN or Gateway now.
  2. 2Should Administrator RDP?Best practice disables direct RDP for built-in admin accounts.
  3. 3What did cmd.exe do?Check later 4688s for credential dumping, disabled security tools, ransomware staging.
This is precisely the entry-point moment described as ransomware's favourite door.

Key takeaways

  1. 01RDP gives full Windows desktop control over TCP 3389; SSH gives a text shell, RDP an interactive desktop.
  2. 02NLA with CredSSP authenticates the user first; the TLS security layer authenticates the server. Enforce both.
  3. 03Internet-exposed 3389 is a top ransomware entry: brute force and BlueKeep. Use VPN or RD Gateway, NLA, MFA, patch.
  4. 044625 floods (type 3 under NLA) then a type 10 4624 is a brute force success; a 4778 plus type 7 4624 marks a reconnect.
  5. 05Event 1149 = successful network-level auth (valid credentials), not a finished logon and never a failed guess; confirm with 4624 Type 10.
  6. 06Shadowing, drive and clipboard redirection are legitimate tools that also enable hijacking and exfiltration.
