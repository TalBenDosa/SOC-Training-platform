Section 2 of 8

NTLM: the challenge and response

Three messages, and the password itself never crosses the network.

HACKTHESOCLesson 59Kerberos vs NTLM10 / 63
In NTLM the password never crosses the network.

The client proves it knows the password by doing maths on a random challenge with the NT hash, a value derived from the password.

Hold onto this: it is clever, and it is also the root of NTLM's biggest weakness, as the next slides show.
HACKTHESOCLesson 59Kerberos vs NTLM11 / 63

Who does what in an NTLM logon

  1. 1NegotiateThe client contacts the server: I want to access you, here is who I am.
  2. 2ChallengeThe server replies with a random number, a challenge (nonce).
  3. 3ResponseThe client encrypts the challenge with the NT hash derived from the password and sends it back.
  4. 4VerificationThe server forwards both to a Domain Controller over Netlogon. The DC checks it: Event 4776.
The server usually cannot check the answer itself because it does not store everyone's password. That is why the DC is consulted.
HACKTHESOCLesson 59Kerberos vs NTLM12 / 63

What the DC records: Event 4776

  • Logged on the Domain Controller, which did the checking, not on the server
  • Source Workstation says where the attempt came from
  • 0x0 = success; a wrong password shows as 0xC000006A
Illustrative values in the real 4776 field layout. This one event is the NTLM trail an analyst reads most.
HACKTHESOCLesson 59Kerberos vs NTLM13 / 63

Three properties that make NTLM risky

The hash is the credential

The hash alone is enough to authenticate. Steal the NT hash from memory and you are the user: Pass-the-Hash.

No mutual authentication

The server proves nothing about itself. An attacker in the middle can forward your response elsewhere: NTLM relay.

No built-in third party

Unlike Kerberos, no trusted authority is part of the exchange; the DC only checks the answer.

NTLM survives everywhere as a fallback, which is exactly why analysts watch it.

These weaknesses are why Microsoft moved to Kerberos as the default.
HACKTHESOCLesson 59Kerberos vs NTLM14 / 63

Pass-the-Hash, as the logs see it

  1. 1Hash stolenAn attacker on one compromised machine takes a user's NT hash from memory.
  2. 2Hash replayedFrom other machines, the attacker answers NTLM challenges using that hash.
  3. 3DC says yesThe maths is correct, so the DC records a successful 4776.
  4. 4The tellThe same account succeeding from workstations it never uses, over NTLM.
No password was ever known or cracked. Section 6 shows this exact trace for a service account.

Kerberos: tickets from a trusted authority

The KDC on every Domain Controller issues time-limited, signed tickets.

HACKTHESOCLesson 59Kerberos vs NTLM16 / 63

Kerberos vocabulary before the flow

  • KDCKey Distribution Center: the trusted authority, running on every Domain Controller.
  • ASAuthentication Service: the half of the KDC you prove yourself to at logon.
  • TGSTicket Granting Service: the half that issues tickets for specific services.
  • TGTTicket Granting Ticket: the master pass, readable only by the KDC.
  • SPNService Principal Name: a service's name, such as cifs/fileserver01.
  • Service ticketA time-limited ticket for one named service.
Six terms carry the whole Kerberos story. The event IDs map onto them one to one.
HACKTHESOCLesson 59Kerberos vs NTLM17 / 63

Log in once, then trade tickets

The KDC has two halves: the Authentication Service (AS) and the Ticket Granting Service (TGS).

  1. 1Get a TGTProve identity to the AS with a timestamp encrypted by your password-derived key. Receive a TGT: Event 4768.
  2. 2Ask for a service ticketPresent the TGT to the TGS for a service named by its SPN. Receive a service ticket: Event 4769.
  3. 3Present it to the serviceThe file server trusts the KDC's stamp; it never contacts the DC to verify you in real time.
  4. 4Mutual authenticationKerberos can also prove the server's identity to the client.
The encrypted timestamp is why Kerberos needs clocks roughly in sync, within about five minutes.
HACKTHESOCLesson 59Kerberos vs NTLM18 / 63

The ticket design is powerful, and attackable

Strengths

Services do not need to validate each login against the DC on the spot.

  • The KDC vouches for everyone
  • Tickets are time-limited
  • Mutual authentication stops impostor servers

Attacks

Each leaves distinct traces, which is why analysts learn the ticket flow.

  • Kerberoasting: crack service tickets (4769) offline
  • Pass-the-Ticket: reuse a stolen ticket
  • Golden Ticket: forge a TGT with the KDC's key
Kerberoasting is the one you will meet most in a SOC; the event pattern for it comes in section 6.

Three contrasts worth a second look

  • Mutual authenticationNTLM never proves the server's identity, so credentials can be relayed. Kerberos verifies both directions.
  • Tickets vs the hashIn NTLM the hash is the reusable credential. Kerberos tickets expire, though a stolen or Golden Ticket is still dangerous.
  • Clock dependencyBadly skewed clocks make Kerberos fail and quietly fall back to NTLM, with security consequences.
The quiet fallback matters: an environment that drifts into NTLM loses mutual authentication without anyone noticing.
HACKTHESOCLesson 59Kerberos vs NTLM25 / 63

How clock drift quietly weakens a domain

  1. 1Clocks driftA client ends up more than about five minutes off the DC.
  2. 2Kerberos failsIts timestamps stop replay, so the KDC rejects it: result code 0x25 (skew).
  3. 3Windows falls backThe logon silently retries over NTLM.
  4. 4Protection is lostNo mutual authentication; the hash is the credential again.
Nobody notices because logons still work. This is why NTP health is a security concern, not just an operations one.

When Windows uses which, and the SOC angle

Windows chooses automatically. Knowing the rule tells you which protocol should appear where.

HACKTHESOCLesson 59Kerberos vs NTLM27 / 63

Kerberos by default, NTLM as fallback

Kerberos when

This covers the majority of normal domain activity.

  • The machine is domain-joined
  • It can reach a Domain Controller
  • It connects to the target by hostname (SPN lookup)

NTLM when

Kerberos cannot apply.

  • Connecting by IP address (no SPN)
  • Workgroup machines, local-account logins
  • Legacy systems or apps that only speak NTLM
  • No DC reachable, or clocks too far out
The IP-address case is the one attackers exploit on purpose, which leads directly into the next slide.

The protocol mix in your logs tells a story

  • Spike in 4776Can mean brute force or password spray, or Pass-the-Hash, especially where the user would normally use Kerberos.
  • NTLM where Kerberos is expectedAttackers force NTLM (e.g. by IP) for relay and pass-the-hash. An admin on NTLM to a server it reaches by name deserves a look.
  • Many 4769s from one accountTickets for many services in a short time: the classic Kerberoasting pattern.
  • Odd 4768s or ticket useUnusual TGT requests, or tickets used from unexpected hosts, can indicate Pass-the-Ticket or a forged ticket.

You do not need every cryptographic detail. Know which protocol belongs where, and pull the thread when the wrong one shows up.

NTLM relay and downgrade: detection and hardening

No mutual authentication makes NTLM relayable. Spot the coercion, apply the controls.

HACKTHESOCLesson 59Kerberos vs NTLM40 / 63

Why NTLM can be relayed and Kerberos resists it

NTLM response

Not bound to any target. Valid anywhere, because nothing ties it to the server you meant to reach.

Kerberos service ticket

Encrypted for one named service, its SPN. Forwarded elsewhere, it is useless.

This is the 'no mutual authentication' property from section 2, turned into an attack.
HACKTHESOCLesson 59Kerberos vs NTLM41 / 63

How a relay works in principle

  1. 1Lure the victimPoison name resolution (LLMNR/NBT-NS/mDNS spoofing) or coerce auth (e.g. PetitPotam) so a request lands on the attacker.
  2. 2Victim authenticatesThe victim's NTLM response goes to the attacker.
  3. 3Forward itThe attacker passes the material to a different server and is accepted as the victim.
  4. 4Why it worksNothing tied the response to the intended destination. A Kerberos service ticket is encrypted for one SPN.
This is why Kerberos resists relay: its ticket is bound to one named service.

Guessing, spray or enumeration? Read the code pattern

Password guessing

Many 0x18 failures against one account.

Password spray

4771 with 0x18 spread thinly across many valid accounts from one source, each tried once or twice.

Username enumeration

Many 0x6 failures across many names: those accounts do not exist at all.

A spray from a guessed user list shows both: 0x6 for its misses, 0x18 for the real accounts it hit.

The same failure code means different things depending on how it is spread across accounts.

Key takeaways

  1. 01NTLM is a client-server challenge-response (DC verifies, 4776); no mutual auth, and the hash is the credential.
  2. 02Kerberos: authenticate once for a TGT (4768), trade it for service tickets (4769); mutual auth, needs synced clocks.
  3. 03Windows uses Kerberos when domain-joined and connecting by hostname; it falls back to NTLM by IP, workgroup, legacy or no DC.
  4. 04NTLM where Kerberos is expected, 4776 spikes, and many 4769s from one account point to PtH, spray and Kerberoasting.
  5. 05Rate, target diversity and deviation from normal turn routine authentication events into an attack timeline.
  6. 06RC4 (0x17) tickets, 0x18 spread across valid accounts, 0x6 enumeration and requests missing from the DC are key signals.

An attacker steals a user's NT hash from memory and authenticates to a file server as that user without ever learning the password. Which protocol design makes this Pass-the-Hash possible, and why?

In NTLM the hash is effectively the credential. A service ticket uses the service account's key, member servers forward the response to a DC (4776) rather than storing hashes, and NTLM never sends the plaintext password.

One user account generates Event 4769 for dozens of unrelated services, all within two seconds and all successful. What should you most suspect?

Dozens of SPNs in seconds is the Kerberoasting shape. A spray shows as 4771 failures with 0x18, Overpass-the-Hash yields a TGT (4768), and real SSO produces a few 4769s spread over minutes.

Many 4768 failures with result code 0x6 (KDC_ERR_C_PRINCIPAL_UNKNOWN) appear across dozens of different account names in a short window. What does this most likely indicate?

0x6 means the name does not exist. A spray against real accounts shows 4771 with 0x18 spread thinly; clock skew is 0x25 and expired passwords are 0x17.
